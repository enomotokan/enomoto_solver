# greenbea 反復#13: 改善見送り(5b)

対象: NETLIB `greenbea`(runtime段、`select_problem.py` 選定、ours/highs比 43-48x、93問題中最悪)。
起点: `main` = f6a8409619acd4d3e5a6f44c99a144d35542ae0a。
分析: `analysis/greenbea_20260921_205039.md`(fable-bottleneck-analyst、model claude-fable-5-1)。
実装・検証: general-purpose subagent(詳細は下記コミット参照)。
未採用PR: [#13](https://github.com/enomotokan/enomoto_solver/pull/13)(`claude/greenbea-20260921_205039`、監査用に残し、マージせずクローズ)。

## 分析で判明した主因

反復#9-#12は「拡張双対の M 側追跡の設計ギャップ」を主因として分析していたが、
反復#13の計装ベース分析でこれは症状であり、真因はより上流の単一の事故だと判明した:
`src/simplex/extended_dual.rs::solve_lp_dual_extended` で、BFRT が候補列のフリップを
`nb_status` に確定させた**後**にピボットの `update_verify` が行われる。verify が
不一致(iter 6650, alpha_q=-1.54e-8 vs alpha_full[r]=-9.71e-9, 37%不一致)でピボットを
破棄する際、**確定済みのフリップ22本は巻き戻されない**(既存コメントは「フリップは
独立した退化ステップなので不要」と主張するが、ratio=0 の候補にしか成り立たない)。
d_j 最大 2.45e7 の列が Upper(M側)に置かれたまま双対ステップが起きないため、
その瞬間に24列が双対不能(違反合計2.37e8)になる。以後 ~6,000 反復を双対不能のまま
走り、実行不能行プールが 225→1,051 に膨張、後始末に残り15,000反復を要する。
健全経路(presolveのparallelcolsを無効化して同じ事故を回避した対照実験)は
11,270反復・5.1sで正答するのに対し、main は27,654反復・14.6s。詳細は分析ファイル参照。

## 実装した修正(`solve_lp_dual_extended` 内、4点セット)

1. 破棄時に `sorted[..best_idx]` のフリップを巻き戻す。
2. 直前反復で破棄した行と同じ行への再挑戦は `update_count()==0` でも verify する
   (`perold` 由来の既存ゲートは維持したまま、破棄直後の行だけ狭く例外を追加)。
3. M幅の極小ピボット(`|alpha| < 1e-7` かつ行の slope が雑音域)しか使えない行は、
   ピボットせず stored `x_b_slope[r]` を0にスナップする。
4. `Infeasible` 判定前に双対不能な非固定列が残っていないか確認し、あれば修復を
   試みる(セーフティネット、最大8回)。

## 検証結果

- `cargo test --release`: 171 passed, 0 failed(既存テスト全通過)。
- `python -m pytest -q`: 20 passed。
- 対象バグ自体は修正できている: `ENOMOTO_DEBUG_EXT_DUAL_CHECK=1` で全反復を通じて
  双対実行可能性違反ゼロを確認(baselineの iter 6650, 22列, 2.45e7 の破綻が消えた)。
- 93問題中92問題は正答性・実行時間とも退行なし(>10%の時間退行はゼロ、当セッション内で
  再計測したfreshベースラインと比較)。

### しかし greenbea 自身が悪化(改善基準を満たさない)

| | main(このセッションで再計測) | 修正版 |
|---|---|---|
| 主ループ反復数 | 27,653 | 27,440 |
| 実行時間 | 14.69 s | 17.62 s(悪化) |
| 目的値 | -72555248.1298(HiGHS一致、相対誤差2e-16) | **-72465273.0169(相対誤差1.24e-3、誤答)** |
| 経路 | `solve_lp_dual_extended` が Optimal を返す | 特異基底 → BIG_Mフォールバックへ転落 |

原因: 修正後の軌跡が、同ファイル内の姉妹関数 `polish_with_true_bounds`
(~4350行目、今回のスコープ外)に渡る最終基底を変える。この関数は
`solve_lp_dual_extended` と全く同じ「破棄時フリップ非巻き戻し」パターンを
独自に持ち、かつ `pivot_grossly_inconsistent` 相当のガードが一切ない。
修正後の軌跡ではここで verify 不一致(alpha_q=-1.86e-9 vs alpha_full[r]=6.4e-16)
が起き、続く refactorize が特異基底を検出して `None` を返し、BIG_M
フォールバックに転落して誤答する。反復#12 が確認した「フリップ巻き戻しのみでは
不十分(M側解消が遅れ最後に特異基底に落ちる)」というプロトタイプの結論と
本質的に同じ壁に、別の関数を経由して再度当たった形。

対象問題(greenbea)自身が正答性・実行時間ともに main より悪化するため、
ループの改善基準(runtime段: ours/highs比の有意な改善、かつ全問題への
退行がないこと)を満たさない。**5b: 実装は main へマージしない。**

## 次回への申し送り

- `polish_with_true_bounds` にも同じロールバック(+可能なら粗ピボットガード)を
  実装するか、`solve_lp_dual_extended` 側で脆い基底を `polish_with_true_bounds`
  に渡さない設計にする必要がある。両関数を同じ反復でセットで直すのが筋が良さそう。
- 修正自体(`solve_lp_dual_extended` 側)は対象バグを正しく直しており、他92問題には
  無害だったので、次回この2関数をセットで直せば採用できる可能性が高い。
  実装の全文は不採用PR #13(ブランチ `claude/greenbea-20260921_205039`)に残っている。
- `greenbea` の `consecutive_failures` は本反復で3(上限)に到達するため、次回選定
  (`select_problem.py`)では自動的に除外される。もし次回また runtime 段で
  greenbea 以外に大きなギャップがなければ `exhausted` 相当の扱いになりうる点に注意。
