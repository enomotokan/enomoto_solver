# 反復#9(greenbea, runtime tier): 改善見送りの記録

- 選定理由: `scripts/select_problem.py` 出力 "ours 10.6095s vs highs 0.2401s (ratio 44.19x)"(93問題中最悪、correctness/accuracy段は該当なし)。
- 分析: `analysis/greenbea_20260921_140700.md`(fable-bottleneck-analystによる)。

## 結論

fable-bottleneck-analystの分析により、この44倍ものours/highs比の主因は以下と判明した。

1. **主因(反復数、上限70-85%)**: 拡張双対法が原問題の上限無限側の列(greenbeaでは5,012列)を「M側」タグで管理し、1列ずつ人工的に解消していく設計になっているが、BFRT(bound-flip ratio test)のフリップが列をM側へ**戻す**回数(`m_enter_via_flip=10205`)が、419e62a時点(511)の20倍に増えている。M側3,569列の解消に26,000反復かかり、途中で進捗が逆行する(iter 8000で実行不能行プールが286→975に跳ね上がる)。HiGHSはこの状況を双対フェーズ1(人工的な±1の箱で通常のフェーズ2反復を回す設計)で処理しており、本ソルバのM追跡方式とは根本的に異なるアプローチ。
2. **副因(22.7%)**: 基底の悪条件化(FT更新後の残差がescalation上限1e-4を超え続け、217回の再分解のうち93回は直前の再分解から10反復以内)により再分解が頻発し、1回あたりのコストも418e62a比+77%(5.3ms→9.4ms)に増加している。

いずれも「反復#7時点でのgreenbeaの状態(2.77-2.80s、正しく最適解に到達)」から、リポジトリ所有者による直接コミット群(PR#8のマージ、および7baad18ベースの古いpresolve拡張の再合流)を経て生じた設計上のギャップであり、398aed9自体は無関係(398aed9が触った拡張双対のslope丸めは、この状態下で発生していた偽infeasible/誤った最適値を防ぐ役割を果たしており、これを元に戻すとむしろ正答性が壊れる)。

## この反復で修正を見送った理由

分析が提示した改善候補は以下の3つだが、いずれも今回のループの「変更は最小限にし、既存のアーキテクチャ・APIを壊さない」という原則、および「他の92問題に退行がないこと」という前提条件に照らして、この1反復内で安全に実装・検証しきれないと判断した。

1. **M側列の解消をM追跡から双対フェーズ1へ再設計する**(効果見積もり最大70-85%): 拡張双対法のコア設計そのものの変更であり、全93問題の解法経路に影響する。設計判断が必要な規模で、1反復で安全に検証できる変更ではない。
2. **再分解単価の削減**(効果見積もり上限22.7%、現実的には5-10%): `refactorize`後のフル再同期(`compute_rhs_affine`+2回のsolve+`InfeasibleRows::rebuild`+`fresh_d_into`)を「ドリフトした行だけ」に絞る案があるが、該当コードのコメント自身が「再分解は多くの行の実行可能性を一度に変えうるため、インクリメンタルな`set`呼び出しでは追いつかない」とフル再同期を意図的に選んだ理由を明記しており、範囲を狭めることは新たな正答性バグを持ち込むリスクがある。狭める根拠となる具体的な安全な条件を今回の分析だけでは確立できなかった。
3. **snapを格納値の書き換えから比較時の許容へ移す**: 目的は速度ではなく脆さの緩和で、効果不明(経路が変わるため)。

## 対応

- ソースコードの変更は行っていない(破棄すべき変更なし)。
- `scripts/benchmark_results.json` は変更していない(既存の93件完全なデータのまま有効)。
- `scripts/loop_state.json` の greenbea `consecutive_failures` を 0→1、`attempts` を 6→7 に更新し、本反復の分析結果へのポインタを記録する。
- 次回以降greenbeaが再選定された場合(あと2回まで)、上記候補1・2のいずれかに的を絞った専用の反復として取り組むことを推奨する。特に候補1(双対フェーズ1化)は`docs/highs_dual_simplex.tex`を参照した設計検討から始めるべき。
