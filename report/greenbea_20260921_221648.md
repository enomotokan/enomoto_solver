# 反復#14: greenbea(runtime段)は改善見送り

対象: `greenbea`(runtime段、ours/highs比 43-48x、5回目の連続再選定)。前回反復#13の
申し送り(`scripts/loop_state.json` の `note_manual_reset`)に基づき、不採用PR #13
(`solve_lp_dual_extended` のBFRTフリップ巻き戻し等)を安全に採用可能にするため、
姉妹関数 `polish_with_true_bounds` に同型の修正を実装できるか分析した。

## 分析結果

fable-bottleneck-analyst サブエージェントによる分析: `analysis/greenbea_20260921_221648.md`。

1. **申し送りの前提は半分誤りだった**: `polish_with_true_bounds` は構造的には
   「BFRTフリップ確定→verify→破棄時に巻き戻さない」という同型パターンを持つが、
   greenbeaで実際に起きた誤答の機序は**フリップ非巻き戻しではない**。真因は、
   polishのchuzcが数値的な丸め残差(`-2^-29`、FTRAN側は正確に0)を幅∞・ratio 0の
   候補として受理し、verify破棄後の再試行を `update_count()==0` ゲートで無検証の
   まま確定させること。主ループが持つ「破棄した(q,r)の行単位禁止リスト」
   (`discard_banned_cols`)がpolishには存在しないのが根本原因。
2. **最小修正(禁止リストの移植のみ)で正答**: `-72555248.12984587`
   (HiGHSと全桁一致)。主ループの完全ミラー(巻き戻し+粗不一致+再verify+禁止)も
   同じビット結果になるが、禁止リスト単体で必要十分と確認された。
3. **しかし実行時間は改善しない**: PR #13(主ループ修正)を当てても主ループの
   反復数は 27,653 → 27,440(-0.8%)しかほぼ変わらず、greenbea自身の実行時間は
   main 10.71/11.14s に対し結合修正後も10.75/10.94sとノイズ内の差でしかない
   (HiGHS 0.18-0.26s)。反復#13分析が見積もった「事故コスト約9秒(65%)」は、
   この修正では回収されないことが実測で判明した。
4. **93問題全数(計装ビルドでの検証)**: PR #13 + polish最小修正で93/93が
   目的関数値・ステータスともmainと一致(相対差 ≤ 1e-6)。反復数が変化したのは
   greenbeaとwood1p(main自身の既知の非決定性)のみ。正答性・頑健性の観点では
   安全に採用可能と確認されたが、runtime段の選定基準(ours/highs比の有意な改善)
   を満たさない。

## 判定: 5b(改善なし)

docs/loop-design.md ルール4により、runtime段で選定された問題の「改善」は
実行時間の有意な短縮のみを基準とする。今回発見された修正は正答性・頑健性上は
価値があるが、選定基準である実行時間を改善しないため、5bとして扱う。
ソースコードの変更は一切行っていない(分析はworktree内のみで実施、
リポジトリ本体は無変更)。`benchmark_results.json` はコード変更がないため据え置き。

## 次回への申し送り

- `polish_with_true_bounds` に禁止リスト(`discard_banned_cols`相当)を移植する
  変更自体は、正答性・頑健性のための独立した価値のある修正として今後
  correctness/accuracy段またはメンテナンスの機会に検討する余地がある
  (現状mainでこのバグが発火する問題は0/93、polishが1反復でも回るのは
  dfl001とgreenbeaのみで、現在は潜在バグ)。
- greenbeaの43-48倍差の主因(反復#9で特定した「M側追跡の設計ギャップ」、
  反復#13で特定した「フリップ確定後のピボット破棄で双対実行可能性が破綻」)は
  未解決のまま。反復#13分析の§6.2(本体側の設計変更、5項目)が依然として
  最有力の方向性だが、1反復で安全に検証しきれる規模ではないとの結論が
  反復#9,#11,#12,#13,#14の5回にわたり繰り返し出ている。
- consecutive_failuresが3(上限)に近づいている。次回選定でgreenbeaが
  再選定されない場合、`scripts/select_problem.py` の次点候補
  (fffff800, 80bau3b, stocfor2, woodw, ganges等、いずれもratio 4-5倍程度)に
  移ることになる。
