- 分析: `analysis/greenbea_20260921_021218.md`(fable-bottleneck-analyst)

## 何が起きたか

原因は特定できた(分析ファイル参照)。要約:

1. 誤判定サイトは `src/simplex/extended_dual.rs` の BFRT 使い切り分岐
   (`site=bfrt_exhausted`、反復4715、4回の実行すべてで同一)。
2. 機序は**許容誤差の不整合**。`Affine1::cmp_lex` の base 比較は絶対 1e-9 で
   行われるのに、同じループは再分解間の `x_B` ドリフトを `XB_DRIFT_TOL_MAX=1e-4`
   まで許容している。FT更新47回時点の偏差 `base=3.0e-7` は誤差であり、
   再分解すると厳密に `-0.0`(反転容量がちょうど覆う)。

これに対し2つの修正を実装した(検証用ブランチのコミット参照):

- **修正1**: 更新済みLUからは `Infeasible` を宣言せず、再分解して同じ反復を
  やり直す(両方の宣言サイト)。→ 反復4715の偽 infeasible は消えた。
- **修正2**: 停滞検出を「直前の反復と同数」から「最良値を更新しない」に変更し、
  上限を `MAX_ITERS/4` で打ち切る。従来の `4*stall_limit = 20*m` は m>1000 の
  問題では `MAX_ITERS=20000` を超えており**原理的に発火できなかった**。さらに
  greenbea は反復8000以降、実行不能行数が 248↔249 で振動するため、等値判定では
  カウンタが2反復ごとにリセットされ Bland 規則が発動しなかった。→ 発動するようになった。

## なぜ改善と認めないか

修正1+2の後も拡張法は反復予算を使い切って `None` を返し、古典 `BIG_M=1e7`
フォールバックに落ちる。greenbea の真の最適解は `x_4180 = 3.3e8`,
`x_4175 = 2.3e8` と `BIG_M` を大きく超えるため、フォールバックは実行可能領域を
切り落とした別問題を解いてしまい、**`optimal` と称して誤った目的関数値
-72465273.02(真値 -72555248.13、相対誤差 1.24e-3)を返す**。

つまりこの修正は「大声で誤る(infeasible)」を「黙って誤る(誤った optimal)」に
変えるだけで、しかも 1.92秒 → 28.3秒 と15倍遅い。後者の方が危険であり、
改善ではなく退行と判断した。

反復予算を10倍(200,000)にする実験も行ったが、500秒でも収束しなかった
(Bland 規則下の前進が遅すぎる)。この方向は行き止まりである。

## 次に何をすべきか(次回反復への申し送り)

分析ファイル §6 の優先順に従うのが妥当:

1. **BIG_M フォールバックが誤った optimal を返すのを止める**。`|x_j| ≥ BIG_M*(1-1e-6)`
   の変数があれば `optimal` と報告しない。ただし現在の `Status` は
   Optimal/Infeasible/Unbounded の3値しかなく、新しい状態(数値的失敗)の追加は
   Python 側まで波及する API 変更になる。これは greenbea 単体の問題ではなく、
   フォールバックに落ちる全問題に共通の安全性問題である。
2. `Affine1::cmp_lex` の slope 側固定下限(1e-9)の設計見直し。固定下限では
   真の微小 slope(3.3e-10)と雑音(3.6e-19)を分離できない。分析 §6.3 の
   (i) 固定評価点 M* での数値比較、(ii) 論文 §4.2 の S 制限、が候補。
3. 修正1(更新済みLUから infeasible を宣言しない)自体は原理として正しく、
   単独では副作用も確認されていない。上記1が入って「誤った optimal」を
   塞いだ後であれば、単独で main に入れる価値がある。
