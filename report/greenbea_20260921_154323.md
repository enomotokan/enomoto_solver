# 反復#11(greenbea, runtime tier): 改善見送りの記録

- 選定理由: `scripts/select_problem.py` 出力 "ours 10.0609s vs highs 0.2315s (ratio 43.46x)"(93問題中最悪、3回連続で再選定)。
- 分析・プロトタイプ検証: `analysis/greenbea_20260921_153000.md`(fable-bottleneck-analystによる)。

## 試みたこと

反復#9で特定された44倍差の主因(拡張双対のM側追跡でBFRTのフリップが列をM側へ戻す回数`m_enter_via_flip`が418e62a比20倍)について、今回は分析に留めず、**タイブレーク(同点候補の優先順位)だけを変える**という最小リスクの介入を4変種プロトタイプし、worktree上で実測検証した。

## 結論: 見送り

- BFRTの候補比較を `(ratio, j)` から `(ratio, m_land, j)`(M側に戻らない候補を同点内で優先)に変えるだけの変更を4変種試したが、**いずれもgreenbeaで正答性が壊れた**(目的値がHiGHSと相対誤差1.2e-3で不一致、またはmax_iters/特異基底経由でBIG_Mフォールバックに落ちて誤答)。
- 詳細分析の結果、「20倍増」の実態はタイブレークの守備範囲外だった: 実際にM側へ戻る10,205回のうち、真に同点(ratio=0の双対退化)で戻す/戻さないが選べるケースは20.6%(2,098回)のみで、残り79%は本当にratioが小さい(＝正しい)候補として戻っている。タイブレークを変えても届かない領域が大半であり、届く範囲を変えると別の経路(容量の埋め方)が変わって不正解に転落した。
- 他13問題(greenbeb, pilot系列, 25fv47, degen3等)ではプロトタイプは完全にno-op(ビット同一)だったため、この経路の脆さはgreenbea固有。全93問題のフルベンチマークは、対象問題自体が誤答になった時点で不採用が確定したため実施していない。

## 対応

- ソースコードの変更は行っていない(worktree内のみで検証、リポジトリ本体は分析ファイルの追加のみ)。
- `scripts/benchmark_results.json` は変更していない(既存の93件が引き続き有効)。
- `scripts/loop_state.json` の greenbea `consecutive_failures` を 0→1 に更新。
- 分析が提示した残る改善候補(いずれも今回より大きい設計変更が必要):
  1. `w_r.slope` の雑音判定を比較時許容に移す(iter 6650型の巨大フリップを抑制、リスク中)
  2. ratio=0同点クラスでのM幅フリップ容量の扱いをHiGHS型双対フェーズ1に再設計、またはM側に「戻す」候補が出た時点でk_starで止める(効果上限70-85%、リスク高)
  3. BIG_Mフォールバックの安全策(本反復の4変種はいずれもこの経路を踏んで誤答を返しており、リスクが再確認された)

次回greenbeaが選定された場合(あと1回まで、consecutive_failures上限3)、候補2の本格的な設計検討(docs/highs_dual_simplex.tex参照)から着手することを推奨する。
