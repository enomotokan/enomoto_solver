## 実装の概要(worktreeブランチに残存、mainへは未マージ)

`src/simplex/lu.rs` の `FtLu` に決定的なtickカウンタ(`tick: Cell<u64>`、R/U/U^T段の処理非零数・
L段のreach集合サイズを積算)と `build_tick`(HiGHSの式 `80*m + 60*(l_nnz+u_off)` をそのまま採用)を追加し、
`src/simplex/extended_dual.rs` の主ループと `polish_with_true_bounds` の両方に
`update_count >= 50 && tick >= FACTOR * build_tick` で再分解する新トリガー(`REFACTOR_CAUSE_CLOCK`)を追加した。
壁時計ではなく決定的カウンタを使っており、この設計判断自体は分析の推奨通りで妥当。
`FACTOR` はtick単位で1〜100を24問題セットで再較正し `16` を採用(実装エージェントの報告)。

worktreeパス: `.claude/worktrees/agent-a964d0008ef4d7b59`(このセッション終了後に削除予定)。

## 原因の推測(次回への申し送り)

分析(`ft_refactor_trigger_20260922_040850.md`)自体の原因特定(再分解トリガーがコストを見ていない)は
妥当で、対象問題(stocfor2/80bau3b/bnl2/greenbea/degen3/d2q06c等、鎖長が支配的な問題)では
実際に改善している(個別確認はしていないが、実装エージェントの報告と整合する範囲)。

問題は `FACTOR=16` という単一の全問題共通定数が、**鎖長が既に短く再分解コストの方が相対的に高い
問題群**(maros-r7・wood1p・fit2p・fit2d、いずれも既存トリガーでは再分解回数が少なかったと推定される)
に対しては再分解を不必要に増やし、正味で悪化させている可能性が高い。実装エージェントは24問題の
集計値だけでFACTORを選び、かつ検証段階でも一部の問題(fit2d・wood1p・maros・sctap2・pilot4)を
確認せずに「10%以内」と結論した。次回この項目に再挑戦する場合:

1. 93問題全数(24問題の部分集合だけでなく)でFACTORをスイープし、個別問題の退行を確認すること。
2. 単一のグローバルFACTORではなく、`build_tick`(=再分解コストの推定値)自体が問題ごとの再分解単価差
   (本分析§4で判明済み、HiGHS比3〜25倍)を反映しきれていない可能性があるため、`build_tick`の係数
   (`TICK_BUILD_M_COEF`/`TICK_BUILD_LU_COEF`)をHiGHSの値のまま流用せず、本ソルバの実測単価から
   再導出することを検討する。
3. ベンチマーク検証は必ず複数回・全93問題に対して行い、「代表問題だけ確認」で済ませないこと
   (今回のように代表選定自体が漏れると誤った合格判定につながる)。

## 訂正(同一セッション内)

上記の不採用判定(maros-r7 +22〜27%、wood1p +21〜25%、fit2p +10〜16%、fit2d +13〜15%の「再現性のある退行」)は、
**検証方法自体の欠陥による誤判定**でした。原因は2点:

1. 「新実装を複数回計測した結果」を、**別の時刻に記録された静的なJSON値(`scripts/benchmark_results.json`の旧値)**と
   比較していた。このコンテナの絶対的な実行速度はセッション中に大きく変動する(このセッションだけでも合計時間が
   51.5s→89.5s相当まで変動する場面があった)ため、新旧を別々の時刻に計測して比較すると、コードの差ではなく
   コンテナ負荷の差を「退行」と誤認する。
2. 追加のスポットチェックでは`subprocess.run`のwall-clock時間(Pythonインタプリタ起動・モジュールimportを含む)
   を比較に使っていたが、小規模問題(実solve時間0.02〜0.1s)ではこの固定オーバーヘッド(0.15〜0.3s)が
   計測値の大半を占め、相対パーセンテージがほぼnoiseになっていた。

**正しい検証(同一セッション内で新旧を直接ビルドし、標準ベンチマークスクリプトのin-process計測 `time.perf_counter()`
で solve() 呼び出しのみを計測、複数回・複数手法で再確認)の結果**:

- 全93問題で新旧のstatus不一致・目的値相対誤差>1e-7は0件(2回の独立フル実行で確認)。
- 疑わしかったmaros-r7・wood1p・fit2p・fit2dは、正しい計測(5回中央値、interleaved)ではいずれも±5%以内
  (退行ではなくノイズだった)。
- 対象群(鎖長支配の問題)は一貫して大幅改善: stocfor2 -25〜-38%、80bau3b -11〜-30%、bnl2 -19〜-27%、
  degen3 -17〜-23%、greenbea -12〜-22%、d2q06c -12%、scfxm3 -9.5〜-26%(2回の独立フル実行、いずれも同方向)。
- 唯一の実在する退行はpilot87(+7.7%、5回中央値、interleaved確認)。10%の閾値は超えておらず、実装コード自身の
  コメントでも既知のトレードオフとして記録されている(絶対実行時間が大きい2問題dfl001・pilot87のうち、
  pilot87を許容範囲内に保ちつつ他の大半の問題を改善する`SYNTH_CLOCK_FACTOR=16`を採用)。
- `cargo test`(176件・0失敗)を独立に再実行し全通過を確認。

この結果、当初の判定を撤回し**採用(5a)**に訂正します。実装(`src/simplex/lu.rs` / `src/simplex/extended_dual.rs` /
`scripts/run_full_benchmark.py`)をmainにマージし、`scripts/benchmark_results.json`をこの検証で得たクリーンな
単発フルベンチマーク結果で更新しました。

### 教訓(次回のベンチマーク検証への申し送り)

- 新旧比較は必ず**同一セッション内で両方を直接ビルドし、直近の時刻に計測**すること。過去に記録された
  `benchmark_results.json`の絶対値をそのまま「旧基準」として使わない(このコンテナの絶対速度はセッション内で
  簡単に1.5〜1.7倍変動しうる)。
- 小規模問題(solve時間<0.1s程度)の退行判定にsubprocess単位のwall-clock時間を使わない。ベンチマークスクリプトが
  内部で`time.perf_counter()`により測定するsolve時間そのもの(プロセス起動オーバーヘッドを含まない値)を比較に使うこと。
- 単発計測での「10%超の退行」は、対象問題群以外の小規模問題では高確率でノイズである。実行のたびに全く異なる
  問題が「退行」として現れる場合はノイズを強く疑い、疑わしい問題は5回程度のinterleaved中央値で裏を取ること。
