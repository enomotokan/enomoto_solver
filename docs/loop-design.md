# 自己再発火最適化ループの状態管理ルール

このリポジトリでは、NETLIBベンチマークの最悪ケース問題を選んでプロファイリング・
修正・再ベンチマークを繰り返す自動化ループ(スケジュール実行)が動いている。
このドキュメントは、そのループが反復をまたいで正しく状態を引き継ぐために
必須の運用ルールを定める。

## 背景: なぜこのルールが必要か

自動化ループは Claude Code のスケジュール実行で動き、実行のたびに
リポジトリを新規クローンしたエフェメラルなコンテナ上で動作する。
そのため、ローカルファイルに書いた状態は **そのままでは次回の実行に
一切引き継がれない**。

過去の実行では、`scripts/loop_state.json` と `scripts/benchmark_results.json`
がコード変更と同じブランチ・PR にコミットされ、その PR がマージされるまで
`main` に反映されないという運用になっていた。その結果:

- PR がマージされずに滞留している間、次回のスケジュール実行は
  `main` にこれらのファイルが存在しないため、過去の試行(連続失敗回数、
  ベンチマーク結果)を一切認識できなかった。
- `loop_iteration_count`(ループ全体の総反復回数を数えるグローバルカウンタ)
  自体がどのファイルにも存在せず、ループ停止条件(反復回数上限10回)が
  一度も機能していなかった。

このドキュメントのルールは、この2点を再発させないためのもの。

## ルール1: ステップ0(問題選定)の前に、必ず main から状態を読み込む

ループの各反復は、作業開始時に必ず以下を行う。

1. `git fetch origin main` してローカルの `main` を最新化する
   (フィーチャーブランチや他の PR のブランチではなく、**`main` の HEAD**)。
2. `main` 上の `scripts/loop_state.json` と `scripts/benchmark_results.json`
   を読み込む。
3. `loop_state.json` に `loop_iteration_count` が存在しない場合のみ 0 として
   扱う。存在する場合はその値をそのまま使う。

フィーチャーブランチや未マージの PR に残っている状態ファイルを参照して
過去の状態を「推測」してはならない。状態の正本(source of truth)は
常に `main` とする。

## ルール1b: 問題選定は「正答性 > 誤差 > 実行時間」の順に行う

ステップ0の問題選定は、`scripts/select_problem.py` に実装する
(プロンプト内の散文ではなく、テスト可能なコードとして持つ)。
ループは必ずこのスクリプトを実行し、その出力した問題を対象とする。

順位付けは次の3段で、上の段が1件でもあれば下の段は選ばれない。

1. **正答性(correctness)** — 本ソルバが HiGHS と**質的に異なる答え**を
   出しているもの。HiGHS が最適解を証明しているのに infeasible /
   unbounded と判定する(またはその逆)、あるいはソルバが panic して
   落ちる場合。誤答は、どれほど遅い問題よりも優先する。
   段内では「自信を持った誤答」→「クラッシュ」の順(落ちる方がまだ
   呼び出し元を騙さないため)。
2. **誤差(accuracy)** — 双方が最適解に到達しているが、目的関数値の
   相対差が許容値(既定 `--obj-tol 1e-6`)を超えるもの。相対差の
   大きい順。
3. **実行時間(runtime)** — 上記に該当しない、正しく解けている問題。
   `ours_time / highs_time` の大きい順。タイムアウトは「無限に遅い」
   ものとして実行時間段の先頭に置く(誤答より上には決して来ない)。

`loop_state.json` の `consecutive_failures` が上限(既定3)に達した問題は
選定対象から外す。全問題が上限に達した場合は最悪の問題を返しつつ
`exhausted` を立てるので、ループはその旨を報告すること(黙って通常の
選定として扱わない)。

`.mps` が展開できない・HiGHS が読めないといった、ソルバの責任ではない
エントリ(`data`)は選定対象にせず、別枠で報告する。

## ルール2: ステップ5a/5bの後、状態ファイルは main に直接反映する

コードの修正(ソルバ本体の変更)は、これまで通り
`claude/<問題名>-<日時>` ブランチにコミットして PR を作成するフローに従う。
これはレビュー対象であり、マージされるかどうかは人間の判断による。

一方で、状態ファイル(`scripts/loop_state.json` / `scripts/benchmark_results.json`)
は **コードの PR とは独立に、`main` へ直接コミット・push する**。
具体的には、ステップ5a(改善確認)・5b(改善不可)のいずれの場合でも、
そのステップの一部として以下を行う。

1. `loop_iteration_count` をインクリメントした値を反映する。
2. 対象問題の `consecutive_failures` / `attempts` / `last_result` /
   `last_attempt_at` を更新する。
3. 5a の場合は `benchmark_results.json` を最新のベンチマーク結果
   (NETLIB 93問題)で更新する。
4. これらの状態ファイルのみを含む単独コミットを作成し、`main` に直接 push する
   (コードの変更は含めない。コードの変更はコード用 PR の側に残す)。

コード PR がマージされるか・いつマージされるかに関わらず、状態ファイルの
更新は毎回 `main` に反映される。これにより、次回のスケジュール実行は
コード PR のレビュー状況とは無関係に、常に最新の試行履歴・反復回数を
読み込むことができる。

## ルール3: 93問題の完全性チェックとの関係

ステップ4の「NETLIB 全93問題が揃っていることの検証」を満たさなかった場合
(5b 相当)も、ルール2は適用される。すなわち、ベンチマークが不完全だった
という事実そのものを `loop_iteration_count` のインクリメントと
`consecutive_failures` の更新として `main` に記録し、`report/` にその原因を
記録する。ベンチマーク結果(不完全なもの)を `benchmark_results.json` として
`main` に上書きしてはならない — 直近の完全な(93問題揃った)結果を
`benchmark_results.json` としては保持し続ける。

ここでいう93問題とは、`netlib.org/lp/data/` の索引に並ぶエントリのうち、
`emps` で展開できる圧縮MPS形式の問題すべて(`scripts/setup_netlib_data.py`
が `.netlib_cache/problems.txt` に書き出すもの)を指す。索引には問題では
ないエントリ(`emps.c` などのツール、`readme`、`kennington/` への
リンク)や、専用の生成プログラムを要する `stocfor3` / `truss` も含まれる
ため、これらは対象外である。

「揃っている」とは全93問題について**エントリが存在する**ことであり、
全問題が最適解に到達することではない。タイムアウトや求解失敗も、その
事実を記録したエントリとして残す(現に `dfl001` は60秒でタイムアウトし、
`greenbea` はこちらのソルバが infeasible と判定している)。

## ルール4: 「改善」の定義は選定された段に対応させる

ステップ5a/5b の判定基準は、その反復で選ばれた問題の段によって変わる。
いずれの場合も**他の92問題に退行がないこと**(状態が悪化した問題が
無いこと)が前提条件であり、これを満たさない変更は改善とみなさない。

| 選定された段 | 改善の定義 |
|---|---|
| correctness | 誤判定・クラッシュが解消し、HiGHS と同じ質の答え(最適解なら最適解)に到達すること。速度は二の次 |
| accuracy | 目的関数値の相対差が許容値(`--obj-tol`)以下に収まること |
| runtime | `ours_time / highs_time` が有意に改善すること(測定ばらつきの範囲内の差は改善としない) |

## まとめ

| タイミング | 読み書き対象 | 反映先 |
|---|---|---|
| ステップ0の前 | `loop_state.json` / `benchmark_results.json` を読む | `main` の HEAD から |
| ステップ0 | `scripts/select_problem.py` で対象問題を選ぶ(正答性>誤差>時間) | スクリプトの出力に従う |
| ステップ5a/5b の後 | 上記2ファイルを更新する | `main` へ直接コミット(コードPRとは別) |
| コード変更 | ソルバ本体などの変更 | `claude/<問題名>-<日時>` ブランチ→PR(レビュー対象) |
