# 不要な探索・データ構造の無駄の監査 (HiGHS 比較) と NETLIB93 A/B

基点: `be5bbea` (main)。対象: presolve / 拡張双対ループ (CHUZR・x_B 更新・BFRT・双対更新 / PRICE・CHUZC1・DSE・FTRAN) / LU Markowitz カーネル。
計測: `scripts/ab_bench.py` (base と new を別 venv に `maturin develop --release`、問題ごとに別プロセスで交互実行、
小問題はプロセス内で約0.5s分反復、3周の全サンプル中央値)。生データ: `analysis/waste_audit_20260923_ab_final.json`。

## 結果 (base = be5bbea, new = 本ブランチ最終)

- **NETLIB93 合計 40.31s → 28.06s (-30.4%)**。重い10問 -30.3% / 軽い83問 -30.9%。
- **93/93 問すべてで高速化** (最小改善 share1b -11.1%)。10% 超の退行 0 件。status・目的関数値の不一致 0 件。
- `cargo test --release` 226 件、pytest 20 件通過。

主な問題: dfl001 18.67→14.01s (-25%)、pilot87 6.38→5.23s (-18%)、maros-r7 2.82→1.03s (-63.5%)、
fit2p 2.72→2.13s (-21.5%)、d2q06c 2.20→1.68s (-24%)、pilot 1.58→1.26s (-20%)。全表は末尾。

## 着手前のプロファイル (base)

- presolve が全体の 13% (5.2s)。うち `reduce_equalities` 2.1s (maros-r7 だけで 1.6s = その問題の 58%)。
  小問題の多くで presolve が総時間の 40-70%。
- 主ループ: dse_update 12-20%、refactor 10-21%、fit2p では bfrt 26% + xb_update 16% + chuzr 11%。
- LU: dfl001 で1ステップ平均 131 候補 (32% が searchLimit=256 到達)、pilot87 で col_max_abs 再走査 14.2M エントリ。

## 見つかった無駄と対応

### presolve (縮約結果はビット同一)
| # | 無駄 | 対応 | 効果 |
|---|---|---|---|
| P1 | `redundancy.rs` 疎消去の各ステップでピボット行に触れた全列 (rhs 列 n 含む) の最大値を BTree 全走査 (maros-r7 で 6690万要素) | 上界キー + exact フラグの遅延ヒープ。先頭に来た列だけ再走査 | 再走査 24万要素、maros-r7 reduce_equalities 1.6s→~0.1s |
| P2 | 閾値未満しか持たない列をピボット探索で毎回走査 | 上界キー < 0.1·gmax の列を O(1) スキップ | dfl001 訪問列 491万→33万 |
| P3 | `csr_from_rows` が faer triplet (全ソート) 経由 | 重複列なしなら O(nnz) 直接構築 | 約126呼び出し箇所に波及 |
| P4 | propagate: 行ごとの Vec 確保・`row.clone()`・無変化でも2パス目 | 個数+先頭添字化、所有権移動、無変化で打ち切り、`rebuild_g_ref` | propagate 389→123ms |
| P5 | reduce_inequalities / parallelcols: 行/列 signature の Vec + SipHash | 安価なインラインハッシュ + 代表比較、無変化時は再構築しない | 842→125ms |
| P6 | aggregator: 候補ごとに A/G 全行を走査 (二乗) | 列→行索引 | dfl001 123→12ms |
| P7 | doubleton/colsingleton/rowsingleton: BTreeMap、無変化でも A 再構築 | Vec 化、無変化時は clone | |
| P8 | graph.rs 最大マッチング: 行ごと `vec![false; n]` | エポック配列 | |

## 実装して不採用にしたもの
- **行シングルトンを閾値なしで優先 (HiGHS 流)** `ENOMOTO_LU_ROW_SINGLETON=0`: 単独A/B 合計 -2.8% だが greenbeb +25.8%、share2b +20.4% → 不採用 (既定OFFで温存)。
  bordered 経路で使うと fit2p が誤答 (-8.9e117) になるため bordered では常に無効。
- CHUZR の refresh_row 分岐レス化: 命令数 +45% で悪化、撤回。
- DSE で alpha==0 行スキップ: 分岐予測ミスで悪化、D2 に置換。

## 未実装の候補 (次の着手先)
- presolve: 外側ラウンド収束判定 (pilot87/pilot/d2q06c が上限20ラウンドを使い切る。縮約結果が変わる)、
  ラウンド内の Csr↔Vec<Vec> 往復 (1ラウンド5回以上)、DM分解のマッチング (Hopcroft-Karp)、dualpropagate の転置再構築、scaling の境界行。
- ループ: flip 用と entering 用の x_B 更新の統合 (fit2p 推定 -7%、行順が変わり経路変更の可能性)、
  HiGHS 式 hyper-sparse CHUZR (経路変更)、BFRT の base/slope 2本 FTRAN を pair solve で融合、drift チェック rhs の増分管理。
- LU: 列メタデータの pack、`detect_border_columns` の二重呼び出し、`MarkowitzState::new` のバケット確保、refactor 計時区間内の x_B/双対再計算 (pilot87 約160ms)。
- FTRAN/BTRAN 内部の O(m) パス (seed fill、permute_out、U 段の u_seq 全走査)。

## 既知の非決定性
wood1p は変更前ビルドでも実行ごとに反復数・縮約結果が揺れる (164〜323 反復)。原因は密行列経路の faer ColPivQR の rayon 並列と推定
(`RAYON_NUM_THREADS=1` で決定的)。A/B のノイズ源なので決定化を推奨。
