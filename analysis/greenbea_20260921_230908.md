## 0. 結論(要約)

1. **原因分類: 初期基底の質(M 側に置かれる列の数)を決める presolve の欠落。** 本ソルバの `presolve::run_extended`(`src/presolve.rs:508-509`, `:986`)は活動度ベースの伝播 `propagate::propagate`(`src/presolve/propagate.rs:120`)を**不等式系 `G x <= h` にしか掛けていない**(`propagate(n, &g, &h, ..)`; 等式系 `a`/`b` は引数にすら渡らない)。greenbea は 2,392 行中 2,199 行(92%)が等式で、HiGHS の presolve ログが示す最大の縮約 "Forcing row: 185 rows / 803 cols" とそれに続く doubleton / aggregator の連鎖(合計 -1,441 行 / -2,416 列)は等式行の活動度解析から始まる。本ソルバの presolve は -407 行 / -944 列で止まり、**上限 +inf の構造列 3,569 本が拡張双対に「M 追跡列」として渡される**。
2. **決定実験(§2)**: HiGHS の presolve 後 LP(951 x 2,989)をそのまま本ソルバに渡すと **4,329 反復 / 0.95-0.97 s で正答**(自前 presolve 経由: 27,653 反復 / 11.8 s)。HiGHS の presolve 規則を 1 つずつ無効化した LP でも 0.92-5.6 s。反復数 11 倍の差は「拡張双対の反復ロジック」単体ではなく「拡張双対に渡される問題の形」で決まっている。
3. **プロトタイプ(§3, §4)**: 等式行に対する活動度伝播 `propagate_equalities`(forcing row 検出 + 両側からの bound 強化、`propagate` と同じ EPS=1e-9・同じ §3.1/3.2 の式)を `run_extended` の各 round の `propagate` 直後に追加(diff 154 行、§9)。greenbea: presolve 後 3,426 列 x 1,587 行、M 追跡列 3,569 → 267-367、主ループ 2,454-2,680 反復、直列計測 0.61 / 0.65 s(main 11.79 / 11.83 s、HiGHS 0.25-0.27 s)、目的値は HiGHS と相対誤差 ≤ 4.1e-14。効果は「M 追跡列の削減」から来る(§4.3): 固定のみ(forcing row だけ、bound 強化なし)の変種は M 追跡列 2,326 本が残り、Bland モードに落ちて `MAX_ITERS`(131,580)を使い切り BIG_M 経路で誤答(377 s)。
4. **93 問題全数(§5)**: 変種 3 種(round 制限なし / 2 round / 3 round)すべてで **status 93/93 一致、目的値の相対差 ≤ 1e-9(main 比)、HiGHS 比 ≤ 1e-10**。`cargo test --release` 171 件通過(モード有効時)。合計時間(公式 `benchmark_highs`、各 1 回)は main 71.1 s → 55.1 / 51.9 / 71.9 s。**推奨は「最初の 2 outer round のみ実行」変種(`ENOMOTO_EQPROP=full ENOMOTO_EQPROP_ROUNDS=2` 相当、§7)**: presolve 時間が main と同等(88 ms vs 96 ms)に収まり、pilot87 の悪化(3 round 変種で拡張双対が特異基底 → BIG_M 経路、11.0 → 30.0 s)を踏まない。直列再計測(§5.4)では greenbea -95%、pilot -54%、greenbeb -46%、cycle -85%、woodw -57% に対し、stocfor2 / d6cube が +0.13 s(+90%)、d2q06c +6%。
5. **398aed9 の切り分け(§6、コーディネータ追加依頼)**: (a) Bland CHUZC の (ratio,j) 順は、main でも 418e62a でも等式行伝播後でも **完全に無関係**(`bland_mode` が一度も立たず、j 順に戻してもプロファイルカウンタまでビット同一)。(b) slope 丸め(snap)を main から外すと `MAX_ITERS`=168,620 到達 → BIG_M → 誤答 1.24e-3(反復#9 §1.1 の再現)。418e62a に snap だけを足すと 6,601 → 9,052 反復(+37%)で正答、`m_enter_via_flip` は 511 → 524 で**ほぼ不変**。つまり「418e62a 比 20 倍」の flip 増は snap ではなく 7baad18 で presolve の出力(4,645 x 2,056 / M 追跡 3,715 → 4,461 x 1,985 / 3,569)が変わったことによる経路変化で、398aed9 はその経路で正答に戻すための対症療法。**等式行伝播を入れた presolve では snap を外しても・Bland 順を戻しても 2,591 反復の同一経路で正答**する(§6.2 D/E/J)。
6. **3 分類**: (a) presolve で落としきれていない — **主因**(M 追跡列 3,569 本、これが (b) を誘発)、(b) 反復数(27.6k vs 2.5k)— 症状、(c) 1 反復 ~418 us vs HiGHS ~100 us — 副因(等式行伝播後は 200-220 us/反復、再分解 241 → 13-17 回)。
7. **想定との食い違い(§8)**: 反復#9-#14 が「M 側追跡の設計ギャップ」として拡張双対内部の部分介入を 17 変種以上試みたが、M 側に置かれる列の *数* を決めているのは presolve 側であり、そこを直すと拡張双対の設計は(少なくとも greenbea では)そのままで HiGHS の 2.5 倍以内に入る。

**結論: (a) 具体的な修正案あり**(§7)。ただし採用判断は「93 問題の直列再計測で stocfor2 / d6cube の +0.13 s を退行とみなすか」に依存する(§5.4、§7.4)。

## 4. プロトタイプ `propagate_equalities`(§9 に diff 全文)

### 4.1 設計

`run_extended` の各 outer round で `propagate`(不等式)の直後・`dualfix` の前に、等式系 `a`/`b` と現在の `lb`/`ub` を渡して:
1. 各等式行の最小/最大活動度を計算(`propagate` と同じ式・同じ `EPS = 1e-9`、Ruiz スケール後の値)。`inf > b + EPS` または `sup < b - EPS` なら infeasible(既存の `extended_infeasible` で返す)。
2. **forcing row(両側)**: `inf == b`(±EPS)なら各項を inf 側の bound に固定、`sup == b` なら sup 側に固定。固定列は既存の `foldfixed`(`src/presolve.rs:618-632`)が次段で行から畳み込み、空になった行は落とす。
3. **bound 強化(`full` モードのみ)**: `A_i x <= b` と `A_i x >= b` の両方から §3.2 の式で各項の bound を強化(`propagate.rs:218-241` と同じ、`candidate < ub - EPS` / `> lb + EPS` の絶対許容)。
4. `lb`/`ub` 以外は触らない。行の縮小は既存の rowsingleton / doubleton / colsingleton / aggregator / parallelcols に任せる。

環境変数: `ENOMOTO_EQPROP=fix`(2 のみ)/ `full`(2+3)、`ENOMOTO_EQPROP_ROUNDS=k`(最初の k outer round だけ実行)、`ENOMOTO_EQPROP_MINREL=r`(有限 bound は改善幅が `r*max(1,|old|)` を超えるときだけ更新)。未設定時は完全に no-op(ビット同一を確認)。

## 7. 修正仕様(提案、実装はしていない)

### 7.1 対象と内容

**対象**: `src/presolve/propagate.rs`(新関数 `propagate_equalities`、§9 の diff の関数本体; `ENOMOTO_EQPROP_MINREL` の `improves` 判定は削除してよい)と `src/presolve.rs::run_extended`(round loop 内 `propagate` 直後・`dualfix` の前で呼ぶ; §9 の diff の `presolve.rs` 部分)。環境変数ゲートは外し、**outer round 0 と 1 でのみ実行**(`ENOMOTO_EQPROP=full ENOMOTO_EQPROP_ROUNDS=2` 相当、`_round_idx < 2`)。`infeasible` は既存の `extended_infeasible` で返す。`interior_point.rs` も同じ `run_extended` を通るため自動的に同じ縮約を受ける(今回は未計測)。

理由: (i) 93 問題で正答性・頑健性を確認済みの変種のうち presolve 時間が main と同等(88 ms)で、pilot87 の BIG_M 経路転落を踏まないもの。(ii) round 2 以降は greenbea でも forcing row が 0 件で、残るのは幾何級数的な締め付けの微小更新のみ(§4.3)。(iii) 他の 2 変種(制限なし・3 round)も 93/93 正答なので、round 数の選択は正答性ではなく時間の問題。

### 7.2 健全性(既存設計との関係)

- forcing row による固定は primal の含意そのもの(固定列は `foldfixed` で LP から消える)。bound 強化は「不等式行由来の含意 bound を LP に書き戻す」既存の `propagate` の挙動と同種で、feasible set を変えないため x と目的値は不変(本ソルバは双対値を返さないので、HiGHS が含意 bound を書き戻さない理由=双対 postsolve は当たらない)。
- 後段で `lb`/`ub` を読む各段(`dualfix` は等式行に現れる列を除外、`aggregator` の implied-free 判定、`colsingleton` の `extra_g_rows`、`dualpropagate` の dominated-column 固定)は、いずれも「現在の bound は有効な含意 bound」という前提しか使わず、含意 bound の由来が等式行でも不等式行でも同じ(§3 のトレースで不等式由来の書き戻しは main でも既に起きている)。
- 数値面: `EPS=1e-9` 絶対(スケール後)は `propagate` と同一。93 問題で HiGHS 比 ≤ 1e-10 の一致。`lb > ub` が EPS 内なら 1 点に潰し、EPS 超なら infeasible。

### 7.3 併せて検討する価値のある追加(今回未検証、効果は推定)

1. `dualpropagate::run`(`src/presolve/dualpropagate.rs:234-242`)の「literal `+inf`」判定を、含意 bound で有限化される前の `orig_ub`/`orig_lb`(既に引数にあり未使用)で行う: 原問題で無限だった bound は最適双対に対する制約として有効なので健全。stocfor2 の縮約減少(§5.3)を戻せる見込み。ただし同モジュールの docs が警告する 80bau3b の事故(有限 bound を「強く含意された」として扱った件)とは別物であることを、80bau3b を含む 93 問題で確認すること。
2. 含意 ub の大きさ上限(例: スケール後 1e6 超は書き戻さない): greenbea では最大 1.05e7(原スケール)の含意 ub が生じ、BFRT はその幅でフリップできる。今回の 93 問題では問題は出ていないが、BIG_M と同種の数値リスクの芽として記録する。
3. 拡張双対の残る脆さ(`fix` 変種・ROUNDS=3 の pilot87 のような別経路での BIG_M 転落、反復#6 以来の「BIG_M フォールバックが `optimal` を返す」問題)は本提案の範囲外で、独立に残る。

greenbea: 11.8 s → 0.61-0.65 s(-95%、ours/highs 比 45x → 2.4-2.6x)。93 問題合計(各 1 回、ノイズ込み): 71.1 → 51.9 s(-27%)、うち greenbea -11.2 s、pilot -2.6 s、greenbeb -0.9 s、cycle -0.46 s、woodw -0.15 s。退行: stocfor2 / d6cube が直列再計測で各 +0.13 s(+90%)、d2q06c +0.15 s(+6%)。ルール 4 の「他 92 問題に退行がないこと」を絶対時間で見るか比率で見るかで採否が分かれるので、採用時はこの 3 問題を明示して判断すること。リスク: 経路が変わる問題が多い(30 問題中 13 問題が古典経路に切替)ので、マージ後の main で 93 問題を再計測して `benchmark_results.json` を更新するルール 2 の手順が特に重要。

## 8. 想定との食い違い(そのまま報告)

- 依頼文・過去 6 反復の前提「主因は拡張双対の M 側追跡の設計ギャップで、本格的な設計変更(双対フェーズ 1)が必要」は、症状の説明としては正しいが**対処箇所が違っていた**。M 側に置かれる列の数(3,569)は presolve が決めており、等式行伝播で数百本に減らすと既存の M 追跡設計のまま HiGHS の 2.5 倍以内に入る。反復#9 §6 の候補 (2)「M 側処理を双対フェーズ 1 に再設計、上限 70-85%」は、より安価な presolve 側の変更で同等以上(-95%)の効果が出る。
- 反復#9 の「7baad18 で presolve の出力が変わり経路が変わった」(§1.1)は、今回の「presolve の出力の細部で反復数が桁で振れる」(§2.2、§4.3、§6.2)と整合する。

+/// the *equality* system `A x = b`, which [`propagate`] never sees (it is

+/// `A_i x <= b` and `A_i x >= b`. Only `lb`/`ub` are mutated; the rows

+    pub forcing_rows: usize,
+    pub fixed_cols: usize,
+    pub tightened: usize,

+pub fn propagate_equalities(a: &Csr, b: &[f64], lb: &mut [f64], ub: &mut [f64], passes: usize, tighten: bool) -> EqPropagateResult {
+    let ar = a.as_ref();
+    // PROTOTYPE knob: a *finite* bound is only tightened when the
+    // improvement exceeds `min_rel * max(1, |old|)` (an infinite bound is
+    // always replaced), to stop the geometric-creep non-convergence the
+    // paper's own §3.2 example warns about.
+    let min_rel: f64 = std::env::var("ENOMOTO_EQPROP_MINREL").ok().and_then(|s| s.parse().ok()).unwrap_or(0.0);

+        if !old.is_finite() { return true; }

+    };

+            let mut finite_sum_sup = 0.0f64;

+            let mut sup_unbounded: Vec<usize> = Vec::new();

+                }

+                    if ub[j].is_finite() { finite_sum_sup += v * ub[j]; } else { sup_unbounded.push(j); }

+                    if lb[j].is_finite() { finite_sum_sup += v * lb[j]; } else { sup_unbounded.push(j); }
+                }
+            }
+            if live == 0 {

+            }

+                }

+        }
