# mc11 の誤った最適値 11712 (SUBMIP_CUTS + サブ MIP のカット 25 ラウンド) の調査 (2026-10-21)

- 発端: inv/subx-a-20261021 (6ffe911) の計測 `suball_rSXa` (`ENOMOTO_MIP_SUBMIP_CUTS=1 ENOMOTO_T_MIP_SUBMIP_CUT_ROUNDS=25
  ENOMOTO_T_MIP_SUBMIP_CUT_STALL=10`、4 スレッド・60 秒) で、mc11 が 34.24 秒・3442 ノードで status optimal・目的値 11712
  (bound 11712、root_bound 11464.9) を返した。最適値は 11689 (HiGHS・MIPLIB)。
- 環境: 専用コンテナ 4 CPU (`nproc` = 4)。土台 develop b9bccd6 (このブランチ)。ソルバーは原則 1 つずつ動かした
  (§2 の 4 の 3〜5 回目と 9 だけ 2 つ重ねた)。
- 台本・要約・小さいログ: `runs/mc11wo/` (`run1.py`・`loop.sh`・`fcfuzz.py`・`hsol.py`、各条件の `*.summary`、
  乱数生成の結果 `fuzz*.log`、デバッグ解 `mc11_pre.sol`)。台本の中の作業場所のパスは調査のときのもの。

## 0. 要約

**再現しなかった。原因は特定できず、修正はしていない。** 試した条件と回数は §2。誤った optimal は 1 回も出ず、
デバッグ解 (HiGHS で求めた前処理後の空間の最適解) を刈る記録 (`MIP_DEBUG_SOL lost at`) も 1 回も出なかった。

- 事実: mc11 (4 スレッド・60 秒) を問題の設定で計 90 回 (FC_SUBMIP あり 60 回、6ffe911 に近づけた NO_FJ_P3 で 30 回)
  回して全部時間切れ、下界は 11446〜11541。誤った回の 34 秒・下界 11712 は、どの回の 60 秒の下界からも 170 以上離れている。
  600 秒にすると 1 回は 283.6 秒で 11689 を証明して正しく終わった。
- 事実: 同じ設定で最後まで解ける固定費用型 (rout 30 回・beasleyC3 15 回・h80x6320d 12 回) と、mc11 風の乱数生成の固定費用
  ネットワーク (§2 の 8・9、optimal 計 300 回) でも、最適値の不一致は 0。
- 事実 (コードを読んだ結果): サブ MIP から親の下界へ漏れる経路は見つからなかった (§3)。サブ MIP の結果のうち親が使うのは
  解だけで、`try_incumbent` が元の問題で実行可能性を確かめてから目的値を計算し直す。サブ MIP にカットの行を加えることは
  サブ MIP を狭めるだけで、親の行・プール・境界には書き戻されない。スレッドローカルの置き場もサブ MIP の側では
  `params.submip` で切ってある。
- 推測: 誤りの形 (34 秒で下界が 11712 まで一気に上がった) は、カットが少しずつ強すぎた形ではなく、探索の途中で大きな部分木を
  まとめて失ったか、打ち切り値が実在しない解の値まで下がった形に見える。サブ MIP の設定はタイミングを変えるだけで、親の
  並列の木の探索 (スレッドの間の共有) の側のまれな競合という可能性が残る。ただし裏付けはない。
- FC_SUBMIP を既定に戻してよいか: この調査で否定する材料は出なかったが、原因が分からないので「直った」とは言えない。
  戻すなら、誤りが FC_SUBMIP に固有でない可能性 (§4) を踏まえて、計測で同じ型の不一致を見張り続けることが条件になる。

## 1. 準備

- `maturin build --release`、`pip install --no-deps --force-reinstall dist/*.whl`。MPS は MIPLIB から `.miplib_cache/` に取得。

  `loop.sh <名前> <問題> <回数> <スレッド> <秒> ENV=...` で繰り返し (`ENOMOTO_MIP_LOG=1` を付ける)。
- デバッグ解: `ENOMOTO_MIP_DEBUG_DUMP_PRESOLVED2` で前処理後 (クリーク行の拡張の後、対称性の行の前) の mc11 を書き出し、
  HiGHS 1.15.1 (`mip_rel_gap=0`) で解いた (`hsol.py`、11689、`mc11_pre.sol`)。`ENOMOTO_MIP_DEBUG_SOL` に渡すと
  `MIP_DEBUG_SOL: reduced objective 11689 feasible true` と出て、根の定義域はこの解を含んでいた。
  - 限界: デバッグ解の検査は刈り込みのすべての場所を見てはいない (`queue.prune` による打ち切り値での一括の刈り込みなどは
    検査しない)。また 1 つの最適解しか見ないので、別の最適解が残っていれば刈られても誤りにはならない。
  - 「all symmetric images gone after node N」は 90 回中 3 回出たが、主スレッドの手元の待ち行列だけを見ていて、共有の
    待ち行列・ほかのスレッドに渡したノードを数えないので、4 スレッドでは誤報になりうる。同じ回に `lost at` は出ていない。

## 3. コードを読んで確かめたこと (サブ MIP → 親の経路)

### 3.1 サブ MIP にカットの行を渡すところ

- `heuristics.rs` `solve_submip_problem` (SUBMIP_CUTS・FC_SUBMIP): `lp_tight_cut_rows` で親の LP の行 (元の行の後ろ) のうち
  効いているものをサブ MIP の行に加え、`MipProblem::from_rows` で作り直す。親の LP からは読むだけ。木の中で呼ばれると局所的な
  行が入りうる (RENS の方は `nodes <= 1` で根だけにしているが、こちらは場所を問わない) が、サブ MIP を狭めるだけで、
  結果は解の候補にしか使わない。
- 潜り式 RENS (`append_lp_cuts`): 同じく読むだけ。
- `separation.rs` のサブ MIP の根のカットのラウンド (`fc_sub` で 25 ラウンド・停滞 10): サブ MIP の中で閉じている。

### 3.2 サブ MIP の結果の使われ方

- 逐次 (`solve_submip_problem`) も別スレッド (`take_submip`) も、使うのは `r.x` (解) を `try_incumbent` に渡すことと、
  固定率・ノード上限の記録だけ。`try_incumbent` は整数列を丸め、元の問題 (`self.p`) で実行可能性を確かめ、`self.p.objective`
  で目的値を計算し直す。連続列の解き直し (`resolve_continuous`) も、解き直した解の実行可能性を確かめてから値を下げる。
- サブ MIP の状態 (Infeasible など) から下界を上げるのは、目的値の二分探索 (`ENOMOTO_MIP_OBJ_BISECT`、既定では使わない) だけ。

### 3.3 スレッドローカル・共有の置き場

- `RESTART_CUTS`/`RESTART_SOL`: 置くのは根の再スタート (`maybe_restart`、サブ MIP では行わない) と二分探索のスレッド
  (既定では使わない) だけ。置いた直後の `solve_problem` の始めで取り出し、再スタートの後に消す。mc11 の 60 秒の回
  (§2 の 1〜3、90 回) では再スタートは 1 回も起きていない (`MIP: restart` なし)。600 秒の回 (§2 の 4) では根のカットの
  時間の上限 (全体の 0.1 倍) が延びるので 21.6〜27.7 秒に再スタート 1 が起き (ログが残る 6 回中 4 回)、そのうち 1 回が
  正しく 11689 を証明した。h80x6320d は 12 回とも、beasleyC3 は 1 回再スタートし、結果は正しかった。
- `SUBMIP_BASIS`: 列の状態だけ。`ORBITOPES`/`SYM_*`: サブ MIP では読まない。`PORTFOLIOS` (共有の最良値・下界):
  `shared: if params.submip { None }`。`ROLE_POOL`: 読むだけ (止めの合図)。`CUT_JOB`: 写しから作る求解だけ (サブ MIP は
  写しを持たない)。`DEBUG_SOL`: サブ MIP では使わない。LU・単体法のスレッドローカルは作業用の領域と閾値で、求解ごとに
  初期化される。
- 木を分け合うスレッドの共有 (`WorkPool`): 大域的な境界 (`bounds`)、双対証明・衝突 (`learned`)、カット
  (`TREE_SHARE_CUTS`、既定では使わない)。どれも木の探索のスレッド自身の `Solver` が書き、サブ MIP の `Solver` は `pool` を
  持たない (`Solver::new` の引数が `None`)。
- 従のスレッドの解: 写しの番号を付けて `inbox` に置き、その後で共有の最良値を下げる。主は従を待った後で必ず `take_inbox`
  する。届いた解を主が受け付けられなければ `a solution from another thread was rejected` と出るが、どの回にも出ていない。
- 根の解発見スレッド (`FIND_OUT`) は自前の `Portfolio::new()` の写しで動き、共有の最良値を下げない。

## 4. 残る可能性 (推測)

- 誤りが FC_SUBMIP / SUBMIP_CUTS に固有でない可能性。計測の記録では、既定・ほかの試作で mc11 が optimal で
  11689 以外を返した回はこの 1 回だけ (benchmarks/ の 4 スレッド・60 秒の JSON と cand_logs を全部見た)。サブ MIP の設定で
  時間の使い方が変わり、親の並列の木の探索のまれな競合に当たった、という説明もありうる。
- 誤った回は 34 秒で 3442 ノード (benchmarks/ の既定などの 60 秒の回は 2000〜15000 ノード・下界 11390〜11630、ここでの 60 秒の回の下界は 11446〜11541)。ふつうの経過では 34 秒で
  下界 11712 に届かないので、待ち行列の大きな部分が一度に消えたか、主の暫定解より良い値で共有の最良値が下がったまま
  解が主に届かなかった、のどちらかが疑わしい。後者は §3.3 の受け渡しの順 (解を置いてから値を下げる、主は最後に必ず
  受け取る) からは起きないはずで、前者の経路も見つけていない。
- 次に調べるなら: (a) 結果が optimal のときに、主が暫定解の目的値と、ほかのスレッドが知らせた最良値・従の結果の値を
  突き合わせて食い違えば警告する (今は `join_workers` が警告するだけで、結果には反映しない)、(b) デバッグ解の検査を
  `queue.prune` と共有の待ち行列の刈り込みにも広げる、(c) 計測で同じ型の不一致が出たときに備え、mc11 の計測は
  `ENOMOTO_MIP_LOG=1` のログを残す。
