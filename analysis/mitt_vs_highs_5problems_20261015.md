# Mittelmann で HiGHS に負けている 5 問の調査 (neos-3025225・stormG2_1000・scpm1・supportcase10・ex10) (2026-10-15)

計測: 4 CPU・15 GB の Linux (クラウドのコンテナ)、`threads=4`、commit fbc66c6 / 60c3a2b。HiGHS 1.15.1 (highspy) も同じ計算機で
`solver=ipm`・`run_crossover=on` で測った。利用者の計算機 (AMD Ryzen 16 論理 CPU、Windows) の値は依頼文から。

## neos-3025225 (91,572 行 × 69,846 列、非零 935 万) の異常終了

- 再現: Linux の既定のスタック (8 MB) では落ちない。`ulimit -s 1024` (Windows の 1 MB 相当) で `auto` を走らせると
  Segmentation fault。gdb の逆追跡で、rayon のプールのスレッド ("enomoto-0") が `simplex::connected_components_of_std_form`
  の union-find の `find` (経路圧縮つきの再帰) を数万段たどってスタックを使い切っていた (前処理の後、独立な成分への分割)。
  依頼文の「節目の記録が 1 つもない」は、節目を解き終わってから取り出すため (途中で落ちると何も残らない)。
- 修正 (fbc66c6): `find` を再帰しない形 (根まで辿ってから、通った節を根につなぎ直す) にした。返す根は同じで分割の結果は変わらない。
  ほかに再帰の union-find はない (`mip/symmetry.rs` の `find` は反復)。
- 修正後 (1 MB のスタックで): `auto` 293 秒・最適 0.05257405203。内点法 44 反復 200 秒 (拡大系、nnz(L) 7,210 万、設定 22.8 秒、
  分解 141 秒 = 1 回 3.2 秒、求解 22.7 秒)、超基底 69,125 本の押し出し 89 秒。正規方程式は三つ組が多すぎて (列あたり平均 134 非零)
  使えない。HiGHS (16 論理 CPU) は IPX 33 反復で 187 秒。

## 退行の確認

- Netlib 93 + Kennington 16 (`benchmarks/crossover/ab65/nk_xo.jsonl`・`nk_race.jsonl`、交互に 3 回): `ipm_crossover` (1 スレッド) は
  全問正解、合計 41.9 → 41.7 秒、10 秒ずらした幾何平均の比 1.000。`auto` (4 スレッド) は全問正解、合計 24.3 → 24.6 秒、比 1.000。
- Mittelmann 21 問 + neos-3025225 (`auto`、4 スレッド、600 秒、交互に、30 秒未満は 3 回の中央値、`benchmarks/crossover/ab65/mitt_race.jsonl`。
  基準は 2 つの変更を環境変数で戻した設定): 全問で新旧とも最適・目的値は基準と相対 1e-6 以内、合計 1,560 → 1,525 秒、
  10 秒ずらした幾何平均の比 0.987。1.1 倍以上遅くなった問題なし (最大 s250r10 25.6 → 27.1 秒、neos-5052403-cygnet 35.7 → 37.5 秒)。
  速くなったのは neos-5251015 125.3 → 109.9、stormG2_1000 194.6 → 182.7、scpm1 80.5 → 74.9、pds-100 96.3 → 90.8 秒など。

## 残り

- stormG2_1000 の内点法 109 反復 (ギャップが 30〜90 反復目で 35 → 0.2 と遅い) と Woodbury の求解。
- neos-3025225・ex10 の拡大系の分解 (1 回 3.2 秒・0.6 秒) と、ex10 の押し出しの比率テスト (密な FTRAN の結果の走査)。
