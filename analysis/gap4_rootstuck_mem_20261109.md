### メモリ (事実)

- 5 問の最大 RSS (既定、600 秒): neos-957323 5.6 GB、uccase12 5.7 GB、fiball 5.6 GB、widden 4.3 GB、tbfp-network 4.5 GB (HiGHS は 0.6〜1.3 GB)。
- **持ち主は 2 つの形に分かれる**:
  1. **開いたノードの持ち物** (uccase12・fiball): 共有の待ち行列のノードの基底・DSE 重み・境界の変更。fiball は 600 秒で 21 万ノード、
     変更 1.03 GB (1 ノード平均 約 1100 個の変更、詰めた後)・基底 1.87 GB・DSE 0.49 GB。uccase12 は 2.6 万ノードで DSE 1.84 GB (481 秒、
     MEMCAP が捨てる前)・基底 0.79 GB。HiGHS はこの 2 問を 667・6949 ノードで解く。
  2. **木のスレッドごとの写し** (neos-957323・tbfp-network・widden): 木に入ると RSS が 1 スレッドあたり 0.5〜0.8 GB 跳ねる
     (neos-957323 2.7 → 4.2 GB、tbfp-network 1.8 → 4.2 GB、widden 1.2 → 4.1 GB。開いたノードは 0.1 GB 前後)。heaptrack (neos-957323、
     400 秒、全部の確保を glibc に回したデバッグの wheel) のピーク 5.6 GB の内訳:
     - 木の各スレッドのカットのプールの伝播の索引 (`cpp_sync` の列ごとの並び) **1.63 GB**。根のカットが 1 本 3.5〜4.4 万非零と密で
       (プール 184 本で 787 万非零)、各スレッドが全部の非零を列の索引に入れる。HiGHS は max(2 × 行の平均の非零, 0.1 × 列) 以上の
       カットを伝播しない (`HighsCutPool::addCut`)。
     - 木の各スレッドの `orig` (対称性の扱いの前の問題) の深い写し **1.12 GB**。中身は行・列ではなく前処理の調べの含意
       (`implied_bounds`・`conflict_edges`) で、`orig` の使い道 (解の実行可能性の確かめ) には要らない。
     - 木の各スレッドのカットのプール 0.48 GB、LP の行列 0.40 GB。
     - 内点法 (根の内点の丸め) の gemm (private-gemm-x86) のスレッドごとの作業領域 2.18 GB は**確保だけで触られず、RSS には効かない**
       (内点の丸めを止めても・使い捨てのスレッドで解いても、150 秒の最大 RSS は 4137 → 4211・4191 MB)。
  3. 再スタートは古い `Solver` の中から入れ子で次の求解を呼ぶので、**再スタートの前の `Solver` (LP・カットのプール・待ち行列) が木の間ずっと
     生きている** (neos-957323 は再スタート 2 回で外側の `Solver` が 3 つ同時に生き、木の 3 スレッドと合わせて 6)。
- **試作 `ENOMOTO_MIP_GAP4=roc`** (r: 再スタートの前に古い `Solver` の LP・カットのプール・待ち行列を捨てる、o: 木のスレッドの `orig` の写しから
  含意を除く、c: 密なカットを伝播に入れない) で neos-957323 の 150 秒の最大 RSS は 4137 → 3002 MB (−27%、r −9%・o −14%・c −8%)。
  600 秒の効き目と、開いたノードの側 (既存の `TREE_NO_PASS_BASIS`) を合わせた効き目は 3 節。

## 3. 試作 (`ENOMOTO_MIP_GAP4=<文字>`、既定では使わない)

| 文字 | 中身 | 場所 |
|---|---|---|
| `i` | 暫定解の整数列を固定した LP が時間の上限で止まったら、以後は解かない (`ENOMOTO_T_MIP_GAP4_INCLP_FAILS`、既定 1 回) | `solver.rs` の `resolve_continuous` |
| `p` | 根の LP の秒が、カットの選び方の比べの予算 (全体の 0.05 倍) の `ENOMOTO_T_MIP_GAP4_PROBE_FRAC` (0.25) 倍を超えるなら比べない | `separation.rs` の `probe_pending` |
| `r` | 再スタートの前に、入れ子の求解の間は使わない古い `Solver` の LP・カットのプール・待ち行列などを捨てる (戻った後は反復の数・ノード数・暫定解・根の下界しか使わない) | `solver.rs` の `maybe_restart` |
| `o` | 木のスレッドに渡す `orig` (対称性の扱いの前の問題) の写しから含意 (`implied_bounds`・`conflict_edges`) を除く (`MipProblem::clone_without_implications`) | `solver.rs` の `Solver` の構築・木の写し |
| `c` | 非零が max(2 × 行の平均の非零, 0.1 × 列) 以上のカットを、カットのプールの伝播の索引に入れない (HiGHS の `HighsCutPool::addCut` と同じ規則) | `solver.rs` の `cpp_sync` |
| `l` | カットの非零を 100 + 0.15 × 列 までにする。超えた分は LP の解が大域の境界にある列の項を係数の小さい順に落とし右辺を直す。足りなければ捨てる (HiGHS の `HighsCutGeneration::postprocessCut` と同じ) | `separation.rs` の `finish_cut` |
| `n` | 共有の待ち行列のノードに基底・DSE 重みを付けない (境界の変更の詰め `MEMC` は残す) | `solver.rs` の `snap_of` |

- 一度入れて外したもの: `g` (根の内点の丸めを使い捨ての rayon のスレッドで解き、gemm の thread_local の領域を返す)。RSS に効かなかった (表 4)。
- 既存の `ENOMOTO_MIP_TREE_NO_PASS_BASIS=1` は `snap_of` の頭で返るので、MEMC の詰めも飛ぶ (fiball で変更が 5.2 GB、最大 RSS 6806 MB と既定より悪い)。
  それで `n` を作った。

### 3.1 根から出られない問題での効き目 (600 秒、ビルドは試作を入れた同じ wheel、既定と並べる)

| 問題 | 種 | 設定 | 比べ (秒) | カットのループの終わり | 根のヒューリスティクスの終わり | 木に入る | 最初の解 | 600 秒の下界 / 解 |
|---|---|---|---|---|---|---|---|---|
| neos-3216931-puriri | 1 | 既定 (`b4def`) | 43.0 | 128.2 | 305.0 | 305.2 | 311.0 | 59671 / 81380 |
| neos-3216931-puriri | 1 | `ip` | 0 (飛ばした) | 84.3 | 261.4 | 261.6 | 267.5 | 59745 / 81380 |
| neos-873061 | 1 | 既定 (`b4def`) | 0 | 85.5 | 352.2 | 484.6 | 22.3 | 104.91 / 117.69 |
| neos-873061 | 1 | `ip` | 0 | 85.6 | 367.5 | 496.6 | 21.8 | 104.91 / **121.75** |

- puriri: `p` で比べの 43 秒が消え、カットのループは同じ (LP の反復 138797 で一致、選び方は既定のまま)。木に入るのも最初の解も 44 秒早い。
  ただし 600 秒の下界は HiGHS の根 (64041) に遠く、結果は変わらない。
- neos-873061: `i` は 1 回の時間切れの後に 1 回飛ばしただけで、根の時間は縮まない (RENS のサブ MIP の長さの揺れの方が大きい)。
  後の解の連続変数を磨かないので**解が悪くなる** (117.69 → 121.75)。`i` は 58 問の比べから外した (害が先に見えたため)。
