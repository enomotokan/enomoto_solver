## 2. commit の二分 (bis.sh・bisrun.sh) と原因

0.1.9 の頃の 2f9919194 (自分でビルドして 21.6・51.6 秒で実行不能) から 4e0dc7b34 (今の既定) まで、`src`・`Cargo.*` を変えた
commit を `git bisect run` で二分した (4 スレッド 90 秒、種 1・2、割れたら種 3。res_bis.jsonl、logs/bisect_log.txt)。

**最初の悪い commit は 558d7a4ce「ノードの LP の際どい実行不能を信用しない (widden の誤答の直し)」** (直前の f7fb51f84 は 20・29 秒で
実行不能、558d7a4ce は 2 種とも時間切れ、558d7a4ce に `ENOMOTO_MIP_NO_LPINF_CHECK=1` で 64・41 秒)。今の版でも
`ENOMOTO_MIP_NO_LPINF_CHECK=1` で 43・26・35 秒 (種 1〜3)。`ENOMOTO_MIP_LPINF_LOOSE=1` (ノードの解き直しの結果をそのまま使う) では 3 種とも時間切れ。

統計の行 (今の既定、種 2、60 秒) では、際どさの判定 `lp_farkas_ratio` が見た約 1000 本の証明のうち 767 本が「NaN・無限・負」の欄に入り、
ノードの LP の解き直し 663 回・強分枝の子を不明にした 104 回。一時の診断で見ると、射線は返っていて、標準形での確かめ
(`std_farkas_ok`、`ENOMOTO_MIP_DEBUG_LPINF`) はすべて成り立つ (Some(true)) のに、元の行の向きで測ると隙間が -∞ だった。

理由: `std_farkas_ok` は |z| が 1e-9 (1 + max|y|) 以下の項の無限の境界を無視するが、`lp_farkas_ratio` は行の重み y_i が 0 でなければ
(1e-17 程度の丸めの誤差でも) その行の境界を数える。片側が無限の行 (neos859080 の `y ≤ 10 b` など) に逆向きの微小な重みが載ると
行の区間が (-∞, ∞) になり、正しい証明を「際どい」とみなしていた。その結果、ノードを刈らずに解き直し、強分枝の子を不明にして
変数を固定せず、木が大きく育つ。

## 3. 試作 `ENOMOTO_MIP_LPINF_ROWTINY` (既定では使わない)

`lp_farkas_ratio` で |y_i| ≤ 1e-9 (1 + max|y|) の行を射線から落とし、z = yᵀA は残した行だけから作る。落とした後の射線そのものを
測るので、隙間が正ならそのまま厳密な証明 (緩めたのではない)。widden の 1e-8 程度の際どい実行不能は、落としても隙間が小さいので
今までどおり信用しない。

neos859080 (4 スレッド 90 秒): 種 1 46.5 秒・種 2 16.2 秒・種 3 51.0 秒で実行不能 (logs/neos859080_rowtiny_s*.log)。際どいとされた
証明は 0 本、全部「≥ 1e-4」の欄。cargo test 409 通過。

計測: `python plan.py 12 4 def rowtiny` → shards_MROWTINY.json (Mittelmann 48 問 × 種 1・2 × {def, rowtiny}、600 秒、12 分担・各 1.4 時間)・
shards_PROWTINY.json (MIPLIB 58 問 × 種 1〜3、60 秒、4 分担・各 0.74 時間)。`python run.py MROWTINY K` / `python run.py PROWTINY K`、
集計は `python summ.py MROWTINY def rowtiny`。判定の変更は LP の実行不能の扱い全部 (ノード・根・強分枝・LP のプロービング) に

## 6. SST を伝播だけに使う案の見立て (利用者の案、2026-11-19、保留)

案: 対称性のある問題で SST の不等式を根の伝播だけにかけ、その後は外してオービトープや orbital fixing で管理する。fhnw-binpack4-4 で確かめた (事実と推測を分ける)。

1. 事実: 根の伝播だけでは何も固定されない (SST あり・なしとも根の固定 0、logs/binpack44_{sst,nosst}_root.log)。SST の行は x_代表 − x_j ≥ 0 の 45 本 (9 段) で、
   根ではどの列も固定されていないので伝播が起きない。オービトープは見つからない (ORBPP 0 個、9 生成元・23 軌道)。根で伝播してから外す形の効き目はほぼ 0。
2. 事実: SST_FEAS で解けた回 (4 スレッド・種 1、7767 ノード、logs/fhnw-binpack4-4_sstfeas_s1.log) でノードを刈ったのは、伝播の衝突の解析 1176 回・
   リテラルの衝突 570 ノード・カットのプールの伝播 103 ノードで、LP の実行不能 (Farkas) は 2 回だけ (LP は最後まで 0 で実行可能)。
   推測: SST の行はほぼ伝播を通じて効くので、LP に入れず伝播だけに使う形 (衝突のプールに消えない 2 リテラルの衝突 {x_代表 ≤ 0, x_j ≥ 1} として入れる) でも
   この問題では効き目の大半が残る。作る手間は半日弱 (年齢・上書きから守る印と、スレッド・サブ MIP への配り方)。
3. 推測: 最適化問題で SST を orbital fixing の代わりにしたときの遅れ (P +21%・M +41%) の主因は LP の重さではなく (SST の行は少ない)、静的な代表の順が
   分枝に合わせて動く orbital fixing より絞りが弱いことと、ヒューリスティクスの解が SST に反して捨てられやすいこと。伝播だけにしてもこの 2 つは変わらないので、

### 5.5 cwrh: HiGHS 式の付け方 × シグモイド、LIT_EXPLAIN も σ で連続に (利用者の依頼、2026-11-20)

利用者の方針「ENOMOTO 式の衝突スコアの付け方 (作れた衝突のリテラルだけを上げる) は捨てて、HiGHS 式 × シグモイドにする」「LIT_EXPLAIN も 0.5 という閾値で
決めるのをやめたい」を受けた形。cwr (5.4) は比べる用。

試作 (どれも既定では使わない。コミット 6f390a05e):
- `ENOMOTO_MIP_CONFLICT_WEIGHT_RAMP_HCS=1`: RAMP のとき、衝突スコアの付け方を σ によらず最初から HiGHS 式 (解析で説明に使った境界の変更全部の列を上げる)。
- `ENOMOTO_T_MIP_CW_RAMP_FLOOR` (既定 0): σ がこれ未満なら重み 0。床なしだと σ ≈ 0.007 (r̄ = 0.2) でも重み 7e-4 が残り、同点の崩し方で既定と道筋が変わった
  (mas76 1 スレッド: 既定 141903 ノード、床なし 128433)。cwrh では 0.05。
- `ENOMOTO_MIP_LIT_EXPLAIN=sig` (親の案 A): リテラルの衝突の伝播にいつも理由を付け、衝突解析 1 回で遡ってよいその理由の変更の数を round(σ × B) まで
  (B = `ENOMOTO_T_MIP_LIT_EXPLAIN_BUDGET`、16)。超えた分は理由のない外からの変更と同じ葉 (`Domain::cut_reason_budget`)。
- 部分 MIP (RINS など) では DYN・RAMP とも上げない (主の木だけ)。上げていたときは、部分 MIP の結果を通して上がらない問題でも主の道筋が変わった。
- 診断: 終わりに `MIP: conflict score diag` (解析の数、解析 1 回あたりに点数を上げた列の数、衝突を作れなかった解析の割合) と、sig のとき
  `MIP: lit explain budget` (遡った数、予算で遡れなかった変更のあった解析の数、解析 1 回で遡った数の分布)。

決め方と既定と同じ道筋の確かめ (1 スレッド・種 1、事実):
- 理由を付けるだけで道筋が変わるか: 初めの形 (予算を超えたら理由の行を返さない) では pk1 が 212422 → 211200 ノードに変わった。理由の付いた変更は「遡れる変更」に
  数えられ、多段の解析の段の作りが変わるため。予算を超えた変更を葉として扱う形に直して、σ が上がらない pk1 212422・mas76 141903 ノードが既定と一致
  (記録の手間は時間の差に出ない: pk1 81.4 / 83.1 秒)。
- 付け方を HiGHS 式の 1 本にしても重み 0 なら既定と同じか: `ENOMOTO_MIP_HIGHS_CONFLICT_SCORE=1` だけで pk1 212422・mas76 141903 ノードで一致
  (衝突スコアは分枝の点数に重み × 衝突スコアでしか効かない)。採用して ENOMOTO 式の道 (pc.add_conflict) を外しても既定は変わらない見込み。

## 6. 部分木ごとに衝突の重みのずれを学ぶ (利用者の依頼、2026-11-20、どれも既定では使わない)

## 8. cwrh0 で neos-933966・neos5 が遅くなる原因 (利用者の依頼、2026-11-20、事実と判断の案)

そのため「1 つだけ入れた形」は r (RAMP だけ)、「1 つ外した形」は rh (sig を外す)・rx (HCS を外す) で代える。
床ありの cwrh (σ < 0.05 で重み 0) も並べた。台本は dyncheck.sh (構成 r・rh・rx)。ログは logs/slow.txt (4 スレッド)・slow1.txt・diag1.txt (1 スレッド)・dyn_*.log。
診断を足した (RAMP 指定時だけ、選び方には使わない): `MIP: cw ramp diag`。衝突の項を 0 にしたときと比べて、擬似費用の点数の 1 位が変わった回数を数える。

### 8.2 読み

- **neos-933966 の遅さは部品のせいではない。** def 自体が 1 スレッドで再現しない。
  - 同じ種・同じ時間上限で 2 回流すと、根までは同じだが、3 ノード目の LP 反復数が 13848 と 14680 にずれる。

    (時間上限を変えると根の乱択丸め (OBJPROBE r) の回数も変わる。予算が時間上限の 2% のため。)
  - この問題は「数百ノードで解ける道」と「数千ノードで時間切れになる道」に二分される。def・r・rh・rx・cwrh0 のどれも両方に落ちる。

  - cwrh が 4 スレッドで 3 回とも良い道だったのも運で、1 スレッドでは時間切れだった。

### 8.3 直し案 (1 問に合わせない形)

  - 問題名や問題ごとの値には頼らず、r̄ だけで決まる。
  - 向きは次のとおり:
    - neos5: def と同一 (1 スレッドで確かめ済み)。
