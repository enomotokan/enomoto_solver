# greenbea 正答性バグ分析（実行可能な LP を `infeasible` と誤判定）

対象: NETLIB `greenbea`（2392 行 x 5405 列, 30,877 nnz; `.netlib_cache/mps/greenbea.mps`）。
記録（`scripts/benchmark_results.json`）: HiGHS `kOptimal` obj = -72555248.12984587（0.22 s）、本ソルバ `infeasible`（1.92 s）。
本セッションで同一ハーネスにより再現（4 回、毎回同一の反復 4715 で同一の数値 → 決定的）: ours `infeasible` 1.80–1.96 s、HiGHS optimal 0.21–0.23 s。

計測環境: HiGHS 1.15.1 (`highspy`)、本クレート HEAD `ff4dca7`。診断用の一時パッチは `src/simplex/extended_dual.rs`（および `BIG_M` 実験のため `src/simplex.rs`）に当てたが、すべて `git checkout` で戻し、元のホイールを再インストールした（コミットなし、`git status` クリーン）。

## 結論（要約）

1. **presolve は無関係**。`ENOMOTO_DEBUG_PRESOLVE_INFEAS=1` は `infeasible=false unbounded=false`、presolve 後サイズ 2056 行 x 4645 列（HiGHS presolve は 951 x 2989）。5012 列が `ub=+inf` の片側無限列なので `had_unbounded_structural=true` となり、`extended_dual::solve_lp_dual_extended`（記号的 M の双対単体法）に入る。
2. **誤判定の場所**: `src/simplex/extended_dual.rs` 主ループ、BFRT ウォークが候補を使い切った直後の `return Some(SimplexResult { status: Status::Infeasible, .. })`（`ENOMOTO_DEBUG_EXT_INFEASIBLE` の `site=bfrt_exhausted`、元ソースで約 2378 行目、`let Some(k_star) = k_star else { ... }` ブロック）。反復 4715、行 r=1501、基底変数 4236（`lb=0, ub=+inf`, M フラグ付き）、候補は 1 本（列 4262, `hat_alpha = -1.0` ちょうど, `d[j] = -1.37e-7`）。
3. **機序**: 行の偏差 `w_r = (3.01e-7, 0.99999999999998)`（`base + slope*M`）に対し、唯一の候補の反転容量は `cum = (0, 0.9999999999999998)`。`Affine1::cmp_lex`（約 676 行目）は slope を相対許容 1e-9 で「等しい」と判定し、base 側は `base_scale = max(|a|,|b|,1.0)` の下限 1.0 のため**絶対 1e-9** で比較する。3.0e-7 > 1e-9 なので「まだ足りない」→ 候補を使い切った → `Infeasible`。
   しかし、この 3.0e-7 は数値誤差である。判定時点で `lu.update_count()=47`（Forrest–Tomlin 更新 47 回）、**基底を再分解して解き直すと `x_b[r] = (-0.0, -1.0)` ちょうど**（反復改良でも `-0.0`）。つまり真の偏差はちょうど M で、反転容量 M がちょうど覆う（`cmp_lex` は `Equal` を返し `k_star` が決まる）。同時点の維持 x_B と再計算 x_B の base 成分の最大差は 2.4e-3、ドリフト検査の許容は 50 回の drift 再分解による段階拡大で 1e-4（`XB_DRIFT_TOL=1e-8` → `XB_DRIFT_TOL_MAX=1e-4`）。**「x_B は 1e-4 までのドリフトを許すが、infeasible 判定は 1e-9 で行う」という許容誤差の不整合**が直接原因である。分類: 数値的問題（許容誤差の不整合 + 更新済み LU の誤差）であり、presolve の論理バグではない。
4. **最小修正案（根拠あり）**: `bfrt_exhausted` に到達したとき `lu.update_count() > 0` なら、`Infeasible` を返さずに再分解 + x_B/d/InfeasibleRows の再同期を行い、その反復をやり直す（同ファイルの `update_verify` 失敗時の discard パス、約 2715–2760 行目と同じ手順）。**新鮮な分解から判定した場合にのみ `Infeasible` を宣言する**。実験（env ゲートの一時パッチ）で反復 4715 の誤判定は消えた。
5. **ただし、これだけでは greenbea は正解に到達しない**（重要）。修正 4 の後、軌道が変わり反復 ~6006 で `|alpha_q| = 7.2e-8` のピボット（`FT_MIN_PIVOT=1e-7` 未満、CHUZC の篩は `TOL=1e-9` のみ）を確定し、直後の再分解が特異（`refactorize` が `None`）→ 拡張法が `None` を返す → 古典 `BIG_M=1e7` パスへフォールバック → **`optimal` だが目的関数値 -72465273.02（真値 -72555248.13、相対誤差 1.2e-3）を返す**。原因は真の最適解に `x_4180 = 3.3e8`, `x_4175 = 2.3e8`（HiGHS の解）があり、`BIG_M=1e7` が実行可能領域を切り落とすため。`BIG_M=1e10` にするとフォールバック自身が `infeasible` を返す。つまり修正 4 単独では「誤った infeasible」が「誤った optimal」に変わる（黙って間違う分だけ悪化しうる）。これも報告が必要。
6. **その下にある設計上の問題**（副次的だが本質的）: `cmp_lex` の slope 側絶対下限 1e-9 は、真の（雑音でない）slope 3.3e-10 を 0 とみなす一方、それをピボット `alpha=-0.03` で割った 1.08e-8 は決定的とみなす。この不整合により、反復 8000 以降で行 1371 上の変数 177/337 が 2 サイクルで永久に入れ替わる（stall 検出は slope 側の「進捗」により発火せず）。下限を 1e-13 に下げると今度は雑音 slope 3.6e-19 が決定的になり別の偽 infeasible が出る。固定の下限では真値と雑音を分離できない。

### 1.1 presolve は宣言していない

```
$ ENOMOTO_DEBUG_PRESOLVE_INFEAS=1 ENOMOTO_PROF_PRESOLVE=1 ENOMOTO_DEBUG_PRESOLVE_SIZE=1 \
  .venv/bin/python -m enomoto_solver.benchmark_highs --worker greenbea --cache-dir .netlib_cache
PROF_PRESOLVE total 48.261ms
DEBUG_PRESOLVE: infeasible=false unbounded=false
PRESOLVE_SIZE n_vars_in=5405 n_rows_in=2392 n_vars_out=4645 n_rows_out=2056
```

presolve ルールの二分探索は不要と判断した（宣言主体が presolve でないことが上記で確定しているため）。presolve が生成する `StdForm` が数値的に不利かどうかは未検証（presolve を丸ごと無効化する環境変数は存在せず、`ENOMOTO_DISABLE_FREEVAR` は greenbea の freevar 除去が 0.08 ms で実質何もしていないため無意味）。

- 4 回の実行すべてで同一（iter=4715, 同一 `w_r`/`cum`）。
- 再分解 50 回はすべて x_B ドリフト検査（`XB_CHECK_INTERVAL=5` ごと）によるもの。`ENOMOTO_DEBUG_XB_DRIFT_EXT=1` では、反復 4687–4712 の維持 x_B 残差ノルム（base）は 3.3e-7 〜 1.4e-6、`drift_trigger_count=50`、`effective_tol=1e-4`（段階拡大後）。`ENOMOTO_DEBUG_D_DRIFT_EXT=1` では `d` の相対ドリフト 1.6–2.6%（`D_DRIFT_TOL=1.0` なので発火しない）。
- `eligible_empty` サイト（候補ゼロ）は一度も infeasible を出していない（`noise_feasible` の救済で処理されている）。

### 1.3 判定に使われた数値は更新済み LU の誤差（一時パッチで検証）

判定サイトに一時的な診断（`compute_rhs_affine` + 現在の LU で解き直し、さらに `refactorize` で新鮮に分解して解き直し + 反復改良 1 回）を挿入した結果:

```
DIAG row r=1501 bv=4236 std.b[r]=0 lb=0 ub=inf delta_bv=1 maintained x_b=(-3.0096e-7,-0.9999999999999851)
     hat_l=(0,0) hat_u=(0,1)                       <- 基底変数 4236 の下限 0 を M+3e-7 だけ割っている、という判定
DIAG fresh (updated LU, update_count=47) x_b[r]=(-1.2030e-7,-0.9999999999999875)   diff_base=1.8e-7
DIAG max|fresh-maintained| over rows: base=2.446e-3 slope=1.17e-10
DIAG fresh-refactor x_b[r]=(-0e0,-1e0) refined_base=-0e0     <- 新鮮な分解では偏差はちょうど M
DIAG cand j=4262 status=Upper hat_alpha=-0.9999999999999998 d[j]=-1.3658e-7 ratio=1.3658e-7 delta=1 lb=0 ub=inf width=(0,1)
```

`std.b[r]=0`、列 4262 と基底列 4236 は係数 ±1 で結ばれており（`hat_alpha=-1` ちょうど）、4262 が M 側にあるため 4236 = -M。列 4262 を 0 側へ反転すれば 4236 = 0 で実行可能。これは真に「反転容量が偏差をちょうど覆う」ケースであり、`cmp_lex` の docs 自身が `degen2` で経験した「一致すべき二つの Affine1 が別経路の丸めで食い違う」問題の base 側版である。base 側の許容は `max(|a|,|b|,1.0)*1e-9 = 1e-9`（絶対）、対して更新済み LU の誤差は 1.2e-7〜3.0e-7。

## 4. 修正 A/B の後に現れる 2 サイクルの機序（`cmp_lex` の slope 下限）

反復 8000 以降のトレース（一時パッチ `ENOMOTO_EXP_TRACE_FROM=8000`, 実験 B 下）:

```
iter=8000 r=1371 bv=177 d_dir=1 w_r=(4.426e0,-3.292e-10) ncand=1510 q=337 alpha_q=-3.035e-2 ratio=8.12e2
iter=8001 r=1371 bv=337 d_dir=1 w_r=(-1.458e2,1.085e-8)  ncand=570  q=177 alpha_q=-3.295e1  ratio=2.47e1
iter=8002 r=1371 bv=177 ... (以下 10,000 反復以上同じ 2 サイクル、pool=302 固定、stall_count=0)
```

新鮮な分解 + 反復改良で確認: `x_177 = (-4.4261, +3.2925e-10)`（slope の改良補正 7e-22、残差ノルム 8e-17）、`x_337 = (145.82, -1.0847e-8)`。**slope は雑音ではなく真の値**である（この LP の係数は double で正確、B^{-1} の像として well-defined）。
- bv=177: `x = -4.43 + 3.3e-10·M` は M→∞ の意味では実行可能（正）だが、`cmp_lex` は slope 3.3e-10 < 1e-9 を 0 とみなし base -4.43 で「下限割れ」と判定。
- 337 が入ると `theta_slope = 3.3e-10 / 0.0303 = 1.08e-8` で slope が 1e-9 を超え、今度は「1.08e-8·M だけ下限割れ」（base は +145.8 なのに）と判定。
- 177 が戻り元に戻る。目的関数の寄与は slope 側で「正」なので `stall_count` は毎回リセットされる。`infeasible_plateau` 検出は pool=302 固定で数え続けるが、`stall_limit = (5*m).max(500) = 10280`、`infeasible_plateau_limit = 4*stall_limit = 41120` であり `MAX_ITERS = 20000`（`simplex.rs:140`）より大きいので、greenbea の規模（m=2056）ではこの検出器は原理的に発火できない。結果、`bland_mode=false` のまま `MAX_ITERS` に到達し `None` → BIG_M フォールバックとなる。

固定下限の限界: 真の slope 3.3e-10 vs 雑音 slope 3.6e-19（実験 C）の間に安全な閾値はこの問題では 1e-12 前後にあるが、雑音レベルは cond(B) 依存で一般には保証できない。

## 5. 副作用確認（全問題ベンチマーク, baseline vs 修正 A）

全 93 問題（`--max-vars 100000 --timeout 60`）を baseline と修正 A（`ENOMOTO_EXP_EXHAUST_REFACTOR=bfrt`）で各 1 回実行し、状態・目的関数値（HiGHS 比の相対誤差）・時間を突き合わせた（CSV: scratchpad `netlib_baseline_full.csv` / `netlib_fixA_full.csv`、リポジトリには置いていない）。

- 状態または目的関数値が変わった問題: **greenbea のみ**（`infeasible` → `optimal` だが相対誤差 1.24e-3 の誤答、1.97 s → 5.07 s）。
- 他 92 問題: 状態同一、目的関数の相対誤差差 < 1e-7、`dfl001` は両方とも 60 s タイムアウト。
- 時間: optimal 同士 91 問題の合計 45.32 s → 45.24 s（0.998x; 改善 51 / 退行 28 / 同一 12、最大退行は `maros-r7` +0.25 s = 5%、いずれも実行間ばらつきの範囲）。

つまり修正 A は「`bfrt_exhausted` で更新済み LU から判定していた問題」にしか作用せず、NETLIB 上で当該経路を踏むのは greenbea だけである（他問題でこの経路が一度も発火しないことは、状態・目的関数・時間が不変であることから間接的に裏付けられる）。

## 6. 推奨する修正（優先順）

1. **[必須・最小] `extended_dual.rs` の `bfrt_exhausted`（および対称的に `eligible_empty` の `noise_feasible` 不成立側）で、`lu.update_count() > 0` のときは `Infeasible` を返さず、再分解 + `compute_rhs_affine`/`solve_into`/`infeasible_rows.rebuild`/`fresh_d_into`（`update_verify` 失敗時の discard パス、約 2743–2757 行目と同一手順）を実行して `continue` する。** 「更新済み LU の状態から infeasible を宣言しない」は古典法 `simplex.rs::solve_lp_dual_on` にも無い保護だが、`cmp_lex` の 1e-9 絶対許容が `XB_DRIFT_TOL_MAX=1e-4` より 5 桁厳しい以上、判定は新鮮な分解に限るべき。効果: greenbea の偽 infeasible は消える（本セッションで確認）。リスク: 再分解 1 回分のコスト（数十 ms）が、真に infeasible な問題で 1 回だけ追加される。副作用は §5。
2. **[必須] 修正 1 の後に露呈する「誤った optimal」を防ぐ**。少なくとも (a) 拡張法が `None` で BIG_M パスにフォールバックした場合、`BIG_M` に張り付いた変数（`|x_j| ≥ BIG_M·(1-1e-6)`）があれば `optimal` ではなく別の状態（例: `Status::NumericalFailure`/`Unknown`）を返す、または目的関数を返さない。greenbea では `x_4180=3.3e8 > 1e7` なので確実に検出できる。(b) 根本的には、7.2e-8 のピボットを確定させない CHUZC（Harris pass 1 をピボット倍率で緩める、または `FT_MIN_PIVOT` 未満のピボットしか無い場合は行 r を棄却して `discard_row` と同じ扱いにする）。ただし後者は `cycle`/`degen3` で反例が記録されている（`HARRIS_RATIO_TOL` docs, `simplex.rs:4025–4040`）ので、単純なスキップ（実験 D）は不可。
3. **[設計課題] `Affine1::cmp_lex` の slope 側下限**。固定の絶対下限（現 1e-9）では真の微小 slope（3.3e-10）と雑音（3.6e-19）を分離できず、2 サイクル（§4）か偽 infeasible（実験 C）のどちらかになる。候補: (i) 比較を「固定の評価点 M* での数値 `base + slope·M*`」で行う（記号的 M の帳簿は維持しつつ比較だけ一貫させる。M* は `BIG_M` と違いデータに代入されないので桁落ちを起こさない。ただし M* の選定問題は残る）、(ii) 論文 §4.2 の S 制限（docs で「HiGHS と一致したが 7.9→9.6 s の退行で戻した」とある版）を greenbea で試す、(iii) slope が下限内のときは `theta_slope` も 0 に丸めて一貫させる（状態の整合性を壊すため要ドリフト検査との整合）。本セッションでは実装・検証していない。
4. **[参考] presolve の縮約率**（2056 行 vs HiGHS 951 行）は性能課題であり本件の原因ではない。

## 7. 最小再現
