# §3.1: Markowitz カーネル能動部分行列のフラット配列化 — NETLIB93 A/B

対象: `docs/lu_comparison_enomoto_vs_highs.md` §3.1 / §4-5 の項目
「`MarkowitzState` の `Vec<BTreeMap<usize,f64>>`(行)+ `Vec<BTreeSet<usize>>`
(列ミラー)を HiGHS の `mc_*`/`mr_*` 相当のフラット配列に置き換える」。
同ドキュメントが「参考度:高、ただし最大のリファクタリング」「単純置換は
`FixedRows` 回帰と同様に負ける可能性も。要注意」と書いていた唯一の未計測項目。

実装は `a4e29bf`(本体)+ `7289525`(初期スラック撤去)で入り、`17c33d3` で
`main` にマージ済みだったが、**この変更単独の A/B は取られていなかった**
(`6c8edce` は searchLimit=8 とのマージ後の状態を再計測しただけで、before が
無い)。本ドキュメントはその欠けていた計測である。

## 0. 計測方法

- **after アーム** = `6c8edce`(= `main` HEAD)そのまま。
- **base アーム** = 同じ `6c8edce` から `a4e29bf` と `7289525` だけを
  `git revert` したツリー。競合は3点(import、`MarkowitzState` のフィールド、
  `find_best_pivot` の内側ループ)で、いずれも **searchLimit=8 (`2840f7b`) を
  残したまま** BTreeMap 側へ戻す形で解決した。つまり2アームの差は C-1 のみで、
  §2.5 の探索上限は両アームに入っている。
- 4 コア、rustc 1.94.1、highspy 1.15.1 / Python 3.11、NETLIB93 **全93問**。
  両アームは別々の venv に `maturin develop --release` で入れ、実行ごとに
  ビルドし直さない(ビルド順による差が入らない)。
- `python scripts/run_full_benchmark.py` を **base → after の順に交互で3周**。
  問題ごとの代表値は3周の**中央値**。10%ルールはこの中央値に対して適用する。
- 中央値で10%以上退行した問題、および重い問題については、その問題だけを
  **交互に15回(軽い問題)/ 5回(重い問題)** 追試した。この箱の軽い問題
  (1〜50ms)は1回計測のばらつきが ±20〜30% あり、3周では判定できないため。
- `cargo test --release` は両アームとも **222 passed / 0 failed**。

## 1. 経路保存の確認(これが計測の前提)

C-1 は「同じ順序の容器を、同じ順序を保つフラット配列に替える」変更として
設計されている(`KernelMatrix` の docs が明記: 行・列の run を**昇順に保つ**
のは HiGHS の末尾swap無順序集合より高いが、`find_best_pivot` のスコア同点・
ピボット絶対値同点が first-encountered で解決される以上、順序を崩すと選ぶ
ピボットが変わり「何を計測しているのか」が分からなくなるため)。

実測でそのとおりだった:

- 93問すべてで `ours_status` / `ours_obj` が**両アーム・全周で完全一致**
  (唯一 `wood1p` だけ実行ごとに揺れるが、これは同一バイナリでも起きる既知の
  非決定性 — `SYNTH_CLOCK_FACTOR` の較正が実時間を読むため再分解タイミングが
  走行ごとに変わる。`scripts/loop_state.json` に既出)。
- HiGHS との目的関数値の相対差 >1e-6 は **0件**。
- `ours_iters` / `ours_refactor_count` も一致。たとえば `pilot87` は両アームとも
  iters=6735、refactor_count=62、`pivot_search steps=89884 candidates=377860`
  まで同一。

つまり本 A/B は**アルゴリズムの経路を一切変えず、データ構造のコストだけを
比べている**。反復数の変化で結果が説明できてしまう §2.6 のときとは違い、
時間差はそのまま構造の差である。

## 4. 機序(なぜ効いたか、どこで効いたか)

`ENOMOTO_PROF_PHASES_EXT` のフェーズ内訳(両アーム、同一反復数・同一再分解回数):

| 問題 | 指標 | base | after |
|---|---|---|---|
| pilot87 | `refactor` フェーズ | 4923ms / 4675ms | 946ms / 950ms |
| pilot87 | `pivot_search scan` | 309.4ms | 97.3ms |
| dfl001 | `refactor` フェーズ | 1431.6ms | 858.4ms |
| dfl001 | `pivot_search scan` | 182.5ms | 113.0ms |
| ship12l | `refactor` フェーズ | 1.42ms | 1.21ms |
| kb2 | 再分解回数 | 0 | 0 |

つまり:

1. **効果は `refactor` フェーズにほぼ全部集中している。** pilot87 では
   再分解が wall の 48% を占めていたのが 17% になり、これだけで約 -3.8s。
   全体の差(-4.2s)のほぼ全部がこれで説明できる。他フェーズ(price、
   dse_update 等)の見かけの差は2回取り直すと ±2〜7% に収まり、走行間の
   ばらつきだった。
2. `find_best_pivot` のバケット走査(`pivot_search scan`)も pilot87 で -69%、
   dfl001 で -38%。同じ候補数(`candidates` は両アーム完全一致)を調べていて
   これだけ縮むのは、候補ごとの `rows[i].get(&j)` が木降下からフラット run の
   線形/二分探索(`KernelMatrix::row_get`、長さ16以下は線形)になったため。
3. **`L` のフラット化(§4-5 項目5)で残った「軽い問題では圧縮形のアクセス
   コストが残る」という非対称性は、カーネル側では起きていない。** 軽い問題は
   そもそも再分解回数が 0〜3 回で、kb2 に至っては 0 回。触らないコードは
   遅くも速くもならない。同ドキュメントが警告していた「動的カーネル部分行列は
   insert/remove を繰り返すので単純置換では負ける可能性大」は、**実測では
   外れた** — ただし外れた理由は「insert/remove が安かった」ではなく、
   `eliminate` が要素ごとの挿抜ではなく**行まるごとのソート済みマージ+
   `set_row` 一括書き戻し**という形をとっており、フラット配列に有利な
   アクセスパターンに作り替えられているからである(`eliminate` の docs 参照)。
   `BTreeMap` をそのまま `Vec` に置き換えただけなら警告のとおり負けた可能性が
   高い。

## 5. 結論

**採用**(コードは `17c33d3` で既に `main` に入っており、本計測はその事後検証)。

- 全93問合計 **-11.4%**(3周の中央値、重い10問 -12.3% / 軽い83問 -1.8%)。
- 10%以上の退行をする問題は無い。
- 正答性: 93/93 optimal、目的関数値は HiGHS と相対差 >1e-6 が0件、両アームで
  ビット一致。`cargo test --release` 222件が両アームで全通過。
- 最大の勝ちは pilot87(-40%、-4.2s)と pilot(-21%)。`refactor` フェーズが
  wall の半分を占めていた問題ほど効く。

`docs/lu_comparison_enomoto_vs_highs.md` §3.1 / §4-5 の「未着手」記述を本結果で
更新した。
