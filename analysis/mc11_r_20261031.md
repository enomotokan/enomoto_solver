# hs_pi0_bgw_r (`ENOMOTO_MIP_SUBMIP_HIGHS_TRIM=r`) で mc11 が遅くなる理由 (2026-10-31)

- 機械: 4 CPU。ソルバーは同時に 1 つだけ動かした。HiGHS (highspy) は 1.15.1。
- 土台: ブランチ `ccr-1beed81b-ex0uhq` の `de63e90` (ソースは変えていない)。
- 計測: `ENOMOTO_MIP_LOG=1 ENOMOTO_MIP_THREADS=4`、60 秒・4 スレッド。
- 台本とログは `analysis/mc11_r_20261031/`:
  - `run.sh 問題 名前 設定 [環境変数 ...]` で 1 回解く。設定は `def`・`bgw` (hs_pi0_bgw)・`r` (hs_pi0_bgw_r)。
  - `batch1.sh` (mc11 を bgw・r で各 5 回、交互)、`batch2.sh` (mc11 を bgw + `ENOMOTO_MIP_BG_CUTS_LOG=1` で 4 回)、
    `batch3.sh` (eil33-2・neos5・noswot・neos17・physiciansched6-2 を bgw・r で 1 回ずつ)。
  - `summary.py` はログを再スタートごとの区間に分けて表にする (`summ.txt`)。
- 発端: `analysis/diag_hsletters_20261031.md` の追記 (58 問)。mc11 が 2 回とも hs_pi0_bgw より hs_pi0_bgw_r で遅かった
  (23.4・29.9 → 29.1・37.6 秒)。再スタート後の根のヒューリスティクスが短くなり、裏のカットが早く止められて下界が弱くなる、と推定していた。

## 1. 結論

事実:

1. **推定は違っていた。mc11 は再スタートしない** (bgw・r の 14 回とも、ログに再スタートの行がない)。
   `TRIM=r` は「再スタート後の根で作るサブ MIP」(`heuristics.rs` の `hs_drop`、`restarts > 0` のとき) にしか効かないので、mc11 では何も変えない。
   - 根のヒューリスティクスの結果 (各ヒューリスティクスと並列のサブ MIP の結果の並び) は、bgw と r で同じだった。
2. **mc11 の bgw と r の時間は同じ分布** (各 5 回):
   - bgw: 13.6・26.8・23.4・28.5・30.1 秒 (平均 24.5)
   - r: 27.4・28.7・26.4・25.0・21.3 秒 (平均 25.8)
   - 過去の 58 問の計測の mc11 も、hs_pi0_bgw は 22.5〜29.9 秒、def は 21.9〜46.8 秒と揺れる。58 問の r の 29.1・37.6 秒は、この木の揺れの範囲 (37.6 は端)。
3. **bgw の待ちは mc11 で上限に当たっていない**。最初の根のヒューリスティクスは 1.7〜1.9 秒で終わり、bgw は 1.9〜2.4 秒待つ。
   14 回のうち 13 回は、裏のカットが自分で終わる (`done`、51 ラウンド・11666.0) までで、上限 (3.4〜4.2 秒) の手前。
   残りの 1 回 (bgw_1) は 50 ラウンド・11683.4 で停滞 (`stalled`) と判定して止めた。
4. **mc11 の時間を大きく分けるのは、根の道筋の違い**。木の時間は、置き換えた後の根の下界でほぼ決まる:
   - 13 回は根の下界が 11666.0 で、21〜30 秒・木のノード 300〜520 (主のスレッドの数)。
   - bgw_1 だけ 11683.4 で、13.6 秒・112 ノード。過去の記録 (`bgcuts_wait_20261030.md` の mc11_def_3 17.1 秒、`mc11_h1_20261030.md` の既定 16.1・19.9 秒) も、11683〜11684 に届いた回だけ速い。
   - 裏のカットの道筋は、始めの状態が同じなら決まっている (`BG_CUTS_LOG` の 4 回は、ラウンドごとの目的値が全部同じで、50 ラウンド目に 11666.0 で停滞して止まる)。
   - bgw_1 は、それより前の**主の根のカットのループ**から違う。3 ラウンド目から目的値がずれ、25 ラウンド後に 11097.6 になった (ほかの 13 回は 11003.7)。
     裏のカットはその後の LP から始まるので、11683.4 に届いた。
   - 根の LP の反復数が回ごとに 512〜1220 (64 の倍数) で揺れている。目的値は同じ 608.84。

推測:

- 揺れの出どころは、根の LP を二段解法と内点法 + クロスオーバーで同時に解くこと (`simplex/mip_lp.rs` の `solve_race`) だと考える。
  どちらが先に終わるか、共有の上界で反復の進みが変わり、着く最適頂点が変わって、主のカットの道筋が分かれる。
  - beasleyC3 で同じ形が見つかっている (`ENOMOTO_MIP_ROOT_LP_IPM` の説明、`analysis/beasleyC3_r3_20261020.md`)。
  - 反復数だけでは道筋は決まらない (bgw_3 は bgw_1 と同じ 1220 反復でも 11003.7)。どちらの頂点を採ったかはログに出ていないので未確認。
- 58 問で r が 1 回だけ遅かった eil33-2・neos5・noswot も、今回の 1 回ずつでは再スタートしない。なので r は何も変えておらず、差は揺れ
  (今回 bgw / r: eil33-2 39.4 / 39.6、neos5 52.1 / 54.0、noswot 12.3 / 16.9 秒。根の流れは同じ)。

## 2. 手当て

- 原因が再スタート後の根ではないので、依頼の例 (再スタート後の根の裏のカットを続ける・待ちの上限を見直す・裏のカットの終わりを切り離す) は mc11 を変えない。**試作はしなかった**。
- 再スタートが起きる問題では、bgw の待ちは再スタート後の根でも働いていて、上限で切られていない。
  - `diag_hsletters_20261031/` の既存のログ: binkar10_1・swath1・mik-250-20-75-4・nu25-pr12・h80x6320d。今回の neos17 も同じ。
  - 再スタート後の区間の待ちの理由は、どれも `done` か `stalled`。上限 (`cap`) に当たったのは、h80x6320d の最初の根 (r と関係しない区間) だけ。
  - 例: swath1 の r の 2 回目の再スタートの後は、ヒューリスティクスが 2.2 秒で終わり、bgw が 2.3〜2.5 秒待って、裏のカットは自分で止まった (`done`、26 ラウンド)。
- mc11 の揺れを減らすなら、根の LP の頂点を決まったものにする (例: `ENOMOTO_MIP_ROOT_LP_IPM` のように片方を待って採る) のが筋。
  ただし、どちらの頂点が mc11 で 11683 に届くかはまだ分かっていない。ほかの問題への影響も大きいので、別に調べる。
