# 下界が動かないのは並列のせいか、ノードの選び方のせいか (2026-11-04、pool_bound3)

bench に使う環境変数: `ENOMOTO_MIP_POOL3_BEST=0.05` (試作、既定では使わない。58 問の設定名は p3、600 秒の回の名前は p3_005)。
診断には `ENOMOTO_MIP_POOL3_DIAG=1`・`ENOMOTO_MIP_LBNODE_DIAG=1`・`ENOMOTO_MIP_LOG=1` を付けた (600 秒・60 秒の個別の回。58 問は診断なし)。

並列 3 セッションのうちの 3 (担当: 下界が動かないのは共有の待ち行列のせいか、ノードの選び方全体のせいかの切り分け・全体の下界の計算と
報告の確かめ・広い問題での評価)。きっかけは `analysis/memcap_c_20261104.md` の「supportcase18 で下界が根の値 47.1867 から 600 秒
動かない (HiGHS は 48.0)」。4 CPU の機械、ソルバーは同時に 1 つ (1 スレッドの回の後半 3 分だけ wheel のビルドと重なった)。
計測の wheel は `edcf0204` + この試作 (rebase の前)。push の際に別セッションの変更 (`pool1_cnt`) の上に rebase した
(衝突は `pool_balance` の 1 か所で、両方を残した)。生データは `analysis/pool_bound3_20261104/`。

## 結論

### supportcase18 (切り分け)

- **並列のせいではない** (事実)。1 スレッドでも 600 秒・12.5 万ノードで下界は 47.186667 のまま (`sc18_t1_def`)。4 スレッドも同じ
  (`supportcase18_def_600s_t4`、32.7 万ノード)。
- **ノードの選び方 (最良下界か深さ優先か) のせいでもない** (事実 + 推測)。下界が全体の最小ちょうど (47.186667) のノードが
  多すぎる:
  - 4 スレッド・600 秒の終わりに、共有の待ち行列 30.3 万ノードのうち **11.6 万ノードの下界が 47.186667 ちょうど** (事実、診断の分布)。
    60 秒で 1.5 万 → 300 秒で 5.8 万 → 590 秒で 11.6 万と増え続ける。
  - 処理したノードの 2〜5 割は下界が全体の最小のノード (10 秒あたり 3500〜8600 ノードのうち 600〜2900、事実)。つまり最小のノードは
    ちゃんと処理されているが、その子 (子の下界 = 親の LP の値) の LP の値もまた 47.186667 で、最小のノードが減らない。
  - 試作 (`ENOMOTO_MIP_POOL3_BEST=0.05`、0.05 秒おきに全体の最小のノードを必ず処理する) を入れると、最小ちょうどのノードは
    44.6 万に増えるだけで、下界は動かない (事実)。
  - LP の値が分枝で上がらない (双対退化・対称性。orbital fixing が効く問題) のが原因で、良いノードを先に処理しても下界は
    上がらない (推測。分枝の後の LP の値の変化そのものは数えていない)。動かすには、カット・対称性の扱いなど根や節の下界そのものを
    強くする必要がある。
- **HiGHS の「48.0」は目的値が整数なことによる切り上げの見込みが大きい** (事実 + 推測)。HiGHS 1.15.1 (1 スレッド・60 秒) の経過の
  行は最後まで 47.18666667 で、終わりの報告だけ `Dual bound 48` (「Objective function is integral with scale 1」)。
  600 秒・4 スレッドの HiGHS の途中の下界は見ていないので、600 秒で 47.19 を超えていたかは確かめていない。
  ENOMOTO は報告の下界を目的値の刻み (`obj_step`) で切り上げない。切り上げれば supportcase18 は 48、ギャップ 4.0% → 2.0% (50 に対し)
  になる (報告の仕方だけの差。刈り込みでは既に刻みを使っている)。

### 全体の下界の計算と報告 (確かめ)

- 一時の診断 `ENOMOTO_MIP_POOL3_DIAG` で、主が 10 秒おきに「報告に使う全体の下界 (`global_lower_bound`)」と「全ノードを数えた
  最小」(共有の待ち行列の全ノードを走査・各スレッドが処理を始めるたびに手元の待ち行列の全ノードを走査して書いた値・自分の待ち行列と
  処理中のノード) を比べた。**全ての行 (1 スレッドの回 + 4 スレッドの 31 回、728 行) で差は 0** (事実)。共有の待ち行列の索引の最小 (`min_lower_bound`) と
  走査の最小も全て一致 (638 行)。
- コードを読んで (事実):
  - 経過の行の全体の下界 = 自分の待ち行列・処理中のノード・共有の待ち行列の最小・各スレッドの `slots` の `lb` (処理を始めたノードと
    手元の待ち行列の最小) の最小。潜りの子は親の LP の値以上なので、処理中の親の値で覆われる。
  - 利用者に返す `bound` = 主の `finish_limit` (自分の待ち行列と処理中のノード) と `join_workers` (各従が返した下界と、従が
    止まるときに共有の待ち行列に返したノードを含む共有の待ち行列の最小) の最小を、根の LP の値で下から抑え、暫定解で上から抑えたもの。
    取りこぼしは見つからなかった。
  - 1 か所だけ、ずれうる所: `pool_balance` は共有の待ち行列から取ったノードを、錠を外してから自分の `slots.lb` に書く
    (`pool_acquire` は錠の中で書く)。その間に経過の行を作ると、そのノードがどこにも数えられず全体の下界が一瞬高く出うる。
    経過の行にしか効かず (終わりの `bound` は `join_workers` で決まる)、診断では起きていない。
  - 診断の限り: ほかのスレッドの手元の分は「処理を始めたとき」の値なので、その後 `pool_balance` で取ったノードは次のノードまで入らない。

### 試作 `ENOMOTO_MIP_POOL3_BEST=T` の効き目

- T 秒おきに (全スレッドで 1 回)、全体の最小の下界のノードをどれかのスレッドが必ず処理する: 共有の待ち行列にあれば取って次に処理し、
  自分の手元にあれば潜りをやめて下界最小を取り、ほかのスレッドの手元にあればそのスレッドに合図する。1 スレッドでは T 秒おきに潜りを
  やめて下界最小を取る。
- 600 秒・4 スレッド (T = 0.05、診断つき。目的値・下界は worker の結果、* はログの最後の行から):

| 問題 | 型 | 既定: 暫定解 / 下界 / ノード | 試作: 暫定解 / 下界 / ノード | 試作で強制した回数 (共有の待ち行列から / 合図) |
|---|---|---|---|---|
| supportcase18 | 平ら | 51 / 47.1867 / 32.7 万 | 50* / 47.1867* / 47.8 万* | 11714 (11521 / 90) |
| csched008 | 平ら | 173* / 171* / 6.0 万* | **解なし** / 171 / 8.7 万 | 9982 (9697 / 385) |
| icir97_tension | 置き去り | 6381 / 6355.46 / 16.0 万 | 6387 / 6354.66 / 12.6 万 | 10560 (9382 / 1133) |
| neos-3024952-loue | 置き去り | 29285 / 25445.88 / 5.5 万 | 32978* / **25783.24*** / 4.9 万* | 1505 (1222 / 3012) |
| glass4 | 置き去り | 1.6000e9 / 8.000065e8 / 61.9 万 | 1.7000e9 / 8.000063e8 / 63.1 万 | 10906 (8374 / 3058) |

  - neos-3024952-loue: 既定は 600 秒間 25445.88 から動かず、その値のノード 100〜200 個が共有の待ち行列に残り続けた。試作は 182 秒で
    25781 (根の下界からの進みは 暫定解 29285 とのギャップの約 8.5%。mitt600 の HiGHS は 26340)。ただし暫定解は悪い (32978 対 29285)。
  - csched008 は試作で 600 秒間解が見つからなかった (既定は 174 → 173)。潜りを頻繁に止めるので潜りで解を見つける機会が減った見込み

- 58 問 (60 秒・1 回): 解けた数 既定 43 対 試作 41、SGM 16.73 対 17.20 秒 (3 節)。少し悪い (揺れの範囲とも区別できない)。

- **既定にはしない**。置き去り型でも効くのは一部で、解の見つかり方に害がありうる。置き去りの本筋は「`pool_donate_n` が良いノードを
  出す」「取ったノードがまた出される」の方 (セッション 1・2 の担当) と見られる。

## 1. 調べ方

- 診断 `ENOMOTO_MIP_POOL3_DIAG` (`src/mip/solver.rs` の `pool3_diag_line`): 主が 10 秒おきに 1 行 `POOL3_DIAG:` を出す。
  報告の全体の下界 (reported)・全ノードを数えた最小 (counted)・打ち切り値 (inc)・前の行からの処理ノード数とそのうち下界が前の行の
  全体の最小以下のもの・共有の待ち行列の索引の最小と走査の最小・大きさ・下界の分布 (全体の最小ちょうど / ギャップの 1% 以内 / 10% /
  50% / それより上)・各スレッドの `slots.lb` / 走査した最小 / 手元の数。各スレッドは処理を始めるたびに手元の待ち行列を走査して
  `ThreadSlot::dlb` に書く (診断のときだけ)。
- `ENOMOTO_MIP_LBNODE_DIAG` (既存): 取り出したノードの種類 (潜りの子・兄弟・下界最小・推定値・共有の待ち行列) ごとの数と、そのうち
  全体の最小だった数。
- 回し方: `run_one.sh` / `run2.sh` (`scripts/run_miplib_benchmark.py --worker-ours` を診断つきで)。表は `series.py` (時刻ごとの表)・
  `classify.py` (60 秒の型分け)・`pick.py` (mitt600 から抜き出し)。
- 注意: 600 秒の回のうち 3 本 (supportcase18 p3_005・csched008 def・neos-3024952-loue p3_005) は、走っている途中で空の `.out` を
  コミットし、その後の rebase が作業ツリーのファイルを置き直したため worker の JSON が失われた。値は stderr のログの最後の
  `POOL3_DIAG` の行 (終わりの 10 秒以内の全体の下界) と `MIP:` の経過の行 (暫定解、主のノード数 + `worker nodes`) から取った。
  `.out` は空のまま残した。

## 4. 試作の中身 (`src/mip/solver.rs`)

- `ThreadSlot` に `dlb`・`dlb_set` (診断) と `force` (合図)、`WorkPool` に `pool3_ms` (最後に強制した時刻)、`Solver` に
  `pool3_force`・`pool3_stats`・`pool3_diag_at`・`pool3_diag_at_best` を足した。
- `pool3_tick`: 釣り合いの所 (毎ノード) で呼ぶ。`pool3_ms` を CAS で取れたスレッドだけが、共有の待ち行列の最小・自分の手元の最小・
  ほかのスレッドの `slots.lb` を比べ、共有の待ち行列にあれば取り (`pool_balance` と同じく待っている側に数えられていれば戻し、
  錠の中で自分の `slots.lb` に書く) `pool3_force`、自分なら `pool3_force`、ほかなら `force` を立てる。
- ノードの選び方: `pool3_force` か `force` が立っていれば、潜りの子を待ち行列に戻し、兄弟へも戻らず、`pop_best` で取る。
- `ENOMOTO_MIP_POOL3_TAKEN=1`: `pool_balance` で取ったノードにも `pool3_force` を立てる。
- どちらの環境変数もなければ、追加した所は全て飛ばす (既定の動きは変わらない)。
- 終わりに `MIP: pool3 (tid t): forced best-bound picks …` を出す (`ENOMOTO_MIP_LOG=1` か診断のとき)。
