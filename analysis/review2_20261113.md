## 誤答: unitcal_7 が実行不能と出る (TREE2_FORCEQ の許容誤差、直した)

- 事実 (分担 M5 の報告、a6a28867): unitcal_7 が base を含む全設定・種 1・2 で 5〜14 秒・0 ノードで infeasible (正しくは最適値 約 19635558)。
  81ca14d6 (cand1113 の計測ビルド) でも同じ。切り分け (`review2_20261113/wrong/split.py`・`split.jsonl`):
  既定は正常、base から外して正常に戻るのは DUALEQ だけ、def + DUALEQ=1 だけで誤る、def + DUALEQ=1 + TREE2_FORCEQ=0 は正常。
- 判定の場所: プロービングの後の DUALEQ (late) が 244 行を等式にし、かけ直しの前処理で TREE2_FORCEQ が 2 項等式を 376 本足し、根の最初の LP が実行不能。
- 最初に破る手順: DUALEQ の前後の問題を書き出し (診断 `ENOMOTO_MIP_DEBUG_DUMP_DUALEQ`)、等式にした後の問題を HiGHS で解いた実行可能な点を
  TREE2_FORCEQ の等式に当てると 376 本中 167 本を破る (`wrong/check_pt.py`)。たとえば行 `x_a + x_b - 1000 y = 0` (x_a ∈ [0, 1000]、
  x_b ∈ [0, 1.002e-6])。DUALEQ がこの行を等式にしたのは x_a (費用 0、上向きの錠はこの行だけ、上限 1000 に当たる前に等号になる) による正しい縮約。
  TREE2_FORCEQ は y = 1 での活動の上限 1000 + 1.002e-6 と右辺 1000 の差を、許容誤差 1e-9 × (係数の和 約 3000) の中として「強制される」と見なし、
  `x_b = 1.002e-6 y`・`x_a = 1000 y` を作って点 (y = 1, x_a = 1000, x_b = 0) を切っていた。**誤りは TREE2_FORCEQ (既定の部品)** で、DUALEQ なしでも
  上限の極めて小さい列を含む等式行があれば起こりうる。
- 直し (40e80904): 一致の許容誤差を絶対値 1e-9 (和の丸めの分だけ `8ε × 係数の和` まで広げる) に締めた。回帰テスト `tree2_forceq_rejects_near_forcing_rows`。
  `cargo test --release --lib` 413 通過・0 失敗。直した後の unitcal_7 (60 秒): def + DUALEQ=1・base・cand1113 とも種 1・2 で時間切れ (暫定解 19647842〜19934014、
  どれも最適値以上)。
- REVIEW2 の計測 (a6a28867) は直す前のビルドなので、unitcal_7 の行は集計から外す。ほかの問題で TREE2_FORCEQ の直しが道を変えるかは見ていない。
