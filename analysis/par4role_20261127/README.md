依頼: 4 スレッドで伸びない問題がどこで時間を使っているかを、スレッドごとに見て、手分けの改良の候補を値打ちの順に挙げる。試作はまだ作らない。

## 1. 240 問の 4T / 1T の比 (`speedup.py` → `speedup.txt`)

- 入力: analysis/combo3_20261126/s2 の既定 (def_t1・def_t4)、MIPLIB 240 問、種 1・600 秒 (ビルド 4d84a33cd ほか、240 問を 11 分担で回した版)。
- 時間の比は 1T の時間 / 4T の時間 (shift 1 秒、時間切れは 600 秒)。1 より大きければ 4T が速い。4T は種 1 回なので、1 問ごとの比には揺れが入る。

| | 問題数 |
|---|---|
| 両方で解けた | 87 |
| 4T だけ解けた | 21 |
| 1T だけ解けた | 0 |
| どちらも解けない | 132 |

- 両方で解けた 87 問: SGM 1.62。分位は最小 0.42・10% 0.84・25% 1.04・中央 1.48・75% 2.27・90% 2.95・最大 16.6。

- どちらも解けない 132 問: 600 秒の時点の相対ギャップは 4T が小さい 81 問、大きい 14 問、同じ 37 問。

## 2. HiGHS (4T) と SCIP の手分け

HiGHS 1.15.1 のソースを読んだ (別のエージェント。タグ v1.15.1 と master)。計測で比べている highspy==1.15.1 の既定の動き:

- **木の探索は 1 スレッド**。並列の木 (HighsMipWorker、ラウンド同期型) は 1.15 で試作として入ったが、`parallel=on` のときだけ使う (既定は "choose")。
  既定で並列の木になるのは 1.16 から (master の FEATURES.md)。
  → 計測の「HiGHS 4T」は、木については 1T と同じ。
- 根で並行して動くのは 2 つだけ: 対称性の検出と、解析的中心 (IPX) の計算。どちらも根の LP の前に TaskGroup に出し、主はそのまま根の LP とカットの周を進める。
  解析的中心は、分離が 5 周を超えたとき・根の終わり・再スタートの前に待ち合わせる。
- クリーク表の近傍の問い合わせは、要素が 10 万以上なら for_each で分ける。
- MIP の中の LP は並列の単体法を使わない。Feasibility Jump は根の前に直列で回す。RINS・RENS のサブ MIP も 1 スレッド。
- SCIP (9・10 の既定) は直列。並行の求解は `SCIPsolveConcurrent` を明示的に呼んだときだけ。

当方との違い:
- 当方は 4T で、木を 4 本で分ける。そのうえ、FJ・Local-MIP のスレッド、背景のカット、根の並列のサブ MIP、強分枝の投機 (PARSB)、木の中のヒューリスティクスの役 (ALNS) を重ねている。
- HiGHS は並列の木を持たず、根の重い計算 2 つを裏に回すだけ。すき間の小さい形で、遊ぶスレッドも食い合いも少ない。代わりに 4T の伸びはない。
- 当方が 4T で HiGHS に勝つ余地は木の並列にある。一方、根で閉じる問題では、HiGHS と同じく裏で何か 1〜2 つ回す程度しか伸ばしようがない。

取り合いの証拠は見ていない。木の 4 本の区間で 1 ノードあたりの秒が増えているか (メモリ帯域の取り合い) は、今回の測り方では分からない。

## 4. 改良の候補 (値打ちの順)

前提:
- 前の調べ (analysis/paridle_20261126) は、木の段の遊び (9.9%) だけを数えていた。今回、遊びの 78% は根にあると分かった。
- 4T の伸びの余地は、根で遊んでいる 2〜3 本にある。
- どの候補も、強さは今ある量のシグモイドで連続に決め、新しい閾値は作らない。

1. **根の空いたスレッドに、解探しと木の先回りを配る (根の手伝い)。** 根の型 1〜4 にまとめて効く。値打ちは最大。
   - 形: 主が根 (カットの周・ヒューリスティクス・背景のカットの待ち) にいる間、空いているスレッド (4 − 動いている本数) に仕事を出す。
     - 解探し: FJ・Local-MIP の続き、RENS・RINS のサブ MIP、潜り。
     - 根の LP の今の解から、木のスレッドの写しを作っておく。
   - 割り振りは連続に決める: 解探しの重み w = σ(ln(相対ギャップ / rel_gap))。rel_gap は既存の終わりの判定の値。
     解がない・ギャップが大きいほど解探し、ギャップが小さいほど先回りの木 (下界) に回す。
   - 見込み: 13 問の根の遊び 1173 スレッド秒が対象。supportcase7 (根 197 秒、1.4 本)・CMS750_4 (35 秒、1.3 本)・neos-1171448・physiciansched6-2。
   - 注意: 4T の道筋は今も決定的でないので、決定性の新しい縛りは増えない。根の LP を共有せず写しで動かすので、主の根の道筋は変わらない。
2. **根のヒューリスティクスを、主が順に回すのをやめて並べる。** 型 1・2。1 の一部として作れる。
   - 形: int shifting・interior rounding・SUBFIX RENS・RENS など、今は主が順に呼ぶものを空いたスレッドに同時に出し、主は結果を固定の順で受け取る。
   - 強さ: 並べる数 = 空いた本数 × σ(ln(前の呼び出しの秒 / 根の LP の秒))。軽いものは主で回し、重いものだけ外に出す。
   - 並列のサブ MIP を 1 本で待つ形 (CMS750_4 の 20 秒) は、待つ間に主がほかのヒューリスティクスを回せばなくなる。
3. **決定的な背景のカットの待ちの間に、木を先に始める。** 型 4。supportcase7 の 66 秒の待ち。
   - 形: 待つ間、従は根の今の LP から木を始める (結果の木は、背景のカットを入れた後に捨てるか、下界だけ使う)。
     あるいは、待ちの上限を空いた本数に応じて縮める: 上限 × σ(ln(動いている本数 / スレッド数))。
   - 背景のカットの決定性 (determ の窓) の意図を崩さない形を選ぶ必要がある。
4. **木の立ち上がりで、ノードが足りないあいだ従に潜り・ヒューリスティクスの役を持たせる。** 型 5。netdiversion の 57〜60 秒、mzzv42z の 33%。
   - 形: 既存の「木のスレッドのうち 1 本がヒューリスティクスの役」を連続にする。役につく本数 = (スレッド数 − 1) × σ(ln(スレッド数 / 開いたノード数))。
     開いたノードが少ないほど多くが役につき、増えれば木に戻る。
   - 根のノードの強分枝が終わる前に従を作る形 (PARIDLE `e`) は、P で上乗せがなく取り下げ済み。今回は「作ったが渡すノードがない」側を埋める。
5. **(測り方の補い) 木の 4 本で 1 ノードあたりの秒が増えているかを測る。** 取り合い (メモリ帯域) の有無は、今回は見ていない。
   - 1T と 4T で、同じ深さのノードの LP の秒と反復の数を比べる。TREEPAR の first LP の数え (反復あたりの ms) が使える。

やらない方がよいもの:
- 強分枝の予算を増やす向き。analysis/relps_20261127 の 1 節で、4T では手間として遅れに出た。
- 根で閉じる短い問題 (1T 10 秒未満、SGM 1.07) を 4T で速くすること。HiGHS も並列で伸ばしていない。根の手伝い (候補 1) の副産物として伸びれば十分。

ログ: `logs/<問題>_t<N>.log.gz` (標準エラー) と `.cpu.jsonl.gz` (0.25 秒ごとのスレッドごとの CPU 秒)。`util.py`・`phases.py`・`win.py` は gzip を解いてから使う。

## 5. 試作 `ENOMOTO_MIP_PAR4ROLE` (既定オフ、親の依頼・利用者の承認済み。src/mip/solver.rs `par4role`・`par4_spawn`・`par4_poll`)

- 2 スレッド以上の外側の求解だけで働く。1 スレッドの道筋は変えない
  (check_default に `ENOMOTO_MIP_PAR4ROLE=ab` を付けても 6 問とも基準と一致。ビルド 36dafcbc6)。
- どちらも、既存の根の解発見スレッド (`find_thread_on`: 根の写しを基底つきで解き直し、`DIVE_ONLY` の 5 でヒューリスティクスだけを回して解を返す) と同じ形の手伝いを使う。
  手伝いの時間の予算も、解発見スレッドと同じ (残りの 0.3 倍、20 秒まで)。
- **`a` (根の手伝い)**:
  - 根の LP の後、カットの周の前に、空いたスレッド (スレッド数 − 主 − FJ のスレッド) の w 倍 (四捨五入) の手伝いを出す。
  - w = σ(ln(g / rel_gap)) = g / (g + rel_gap)。g は暫定解と根の LP の相対ギャップ (暫定解がなければ 1)、rel_gap は終わりの判定の値。新しい閾値はない。
  - 手伝いは、解発見スレッドの並び (局所探索・ダイビング 3 種・Feasibility Pump) を、手伝いごとに始めをずらして回す。
  - 主は根のヒューリスティクスの 1 本ごとに解を受け取り、根のヒューリスティクスの終わりで止める。
  - 「木の先回り」(下界の側) は作っていない。根のカットが入る前の写しで木を進めても、カットを入れた後の主の木に渡す形が要るため。
- **`b` (根のヒューリスティクスの並列)**:
  - 主が順に回す根のヒューリスティクスのうち、LP 解からの重い丸め 3 つ (int shifting・randomized rounding・interior rounding) を、1 つずつ手伝いに出す。
  - 主はそれらを飛ばして先へ進み、根のヒューリスティクスの終わりで待って受け取る。
  - 出すのは、主が回す条件 (環境変数・再スタートの前に解を出さなかったものを飛ばす印) を満たすものだけ。
- 診断: 「MIP: PAR4ROLE: helpers a … b …, helper solutions …, accepted as incumbent …」(求解 1 回ごと。再スタートの後の求解は別に数える)。
- 主の側のログ: 「MIP: PAR4ROLE a: gap …, weight …, free threads …, helpers …」「MIP: root heuristic …: delegated to a PAR4ROLE helper」。

### 5.1 13 問の 4T (`batch2.sh ab`・`compare.py ab` → `compare_ab.txt`、ビルド 36dafcbc6、種 1)

- 既定は 3 節の回 (ビルド 4a23ac9c9)。その後に取り込んだ先端の差 (e2f166597 まで) は、check_default で道筋が変わらないことを確かめた範囲。
- 13 問の時間の比 (ab / 既定) の幾何平均は 0.970。根の遊びの合計は 1173 → 1169 スレッド秒で、減っていない。
- 手伝いは全問で出た (`a` 2 本・`b` 3 本)。手伝いの解が暫定解を良くしたのは exp-1-500-5-5 (2 回)・supportcase7 (1 回)・mcsched (3 回) だけ。
- 根の秒はほぼ同じ (neos-1171448 18.4 → 18.5、mzzv42z 48.0 → 48.7、CMS750_4 35.5 → 32.8、supportcase7 196.9 → 226.1)。
  根で動いている本数は増えたが (neos-1171448 1.4 → 2.5、physiciansched6-2 1.7 → 3.0)、根の長さは主の順の仕事で決まっていて、それは縮んでいない。
- 1 回だけの比べの揺れは大きい。swath3 (0.63) と mcsched (0.64) の差は、木の段 (230.8 → 145.4 秒、45.9 → 11.7 秒) の道筋の揺れ。
  swath3 では手伝いの解は 1 つも使われていない。

考え:
- 根の遊んでいるスレッドに解探しを足しても、根は短くならない。根の長さを決めているのは、主が 1 人で回す仕事だから。
  - カットの周 (supportcase7 の 63 秒)
  - 決定的な背景のカットの待ち (supportcase7 の 66 秒)
  - 並列のサブ MIP の待ち (CMS750_4 の 20 秒)
- 手伝いが効くのは、手伝いの解で根が早く閉じる問題 (暫定解がまだ悪く、根のヒューリスティクスの後半が解で飛ぶ問題) だけ。今回の 13 問にはほとんどない。
- `b` で主が飛ばした 3 つは、これらの問題では軽かった (neos-1171448 で計 3〜4 秒)。根の待ちの大半を占めるのは、それより重いサブ MIP とカットの周。
