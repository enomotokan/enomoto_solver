対象: Netlib `pilot.ja` (`.netlib_cache/mps/pilot.ja.mps`、原問題 940 行 × 1988 列、nnz 14,698)。
基点: HEAD `7661355` (src/ は無変更)。計測ビルドは `venv_base` (HEAD の wheel、無改変) と、
scratchpad の worktree `pj_wt` (HEAD から `git worktree add`) に計測専用カウンタを足した `venv_pj`

同一設定でも ±5〜10% 揺れる (最大 +20%) ので、**時間は min/複数回の値、判断は反復数・再分解回数・
演算数 (callgrind Ir、演算カウンタ) を主に使う**。

## 1. 計測方法

- 問題読込・モデル構築は `benchmark_highs._load_lp` → `_build_our_model` (HiGHS が読んだ LP から直接構築)、
  `model.solve(root_solver=None)`。1 プロセス内で solve を 7 回繰り返し最小/中央値 (`scratchpad/pj/time_ours.py`)。
- フェーズ内訳: `ENOMOTO_PROF_PHASES_EXT=1` (+ `ENOMOTO_PROF_PHASES_EXT_WORK=1` で密度、`ENOMOTO_PROF_PRESOLVE=1`、
  `ENOMOTO_DEBUG_PRESOLVE_SIZE=1`、`ENOMOTO_DEBUG_ELIMINATE_COST=1`、`ENOMOTO_DEBUG_XB_DRIFT_EXT=1`、
  `ENOMOTO_DUMP_LU_DIR=<dir>`)。3 回以上実行。
- 命令数: `valgrind --tool=callgrind --toggle-collect='*solve_lp_dual_extended*'` (主ループのみ) と
  `'*PyModel*solve*'` (solve 全体)。HEAD wheel (シンボル有り) と、行単位のため `CARGO_PROFILE_RELEASE_DEBUG=1`
  で組んだ計測ビルド。
- 計測ビルド (`venv_pj`, worktree `pj_wt`) のカウンタ: FTRAN の R 段/U 段の演算数・ヘッダ訪問数、BTRAN の
  U^T/R 段演算数、再分解ごとの `updates / r_nnz / u_nnz / l_nnz / build_tick / tick / ms`、再分解内部の
  区間タイマ (行リスト構築, `factorize_diagonal`, 再利用試行, `MarkowitzState::new`, pivot ループ, factors 構築,
  `FtLu::new`)。既定挙動は不変 (反復数・再分解回数・目的関数が venv_base と一致することを確認)。
- HiGHS: `highspy` 1.15.1、`threads=1`、`log_dev_level=3` のログから反復内訳と再 INVERT 理由を採取。
  INVERT 単価は `simplex_update_limit` を振った時間差から推定 (§3.2)。
- fill の参照: `ENOMOTO_DUMP_LU_DIR` で本実装の分解入力 (基底行列 11 個) をダンプし、`scipy.sparse.linalg.splu`
  (SuperLU, COLAMD / MMD_AT_PLUS_A, `diag_pivot_thresh=0.25`) の L+U nnz と比較。

### 3.2 再分解: 単価が HiGHS の ~3 倍で、fill ではなく簿記が原因
再分解内部の区間 (計測ビルド、14 回合計 32 ms): 行リスト構築 1.3 / `factorize_diagonal` 試行 0.04 /
再利用試行 4.0 (6 回、採用 3、fill 超過 3、バックオフスキップ 8) / フル分解 23.0 (11 回: border 0.25、
`MarkowitzState::new` 2.2、**pivot ループ 19.7**、factors 構築 1.0) / `FtLu::new` 1.3。
pivot ループ 19.7 ms の内訳: `eliminate` 10.4 ms (`ELIMINATE_COST`)、ピボット探索 7.5 ms (`pivot_search
steps=7106 candidates=88749 (12.49/step) scan=7.5ms`、`search_limit_hits=0`)、snapshot 0.45 ms。

パターンのみ・非整列・末尾追記で、閾値判定に行内探索を要しない。

### 3.4 drift 起因の再分解 (10 回)
`ENOMOTO_DEBUG_XB_DRIFT_EXT=1`: 通常残差 1e-9〜5e-9 (‖x_B‖ ~1e4〜1e5、`bound norm 1.47e5` なので相対
1e-13〜1e-14 = 丸め水準)、発火値 1.85e-8 (iter 14)、4.99e-8 (129)、6.09e-8 (194)、**1.03e-5 (224)**、
1.6e-8 (239)、**4.15e-7 (244)**、… 鎖長 5〜15 で再発火した 4 回 (iter 225/240/245/460) のうち iter 224/244 は
残差が 3〜5 桁跳ねた本物の数値イベント (小ピボットの FT 更新)、他は閾値 1e-8 に対する丸めノイズ。
| 設定 | 再分解 | 反復 | wall (3 回) |
|---|---|---|---|
| 既定 | 14 (drift 10) | 1,451 | 191〜199 ms |
| `ENOMOTO_XB_DRIFT_TOL=1e-7` | 9 (drift 4, clock 5) | 1,451 | 184〜199 |
| `ENOMOTO_XB_DRIFT_REL_K=10` | 14 | 1,451 | 185〜191 (r0 ~3e-10 なので床が効かない) |

pilot.ja 単独では `1e-7` が −3〜5% だが、`analysis/lu_impl_20260923_130507.md` L3 の 93 問 A/B で
25fv47 +21% を出して不採用になった経緯があり、**再提案しない**。

### 3.5 その他の LU 関連
- **BTRAN L^T gather** (`lu.rs:3419-3426`): ρ 密度 0.28 に対しゲート `BTRAN_L_SCATTER_FRACTION=0.10`
  (`lu.rs:3959`) で gather 1,006 / scatter 471。`ENOMOTO_BTRAN_L_SCATTER=1.0` で btran 23〜25 → 20〜21 ms

  全体 +3.0%・10% 超退行 2 問なので、ゲート値変更は全体 A/B 前提。
- **FT 更新** (`commit_update` `lu.rs:5985-6068`): `push_scaled_dense` (`lu.rs:3784`) が R eta (e_tilde、
  非ゼロ ~65) と U スパイク (a_tilde、非ゼロ ~48) を作るのに **長さ m の密ベクトルを各 2 パス** (計 4m =
  2,584 要素/更新) 走査、`a_tilde_out.copy_from_slice` (`lu.rs:5264, 5347`) も m。1 更新 19.6k Ir、
  合計 28.4M Ir (2.4%)。`u_seq.remove(k)` + `slot_pos` 再番号 (`lu.rs:6039-6042`) と `row_owners` の
  線形探索 (`lu.rs:6027-6031`) が `commit_update` 自己 12.6M Ir (1.1%)。
- **`permute_out`** (`lu.rs:5412-5455`): 3.6% Ir。全 m 要素に singleton 除算判定 (`if d != 0.0 && v != 0.0`)、

- **微小値**: `ENOMOTO_TINY=1e-14` は経路が変わり drift 再分解 16 回に増加、時間は中立。pilot.ja では効かない。

## 6. 改善候補 (優先順; 採用基準「93 問で 10% 超退行なし・幾何平均 1% 以上」を意識)

### P1 (最優先・ビット同一・S): eta 適用ループの境界検査除去
- 変更箇所: `src/simplex/lu.rs:3703-3730` (`EtaFile::dot` / `EtaFile::axpy` の疎アーム)。同型の内側ループ:
  `l_solve_into_pair` `lu.rs:3150-3235` (`zb[row_step] -= mult * xb` 等)、`l_solve_into` `:3238-3250`、
  `l_transpose_gather_core` `:3419-3426`、`u_transpose_sweep_track` `:4737-4770` (`z[q] -= v * zp`)、
  `permute_out` `:5412-5455` (`out[col_perm[s]]`)。
- 内容: 格納 index が `< m == dense.len()` であることは構築時に保証されている (`push_scaled_dense` は
  `src.len()==m` の添字、`FtLu::new` は `row_step < m`、`l_col` は `row_perm_inv` 経由)。各ループ先頭に
  `debug_assert!(idx.iter().all(|&i| (i as usize) < dense.len()))` を置き、本体を
  `unsafe { *dense.get_unchecked_mut(i as usize) += alpha * v }` (dot は `get_unchecked`) にする。
  `eliminate` (`lu.rs:1489`) が既に同じ流儀 (`wval.get_unchecked`) なので新しい種類の unsafe ではない。
- 実測 (worktree、`dot`/`axpy` の 2 箇所だけ): 主ループ Ir **1,201M → 1,092M (−9.1%)**、目的関数ビット同一、
  壁時計 min 0.2025→0.2020 / 0.2002→0.1912 (2 ラウンド、ノイズ ±5%)。
- 期待効果: pilot.ja FTRAN/BTRAN 命令数 −25% 程度 (axpy 行単独で 14%)。メモリ律速の大問題 (dfl001) では
  壁時計の伸びは小さい。93 問全体では FTRAN+BTRAN が総時間の 39% なので幾何平均 −1〜3% を見込む。
- 退行リスク: 経路不変 (ビット同一)。リスクは unsafe の不変条件のみ (debug_assert + テストでカバー)。

### P2 (ビット同一・S〜M): FT 更新の eta を index リストから構築
- 変更箇所: `lu.rs:5985-6068` (`commit_update`)、`:3784-3830` (`push_scaled_dense`)、呼び出し側
  `extended_dual.rs:3839` (`solve_transpose_unit_work` の `work.touch` = e_tilde の非ゼロ位置、`tracked` 時)、
  `lu.rs:5264/5347` (`a_tilde_out.copy_from_slice`)、`solve_sparse_into_pair_capture` `:5107-5150` (`gp.reach`)。
- 内容: `push_scaled_dense` に「index リスト版」`push_scaled_list(key, pivot, src, list, skip, scale)` を追加。
  リストは昇順ソート (`O(k log k)`、k≈50〜70) してから走査すれば、格納順が密走査と同一になり **ビット同一**
  (R eta の dot 順序・U eta の axpy 順序が保たれる)。e_tilde 側: `UnitBtranWork::touch` (重複あり) を
  sort+dedup、`tracked=false` (触った数 > m) のときは従来の密走査。a_tilde 側: 疎経路では `gp.reach` ∪
  R eta の `slot` 集合、密経路 (`solve_into_pair_capture`) では従来通り密走査 (pilot.ja は α 密度 0.53 で
  密経路が主なので、ここでの利益は e_tilde 側の 2m と `copy_from_slice` の削減が中心)。
- 期待効果: pilot.ja ft_update 11 ms → 7〜8 ms (−1.5〜2% solve)。m が大きく eta が小さい疎問題
  (80bau3b m=1977、ship12l、stocfor2、sctap3、czprob; ft_update 5〜6%) で −2〜4%。幾何平均 +1% 前後。
- 退行リスク: なし (ビット同一)。実装量は中 (リスト有無で分岐)。

### P3 (ビット同一・S): 再分解 1 回の固定費 (~0.5 ms/回 = 20%) 削減
- 変更箇所: `extended_dual.rs:1338-1370` (`refactorize` の行リスト構築 1.3 ms/14 回)、`lu.rs:4432-4552`
  (`FtLu::new` 1.3 ms: `row_owners: Vec<Vec<(usize,f64)>>` を m 個 `with_capacity` → `owner_count` は既に
  あるので CSR (`start`/`idx: u32`/`val`) に平坦化、`scratch_a_tilde`/`scratch_e_tilde` の再確保を前の
  `FtLu` から引き継ぐ)、`lu.rs:2820-2860` (factors 構築 1.0 ms: `u_row: Vec<Vec>` m 個確保 → `u_entries`
  は step 昇順に生成されるので L と同様に CSR へ直接)、`lu.rs:478-560` (`MarkowitzState::new` 2.2 ms/11 回:
  `buf.sort_by_key` は入力が既に列昇順 (`std.cols` を j 昇順で走査) なので `is_sorted` 判定でスキップ可)。
- 期待効果: 再分解 2.2 → 1.8 ms (pilot.ja −2〜3% solve)。再分解比率の高い中規模問題 (grow22 31 回、
  25fv47 21、perold 17、pilot4 10、grow7 13、pilot87 61) で 1〜4%。幾何平均 +0.5〜1%。
- 退行リスク: なし (ビット同一; `u_row` の順序を保てば `FtLu::new` の格納順も不変)。

### P4 (ビット同一・M): ピボット探索の `col_max_abs` 再走査を列値ミラーで置換
- 変更箇所: `lu.rs:442-460` (`KernelMatrix` に `col_val: Vec<f64>` を `col_ent` と並列に追加)、
  `lu.rs:626-652` (`col_insert`/`col_remove` に値を同伴)、`lu.rs:1484-1560` (`eliminate` の in-place 更新で
  変化した `(i,j)` の値を `col_val` にも書く: 位置は `col_ent[j]` が行昇順なので `partition_point` で O(log))、
  `lu.rs:1100-1105, 1197-1262` (`col_max_abs_rescan` と候補閾値判定を `col_val` の直読みに; `row_get`/`colval`
  キャッシュ廃止)。
- 内容/根拠: 再走査 146k 要素 (14.6M Ir = 再分解 Ir の ~9%) と候補ごとの `row_get` (行内探索) を、
  列側の値配列の一直線走査にする。HiGHS `buildKernel` が `mc_value` を持つのと同じ考え方 (行側は現状の
  整列パターン維持のまま)。max は順序に依存しないのでピボット選択はビット同一。
- 期待効果: pilot.ja 探索 7.5 → ~5 ms (−1.2% solve); pilot87 (再走査 9.2M 要素/solve、refactor 28%) と
  dfl001 (探索 13%) で −2〜4%。値更新の二分探索 (flops × ~30 Ir) が相殺する問題もあり得るので、
  `ENOMOTO_LU_BENCH_FILE` の replay ベンチ (`lu_kernel_bench`) で先に確認する。
- 退行リスク: 経路不変。メモリ +8B/nnz。

### P5 (経路が変わる・S; 参考): 再分解単価に見合う鎖長制御は現状の係数 16 が妥当 — 変更しない
- §3.3 のとおり係数を下げると pilot.ja でも中立〜悪化。**P3/P4 で再分解単価が下がった後に** 24 問スイープで
  再校正するのが順序 (単価 −30% なら最適係数は 8〜12 に寄る見込み)。同様に、drift 許容 (`1e-7`、
  `REL_K`、`MIN_UPDATES`) と BTRAN L^T ゲート (0.10 → 0.3) は pilot.ja 単独で −1.5〜5% だが、既存の 93 問
  A/B で退行実績があるため今回は提案しない。

### 構造的課題 (L; 今回は提案のみ)
再分解単価 3 倍の根本は行指向 Markowitz 核の簿記 (§3.2)。HiGHS 型 (列側に値、行側は非整列パターン、
バケットは連結リスト) への置換は `lu.rs:442-1700` の書き直しで、ピボット同点の順序が変わり経路も変わる。
効果は再分解 −50% 前後 (pilot.ja −8%、pilot87/pilot/grow 系 −10〜15%) + 鎖長再校正で FTRAN −20% の可能性。
