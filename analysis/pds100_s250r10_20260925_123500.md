# pds-100 / s250r10 (Mittelmann LPopt) のボトルネック調査 (2026-09-25)

対象: `pds-100.mps` (156,244 行 × 505,360 列, 1.39M 非零) と `s250r10.mps` (10,963 × 273,142, 1.57M 非零)。
enomoto_solver は HEAD `2017685` (`/home/user/venv_base`) で両方とも 600 s タイムアウト。HiGHS 1.15.1 は同一機で
pds-100 75.9 s / 284,637 反復、s250r10 108.3 s / 177,198 反復。**src は変更していない** (計測は clone
`/home/user/prof_repo3`, `/home/user/prof_repo4` + `venv_prof3`/`venv_prof4` に反復上限・プラトー上限の env 上書きと
計時カウンタを足しただけ)。4 コアを他の調査と共有しており、絶対時間は ±15% 程度揺れる (同時実行は 2 本まで)。

## 0. 要約

- **両問題とも原因は 1 つ: 実行不能行数の「プラトー検出」が誤発動して Bland 規則モードに入り、そこから収束しなくなる。**
  `slope_intercept_dual.rs:2263` の `infeasible_plateau_limit = min(4·stall_limit, MAX_ITERS_FLOOR/4) = 5,000` は
  m によらず 5,000 反復固定で、「実行不能行数の最小値を 5,000 反復更新できない」と `bland_mode = true` (`:4001-4004`)。
  双対単体法では実行不能行の *個数* は進展の指標ではない (pds-100 は最小 4,298 → 5,000 前後で振動、s250r10 は
  486 → 900〜1,000 に増えたまま目的関数は着実に改善) ので、pds-100 は反復 ~13,000、s250r10 は反復 ~7,000 で
  Bland に落ちる。Bland (最小添字行 + 全候補ソート) は 1 反復が 3〜8 倍遅くなるうえ収束せず、pds-100 は 600 s 枠で
  ~16 万反復 (Bland 内 15 万反復) 回しても実行不能行が 4,800 前後から減らない。
- **プラトー検出を無効化 (`ENOMOTO_T_PROF_PLATEAU_LIMIT=1e9`) するだけで両問題とも最適解に到達する:**
  pds-100 **195 s** (main 174,881 反復、目的値 10928229968.0 = HiGHS と一致)、s250r10 **118.6 s**
  (117,385 反復、-0.172677041905481 = HiGHS と 12 桁一致)。反復数はどちらも HiGHS より少ない
  (0.61 倍、0.66 倍)。Netlib 93 問は現状 1 問も `bland_mode` に入らない (§3.3、全問で確認) ので、この検出条件を
  緩める/直すことによる Netlib の経路変化は **ゼロ**。
- 残る差は 1 反復のコスト。pds-100: ours 1.08 ms/反復 vs HiGHS 0.28 ms (3.9 倍)。内訳は **FTRAN 48%** (505 µs: 融合
  FTRAN の `R` 段 128 µs、`tau` の `U` 段 105 µs、入る列の超疎 `U` 段 78 µs、`tau` の `L` 段 51 µs、全走査に落ちた
  反復の `U` 走査+出力 137 µs。**tau が密になる 19% の反復が FTRAN 時間の 58%、1 回 1.49 ms**)、BTRAN 13% (132 µs: 8% の反復で `rho` が m の 10% 以上に密で 1.1 ms)、BFRT 8%、
  PRICE 5%、chuzr 4.5%、chuzc 4%、x_B 更新 4%。s250r10: ours 0.99 ms vs HiGHS 0.57 ms (1.7 倍、ただし HiGHS は
  終盤 2〜6 ms/反復に落ち込み ours は落ちない)。内訳は **PRICE 31% + chuzc1 30% + dual_update 10.5% = 71%** で、
  すべて「行 `a_p = rho^T A` の非零列 (平均 21,900 列 = 全列の 8%) を列添字でランダムアクセスする」コスト
  (callgrind: 1 反復 3.5M 命令、D1 ミス 143K/反復のうち 80% がこの 3 パス)。
- presolve は問題ではない: pds-100 6.2 s (HiGHS 11.4 s)、s250r10 1.8 s (HiGHS 6 s)。縮約後サイズは pds-100 で
  HiGHS より行 12% 多い (87,389 vs 77,914)、s250r10 は同等 (6,980 vs 6,622 行)。

さらに rho/alpha が密になっており 3〜8 ms/反復。

### 2.3 なぜプラトー検出が誤発動するか (`slope_intercept_dual.rs:2259-2268, 3980-4004`)

- 上限は `min(INFEASIBLE_PLATEAU_STALL_MULT * stall_limit, MAX_ITERS_FLOOR / INFEASIBLE_PLATEAU_BUDGET_DIVISOR)` =
  `min(20·m, 5,000)`。`MAX_ITERS_FLOOR` (20,000) は反復予算が固定 20,000 だった頃の名残で、予算はその後
  `max_iters_for = 20·(m+n)` (pds-100 で 1,000 万超) にスケールしたが上限側は据え置き。
  m ≥ 250 の全問題で 5,000 反復固定になる。
- 進展の判定は「実行不能行数の *最小値* を更新したか、または `remaining_m_side` が減ったか」。大きな問題では
  段階 A が空 (`S empty`、`remaining_m_side = 0` で始まる) なので第 2 の指標は最初から無い。
  双対単体法 (特に BFRT 付き) では主実行不能行の個数は単調でなく、大きな問題では最小値を数千反復更新しないのが普通
  (pds-100 は 8,000 反復目の 4,298 を 17 万反復まで下回らない: プラトー検出オフの走行でも 92,000 反復目に 8,225 行、
  158,000 で 4,832、170,000 で 2,182 と収束は終盤)。
- この検出は Netlib pilot4 (`infeasible_rows` が 31 で 16,000 反復固定) と greenbea (248/249 で振動) のために入った
  (`docs/improvement_history.md` L1924-1963)。**HEAD では Netlib 93 問とも `bland_mode` に一度も入らない**
  (§3.3) ので、現状の Netlib にとってこの検出は完全に休眠している。

読み取れること:
- pds-100 は `tau` (DSE) の密度が 4.6% と高く、行ごとの `B^-T e_r` 密度が反復によって大きく変わる。密度の移動平均や
  「構造的到達数 > 0.1 m」の閾値で経路を決めるため、2 割前後の反復が O(m) の全走査経路に落ち、その反復だけで
  FTRAN の半分近くを使う。
- 全走査に落ちない反復でも `R`/`U` の超疎段が 80 ns/要素と遅い (ヒープ駆動)。HiGHS の hyper-sparse は DFS +
  リスト (Gilbert-Peierls) で 10〜20 ns/要素。
- `R` eta が平均 1,181 個 (策10 で再分解間隔を √m 倍に広げたため) で `R` 段が最大の単一項目。

### 3.3 Netlib で確認したこと

- HEAD (`venv_prof3` = HEAD + 計時) で Netlib 93 問を `ENOMOTO_DEBUG_EXT_TRACE=1` で走らせ (`scratchpad/netlib_bland.txt`)、
  **93 問すべてで `bland_mode=false` のまま終了、Bland 移行トレースは 0 件**。stall_count 起因も plateau 起因も無い。
