# ピボット順の再利用(`docs/lu_comparison_enomoto_vs_highs.md` §2.2)

対象: 再分解 (`refactorize`) が毎回ゼロから Markowitz 探索している点。
基点 = このブランチのマージコミット 429c72a(`main` ff53323 に
practical-hopper の疎表現集約/L フラット化と sweet-brahmagupta の §2.6
BTRAN `L^-T` 転置行major化を取り込んだもの)。
4 コア、rustc 1.94.1、highspy 1.15.1、Python 3.11、NETLIB93 全問題。

指摘された問題: 再分解は「前回分解した基底とは数本の列しか違わない」行列を
毎回ゼロから Markowitz 探索している。HiGHS は `HFactor::rebuild()`
(`util/HFactorRefactor.cpp`)で前回のピボット順を再利用する。
プロファイルでも refactor の占有率が 3.4% → 10.2% に増えていた。

## 0. 結論

1. **指摘は妥当**だが、**HiGHS の `rebuild()` をそのまま移植しても効かない**。
   HiGHS の `refactor_info_.use` を立てるのは `HEkk::setNlaRefactorInfo()`
   (ホットスタート = **同じ基底**を分解し直す場合)だけで、反復中の
   `HSimplexNla::invert()` は `use = false` のまま `buildSimple` +
   `buildKernel` を通る(§1)。実際、(行,列)の順を丸ごと再生する実装を
   最初に作って計測したところ、**採択率はほぼ 0%** だった(§2)。
2. 再利用すべきは **列順だけ**で、行は毎ステップ選び直す必要がある。
   列順こそ Markowitz の fill 最小化が符号化しているもので、行の割当は
   数値的選択にすぎない。FT 更新で差し替わった列は「前回その列の
   ピボットだった行」に成分を持たないのが当然であり、行順の再生が
   失敗する原因はそこにある(§2)。
3. 行の選び直しは **安定性床 `STABILITY` を通る候補のうち、まだ到達して
   いない列に残っている非ゼロ数が最小のもの**(列固定下の Markowitz
   カウントの残り半分)。純粋な部分ピボットだと fill が増えて負ける(§3)。
4. fill 上限 `REBUILD_FILL_LIMIT` は **1.25**。fill は 1 回限りのコストでは
   なくその分解が生きている間の全 FTRAN/BTRAN が払うので、緩い上限は
   採択率が上がっても**総和では負ける**(2.0 で +2.7%、1.1 で +0.4%、
   1.25 で -1.5%。2.0 の最悪ケースは greenbeb +30%)(§3)。
5. `fit1p`/`fit2p` 型(border 列を持つ)基底は再利用の対象外にする。
   bordered 分解の意義は密な trend 列を疎な消去から外すことなので、その順を
   平坦に再生すると逆効果になる(fit2p が +6.4% → +3.8% に改善、§3)。
6. 失敗は連続する傾向があるので、棄却後は指数的バックオフ(2,4,8,16 回の
   再分解を試行しない)。dfl001 は棄却で 451ms(壁時計の 2%)を捨てていたが、
   バックオフ後は 89ms になった(§3)。
7. **NETLIB93 全 93 問題の同一プロセス A/B で、独立 2 回とも改善側:
   合計 -2.55%(46.42s → 45.24s)と -4.31%(49.29s → 47.17s)、
   両方の min を取っても -1.98%。目的関数値は両回とも 93/93 一致、
   10% 以上の退行は両回ともゼロ**(best-of-4 の最悪は d6cube +5.9%、
   pilot +4.5%)(§4)。
8. 再分解フェーズ自体の時間は 25〜40% 減る(25fv47 69.6→42.3ms、
   greenbea 58.2→40.8ms、pilot 578→468ms、fit2p 315→262ms、
   dfl001 4701→4011ms)。壁時計の改善がそれより小さいのは、分解が変われば
   ピボット列も変わって反復数が両方向に動くため(§4.3)。

## 1. HiGHS の `rebuild()` は「同じ基底の再分解」専用である

`HFactor::build()`(`HFactor.cpp:369`):

```cpp
if (refactor_info_.use) {
  rank_deficiency = rebuild(factor_timer_clock_pointer);
  if (!rank_deficiency) return 0;
}
refactor_info_.clear();      // 以降は buildSimple + buildKernel
```

`refactor_info_.use = true` を立てているのは HiGHS 全体で 1 箇所:

```cpp
void HEkk::setNlaRefactorInfo() {                     // HEkk.cpp:392
  simplex_nla_.factor_.refactor_info_ = this->hot_start_.refactor_info;
  simplex_nla_.factor_.refactor_info_.use = true;
}
```

`hot_start_` は `HEkk::computeFactor()` が INVERT のたびに保存する
スナップショット(`HEkk.cpp:2025`)で、`setNlaRefactorInfo()` はホットスタート
(保存した基底へ戻って解き直す)経路から呼ばれる。反復中の再分解
(`HSimplexNla::invert()`)は `refactor_info_.clear()` された状態
(`HSimplexNla.cpp:126`, `HFactor.cpp:377`)で走るので、**通常の
再分解で `rebuild()` は使われない**。

`rebuild()` 自身も、記録したピボットが使えなければ即座に
`rank_deficiency` を返してフル分解にフォールバックする作りで、
そこには相対安定性判定すらなく `pivot_tolerance`(絶対値)だけを見る
—「同じ基底なのだから落ちるはずがない」という前提である
(`assert(abs_pivot >= pivot_tolerance);` というコメントが明示的にそう書いている)。

したがって `docs/lu_comparison_enomoto_vs_highs.md` §2.2 の
「反復中の基底がほぼ同じであることを考えると HiGHS 方式は探索コストを
大幅に削れる」という読みは、HiGHS が実際にやっていることとは違う。
同 doc の当該節は本コミットで訂正した。

## 2. 計測1: (行,列) 両方の順を再生する実装は採択率ほぼ 0%

最初の実装は HiGHS の `rebuild()` と同形(左向き・`ftranL` で列を通し、
記録したピボット行で分割)で、記録した行が使えなければ丸ごと棄却する。
NETLIB で計測した採択率と棄却理由:

| 問題 | 試行 | 採択 | 棄却理由 zero / stability | 平均棄却位置 |
|---|---:|---:|---|---:|
| 25fv47 | 26 | 0 | 23 / 3 | 0.13·m |
| greenbea | 28 | 1 | 23 / 4 | 0.26·m |
| degen3 | 7 | 0 | 7 / 0 | 0.03·m |
| pilot | 30 | 0 | 28 / 2 | 0.15·m |
| fit2p | 32 | 0 | 32 / 0 | 0.01·m |

棄却のほぼ全部が **zero**(記録した行にそもそも成分がない)であり、
安定性不足 (stability) ではない。つまり閾値を緩めても直らない。
理由は単純で、FT 更新は基底スロット `p` の列を別の列に差し替えるが、
入基底列が「出た列のピボット行」に非ゼロを持つ理由は何もないからである。
再分解の間隔は `FT_MAX_UPDATES` 近くまで伸びるので、毎回 50〜100 本の列が
入れ替わっており、そのうち 1 本でも当たれば全体が棄却される。

## 3. 実装: 列順だけ再利用し、行は選び直す

`sparse_lu::factorize_reusing(m, rows, prev)`:

- `prev` の `col_perm` をそのまま列順として使い、`row_perm` は**ヒント**として
  扱う。ヒント行がまだ空いていて `|a| >= STABILITY * max_rest` を満たせば
  それを使い(基底が変わっていなければ前回と同一の分解になる)、
  だめなら選び直す。
- 選び直しは「`STABILITY` の床を通る候補のうち、**まだ到達していない列に
  残っている非ゼロ数**(`row_remaining`、O(nnz) で保守)が最小、同数なら
  ピボットが大きい方」。純粋な部分ピボット(最大要素)にすると fill が
  増え、fit2p / greenbeb などで負ける。
- 分解本体は左向き(Gilbert-Peierls 形): 列を読み、今まで作った `L` を
  通し(到達集合はステップの最小ヒープで辿る)、既にピボット済みの行は
  `U` の列、ピボット行は対角、残りは `L` の列。探索も能動部分行列
  (`MarkowitzState` の `BTreeMap`/`BTreeSet`)も一切持たない。
- 安全弁は 3 つ。いずれも**フル Markowitz へのフォールバック**で終わる:
  (a) 列に `REBUILD_MIN_PIVOT` を超える成分が残っていない(特異)、
  (b) fill が直近の**フル**分解の `nnz(L+U)` の `REBUILD_FILL_LIMIT` 倍を
  超えた、(c) border 列を持つ基底(`wants_bordered`、`factorize` が
  bordered 経路へ回す条件そのもの)。
- 棄却は連続しやすいので、棄却後は 2,4,8,16 回の再分解を試行しない
  (`reuse_skips_left`、採択で 0 にリセット)。
- fill 上限の基準は**直近のフル分解**の nnz に固定する。再利用の連鎖で
  基準が少しずつ上がっていくのを防ぐため(上限に当たれば 1 回フル分解が
  走り、その nnz が新しい基準になる)。

### 3.1 fill 上限の A/B(中量級 10 問題、reps=3、合計 min)

| 上限 | 合計 | 対 off |
|---|---:|---:|
| off(再利用なし) | 9.612s | — |
| 2.0 | 9.867s | +2.7% |
| 1.3 | 9.524s | -0.9% |
| 1.1 | 9.360s | -2.6% |

2.0 の最悪ケースは greenbeb +30.4%。fill は分解が生きている間の全
FTRAN/BTRAN が払い続けるコストなので、「採択率が上がる = 速くなる」では
ない。逆に 1.0 / 1.05 まで締めると今度はほぼ全部棄却されバックオフが
効いて、オーバーヘッドだけが残る(10 問題合計で +1.4〜+1.8%)。

### 3.2 border 列基底の除外(25 問題、reps=3、合計 min)

| | off | 1.1 | 1.25 |
|---|---:|---:|---:|
| 除外前 | 14.569s | 14.685s (+0.8%) | 14.981s (+2.8%) |
| 除外後 | 14.732s | 14.797s (+0.4%) | **14.512s (-1.5%)** |

fit2p 単体では 1.25 で +16.3% → +0.6%。以降 `REBUILD_FILL_LIMIT = 1.25`。

| 問題 | off | on | 再分解回数 off→on | 採択率 |
|---|---:|---:|---|---:|
| 25fv47 | 69.6ms (18.5%) | 42.3ms (12.7%) | 28 → 27 | 80% |
| greenbea | 58.2ms (17.7%) | 40.8ms (11.3%) | 28 → 28 | 92% |

壁時計の改善がこれより小さい / 問題によっては逆を向くのは、分解が変われば

分離できない**。採否は end-to-end の壁時計で判断した。

## 5. 採否

**採用**。

- NETLIB93 全 93 問題で **10% 以上の退行なし**、合計 -2.55%、
  目的関数値 93/93 一致。
- 決定的(deterministic)である点は維持: 環境変数の読み取りは再分解ごと
  1 回、バックオフ状態も決定的に引き継がれ、`Instant::now()` は
  診断カウンタにしか使っていない。同じ問題を 2 回解けば同じ反復列になる。
- 単体テスト 6 本を追加(列差し替え後の解の残差、同一行列なら分解が
  一致すること、特異行列の棄却、弱いヒント行の選び直し、fill 上限、
  FT 更新を挟んだ end-to-end の fresh 比較)。`cargo test --release`
  222 passed / 0 failed。

### 5.1 残る課題

- 列順は「直近のフル分解のもの」を固定で使い続けるため、再利用が長く続くと
  順が古くなる。今は fill 上限が当たった時点でフル分解に戻ることで
  実質的に打ち切っているだけで、「そろそろ取り直した方がよい」を
  直接判定してはいない。
- border 列を持つ基底は丸ごと対象外にしている。bordered 分解の
  (疎部分の列順 + border 列集合)を記録して再利用する余地はある。
- pilot の +5.3% は反復数 +2.8% と再分解回数 33 → 35 に対応しており、
  再利用で作った分解の数値品質が(安定性床は同じでも)わずかに劣ることを
  示唆する。ヒント行の採用条件を `STABILITY` より厳しくする案は未検証。
