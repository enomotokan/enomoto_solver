# neos-5188808-nattai で既知の最適値より良い値を返した件 (2026-11-24〜25)

## きっかけ

- combo の分担 2 で食い違いが出た (analysis/combo_20261124/res_s2.jsonl、summ.py)。
- neos-5188808-nattai の combo_t1 (1 スレッド、600 秒で時間切れ) が暫定解 0.11018650 を返した。
- これは solu.json の既知の最適値 0.11028362 より相対 9.7e-5 良い。MIPLIB は最小化なので、ありえない値。

## 結論

- **漏れの仕組み:** B&B の中の LP は、許容誤差の範囲で行を少しずつ破った解を返す。
  - 行ごとの違反は 1e-6 未満なので、元の問題での受け入れの確かめ (絶対 1e-6) は通る。
  - しかし多くの行で積もると、目的値が許容誤差よりずっと大きく下がる。
- **返す前の研磨が 2 か所で効いていなかった:**
  - (a) `ENOMOTO_MIP_LATE_NO_RESOLVE` (既定) により、時間を使い切った回は研磨の LP を解かない。
  - (b) 研磨した解は違反が減っても、目的値の悪化が相対 1e-6 を超えると捨てる。
  - 研磨は `polish_solution`。整数を固定した元の問題を、前処理 + LP で一から解き直す。
- **既定でも起きる:** def_t1 は本当の値より 9.5e-7 低い値を返した。combo で差が 1e-4 と大きく出たのは、下の構造を通る漏れのため。
- **試作 `ENOMOTO_MIP_POLISH_STRICT=1` (既定オフ、src/mip/mod.rs):**
  - 時間切れの回でも研磨し、研磨の LP に期限を渡さない。
  - 違反が真に減る解き直しは、目的値の悪化の大きさによらず採る。新しい閾値は作っていない。
  - 600 秒の combo_t1・def_t1 とも、返す値が整数を固定した LP (HiGHS、許容差 1e-9) の値と一致した。行違反は 7e-18。
  - 時間の超過は 0.06〜0.08 秒。
- **まだ入れていないもの:** 木の中の打ち切り値に研磨した値を使う部分。
- **過去の記録での刈りすぎの疑い:**
  - combo の 625 行と final_20261118 で、optimal と言い切った行はすべて既知の値との差が +2.1e-7 以下。どれも既知より悪い側 (丸め) にずれている。
  - 既知より良い値は、nattai の時間切れ 1 件だけ。
  - 刈りすぎを示す記録は見当たらない。

## 2. どこで漏れるか

- **combo_t1 の違反行:** 違反した 112 行は、すべて `C14289 - C42xx >= 0` の形。
  - C14289 は 0/1 の切り替えで、133 本の行で連続の流れ C42xx を抑える。
  - 解では C14289 = 0 なのに、C42xx = 9.5238e-7 (= 1e-6/1.05) が流れている。
  - 違反の合計は 1.07e-4 で、目的値はその分だけ低い。
- **B&B の外では漏れない:** 整数を固定した問題を MPS に書き出し (`fixmps.py`)、このクレートで一から解くと 0.122404775 (違反 7e-18)。
  - よって漏れは、B&B の中の LP (前処理後の問題、カット・境界のずらしつき) の許容誤差の範囲で入る。
- **未特定:** 1.05 倍の出どころは追えていない。
  - MPS に 1.05 の係数はなく、LP の中のスケーリングか境界のずらしと見ている。
  - 研磨で消えるので、直しには要らない。

## 5. STRICT=2 (暫定解を受け入れるたびの研磨) と時間の上限の超過 (2026-11-25)

### STRICT=2

暫定解を受け入れるたびに、`polish_in_problem` (src/mip/mod.rs) で研磨する。
- 研磨の中身: 整数を固定した前処理後の問題を、B&B の LP とは別に、前処理 + 単体法で一から解き直す。
- 研磨した値を使うもの: 打ち切り値、共有する最良値、解の溜め。
- 研磨で今の暫定解より良くなくなった解は、受け取らない。
- 集計の表示: `ENOMOTO_MIP_POLISH_STATS=1` で、研磨の回数・取り替えた回数・時間を出す。

## 6. 超過を抑える試作 `ENOMOTO_MIP_POLISH_WARM` (2026-11-25、既定オフ)

P の比較 (analysis/polishp_20261125) は、この直しの前の版として記録した。

### 中身 (src/mip/mod.rs の `polish_in_problem_warm`、solver.rs の `leak_estimate`)

- 研磨の LP を、前処理後の問題 (self.p) の上で、B&B の LP (`TwoStageLp`) と同じ単体法で解く (前処理なし)。
  - 基底は B&B の LP のものを写す: カットの行の分は捨て、固定した整数列は基底から外す。行の数の過不足は `set_basis` の修復に任せる。
- `STRICT=1` と組むとき: 木の求解の終わり (`Solver::finish`) で返す暫定解を研磨する。外側の元の問題での研磨は既定と同じ扱い (時間を使い切っていれば解かない・期限を渡す) にする。
- `STRICT=2` と組むとき: 木の中の研磨もこれで解き、求解の期限を渡す。
- 値の意味:
  - `1`: 返す前の研磨に期限を渡さない。
  - `d`: 期限を渡し、間に合わなければ漏れの見積り (今の LP の双対値・被約費用の絶対値 × 行・列の境界の違反の和) を目的値に足す。
  - `e`: 研磨の LP を解かず、いつも見積りを足す。
- 新しい閾値は作っていない。期限は求解の期限そのもの。
- 診断 `ENOMOTO_MIP_POLISH_STATS`: `v` で研磨ごとの反復・違反・見積りと実際の差、`c` で基底を写さずに解く。

  - 写さずに同じ単体法で解くと 8513 反復・7.1 秒 (`STATS=vc`)。
  - 写した基底は行の数ぶんそろっている (3151 行、カットの行 22 本を捨てた)。それでも遠い出発点になっている。
  - 一から前処理 + 単体法 (`polish_solution`・`polish_in_problem`) は 14〜23 秒。前処理なしの単体法の方が速いが、それでも 7 秒越える。

### まとめと次の候補

- 第一候補の「B&B の基底から温める」は、dano3 では逆効果 (5 倍の反復)。超過は 1 秒には収まらない。
- 見積りで正す形は、時間は守るが、今の双対値の取り方では漏れを捉えない。
- 次の候補 (未実装):
  - 見積りの双対値を、漏れた解を出した LP そのもの (`resolve_continuous` の整数を固定した LP の最適での双対値) から取る。
  - 暫定解の漏れは、整数を固定した LP が許容誤差の範囲で行を破るところで入る。その最適の双対値なら、違反した行に効くはず。

## 7. 見積りの取り方の直しと「未研磨」の印 (2026-11-25、親の依頼の 2 回目)

### 変えたこと

- **見積りの双対値:**
  - 暫定解の連続部を出した LP そのものから取る。つまり `resolve_continuous` の整数を固定した LP の最適の双対値。
  - その LP を解かずに「今の LP の双対値で最適と示せた」ときは、今の LP の双対値から取る。
  - 温める基底も、その LP の最適の基底があればそれを使う。
- **STRICT=2 の木の中の研磨:**
  - 求解の期限を渡す。
  - 間に合わなければ研磨せずに受け取り、見積りを足して「未研磨」の印をつける (`Solver::warm_mark`)。
- **返す前の研磨:**
  - 木の中で研磨が済んだ暫定解なら飛ばす。
  - 未研磨・印のない暫定解だけを `d` の形 (期限つき、間に合わなければ見積り) で扱う。

### 温めが dano3 で逆効果だった訳

- 基底なしの `TwoStageLp::solve` は、1 スレッドで大きい LP なら G5SEQ の経路に入る。
  - 単体法を反復の上限 (0.5 × (行 + 列)、dano3_3 では 8512) で打ち切り、内点法 + クロスオーバーの頂点を採る。
  - dano3_3: 単体法 2.55 秒 (上限に到達) + 内点法 + クロスオーバー 4.3 秒 = 6.8 秒 (`ENOMOTO_DEBUG_RACE=1` で確認)。
- 基底を渡すと、この経路を通らず、双対単体法だけで解く。
  - dano3_3: 4.2〜4.5 万反復、16〜17 秒。
  - 整数を固定した LP の最適の基底 (`resolve_continuous` のもの) から始めても、同じく 4.2 万反復だった。
  - 写した基底の出来の問題ではなく、dano3 の整数を固定した LP が双対単体法に重い。
- 直すなら、温めた解き方にも同じ上限を当て、超えたら基底なしの経路に切り替える形が考えられる (未実装)。
