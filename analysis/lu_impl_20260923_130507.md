## L2 (+ L10): 再分解カーネル G1

実装 (コミット `b84bec9`, `ac374c6`, `b38b3de`、`ceb2c96` で revert):
- `KernelMatrix::col_val` — 列ミラーと並行の値キャッシュ。列 `j` の値は `col_max_abs_dirty[j] == false` の間だけ有効
  (列の要素・所属が変わる経路は全て `eliminate` の `touch` → `refresh_column` で dirty になり、清浄化する再走査は
  列全体を書き直す)。`find_best_pivot` の清浄列の候補値と `eliminate` のピボット列値 (`row_get(i, pj)`) を
  キャッシュから読む。
- `KernelMatrix::col_hint` — 列ミラー各要素の「行内位置」の推測。再走査 (`col_max_abs_rescan`) は推測位置を検証し、
  外れたら最大 8 要素の線形歩行、それでも外れたらその側だけ二分探索。ヒントは `col_insert`/`col_remove`/
  再配置でも一緒に動かす。
- L10: `refactorize` の行ベクタを列走査 1 回分で数えて正確な容量で確保、`factorize` の `u_row` を
  ステップ昇順の `u_entries` から正確な長さで切り出し。

効果 (フェーズ計測、`ENOMOTO_PROF_PHASES_EXT=1`、1 回):

| 問題 | pivot 探索 base → G1 | refactor base → G1 | wall |
|---|---:|---:|---:|
| pilot87 | 613 → 324〜349 ms (-43%) | 2027 → 1712〜1755 ms (-15%) | 6735 → 6246〜6296 ms |
| dfl001 (L2 のみ) | 1216 → 895 ms (-26%) | 2218 → 1894 ms (-15%) | 15907 → 15255 ms |

A/B (base vs G1, 3 rounds, 再分解の多い 18 問): pilot87 -6.1%, grow22 -6.4%, dfl001 -5.1%, maros-r7 -4.5%,
d2q06c -2.9%, perold -2.4%, pilot -2.2%、合計 -4.0%。25fv47 が +11.8% だったが 5 rounds の再計測で -0.1%
(ビット同一なので経路は同じ; ノイズ)。10% 以上の改善問題なし → 不採用。
目的関数値と反復数ログが基準版と一致 (名前衝突のため pilot / pilot.ja / pilot.we は 3 問中 1 問だけが突き合わせ対象で、残りは A/B 側の status・目的関数値で確認; wood1p だけは基準版自体が実行ごとに反復数の変わる非決定的問題
— faer 並列 QR、既報 P1 — のため比較対象外)。

callgrind (pilot87, L2 適用後) で見た残りの内訳: `refactorize` 24.3% のうち `eliminate` 13.6%、
`find_best_pivot` 7.6% (うち再走査 4.3%、その `row_get` 3.4%)。ヒントで再走査の二分探索はほぼ消えたが、
refactor が総時間の 28% しかない pilot87 で総時間 10% を得るには refactor を 36% 削る必要があり、G1 では 15%。

## L11: `eliminate` の散布方式 (A/B 前に棄却)

ピボット行を列で散布 (`pmark`/`pval`、epoch 印) し、影響行を 1 パスで in-place 更新 (既存要素は散布を引くだけ、
ピボット列要素と相殺ゼロは詰める)、ピボット行の列数より当たりが少ない行だけ 2 パス目で fill を集めて後ろから
in-place マージ、という実装をした (ビット同一を全 93 問で確認)。ピボット行の最大列より右は `copy_within`
で済ませる早期打ち切りも追加。しかし pilot87 の refactor フェーズは 1712〜1750 ms (従来の 2 ポインタ
merge) → 2048〜2165 ms と悪化した。従来の merge は fill の無い行 (pilot87 で 68%) では既に「行の要素数
程度」の反復で済んでおり、散布方式は 1 要素あたりのランダム参照 (`pmark[ja]`) と行ごとの `rmark` 書き込み、
fill 行での 2 パス目が上乗せになるだけだった。コードは破棄 (コミットせず)。

## L5 + L6: eta ファイル G2

- L6 (コミット `6566566`、`ebdebcb` で revert): `u_transpose_solve_seeded` を、seed が `u_seq` にあれば
  `u_seq[slot_pos[seed]..]` だけ (singles は全てゼロなので飛ばす)、seed が singleton ならその 1 本 + `u_seq`
  全体、の走査にした。FT 更新後も「eta の off_diag は `u_seq` 上で前方しか参照しない」不変条件が保たれる
  (新 eta は末尾、行 p は全 eta から除去) ので厳密同一、tick 合計も同じ。pilot87 の btran(rho_p) 664 → 617 ms。
- L5: `commit_update` を callgrind で見ると pilot87 で 2.55% (うち `pack_scaled_dense` 1.0%、`u_seq.remove`
  の memmove 0.15%)、上限が小さいため `pack_scaled_dense` の密分岐の「複写→スケール」を 1 パスにする
  最小変更だけ実装した (tombstone 化は FTRAN/BTRAN の最内ループに分岐を足すため見送り)。
- A/B (base vs L5+L6, 3 rounds, 14 問): maros-r7 -8.6%, pilot87 -5.6%, pilot -2.2%、他は ±7% のノイズ幅
  (80bau3b +6.6%, d2q06c +5.8% — いずれもビット同一)。10% 以上の改善なし → 不採用。

## メモ (今後向け)

- G1 (L2+L10) と L6 はビット同一で一貫して数% 速い (pilot87 で合計約 -10% 相当になりうる) ので、
  基準を「複数の対処法の合算」で評価する場合は再検討の価値がある。コードは `b84bec9`/`ac374c6`/`b38b3de`/`6566566`。
- 計測ノイズ: 同一ビルド同士でも小〜中規模問題で ±10% 前後振れた (pilot.ja -12.4% / +3.5%、25fv47 +11.8% / -0.1%)。
  10% 基準の判定には 5 rounds 以上か再計測が必要。
- `lu_ident.py` 系の自作スクリプトで問題名を `split('.')[0]` にしていたため pilot / pilot.ja / pilot.we が衝突し、
  案 (f) の pilot の破綻を最初の全問チェックで見落とした (A/B で発覚)。拡張子だけ落とすよう修正済み。
