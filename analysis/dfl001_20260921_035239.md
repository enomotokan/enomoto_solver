# dfl001 タイムアウト分析(自己改善ループ 反復#3)

対象: NETLIB `dfl001`(6071 行 x 12230 列, 35,632 非零; `.netlib_cache/mps/dfl001.mps`)。
ベンチマーク記録 `scripts/benchmark_results.json`: `{"error": "timed out after 60.0s"}`(HiGHS・自ソルバとも未記録)。
対象コミット: `267e33f`(main)。HiGHS 1.15.1(`highspy`)。全数値は本セッションでこの環境で実測したもの。推定値はその旨明記する。

## 結論(要約)

**timeout の直接原因は、`extended_dual` 主ループの「実行不能行数プラトー」検出器(`src/simplex/extended_dual.rs:1700`, `:2964-2973`)が、退化もサイクリングもしていない健全な解法過程で誤発火して Bland 規則(`bland_mode`)にラッチし、その Bland モードが数値的に崩壊して再分解を 5 反復に 1 回以上の頻度で起こし続けること**である。

- 主ループ 20,000 反復のうち、ラッチ前の約 8,900 反復は約 10 秒(約 1.2 ms/反復)。ラッチ後の約 11,100 反復に約 265 秒(約 24 ms/反復、20 倍)かかる。ラッチ後の時間の **91.8% が再分解**(2,120 回 x 約 119 ms; 原因内訳 `d_drift=1335 try_update=692 drift=55 verify=23 illcond=15`)。
- ラッチ前の解法過程は健全: 退化ピボット 0.0-0.2%、`stall_count` は終始 0、目的関数値は単調増加(2.04e6 → 9.25e6)、`remaining_m_side` も 11045 → 4762 と単調減少。プラトー検出器が見ている「実行不能行数の最小値が 5,000 反復更新されない」は、この問題では HiGHS でも同じ(HiGHS のログでも `Pr:` 件数は 1000 反復目から 12000 反復目まで 900-1100 で横ばい)。つまり **停滞の兆候ではなく、この問題の性質**。
- プラトー検出器を無効化するだけ(他は一切変更なし)で、主ループ 22,978 反復・**39.4-39.9 秒**で `Optimal`、目的関数値 **11266396.04667138**(HiGHS と 1e-15 相対で一致)、返却点は元 LP に対して行違反最大 5.7e-14・列違反最大 7.9e-14(3 回計測、39.7/39.9/40.2 s)。
- ただし `MAX_ITERS = 20_000`(`src/simplex.rs:140`)は dfl001 に必要な 22,978 反復より小さく、検出器を外しても反復上限で `None` になり BIG_M フォールバックに落ちる(実測 62.8 s、誤答)。両方直す必要がある。
- フォールバック(`src/simplex.rs:2996-3000`, 古典 BIG_M 経路)は `optimal` と称して **元 LP に対して実行不能な点**を返す(目的関数値 11259043.80 = 真の最適値より 6.5e-4 相対で小さい; 列上下限違反 1,289 本、最大 108; 行違反 22 本、最大 0.44)。greenbea 分析の欠陥 (C) が未修正のまま残っており、現在は 60 秒タイムアウトで隠れている。

**原因分類**: (主) **ピボット選択の非効率 -- 反サイクリング機構(プラトー検出 → Bland 規則)の誤発火**。悪条件・再分解頻発はその結果であって原因ではない。(副) **反復上限の不足**(`MAX_ITERS`)。(副) **正答性バグ -- BIG_M フォールバックが実行不能点を `optimal` として返す**。退化・サイクリングには該当しない(実測で否定)。初期基底・presolve は timeout の原因ではない(ただし presolve 縮約率と 1 反復コストは HiGHS 比で劣り、修正後も 5.3 倍遅い; 後述)。

## 3. 機序(該当ソースを読んだ上での説明)

### 3.1 プラトー検出器の誤発火(`src/simplex/extended_dual.rs:1687-1704`, `:2927-2973`)

```rust
let infeasible_plateau_limit = (4 * stall_limit).min(MAX_ITERS / 4);   // :1700  dfl001 では 5000
...
if infeasible_len < best_infeasible_len { best_infeasible_len = infeasible_len; infeasible_plateau_count = 0; }
else { infeasible_plateau_count += 1; if infeasible_plateau_count > infeasible_plateau_limit { bland_mode = true; } }  // :2964-2973
```

- この検出器は `pilot4`(実行不能行数が 16,000 反復固定)と `greenbea`(248/249 で振動)のために追加され、`MAX_ITERS / 4` の上限はコミット `2cffbe5`(greenbea 修正, 2026-09-21)で導入された。それ以前は `4 * stall_limit = 118,280 > MAX_ITERS` で dfl001 では発火し得なかった(greenbea 分析の記述「dfl001 は 52 s で `MAX_ITERS` 到達」はその状態)。この上限導入で dfl001 は約 52 s → 約 305 s に悪化した(どちらも誤答なので `benchmark_results.json` 上は変化なし)。
- 判定は「実行不能行数の *最小値* が更新されない」ことだけを見ており、目的関数の進捗(`stall_count`)、`remaining_m_side` の減少、基底の実際の変化のいずれも参照しない。dfl001 のような大規模・ネットワーク的 LP では実行不能行の集合は絶えず入れ替わりつつ数は横ばい(`pool_grew 40% / pool_shrank 50%`)であり、HiGHS の同問題ログでも同じ挙動を示す。「数が減らない」は停滞の証拠にならない。
- 一方で真の停滞検出(`stall_count`, `:2918-2925`, `theta_q * dj_q < 1e-9` が `stall_limit = 5m = 29,570` 回連続)は dfl001 で一度も発火しない。

### 3.2 Bland モードが数値的に崩壊する理由(`:2428-2432`, `:2443-2455`, `:2134-2135`)

- `bland_mode` では chuzr は最小行番号、chuzc1 は候補を **比率ではなく列番号順にソート**し(`candidates.sort_by_key(|c| c.j)`, `:2429`)、そのままの順序で BFRT の歩み(`:2443-2455`)を実行する。すなわち進入列は「最小比率」ではなく「列番号が小さい順に幅を積んでいって偏差を覆った最初の列」になり、それより比率の小さい列が非基底のまま残るので双対実行可能性が壊れる。§1.3 の目的関数値の暴走(9.25e6 → -3.30e8 → +6.54e8)はこれと整合する。古典経路(`src/simplex.rs:4034-4039`)も同様に比率を無視するが、そちらは `FT_MIN_PIVOT` を超えるピボットを優先する保護があるのに対し、拡張経路の Bland 分岐にはピボット規模の保護がない。
- 双対実行可能性が壊れた `d` は 5 反復ごとの `d` ドリフト検査(`D_DRIFT_TOL = 1.0`, `:3137-3157`)で相対残差 57-159 として捕まり、そのたびに再分解 + `fresh_d_into` で `d` を作り直す(1,335 回)。加えて小さいピボットで `try_update_precomputed` が拒否され(692 回)、再分解が続く。1 回の再分解は m=5914 で約 119-125 ms(`sparse_lu::factorize`, `refactorize` `:902`)なので、これだけで 253 s。
- Bland モード中 `remaining_m_side` は 4,713 で完全に静止し(iter 10,000-20,000)、実行不能行数も 1,487-1,526 で横ばい。つまり Bland モードは「停滞を打破」するどころか本物の停滞を作り出している。

- **再分解 125 ms/回**: m=5914、基底非零約 3 万で 125 ms は遅い(HiGHS は m=3657 の再分解を約 185 回行って解全体が 7.5 s)。59 回は `x_B` ドリフト検査由来で、エスカレーション梯子(`XB_DRIFT_TOL` 1e-8 → 1e-4, `:496-519`)は iter 約 9,000 で上限 1e-4 に達している。

- 拡張経路で最も遅い問題: pilot87 17.0 s(6,631 反復, 再分解 55)、pilot 4.7 s、fit2p 4.6 s、d2q06c 3.3 s、maros-r7 3.1 s、greenbea 2.9 s、greenbeb 2.6 s。いずれも再分解回数が数十回で、`x_B` ドリフト梯子が効いている問題群。dfl001 の「1 反復が重い」問題(§3.3)はこれらと共通。

## 5. 根本原因の分類

1. **ピボット選択の非効率 -- 反サイクリング機構の誤発火(主因)**: `infeasible_plateau_limit`(`extended_dual.rs:1700`)による `bland_mode` ラッチが、停滞していない解法過程で発火する。Bland モードは双対実行可能性を保たない実装(`:2429` の列番号ソート + BFRT 歩み)で、`d` ドリフト再分解が 5 反復ごとに走り、1 反復が 20 倍重くなる。全体時間の約 87%(265 s / 305 s)がこの状態で費やされる。
2. **反復上限の不足(副因)**: `MAX_ITERS = 20_000`(`simplex.rs:140`)< 必要反復 22,978。HiGHS は 18,117 反復(presolve off では 21,189)で、この規模の問題では 2 万反復は普通に必要。
3. **正答性バグ(副因, 現在は timeout で隠れている)**: BIG_M フォールバック(`simplex.rs:2996-3000`)が実行不能な点を `optimal` として返す。greenbea 分析の欠陥 (C)、未修正。
4. 非該当: 退化・サイクリング(退化ピボット 0.2%, `stall_count=0`)、悪条件(修正後は `verify=1 try_update=0 illcond=0`, DSE 誤差 99.8% < 1%)、初期基底(crash 後の目的関数は単調に改善)。
5. 修正後に残る runtime 課題(5.3 倍): 1 反復コスト 4.2 倍(再分解 125 ms/回, ドリフト検査 12%, PRICE/CHUZC1 24%)、presolve 縮約率(行 -2.6% vs -40%)。

## 6. 改善候補(優先順、効果見積もりつき)

1. **プラトー検出器の条件を「本当に停滞している」ときに限定する**(`extended_dual.rs:2964-2973`)。候補: (a) 窓内で `remaining_m_side` が減少していたらリセット(dfl001 では 8,575 → 4,762 と減り続けている); (b) 窓内で目的関数(`contribution_base` の累積)が `STALL_PROGRESS_EPS` を超えて改善していたらリセット; (c) 発火時の応答を `bland_mode` ではなく「再分解 + DSE リフレッシュ + 実行不能集合の再構築」にし、それでも同じ状態が続く場合のみ Bland へ。効果: 実測で 305 s → 40 s(全体の 87% を占める Bland 区間が消える)。リスク: pilot4/greenbea の再発。ただし §4.1 のとおり現状どちらも検出器なしで解けており、`greenbea` 分析 §D の「248/249 振動」は PR #3 の BFRT 許容誤差修正で解消済み。全 93 問題スイープで確認すること。
2. **`MAX_ITERS` を問題規模に応じて設定する**(`simplex.rs:140`)。例: `max(20_000, 10 * (m + n))` 程度、あるいは HiGHS 同様に実質無制限にして時間・停滞で打ち切る。効果: 1 と組み合わせて初めて正答になる(実験 C で実証: 1 だけでは反復上限で誤答)。リスク: 真に停滞する問題で長時間走る → 1 (c) の停滞応答と `stall_count` に任せる。
3. **BIG_M フォールバックの返却点を検証する**(`simplex.rs:2996-3000`)。`unscale_result` 前後で元の上下限・行制約に対する違反を測り、`PRIMAL_FEAS_TOL` を超えるなら `optimal` を返さない(別ステータス、または拡張経路を新しい分解から再開)。効果: 誤答の防止(dfl001 の 1,289 本の列違反、greenbea 分析の (C))。1・2 が入れば dfl001 ではこの経路は通らないが、他問題で `None` になったときの安全網として必要。
4. **Bland モード自体の修正**(`extended_dual.rs:2428-2432`): 双対単体法での Bland 規則は「最小比率を達成する候補の中で最小添字」であって、比率を無視して最小添字を取ると双対実行可能性を失う。古典経路の `FT_MIN_PIVOT` 保護も移植する。効果: 将来 Bland にラッチした問題での再分解嵐(24 ms/反復)の回避。1 が入れば dfl001 には影響しない。
5. **1 反復コスト**(修正後 40 s → HiGHS 7.5 s の残り 5.3 倍; 上限見積もり): 再分解 19% + ドリフト検査 12% = 31% が「基底の健全性維持」コスト。(a) `sparse_lu::factorize` の 125 ms/回(m=5914)の高速化、(b) ドリフト検査を `XB_CHECK_INTERVAL=5` から HiGHS 型の `updateVerify`(行/列ピボット比較は `pivot_grossly_inconsistent` として既に一部存在)に寄せて頻度を落とす(過去に間隔緩和で cycle/degen3 が壊れた記録あり、`:426-447`; 要 A/B)、(c) PRICE の `std.lb[j] == std.ub[j]` 判定を事前に除外した行構造にする(固定列は `std` から既に落とされているはずなので判定自体が不要かもしれない; 要確認)。presolve は HiGHS が 2,414 行落とすのに対し 157 行で、`reduce_equalities`(227 ms)が依存等式をほとんど見つけていない。
6. 診断: `PROF_PHASES_EXT` の報告にドリフト検査の時間(本分析で 12.4%)と、プラトー検出器の発火反復・`bland_mode` ラッチ反復を出すと、今回の切り分けが一発でできる。
