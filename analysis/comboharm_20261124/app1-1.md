# app1-1 の combo の害の切り分け (2026-11-25、親の依頼)

combo の計測 (analysis/combo_20261124) で、app1-1 は 1 スレッド 7.7 → 65.9 秒、4 スレッド 8.9 → 34.8 秒と遅くなった。
この機械 (4 コア)・1 スレッド・種 1・600 秒で、1 本ずつ (並べずに) 回して切り分けた。部品の短い名前は README.md の表と同じ。

## 0. まとめ

| 項目 | 内容 |
|---|---|
| 原因の部品 | 1 スレッドは **heur と tie の組み合わせ** (どちらか 1 つでは害がほぼない)、4 スレッドは **heur** だけ (4 節)。時間の大半 (約 36 秒) は、heur が開くサブ MIP の中の robust FJ が、手間 (ticks) の数え違いで上限の 10 倍まで回ること |
| 仕組み | 下の 2 節。tie で根の shifting が暫定解 −2 を出さなくなり、暫定解が FJ の 0 だけになる → heur (FJSYNC_LABEL) でそれが「FJ だけの悪い暫定解」(`fj_poor`) と見なされ、暫定解なしの RENS を回す → そのサブ MIP の中の robust FJ (HEUR_ADAPT の f_s で開く) の Local-MIP が、密な列の多いこの問題で手間を実時間の 1/14 にしか数えず、上限 3.6 秒が安全網の 36 秒まで回る |
| 直し (既定オフ) | `ENOMOTO_MIP_LMIP_SCORE_TICKS=1` (src/mip/localmip.rs): Local-MIP の手間に、列の走査で実際に見た非零の数を足す。新しい閾値なし。1 スレッドの combo 69 → **32.6〜37.5 秒**、4 スレッドの combo 36.2 → **25.1 秒** |
| 残る害 | 直しの後も 32.6 秒 (既定 8.4 秒)。暫定解なし用のヒューリスティクス (FP の第 3 段 4〜6 秒 × 4 回など) に時間を使う。HEUR_ADAPT の設計どおりの動き (f_g = 0.86) で、元は tie で根の道筋が変わり shifting の −2 を失うこと |

## 1. 抜く・足す (`res_app1-1.jsonl`・`res_app1-1_rep2.jsonl`・`res_app1-1_ks.jsonl`)

| 形 | 1 回目 秒 / ノード | 2 回目 秒 / ノード |
|---|---|---|
| 既定 | 8.4 / 8 | 8.2 / 8 |
| combo | 69.0 / 316 | 66.2 / 316 |
| −sbpb | 70.1 / 316 | 69.0 / 316 |
| −cutu | 68.1 / 316 | 68.5 / 316 |
| −bfrt | 70.0 / 771 | 70.4 / 771 |
| −ppi | 69.5 / 316 | 67.6 / 316 |
| **−heur** | **11.5 / 1080** | **12.0 / 1080** |
| −nra | 70.9 / 341 | 70.3 / 341 |
| −enum | 70.8 / 316 | 68.5 / 316 |
| **−tie** | **15.2 / 157** | **15.5 / 157** |
| +heur | 13.3 / 8 | |

- 2 回とも同じノード数で、秒の差も 3 秒以内。揺れではない。
- heur・tie のどちらを抜いても害が消える。片方だけ足しても 13 秒前後で、両方そろうと 70 秒。
- 直し k・s は効かない (この問題の害は nra・enum と関係しない)。
- 根の下界は最初から −3 (= 最適値) で、時間はすべて −3 の解を見つけるまでにかかる。

## 2. 仕組み (ログ `logs_app1-1_{def,heur,tie,heurtie}.err`、`ENOMOTO_MIP_LOG=1`。サブ MIP の中は `logs_app1-1_heurtie_subv.err`、`ENOMOTO_MIP_SUBMIP_VERBOSE=1`)

| 形 | 根の暫定解 | 根の後の暫定解 | −3 を見つけた所 |
|---|---|---|---|
| 既定 | FJ の 0 (名札 `[tree]`)、shifting の −2 (1.10 秒) | −2 | ノード 8、7.8 秒 (tree diving) |
| +heur | FJ の 0 (名札 `[feasibility jump]`)、shifting の −2 (1.18 秒) | −2 | ノード 8、11.8 秒 |
| +tie | FJ の 0 (`[tree]`)。shifting は見つけない | 0 | ノード 1201、11.2 秒 (tree rounding) |
| +heur+tie | FJ の 0 (`[feasibility jump]`)。shifting は見つけない | RINS の −1 (57.6 秒) | ノード 105、68.8 秒 (tree RINS) |

1. **tie**: 根のカットの 1 周目の選び方が変わる (19 本 → 1 本)。カットの後の LP の解が変わり、そこから丸める shifting が −2 を見つけない。
2. **heur** (`FJSYNC_LABEL`): 同期の FJ の解に `[feasibility jump]` の名札をつけ、`inc_only_fj` を真にする。既定では同じ解の名札は `[tree]` で、偽のまま。
3. 1 と 2 がそろうと、暫定解は FJ の 0 だけ (根の LP −3.99 に対しギャップ 1.0 > `ENOMOTO_T_MIP_FJ_POOR_GAP` 0.5)。
   - `fj_poor()` (src/mip/solver.rs) が真になる。
   - 暫定解なしの RENS (src/mip/heuristics.rs `rens`、固定率 0.8、サブ MIP に残りの 4 割・最大 20 秒) が回る。
   - 片方だけなら、shifting の −2 があるか (+heur)、名札が `[tree]` (+tie) なので、この道に入らない。
4. **サブ MIP の中の robust FJ**: そのサブ MIP (自由な列 238) は実行不能で、根のヒューリスティクスで解がない。
   - `HEUR_ADAPT` の f_s で開く robust FJ (`robust_fj_retry`、`ENOMOTO_MIP_ROBUST` の `g` の位置) が回る。
   - 上限 cap = 3.59 秒 (6 秒 × f_s 0.6)。
   - 1 スレッドでは `ENOMOTO_MIP_TICKS` の `f` で、上限を手間で数え、時間は 10 倍 (35.9 秒) の安全網 (src/mip/mod.rs `feas_fj_lmip_early_salt`)。
   - ログ: `early FJ/Local-MIP (1 thread): FJ 0.18s (0.54s in ticks), Local-MIP 35.75s (2.55s in ticks)`。
     Local-MIP の手間が実時間の 1/14 で、安全網まで回った。
   - この間、主のスレッドは待つだけ。サブ MIP の `TICKS cpu` は 8.8 秒なのに、経過は 44 秒。
5. **手間の数え違いの元**: Local-MIP は 1 手の手間を見当 `step_work` = (行の平均の長さ + 列の平均の長さ + 1) × 見る列の数 (64) で数える。
   - 実際の重さは候補の列のスコア (`St::score`、列の長さに比例)。gdb で 2 秒おきに 12 回止めると、12 回とも `St::score` の中だった。
   - 候補の列は違反行の非零から選ぶので、選ばれる列の長さの期待は Σ len² / Σ len。
   - app1-1 は密な列が多く (長さ 1175〜1225 の列が 5 本、長さ 100 超の 30 本で非零の 53%)、この期待は 429。列の平均の長さ 7.4 より 2 桁大きい。
6. 確かめ (同じ heur+tie と combo、1 本ずつ):

| 変えたもの | +heur+tie | combo | 暫定解なしの RENS |
|---|---|---|---|
| なし | 69.5 秒 | 69.0 秒 | 44.3 秒 |
| `ENOMOTO_MIP_TICKS=ntwumclshk` (`f` を抜く: 上限を秒で数える) | 34.6 | 35.2 | 12.5 |
| `ENOMOTO_T_MIP_ROBUST_FJ_SECS=0.1` (robust FJ を回さない) | 31.0 | 31.0 | 8.9 |
| `ENOMOTO_MIP_NO_NOINC_RENS=1` (暫定解なしの RENS を回さない) | 23.6 | 24.8 | — |
| `ENOMOTO_T_MIP_HEUR_ADAPT_SUBFJ_A=50` | 92.8 | 93.6 | |
| `ENOMOTO_MIP_FEAS_EARLY_LMIP_NO_CHAIN=0` (連鎖の手を使う。連鎖の手間は数える) | 33.7 | | Local-MIP 3.99 秒 (2.79 秒 in ticks) |

- f_s は経過と上限の比で増える形なので、a_s を大きくすると上限 6 秒 (安全網 60 秒) になり、かえって悪い。
- lift の掃引の手間を数える案 (門の付いたスレッドの数え方を手間の期限の中でも使う) は効かなかった。この問題では lift の掃引はほとんど回らない。

## 3. 直し `ENOMOTO_MIP_LMIP_SCORE_TICKS` (src/mip/localmip.rs、既定オフ)

- `St` に、列の走査 (`St::for_col`: スコア・breakthrough など) で見た非零の数 `col_work` を持たせる。
- 16 手ごとに手間を足す所で、見当 `16 × step_work` に加えて `col_work` の増えた分を足す。
- 新しい閾値はない。見当の分は残すので、手間は実時間よりやや多めに数える (app1-1 では Local-MIP 1.34 秒を 2.77 秒と数える)。上限より先に止まる側。

| 形 (1 スレッド、種 1、600 秒、ログつき 1 本) | 秒 / ノード | サブ MIP の中の Local-MIP |
|---|---|---|
| +heur+tie + 直し | 32.3 / 105 | 1.34 秒 (2.77 秒 in ticks) |
| combo + 直し | 32.6 / 316 | 1.35 秒 (2.84 秒 in ticks) |
| combo + 直し k・s + 直し | 32.9 / 316 | 1.56 秒 (2.98 秒 in ticks) |

run.py で 1 本ずつ・2 回 (`res_app1-1_sct.jsonl`・`res_app1-1_sct_rep2.jsonl`・`res_app1-1_sct_ks.jsonl`・`res_app1-1_sct_rep2_ks.jsonl`、`CH_EXTRA` で直しをつける):

| 形 | 1 回目 秒 / ノード | 2 回目 秒 / ノード |
|---|---|---|
| combo + 直し | 37.5 / 316 | 37.4 / 316 |
| combo + 直し k・s + 直し | 37.4 / 316 | 38.4 / 316 |
| +heur+tie + 直し | 39.0 / 686 | 39.3 / 686 |

- ログつきの回 (32 秒台) より 5 秒ほど遅い。+heur+tie はログつきの回の 105 ノードに対し 686 ノードで、道筋が違う
  (ログの有無で経過時間に依る判定の時刻がずれる。README の 7 節)。
- 確かめ: fuzz 7 本は誤答 0 (`fuzz_sct.out`、直しと `HEUR_ADAPT=1` をつけて)、cargo test は 424 通過・0 失敗。
- 既定の道筋は変わらない (`check_default.py` の 6 問は基準と一致)。
- 残る 32 秒の内訳 (`logs_app1-1_combo_sct.err`):
  - 暫定解なしの RENS 約 9 秒 (中の FP の第 3 段 6.3 秒・robust FJ 1.55 秒)。
  - 外側の FP の第 3 段 5.1 秒、RINS 4.6 秒 (中の FP の第 3 段 4.2 秒、−1 を出す)。ここまでで木に入るのが 21.7 秒。
  - 木の中のサブ MIP の FP の第 3 段 4.6 秒など。ノード 316 (31.9 秒) で −3。
  - どれも HEUR_ADAPT が暫定解なしとみなした問題で回す設計どおりの動き (f_g = 0.86)。
  - 元は tie で shifting の −2 を失うことで、tie の根のカットの選び方の運の問題と見る。仕組みとしての直しの見当はない。
- **ほかへの波及の見込み**: 同じ数え違いは、手間の期限で止める 1 スレッドの早めの FJ/Local-MIP (前処理と根の後の robust FJ) すべてに当たる。
  - 当たるのは、密な列がある問題で連鎖の手を使わないとき (2026-11-20 から既定で連鎖なし)。
  - 既定でも、外側の根の robust FJ (暫定解がないとき) で同じことが起きうる。上限 6 秒 (実行可能性問題は 30 秒) の 10 倍まで回る。
  - 既定にするかは、早めの FJ/Local-MIP が効く問題 (fhnw-binpack4-48・ns1116954 など) で、早く止まりすぎないかの確かめが要る (未測)。

## 4. 4 スレッド (`res_app1-1_t4.jsonl`・`res_app1-1_t4_sct.jsonl`、ログ `logs_app1-1_{def,combo}_t4.err`)

| 形 (4 スレッド、種 1、600 秒) | 秒 / ノード |
|---|---|
| 既定 | 10.8 / 4223 |
| combo | 36.2 / 1545 |
| −heur | **9.0** / 2425 |
| −tie | 38.6 / 1197 |
| combo + 直し (`LMIP_SCORE_TICKS`) | **25.1** / 1881 |

- 4 スレッドでは heur だけが原因で、tie は関係しない。
  - 根の暫定解は既定でも combo でも Local-MIP のスレッドの 0 なので、tie がなくても暫定解なしの道に入る。
  - 既定でも暫定解なしの RENS は回るが、1.4 秒で終わる。
- combo では、並列のサブ MIP (RENS、自由な列 238、1 スレッドの暫定解なしの RENS と同じもの) が 19.9 秒かかり、根のヒューリスティクスの終わり (28.1 秒) まで根を止める。
  - 中で 1 スレッドと同じ robust FJ の回りすぎが起きていると見る。直しで 36 → 25 秒になることと合う。サブ MIP の中のログは未確認。
  - ほかに、heur の FP の第 3 段 (6.1 秒) と RINS (5.4 秒) が根の時間を足す。
