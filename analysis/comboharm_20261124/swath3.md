# swath3: combo の害の切り分け (2026-11-25、親の依頼、GATE)

MIPLIB 240 問の組み合わせの計測で、swath3 は combo で 1・4 スレッドとも約 1.8〜1.95 倍遅かった。
- 1 スレッド: 101 → 191 秒
- 4 スレッド: 44 → 86 秒

最適値 397.76 はどちらも同じ。

1 スレッド・種 1・600 秒で切り分けた。部品の短い名前は README の表のとおり。
- ビルド: 先端 12a360ac8 で `pip install -e .` し、check_default は 6 問とも一致した。
- 回し方: 2 本ずつ並べて回した。
- ノード数: この問題では、同じ設定・同じ種なら回をまたいで同じだった (種 2 の `1o` だけ揺れた。3 節)。

## 0. 結論

- **原因: heur (`HEUR_ADAPT=1`) が中で有効にする FP の第 3 段 (`fp_stage3`)**。
- **仕組み:** 第 3 段がサブ MIP の中の FP で、縮まずに満額で回る。
  - サブ MIP (LP face・RENS など) は暫定解なしで始まる。そのため `adapt_gap_f` (f_g) は 1 を返し、第 3 段の上限 (500 ノード・10 秒) が f_g で縮まない。
  - その結果、孫のサブ MIP が出る。
  - これで根の RENS の解が変わり、そこからの再スタートの道筋も変わって、木が大きくなる (1 節)。
- **直し:** サブ MIP の中では第 3 段を回さない。
  - 私の版は文字 `o` (`HEUR_ADAPT=1o`) として作った。
  - 同じ中身の `m` (ff7c0f745、neos-1582420 の切り分け) が先に入っていたので、取り込みでは `m` を採った。この記録の `1o` は `1m` と同じ意味。
  - 既定オフで、新しい閾値はない。
- **直しの効き目:**
  - 種 1: 既定に足した形は既定と同じ 9459 ノードに戻る。combo は 8081 ノード・97 秒で、既定 (101 秒) より速い。
  - 種 3: 既定と同じに戻る。
- **残る差 (種 2):** 直しを入れても遅い。heur の f_t (木の中の大近傍探索の割合) が、木の初めの見込み est = ∞ で 1 に張り付き、道筋が変わる。
  - 第 3 段とは別の害で、道筋の運が大きい (3 節)。

## 1. 切り分け (`res_swath3.jsonl`・`res_swath3_part_*.jsonl`)

| 形 (1 スレッド、種 1) | 秒 | ノード |
|---|---:|---:|
| 既定 | 101 | 9459 |
| combo | 182 | 16976 |
| −sbpb | 216 | 22500 |
| −cutu・−tie・−ppi | 179〜184 | 16976 |
| −bfrt | 280 | 26667 |
| **−heur** | **100** | **8081** |
| −nra | 252 | 23549 |
| −enum | 182 | 17119 |
| **+heur** | **156** | **13653** |
| +sbpb | 172 | 14477 |
| combo + 直し k・s (nra `tk`、enum `1s`) | 187 | 16976 |
| combo + 直し k・s − heur | 98 | 8081 |

- heur を抜くと既定並みになる。ほかの部品は、抜くとかえって遅くなるか、変わらない。
- 直し k・s では消えない。
- heur が中で使う部品を、1 つずつ既定に足した。
  - `FP_STAGE3=1` だけで 150 秒・**13653 ノード** (+heur とノード数まで同じ)。
  - `FJSYNC_LABEL=1`・`P2RIT=a`・`HEUR1T=f` は 9459 ノードで、既定と同じ。
  - つまり、この問題での heur の害は FP の第 3 段がまるごと担っている。

## 2. 仕組み (`logs_swath3_{def,heur}_t1.err`、`logs_swath3_heurdbg_t1.err`。ログはコミットしない)

- 根の LP・カットまでは同じ。最初の違いは、根のサブ MIP (146 列が自由、実行不能で終わる) の手間。
  - 既定は 0.52 秒。heur は 1.89 秒、伝播の手間は 3.5 倍。
  - heur の側では、その前に CUTMIX・fixed-charge の行が 2 組余分に出る。これが孫のサブ MIP。
- 診断 (`HEUR_ADAPT_DEBUG`、この調べのために一時足した行。今のソースにはない) で、第 3 段は 13 回呼ばれた。
  13 回ともサブ MIP の中 (`submip true incumbent false f_g 1.0000`) で、外側の求解では 0 回。
  - FP は外側の根では回っていない。サブ MIP の根のヒューリスティクスとして、暫定解なし用に回る。
  - サブ MIP には暫定解がないので、f_g = 1 になる。第 3 段の上限は満額 (500 ノード・10 秒)。
- 根の RENS (4278 列が自由):
  - 既定: 8.6 秒 (CPU) で 414.34、新たに固定 820 列。
  - heur: 16.1 秒 (CPU) で 413.75、新たに固定 839 列。
  - どちらも、そこで早い再スタートに入る。
- 再スタート 1 の後の根で分かれる。
  - 既定は RENS 412.41 の後、clique で **397.76 (最適)** を見つけ、再スタート 2 (564 列固定)。そのまま木で閉じる (9459 ノード)。
  - heur は RENS 401.60 (277 列固定)、RENS 399.46・RINS 399.457 と進み、最適は木の中で見つかる (13653 ノード)。
- 第 3 段の孫の MIP が何かを見つけたわけではない。サブ MIP の手間と道筋を変え、最適を早く見つける運を外した形。

## 3. 揺れの確かめ (種 2・3、`res_swath3_seed.jsonl`・`_rep`・`_o`・`_orep`)

| 種 | 既定 | +heur (`1`) | +heur (`1o`) |
|---|---|---|---|
| 1 | 101 秒 / 9459 (2 回とも同じ) | 156・150 / 13653 (2 回とも同じ) | 102 / **9459** |
| 2 | 182・176・192 / 28067 (3 回とも同じ) | 241 / 26057 | **357・353・471 / 44580・41917・55424** |
| 3 | 109 / 11303 | 229 / 27087 | 107 / **11303** |

- 種 1・3: heur の害は再現し、`1o` で既定とノード数まで同じに戻る。
- 種 2: `1o` はかえって遅く、回ごとにノード数が揺れる (経過時間に依る判定)。
  - ログ (`logs_swath3_{def,heuro}_s2.err`):
    - 木の初めは完了率 ≈ 0 (w = 1) で、見込み est = ∞。そのため f_t = 1 の区間が長い (64 ノードおきの測り 808 回のうち 174 回)。
    - 木の中の大近傍探索の割合が、役の割合 0.25 へ寄る。
  - 再スタート前の暫定解 (tree mutation 491.38 など) が変わる。
    - 再スタート後の RINS は、既定では 2.5 秒で **397.76 (最適)**。`1o` では 402.48 で、最適は木の中 (73 秒目)。木が 2 倍になる。
  - これは f_t の働き (暫定解のギャップ 30% で木の見込みが立たないときに解探しを増やす、設計どおり) の結果で、道筋の運の要素が大きい。
    種 2 では、第 3 段ありの `1` のほうが速い (241 秒)。
- combo の計測の 1 スレッドは種 1 なので、計測の害 (101 → 191 秒) は 1・2 節の第 3 段の仕組みで説明がつく。
- 4 スレッド (44 → 86 秒) は測っていない。
  - heur の f_t・f_s・FJSYNC は 1 スレッド用。ただし第 3 段 (`heuristics.rs`) と `P2RIT=a` はスレッドの数によらない。
  - 同じ仕組みが働いていると見るが、4 スレッドは決定的でないので確かめていない。

## 4. 直し `1o` (= `1m`) の確かめ (`swath3_o_check.sh` → `res_swath3_ocheck_{1,1o}.jsonl`)

heuradapt で heur が効いた問題・害の出た問題を、1 スレッド・種 1〜3 で `HEUR_ADAPT=1` と `=1o` で比べた (2 本並べて)。

| 問題 (上限) | 種 1 (`1` → `1o`) | 種 2 | 種 3 |
|---|---|---|---|
| 10teams (120) | 9.2 → 6.6 秒 | 6.3 → 5.8 | 9.9 → 4.1 |
| neos-1171448 (120) | 105.9 → 108.0 (501 ノード、同じ) | 43.0 → 43.3 (同じ) | 92.0 → 92.1 (同じ) |
| CMS750_4 (200、時間切れの値) | 338 → 458 (2 回目: 438 → 438) | 512 → 512 | 342 → 363 |
| misc07 (60) | 8.6 → 7.7 | 9.2 → 8.0 (同じ 3561) | 11.3 → 9.7 |
| blend2 (60) | 1.4 → 1.2 | 1.3 → 0.9 (同じ 689) | 1.0 → 0.6 (同じ 285) |
| markshare_4_0 (60) | 11.0 → 11.0 (同じ) | 13.8 → 13.1 (同じ) | 14.0 → 12.3 (同じ) |

- 効いた問題の得 (10teams・neos-1171448) は残る。害の出ていた misc07・blend2 は少し速くなる。
- CMS750_4 の第 3 段の得 (presym 6.1 節) は、外側の根の第 3 段で出るので残る。
  - 種 1 の 338 → 458 は、同じ設定を 2 回目に回すと両方 438 になった。経過時間に依る揺れ (CMS750_4 は 1 スレッドでも回ごとに値が変わる)。
- fuzz・cargo test は、`m` を入れた側 (ff7c0f745、neos-1582420 の担当) の確かめに任せた。この調べでは回していない。
