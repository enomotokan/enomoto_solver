# sbdegen: 退化したノードで強分枝を省く判定を連続にする (2026-11-26、親の依頼、gap240 の型 2)

対象: analysis/gap240_20261126 の候補 2 (分枝) の 3 問 dano3_5・mcsched・swath1 (根の強さ・1 ノードの速さは SCIP と並ぶのに木が 2.5〜34 倍)。
親の案: 退化したノードで強分枝を省く判定を、0/1 でなく、退化の度合いと擬似費用の信頼度のシグモイドにする (`ENOMOTO_MIP_SBDEGEN`、既定オフ)。

## 1. 今の判定 (src/mip/solver.rs `select_branch_inner`)

- 根以外のノードで、双対退化の度合い ([`dual_degeneracy`]) が deg ≥ 0.8 (非基底の自由な構造列のうち被約費用 0 の割合) か
  ratio ≥ 2.0 ((基底の列 + 被約費用 0 の非基底列) / 行) なら、そのノードでは強分枝をしない (擬似費用だけで選ぶ)。`SB_NO_DEGEN_SKIP` で切れる。
  SCIP の relpscost の `degeneracyaware` (既定 1 = 根以外) と同じ形・同じ値 (SCIP は 0.8・2.0 で強分枝を省き、それ未満では退化の度合いで
  擬似費用の重みを上げる)。
- そのほかの強分枝の仕組み: 予算 = 強分枝以外のノードの LP 反復の 0.125 倍 + 25000 (SCIP: 0.5 倍 + 100000、`SB_BUDGET_HIGHS` で HiGHS 並み)、
  信頼度の閾値 = 予算の残りに応じて 1〜5 回、先読み 9 × (1 + 信頼できない候補の割合)、子の LP の反復の上限 = 平均の 4 倍 (10〜500)。

## 2. 3 問での働き方 (`diag0.sh` → `diag0.out`、1 スレッド・種 1・120 秒、ビルド 446700d9d)

終わりの「MIP: branching: 選んだ数, うち退化で強分枝を省いた数; 強分枝の LP 数 反復」:

| 問題 | 結果 | ノード | 分枝の選択 | **退化で省いた** | 強分枝の LP・反復 |
|---|---|---:|---:|---:|---|
| dano3_5 | 時間切れ (578.45 / 576.29) | 89 | 68 | **0** | 150・35590 |
| mcsched | 時間切れ (213803 / 194363) | 18523 | 11034 | **0** | 2884・132299 |
| swath1 | 最適 43.6 秒 | 4791 | 2787 | **0** | 2074・32726 |
| 30n20b8 (参考) | 時間切れ (解なし) | 1416 | 1355 | **1003 (74%)** | 372・75711 |

- **対象の 3 問では、退化で強分枝を省く判断は 1 度も起きていない** (analysis/sbadapt_20261124 の表の deg = 0 と同じ)。省く判定を連続にしても、
  この 3 問の木は変わらない。退化で省くのが効いているのは 30n20b8 (と P の 10teams・noswot、sbadapt の 5.4 節) の方。
- mcsched は分枝の選択 11034 回に強分枝の LP 2884 本 (候補 1442 個ぶん) で、選択の多くは擬似費用だけ (予算か信頼度で強分枝が止まる)。

## 3. 予算を HiGHS 並みにすると木は縮むか (`diag1.sh` → `diag1.out`、`ENOMOTO_MIP_SB_BUDGET_HIGHS=1`、1 スレッド・種 1・120 秒)

`SB_BUDGET_HIGHS`: 強分枝の予算を 0.125 × ノードの LP 反復 + 25000 から 0.5 × + 100000 にする (HiGHS の `mip_pscost` の予算と同じ大きさ。
SCIP の relpscost も sbiterquot 0.5・sbiterofs 100000)。

| 問題 | 形 | 結果 | ノード | 強分枝の LP・反復 | 下界 |
|---|---|---|---:|---|---|
| dano3_5 | 既定 | 時間切れ 578.448 | 89 | 150・35590 | 576.2891 |
| | 予算 HiGHS | 時間切れ 578.448 | **26** | 312・114887 | 576.2891 (同じ) |
| mcsched | 既定 | 時間切れ 213803 | 18747 | 2914・133530 | 194394 |
| | 予算 HiGHS | 時間切れ **212809** | **10925** | 9724・419472 | **195175** |
| swath1 | 既定 | 最適 41.9 秒 | 4791 | 2074・32726 | — |
| | 予算 HiGHS | 最適 40.3 秒 | **2611** | 5510・89245 | — |

- 予算を増やすと強分枝の反復は 2.7〜3.2 倍になり、**ノード数は swath1 で 0.54 倍、mcsched で 0.58 倍** (同じ 120 秒で下界 +781・暫定解 −994)。
  dano3_5 は 1 ノードが重く (2 秒)、120 秒では強分枝の分だけノードが減って下界は同じ。
- 時間は swath1 で 41.9 → 40.3 秒とほぼ同じ (強分枝の手間と木の縮みが釣り合う)。予算を増やすだけで木は縮むが、得は手間で相殺されやすい。
  → 予算を「強分枝が選び方を変えている (情報を生んでいる) ときだけ」大きくする形 (4 節) を試す。

## 4. SBDEGEN: 強分枝の効き目のシグモイドで予算を動かす (`ENOMOTO_MIP_SBDEGEN=1`、既定は切)

- 効き目 s = (強分枝が疑似費用だけの一番手と違う変数を選んだノードの数 + 1) / (強分枝をしたノードの数 + 2)。
  Laplace でならした割合で、log-odds のシグモイドと同じもの。新しいしきい値は作らない。
- 予算は既定 (0.125 × ノードの LP 反復 + 25000) と HiGHS・SCIP の大きさ (0.5 × + 100000) の間を s で内挿する。
  幅をこの 2 つにした理由: 下端は今の既定で、効かないときに今より悪くしないため。上端は HiGHS (`mip_pscost`) と SCIP (relpscost の sbiterquot・sbiterofs) が使う大きさで、
  それより大きい予算は確かめた例がなく、3 節で上端でも手間と木の縮みが釣り合うところまでしか得がなかったため。
- sbadapt の失敗 (予算を減らす向きに動いて木が膨らむ) を避けるため、下端は既定のまま減らさない。`SB_BUDGET_HIGHS`・sbadapt・部分 MIP のときは働かない。
- 3 問 (`diag2.sh` → `diag2.out`、1 スレッド・種 1・120 秒): dano3_5 はノード 89 → 28 (s = 0.96)、mcsched は下界 194394 → 196193 (s = 0.11)、
  swath1 は 4791 ノード・41.9 秒 → 3019 ノード・41.5 秒 (s = 0.45)。check_default は一致。

## 5. P での計測 (`wide/`、174 回 × 4 設定 = 696 回、種 1〜3・60 秒、ビルドは .so 11-26 22:08 = e19d5ad0a のソース)

`python summ.py --perprob` (crash・取得失敗 0、食い違い 0):

| スレッド | 比 | 95% 区間 | 解けた数 既定 → SBDEGEN | 全種 1.25 倍超の遅れ | 目安 |
|---|---:|---|---|---|---|

- 1 スレッド: 効いたのは 10teams 0.57 (解けた 0 → 2)、noswot 0.80、rout 0.85。害は qiu 1.26、eil33-2 1.19 (解けた 3 → 1)、neos-911970 1.14。
  解けた数の増減は 10teams +2・h80x6320d +1・swath1 +1・timtab1 +1、eil33-2 −2・roll3000 −1。
- 4 スレッド: 効いた問題は無く (一番は timtab1 0.87)、10teams 1.58・mc11 1.39・roll3000 1.32・eil33-2 1.28 が遅い。解けた数は mzzv42z −1・physiciansched6-2 −1。
  1 スレッドで効いた 10teams が 4 スレッドでは逆に遅い。4 スレッドは強分枝の LP がノード処理と取り合うため、予算を増やした分の手間がそのまま時間に出ていると見られる。
- 結論: 1 スレッドは中立 (区間が 1 を挟む)、4 スレッドは 3% 遅く目安で外れ。既定にはしない。
  s は「選び方を変えた割合」だけを見ていて、強分枝 1 回の重さ (ノードの LP の反復に比べた子の LP の反復) を見ていないので、
  続けるなら重さも合わせた連続関数にする余地があるが、1 スレッドの得が小さいため今は打ち切りを提案する。
