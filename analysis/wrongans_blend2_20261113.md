# WRONGANS blend2 (2026-11-13): 衝突プールの連続列のリテラルの比べの許容

cand1114 の P (54a057b8、analysis/cand1114_20261113/) で、blend2 種 3 の cand1114 が optimal 7.716613 (下界も同じ、0.4 秒、850 ノード) と返した。
正しい最適値は 7.598985 (def の全種・cand1114 のほかの種・cand1113 の全種)。

## 結論

- **原因 (事実)**: リテラルの衝突プール (`src/mip/conflict_pool.rs` の `holds`) が、リテラル `x ≤ v` を `up ≤ v + 1e-9 (1 + |v|)` で「成り立つ」と読んでいた。
  ところが連続列の境界は、行の伝播で同じ大きさ 1e-9 (1 + |v|) だけ緩めて置かれる (`Domain::propose_upper`)。そのため、
  上限 2127.999997871 (= 2128 − 1e-9 × 2129) のノードで作った正しい衝突 `{x24 ≥ 2, x112 ≥ 1, x200 ≤ 2127.999997871}` を、
  上限 2128 のノードでも x200 のリテラルが成り立つと読んでいた。それで x112 ≤ 0 を課し、最適解 (x24 = 2, x112 = 1, x200 = 2128) を含むノードを捨てていた。
- **直し (f1c14c30、既定)**: 連続列のリテラルは許容なしで比べる (整数列は今のまま 1e-9)。リテラルの値は定義域の境界そのものなので、許容は要らない。
  直しで減るのは「成り立つ」と読む場合だけなので、安全側の変更。回帰テスト `conflict_pool::tests::continuous_literal_is_compared_without_tolerance`。
- **起きる条件**: 4 スレッドでだけ、約 500 回に 1 回 (1 スレッドでは種 1〜300 で 0 回)。どのノードでどの境界の下で衝突ができるかが、スレッドの順序で変わるため (推測)。
  束に固有ではなく、直す前の cand1113 でも 2 / 1200 回出た。def は 0 / 1200 回 (出なかっただけで、既定の部品の誤りなので def でも起こりうる)。

## 再現と切り分けの手順

1. 54a057b8 のビルド。blend2 を同じプロセスで繰り返し解く (種 3、4 スレッド、4 本並べて)。cand1114 は 10 / 約 5400 回 (誤った値は 7.716613・7.705284・7.716814)。
2. 前処理の後の問題を書き出し (`ENOMOTO_MIP_DEBUG_DUMP_PRESOLVED3`、前処理は決定的)、HiGHS で解いた最適解をデバッグ解にした (`ENOMOTO_MIP_DEBUG_SOL`。
   木の従スレッドにも渡る)。誤った回では毎回、ノードの伝播で、リテラルの衝突 (理由 -7) がデバッグ解の列の境界を外していた。
3. 衝突をプールに入れる所 (自前・取り込み・大域的に成り立つリテラルを除いた後) で調べると、どの衝突もデバッグ解を切っていなかった。
   大域的な境界 (`tighten_global`・`commit_root`・待ち行列の包) もデバッグ解を外していなかった。
4. プールの伝播の中で、「定義域がデバッグ解を含むのに、課す否定がデバッグ解を外す」節を出すと、上の衝突だった。
   x200 のリテラル 2127.999997871 は、デバッグ解の 2128 と 2.13e-6 だけ違う。旧い許容は 1e-9 × 2128.999997871 = 2.13e-6 で、2128 ≤ 2128.0000000000 として成り立つと読む。
   (2〜4 の診断は手元のビルドだけに足したもので、コミットしていない)

## 影響

- 既定の部品の誤りなので、直しは全設定に効く。cand1114 の P・M の分担 (54a057b8) は直す前のビルドで回っているが、起きるのは 500 回に 1 回ほどなので、
  集計では blend2 種 3 の 1 回を誤答 (解けていない扱い) にすればよい。
- 似た比べ: 連続列の境界を許容付きで比べて「成り立つ」と読む所が、ほかにもあるかもしれない (双対証明の伝播など)。今回は調べていない。
