# 共有の待ち行列からノードを「いつ・いくつ取り込むか」 (pool_bound2、2026-11-04)

bench に使う環境変数: `ENOMOTO_MIP_POOL2_TAKE=h` または `ENOMOTO_MIP_POOL2_TAKE=g,i,k4` (試作、既定では使わない)。
診断は `ENOMOTO_MIP_POOL2_DIAG=1` (+ `ENOMOTO_T_MIP_POOL2_DIAG_REF=<値>`)、どちらも既定では使わない。

並列 3 セッションのうちの 2 (担当: 共有の待ち行列からノードを取り込む時機と数)。きっかけは `analysis/memcap_c_20261104.md` の
「supportcase18 で 4 スレッド・600 秒、共有の待ち行列が 40 万ノードまで増え、下界が根の値 47.1867 から動かない (HiGHS は 600 秒で
下界 48.0)」と、その原因の推測「共有の待ち行列の良いノードが `pool_balance` でほとんど取り込まれない」。
4 CPU・約 15 GB の機械、ソルバーは同時に 1 つ、4 スレッド。生データ・スクリプトは `analysis/pool_bound2_20261104/`。

## 結論

- **推測の仕組みそのものは半分当たっていた (確かめた)**。supportcase18 の 300 秒で `pool_balance` は 6966 回呼ばれ、98.5% の回で
  共有の待ち行列が全体の最小の下界 (= 根の値) を持っていたのに、半分 (3397 回) はしきい値 0.2 × (打ち切り値 − 全体の下界) の内側で
  取り込まなかった。さらに**取り込んだ 3387 ノードのうち 2900 (86%) は、処理される前に `ENOMOTO_T_MIP_TREE_LOCAL_CAP` (1000)
  の超過分として共有へ出し直されていた** (超過分は下界の小さい順に出すので、取り込んだばかりの最良のノードが真っ先に出ていく)。
  しきい値を 0 にしても 92%、32 ノードごとを 4 ノードごとにしても 97% が出し直しで、取り込みは事実上空回りしている。
- **しかし、それは supportcase18 で下界が動かない原因ではない (確かめた)**。根の値 47.18666… を持つノードを分けたとき、子の LP の値も
  根の値のままかを数えると、既定で 65781 ノード中 65518 (99.6%)、純粋な最良下界優先 (`ENOMOTO_MIP_TREE_SHARED_QUEUE=1`
  `ENOMOTO_T_MIP_BB_EVERY_INC=1`) で 159986 ノード中 159900 (99.95%) が根の値のままだった。根の値のノードは処理しても処理しても
  根の値の子を生むので、どの順に・どれだけ取り込んでも下界は上がらない。実際、試した 9 通りの設定 (既定、しきい値 0、
  4 ノードごと、共有の待ち行列だけ、兄弟を残す、純粋な最良下界優先、試作 3 種) はすべて 300 秒で下界 47.1867 のままだった。
- **HiGHS の「下界 48.0」は進んだのではなく、目的関数が整数値なので 47.1867 を切り上げた表示 (確かめた)**。HiGHS 1.15.1 の 60 秒の
  ログ (`highs_supportcase18_60.log`) は途中の表で下界 47.18666667 のまま、最後の要約だけ `Dual bound 48` (ギャップ 3.70% =
  (49 − 47.19) / 49 から逆算しても切り上げ前の値で計算している)。ENOMOTO も枝刈りでは目的関数の刻み (obj_step) を使っているが、
  報告する下界は切り上げていない。この報告の差はセッション 3 (下界の計算と報告) の担当に渡す。
- **試作 `ENOMOTO_MIP_POOL2_TAKE` (取り込んだノードを出し直さず次に処理する、ほか) の効果**: supportcase18・sct2・fiball・
  mushroom-best の 600 秒では下界は既定と同じか悪く、neos-3627168-kasai だけ `g,i,k4` で下界が 984411.6 → 985386.9
  (上界 988585.6 との差が 4174 → 3199) と良くなった (各 1 回)。ノード数が減る分、supportcase18・fiball では最大 RSS が
  11.6 GB → 6.9 GB、11.2 GB → 6.3 GB と小さくなった。58 問・60 秒では解けた数が既定 44・`h` 43・`g,i,k4` 44、
  SGM 18.00・18.03・17.54 秒 (各 1 回、振れの範囲)。**既定は変えない**。

推測 (確かめていない):
- supportcase18 の根の LP は強く退化していて、分枝した変数を固めても別の最適解に移るだけで値が変わらない、と考えている
  (根の値のまま子を作る割合 99.6〜99.95% と矛盾しない)。下界を上げるにはノードの選び方ではなく、カット・分枝変数の選び方・
  対称性の扱いなど LP の値そのものを動かす手段が要る。
- 取り込みの空回り (取り込み → LOCAL_CAP で出し直し) は、上界が良く下界がばらつく問題では効いているかもしれない
  (neos-3627168-kasai の 1 回の改善はその例かもしれないが、1 回だけで振れとの区別はついていない)。

## 1. 今の取り込みの決まり (読んで確かめた)

- `pool_balance` (`src/mip/solver.rs`) は `ENOMOTO_T_MIP_TREE_BALANCE_EVERY` (32) ノードごとに呼ばれ、
  共有の最小の下界 < 自分の下界 − q × (打ち切り値 − 全体の下界) (q = `ENOMOTO_T_MIP_TREE_BALANCE_Q` = 0.2) のときだけ 1 ノード取り込む。
  そうでなく自分のほうが良ければ 1 ノード出す。
- 毎ノードの同期で、手元の待ち行列が `ENOMOTO_T_MIP_TREE_LOCAL_CAP` (1000) を超えると超過分を `pool_donate_n` で
  **下界の小さい順に**共有へ出す。潜り (plunge) の間は待ち行列が増えるので、取り込んだ直後のノードが処理より先に出ていく。
- 経緯: しきい値 0.2 は `analysis/tree_parallel_profile_20261013.md` の B1「質の釣り合い」で決まった (試したのは q = 0.2 だけ、
  SGM −3.2%)。LOCAL_CAP はその後 (2026-10-19、`docs/improvement_history.md` 9138 行目付近) にメモリの対策として入り、
  釣り合いとの噛み合わせは見直されていない。`analysis/mc11_r3_20261020.md` でも「共有の待ち行列に下界の低いノードが溜まり、
  大域の下界がそこで止まる」が主因 2 として確かめられ、試作 `ENOMOTO_MIP_TREE_POOL_BB` があった (今のコードにはない)。

## 3. 試作 `ENOMOTO_MIP_POOL2_TAKE` (既定では使わない)

カンマ区切りの組み合わせ。何も付けなければ既定と同じ動き。
- `l`: しきい値をやめ、共有の最小 < 自分の下界 (小さな許容差) なら取り込む。
- `g`: 共有の最小が全体の下界 (相対 1e-6) なら取り込む。
- `k<N>`: 1 回に N 個まで取り込む (`h`/`i` のときは止めているノードも数に入れる)。
- `h`: 取り込んだノードを止め (pin)、LOCAL_CAP の出し直しの対象から外し、次に待ち行列から取る番で最初に処理する。
- `i`: `h` に加え、今の潜りを打ち切って (潜り中のノードを待ち行列へ戻し、dive_stack を空にして) すぐ取り込んだノードへ移る。
- `t<S>`: S 秒ごとに、共有の最小 ≤ 自分の下界なら必ず取り込む (`h`・`i` を含む)。

止めたノードは `NodeQueue::holds` で待ち行列に残っているかを確かめ、処理されたら外す。

```

bash sc18_300.sh                # 2 節の表 (既定の diag_def は ENOMOTO_MIP_LOG=1 ENOMOTO_MIP_POOL2_DIAG=1 python run.py diag_def supportcase18 300)
```
