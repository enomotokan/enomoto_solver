# app1-1・nu25-pr12: HiGHS が解けて ENOMOTO が解けない原因の調査 (2026-10-19)

依頼: Mittelmann の MIP (16 スレッド) で HiGHS だけが解けた app1-1・nu25-pr12 の原因。

## 0. 要約

このマシン (4 vCPU) では、どちらの問題も 1・4・16 スレッド・120 秒で ENOMOTO も最適を示す。16 スレッドは、使える CPU の数の上限を
外した計測用のビルド (`max_threads` を環境変数で 16 にしたもの。コミットしていない) で、4 コアに 16 スレッドを詰め込んで再現した。
この形では 2 問とも 23〜57 秒かかり、ノード数は 4 スレッドの 2〜10 倍になる。60 秒の上限では解けるかどうかの境目になる。

- **nu25-pr12: 根の下界の差 → 再スタートでの被約費用による固定の差 → 木の大きさの差。**
  HiGHS は根のカットで 53766 まで上げ、暫定解 53905 との差 139 で列の 32.7% を固定して再スタートし、19〜24 ノードで終わる。
  ENOMOTO の既定は最初の根のカットのループが 53510 で止まり (LP に残るカット 34 本)、再スタートで固定される列は 3 本だけ。
  根のカットのループの第 2 段階 (`ENOMOTO_MIP_CUT_PHASE2`、HiGHS のスコアで続ける) を有効にすると最初の根が 53675 になり、
  再スタートで 525 列が固定され、4 スレッドで 17.6 → 11.9 秒になる。HiGHS 流のカット管理 (`ENOMOTO_MIP_HIGHS_CUTMGMT`、
  第 2 段階を含む) なら根は 53766 (HiGHS と同じ)、4 スレッドで 11.0 秒・17 ノード、16 スレッド相当で 40〜46 → 19〜21 秒。
  どちらも 40 問で悪化が出ていて既定ではない (`separation.rs` と `solver.rs` の `highs_cutmgmt` の注記)。
- **app1-1: 根の tableau カットの伸びが遅い + 最適解 −3 が見つかる時刻。**
  最適解 −3 が見つかると、どちらのソルバーもすぐに終わる (木の下界はすでに −3 付近)。HiGHS は根の tableau カットで
  −20.96 → −4 (14 ラウンド、5 秒)。ENOMOTO の根は 25 ラウンド・約 12 秒で −6.9〜−8.6。最初のラウンドの効き目は同じだが
  (−18.27 対 −18.08)、2 ラウンド目からの伸びが遅く、選択・前処理・目的関数の整数性のどれでもなかった。
  16 スレッド相当ではノードが 6000〜19000 に増え、−3 が見つかるのが 23〜40 秒になる。

## 1. 調べ方

- コード: 調査を始めた時点の develop 7e9f192 と、途中で取り込んだ cf46224 (二項等式の消去・時間上限に前処理を含める・
  根のカットのラウンドの上限の拡大)。下の表は特に断らなければ cf46224。
- HiGHS 1.15.1 (highspy と、`scripts/highs_instrument.patch` を当てたビルド)。HiGHS の MIP は 1〜16 スレッドのどれでも
  「Parallel search off」で、時間はほぼ同じ。
- ENOMOTO は `solve` の threads と `ENOMOTO_MIP_THREADS` に同じ値。1 問ずつ順に解いた。

## 2. nu25-pr12 (2 値 5832 + 一般整数 36、流れの保存の等式と容量の行、目的関数の刻み 5)

| | 1 スレッド | 4 スレッド | 16 スレッド相当 (60 秒) |
|---|---|---|---|
| HiGHS (既定、gap 1e-4) | 8.0 秒 (19 ノード) | 8.0 秒 | 7.8 秒 |
| HiGHS (gap 0) | | 8.3 秒 (24 ノード) | |
| ENOMOTO 7e9f192 | 62.1 秒 (1295) | 26.1 秒 | 51〜57 秒 |
| ENOMOTO cf46224 | 24.1 秒 (365) | 17.6 秒 (2073) | 40.1・45.8 秒 (3900〜5000) |
| + `ENOMOTO_MIP_CUT_PHASE2` | 18.9 秒 (355) | 11.9 秒 (355) | |
| + `ENOMOTO_MIP_HIGHS_CUTMGMT` | 21.2 秒 (207) | 11.0 秒 (17) | 18.7・21.4 秒 (207・557) |

- **ギャップの扱いは原因ではない**。HiGHS は既定では下界 53900・解 53905 (0.0093%) で止まるが、gap 0 でも 8.3 秒・24 ノード。
- **前処理**: HiGHS は 2313 行・5868 列 → 1521 行・4263 列、LP 値 52757.5 → 52957.5。LP 値を上げた 1 手は、一般整数の列
  C5858 (費用 250) の下限 0 → 8 (容量の行 `sum a_j x_j - 5 y <= 0` で、前処理で 1 に固定された x の分の活動量が 38 なので
  y >= 7.6 → 8)。7e9f192 の前処理は 2263 行・5834 列で LP 値は変わらなかった。cf46224 (二項等式の消去) で 1697 行・4730 列、
  LP 値 52957.5 になり、1 スレッドで 62 → 24 秒。HiGHS の前処理後のモデルを渡しても根のカットの後は 53550 で、残りの差は
  根のカット。
- **根のカット**: 最初の根のカットのループの後の値は、既定 53510、第 2 段階あり 53675、HiGHS 53766。暫定解 53905 は
  どちらも根で見つかる (4〜6 秒) ので、再スタートで被約費用によって固定できる列の数は根の下界でほぼ決まる (既定 3 列、
  第 2 段階 525 列、HiGHS 32.7%)。
- HiGHS の分離器を止めた結果 (`HIGHS_SKIP_SEP`、gap 0、1 スレッド): すべてあり 7.5 秒・24 ノード、tableau なし 10.2 秒・181、
  tableau・path なし (mod-k だけ) 9.6 秒・288 ノード (根 53391)。HiGHS は根が弱くても 300 ノード弱で解けるので、木の探索の
  効率にも差がある (ENOMOTO は根 53541 で 2073 ノード、4 スレッド)。
- **7e9f192 で見つけた、ノードの LP の暖め直しの問題**: 1 スレッドでノードの LP の反復 22.0 万のうち 21.0 万が、待ち行列から
  取り出したノードの基底を戻した直後の 1 回目の LP だった。1010 回の戻しのうち 102 回は、保存した後に効いていたカットの行が
  消えて基底変数の数が合わず、`set_basis` の修復で作った基底が悪い。`ENOMOTO_MIP_RESTORE_KEEP_CURRENT` (合わなければ今の
  基底のまま) で 6.0 万反復・40.1 秒、`ENOMOTO_MIP_RESTORE_NEVER` で 37.1 秒。cf46224 の nu25-pr12 では合わない戻しは 0 回に
  なったが、**app1-1 (1 スレッド) では 1407 回中 381 回が合わず、ノードの LP の反復 5.2 万のうち 3.9 万が戻した直後の LP**。
- 7e9f192 では根の「root reduced cost」ヒューリスティクスが解なしで 1 回 4〜6 秒かかっていた。cf46224 では 1 回目で解を出す
  (3.1 秒)。再スタート後も解なしで 5.6 秒使う (1 スレッド)。

## 3. app1-1 (2 値 1225 + 連続 29、目的関数は 23 個の −1)

| | 1 スレッド | 4 スレッド | 16 スレッド相当 (60 秒) |
|---|---|---|---|
| HiGHS | 27.0 秒 (2663 ノード) | 27.8 秒 | 26.9 秒 |
| ENOMOTO 7e9f192 | 27.7 秒 | 18.4 秒 | 35.0・41.6・34.7 秒 (12000〜17000) |
| ENOMOTO cf46224 | 30.7 秒 (3804) | 17.7 秒 | 39.7・23.4 秒 (17000・6100) |
| + `ENOMOTO_MIP_HIGHS_CUTMGMT` | 22.1 秒 | 17.7 秒 | 29.6・39.7 秒 |

- **終わりは −3 が見つかった時刻で決まる**。ENOMOTO は木の別スレッドの丸め・RINS で −3 を見つけた 0.02 秒後に終わる。
  HiGHS も 20.8 秒で下界 −3 に達し、27.8 秒にノードの評価 (「T」) で −3 を見つけて終わる。
- **根の下界**: HiGHS は −20.96 → −4 (再スタート後、5.0 秒)。ENOMOTO は −6.88 (1 スレッド)・−7.98 (4 スレッド、裏のカット込み)。
  根のカットのループは 25 ラウンド・約 12 秒 (分離 1 ラウンド 0.4〜0.5 秒。経路集約が 1 回 0.1〜0.17 秒で、カットは数本)。
  HiGHS の分離器を止めると、path なし 13.8 秒、tableau なし 25.6 秒で、HiGHS の根を上げているのは tableau カット。
- 差を分けた結果 (どれも根の下界の推移で比べた):
  - 前処理: HiGHS の前処理後のモデル (3242 行・1059 列) を渡しても ENOMOTO の根は −9.06。原因ではない。
  - カット選択: 既定では 1 ラウンド 150〜300 候補から 1〜13 本しか採らないが、緩めて (`ENOMOTO_T_CUTSEL_MIN_REL=0`
    `ENOMOTO_T_CUTSEL_MAXPAR=0.99` `ENOMOTO_T_MIP_ROOT_MAX_CUTS=500`) 1 ラウンド 84〜239 本採っても、9 ラウンドで −11.1 で止まる
    (既定の選択で 1127 本採った設定でも −8.7)。`ENOMOTO_MIP_TAB_HIGHS_RULES`・`ENOMOTO_MIP_CUTSEL_HIGHS` も同程度。
  - 目的関数の整数性: 費用に 1e-4 の相対的な乱数を足して整数性を崩しても、HiGHS の根は −5.04。原因ではない。
  - 最初のラウンドは同じ: 緩めた選択で ENOMOTO −18.27、HiGHS −18.08。2 ラウンド目以降は ENOMOTO −17.70、−14.37、−11.57、
    −11.24 と伸びが鈍り、HiGHS は −13.10、−8.16、…、14 ラウンドで −4。
  - 回し続ければ届く: 停滞判定・ラウンド数・時間・年齢の上限を外すと、44 ラウンドで −7、再スタート後に −4。到達点は近いが、
    **1 ラウンドあたりの伸びが小さい**。2 ラウンド目以降の tableau カットの何が違うか (カットのカットの扱い、どの基底の行を
    使うか、相補化・境界の置き換え) は未解明。
- 16 スレッド相当では 4 本が役 (ヒューリスティクス) に回り、木のスレッドは 12 本。−3 が見つかるまでに広く探す分ノードが増える。

## 4. 次の手

1. nu25-pr12: 第 2 段階 (`ENOMOTO_MIP_CUT_PHASE2`) は根の下界を HiGHS に近づけ、再スタートの固定を効かせる。40 問の悪化
   (neos5・10teams・qnet1・misc07) を避ける条件 (根の暫定解と下界の差が小さく、再スタートで固定が増えそうなときだけ、など)
   を探す。
2. ノードの基底の戻しで基底変数の数が合わないとき: 修復した基底は 1 回目の LP の反復を大きく増やす (nu25-pr12 の 7e9f192、
   app1-1 の 1 スレッド)。`RESTORE_KEEP_CURRENT` は以前 40 問で悪化 (19 → 18 問) したので、修復のやり方を見直す。
3. app1-1: HiGHS の tableau の分離 (`HighsTableauSeparator`) の 2・3 ラウンド目のカットを書き出して (`HIGHS_CUT_DUMP` を tableau に
   広げる) こちらと比べる。
4. 16 スレッドの結果は 16 コアの計算機で確かめる (ここでは詰め込みなので時間はそのまま比べられない)。
