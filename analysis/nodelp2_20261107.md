# ノードの LP の重さ: HiGHS の動きを追って差の元を探す (2026-11-08、調査と試作 `ENOMOTO_MIP_NODELP2`)

bench に使う環境変数: `ENOMOTO_MIP_LOG=1 ENOMOTO_MIP_THREADS=4 ENOMOTO_T_MIP_SEED=s` (4 スレッド)。計数の回は `ENOMOTO_MIP_NODELP_DIAG=1`
(+ LP 1 回ごとの行 `ENOMOTO_MIP_HO4_DIAG=1`)。試作の回は `ENOMOTO_MIP_NODELP2=pbxg` (600 秒・58 問の `nl2`)。比べの設定は `run1.py` の `CFGS`。
HiGHS は highspy 1.15.1 (threads=4・mip_rel_gap=0、`hrun.py` の `CFGS`)。

生データ: `analysis/nodelp2_20261107/` (台本 `drive.py`・`run1.py` (ENOMOTO)・`hrun.py` (HiGHS)、結果 `e.jsonl`・`h.jsonl`、ログ `logs/`)。

## 結論 (先に)

- **ノードの LP の重さの差の元 (事実)**: HiGHS の MIP の側の部品 (強分枝・ヒューリスティクス・再スタート・木の分離・子の向き・打ち切り値) を止めたり
  ENOMOTO で HiGHS に合わせたりしても、1 回の反復の 3〜10 倍の差は出ない・消えない。差を動かすのは (1) **双対単体法の費用の摂動**
  (HiGHS は near optimal でない限り木の全部の LP で摂動する。ENOMOTO の既定は木の LP で摂動しない。ENOMOTO で入れると 1 回の反復 0.5〜0.6 倍)、
  (2) **基底を置き直した後の DSE 重み** (HiGHS は捨てて厳密な値を計算し直す。ENOMOTO は保存した重みを戻す。厳密にすると rococoC10 で 294 → 156 反復)、
  (3) **LP の行の数** (HiGHS は年齢の上限 10 → 100 で 1.2〜1.7 倍重くなる。ENOMOTO の LP は traininstance6・tr12-30 で行が HiGHS の 2 倍前後)。
  ENOMOTO の待ち行列のノードは潜りの子の 4〜5 倍重く、反復の 47〜78% を占めるが、出発の主実行不能の数 (保存した置き場所で 1/3 になる) は決め手でない。
- ノードの処理量で HiGHS に負けているのは 5 問中 ns1830653 だけ。supportcase33 は ENOMOTO が 10 倍のノードを解いており、差は木の大きさ (下界) の側。
- **試作 `ENOMOTO_MIP_NODELP2=pbxg`** (既定では使わない): 重い LP のスレッドで、木のノードの LP を摂動つきで解き (`p`)、基底を戻すとき保存した置き場所を渡し (`b`)、
  待ち行列のノードの最初の LP の重みを「保存した重み / 厳密な重み」のうち時間の移動平均の小さい方で選ぶ (`x`)。
  - 効き目: ns1830653 は 600 秒で 2 回とも最適 (482.5・524.5 秒。既定は 2 回とも時間切れ)。rococoC10・supportcase33 は揺れの範囲 (supportcase33 は少し悪い向き)。
  - 害: traininstance6・tr12-30 は 600 秒の下界が 2 回とも悪い。58 問 (60 秒・種 1・2) は SGM +0.9% (95% 区間 −1.5%〜+3.6%、p=0.52)、
    解けた数 84 対 84 (揺れの範囲)。時間切れの問題の最終ギャップは種 1 で悪い向き (p=0.010、2 回合わせると p=0.32)。
  - 誤答の検査: 58 問・600 秒の全部の回で下界と暫定解の矛盾 0 件。`mip_fuzz_vs_highs.py 300` 0 件。`fuzz_tiny.py 400 0` は既定・試作とも
    同じ 13 件 (以前から記録のある既知の件、analysis/wrongans_20261105.md)。木の大きい 10 問を判定なし (`pbxX`、重みを頻繁に入れ替え) で解き、
    10 問とも既定と同じ最適値。`cargo test --release --lib` 375 件通過。
- 次の一手 (推測を含む): (a) `g` の境 (平均 100 反復) を上げるか、待ち行列のノードの重さで判定して traininstance6・tr12-30 の害を消す
  (この 2 問は 120 秒の平均が 70〜110 で境の上下を行き来する)。(b) LP の行の数の差 (tr12-30 のカット 1600 行対 600 行、traininstance6 の前処理の
  後の行 4160 対 2314) は別の部品で、年齢の上限 (`ENOMOTO_T_MIP_CUT_AGE_*`) と前処理の側 (TREE2_FORCEQ が足す 2004 行の等式) を調べる。
  (c) 厳密な DSE 重みの計算 (行ごとの BTRAN) を速くすれば `x` の選ぶ範囲が広がる。

## 0. 方法の制約 (事実)

- 計装した HiGHS v1.15.1 のビルド (cmake) はこの環境で拒まれた (外のコードのビルド)。用意した計装 (`highs_nodelp2.patch`: 前回の
  `NLP` の行に、基底を戻したか (`rst`: 0 親の続き・1 兄弟/戻り・2 待ち行列 (前の潜りの最上位の基底)・3 待ち行列 (行が合わない古い基底)) を足し、
  `HIGHS_LPOPT` で MIP の LP の内側の Highs の設定を変える) は置いておくが、測っていない。HiGHS の数は highspy のログの終わりの表
  (ノード・LP の反復の内訳) と、オプションの切り替えと、ソースを読んだ事実に限る。
- highspy で `simplex_*`・`dual_simplex_cost_perturbation_multiplier` を変えても、MIP のノードの LP には届かない
  (`HighsLpRelaxation` の内側の `Highs` は既定の設定で作られ、MIP から渡すのは許容誤差と乱数の種だけ: `HighsLpRelaxation.cpp` の構築子)。
  だから HiGHS の双対単体法の部品 (摂動・DSE) を止めて比べることは highspy ではできない。

### 1.2 HiGHS のソースで確かめたこと (v1.15.1)

- ノードの LP の双対単体法は、出発点が「摂動なしで双対実行可能で、主実行不能が 1000 行未満かつ最大 1e-3 未満」(near optimal) のときだけ
  費用の摂動を省く (`HEkkDual::solve`)。分枝した子は境界が 0.1 以上動くので、木のほぼ全部の LP を摂動した費用で解く。摂動の量は列ごとに
  固定の乱数 (`numTotRandomValue`) で、`(1 + r)(|c_j| + 1) * 5e-7 * max|c|` (max|c| > 100 なら 4 乗根)。ENOMOTO の `perturb_costs` は同じ式。
- 待ち行列のノードは基底を持たない (`installNode` は `nodeBasis` を空にする)。潜りが終わったとき (`openNodesToQueue`) に、潜りの一番上の
  ノードの基底 (行の数が合えば) を LP に戻し、次に取り出したノードはその基底から解く。兄弟 (`backtrack`) は親の基底を、非基底の上限・下限の
  区別まで含めて戻す (`HighsBasis`)。
- 潜りの間は LP の行を消さない (`performAging(false)` は年齢を進めるだけ。消すのは分離のラウンドの `performAging(true)`)。兄弟に戻す基底は
  必ず行の数が合う。
- 強分枝は `Playground` で親の状態 (基底・重み) を保存して戻し、終わりに親の LP を 0 反復で解き直すので、子の LP の仕事を肩代わりしない。
- ノードの LP の反復の上限は max(10000, 10 x 平均, 1.5 x 最初の根の LP) で、反復を抑える仕組みではない。

  HiGHS の MIP の側の部品では、ENOMOTO との 3〜10 倍の差は出ない。差の元は LP の解き方 (双対単体法の部品) と LP の大きさの側にある (推測)。

## 3. ENOMOTO の側で HiGHS に寄せる (120 秒・種 1、`e.jsonl`、途中)

## 8. 厳密な DSE 重みの計算を効率的な実装にする (`ENOMOTO_DSE_EXACT_SPARSE`、既定で使う。`=0` で従来)

事実 (コード): `DseState::from_basis` (src/simplex.rs) は行ごとに密な単位 BTRAN (`solve_transpose_unit_into`: U^T 段を s0 から最後まで・
L^T 段を全部掃き、`scratch.fill(0)`) と、長さ m のノルムの和をしていた (m 回で O(m^2) 以上)。反復の中のピボット行の BTRAN が使う超疎の
単位 BTRAN (`solve_transpose_unit_work_sparse`・`UnitBtranWork`・`nonzero_rows`) を通っていなかった。`from_basis_stoppable`・`fill_missing`
(カットを足した直後の行の重みを埋める) も同じ形。HiGHS (`HEkk::computeDualSteepestEdgeWeight`) は超疎の BTRAN と非零の位置だけのノルム。

直したこと:
- 3 か所とも超疎の単位 BTRAN にし (`dse_exact_row_sparse`)、ノルムは非零の位置だけで足す (昇順に足すので値は密な版と同じ)。
- 反復の中の BTRAN は結果の非零率の移動平均が高いと超疎の経路を試さない。重みの計算は行ごとに独立で密度が大きく違うので、行ごとに 0 に戻して試す
  (`ENOMOTO_T_DSE_EXACT_KEEP_DENSITY=1` で反復の中と同じ判断)。最初の版はこれがなく、超疎の経路を通る割合が 0〜30% だった。
- 重みの計算の作業を LU の決定的演算量カウンタ (`synth_tick`、双対単体法の `CLOCK` 再分解トリガが読む) に残さない (`DseTickGuard`。
  `ENOMOTO_T_DSE_EXACT_TICKS=1` で残す)。密な従来の経路 (`=0`) は従来どおり数える。
- 診断: 計数つきの回の終わりに `MIP: dse-exact n .. secs .. ms/call .. rows/call .. max_rel_diff .. result_density .. hyper_frac ..`。
  `ENOMOTO_DSE_EXACT_SPARSE=check` で密な版と照合し、相対差の最大を出す。

## 10. 部分問題の LP の DSE 重みの初期化 (2026-11-09)

### 10.1 今の既定 (事実、`e.jsonl` の `diag` の `dse unit/inh/exact` の計数、120 秒)

木のノードの最初の LP は、ほとんどが前の LP から重みを引き継いで始まる (`inh`)。単位重みで始まる (`unit`) 回は次のとおり:

| 問題 | 潜りの子 | 兄弟 | 待ち行列 | 解き直し |
|---|---|---|---|---|
| tr12-30 | 49/29276 | 2/19071 | **2654/33756 (7.9%)** | 0/3727 |
| rococoC10-001000 | 65/7401 | 156/4572 | **426/4174 (10.2%)** | 22/4106 |
| traininstance6 | 19/13057 | 34/8390 | **256/2397 (10.7%)** | 10/9995 |
| supportcase33 | 0/6864 | 1/3436 | 118/1677 (7.0%) | 1/1771 |
| ns1830653 | 5/2474 | 10/1541 | 39/808 (4.8%) | 9/606 |

抜けは 2 種類あった (コードと計数で確かめた事実):
1. **待ち行列のノードの単位重みの回は、warm start そのものの失敗**。保存した基底を戻すと特異で、warm start をやめて全スラックの基底から解き直していた
   (tr12-30 のスレッド 0: 1832 回中 warm 1695、差の 137 回が単位重みの回と一致)。重みどころか基底も使えていない。
   特異な列だけスラックに替える既存の修復 (`ENOMOTO_SIMPLEX_WARM_SING_REPAIR`、根では遅くなる問題があり既定でない) を入れると 137 → 0 回。
2. **「引き継ぎ」に数えていた回も一部は単位重み**。保存した重みを戻すとき (`TwoStageLp::set_dse_vars`)、保存したときの基底になかった基底変数
   (戻した後に入った列・足したカットの行) の重みを 1 にしていた。tr12-30 では戻すたびに平均 72 行 (60 秒で 7333 回・52.7 万行)、rococoC10 で 64 行。

### 10.2 試作 `ENOMOTO_MIP_DSE_INIT` (既定では使わない)

- `m`: 重みのない基底変数を 1 でなく未知にし、求解の始めに厳密な値で埋める (`fill_missing`、8 節の超疎の計算)。
- `u`: warm start で重みが渡らなかった求解も、基底に構造列があれば厳密な重みから始める (HiGHS の `HEkkDual::solve` と同じ)。
- `r`: 木のノードの LP で、戻した基底が特異なら特異な列だけをスラックに替えて warm start する (`SingRepairScope`、根では使わない)。

60 秒・種 8 (`dse.jsonl`、`diag` 対 `di3` = `umr`、ノード / 暫定解 / 下界、スレッド 0 の待ち行列のノードの反復/LP・ms/LP):

## 11. MIP の中の効率の直し (9 節の洗い出しの続き、2026-11-09)

値を変えない直しは既定にした。それぞれ戻し方の環境変数を付けた (58 問の比べの `eff0` はこれを全部戻した形)。

| # | 直したこと | 戻し方 | 値 |
|---|---|---|---|
| 8 節 | 厳密な DSE 重み (`from_basis`・`from_basis_stoppable`・`fill_missing`) を超疎の単位 BTRAN に | `ENOMOTO_DSE_EXACT_SPARSE=0` | 密な版と相対差 0 (照合) |

直さなかったもの (理由):
- 2・7 (カットを消すと LU を捨てて分解し直す、行の出し入れごとに標準形を作り直す): 値を変えずに直すには LU から行と列を除く・行を足すときに
  LU を広げる (HiGHS の `kExtendInvertWhenAddingRows`) 実装が要る。既存の試作 `ENOMOTO_MIP_CUT_KEEP_LU` (外す時機をまとめる) は以前の 58 問の比べで
  +5.2% と悪かった (analysis/cbcimpl_20261029.md)。以前の計測 (mip_lp.rs の注記) では mik-250 の 40 秒のうち add_rows 0.9 秒・delete_rows 0.7 秒・
  再分解 0.1 秒未満で、残りの重さは小さい。
- 9 の `nb_hint` の行の活動度・被約費用: どちらも既にメモ化されていて、1 回の求解あたり O(非零) を 1 回。
- `trial_row_ratio` (反復が停滞したときだけの「最大改善」の試し BTRAN)・試作だけで通る所 (`degen_dual_fixing`・`optface_move`・`basis_start_info`・
  `dse_sample_deviation`): 既定ではほぼ通らない。

確かめ: `cargo test --release --lib` 375 件通過。`mip_fuzz_vs_highs.py 300` は既定・`DSE_INIT=umr` とも 0/300、`fuzz_tiny.py 400 0` は既知の 13/400 (同じ種)。
