# HILOSS: Mittelmann 600 秒で HiGHS に負ける問題の原因 (2026-11-11)

目的: Mittelmann の MIP ベンチマーク (186 問、600 秒・4 スレッド) で HiGHS に負けている問題ごとに、負けの主因を事実 (ログ・時刻・下界と暫定解) から
突き止め、何を直せば負けが減るかの順を出す。調査と診断が主で、**既定の動きは変えていない** (ソースの変更なし。足したのは台本と記録だけ)。

- ビルド: ブランチ ccr-1beed81b-ex0uhq の 794f7580 以降 (解く側のソースは cand1111 の計測と同じ既定)。HiGHS 1.15.1 (highspy)、`mip_rel_gap=0`。
- 生データ・台本: `analysis/hiloss_20261111/`
  - `losses.py` → `losses.txt`: 負けの一覧 (res9・HiGHS・cand1111 の Mittelmann の回から)。
  - `run.py`・`shards.json` → `res_s*.jsonl`・`logs/<問題>.<highs|ours>.log.gz`: 26 問を HiGHS と ENOMOTO (既定、種 1、`ENOMOTO_MIP_LOG=1`) で
    同じ機械で続けて 600 秒回した時刻つきのログ。csched008・net12・unitcal_7・physiciansched6-2 は分担 2 の push したログが 0 バイトだったので
    分担 0 の機械で取り直した (`res_s0.jsonl` の終わりの 8 行。この 4 問だけ `ENOMOTO_MIP_TREE4_TRACE=10` 付き)。
  - `summ.py` → `summ.txt`・`summ.json`: 2 つのソルバーの同じ量を並べる。`table.py` → `table.txt`: 1 問 1 行。`phases.py` → `phases.txt`: ENOMOTO の根の段の時系列。
  - `run2.py`・`shards2.json`〜`shards5.json` → `res2_s*`〜`res5_s*.jsonl`・`logs2/`: 既存の試作の環境変数を 1 つずつ足した切り分けの実験 (38 回)。`exp.py` → `exp.txt`、`mdtab.py` (この記録の表)。
- 注意 (読み方):
  - どれも種 1・1 回。分担の機械は res9 を取った機械よりやや遅く、HiGHS も uccase12・puriri・mcsched・traininstance6・net12 (取り直しの回) は
    600 秒で解けていない (res では 407〜488 秒)。「解けた/解けない」は境目の問題では回ごとに変わる。

    計 約 2.5 分) を回してしまった。csched008 の HiGHS の時間はその分遅い側にずれている (解けた・解けないは変わらない)。
  - 実験 (`exp.txt`) は既定の回と別の機械なので、時間の数 % の差は読まない。解けたかどうか・終わりの下界と暫定解・根の下界を見る。

    刈り込みには再スタート前の暫定解の打ち切り値が効いている (`prune_limit_of` の `cutoff`)。

## 3. 問題ごとの主因 (事実と証拠)

分類の記号: **P** 前処理で縮まない / **C** 根の下界が弱い (カット) / **R** 根で時間を失う (根のヒューリスティクス・サブ MIP・待ち・カットの LP) /
**F** 根の固定・再スタートで縮む量が小さい、木の中の再スタートがない / **H** 暫定解が遅い・出ない / **N** ノードの LP が重い /
**T** ノード数が多すぎる (分枝・木の下界) / **V** 揺れ (この回では負けていない)。
