対象: NETLIB `greenbea`(2392 行 x 5405 列, 30,877 非零)。HiGHS 1.x(`highspy`)、4 コア。
基点: `main` = f6a8409。前回分析: `analysis/greenbea_20260921_140700.md`(反復#9)、`_153000.md`(反復#11)、`_160000.md`(反復#12)。
全数値はこのセッションでこのコンテナ上で実測(本日のコンテナは前回より約 30-45% 遅い: HiGHS 0.30 s、main の greenbea 14.6 s。比率は変わらない)。計装・プロトタイプはすべて worktree(`f6a8409` + 環境変数ゲート、`CARGO_TARGET_DIR` 分離)で行い、**ゲート off でリポジトリの `.so` と反復数・全カウンタ・目的値がビット同一**であることを確認済み(§3.0)。**リポジトリ本体のソースは変更していない**(本ファイルの追加のみ)。推定で埋めた箇所はそう明記する。

## 0. 結論(要約)

1. **反復#9-#12 の「M 側スラッシング」「ratio=0 同点クラス(平均 84 本)」「iter 6650 の 22 本 M 側戻し」は、すべて 1 つの事故の症状だった。** 主ループは iter 0-6649 の間、双対実行可能性を厳密に保っている(固定列を除く非基底列の違反数 0、§2.2)。iter 6650 で chuzr が行 1270(偏差 base 6.0e4、slope 1.67e-7 = snap 閾値 1e-7 をわずかに超えた雑音)を選び、BFRT が slope を埋めるために |alpha| 7e-9..1.5e-8・ratio 1.1e15..1.6e15 の M 幅候補 22 本を通過し、q=482(alpha_q=-1.54e-8)を進入列に選ぶ。FTRAN 側の値は -9.7e-9(相対不一致 37%)なので `update_verify` がこのピボットを**破棄**し再分解する(`extended_dual.rs:2981`)。ところが **BFRT フリップ 24 本(有限幅 2 本 + M 幅 22 本)は verify より前の `:2836-2852` で `nb_status` に確定済みで、破棄時に巻き戻されない**。コメント(`:2918-2923`)は「フリップは独立した退化ステップなので巻き戻し不要」と主張するが、これは ratio=0 の候補にしか成り立たない。d_j = +2.45e7 の列を Upper(M 側)に置いたまま双対ステップが起きないので、**その瞬間 24 列が双対不能(最大 2.45e7、合計 2.37e8)になる**(§2.3、計装カウンタ `PROTO_DISCARD` で直接観測)。
2. 以後の経路は双対単体法の前提を失っている: 双対不能列は `hat_c = max(sigma d_j, 0) = 0` として ratio=0 の候補になり(反復#11 の「同点クラス」)、次の機会に一斉にフリップされる(M 側戻し 10,205 回の 92% が iter 6k-12k に集中、反復#11 §2.2)。違反数は iter 7000: 155(最大 6.8e3)、8000: 595、9000: 105、12,000: 1 と推移し **iter 12,500 で初めて 0 に戻る**。この間に実行不能行プールが 225 → 1,051 に爆発し、iter 12,500 時点でも 759 行(健全経路の同時点は ~200 行)。残り 15,000 反復はこの後始末。**時間換算: 主ループ 14.2 s のうち、健全経路(11,270 反復 x 同じ単価)なら 5.1 s で済む分を除いた約 9 s(65%)がこの事故の直接・間接コスト**(§2.4)。
3. **presolve 出力が少し変わるだけで、事故を踏むか・別の事故を踏むか・踏まないかが変わる(経路の宝くじ)**。同じ LP を 5 通りの妥当な presolve 結果で主ループに渡した結果(§3.1): parallelcols 無効 → 11,270 反復・正答・双対違反 0 回(5.1 s); main(133 本マージ)→ 27,654 反復・正答(14.6 s); コスト非零のマージ 35 本だけ抜く → 10,900 反復で **拡張双対が偽 `Infeasible` を直接返す**(同じ機序: iter 5799 で 25 本フリップ確定後に破棄、最大 1.0e5 の違反注入、最終 737 列違反、§3.2); 上限無限のマージを抜く → 171,200 反復バイアウト → BIG_M → 偽 infeasible(334 s); aggregator 無効 → 170,000 反復バイアウト → BIG_M → **`optimal` として相対誤差 2.0e-2 の誤答**(718 s)。
4. **プロトタイプ(worktree、§4)**: (a) 破棄時にフリップを巻き戻す `UNFLIP` → 双対違反は全 27k 反復で 0 になる(機序の裏付け)が、M 側解消が遅くなり最後に特異基底 → BIG_M 誤答。必要条件だが十分ではない。(b) HiGHS 型 `chooseFinalLargeAlpha`(Harris 窓の最大ピボットが 0.1·max|alpha| 未満なら比の小さい側へ群単位で遡る)→ main の presolve では 26k 回のドリフト再分解でバイアウト誤答、別 presolve では 5,451 反復で正答。(c) |alpha_q| < 1e-7 のピボット破棄 → 既存の verify 破棄 6 回と完全に一致し経路不変(破棄後の再試行は `update_count()==0` のため verify されず、次の極小ピボットがそのまま通る)。**局所パッチ 1 個では届かない**ことを再確認。
5. **3 分類: (b) 反復数**(27,654 vs HiGHS 2,524 = 11x; 事故なし経路 11,270 でも 4.5x)が主因、(c) 1 反復 445-520 us vs HiGHS ≤ 120 us が副因(refactor 20%、dse_update 14%、price 12%)、(a) presolve は 118 ms(0.8%)で非該当。原因分類: **数値的健全性(悪条件ピボット |alpha| 1e-9..1e-8 の受理)+ 正当性バグ(破棄時のフリップ非巻き戻し)**。退化・サイクリングではない(退化ピボット 0.2%)。初期基底の質(M 側 3,569 列)は「事故を起こしやすい土壌」であって主因ではない。
6. **本反復で安全に実装できる範囲の候補**は 2 つ(§6): (A) presolve 側のみ: `parallelcols` を既定 off(`ENOMOTO_DISABLE_PARALLELCOLS` の意味を反転)。93 問題全数で目的値一致、合計 86.0 → 75.5 s(-12%)、greenbea 14.4 → 5.2 s、pilot 5.5 → 2.7 s(main では特異基底 → BIG_M 経路だったものが拡張双対で正常終了)、退行 greenbeb +0.78 s(+31%)、pilot87 +0.87 s(+7%)。ソルバ本体に触れないので正答性リスクは presolve 前後の等価性のみ(無効化なので新規リスクなし)。ただし**機序の修正ではなく宝くじの引き直し**であり、モジュール自身の docs が「所有者の明示的指示で既定 on にした」と記録しているため、所有者判断が要る。(B) 本体側: 破棄時のフリップ巻き戻し + 相対ピボット下限 + 破棄後再試行の verify + 雑音 slope 行の扱い、をセットで設計する(§6.2 に関数・行番号付きの作業範囲)。単体では効かない(§4)ので 1 反復で安全に入れるのは無理。

## 8. 想定との食い違い(そのまま報告)

- 依頼文の「反復#9 で特定した主因 = M 側追跡の設計ギャップ」は、**より上流の具体的な事故(フリップ確定後のピボット破棄)の症状**だった。反復#9-#12 は事故後の状態(ratio=0 同点クラス、M 側戻し、雑音 slope)を分析していたので、局所パッチが全部壊れたのは当然で、設計ギャップの証明にはなっていない。ただし「事故を踏まなければ速い」(11,270 反復)とは言え、HiGHS の 2,524 反復に対しては 4.5 倍のままなので、M 側の解消コストという反復#9 の副次的な指摘自体は残る。
- 反復#12 §7 候補 3「極小ピボットの相対許容: 効果は数十反復」は過小評価だった。iter 6650 の 1 ピボット(破棄されたもの)が 16,000 反復分の差を作っている。一方、単純な下限(§4 MIN_PIVOT)では既存の verify と同じ 6 事象しか捕まらず、経路は変わらない。
- 「parallelcols 無効で 2.85 倍速い」は事実だが、機序を直した結果ではない。§3.1 の 5 変種で 3 つが誤答(うち 1 つは `optimal` として)になる問題で、presolve ノブの ON/OFF を「改善」と呼ぶかは判断が要る。
- 本日のコンテナは前回までより約 40% 遅い(main 10.06 → 14.6 s、HiGHS 0.23 → 0.30 s)。絶対時間は loop_state と直接比較しないこと。
