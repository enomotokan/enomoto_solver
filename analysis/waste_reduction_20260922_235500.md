# 不要な探索・データ構造の無駄の洗い出しと除去 — HiGHS 比較と NETLIB93 A/B

対象: `main` の `be5bbea`(PIVOT_SEARCH_LIMIT 8→256 のマージ直後)を基点に、
双対単体法の主ループ(`src/simplex/extended_dual.rs`)、LU(`src/simplex/lu.rs`)、
presolve(`src/presolve/*`)から「必要以上の探索」「データ構造の無駄」を
HiGHS(`HEkkDual*.cpp` / `HFactor.cpp` / `HighsSparseMatrix.cpp`)と読み比べて
できるだけ多く列挙し、実装して NETLIB93 全問で前後比較した記録。

採用基準: **各問題で 10% 以上の退行が無いこと**(3 周中央値で 10% 以上に
見えた問題は、交互 10 回 × 各 5 反復などで取り直して判定)。

## 0. 計測方法

- 4 コア、rustc 1.94.1、Python 3.11、highspy 1.15.1、NETLIB93 **全 93 問**。
- 各アームを `maturin develop --release` でビルドし、パッケージ一式を
  アームごとのディレクトリに固定コピー(計測中に再ビルドしない)。
- 1 問ごとに新しい Python プロセスを起こし、`benchmark_highs._build_our_model`
  →`model.solve()` の時間だけを計る(HiGHS の読み込みは計測外)。
  周ごと・問題ごとにアームの実行順を交互に入れ替え、**3 周の中央値**で比較。
- 10% 以上に見えた問題は、その問題だけ交互 8〜10 回 × プロセス内 3〜5 反復の
  最小値の中央値で取り直した。
- 正答性: 全 A/B で 93/93 optimal、各アーム間で status/目的関数値の不一致 0 件。
  `cargo test --release` 226 passed / 0 failed(debug ビルドの
  `orphaned_unbounded_column_with_zero_cost_is_cleaned_up_without_a_pivot` は
  グローバルカウンタ `CLEANUP_PIVOTS` を並列テストと共有する既存のレースで
  まれに落ちる。単独実行・再実行では通る。本変更とは無関係)。

## 1. プロファイル(基点)で見えたこと

`ENOMOTO_PROF_PHASES_EXT` / `ENOMOTO_PROF_PRESOLVE` / callgrind で基点を見ると:

- **presolve が 93 問合計 8.2s(求解時間合計 47.6s の 17%)**。うち
  `reduce_equalities` だけで 3.8s、maros-r7 単独で **3.15s**(HiGHS は maros-r7 を
  丸ごと 0.8s で解く)。callgrind では maros-r7 の冗長等式検出の命令数の
  **98% が `refresh_col`**(列最大値を列の全行について `BTreeMap::get` で毎回
  再計算)。
- 主ループでは dfl001 の `xb_update`(12.5%, 119µs/iter)・`dse_update`(12.2%)・
  `bfrt`(10.9%)・`price`(11.5%)が上位。`xb_update` は `alpha` の非ゼロ行ごとに
  `basis[i]` 経由で列添字の境界配列を引いて `row_deviation` を計算しており、
  CHUZR はさらに同じ `row_deviation` を感染行全部について毎反復計算し直していた。
- BFRT は M 傾きチャネルが全ゼロでも傾き用 FTRAN をもう 1 本解いていた
  (dfl001/fit2p 等で傾きが全ゼロのものが 91〜100%)。

## 2. 改善案の一覧と判定

凡例: **採用** / 不採用(計測で負け・効果なし)/ 未実施(理由付き)。
「経路」は反復数・再分解回数・目的関数値が基点とビット一致するか。

## 4. 所見

- 最大の単発の無駄は presolve の冗長等式検出(#34)だった。HiGHS はこの種の
  検出を 1 回の LU で済ませるが、こちらの BTreeMap ベースの消去自体は残し、
  「列最大値の全再走査」だけを増分化した。経路は完全に同一のまま maros-r7 が
  約 3 倍速になった。
- 主ループで効いたのは、HiGHS が「行添字の配列を持つ」「値を保持して再計算
  しない」形にしている箇所(#4, #5, #22)と、密になったら bookkeeping を
  やめる切替(#2)。逆に HiGHS の列方向 PRICE(#3)と LTO(#42)は負け/効果なし。
- 経路を変えたのは #22 だけ。それ以外はすべて反復数・再分解回数・目的関数値が
  基点とビット一致することを重い問題で確認している(A/B 全 93 問でも
  status/目的関数値の不一致は 0)。
