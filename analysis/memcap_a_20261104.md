# メモリの上限の試作 A: 実際の RSS を見て開いたノードの持ち物を捨てる `ENOMOTO_MIP_MEMCAP` (2026-11-04)

bench に使う環境変数: `ENOMOTO_MIP_MEMCAP=1` (試作。既定では使わない。段階の割合は `ENOMOTO_T_MIP_MEMCAP_FRAC` (既定 0.7)・
`ENOMOTO_T_MIP_MEMCAP_FRAC2` (0.8)・`ENOMOTO_T_MIP_MEMCAP_FRAC3` (0.9)、使えるメモリを決め打ちするなら `ENOMOTO_T_MIP_MEMCAP_MB`)

並列 3 セッションのうちの A (担当: 実際の RSS を見て、開いたノードの持ち物を捨てて上限を守らせる試作)。B は「目安に入らない持ち物」の
正体と MEM2 の b、C は supportcase18 の持ち主の特定。土台は ae1497cc (memall が既定) の後のブランチ (f2750cff〜)。4 スレッド、
この機械は 4 CPU・15.7 GB (このシェルの cgroup v1 の上限 14.34 GB)。生データは `analysis/memcap_a_20261104/`
(`long.jsonl`・`bench58.jsonl`・`summ58.txt`・`logs/`)。

## 要点

1. **既定で落ちた supportcase18 が落ちなくなった** (1200 秒。既定は 884 秒・13.6 GB でメモリ不足で殺される。試作は 564 秒で段階 1 に入り、
   以後 RSS 9.7〜9.9 GB で横ばい、時間切れで目的値 50・下界 47.19。600 秒の HiGHS は 49・2.0%)。
2. 既定は 1800 秒にすると CMS750_4 (約 1680 秒)・uccase12 (約 1200 秒) もメモリ不足で落ちる。試作の 1800 秒の CMS750_4 は落ちない (8.8 GB、
   ただしこの回は伸びが遅く段階 1 に入らなかった)。
   1200 秒では 4 問とも試作の **最大 RSS が 8.2〜10.0 GB で頭打ち** になった (既定 9.3〜13.6 GB で、radiationm40-10-02 以外は 1200 秒の時点でまだ伸びている)。
   CMS750_4 の既定は 1200 秒で 13.5 GB (落ちる手前)、uccase12 の既定は 11.6 GB で 2 分あたり約 0.8 GB 伸びている。
3. 結果への影響は小さい: CMS750_4・uccase12 は既定と同じ (同程度) の値、radiationm40-10-02 は試作の方が暫定解が良い (155382 vs 158565、1 回)。
   **どの問題でも段階 1 (DSE 重み → 基底を捨て、新しいノードに DSE 重みを保存しない) だけで止まり、段階 2・3 には入っていない**。
4. supportcase18 の増え方は開いたノードの基底・DSE 重み (主に共有の待ち行列の `SnapNode`) で、捨てると止まる (事実: 段階 1 の
   間に共有の待ち行列から基底を 1 スレッドあたり 15〜17 万ノード分捨て、その間 RSS が横ばい)。C の持ち主の特定の手がかり。
5. 58 問 1 回 (60 秒): 試作は **一度も段階 1 に入らず何もしていない**。SGM 18.12 → 17.62 秒、解けた数 44 → 44、食い違いなし (揺れの範囲)。
6. 使えるメモリの見積もりが控えめに出る: cgroup の使用量にページキャッシュが入るので、起動時の見積もりが 11.5〜13.6 GB (上限 14.34 GB)
   と回ごとに違い、段階 1 が 8.1〜9.5 GB で働いた。

## 試作の中身 (`ENOMOTO_MIP_MEMCAP`、`src/mip/solver.rs`・`src/mip/queue.rs`)

- 見張りのスレッド (`memcap_start`、最初のノードで 1 つ立てる) が `ENOMOTO_T_MIP_MEMCAP_SECS` (既定 0.5) 秒ごとに `/proc/self/statm` の RSS を
  読み、使えるメモリ (`memcap_limit`) に対する割合で段階 0〜3 を決めて原子変数 `MEMCAP_LEVEL` に書く。全スレッド (木のスレッドもサブ MIP も)
  がこの 1 つを見る。木の処理が大きな LP で止まっていても段階は更新される。
- 使えるメモリ: 最初に呼んだときの (cgroup の上限 − 使用量 と MemAvailable の小さい方) + 自分の RSS。cgroup は `/proc/self/cgroup` の
  memory の階層を読み、v1 は親をたどって上限の最小を取る (以前の `mem2_budget` は根の `/sys/fs/cgroup/memory` を読んでいて、この機械では
  上限なしになり MemAvailable だけで決まっていた)。
- 段階ごとの動き:

| 段階 | 割合 (RSS / 使えるメモリ) | 動き |
|---|---|---|
| 1 | > 0.7 | 新しいノードに DSE 重みを保存しない。RSS を読むたびに、各スレッドが自分の待ち行列の DSE 重みを深いノード (同じ深さなら下界の大きいもの) から 1/4 (`ENOMOTO_T_MIP_MEMCAP_STRIP`) 捨て、DSE 重みが残っていなければ基底を 1/4 捨てる。共有の待ち行列も同じく (1 回の読みで 1 スレッドだけ)。潜りの兄弟は捨てない |
| 2 | > 0.8 | 新しいノードに基底も保存しない。開いたノードの DSE 重み・基底を全部捨て、潜りの兄弟の LU を持たず、深さ優先に寄せる (`ENOMOTO_MIP_MEM2` の `d` と同じ: 潜りのノード数の上限と兄弟へ戻る下界の条件を外す) |
| 3 | > 0.9 | 求解を止める (`time_up` が真になり、時間切れとして暫定解を返す) |

- 基底・DSE 重みのないノードは今の仕組みで解ける (`ENOMOTO_MIP_MEM2` の `b` で使っていた経路。取り出したノードは今の LP の基底から解き直す)。
- 求解の終わりに `MIP: MEMCAP: tid … limit … peak rss … level-reads a/b/c first-at … s; strips … local dse … basis … pool dse … basis … siblu …`
  を標準エラーに出す (試作を使うときだけ。level-reads は段階 1・2・3 以上で読んだ回数、first-at は見張りを立ててから初めてその段階になった時刻、
  local/pool の数は持ち物を捨てたノードの数)。
- 既定の経路は変えていない (全て `memcap()` の内側。`cargo test --release --lib`: 332 通過、1 失敗 (`fix_tiny_width_columns_fixes_within_tolerance`、
  変更前のコードでも同じく落ちる。MEM3_TINY_MARGIN の既定化で期待値がずれたもの)、18 は無視の印)。
- 小さな上限での確かめ (`ENOMOTO_T_MIP_MEMCAP_MB`): uccase12 を 1500 MB で解くと、木の始めに段階 3 に入って止まり時間切れで返る。CMS750_4 を
  3000 MB で 300 秒解くと 195 秒で段階 1 に入り、以後 RSS 2.1 GB で横ばい (結果は 252/250 で既定と同じ)。

## 考え・次の手

- RSS そのものを見る形は、目安で数える MEM2 の `b` (上限 1.46 GB で RSS 4.95 GB) と違い、上限をちゃんと守る。今回の 4 問は段階 1 だけで
  足りた (開いたノードの基底・DSE 重みが伸びの主だった)。段階 2・3 は小さな上限で働くことだけ確かめた。
- 既定にするなら: (1) 使えるメモリの見積もりからページキャッシュを除く (cgroup v1 の `memory.stat` の `total_inactive_file` を使用量から引く、
  v2 は `inactive_file`)、(2) 58 問をもう 1〜2 回回す (害がないのは「何もしない」からで、見張りのスレッドの読みの手間は 0.5 秒に 1 回の
  ファイル読み)、(3) 段階 3 で止めるのが落ちるより良いかは、止まるまでの暫定解・下界を返せるので良いと考えるが、まだ一度も 段階 3 に
  入る長い計測をしていない。
- 段階 1 の間に新しいノードの DSE 重みを保存しないのは、探索の速さに効くかもしれない (どちらの向きにも)。1 回ずつなので分からない。

## 再現手順

```sh
pip install -q highspy==1.15.1 maturin
maturin build --release -o /tmp/whl && pip install -q --force-reinstall --no-deps /tmp/whl/*.whl
D=analysis/memcap_a_20261104
for p in radiationm40-10-02 uccase12 CMS750_4 supportcase18; do
  for c in memcap def; do python $D/run_long.py $c $p 1200; done
done
python $D/bench58.py def,memcap 0 && python $D/summ58.py > $D/summ58.txt
python $D/run_long.py def CMS750_4 1800; python $D/run_long.py memcap CMS750_4 1800; python $D/run_long.py def uccase12 1800
```

- `run_long.py` は 1 秒ごとに VmRSS を読み (最大 RSS)、10 秒ごとに推移を残す。標準エラーは `logs/<問題>_<設定>_<秒>.err`。`chain.sh`・`chain2.sh`
  は今回回した順。設定 `memcap` は `analysis/halve_submip_20261030/run.py` の CFGS にも足した。
