# 複数スレッド (主に 4 スレッド) に特有の改良 (2026-11-26、親の依頼)

- 1 スレッド: 240 問 0.981、解けた数 84 → 93

このため、4 スレッドに特有の伸びの悪さを診断し、改良を試作する。試作はどれも環境変数で切り替え、既定はオフ。

## 2. 原因の型と数字 (既存の記録とコードの読み、fhnw-binpack4-4 のログ)

既存の記録 (par4slow・parorder・parprof・parspeed・partree_race・share・sharecuts・rootpar・tree_parallel_profile・treeclose 9.60〜9.79) とコードを読んだ。共有の表は 3 節に置く。

型ごとの数字:
- **根の直列 (いちばん大きい)**
  - parspeed (b): 根の時間は 4T で 1.28 倍しか速くならない。全体に占める根の割合は 1T 29% → 4T 42%。
  - rootpar: 4 スレッドの根で使う CPU は平均約 2 本 (段ごとに pre 1.87・lp 2.22・cut 2.34・heur 1.95)。
  - 1.1 の nw04・physiciansched6-2・cod105・dano3_3・supportcase7 はこの型。
- **根の前の直列 (新しく見つけた)**: fhnw-binpack4-4 (目的が 0 の実行可能性問題、実行不能)。版 27a8f25eb、種 1、ログは logs/ (コミットしない)。

| 形 | 全体 | 木に入る時刻 | 早めの FJ・Local-MIP |
|---|---:|---:|---|
| 既定 1T | 67.6 秒 | | 手間の期限で 1.7 秒 (FJ 0.80 秒・Local-MIP 0.90 秒、手間では 20 秒) |
| c2c 1T | 14.9 秒 | 3.6 秒 | 同上 |
| 既定 4T | 35.4 秒 | | 壁時計の上限 20 秒を使い切る (4 本、見つからない) |
| c2c 4T | 25.1 秒 | 21.4 秒 | 同上 |

  - src/mip/mod.rs `feas_fj_lmip_early_from` は、手間の期限 (`ticks_on('f')`) を 1 本のときだけ使う (`tk_f = ticks_on('f') && threads == 1`)。2 本以上では壁時計の上限 (cap 20 秒) まで 4 本で回る。
  - 解のない (実行不能な) 問題では 18 秒が丸ごと無駄になる。
  - ただし ns1116954 (P の中で唯一の目的が 0 の問題) は 4T で 4.4〜5.1 秒 (1T は時間切れ) で、長い並列の探索が効く側。単に 1 本と同じ手間の期限にすると、こちらを壊すおそれがある。
- **重複探索・水増し**
  - 全体では 4T のノードは 1T の 0.785 倍 (parspeed) で、余分は少ない。
  - 問題によっては大きい: neos-1582420 21 倍、neos-911970 57〜86% が最終の暫定解で刈れるノード、sct2 4.6〜5.0 倍 (treeclose 9.75)。
  - treeclose 9.77 の見立てでは、共有の頻度を上げてもノードは減らない。元は探索の順と揺れ。
- **共有の抜け (コードで確かめた、未測)**
  - (a) 主 (tid 0) が木の中で作ったカットは、ほかのスレッドに流れない。条件は `!self.importing && self.snap.is_some()` (separation.rs `add_to_pool`) で、主は `snap` が None。取り込みは主もする。
  - (b) 従は始めに、写しの根のカットプールを `add_to_pool` で入れる。このとき `importing` が偽なので、根のプールを全部学習の記録 (20000 件の輪) に流し直す。根のプールが大きい問題 (kasai 9741 本) では、従 3 本で約 3 万件が入る。輪から押し出された証明・衝突・カットは、まだ読んでいないスレッドに届かない。
- **スレッドの遊び**: 平均 8.6%。木の短い問題で大きい (neos17 20〜33%、rout 17〜21%)。
- **メモリ・同期**: 小さい。同じ求解の 4 プロセスの同時実行で 0.977 倍、同期 0.3% (parspeed)。
- **c2c の部品が 4T で効きにくい**: nra の φ・f は各スレッドが自分の葉だけで数える (solver.rs `nra_leaves`、スレッドごと)。1 スレッドより少ないデータで判断する。neos-631710・neos-911970 の 4T の害は nra の部品。

## 3. スレッド間で共有するもの / しないもの (既定)

主 = tid 0 (根を解いたスレッド)、従 = 写し (`TreeSnapshot`) から始めるスレッド。

| 項目 | 共有 | 頻度・向き |
|---|---|---|
| 暫定解の値・打ち切り値 | する | 全スレッドから全スレッドへ。毎ノード読む |
| 暫定解のベクトル | 一部 | 従から主へだけ |
| 根のカット・カットプール | 主から従へ 1 回 | 写しで渡す |
| 木の中のカット | する (11-17 から既定) | **従のものだけ**流す。全スレッドが 64 ノードおきに取り込む |
| 衝突・双対証明 | する | 使われたら流す (証明は 3 回)。64 ノードおきに取り込む |
| 擬似コスト | する | 16 ノードおき、双方向 (記録ではっきり効いていた共有はこれだけ) |
| 含意・クリーク | 根の分だけ 1 回 | 木の中で見つけた含意は共有しない |
| 大域の固定・境界 | する | 64 ノードおき、双方向 |
| ノード | 共有の待ち行列 + 各スレッドの手元 | 32 ノードおきに質の釣り合い、空になったら共有から取る |
| 根の並列 | 一部 | 早めの FJ・Local-MIP、LP プロービングの窓、根の LP の同時実行、裏のカット、RENS の並列のサブ MIP など。CPU は平均 2 本 |
| 木の中の再スタート | 判定は主だけ | 主が判定したら従を止めて作り直す |
| ヒューリスティクス役 | あり | 4 スレッドで 1 本 (tid 3) |
| LP の基底 | 渡さない | 共有の待ち行列のノードに基底を付けない (GAP4=`rocn` の `n`) |
| nra の統計 (φ・f) | しない | スレッドごと |

試して取り下げた案 (繰り返さない): 証明の共有を止める・絞る、collect mode、racing、根の局所探索の同時実行、並列の強分岐、従を遅れて起こす、根のダイビングの同時実行、共有の待ち行列だけ、手元の上限、共有の頻度を上げる、釣り合わせなし、探索の順 (PARORD)、根の分離・RINS・プロービングの並列 (rootpar)。

## 4. 改良の候補 (見込みの大きい順)

1. **実行可能性問題の早めの探索の手間の期限を、2 本以上でも使う** (根の前の直列)。
   - 案: 各スレッドに 1 本のときと同じ手間の期限を置き、壁時計の上限は安全網にする。4 本なら手間の合計は 1 本の 4 倍になる。
   - 見込み: fhnw-binpack4-4 で 4T −18 秒 (25 → 約 7 秒)。目的が 0 の実行不能な問題はほかにもある (240 問の中で調べる)。
   - おそれ: ns1116954 は長い探索が効く。手間の期限の中で見つかるかを測る。
2. **主の木のカットも流す (共有の抜け (a))**。主が木の中で作ったカットがほかに届かない、のを直す。
   - 見込み: カットの共有は kasai・csched008 でノード 0.47 倍と効いた (treeclose 9.79)。主はノードの 1/4 を受け持つので、その分が届く。
3. **従が根のプールを流し直さない (共有の抜け (b))**。写しのプールを入れる間は `importing` を真にする。
   - 見込み: 輪から押し出される証明・衝突・カットが減る。根のプールの大きい問題 (kasai など) で効くはず。
4. nra の統計をスレッドで合わせる (c2c の部品の 4T の害)。nra の φ はスレッドごとに少ないデータで数える。neos-911970 の害は φ の上昇が元で、合わせても消えない見込みが強く、後回し。
5. 根の段の並列 (記録の未試行の案: カット選びの下見の 2 つの側を同時に解く、裏のカットを待つ所を後ろへずらす)。大きい仕事で、今回の試作の後に回す。

試作は 1〜3 を、`ENOMOTO_MIP_PAR4` の文字で切り替える (`f`・`m`・`r`、既定はオフ)。
