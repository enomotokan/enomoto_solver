## 結論 (先に)

1. **差の正体 (事実)**: HiGHS は mzzv11 で 4486 列を消し、うち 4133 列が 0 への固定、残りが代入。ENOMOTO (既定) が消すのは 1044 列で、
   すべて HiGHS も消す。HiGHS だけが 0 に固定した列 (3089 本) の標本 20 本のうち 14 本は「x=1 で LP 緩和が実行不能」(主の議論)、6 本は x=1 でも
   整数解がある (双対の議論、支配された列など)。主の 14 本は、行の伝播でも行から取り出したクリークの伝播でも矛盾が出ず、**プロービングで学んだ含意
   (x_j = v ⇒ x_k = w。HiGHS のクリーク表の 2 文字のクリーク) を伝播に使うと 14 本すべてで矛盾する** (Python で確かめた)。
2. **ENOMOTO で効かなかった理由 (事実)**: ENOMOTO のプロービングは含意を集めるが、(a) 既定では後の列の伝播に使わない (既存の試作 `ENOMOTO_MIP_GAP4=q` で使う)、

   約 240 万本あり、後ろの候補の含意が落ちていた。(a) だけ (`q`) でも (b) だけ (上限 50 倍) でも固定は 336 → 350 列で変わらず、両方で 1085〜1544 列。
   伝播 1 回の手間の上限 (20×(行+列)) で打ち切られた伝播は 0 回で、原因ではない。
3. **試作 `ENOMOTO_MIP_CLQPRB=1`** (既定では使わない): (a) 学んだ含意を後の列の伝播に使う、(b) 含意の上限を非零数の 40 倍・600 万本の小さい方にし、

## 1. HiGHS の前処理の流れ (mzzv11、`analysis/presolve2_20261111/hlog/mzzv11.log.gz`)

- 前処理 30 秒のうちほとんどが probing。probing は 6 回 (7191・2500・3837・5971・5712・5593 回の試し)。1 回目の後 7731 行・8065 列、3 回目の後 6327・6273、最後 5723・5754。
- HiGHS の `HPresolve::runProbing` (v1.15.1): 0-1 列を含意の数の多い順に試し、消した列が max(1000, (行+列)/20) を超えたら打ち切って前処理に戻り、
  また probing する (これが「繰り返し」)。`HighsImplications::computeImplications` は 0-1 列への含意を 2 文字のクリークとしてクリーク表に足し
  (`addClique`)、クリーク表は伝播にも使われる (`HighsDomain` がクリーク表で伝播する)。`processNewEdge` は (¬v1, v2) が既にクリークにあれば v2 を固定し、
  補の組もクリークなら代入 (同値な列) にする。`finaliseProbing` はクリークの統合 (行の持ち上げ)、固定の除去、代入をする。

## 9. puriri で clq だと解が出なくなる原因 (種 1 の 600 秒のログ `logs_D/neos-3216931-puriri.{def,clq,clqk}.s1.log.gz`)

- 事実: 既定の暫定解 81380 は、根の **locks のサブ MIP** (固定率 0.68、残り 1087 列、49 ノードでノードの上限、5.8 秒) が 390 秒に出したものだけ。
  clq では locks の固定率が 0.75 (残り 805 列) で、サブ MIP は **0 ノードで実行不能**。RENS・根の被約費用・clique・LP face のサブ MIP は両方とも実行不能。
- 潜り: fractional diving は既定で深さ 1・分数 812 で止まり、clq では深さ 360・分数 605 まで進む (vector length は既定で尽き、clq は深さ 21)。
  伝播の矛盾で早く止まる型 (型 3) ではない。根の LP の値は 58940 → 60403 と頂点が移る (型 2 の要素もあるが、決め手は locks)。
- 時間: clq では根のヒューリスティクスが遅い (実行可能性ポンプ 90 → 178 秒、潜り 3 種 133 → 242 秒)。locks に届くのが 384 → 567 秒。
- 小さな対策の試し `clqk` (= clq + 既存の試作 `ENOMOTO_MIP_GAP4=k`: locks の固定の伝播に含意も使い、根で実行不能なら固定率の目標を半分にしてやり直す。
  `res_D_s2.jsonl`): locks は固定率 0.65 で実行不能、0.34 でやり直しても 0.03 秒で解なし。600 秒で解なし。固定率を下げる型の対策では直らない。
- 推測: locks の丸める向き (錠の少ない側) 自体が、clq で締まった問題と合わない。既定でも locks 1 つに頼った当たり (hiloss の H の型) なので、ここで止める。

### クリーク表の設計案 (試作の前の見積り、推測を含む)

- 持ち方: クリーク = 文字の並び (行の集合詰め込みの部分はそのまま 1 つのクリーク、一般の行は HiGHS の `extractCliques` と同じく重みの大きい順の
  先頭の「どの 2 つも衝突する」部分をクリークに、残りの文字ごとに「その文字 + 先頭の衝突する部分」を足す)、含意の組は 2 文字のクリークの表
  (ハッシュ) のまま (まとめても縮まないため)。文字 → クリークの番号の索引。含まれるクリークは作るときに消す (行の重複・包含は extend_clique_rows と共通)。
- 問い合わせ: `adjacent(u, v)` は 2 文字の表を引き、なければ u と v のクリークの番号の短い方を走って相手の所属を調べる (HiGHS の `findCommonClique`。
  所属は文字ごとのクリークの番号の並びを二分探索)。`neighbors(u)` は使う側が多い (クリークのカットの貪欲、クリークの拡張) ので、大きなクリークを
  展開しない形 (クリークの番号と 2 文字の相手を別に返す) に使う側を直す。
- 使う側: (1) 伝播 (Domain の含意の伝播): 文字が真になったら、その文字のクリークごとに 1 度だけ相手を全部偽にする (HiGHS と同じ)。(2) クリークのカット
  (separation の `clique_graph_get` と `CliqueGraph::separate`): 重みの貪欲をクリーク単位で。(3) プロービング: 見つけた含意は 2 文字の表へ。
  (4) クリーク行の拡張 (`extend_clique_rows`)。(5) CLQACT の分割 (adjacent だけ)。
- 効き目の見込み: 集合分割の問題 (nw04・air03・eil33-2) で、行の衝突が全部表に入る (今は 99% 以上落ちる)。クリークのカット・プロービング・伝播に効く
  可能性。ほかの問題ではほぼ同じ (含意の組は縮まない)。
- 手間の見積り: 表の型と作り方・問い合わせ (約 300〜400 行) 1 日、使う側 5 か所の置き換えと既存の CliqueGraph との突き合わせの確かめ (同じ問題で
  同じ辺の集合になるか、上限のない範囲で) 1〜2 日、58 問・Mittelmann の計測 1 日。
