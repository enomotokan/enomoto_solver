# stocfor2 の前処理が HiGHS より効かない原因と対処 (2026-09-23)

原因特定・対処案の列挙は Fable サブエージェント、実装と検証は本セッション。
計測: base = `3d51b78`(main)、各案は env スイッチで切替えた同一ビルド。93 問すべてを問題ごと別プロセスで
アーム順シャッフルの交互実行、小問題はプロセス内反復 (約0.6s/サンプル)、5 周の**最小値**で比較
(中央値でも同傾向だが、この環境は小問題で ±15% のノイズがあるため)。
ノイズと実効果を分けるため、各案で前処理出力ハッシュ (`ENOMOTO_DEBUG_PRESOLVE_HASH`)・反復回数が
変わる問題を別途確定的に特定した。

## 原因 (Fable の計測)

- 差はすべて **aggregator (暗黙自由列の代入消去)** にある。HiGHS で Aggregator だけを切る
  (`presolve_rule_off=4096`) と 1768 行 × 1654 列になり、当方の 1766 × 1652 とほぼ一致する。
  強制行・双対固定・平行行列・sparsify・probing などは stocfor2 では効果ゼロ。
  HiGHS のルール別: doubleton 267、自由列代入 97、**aggregator 708** → 1052 × 976。当方の aggregator は 74 列。
- `aggregator.rs::eliminate_implied_free_columns` の 4 つのゲートが阻んでいた:
  1. `col_a_count >= 2`: 等式 1 行 + 不等式行に現れる列を棄却 (colsingleton も不等式行を数えるので棄却)。
     **生き残り 1652 列のうち 704 列がこの形**。
  2. 暗黙境界の根拠が等式行のみ (HiGHS `isImpliedFree` は不等式行も使う)。
  3. `propagate_equalities` が 2031 列中 1293 列の上界を箱に書き込むため、上側の暗黙性を等式 1 行で示す必要があった。
  4. fill-in 判定が総数 (HiGHS は正味 `新規 - (行長 + 列長 - 1)`、長さ 2 は免除)。

## 最終結果 (base vs 採用案すべて既定化)

- **stocfor2: 前処理後 1766 × 1652 → 1072 × 958** (HiGHS 1052 × 976)、反復 1648 → 626、
  **79.1 ms → 27.9 ms (−64.7%)**。
- 93 問合計 23.78s → 21.04s (**-11.5%**)。10% 以上改善 28 問、10% 以上退行 15 問。
  status・目的関数値の不一致 0/93。`cargo test --release --lib` 229 件、pytest 20 件通過。
- 前処理後サイズ (行+列) の 93 問合計: base 193,531 → 184,602 (HiGHS 188,686)。
- 10% 以上退行 15 問の内訳: boeing2・fit1d・fit2d・israel・maros-r7 は前処理出力が base と同一
  (ノイズまたは数 ms の前処理時間)。実際に変化したのは小問題で、forplan (反復 +17%)・grow22 (+11%)・
  share1b (+10%)・brandy (反復 +12%、前処理 5.9→15.8ms)・scagr25 (前処理周回増) など。いずれも絶対値は数 ms。
  brandy と scagr25 の前処理周回は今後の改善候補。
