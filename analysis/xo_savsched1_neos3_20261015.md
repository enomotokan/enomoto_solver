# Mittelmann savsched1・neos3 が HiGHS に負ける原因と対策 (クロスオーバー) (2026-10-15)

計測: 4 CPU・15 GB の Linux (クラウドのコンテナ)、`threads=4`、HiGHS との比較は利用者の計算機 (AMD Ryzen 16 論理 CPU、Windows) の値。
内点法の点は `ENOMOTO_DEBUG_XO_POINT_SAVE`/`_LOAD` (双対化しない問題でも使えるようにした) で保存し、クロスオーバーだけを繰り返した。
数値の詳細と表は `docs/crossover.md` の第 64 回。結果は `benchmarks/crossover/ab64/`。

## neos3 (512,209 行 × 6,624 列、前処理で変わらない)

構造: x ≥ 0、行は係数 ±1・右辺 0 の ≥ 行 (3 非零) が 51 万本と、6,480 非零・右辺 1e7 の等式 1 本。費用は 0/1。

| 段 (変更前、`ipm_crossover`) | 時刻 | 内容 |
|---|---|---|
| 内点法 | 55 秒 | 13 反復。設定 (記号分解) 26 秒 |
| 基底の選択 | 117 秒 (62 秒) | マッチングの順、消去 36.7 億回、nnz(L) 7,851 万 |
| 頂点の判定 | 123 秒 | 目的値 27777.777777778、L(y_ipm) 27777.777164 → 判定ギャップ 2.2e-8 > 1e-8 で不採用 |
| 双対の押し出し | 182 秒 | 候補 22.8 万、押し出し 7,382・飛ばし 22.0 万 |
| 仕上げ | 300 秒で打ち切り | |

1. **頂点が採られない** のは内点法の精度が足りないため。`ENOMOTO_DEBUG_IPM=1`: 12 反復目でギャップ 1.1e-10 (停止基準) に達し、
   高精度化の 1 反復目で正規方程式の求解の相対残差が 4.2e76 になり、その方向で歩いた点が NaN になって高精度化を打ち切っていた
   (終点の主目的値は最適値と相対 1.7e-8)。`ENOMOTO_T_IPM_SOLVE_ACC=1e-6` (相対残差が大きい方向を捨て、ρ・δ を 100 倍にして
   同じ点で解き直す) を高精度化の段だけに効かせると、ρ・δ = 1e-13 → 1e-11 → 1e-9 で解けてギャップ 5.5e-13、頂点の判定ギャップ
   1.1e-10 (主実行不能 1,574 の頂点は修復で 14 秒、後述の基底の選択の変更後はそのまま受理)。
   → 既定にした (`ENOMOTO_T_IPM_PUSH_SOLVE_ACC`、既定 1e-6)。
   - 効かなかった案: y の補正 (YFIX) は下界 −5.4e8、最適面への射影 (PROJ) は −9.3e6、頂点で内側にある基底のスラックの行の y を 0 に
     する案は −5.0e6 (13.3 万行。その行の y が小さくない)。行から導いた範囲 (IMPLIED) は効果なし。
   - 双対 LP (6,624 行) のままクロスオーバーする経路 (`ENOMOTO_T_XO_DUALIZE_MAX_COL_NNZ=1000`・`ENOMOTO_T_XO_DUALIZE_BACK=0`) は、
     内点法 37 秒・押し出し 52 秒 (超基底 14.2 万) だが、検出で丸めた分 (残差 2.9e-3) で頂点が主実行不能 4,018 本 (最大 10) になり、
     仕上げの双対単体法が 300 秒で終わらない。
2. **基底の選択が遅い** のは、マッチングの順 (最大の強連結成分 3 列) で三角に近いのに、どの候補にもマッチしなかった 22.8 万行の成分が
   消去のたびに L の列に残って積み上がるため。マッチしなかった行は最後に必ずスラックで埋まるので、そのスラックを先に入れる
   (`ENOMOTO_T_XO_LI_MATCH_SLACK_FIRST`、既定 1) と、消去 75 回・0.14 秒。

## savsched1 (前処理後 289,056 行 × 280,084 列、0/1 の上限、±1 の係数)

内点法 24 反復 26 秒で収束し、基底の選択は 0.2 秒、超基底 204,478 本の Megiddo 式の押し出しが終われば頂点はそのまま受理される
(判定ギャップ 5e-15)。押し出し (保存した点から、4 スレッド) は 658 秒: FTRAN 245、BTRAN 210、再分解 137 (437 回、うち照合で 143)、
ピボット 124,947・境界へ 79,531、FTRAN の平均非零 11,496。

1. **押し出す順** (`ENOMOTO_T_XO_MEGIDDO_ORDER`): 境界までの距離 / |s_j| の小さい順 (4) にすると、ピボット 11.4 万・境界へ 9.0 万・
   FTRAN の平均非零 4,768 で約 1.5 倍速い (IPX の順 = 大きい順 (3) は 15.7 万・14,155 で 1.4 倍遅い)。境界までの距離の小さい順 (1) も
   savsched1 では同じだが、neos-5251015 で列番号の順より遅い (押し出し 115 → 145 秒、4 は 105 秒)。→ 4 を既定にした。
   pilot.ja は 0.11 → 0.43 秒 (1 なら 0.09 秒)。
2. **照合の BTRAN**: 照合の行の値 `ρᵀ a_q` は `e_tilde · a_tilde` (`e_tilde = U^{-T} e_r` は FT 更新のために求める、`a_tilde = R L^{-1} a_q`
   は FTRAN の記録) に等しいので、BTRAN を `U^T` 段だけにした (`FtLu::solve_transpose_unit_e_tilde`、`ENOMOTO_T_XO_MEGIDDO_BTRAN_U`)。
   ピボットの列は従来と完全に同じで、BTRAN 120 → 9 秒、押し出し 357 → 239 秒 (順 1、2 本を同時に)。
   実装の注意 (`ENOMOTO_DEBUG_XO_TILDE=k` で照合の 2 通りの値を並べて確かめた): 超疎でない `U^T` 掃引の `touch` には同じ位置が
   重複して入るので写してから 0 に戻すこと、`a_tilde` の配列には記録の外に古い値が残るので記録した位置で内積を取ること
   (どちらも FT 更新の 1 万回目あたりから効いて、照合が誤って外れ再分解が増えた)。
3. FT 更新の上限 600・1200 は 239 → 251・330 秒 (FTRAN が重くなる)。300 のまま。

## neos-5251015 (順の変更で出た退行と対策)

押し出しの順を変えると auto で 152 秒 → 900 秒で時間切れになった。押し出しの後の基底は主・双対とも実行可能 (最適) だが、内点法が
同時実行の二段解法の下界で 4 反復で打ち切られていて y_ipm の下界が粗く (判定ギャップ 286) 受理されず、双対の押し出しが
基底を崩して仕上げが終わらなかった。頂点の判定で基底の双対 y_B も試す (`ENOMOTO_T_XO_ACCEPT_YB`、既定 1) と L(y_B) = 頂点の
目的値で受理し、121 秒。
