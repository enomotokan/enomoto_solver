# presolve と小問題の固定費 (P1〜P11, F2) の実装結果 (2026-09-23)

担当: "presolve"。対象はレポート `analysis/overall_inefficiency_20260923_064827.md` の §P と F2。
基点: `5ea112e` (= `/tmp/claude-0/venv_base` と同じ src)。ブランチ `worktree-agent-ad7e0d4a09b8219fa`。

## 採用基準と計測方法

- 採用基準 (ユーザー指定): 直前の採用済み状態との A/B で「10% 以上速くなる問題が 1 問以上」かつ
  「10% 超遅くなる問題なし」かつ「status・目的関数 (相対 1e-6) が全問で一致」。10% 未満の効果しか
  ない対処法は戻す。
- A/B: `scripts/ab_bench.py --rounds 3` (1 プロセスで最大 20 回 solve、中央値)。presolve だけに効く
  変更は solve < 60 ms の 66 問 ("light") に絞り、経路が全問に及ぶもの (P6) と最終確認は全 93 問。
- 各ビルドは `maturin develop` の出力 (`python/enomoto_solver/`) を `/tmp/claude-0/snap_ps_<tag>` に
  複製して専用 venv から読む (editable install は worktree を共有するため、比較中の再ビルドで
  片側が入れ替わるのを防ぐ)。
- 正しさ: `ENOMOTO_DEBUG_PRESOLVE_HASH` の縮約ハッシュと status/目的関数を全 93 問で比較。
- 1 ms 未満の問題 (afiro, sc50b, kb2, adlittle) は同一ビルド同士でもプロセスごとに ±20〜30% 振れる
  (プロセス単位の二峰性)。3 rounds で 10% 超の「退行」が出たものは `--rounds 9` で再計測して判定した。

  サイズで振り分ける `SplitAlloc` にした (`src/lib.rs`)。閾値 16 KiB では degen3 +17% が残り、

## 補足

- P1 で `ColPivQr::new` を使わなくなったので、密経路 24 問で rayon のグローバルプールが作られない
  (新プロセス初回の ~0.5 ms とスレッド 4 本の生成が消える)。faer の他の呼び出し (`simplex::lu` の
  密 LU、`interior_point::kkt`) はグローバル並列度のまま (担当外なので `set_global_parallelism` は
  使っていない)。
- 作業開始時、worktree のブランチは基点より古い `1eb4b1e` から作られていたため、基点 `5ea112e`
  (レポートと `scripts/ab_bench.py` を含む) へ fast-forward してから作業した。
