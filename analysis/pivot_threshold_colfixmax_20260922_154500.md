# ピボット安定性床の動的化 と `colFixMax` のインクリメンタル化(`docs/lu_comparison_enomoto_vs_highs.md` §2.4)

対象: §2.4 が挙げる 2 点 —「安定性床 `STABILITY` が固定」「`col_max_abs` を
`refresh_column` が毎回全列再計算」。基点 `main` = 6c8edce(§2.5 searchLimit=8 と
§3.1 `KernelMatrix` フラット化のマージ後)。4 コア、rustc 1.94.1、highspy
(Python 3.11)、NETLIB93 全 93 問題、各アーム 3 回(問題ごとに中央値を取る)。
最終構成の確認のみ、環境ドリフトのため基点と交互に取り直した(§5)。

## 0. 結論

1. **どちらも不採用**。実装して計測した結果、両方とも退行だった。既定の挙動は
   基点と完全に同一に戻してある。
2. **安定性床の動的化(HiGHS `info_.factor_pivot_threshold` 相当)は +7.4%**。
   10% 以上の退行が 3 問題(`pilot87` +29.2%、`brandy` +67%、`gfrd-pnc` +12.3%)
   出たため、採用基準を満たさない。機構自体は残し、既定で無効
   (`PIVOT_ESCALATION_STEP = 0`、`ENOMOTO_PIVOT_ESCALATION_STEP` で再有効化)。
3. **`colFixMax` のインクリメンタル化は +2.8%**。10% 超の退行は無いが、
   **ピボット選択が基点とビット単位で同一**(§2.1)なアームで一貫して遅い —
   つまり差分はまるごと実装オーバーヘッド。巻き戻した。
4. **(3) が負けた理由は §2.5 が先に入ったから**。`PIVOT_SEARCH_LIMIT = 8` が
   1 回の探索を 8 候補列に抑えているので、`ensure_col_max_abs` の再走査は
   もともと少ない。削れる再走査(`pilot87` で 150 万エントリ)より、マージ
   ループに足す per-entry 更新(同 6150 万回)の方が 30 倍以上重い(§2.2)。
5. HiGHS との差として §2.4 が指摘していた「`refresh_column` が BTreeSet 全走査」
   という前提は、この時点では既に古い。`col_max_abs_dirty` による遅延再計算
   (既存)と §2.5 の探索打ち切りで、再走査は既に実測 1 問あたり数百万エントリ
   —— 全体の 1% 未満の時間 —— まで落ちていた。

## 1. 実装したもの

### 1.1 安定性床の動的化

HiGHS は `pivot_threshold`(既定 0.1、`kMinPivotThreshold=8e-4` 〜
`kMaxPivotThreshold=0.5`)を可変にし、数値的失敗のたびに
`kPivotThresholdChangeFactor=5.0` 倍して上げる。本実装も同じ向き(**きつくする**):

- 閾値はスレッドローカル。分解ごとに 1 回だけ読む(`MarkowitzState::new` と
  `factorize_reusing_order`)。解の入口(`solve_lp_dual_extended`、
  `try_initial_refactorize`)で `reset_pivot_threshold()`。
- 開始値 `STABILITY = 0.25`、上限 `0.5`、倍率 `2.0`(= 1 段で上限)。
- 上昇条件: 「数値的原因の再分解」が `PIVOT_ESCALATION_STEP` 回たまるごと。
  数えるのは FT 更新の棄却・`x_B(M)` ドリフト・`d` ドリフト・PRICE との
  ピボット不一致の 4 つ。コスト起因(eta-bump fill、`ft_max_updates`、
  決定論的 CLOCK)は数えない —— これらは条件の良い問題でも定期的に発火する
  ので、数えると `dfl001` の 100 回の再分解がそのまま閾値上昇になる。

向きについて: §2.4 の本文は「悪条件時に**緩める**」と書いているが、実装は
HiGHS と同じく**きつくする**側にした。緩める側は `STABILITY` 自身のドキュメントが
既に測っている(0.1 では `pilot` のドリフト起因再分解が 88 → 190 回に増え、
その問題だけで実時間が約 2 倍)。

### 1.2 `col_max_abs` のインクリメンタル更新(`colFixMax` 相当)

変更前: `eliminate` が触れた列を `refresh_column` が無条件に dirty とし、
`find_best_pivot` が読む直前に `ensure_col_max_abs` が列全体を再走査する。

変更後: `eliminate` のマージループ内で、書き込む各エントリについて

- 充填(fill-in)や絶対値が増えた更新 → `col_max_abs[j]` をその場で引き上げる
  (最大値は上がる方向にしか動かないので再走査不要)
- 絶対値が減った更新・消滅した更新・ピボット行の退役による削除 →
  失われた値が現在の最大値以上のときだけ dirty

とする。`max` は丸めを伴わないので、clean な列の値は全再走査の結果と
ビット単位で一致する(§2.1 で実測検証)。

## 2. `colFixMax` インクリメンタル化の計測

### 2.1 挙動が同一であることの確認

- 実装時に `ENOMOTO_VERIFY_COL_MAX=1`(clean な列も毎回再走査して
  インクリメンタル値と `assert_eq!`)を用意し、Netlib 10 問題
  (`pilot` `greenbea` `25fv47` `fit1p` `maros` `bnl1` `perold` `degen3`
  `d2q06c` `fit2p`)で完走を確認。1 件も不一致なし。
- したがって A/B の差は実装コストのみで、ピボット列の違いではない。

### 2.2 なぜ負けたか(削れる仕事 vs 足す仕事)

`ENOMOTO_PROF_PHASES_EXT` の新カウンタで両方を直接数えた。

| 問題 | 再走査エントリ(変更前) | 再走査エントリ(変更後) | 変更後が払う per-entry 更新 |
|---|---|---|---|
| `dfl001`  | 1,587,065 | 1,234,958 | 9,818,596 |
| `pilot87` | 3,388,101 | 1,873,731 | 61,540,229 |
| `pilot`   |   569,337 |   314,459 | 5,926,249 |

削減できた再走査は `pilot87` で 150 万エントリ。その代わりにマージループへ
6150 万回の「`m` 長配列への散在 read-modify-write」を足している。30〜40 倍の
負け。dirty 率自体は狙いどおり下がっていた(触れた列の 0.1〜6% だけが stale)
が、**分母が最初から小さかった**。

理由は §2.5 の `PIVOT_SEARCH_LIMIT = 8`:`ensure_col_max_abs` は
`find_best_pivot` が実際に見る候補列でしか呼ばれず、その候補列は 1 ステップ
あたり最大 8 列に抑えられている(実測の平均走査幅は `dfl001` 5.58 列/ステップ、
`pilot87` 4.20 列/ステップ)。§2.4 が前提にしていた「毎回全列を再計算」は
この時点では既に成り立っていない。

### 2.3 NETLIB93 全体

`ENOMOTO_PIVOT_ESCALATION_STEP=0`(= 閾値の動的化だけ無効化、colFixMax のみ有効)

- 合計 40.7645s → 41.8894s(**+2.76%**)
- 重い 10 問: 36.5868s → 37.6803s(+2.99%)
- 残り 83 問: 4.1777s → 4.2090s(+0.75%)
- 10% 以上の退行: 0 件(10ms 未満の問題を除く)。ただし 3 回とも
  40.7s 台 → 41.9s 台で、ばらつきでは説明がつかない。

## 3. 安定性床の動的化の計測

`PIVOT_ESCALATION_STEP = 10`(`XB_DRIFT_ESCALATION_STEP` と同じ段幅)で計測。

- 合計 40.7645s → 43.7825s(**+7.40%**)
- 重い 10 問: 36.5868s → 39.6106s(+8.26%)
- 残り 83 問: 4.1777s → 4.1719s(-0.14%)

10% 以上の退行(3 回分の中央値、10ms 未満を除く):

| 問題 | 変更前 | 変更後 | 比 | 3 回の生値(変更後) |
|---|---|---|---|---|
| `pilot87`  | 6.5023s | 8.4042s | **1.292x** | 8.3599 / 8.4268 / 8.4042 |
| `brandy`   | 0.0086s | 0.0144s | **1.673x** | 0.0163 / 0.0144 / 0.0087 |
| `gfrd-pnc` | 0.0133s | 0.0150s | **1.123x** | 0.0150 / 0.0134 / 0.0159 |

`pilot87` は 3 回とも 8.3s 超で、これは測定ばらつきではない。`dfl001` も
+5.7%(17.44s → 18.44s)。

原因は単純で、**上がった先の 0.5 が重い問題にとって高すぎる**。`STABILITY` 自身の
ドキュメントが既に「静的な 0.5 は `d2q06c`/`greenbeb`/`fit2p` で充填増により
約 4% 遅い」と記録しており、今回はその 0.5 が**重い問題ほど当たる**。
`x_B(M)` ドリフト起因の再分解だけで 10 回に達する問題が多いため
(`pilot` 21 回、`dfl001` 24 回、`greenbea` 22 回、`d2q06c` 22 回)、
「病的な解にだけ効く安全弁」のつもりが「重い解には必ず発火するスイッチ」に
なっていた。

段幅を上げて発火条件を厳しくする案は、NETLIB93 ではどの問題でも発火しなく
なるだけで改善にはならない(発火しない = 基点と同一)。よって「再調整して
採用」ではなく「既定で無効・機構は温存」とした。

## 4. 最終状態

- `col_max_abs` の扱いは基点に戻した(`refresh_column` が dirty を立て、
  `ensure_col_max_abs` が遅延再走査)。`eliminate` の最内ループも基点と同じ。
- 閾値の配管は残す。既定では `pivot_threshold()` は `STABILITY = 0.25` を
  返し続け、`escalate_pivot_threshold` はどこからも呼ばれない
  (`PIVOT_ESCALATION_STEP = 0`)。したがって**既定ビルドの挙動は基点と同一**。
  - `ENOMOTO_PIVOT_THRESHOLD` — 開始値の上書き(`STABILITY` 自身の A/B が
    リビルド無しで取れる。`PIVOT_SEARCH_LIMIT` の `ENOMOTO_PIVOT_SEARCH_LIMIT`
    と同じ意図)
  - `ENOMOTO_PIVOT_ESCALATION_STEP` — 動的化の再有効化(今回の計測の再現)
- 計測用カウンタ `PROF_COLMAX_RESCAN_ENTRIES` / `PROF_PIVOT_ESCALATIONS` を
  `ENOMOTO_PROF_PHASES_EXT` の出力に追加。§2.2 の「削れる仕事の大きさ」は
  これが無いと測れない。触れた列を数える側(実装中は
  `PROF_COLMAX_TOUCHES` / `PROF_COLMAX_DIRTIED`)は、最内ループまたは
  `refresh_column` に計数を足すことになるので残さない —— 実際、
  `refresh_column` での計数(1 列あたり 1 回)を残したビルドは最終計測で
  +0.34%、外したビルドは交互計測で +0.59% と、どちらもばらつきの範囲だが、
  計測のために計測対象を重くする理由が無い。
- 最終構成での NETLIB93 再計測(3 回)で基点と同等であることを確認(§5)。

## 5. 最終構成の再計測

前半(§2.3/§3)の 3 アームは連続した時間帯に取っており、比較可能:

| アーム | 合計 | 対基点 | 10% 以上の退行 |
|---|---|---|---|
| 基点(6c8edce) | 40.7645s | — | — |
| §2.4 全体(閾値動的化 + colFixMax) | 43.7825s | +7.40% | 3 件 |
| colFixMax のみ | 41.8894s | +2.76% | 0 件(ただし 3 回とも一貫して遅い) |

最終構成(両方不採用・配管のみ)の確認では、**セッション中にマシン自体が
遅くなる方向にドリフトした**ことが判明した。最終アームの 3 回が
40.98 / 41.72 / 42.54s と単調に増加し、同じバイナリの反復とは思えない
広がりになった(前半の基点は 40.66 / 40.84 / 40.88s と安定していた)。
`analysis/btran_l_transpose_20260922_113000.md` §5 が記録している
「この環境では 10〜20% の振れが日常的に出る」の、合計値版。

そこで最終構成は**基点と交互に**(基点 → 最終 → 基点 → 最終 → 基点 → 最終)
取り直した:

| 組 | 基点 | 最終 |
|---|---|---|
| 1 | 41.4595s | 41.1091s |
| 2 | 40.9816s | 41.0302s |
| 3 | 41.1779s | 41.9809s |

問題ごとの中央値で集計して **基点 41.0041s / 最終 41.2440s (+0.59%)**、
10ms 以上の問題で 10% 以上の退行は **0 件**(10ms 未満の `lotfi` / `vtp.base`
/ `sc50a` が 1.10x 台に出るが、いずれも 3 回のうち 1 回だけ跳ねた値であり、
中央値の分母が 1〜7ms しかない)。既定ビルドの挙動が基点と同一であることと
整合する範囲。

**計測手順の教訓**: 1% 前後の差を主張するアームは、基点と交互に取ること。
別々の時間帯に取った 3 回の平均/中央値は、このマシンでは 1〜2% 単位で
系統的にずれうる。

## 6. 学び

- **後から入った最適化が、先に提案されていた最適化の前提を消すことがある。**
  §2.4 の「毎回全列再計算」という問題設定は §2.5 の探索打ち切りが入った
  時点でほぼ無効になっていた。比較ドキュメントの項目は、着手前に「その前提が
  今も成り立つか」を計測で確かめる必要がある。
- **「挙動が変わらない最適化」でも必ず計測する。** 今回の colFixMax は
  ピボット選択がビット単位で同一なので正しさの議論は不要だったが、
  それと速いことは別問題だった。
- 1 反復あたりのコストを下げる変更は、最内ループに散在アクセスを足した時点で
  負けうる。`dirty 率 0.1%` のような「狙いどおりの指標」は、分母を測るまでは
  改善の証拠にならない。
