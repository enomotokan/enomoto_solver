# greenbea 実行時間分析(自己改善ループ 反復#9, runtime 段) -- 398aed9 の「悪化」は snap(変更3)が誤答経路を正答経路に置き換えた結果であり、真因は拡張双対の M 側スラッシングと数値的脆弱性

対象: NETLIB `greenbea`(2392 行 x 5405 列, 30,877 非零)。HiGHS 1.x(`highspy`)、4 コア。
基点: `main` = 9fdb168(直前 3873b18)。比較対象: 398aed9 とその親 cb42295、および反復#7 の基点 418e62a。
全数値はこのセッションでこのコンテナ上で実測。**worktree ごとに `CARGO_TARGET_DIR` を分け、`PYTHONPATH=<worktree>/python` で `_core` の .so を切り替え、各実行で `_core.__file__` を出力して取り違えがないことを確認した**(§7)。推定は明記する。

## 0. 結論(要約)

1. **398aed9 の 4 変更のうち greenbea の実行時間を変えたのは変更3(`x_B(M)` slope の |slope|<1e-7 丸め = `snap_slope`)だけ**。ただし「5.4 s → 10.5 s の悪化」ではなく、**「誤答を返す 5.4 s の経路」を「正答を返す 10.5 s の経路」に置き換えた**のが実態である。
   - cb42295(398aed9 直前)は拡張双対が iter 6000 付近から `infeasible_rows=425 / remaining_m_side=1123` のまま動かなくなり(サイクリング)、約 12,000 反復で特異基底 → `refactorize` が `None` → **BIG_M 古典経路にフォールバック**して 5.35 s で `optimal` を返すが、**目的値は 9939528.77(HiGHS -72555248.13 と不一致、相対誤差 1.1)**。この環境では公式コマンド(`benchmark_highs --only greenbea`)でも同じ(§1.1)。依頼文の「cb42295 でも目的値一致」は再現しない。
   - 398aed9 で snap を無効化した変種(`c398_both`: snap 無効 + Bland ソート旧)は cb42295 と同じ経路(特異基底 → BIG_M、5.36-5.54 s)で、目的値 -72465273.017(相対誤差 1.2e-3、やはり不一致)。9939528.77 との差は変更1(postsolve 単一ログ化)による BIG_M 経路の x 復元の違いで、変更1は拡張双対経路のカウンタ・目的値には全く影響しない。
   - main(snap 有効)は拡張双対で 27,654 反復かけて正答(-72555248.12984608、相対誤差 2.9e-15)に到達し 10.2-10.7 s。
2. **変更2(Bland CHUZC の (ratio,j) 順)は snap 有効時には無関係**: main で `bland_mode` は一度も立たない(`main_loop_iters=27653 bland_mode=false`)ため、`c398_blandj`(snap 有効 + j 単独ソート)は main と反復数・再分解回数・目的値がビット同一。snap 無効時にのみ効き、j 単独ソートだと約 12k 反復で特異基底 → BIG_M(5.4 s)、(ratio,j) 順だと特異基底を避けて `max_iters=168,620` まで走って BIG_M(51-54 s)になる(どちらも誤答)。
3. **変更1(postsolve ログ統合)・変更4(診断チェックの固定列除外)は実行時間に無関係**: 変更1は postsolve 一回分(presolve 全体で 84 ms、2.3%)、変更4は `ENOMOTO_DEBUG_EXT_DUAL_CHECK` でゲートされた診断コードのみ(同コミットで追加された `prev_dbg = Some((a_p.clone(), ..))` も同じゲート内、`extended_dual.rs:2860-2866`)。
4. **本当の問題は 398aed9 より前に入っている**。反復#7 の基点 418e62a では拡張双対が 6,602 反復・2.0 s で正答していた。7baad18(presolve に aggregator/parallelcols/foldfixed/dualpropagate 列固定を追加、MAX_ITERS をサイズ依存化)で拡張双対が受け取る問題が変わり(M フラグ列 3,715 → 3,569)、同じ問題で **7baad18 は 4,499 反復で偽 `infeasible`**、57546db/cb42295 は上記のサイクリング → 特異基底 → BIG_M 誤答、398aed9 の snap でようやく正答に戻ったが反復数は 4.2 倍(6,602 → 27,654)のまま。
5. **分類: (b) 反復数が多い(HiGHS 2,524 の 11 倍、418e62a の 4.2 倍)が主因、(c) 1 反復が重い(360 us vs HiGHS 88-147 us)が副因、presolve 不足ではない。** 性質としては「退化・サイクリング」ではなく(退化ピボット 0.2%、最終経路の `stall_count=0`)、**「初期基底の質 = M 側に置かれた 3,569 列の解消が BFRT フリップで何度も巻き戻される(M 側スラッシング)」+「悪条件(FT 更新の x_B 残差が 5 反復以内に 1e-4 を超え、再分解 241 回 = 壁時計の 22.7%)」**の複合。snap 閾値 1e-7 は感度スイープ上の孤立点(1e-9/1e-6 → 偽 infeasible、1e-8/1e-4 → 168k 反復バイアウト、1e-5 → 特異基底、§4)で、堅牢な修正ではない。
6. 改善候補(§6): 優先度順に (1) BIG_M フォールバックが `optimal` を返す安全策(正答性)、(2) M 側列の扱いを HiGHS 型の双対フェーズ1(人工上下限)に寄せて M 側スラッシングを止める(反復数 4-11 倍の削減余地、上限 90%)、(3) 再分解 22.7% の削減(ドリフト閾値ではなく再分解単価 9.4 ms/回の削減)、(4) snap を「格納値の書き換え」から「比較時の許容」へ移す(経路依存性の緩和、要 93 問題検証)。

### 1.5 snap がサイクリングを止める機序(コード)

- `Affine1::cmp_lex`(`extended_dual.rs:706-720`)は `(slope, base)` の辞書式比較で、slope の許容は相対 1e-9(スケール下限 1.0)。LU/FT 更新の丸め由来の |slope| ~ 1e-8..1e-7 は「本物の slope」として base の優劣を上書きする(`row_deviation`, `extended_dual.rs:1096-1130`)。
- cb42295 のトレース(`ENOMOTO_DEBUG_EXT_TRACE=1`)は iter 6000-10000+ で `infeasible_rows=425 / remaining_m_side=1123` が固定 = 2 変数交互ピボット(コミットメッセージの記述と整合)。その後 `refactorize` が特異(`extended_dual.rs:953`)→ `None` → `simplex.rs:3042` 以降の BIG_M 古典経路。
- `snap_slope`(`extended_dual.rs:651-668`)は格納値 `x_b_slope` 自体を |v|<1e-7 で 0 に書き換える(呼び出し: 1730, 2547, 2694, 2824, 3015, 3102, 3107, 3432)。これで雑音 slope が比較に効かなくなり交互ピボットは止まるが、**格納値を書き換えるので `residual_norm_affine` の slope 残差(§1.3 で median 3.2e-7)にも、後続の増分更新にも影響し、経路全体が閾値に依存する**(§4)。

## 6. 改善候補(優先順、効果見積もりとリスク)

1. **BIG_M フォールバックの安全策(正答性、最優先)**: 拡張双対が `None` を返して BIG_M 古典経路に落ちたとき、BIG_M クランプが有効な列(`|x_j|` が `BIG_M/dj` 近傍)が最終解に残っていれば `optimal` を返さない、あるいは拡張双対を別の初期基底で再試行する。効果: 実行時間ではなく「5.4 s で誤答」を防ぐ。リスク: 低(返す状態が変わるだけ)。場所: `src/simplex.rs:3042-3070` と `simplex.rs:1086-1140`(クランプ)。
2. **M 側 3,569 列の解消を M 追跡から双対フェーズ1へ**: HiGHS 型(人工上下限 ±1 の箱で通常反復、`z1=0` でフェーズ2、`docs/highs_dual_simplex.tex` §フェーズ1)か、少なくとも BFRT が列を M 側へ**戻す**フリップ(`m_enter_via_flip`、`extended_dual.rs:2842-2849` で計数)を候補から外す/コストを付ける。効果見積もり: 反復数の主因なので上限は主ループ 93% x (1 - 6,602/27,654) ≈ **最大 70%**、HiGHS 並み(2.5k)なら 85%。リスク: 高(拡張双対のコア、全 93 問題の経路が変わる)。設計判断が必要なので本反復では提示のみ。
3. **再分解単価の削減(22.7%)**: 9.4 ms/回 x 241。ドリフト閾値を緩める案は §4 の通り経路を壊す(1e-4 で 168k 反復)ので不可。単価側(`refactorize` の Markowitz、`compute_rhs_affine` + 2 solve + `rebuild` + `fresh_d_into` の再同期を「ドリフトした行だけ」に絞る等)なら経路を変えずに済む。効果: 上限 22.7%、現実的には 5-10%。リスク: 低-中(反復#7 §6 の候補と同じ)。
4. **snap を格納値の書き換えから比較時の許容へ**: `cmp_lex` の slope 許容を相対 1e-9 から「絶対 1e-7 かつ相対」に広げ、`x_b_slope` 自体は書き換えない(`extended_dual.rs:706-712`)。目的は速度ではなく、増分更新・ドリフト残差・再同期に閾値が波及しないようにして §4 の脆さを減らすこと。効果: 不明(経路が変わる)。**必ず greenbea の目的値一致と 93 問題全数を確認すること**。
5. 1 反復 360 us の定数(dse_update 14.6%、price 9.9%、btran/ftran 各 9%)は反復#7 の分析と同じ構造で、本反復の主因ではない。
