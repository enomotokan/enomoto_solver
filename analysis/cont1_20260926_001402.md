## 3. 原因 (問 2)

### 3.1 presolve / scaling / 摂動除去の切り分け

- presolve: `PRESOLVE_SIZE n_vars_in=40398 n_rows_in=201189 n_vars_out=40398 n_rows_out=119599` (`_build_our_model` は
  両側行を `≤`/`≥` の 2 本にするので入力行数が 201,189)。HiGHS の縮約後も 119,599 × 40,398。ours が落とす 81,590 行 =
  単一変数行 80,794 (境界へ) + 冗長行 796。796 行は Python で伝播を再現すると (`scratchpad/presim.py`) `t ≥ 0`
  (`−0.00707·x_k − t ≤ 0` と `x_k ≥ 0` から) により冗長になる `−0.00707·x_k − t ≤ 0` 型の行で、HiGHS が落とす 796 行と
  同じ。**違反した 12 行はいずれも標準形に残っている** (書き出した標準形で確認: 違反スラック列 `159347` 等は
  それらの行のスラック)。postsolve の代入ログは空 (列数不変)。
- scaling: 書き出した標準形で `|Ax − b| = 1.9e-11` (引き継ぎ前 4.5e-13)。x のアンスケール (`scaling::unscale_x`)
  は対角なので違反を作らない。
- 費用摂動: 双対段 (`solve_slope_intercept_dual_impl`) の最終基底 (`final_prehandoff`) は標準形で **境界違反 0**、
  摂動費用に対する最適値 0.014930676906 (真の費用では同じ x で 0.0149、真の最適値 0.00878)。真の費用で
  再計算した被約費用は 788 列 (下限側) で負 → `polish DUAL->PRIMAL cleanup handoff` (`polish_iters=0`)。
  摂動の除去 (clean-up) そのものは正しく動き、**壊れるのは引き継いだ主単体法の中**。
- 許容誤差: `PRIMAL_FEAS_TOL = 1e-7` (HiGHS `primal_feasibility_tolerance` 1e-7 と同じ)、`TOL = 1e-9`、
  `PRIMAL_HARRIS_TOL = 1e-7`、`EXPAND_DELTA_F = 1e-6`。値は HiGHS 並みだが、下記のとおり Harris 窓の使い方が
  変数空間でなくステップ長空間なので `|alpha|` 倍に増幅される。

### 3.2 主単体法引き継ぎ (`run_phase2_incremental`, `src/simplex.rs:1165-1420`) の何が悪いか

引き継ぎ後の書き出し (`final_handoff`, `dump_check.py`):

```
std: max |Ax-b| 1.9e-11
std: max col-bound viol 6.62e-3  n>1e-9=12  n>1e-7=11  (基底 1 本 = 2.2e-8、残り 11 本は非基底 L でスラック)
  col 159347 st=L lb=0 ub=inf x=-6.62e-3  d=+1.3e-6
  col 159523 st=L lb=0 ub=inf x=-4.98e-3  d=+8.4e-8   ...
nonbasic at non-bound: L 11
dual infeas (真の費用、固定列除く): 0
```

流れ:

1. 比率テスト (`:1296-1331`): pass 1 で `expand.delta` (≤ 1e-6) だけ緩めた境界への最小ステップ `alpha1`、pass 2 で
   `exact ≤ alpha1 + harris` (`harris = 1e-7`、**ステップ長の絶対値**) の候補のうち `|pivot|` 最大を出る行にし、
   `theta = max(alpha2, EXPAND_TAU/|pivot|)`。出る行以外の候補 c' の行き過ぎは `(theta − exact_c')·|rate_c'|
   ≤ delta + harris·|alpha_c'|`。cont1 では `|alpha|` が 100 級 (違反列の `B⁻¹A_j` は `|·|_∞ = 141`、非零 119,587/119,599)
   なので 1e-7 の窓でも 1e-5 級、さらに一度上下限を外れた基底変数は次以降の反復で `exact < 0` となり
   `theta = EXPAND_TAU/|pivot|` (pivot が小さいと大きなステップ) で押し出され続けるので累積して 1e-3 級になる
   `run_phase` (`:1000-1084`) も同じ設計。
   計装 clone の `ENOMOTO_PROF_HANDOFF` ログ (`scratchpad/exp.err`、双対段の経路が違う走行だが機構は同じ) の実測:
   反復 0〜6 で毎回 `alpha2 < 0` (出る変数が既に境界の外) となり行き過ぎが `EXPAND_TAU` ずつ累積 (9.8e-9 → 6.9e-8)、
   反復 13〜16 で `|pivot| = 754〜759` の列が入って `alpha1 = −7.3e-8` (ステップ長) × 759 = **2.1e-5** の違反、
   反復 64〜138 で 1e-4〜3.6e-4 (pivot 5e3、`n_basic_bad = 7`)、反復 251 で 0.10、反復 428 で 16.9、反復 440 以降
   `|pivot| = 1.3e-7〜2e-7` (`FT_MIN_PIVOT` ぎりぎり) で `theta = 0.05〜0.08` の巨大ステップ → 反復 451 で違反 6.9e8、
   基底違反 38,627 本 → 再分解失敗で `None` (**この走行は not_solved**)。HEAD 既定の走行では同じ機構が 6.6e-3 で
   止まって "optimal" を返した。つまり結果は経路依存で、正しい解 (§3.3)・実行不能な解・not_solved のどれにもなりうる。
2. 出る変数の値: `t.x[var] -= best_dir·alpha[i]·theta` の後 `nb_status[leaving] = Lower/Upper` にするだけで
   **値を境界にスナップしない** (`:1384`)。HiGHS/古典実装は出る変数の値を境界に置き、その差は次の再計算で吸収する。
3. `expand_reset_nonbasics` (`:724`) は `|x − bound| < EXPAND_DELTA_F = 1e-6` の非基底しか戻さないので、
   1e-6 を超えて外れた非基底は永久にその値に留まる。`recompute_basics` (`:668`) の `compute_rhs` は非基底の
   `t.x[j]` をそのまま使うので `Ax = b` は保たれ、境界違反だけが残る。
4. 終了判定 (`:1281-1284`) は「被約費用に適格列なし」だけで主実行可能性を見ない。`polish` 側 (`:5201-5211`) も
   `t.x[0..n_structural]` をそのまま返す。→ 実行不能な x が "optimal" として返る。

### 3.3 最終基底は正しい (`scratchpad/basis_check.py`)

書き出した最終基底 B (119,599 × 119,599、scipy `splu` 0.3 s、L+U 3.7M 非零) で、非基底列 11 本を境界 (0) に戻して
`x_B = B⁻¹(b − N x_N)` を解き直すと:

```
after snapping nonbasics: max basic viol 0.0  n>1e-9 0   obj 0.008782486003705074   ||B x_B - rhs|| 6.4e-15
```

HiGHS の 0.00878248600370569 と 1e-15 で一致。被約費用は既に双対実行可能なので、この基底解が最適解。
**cont1 の目的関数値の問題は「返す前に非基底を境界に戻して x_B を再計算する」だけで解決する。**

  chuzr から除外する。今回は関与していない (引き継ぎ前の x は違反 0)。

主ループの内訳 (12.1 ms/反復): **FTRAN 5.86 ms (48%)**、**BTRAN 2.63 ms (22%)**、再分解 1.67 ms (14%、68 回、1 回
約 1 s)、DSE 更新 0.67、x_B 更新 0.49、chuzr 0.28、PRICE 0.25。`density_gate_ftrans=26646`、入る列の FTRAN 結果の
非零率の移動平均 **0.999** (m = 119,599 の密ベクトル)、`pivot_order_reuse` は 4 回試して fill で全部失敗、
`refactor_count=68 (clock=68) max_update_streak=1144`、LU 非零 1.43M。

つまり `B⁻¹` が密 (格子 PDE + L∞ 結合) で、(a) FTRAN/BTRAN の結果が毎回 O(m) 密、(b) FT 更新の eta も密 (1 本 ≈ m)
で、合成クロックが `sqrt(m/2000)·16 ≈ 124` 倍 (策10) まで再分解を遅らせるため **平均数百本、最大 1,144 本の密 eta を
毎反復 3 回 (rho, alpha, tau) 通す** のが FTRAN/BTRAN の時間の主因。`SYNTH_CLOCK_DENSE_FRACTION = 0.3` (密なら sqrt 倍を
掛けない) は入る列の密度 0.999 で効いているはずだが、それでも `SYNTH_CLOCK_FACTOR = 16` × build_tick (LU 1.43M 非零、
1 回 1 s の分解) が大きく 600 更新前後まで伸びる。HiGHS は `update_limit = 100`。

### 4.2 実験: `ENOMOTO_SYNTH_CLOCK_FACTOR=4` (計装 clone、`scratchpad/exp.err`)

走行結果 (双対段の経路が変わるので厳密な A/B ではないが、内訳は比較できる):

| 主ループ反復数 | 40,492 | 40,202 |
| 再分解回数 / 最大更新連鎖 | 68 / 1,144 | 231 / 411 |
| 1 反復 | 12.1 ms | **15.2 ms** |

## 5. 対処法 (問 4)

優先順。効果は cont1 での見込み、Netlib は HEAD で引き継ぎ経路に入る 13 問 (25fv47, bnl2, cycle, d2q06c, dfl001,
etamacro, fffff800, greenbea, nesm, pilot.ja, pilot87, scsd1, scsd6。`scratchpad/netlib_handoff.json`) と
`polish handoff skipped` の 35 問が影響範囲。13 問の現状の返した x は元問題で最大違反 1.3e-7 (pilot.ja)、
1.2e-7 (greenbea)、他は ≤ 6e-8 で、目的関数値は HiGHS と 1e-10 以内 (`netlib_viol.py`)。

### 策1 (必須、小): 引き継ぎの終わりで非基底を境界に戻し `x_B` を再計算してから返す

- `run_phase2_incremental` / `run_phase` が `Optimal` を返す直前 (または `polish` の `:5201-5211`) で、全非基底列を
  `nb_status` の境界値 (Zero は 0) にスナップし、`t.recompute_basics(&lu)` (必要なら再分解) で `x_B` を作り直す。
- 効果: cont1 は §3.3 のとおり **HiGHS と 1e-15 で一致する最適解**になる (最終基底は最適基底なので追加反復なし)。
  ただし §4.2 の走行のように引き継ぎが発散した場合は基底自体が壊れているので策1 だけでは足りず、策2・策3 が必要。
- 難度: 低 (数十行)。Netlib: 13 問の返す x が変わりうるが、現状の非基底のずれは ≤ 1.3e-7 なので目的関数値の変化は
  1e-7 相対以下 (ビット一致は保証されない。`ab_bench` で status/目的関数値の確認が必要)。時間への影響は無視できる
  (O(nnz) 1 回)。

### 策2 (必須、小): 返す前の主・双対実行可能性の最終検査 (HiGHS の cleanup ループ相当)

- 策1 の再計算後に `x_B` の境界違反を `PRIMAL_FEAS_TOL` で検査し、違反があれば (i) 双対段 (`polish` の主ループ) に
  戻す — 基底は双対実行可能なので双対単体法で直せる — を上限回数まで繰り返し、(ii) 直らなければ `Optimal` と
  言わず `NotSolved` を返す。今の終了判定 (`simplex.rs:1281`) は被約費用だけ見ており、実行不能解を "optimal" と
  報告する経路が残っている。
- 効果: 誤答の再発防止 (cont1 以外の密な問題でも)。難度: 中 (polish ↔ 引き継ぎのループ化)。Netlib: 検査に引っかかる
  問題は現状ないはずなので不変。

### 策3 (推奨、中): 主単体法の比率テストを変数空間の Harris 窓にし、出る変数を境界に置く

- `admitted` の条件 `exact ≤ alpha1 + PRIMAL_HARRIS_TOL` (`:1064`, `:1313`) はステップ長空間の絶対値で、行き過ぎが
  `harris·|alpha_i|` になる。標準の Harris/EXPAND (Gill et al. 1989, HiGHS `HEkkPrimal`) は pass 1 で緩めた境界
  (`bound ± delta`) への最小ステップを `alpha1` とし、pass 2 は `exact ≤ alpha1` (追加の窓なし) か、窓を
  `harris/|rate_c|` に割る。さらに出る変数の値を境界にスナップし (`:1384` の直前で `t.x[leaving] = bound`)、
  既に上下限を外れている基底変数は `run_phase` の phase 1 と同じ「実行可能側へ戻る向きだけブロック」規則
  (`:1015-1035`) を phase 2 でも使う (`run_phase2_incremental` にはこの分岐がない)。
- 効果: 行き過ぎが `delta ≤ 1e-6` に収まり、cont1 の 1e-3 級の違反は発生しなくなる。策1 と併用で安全。
- 難度: 中。Netlib: 引き継ぎ 13 問のピボット列が変わりうる (反復数・目的関数値の微小変化。A/B で要確認)。

### 策4 (推奨、中): 引き継ぎに入る前に真の費用で双対実行不能な箱型列をフリップする (`ENOMOTO_HANDOFF_FLIP=1`, S5)

- 既存の `polish` の S5 (`:5027-5031`, `:5140-5180`) は既定オフ。cont1 の 788 列はすべて箱型 (presolve で `[0, 3.5〜10]`) なので
  フリップ可能で、その後は双対単体法 (polish ループ) だけで直る = 主単体法引き継ぎ自体を通らない。
- 効果: cont1 の 55 s (10%) の引き継ぎが双対反復に置き換わる (反復数は要計測)。難度: 低 (フラグを既定オンにするか、
  条件付きで有効化)。Netlib: 引き継ぎ 13 問の経路が変わる (要 A/B)。

### 策5 (推奨、小〜中): `polish` の費用摂動を主ループと揃え、真の費用の尺度に比例させる

- `polish` の `active_cost` でスラックの摂動を戻す (主ループ `:1982-1984` と同じ)。
- 摂動量 `(1+r)·(|c_j|+1)·base` は `c_j = 0` の列にも `base` を付ける (HiGHS も同じ式だが、HiGHS は
  `cost_perturbation_max_abs_cost` と `max_abs_cost` の比で `base` を `5e-7·max(1, ...)` にする)。cont1 のように
  費用が 1 列にしかない問題では、`c_j = 0` の列の摂動を `base·|c|_max/n` 級に落とすか、摂動の合計
  `Σ xpert_j·(ub_j − lb_j)` を `|c|_max` に対して抑える。
- 効果: 双対段の最適値のずれ (0.01493 vs 0.00878) と 788 列の双対実行不能が減り、引き継ぎ反復が減る。
  難度: 低〜中。Netlib: 摂動が変わると全問の経路が変わる (要 A/B、退化問題での反復増に注意)。

### 策6 (速度、中): 密な eta のときの再分解間隔の上限

- `refactor_count=68`, `max_update_streak=1144` で FTRAN/BTRAN の 70% が eta 適用。HiGHS の `update_limit=100` 相当の
  上限 (例: FTRAN 結果の非零率が `SYNTH_CLOCK_DENSE_FRACTION` 以上なら `ft_max_updates = max(100, …)`)、または
  合成クロックの `synth_tick` に eta の実サイズ (`eta_nnz × 3 solves/反復`) を加算して密 eta の費用を数える。
- 期待効果: §4.2 の実験 (係数 16 → 4) は逆効果 (490 → 610 s) で、再分解 1 回 ≈ 1 s が高すぎるため cadence 調整では
  速くならない。この策は **見送り**、策7 を優先。

### 策7 (速度、大): 密な `B⁻¹` 向けの経路

- FTRAN/BTRAN の結果が m の 99.9% 非零なら、疎経路 (Gilbert-Peierls、超疎 U、`R` eta の疎適用) のオーバーヘッドは
  無駄で、密 LU (`ENOMOTO_LU_DENSE_SWITCH`、今回 `count=0`) や密行列ベクトル積へ切り替える方が速い。
  再分解 1 回 1 s (pivot search 0.34 s、`col_max_abs rescan` 741M 要素) も密度対応で短縮できる。
- 期待効果: 1 反復 12 ms → HiGHS 並み (3〜6 ms) なら 490 s → 150〜250 s。難度: 高。Netlib: 密度ゲートで不変。
