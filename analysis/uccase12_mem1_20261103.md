# uccase12 のメモリ不足: 求解 100〜170 秒の RSS の跳ねの持ち主 (2026-11-03、mem1)

bench に使う環境変数: `ENOMOTO_MIP_MEM1_SIBLU=1` (試作、既定では使わない。58 問の設定名は siblu1)。次に回すなら `ENOMOTO_MIP_MEM1_SIBLU=1 ENOMOTO_MIP_MEM1_SIBLU_ROWS=1000` (siblu1r)

並列 3 セッションのうちの 1 つ (担当: ヒーププロファイラで、求解 100〜170 秒の 5〜6 GB の跳ねを誰が持っているかを特定する)。
発端は `analysis/mittelmann_ready_20261103/long_b.md` の「uccase12 の調べ (OOM)」。4 スレッド、4 コア・メモリ 15 GB の機械
(cgroup の上限 ≈ 13.6 GB)、ソルバーは同時に 1 つ。土台はブランチ `ccr-1beed81b-ex0uhq` の `3076c6b7` (今の既定 = canddet + p)。

## 結論

- **跳ねの持ち主は、潜りの兄弟の一覧 (`dive_stack`) が兄弟ごとに持つ親の LP の LU キャッシュ (`LuSnapshot`)** (事実、heaptrack)。
  分枝のたびに `self.lp.lu_snapshot()` で親の LU を `Arc` で共有して積むが、子の LP を解くと LU が共有中なので
  `Arc::try_unwrap` が失敗して **FtLu を丸ごと複製** し (`src/simplex/mip_lp.rs:1219`)、さらに Forrest-Tomlin の更新の eta を
  その写しに足していく。潜りが深いと、スレッドごとに深さの数だけ別々の LU (uccase12 の 6.8 万行で 1 つ数十 MB) が残る。
  - heaptrack (330 秒、跳ねが起きた回) の最大のヒープ 5.95 GB のうち、**LU の写し 2.14 GB + 写しの FT の更新の eta 1.87 GB = 4.0 GB**
    が木の探索のスレッド (`solve_worker` → `run` → LP の求解) の確保 (`analysis/uccase12_mem1_20261103/ht2_peak_summary.txt`)。
  - 数え上げ (`ENOMOTO_MIP_MEM1_SIBLU=1000000` = 既定と同じ動きで数えるだけ、200 秒): 1 スレッドが同時に持った LU 付きの兄弟は
    **最大 93 個**、積んだのは 267 個、**兄弟へ戻って LU を使えたのは 0 回** (`sibling backtracks 0`)。持つだけで使っていない。
  - `ENOMOTO_MIP_NO_SIBLING_LU=1` (既存の診断用) で 200 秒の最大 RSS が 6.3 GB → 1.7 GB (同じくらいのノード数)。
- **試作 `ENOMOTO_MIP_MEM1_SIBLU=K`**: LU を持つのは潜りの兄弟のうち新しい方から K 個だけ (古い兄弟の LU は積むときに捨てる)。
  兄弟へは新しい方から戻るので、使われるのはほぼ一番上だけ。K = 1 で uccase12 の跳ねは消える (下の表)。
  - 600 秒: 既定は起動から 413 秒・13.6 GB で OOM に落ちる (同じ機械。long_b では 325 秒)。siblu1 は 200 秒で 1.8 GB
    (既定は 5.6 GB、開いたノードはどちらも約 1100) だが、その後の開いたノードの保存 (DSE 重み・基底、約 0.55 MB/ノード) で
    **510 秒に OOM** (落ちるのが 100 秒延びただけ)。siblu1 に DSE の保存を切る (`ENOMOTO_MIP_NO_DSE_ALL=1 ENOMOTO_MIP_POOL_DSE=0`) と
    **600 秒を走り切り、最大 RSS 3.5 GB**、目的値 11507.40506 (HiGHS の最適値 11507.4051 と一致)、下界 11507.3704 (時間切れ)。
  - 58 問 (60 秒、1 回): 解けた数 44 対 43・SGM 16.78 対 16.74 秒でほぼ同じ、crash・誤答 0。行が数千の問題で最大 RSS が下がる
    (neos-1456979 2.1 → 0.7 GB など)。小さい pk1 (46 行) は遅くなる (3 回中 2 回 35 秒超、既定は 21 秒) ので、LP の行が R 以上の
    ときだけ間引く `ENOMOTO_MIP_MEM1_SIBLU_ROWS=R` を足した (R = 1000 で pk1 は既定と同じ動き、uccase12 の木の LP は 6.8 万行なので効いたままの見込み)。
- 既定にする候補: `ENOMOTO_MIP_MEM1_SIBLU=1 ENOMOTO_MIP_MEM1_SIBLU_ROWS=1000`。既定にする前に、この組で 58 問・Mittelmann の bench を
  回して確かめる (今回は siblu1 の 58 問 1 回と、pk1・h80x6320d の解き直しだけ)。
- 残り: 跳ねを消しても、uccase12 は開いたノードの保存 (DSE 重み (u32, f32) × 6.8 万行 ≈ 550 KB/ノード) で 600 秒の中で落ちる。
  これはほかのセッションの担当 (開いたノードの DSE・基底の間引き)。両方を直せば 600 秒を 3.5 GB で走り切る見込み (上の DSE なしの回)。
- 並行のセッション (`analysis/uccase12_mem2_20261103.md`、試作 `ENOMOTO_MIP_MEM2`) も `ENOMOTO_MIP_NO_SIBLING_LU=1` の切り分けで
  同じ原因に着き、`l` (兄弟の LU を新しい 8 個まで、`ENOMOTO_T_MIP_MEM2_LU_KEEP`) を入れている。こちらは heaptrack による持ち主の
  特定 (複製の場所と大きさ)・持った数と使った数の数え上げ・K = 1 の 58 問を足す。2 つの試作はどちらも積むところで古い LU を
  捨てるだけで、同時に付けても矛盾しない。既定にするなら 1 つにまとめる (K と行の下限の値は、pk1 のような小さい問題の遅れと
  合わせて決める)。

## 1. 調べ方

- heaptrack 1.5.0 (`apt-get install heaptrack`) を、デバッグ情報 (行番号) つきの wheel
  (`CARGO_PROFILE_RELEASE_DEBUG=line-tables-only`、コード生成は同じ) で使った。
  - **注意: このソルバーのグローバルアロケータは 4 KB 未満を mimalloc、4 KB 以上を glibc に振り分ける** (`src/lib.rs` の `SplitAlloc`)。
    heaptrack が見えるのは glibc の側 (4 KB 以上) だけ。`MALLOC_ARENA_MAX=2` が効かなかったのも、glibc の領域の数ではなく
    生きている大きい確保が原因だったため (下の smaps の分類でも、増えたのは glibc のスレッドの領域)。
  - 途中から付ける (`heaptrack -p`) は gdb の注入が失敗した (`The program being debugged was signaled`)。始めから付けた。
  - 1 回目 (`ht1`、170 秒) は再スタートが 2 回入って木が 54 ノードしか進まず跳ねが起きなかった (最大のヒープは根の内点法の
    gemm の作業領域、下の「ついでに見つけたこと」)。2 回目 (`ht2`、330 秒) で跳ねが起き (RSS 7.1 GB)、その最大の時点の持ち主を読んだ。
- 並行して、2〜3 秒ごとに `/proc/<pid>/smaps` を読み、無名の写像を mimalloc の 1 GB の領域・glibc の主ヒープ・glibc のスレッドの
  領域 (64 MB)・そのほかに分けた (`watch_proc.py`)。既定の 600 秒の回 (`watch_def_600.jsonl`) の 121 → 242 秒 (RSS 1.5 → 9.6 GB) では、
  glibc のスレッドの領域が 0.96 → 7.38 GB (64 MB の領域 29 → 135 個)、主ヒープが 0.15 → 0.61 GB、mimalloc の領域が 0.32 → 1.33 GB。
  増えたのの 8 割は heaptrack が見える glibc の側。
- 求解は `analysis/mittelmann_ready_20261103/long_b/diag_worker.py` (log=True、全スレッドの開いたノードの数つき) を
  `run_mem.py` から起動した。

## 2. uccase12 の RSS の推移 (4 スレッド、起動からの秒、MB)

| 回 | 60 | 100 | 150 | 200 | 250 | 300 | 350 | 400 | 450 | 500 | 600 | 結果 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---|
| 既定 (`def_600`) | 695 | 839 | 1857 | 5558 | 9686 | 9986 | 12683 | 12841 | - | - | - | 413 秒で OOM (13.6 GB) |
| siblu1 (`siblu1_600`) | 709 | 1275 | 1616 | 1782 | 2494 | 4032 | 5779 | 8087 | 10161 | 13143 | - | 510 秒で OOM (13.5 GB) |
| siblu1 + DSE なし (`siblu1_nodse_600`) | 642 | 890 | 890 | 1455 | 1616 | 1665 | 1866 | 2228 | 2428 | 2725 | 3366 | 時間切れ 600.9 秒、11507.40506 / 下界 11507.37045、13798 ノード、最大 3.5 GB |

同じ開いたノードの数で比べる (全スレッド、求解の時計):

| 回 | 求解 200 秒の開いたノード / RSS | 求解 300 秒の開いたノード / RSS |
|---|---|---|
| 既定 | 1099 / 5.6 GB | 5529 / 10.0 GB |
| siblu1 | 1112 / 1.8 GB | 5205 / 4.0 GB |
| siblu1 + DSE なし | 1627 / 1.5 GB | 6646 / 1.7 GB |

- 同じ開いたノードの数で、siblu1 は既定より **3.8〜6 GB 少ない**。siblu1 の 200 → 300 秒の増え方は (4032 − 1782) / (5205 − 1112) ≈
  0.55 MB/ノードで、long_b の見積もり (DSE 重み 550 KB/ノード) と合う。DSE を切ると約 40 KB/ノード。
- siblu1 + DSE なしの数え上げ: LU を持つ兄弟は各スレッド 1 個まで、積んだ 13849、捨てた 11091、兄弟へ戻って LU を使えた 93 回。
- 200 秒の回 (跳ねだけを見る): 既定 (`plain1`) 6.3 GB・222 ノード、`ENOMOTO_MIP_NO_SIBLING_LU=1` (`nosiblu1`) 1.7 GB・248 ノード、
  `ENOMOTO_MIP_MEM1_SIBLU=1000000` (`siblu_inf_200`、既定と同じ動き) 7.3 GB・268 ノード。
- long_b の「気になる点」(木の中の暫定解が HiGHS の最適値より 2.5e-3 小さい): DSE なしの回の最後の解は 11507.40506 で、
  HiGHS の 11507.4051 と一致 (後処理を通った元の問題での値)。ほかの回の木の中の暫定解 (進み行の ub) は 11507.40280〜11507.40254 で、
  long_b と同じく HiGHS より小さい。最後まで走った回の返す値は小さくならなかったが、1 回だけなので確かめは足りない。

## 3. 試作の中身

`src/mip/solver.rs`:

- `mem1_siblu_keep()` (`ENOMOTO_MIP_MEM1_SIBLU` を数として読む。なければ `None` で、今までどおり)。
- 分枝で兄弟を `dive_stack` に積む直前に `mem1_siblu_trim` で、新しい方から K − 1 個を残して古い兄弟の LU を捨てる
  (積む 1 個と合わせて K 個)。K = 0 なら持たない (`ENOMOTO_MIP_NO_SIBLING_LU` と同じ)。
- 数え上げ `MEM1_SIBLU_STATS` (全スレッドの和: 持った最大の数・積んだ数・捨てた数・兄弟へ戻って LU を使えた数) を、試作のときだけ
  終わりのログ (`MIP: mem1 sibling LU (all threads): ...`、`ENOMOTO_MIP_LOG=1`) に出す。
- `ENOMOTO_MIP_MEM1_SIBLU_ROWS=R` (既定 0): LP の行が R 以上のときだけ間引く (58 問の後に pk1 の遅れを見て足した、4 節)。
- 既定の経路 (環境変数なし) は変わらない。`cargo test --release --lib` 333 件通過 (この機械では pyo3 の extension-module の
  リンクのため `RUSTFLAGS="-L /usr/local/lib -l python3.13" LD_LIBRARY_PATH=/usr/local/lib` を付けた)。

## 5. ついでに見つけたこと

- **内点法の行列積 (faer 0.24 → private-gemm-x86) のスレッドごとの作業領域が 1 スレッド 545 MB** (L3 の大きさ 260 MiB × 2 を
  thread_local に確保する、`private-gemm-x86-0.1.22/src/lib.rs:1287`)。heaptrack の 1 回目では根の内点法 (multifrontal) の
  4 スレッドで 2.18 GB (仮想。触った分だけが RSS)。同時実行のプールは使い終わると消えるのでスレッドとともに解放されるが、
  L3 が大きいクラウドの機械では、内点法が走っている間だけ RSS が数百 MB〜1 GB 増えうる。今回の跳ねとは別。
- 兄弟の LU は uccase12 ではほとんど使われない (戻った 93 回 / 積んだ 13849 回)。木の 1 ノードの LP が強分岐で数秒かかる問題では、
  潜りが枝刈りで終わらずに待ち行列から選び直すことが多いため (推測)。

## 6. 再現手順

```sh
pip install -q highspy==1.15.1 maturin
maturin build --release -o /tmp/whl && pip install -q --force-reinstall --no-deps /tmp/whl/*.whl
D=analysis/uccase12_mem1_20261103
python $D/run_mem.py def_600 uccase12 600 &           # 既定 (別の端末で watch_proc.py <pid> $D/watch_def_600.jsonl)
ENOMOTO_MIP_MEM1_SIBLU=1 python $D/run_mem.py siblu1_600 uccase12 600
ENOMOTO_MIP_MEM1_SIBLU=1 ENOMOTO_MIP_NO_DSE_ALL=1 ENOMOTO_MIP_POOL_DSE=0 python $D/run_mem.py siblu1_nodse_600 uccase12 600
# heaptrack (デバッグ情報つきの wheel を PYTHONPATH で与える)
CARGO_PROFILE_RELEASE_DEBUG=line-tables-only CARGO_TARGET_DIR=target_dbg maturin build --release -o /tmp/whl_dbg
pip install --no-deps --target /tmp/site_dbg /tmp/whl_dbg/*.whl
PYTHONPATH=/tmp/site_dbg python $D/run_mem.py ht2 uccase12 330 heaptrack
heaptrack_print -f /tmp/claude-0/mem1_logs/ht_ht2.gz > ht2.txt && python $D/ht_summary.py ht2.txt 10
python $D/bench.py def,siblu1 "" bench && python $D/summ.py   # 58 問
```

  `watch_<回>.jsonl` (3 秒ごとの smaps の分類とスレッドの名前ごとの数。`watch_plain1_oldfmt.jsonl` は分類前の形)、
  `ht1_peak_summary.txt`・`ht2_peak_summary.txt` (heaptrack の最大の時点の持ち主の要約)、`bench.jsonl`・`summ.txt` (58 問)、
  `logs.tar.gz` (uccase12 の回の stderr・stdout)。
