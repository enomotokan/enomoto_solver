# 10teams の揺れの調査 (2026-10-20)

ブランチ `inv/tenteams-20261020` (基点 0542795)。計測はすべて同じコンテナ (nproc 4) で、ほかの重い処理と重ねずに行った。
ENOMOTO は `m.solve(None, False, 60, None, None, threads, log=True)` (`benchmark_highs._load_lp`・`_build_our_model`)、
ログは `ENOMOTO_MIP_LOG=1`。

- 根の下界は全回 924 (カットの 1 ラウンド目で 917 -> 924 になり、そのまま)。最適値も 924。つまり揺れは**主側 (924 の解を見つけるかどうか) だけ**の問題で、924 が出た時点で終わる。
- 最初の解は全回 Feasibility Jump (並列) の 964 (2.5〜3.1 秒)。964 は根の LP との相対ギャップ 4% なので `fj_poor` (既定 0.5) に当たらず、暫定解なし用の RENS・find スレッドは動かない。
- 根の RENS・locks・clique のサブ MIP は全回 0 ノードで実行不能、根の RINS は 964 をそのまま返す。
- 924 を根で出しうるのは root reduced cost と LP face のサブ MIP だけ (被約費用が 0 でない列を境界に固定する。両者は同じ部分問題になる)。どちらも「整数列の固定率 0.3 以上」(`ENOMOTO_T_MIP_RRC_MIN_RATE`・`ENOMOTO_T_MIP_LPFACE_RATE`) のときだけ動く。
- カット後の根の LP で被約費用が 0 でない整数列の数は回によって 440〜535 本 (固定率 0.28〜0.33) と揺れる。カットのループの結果 (加えたカットの数 385〜551、LP に残る数 10〜19) が回ごとに違い、最後の基底が変わるため。0.3 を超えた 4 回だけサブ MIP が動き、動いても時間の上限 (残りの 7% = 3.6 秒) で 3 回は解なしで止まった。
- 木に入った回は、924 を見つけるまで数千〜1 万数千ノードかかる (下界は 924 で止まっていて、解が見つかるまで閉じない)。

### 1 スレッド (既定、4 回)

### 試作 `ENOMOTO_MIP_LPFACE_TIGHT` (src/mip/heur_scip.rs の `lp_face`)

既定は変えない。有効にすると LP face のサブ MIP について:

1. 打ち切り値を根の LP の値 (目的関数の刻みがあれば刻みで切り上げ) にする (暫定解の打ち切り値と小さい方)。最適面の上の整数解だけを探す。`=nocut` なら打ち切り値は変えない (切り分け用)。
2. 固定率の下限を `ENOMOTO_T_MIP_LPFACE_TIGHT_RATE` (既定 0.1) に下げる。
3. 時間を残りの `ENOMOTO_T_MIP_LPFACE_TIME_FRAC` (既定 0.07)、最大 `ENOMOTO_T_MIP_LPFACE_TIME_MAX` (既定 6 秒)、ノードの上限を `ENOMOTO_T_MIP_LPFACE_NODES` (既定 500) にする (既定値は通常のサブ MIP と同じ)。

### 副作用 (MIPLIB 40 問、4 スレッド・60 秒、既定と F を問題ごとに交互に 1 回ずつ)

- 解けた数 25 / 25、SGM (shift 10、解けなければ 60 秒) 20.74 -> 21.03 秒。不一致 (誤った最適) なし。
- F で締めた LP face が動いた問題は 27 問 (固定率 0.1〜0.3 で新たに動いたのは gen-ip054・flugpl・dcmulti・neos-911970・assign1-5-8・beavma)。
- 解けた問題で差が大きかったもの: rout 8.8 -> 13.1、binkar10_1 13.1 -> 17.3、eil33-2 37.5 -> 42.1 (どれも LP face が動いた)、h80x6320d 48.5 -> 41.1、10teams 11.9 -> 10.2、mik-250-20-75-4 11.0 -> 9.5。noswot 33.4 -> 44.5・qiu 30.9 -> 32.8 は LP face が動いていないので揺れ。
- 時間切れの問題の暫定解: blp-ar98 7155 -> 6502、timtab1 789780 -> 780064 (LP face は動いていない)、gen-ip054 6847 -> 6854、supportcase26 1789 -> 1798 (動いていない)。
- 30n20b8 では締めた LP face のサブ MIP が 0 ノードで実行不能と分かるまで 15.2 秒かかった (サブ MIP の根の LP が重い)。時間の上限を 15 秒に広げたことの費用がそのまま出る例。
- サブ MIP は打ち切り値より悪い解も返す (rout で 1534.8、qnet1 で 25222 など。暫定解がないサブ MIP の中のヒューリスティクスの解は打ち切り値で捨てられていない)。元の問題の側で暫定解より悪ければ捨てられるが、暫定解がなければ悪い解が暫定解になる。

## 推測

- 分かれ目は「根の LP face (と root reduced cost) のサブ MIP が動いて、上限までに 924 を見つけるか」。被約費用が 0 でない列の数がカットのループの結果で揺れ、固定率 0.3 の閾値をまたぐかどうかで動く・動かないが決まる。動いても既定の時間 (3.6 秒) とノード (500) ではおよそ半分しか見つからない。スレッドのタイミング (並列のカットの分離・背景のカット) は基底を変える経路で効いているだけで、直接の原因ではない。1 スレッドで揺れるのも時間の上限で打ち切る部分 (サブ MIP の時間) があるため。
- 10teams の根の LP は強く双対退化していて、最適面 (目的値 924) の中に整数解がある。打ち切り値を根の LP の値にすると、木の中で目的値が上がる枝を切れる (G との比較で、打ち切り値なしだと 4 回中 1 回が 15 秒で見つからない)。
- HiGHS が 1.6〜2.4 秒で解くのは、根の RENS 系のサブ MIP (固定率を目標で止める・入れ子の RENS) が 924 を直接見つけるため。FJ の 964 が出ないので、暫定解なしの扱いのまま RENS が強く回ると考えられる。ENOMOTO で FJ の 964 を「質の悪い解」とみなす A でも安定しなかったので、HiGHS の RENS との差は入れ子の深さ・固定の積み方の方にありそう (未確認)。
- 副作用は小さいが、LP face が実行不能と分かるまでの時間 (30n20b8) と、サブ MIP が打ち切り値を超える解を返す点は既定にする前に直したい。時間の上限は 15 秒より、10teams で足りる 8 秒程度にしても 10teams の 10 回中の最長 6.2 秒は収まる (未計測)。
