# greenbea 実行時間分析(自己改善ループ 反復#7, runtime 段) -- BTRAN の U^T 段が hyper-sparse になっていない

対象: NETLIB `greenbea`(2392 行 x 5405 列, 30,877 非零; presolve 後 2056 x 4645 x 32,474、等式スラック 1,549 本 = 固定列)。
選定理由(`scripts/select_problem.py`): runtime 段、ours/HiGHS 比が 93 問題中最悪(6 回目の選定)。
HiGHS 1.15.1(`highspy`)、4 コア、`perf` なし(callgrind あり)。全数値は本セッションでこのコンテナで実測。推定は明記する。

過去 4 本(+ PR #9 ブランチ上の 1 本)の分析と重複する指摘は繰り返さない。本反復の主題は、
(1) **BTRAN の `U^T` 段(`lu.rs::u_transpose_solve_into`)が全 m 本の eta を無条件に走査しているが、結果の非零は 1 回あたり 64 個(m=2056 の 3%)しかなく、既存の `row_owners` 逆索引を使えばピボット経路をビット単位で保ったまま hyper-sparse 化できる**(実装・検証・A/B 済み、greenbea -3.9%、他 8 問題でも -1..-9%)、
(2) 1 反復あたりのコストが「LU solve の定数」に広く分散していることの callgrind(命令数・L1 ミス)による裏付け、
(3) 反復#6 の PR #9 に関する記録の訂正、の 3 点。

## 3. 機序: BTRAN の U^T 段が hyper-sparse でない(`src/simplex/lu.rs:1737-1748` @418e62a)

```rust
fn u_transpose_solve_into(&self, z: &mut [f64]) {
    for eta in &self.u_seq {                       // 全 m 本、作成順
        let p = eta.slot;
        let y: f64 = match &eta.off_diag { Sparse(v) => v.iter().map(|&(r, v)| v * z[r]).sum(), .. };
        z[p] = (z[p] - y) / eta.pivot;
    }
}
```

- 入力は単位ベクトル `e_r`(置換後に 1 個の非零)。上三角系 `U^T z = e` の解は疎(平均 64 非零/2,056)だが、gather 形では「どの eta の内積が非零になるか」を事前に知れないので全 eta の全要素を読む(1 回 11,343 要素)。FT 更新で置き換えられた eta は要素数が数百に達する(反復#6 §1.4: 更新 500 回超で U の off-diagonal 46k)ので、更新列が伸びるほど無駄が増える。
- 必要な情報は既に `FtLu::row_owners` にある(`lu.rs:1654-1665`): `row_owners[r]` = 「off_diag に行ステップ r を持つ slot の一覧」で、`commit_update`(`:2166-2221`)が登録・抹消を厳密に行っている(古い要素の抹消 `:2195-2199`、`remove_row(p)` 後の `row_owners[p]` の take `:2205-2208`、新要素の登録 `:2212-2214`)。`u_seq` の不変条件「各 eta の off_diag が参照する slot はその eta より前の位置にある」(`u_solve_into` の docs `:1758-1763`; 現行の gather 自体がこれに依存)により、eta p を処理して `z[p] != 0` になった時点で `row_owners[p]` の各 q に「訪問必要」フラグを立てれば、q の処理時までに q の全依存先が確定している。
- **ビット同一性**: 訪問する eta では現行と同じ `off_diag` を同じ順に gather し同じ式で `z[p]` を求めるので、非零の結果はビット同一。訪問しない eta は現行では `(0 - Σ v·0)/pivot = ±0.0` を書くところを +0.0 のまま残す -- 違いはゼロの符号だけで、下流(`commit_update` の `v != 0.0` フィルタ、R eta の `yp == 0.0` スキップ、`l_transpose_solve_into`、PRICE の `rv.abs() <= TOL`、`dot(rho,rho)`、DSE の tau FTRAN)はすべて「非零の値」と「ゼロか否か」しか見ないので伝播しない。実験ではチェックモード(密版と hyper 版を両方計算し、非零をビット比較)で greenbea の全 6,723 回 + 他 9 問題の全 BTRAN で不一致 0、反復数・再分解回数・目的関数値もすべて同一(§4)。

参考(同じ hyper-sparse 化が FTRAN 側に効かない理由): `u_solve_into` は scatter 形で `xp == 0` の eta を既にスキップしており、非零 eta は 38%(tau が 61% 密)。訪問を減らすには DFS で reach を求める GP 型が必要で、それは `lu.rs:1756-1776` の docs にある通り全 NETLIB で +10.4% の退行で撤回済み。BTRAN 側は `row_owners` が既にあり、seed が単位ベクトルで、出力が 3% 密という三条件が揃うので DFS なしで済む。

## 5. 根本原因の分類

**(c) 1 反復が重い。実装定数の問題で、内訳は LU solve(BTRAN 13% + DSE の FTRAN 15% + FTRAN 9% + BFRT 4% = 41%)、再分解 16%、PRICE 12%、行走査系(xb_update/chuzc1/chuzr)17%、ドリフト検査 6%。** 正答性バグ・悪条件・退化・サイクリング・初期基底のいずれでもない(§1.5)。反復数 2.6x は設計由来の副因。

今回新たに切り出せた「HiGHS が払っていない費用」は、BTRAN の U^T 段を毎回全走査していること(主ループの 6.5%、うち 3.5% は除去可能で実証済み)。反復#6 が定量化した eta 肥大(14%)と再分解の単価(16%)は依然として大きいが、前者は再分解タイミングを変える(BIG_M 安全網が前提)、後者はピボット選択をビット単位で保つ必要がある(反復#5 §4.3, 反復#6 §3.1)という制約が続いている。

## 6. 改善候補(優先順)

### 6-1. [本反復の最小修正・経路保存・実証済み] BTRAN の U^T 段を `row_owners` で hyper-sparse 化

- 場所: `src/simplex/lu.rs` `FtLu::u_transpose_solve_into`(`:1737-1748`)と、その呼び出し元 `solve_transpose_into`(`:1943`)/`solve_transpose_into_capture`(`:1980`)。
- 変更(概形; 実験パッチと同じロジック):
  ```rust
  // FtLu に epoch スタンプ式の訪問フラグ scratch を持たせる(GpScratch と同じ手法; `RefCell<(Vec<u32>, u32)>` か、
  // 呼び出し元から `&mut BtranScratch` を渡す。後者が既存の `gp_scratch` の慣習に合う)
  fn u_transpose_solve_into(&self, z: &mut [f64], sc: &mut BtranScratch) {
      sc.epoch += 1; let ep = sc.epoch;                       // (ラップ時は全クリア)
      for s in 0..m { if z[s] != 0.0 { sc.needed[s] = ep; } }   // 入力の非零が seed(BTRAN では 1 個)
      for eta in &self.u_seq {
          let p = eta.slot;
          if sc.needed[p] != ep { continue; }                  // 入力ゼロかつ依存先すべてゼロ → 現行は ±0 を書くだけ
          let y = /* 現行と同じ gather、同じ順 */;
          z[p] = (z[p] - y) / eta.pivot;
          if z[p] != 0.0 { for &q in &self.row_owners[p] { sc.needed[q] = ep; } }
      }
  }
  ```
  `row_owners` の不変条件(厳密に「現在 off_diag に r を持つ slot」の集合であること)は `commit_update` が既に保証している(§3)。`u_seq` の位置不変条件も既存コードが依存しているものと同じ。
- 効果(実測): greenbea BTRAN 349 → 264 ms、総時間 -3.9%(比 9.7x → 約 9.3x)。他 8 問題 -1..-9%、1 問題 ±0。全問題で反復数・再分解数・目的関数値がビット一致。
- リスク: 極小。数値経路の変化はゼロの符号のみ(§3)。検証には実験と同じチェックモード(密版と二重計算して非零をビット比較する env ゲートの一時コード)を 93 問題スイープで 1 度回すのが確実。`fresh_d_into`(`extended_dual.rs:1182`)や `DseState::from_basis` のように入力が密な BTRAN では seed が m 個になり利得はないが退行もない(訪問判定は 1 分岐/eta)。`polish_with_true_bounds`(`:3773`)と古典経路 `simplex.rs::solve_lp_dual_on` の BTRAN、`trial_row_ratio` も同じ関数を通るので自動的に恩恵を受ける。
- BIG_M フォールバック注記との関係: ピボット順・再分解頻度・数値をいずれも変えないので**該当しない**。

### 6-2. [任意・経路保存・小] 定数削減 2 点(合計 -0.5..-0.7%)

- `u_solve_into`(`lu.rs:1777-1800`): `x[p] /= eta.pivot` の前に `if x[p] == 0.0 { continue; }`(ゼロの符号以外ビット同一; 実測 ftran -8 ms)。
- PRICE(`extended_dual.rs:2399-2416`): `std.lb[j] == std.ub[j]` を非零ごとに引く代わりに、ループ前に一度作った固定列マスク(`Vec<bool>`)を引く(実測 price -8..-11 ms)。より良いのは固定列を除いた PRICE 専用の行構造を presolve 後に一度作ること(判定自体が消える; 未計測)。
- **やらないこと**: DSE 重み更新の `alpha[i]==0` スキップ(+40 ms の退行、§4.1)。

### 6-3. [経路保存・中規模・別反復] 再分解の定数(`factorize` 5.9 ms/回 = 主ループ 13%)

- `MarkowitzState::eliminate`(`lu.rs:403-470`、142 ms)と `MarkowitzState::new`(`:200-263`、約 40 ms)の `BTreeMap<usize,f64>` / `BTreeSet<usize>` を、平均次数 3.5 の行に見合うソート済み `Vec` に置き換える。走査順(昇順キー)と同点規則を変えなければピボット選択は不変(反復#5 §6-3 と同じ条件)。上限 約 300 ms(11%)、現実的には 100-150 ms(推定)。PR #9 の変更と衝突しない。
- 変更後の確認: greenbea で `refactor_count=58`、反復 6,601、目的関数値ビット一致 → 93 問題スイープ。

### 6-4. [経路を変える・BIG_M 安全網が前提] eta 肥大と再分解タイミング

反復#6 §1.4 の通り、更新列が 695 本まで伸びて FTRAN/BTRAN/DSE が新鮮時の 4.8 倍になる分が主ループの 14%。HiGHS 型の synthetic clock(累積 solve コストが再分解コストを超えたら rebuild)が正しい形だが、反復#6 §3.1 で 14 構成中 6 構成が誤答に落ちた経路依存性があるので、**`simplex.rs:2972-3000` の BIG_M フォールバックが `BIG_M` クランプのアクティブな状態で `optimal` を返さない安全策と、特異基底時に `refactorize` が直前のピボットを取り消す対応(反復#6 §5-2)を先に入れる**。6-1 の hyper-sparse U^T は eta 肥大の影響を U^T 段については緩和する(訪問する eta 数は肥大に依存しない)ので、synthetic clock の最適列長を長くする方向に働く点も記録しておく。

### 6-5. [設計・別反復] 反復数(2.6x)、DSE の密 FTRAN(361 ms; HiGHS も払う本質的コスト)、R eta の gather(182 ms)、ドリフト検査の `compute_rhs_affine`(148 ms; 増分維持は丸めが変わり発火判定が変わり得るので経路を変える)。

### 6-6. 診断の常設化

`PROF_PHASES_EXT` に「btran の U^T/R/L^T 分割」「u_transpose の訪問 eta 数と非零 eta 数」を足すと、hyper-sparsity の効き具合が問題ごとに 1 回で分かる(fit2p のように効かない問題の切り分けに使える)。
