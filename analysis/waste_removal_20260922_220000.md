# 探索・データ構造の無駄の洗い出しと除去 — NETLIB93 A/B

対象: `main` = `be5bbea`(PIVOT_SEARCH_LIMIT 8→256 マージ後)を基点に、
HiGHS(`HEkkDual` / `HMatrix` / `HEkkDualRHS` / `HPresolve`)の対応箇所と
読み比べながら「必要以上の探索」「データ構造の無駄」を洗い出し、実装・計測した。

## 0. 計測方法

- 4 コア、rustc 1.94、highspy 1.15.1 / Python 3.11、NETLIB93 **全93問**。
- 2 つの venv に base / after をそれぞれ `maturin develop --release` で入れ、
  `python -m enomoto_solver.benchmark_highs --worker <問題>` を問題ごとに
  **base/after 交互**(周ごとに先後を入れ替え)で **3周**。代表値は3周の**中央値**。
- 各バッチは直前のバッチの commit を base とする(変更ごとの寄与を分離するため)。
  最後に **基点 `be5bbea` 対 最終版** の累積 A/B も取った(§3)。
- 中央値で +10% を超えた問題は、その問題だけ交互 15 回(重い問題は 5 回)で追試し、
  10%ルールは追試の中央値で判定した。この箱の 1〜10ms の問題は 1 回計測で ±20〜30%
  揺れる(`kernel_flat_matrix_20260922_143000.md` と同じ事情)。
- **経路の確認**: 各バッチで `ENOMOTO_PROF_PHASES_EXT=1` を付けて全93問を base/after
  両方で解き、`ours_status` / `ours_obj` / 主ループ `iters` / `refactor_count` を比較した。
  全バッチで **93問中92問が完全一致**(残る1問は常に `wood1p`: 同一バイナリでも
  `iters` が 164/194/217/311/313 と実行ごとに変わる既知の非決定性で、主ループに
  入る前の段階で入力が変わっている)。つまり本 A/B の時間差は、反復数の変化ではなく
  1反復・1 presolve あたりのコスト差そのものである。
- `cargo test`(debug / release)は各バッチとも 223 passed。

## 1. 洗い出した改善案(HiGHS 比較込み)

プロファイル(`ENOMOTO_PROF_PHASES_EXT`、基点)では、重い問題の主ループ時間は
PRICE 10〜14% / DSE 更新 10〜19% / BFRT 10〜24% / x_B 更新 4〜14% / BTRAN 7〜13% /
FTRAN 8〜13% / CHUZR 3〜12% / 再分解 10〜21% とばらけていた。加えて、全93問で
`ours_time` と主ループ wall の差を取ると **主ループ外(presolve 等)が約2割**あり、
特に maros-r7 は求解の **7割**が主ループ外だった(§1.4)。

### 1.1 主ループ: 1反復ごとの O(m)/O(nnz) の無駄(経路不変)

| # | 無駄 | HiGHS の対応 | 対応 |
|---|---|---|---|
| A1 | `theta_d` のデバッグ出力判定が毎反復 `std::env::var("ENOMOTO_DEBUG_D_DRIFT_EXT")` を評価(env ロック+確保)。安い `theta_d.abs() > 1e3` より先に評価されていた | — | ループ外で1回読む。`ENOMOTO_DEBUG_XB_DRIFT_EXT` も同様 |
| A2 | 入基底列 FTRAN の `dense_q.fill(0.0)`(O(m))+散布が、疎 FTRAN 経路でも毎反復実行 | `HVector` は疎のまま渡す | dense 分岐でだけ散布し、使用後は列の行だけ戻す(polish 側も) |
| A3 | BFRT の組み合わせ flip FTRAN を base/slope の2本解いていたが、slope は M 側列を flip したときしか非ゼロにならない(有限の箱幅は slope 0)。通常は**全ゼロ右辺の FTRAN** を丸ごと1本解いていた | `col_BFRT` は1本 | slope が全ゼロなら解かない。密度履歴と CLOCK tick は解いた場合と同額を計上 (`FtLu::charge_zero_rhs_solve`) — 再分解のタイミングを変えないため |
| A4 | BFRT の `BinaryHeap` と `sorted_prefix` を毎反復新規確保 | — | バッファを反復間で再利用(`BinaryHeap::from(Vec)` は `collect()` と同じ heapify なので pop 順は同一) |
| A5 | PRICE が非ゼロごとに `std.lb[j] == std.ub[j]`(ランダムロード2回)で固定列を判定 | `ar_N` に固定列は無い | 固定列を除いた行行列を事前に作る(→ C1 に発展) |
| A6 | DSE の `tau = B^-1 rho_p` を常に密 FTRAN(`rho_p` が疎でも L 段を m 全走査) | `ftran(col_DSE, expected_density)` で疎/密切替 | PRICE の `rho` 走査ついでに非ゼロリストを作り、密度ゲート付きで疎 FTRAN。結果はビット同一(同じ L の非ゼロ段を同じ昇順で処理)、tick は密版と同額 (`FtLu::solve_sparse_into_dense_tick`) |
| A7 | DSE 重み更新が全 m 行で割り算+RMW(`alpha[i] == 0` の行は値が変わらない)、`||rho_p||^2` も m 全走査 | `updateWeightDualSteepestEdge` は `column.index` の非ゼロだけ | x_B 更新の走査で `alpha` の非ゼロ行を集め、その行だけ更新 (`DseState::update_after_pivot_sparse`)。`||rho_p||^2` も非ゼロだけで合計(足していたのは +0.0 なのでビット同一) |
| A8 | `row_infeasible_affine` が `row_deviation` を丸ごと作ってから `is_some()` | — | 2つの比較を短絡評価(→ B1 で主ループからは外れ、debug 検査専用に) |
| A9 | x_B ドリフト検査(5反復ごと)が毎回 m 長 `Vec` を2本確保 | — | `compute_rhs_affine_into` でバッファ再利用 |
| B1 | CHUZR が毎反復、実行不能行プール全体について `row_deviation`(`Affine1` の lex 比較2回+選択)を再計算 | `work_infeasibility[]` を x_B 更新時に保持し CHUZR は読むだけ | 逸脱量が変わり得る書き込み(x_B / basis / noise_feasible)は全て直後に `infeasible_rows.set/rebuild` を通るので、そこ (`cache_row_deviation`) で `row_dev[i]` に保存し CHUZR は読むだけ。debug ビルドでは毎反復、キャッシュが新規計算とビット一致することを assert |
| C1 | PRICE が行の**基底列**まで `a_p` を計算し、CHUZC で捨てていた(`touched_cols` 経由で CHUZC・双対更新・リセットの各ループも同じだけ長い) | `HMatrix` の行行列は「非基底 \| 基底」に分割され、基底交換で入る列・出る列の要素を境界越しに swap | 同じ分割行列 `PriceMatrix`(索引 u32 + 値の SoA)。出る列の `a_p` は PRICE と同じフィルタ・同じ加算順序(行昇順)で列から計算し直す。行内の要素順の入れ替えは「列を最初に触る順」しか変えず、各 `a_p[j]` の加算順序と CHUZC の候補順序(`(ratio, j)` の全順序)は不変 |

### 1.2 presolve の無駄

| # | 無駄 | 対応 |
|---|---|---|
| D1 | `reduce_equalities` の従属行検出 (`drop_linearly_dependent_sparse`) が、ピボットごとにピボット行が触れる全列の列最大値を丸ごと再走査(列の全要素について `BTreeMap::get`)。**maros-r7 で 3.32s 中 3.27s**、求解全体 4.7s の 7 割 | 列の要素が変わるのは「ピボット行が抜ける」「消去で書き換わる/生成・消滅する」だけで、`max` に丸めは無い。旧最大値を持っていた要素が小さくなった/消えた場合だけ再走査し、それ以外は `max(旧最大値, 書き込んだ値)`。heap の内容は全再走査と同一。debug ビルドで毎回全再走査と一致を assert し、NETLIB93 全問の presolve を debug ビルドで通した |
| D2 | `max_bipartite_matching` が**行ごとに** `vec![false; n_cols]` を確保・ゼロ化(O(p·n)、maros-r7 で 3135×9406)、DFS スタックも行ごとに確保。`dulmage_mendelsohn_blocks` の列→行が `HashMap`(SipHash) | エポック番号付き `visited` 1本とスタックの再利用、列→行は `Vec`。挙動は同一 |
| E1 | `csr_from_rows`(ほぼ全 presolve パスが行を書き戻すたびに呼ぶ)が faer の `try_new_from_triplets` 経由で、**既に列昇順の行**でも三つ組を作ってソートし直していた | 全行が列昇順・重複無しなら O(nnz) で直接 CSR を組む(三つ組経路が作るものと同一)。それ以外は従来経路 |
| E2 | 行/列の正規化シグネチャ `Vec<(usize,u64)>` の `HashMap`/`HashSet`(`reduce_inequalities` は presolve の**毎ラウンド**)が既定の SipHash | `crate::hash::FxHasher`(rustc の FxHash と同じ乗算・回転)。いずれも lookup 専用か、反復後にソートするテーブルなので結果は変わらない |

### 1.3 見送った案(理由つき)

| 案 | 見送り理由 |
|---|---|
| `reduce_equalities` の Markowitz 探索に候補上限(HiGHS `searchLimit`) | dfl001 で探索 260ms / 候補 43.8 万件と効きそうだが、ピボット順が変わると**どの従属行を落とすか**が変わり LP 自体が変わる。経路不変の変更と混ぜず別途検証すべき |
| `max_bipartite_matching` に貪欲初期マッチング / Hopcroft-Karp | maros-r7 で 75ms 残るが、マッチングが変わると DM ブロック分割(→ ブロックごとの従属行検出)が変わり得る |
| 従属行検出の `BTreeMap`/`BTreeSet` を LU カーネル同様フラット化 (§3.1 の `KernelMatrix` 相当) | D1 後は maros-r7 で 65ms、dfl001 は探索が支配的。大きな改修の割に残りが小さい |
| `Score2::new` の3回の割り算を `1/w` の乗算に | 丸めが変わり CHUZR のタイブレークが動く(経路変化) |
| x_B 更新・BFRT 反映の `0..m` 走査を FTRAN 結果の非ゼロ索引リストで(HiGHS の packed `HVector`) | `permute_out` に索引出力を足す必要がある。残る O(m) パスは各 FTRAN 自体にもあり、単独では小さい |
| U 段の hyper-sparse FTRAN | 既に2回計測して不採用 (`docs/lu_comparison_enomoto_vs_highs.md` §2.6) |
| rho が密なときの列方向 PRICE(HiGHS `choosePriceTechnique`) | 加算順序が変わる(経路変化) |
| 再分解時の `Vec<Vec>` 行リスト確保、`is_dense_input`/`detect_border_columns` の二重計算、再分解後の slope FTRAN(全ゼロ右辺) | いずれも O(nnz(B)) で再分解本体に比べ小さい |
| `CsrMat` の `(usize, f64)` AoS(16B/要素)→ u32 + f64 SoA | 影響範囲が広い。PRICE は C1 で SoA 化済み |
| `ColCache` の `Option<Affine1>` ×3 配列、`InfeasibleRows::pos` の `Option<usize>` | 効果は小さい見込み |

### 1.4 主ループ外の時間

基点で全93問を `ENOMOTO_PROF_PRESOLVE=1` で取ると(4並列なので絶対値は膨らむ):
`reduce_equalities` 合計 4.28s(うち maros-r7 3.45s、dfl001 0.39s)、
`reduce_inequalities(round)` 1.17s(pilot87 205ms、pilot 115ms、d2q06c 103ms)、
`propagate` 0.57s、`rebuild_g(inner)` 0.32s、`aggregator` 0.28s(dfl001 131ms) …。
D1/D2 で maros-r7 の presolve は 3.68s → 0.38s になった。

## 4. 今後の候補

§1.3 のうち、経路が変わるため本作業では混ぜなかったもの
(従属行検出の探索上限 — dfl001 で 260ms、DM マッチングの貪欲初期化 — maros-r7 で 75ms)
が次の候補。どちらも「落とす従属行の選び方」が変わるので、目的関数値の一致に加えて
presolve 後の行数が変わらないことを確認する計測が要る。
