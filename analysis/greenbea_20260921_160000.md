# greenbea `w_r.slope` 雑音判定の「比較時許容」化 プロトタイプ検証(自己改善ループ 反復#12, runtime 段) -- 結論: **本反復では見送り推奨**。格納値 `x_b_slope` を書き換えずに `row_deviation` / `bfrt_reached` の比較だけで |slope| < 閾値 を 0 とみなす変更は、閾値 3 段(2e-7 / 3e-7 / 1e-6)x 適用サイト 2 種(chuzr+BFRT / BFRT のみ)+ 更新側整合の変種 B 2 段の **9 変種すべてで greenbea の正答経路を失う**(168,620 反復 = `max_iters` バイアウト → BIG_M 誤答 -72465273.017、相対誤差 1.2e-3)。機序は「比較は slope=0 と見るが、ピボットの `theta_slope` と `x_B` 更新は格納された非零 slope で進む」不整合が **2 変数交互ピボット**(周期 2、同一の数値で 79,685 回反復)を作ること — `snap_slope`(格納値書き換え)がそもそも止めに行った現象そのもの。他問題(5 問題で詳細確認、全 93 問題で退行確認)では |w_r.slope| < 1e-3 の行が存在せず、この変更は完全な no-op

基点: `main` = 45cc904。前回分析: `analysis/greenbea_20260921_140700.md`(反復#9、snap の機序)、`analysis/greenbea_20260921_153000.md`(反復#11、タイブレーク変種、§4 候補 1 = 本反復の対象)。

## 0. 結論(要約)

1. **実装は可能で、変更箇所は 2 関数に閉じる**(§1)。`w_r` は `row_deviation`(`extended_dual.rs:1096-1128`)が返す deviation `hat_l - x_bi` / `x_bi - hat_u` そのものが chuzr → `best` → BFRT(`bfrt_reached`, `:759-768`)へ流れるので、deviation の slope に許容を当てれば chuzr の採点・`InfeasibleRows` の所属・BFRT の停止判定が一貫して「slope=0」を見る。格納値 `x_b_slope` は触らない。BFRT だけに効かせたい場合は `bfrt_reached` の入口で同じ関数を通す(`bfrt` サイト)。
2. **iter 6650 型の巨大フリップは、狙い通りには消えない**。iter 6650 の `w_r.slope = 1.670093e-7` は chuzr 時点の `x_b_slope[r] = -1.67e-7`(snap 閾値 1e-7 を 1.67 倍だけ超えた値)で、これを比較で 0 と見るには閾値 > 1.67e-7 が要る。ところが baseline の「選ばれた行の生 |w_r.slope|」は **連続分布**(§2.2: 1e-7 台 829 反復、1e-6 台 1,287、1e-5 台 2,671、1e-4 台 3,557、…)で、どの閾値も iter 6650 だけを切り出せない。閾値 2e-7 でも [1e-7, 2e-7) に 227 反復あり、経路は iter 2867 で分岐する(§4.1)。
3. **9 変種すべてが greenbea で誤答**(§3)。`m_enter_via_flip` は 10,205 → 347-511(変種 bfrt 1e-5 を除く)と激減するが、それは M 側解消が進んだからではなく **2 変数交互ピボットに落ちて M 側に触れなくなった**から(`remaining_m_side` が 478-1,347 のまま `max_iters` 到達)。変種 dev 2e-7 では iter 9248 以降 `(r=8, bv=3528, x_b=(-1.501077e3, +1.253214e-7), q=3647, alpha_q=-5.639e-2)` が **周期 2 で 79,685 回、7 桁まで同一の数値で再出現**する(§4.2)。
4. **機序**(§4.3): baseline はこの行を可行と見る(slope +1.25e-7 > 0 なので `x_bi = -1501 + 1.25e-7·M` は M→∞ で下限の上)。許容を入れると「slope は雑音、base -1501 は下限 100 の下で 1,601 不足」と見て選ぶ。しかしピボットの `theta_slope = (x_r.slope - target.slope)/alpha_q`(`:3096`)は格納値 1.25e-7 で計算されるので非零(-2.2e-6)になり、進入列の行には ±1 + 2.2e-6 級の slope、他行には `alpha_i·2.2e-6` が入る。次の反復で今入った列が同じ行から退出し、状態が **ビット同一**に戻る。停滞検出は「`contribution_slope != 0` は無条件に進捗」(`:3141`)と見るのでこの交互ピボットを stall と数えず、後から `bland_mode` が立っても比較の意味は同じなので同じ 2 本を選び続ける。これは `snap_slope` のコメント(`:647-650`)が「slope 優先比較が雑音 slope で 2 変数サイクルを作る」と書いたのと同じ現象を、比較と算術の役割を入れ替えて再現している。**比較と格納値の不整合そのものがサイクルの原因**であり、閾値の問題ではない。
5. **更新側も整合させる変種 B**(`theta_slope` も同じ許容で 0 に; 依頼の「格納値は書き換えない」枠の外、機序切り分け用)は交互ピボットを消す(`snapped` 82,197 → 1,076)が、今度は `x_b_slope` が `B^{-1}·rhs_slope` と一致しなくなり、ドリフト検査(slope 残差)が **22,958 回**(1e-6)/ `infeas_check` 再分解が **21,190 回**(2e-7)発火して同じくバイアウト(§3)。再分解が真の slope を戻し、また許容で消し、の往復になる。「比較だけ」「更新も」のどちらでも、格納値を書き換えない限り不整合は残る。
6. **他問題では no-op**(§5)。greenbeb / degen3 / d2q06c / fit1p / cycle は選ばれた行の生 |w_r.slope| が **0 か ≥1e-3 のどちらか**(1e-7〜1e-4 の桁は 0 反復)で、tol=1e-6 は dev/bfrt 両サイトとも反復数・`m_enter_via_flip`・目的値がビット同一。全 93 問題の tol=0 vs dev 1e-6 も §5.2 の通り。1e-7〜1e-5 の微小 slope が連続的に出るのは greenbea 固有で、**「x_B(M) の M 係数は厳密算術では 0 か order 1」という `snap_slope` の前提(`:647-650`)は greenbea では成り立っていない**(格納 `x_b_slope` の非零値 34,108 個のうち整数近傍は 256 個、§2.2)。
7. 3 分類は前回と同じ **(b) 反復数**が主因(27,654 vs HiGHS 2,524、11x)、(c) 1 反復 360 us vs ≤88 us が副因(§6)。本反復で試した経路は閉じたので、残る候補は §7: (1) M 側 3,569 列の双対フェーズ1化(反復#9/#11 と同じ、上限 70-85%)、(2) BIG_M フォールバックの安全策(9 変種すべてがこの経路で `optimal` を返している)、(3) 極小ピボット(|alpha_q| < 1e-7 が baseline で 6 回、iter 6650 は -1.5e-8)の相対許容 — いずれも 93 問題全数検証が必須。

## 1. 実装方針(依頼 1: コード読解の結果)

### 1.1 `w_r` の出所と比較箇所(main 45cc904 の行番号)

| 段階 | 行 | 内容 |
|---|---|---|
| deviation 計算 | `row_deviation` 1096-1128 | `x_bi = (x_b_base[i], x_b_slope[i])`、`hat_l = cache.lower[bv]`(`hat_lower` 893-903: slope は 0 か -1)、`hat_u`(slope 0 か +1)。`v_minus = hat_l - x_bi`、`v_plus = x_bi - hat_u` を `cmp_lex(ZERO)`(706-720、slope 相対 1e-9 → base 相対 1e-9)で「正なら実行不能」。**deviation の slope = ∓x_b_slope[i] + {0, ±1}** |
| chuzr | 2278-2308 | `row_deviation` の戻り `dev` を `Score2::new(dev, w_i)` で採点、`best = (i, d_dir, dev)` |
| `w_r` | 2369 | `let Some((r, d_dir, w_r)) = best` — **`w_r` は `row_deviation` の戻り値そのもの** |
| 雑音可行チェック | 2512 | `bfrt_reached(w_r, ZERO, x_b_base[r])` |
| BFRT pass 1 | 2639 / 2658 | `bfrt_reached(w_r, new_cum, x_b_base[r])`: slope が相対 1e-9 以上違えば slope で決定 |
| `InfeasibleRows` | 2548, 2695, 2825, 3103, 3432 | `row_infeasible_affine` = `row_deviation(...).is_some()` |
| ピボット算術 | 3093-3107 | `theta_slope = (x_b_slope[r] - target.slope)/alpha_q`(**格納値**を使う)、`x_b_slope[i] = snap(x_b_slope[i] - a·theta_slope)`、`x_b_slope[r] = snap(nb_val_q.slope + theta_slope)` |

したがって「`w_r.slope` の雑音判定を比較時許容に移す」最小実装は、`row_deviation` が `v_minus`/`v_plus` を作った直後に `|slope| < tol` なら slope を 0 に置いた **一時値**で比較・返却すること(格納配列 `x_b_slope` は不変)。`w_r` がその戻り値なので `bfrt_reached` 側に追加の変更は要らない。chuzr の行選択と `InfeasibleRows` の所属も同じ許容で変わる(= `dev` サイト)。行選択は baseline のままにして BFRT の停止判定だけ変えたい場合は `bfrt_reached` の入口で `w_r` に同じ置換をかける(= `bfrt` サイト)。

## 4. 失敗の機序

### 4.1 分岐点(A-dev 2e-7 vs baseline)

- baseline で |w_r.slope| ∈ [1e-7, 2e-7) の行が選ばれる反復は 227 回、最初は iter 2953。変種側で許容が効いた最初の反復は **iter 2867**(baseline より前)。dev サイトは `InfeasibleRows` の所属も変える(slope 微小・base 可行の行が可行に落ちる)ので、選ばれた行に現れる前からプールが違う。`WR_SLOPE` トレースが両者で一致する最後の反復は 2880 直前。
- したがって「閾値 2e-7 で iter 6650 だけを狙う」は成立しない。iter 6650 は分岐後の経路には存在しない(変種の iter 6650 は別の行 r=888)。

### 4.2 2 変数交互ピボット(A-dev 2e-7、`WR_SLOPE` トレース)

```
iter=9248 r=8 bv=3528 raw_slope=-1.253214e-7 x_b_slope_r=1.253214e-7 x_b_base_r=-1.501077e3 d_dir=1 w_r=(1.601073e3, 0) k_star=1 best_idx=1 n_cand=419 q=3647 ratio_q=4.081e-2 alpha_q=-5.639e-2 pool=412 remaining_m_side=1307

iter=9252 (同一)

```

- 許容が効いた 82,197 反復のうち **79,686 回が (r=8, bv=3528)、2,501 回が (r=888, bv=2070)**(後者は iter 4084 から周期 2)。相異なる行は 9、相異なる進入列は 8。プールは 407 で固定。
- 同じ構造は A-dev 1e-6(iter 14626 から (r=64, bv=6061) が 76,997 回、周期 2)、A-bfrt 1e-6(row 102 で bv 6019 と 1552 が各 4,326 回交互)でも観測。B 変種では `snapped` が減る代わりに再分解が毎反復近く発火する(§3)。

### 4.3 なぜサイクルになるか(コード)

1. 行 8 の基底変数 3528 は `x_B = (-1501.077, +1.253e-7)`、下限は有限(`hat_l.slope = 0`、base ≈ 100)。**baseline**: `v_minus = hat_l − x_bi = (1601, −1.253e-7)`、`cmp_lex(ZERO)` は slope −1.25e-7 (< −1e-9) を見て `Less` → **可行**(M→∞ で x_bi は下限の上)。**許容あり**: slope を 0 に置き `(1601, 0)` → `Greater` → **実行不能 1,601**、Score2 が大きいので選ばれる。
2. BFRT: `w_r = (1601, 0)` に対し k_star=1(1 本フリップ)、q=3647(|alpha| 0.056)で進入。
3. ピボット算術(`:3094-3107`)は **格納値** `x_b_slope[8] = +1.253e-7` を使う: `theta_slope = (1.253e-7 − 0)/(−0.0564) = −2.22e-6`。進入列の行 8 は `x_b_slope[8] = nb_val_q.slope + theta_slope`(q が M 側なら ±1 − 2.2e-6)、他行は `x_b_slope[i] −= alpha_i · theta_slope`(1e-6 級、snap 閾値 1e-7 を超えるので残る)。
4. 次の反復で今入った 3647 が行 8 から退出し 3528 が戻る(`alpha` 0.056 の逆ピボット)。`x_B` は **7 桁まで同一の値**に戻る(実測、§4.2)。base と slope の両方が元に戻るのは、この 2 ピボットが互いの厳密な逆で、丸めが再現的だから。
5. 停滞検出(`:3141`): `contribution_slope = theta_slope · dj_q ≠ 0` → 「非零 slope は無条件に進捗」→ `stall_count` は増えない(バイアウト時 `stall_count=0`)。プラトー検出(`:3187-3208`)で後に `bland_mode` が立つが、Bland でも `row_deviation` の意味は同じ(行 8 が実行不能、候補順は (ratio, j))なので同じ 2 本を選び続ける。
6. `snap_slope` のコメント(`:647-650`)は「slope 優先比較が丸め由来の slope で 2 変数サイクルを作る」と述べている。本変更はその対策(格納値を 0 にして比較と算術を一致させる)を、比較側だけ 0 にして算術側に非零を残す形にしたので、**同じサイクルが役割を入れ替えて復活した**。閾値をどう選んでも、比較が「0」、算術が「非零」である限り、この行に対する 2 ピボットは恒等写像になる。

### 4.4 変種 B が失敗する理由

`theta_slope` を 0 にすると 4. の逆ピボットは起きない(`snapped` 82,197 → 1,076)が、`x_b_slope` は「`B^{-1}·rhs_slope` の解」ではなくなる(算術的に一貫しない値を保持する)。ドリフト検査(`:3341-3370`、slope 残差)または `Eligible=empty`/BFRT 枯渇時の `infeas_check` 再分解(`:2537`, `:2684`)が発火 → `refactorize` + `solve_into` が真の slope(1e-7 級)を復元 → 次の反復でまた許容で 0 と見て `theta_slope=0` → 再分解、の往復(2e-7: 21,190 回、1e-6: 22,958 回、1 反復 1.7 ms に悪化)。格納値を書き換えずに整合を保つ方法は、更新側まで含めても存在しない。

## 8. 想定との食い違い(そのまま報告)

- 反復#11 §4 候補 1 の見積もり「iter 6650 型を止める、リスク中」は、**「止める」は経路上到達しないので検証できず、「リスク中」は過小評価**だった。閾値を 1.67e-7 のすぐ上(2e-7)に置いても分岐は iter 2867 で起き、正答経路を失う。
- 依頼の前提「絶対値が閾値未満なら 0 とみなして比較するが格納値は書き換えない、という変更が可能か」: 実装は可能(§1.2)だが、**比較と算術の不整合が 2 変数サイクルを生む**ため、この設計は greenbea では成立しない(§4.3)。更新側まで整合させても(変種 B)再分解との往復に置き換わる(§4.4)。
- `m_enter_via_flip` は 9 変種中 8 変種で 20-30 分の 1 に減った。数字だけ見れば依頼の検証項目 2 を満たすが、これは M 側解消が進んだからではない(`remaining_m_side` 478-1,347 で停止)。カウンタの減少を改善と読まないよう注意が要る。
- 全 93 問題の突き合わせで wood1p が「差分あり」に出たが、再実行で tol=0 同士でも 252 / 333 反復に割れた(§5.2)。main には少なくとも 1 問題で実行間の非決定性があり、「ビット同一」を退行判定に使うときは同一設定で 2 回走らせて自己一致を先に確かめる必要がある。今回の 91 問題ビット同一は 1 回ずつの比較なので、wood1p 型のばらつきを持つ問題が他にもあれば見落としている可能性はある(目的値の HiGHS 一致は 93 問題すべてで確認済み)。
- greenbea の格納 `x_b_slope` の非零値が全桁に連続分布していること(§2.2)は、反復#9 §1.5 の「LU/FT 更新の丸め由来の |slope| ~ 1e-8..1e-7」という説明より広い: 1e-6..1e-3 の slope が 11,000 個あり、これらは丸めではなく `B^{-1} N_M s` の本物の分数成分(または悪条件による増幅)。snap 閾値 1e-7 の感度(反復#9 §4)はこの連続分布の直接の帰結。
