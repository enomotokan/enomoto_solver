  HiGHS は根での再スタートとは別に、木のループの中で「木の全体のノード数の見積もりが大きく、ギャップが縮まない」ことが続くと前処理からやり直す。

- 同じ打ち切り値でも、HiGHS は 1445 ノードで 984079、ENOMOTO は 4481 ノードで 984025 (**ノードあたり約 3 倍の差**)。HiGHS は再スタートの
  後に伸びが速く (2851 ノード 985304 → 4471 ノード 986655)、ENOMOTO は 4500 ノードを過ぎると 1 万ノードで 350 しか上がらない。

  `TREEPAR`)。待ち行列からの取り出しが増えると (暫定解が良くなり潜りが早く刈られる) 1 秒あたりのノードが 25 前後まで落ちる (`t1` の 40 秒以降)。
  これはノードの速さの問題なのでセッション 3 に回す (ここでは手を付けていない)。

### 2.3 4 スレッドの木の構造 (共有の待ち行列に下界の低いノードがたまる)

- `tsb` の 123 秒の詳細ログ: 主スレッドの手元の下界 987874、開いたノード 996 (上限 1000) に対し、**共有の待ち行列が 20013 ノード**、全体の下界 983453。
- 仕組み (`src/mip/solver.rs`): 各スレッドの手元の待ち行列が `ENOMOTO_T_MIP_TREE_LOCAL_CAP` (1000) を超えると、超えた分を**下界の小さい順に**共有の
  待ち行列へ出す (`pool_donate_n`)。共有の待ち行列から戻るのは、手元が空のとき (`pool_acquire`) と釣り合い (`pool_balance`、32 ノードに 1 回、
  1 ノード) だけ。下界最小を取る番 (暫定解があれば 4 回に 1 回) は手元の中の最小しか見ない。→ 全体の下界を決めるノードが共有の待ち行列に何万も残り、
  各スレッドは手元の下界の高いノードを解き続ける。
- 1 スレッドの比べ (2.2) のとおり 1 スレッドでもノードあたりの効き目は HiGHS より弱いので、これは原因の一部 (4 スレッドの分を無駄にしている)。

|---|---|---|---|---|

| `def2` (既定、2 回目) | | 983005 | 983470 | 983855 |
| `bb1` | 暫定解があれば下界最小を毎回取る (`ENOMOTO_T_MIP_BB_EVERY_INC=1`) | 983061 | 983291 | 983708 |
| `sbh` | 強分岐の予算を HiGHS と同じに (`ENOMOTO_MIP_SB_BUDGET_HIGHS=1`、前からある試作) | 983553 | 983824 | 984333 |
| `tsb` | 試作 `ENOMOTO_MIP_TREE1_SB=1` (HiGHS の信頼性分枝: 予算 + 閾値 8) | 983130 | 983447 | 983667 |

- 1 スレッドでも `TREE1_SB` は悪い (`tsb1`: 120 秒で 982082、既定 1 スレッドは 984144)。強分岐を増やすと最初の 30 秒が強分岐で重くなり、その後も
  下界が伸びない。**分枝変数の選び方の強さ (強分岐の量・信頼の閾値) は、kasai の差の原因ではない**と見る。
- 下界最小を毎回取るだけ (`bb1`) は 4 スレッドでは悪くなる。手元の中の最小しか見ないので、共有の待ち行列に積もったノードは処理されないまま、
  各スレッドが手元の浅い部分を広げる (300 秒で開いたノード 3.3 万)。
- 効いたのは、共有の待ち行列を見ること (`tp`) と、木の中の再スタート (`tr`)、その組み合わせ (`trp`、ギャップ 0.45% → 0.20〜0.24%)。kasai の
  再スタートは新たな固定が 0 本でも効く: 再スタートの後の木は、学んだ擬似費用 (`RESTART_PC`) と良い暫定解・カットプールで始まり、最初の木
  (擬似費用のない間に上の方の分枝を決めた木) より伸びが速い。

## 4. 試作の中身 (どれも既定では使わない)

- `ENOMOTO_MIP_TREE1_POOL=1` (`Solver::tree1_pool_take`): 待ち行列から取る番のうち下界最小を取る番 (`NodeQueue::next_is_best`) では、共有の待ち行列の
  下界最小が手元の最小より小さければ、共有の待ち行列から取る。受け取りの記帳 (スレッドの下界・忙しい数) は `pool_acquire`・`pool_balance` と同じ。
- `ENOMOTO_MIP_TREE1_RESTART=1` (`Solver::tree1_restart_due`): HiGHS の `HighsMipSolver::run` の木の中の再スタートの判定を真似る。主スレッドが、
  全体のノード数が 1000 (`ENOMOTO_T_MIP_TREE1_RESTART_FIRST`) を超えてから 100 (`..._EVERY`) 増えるごとに、未処理のノードの重み (深さ d で 0.5^d、
  手元・ほかのスレッドが知らせた分・共有の待ち行列) から刈った割合 q を出し、前に数え直したときからの q の進みで全体のノード数を見積もる。
  r = (この求解の根の始めに自由だった整数列のうち、まだ自由な割合)^2 として、ギャップの縮み < 1 + 0.05/r かつ 見積もり >= 20 r × ノード数 なら
  「木が大きい」を数え、そうでなければ 0 に戻して数え直す。r (10 + 0.0005 × ノード数) × 1.5^(再スタートの回数) 回続き、暫定解があり、
  残り時間が時間上限の 0.1 倍以上、再スタートの回数が上限 (`ENOMOTO_T_MIP_MAX_RESTARTS`、4) 未満なら、従を止めて `maybe_restart` で前処理から
  やり直す (新たな固定の数の閾値は見ない。`=f` なら見る)。ほかのスレッドは 64 ノードごとに重みを知らせる。`ENOMOTO_MIP_TREE1_RESTART_LOG=1` で判定の途中を出す。
- `ENOMOTO_MIP_TREE1_SB=1`: 強分岐の予算を 100000 + 0.5 × ノードの LP の反復にし、信頼の閾値を `ENOMOTO_T_MIP_TREE1_MINREL` (8) に、予算の半分を
  超えたら 1 まで直線で下げる (HiGHS の `HighsSearch::branch`)。効かなかった (3 章)。
- 注意: 再スタートの回数の上限 4 は根の再スタート (早めの再スタートを含む) と共有。最初の版は r を全部の整数列に対して数えたため、再スタートで
  固定した列が増えるたびに判定が甘くなり、swath3 で 4 回を最初の 40 秒で使い切った (`tr_swath3`・`trp_swath3`、365.2・367.5)。今の版 (`trpb_swath3` 以降) は
  根の始めに自由だった列に対する割合。kasai の `tr`・`trp` は最初の版 (kasai は新たな固定が 0 本なので r は 0.79 → 1 の違い)、`trp2` は今の版。
- 木の重みの見積もりは粗い: ほかのスレッドの重みは 64 ノードごとの値で、共有の待ち行列との受け渡しの間に二重に数えることがある。csched008 では q が
  0 のまま (開いた重みの和が 1 以上) で、判定がいつも「木が大きい」になった。

## 5. 600 秒の確かめ (trp、4 スレッド、1 回)

既定は mitt600 の回 (`mitt600_20261103/res_s*.jsonl`) と、この機械での既定 (kasai は `def`、neos-933966 は `def600`)。

| 問題 | 既定 600 秒 | trp 600 秒 (`trp600_*`) | trp の再スタート | HiGHS |
|---|---|---|---|---|
| neos-3627168-kasai | 時間切れ、下界 984198 (mitt600)・984971 (`def`)、ギャップ 0.44%・0.37% | 時間切れ、下界 **986610**、ギャップ **0.20%** | 3 回 (固定 0 本、最初の 45 秒の間) | 最適 84〜94 秒 |
| swath3 | 時間切れ、下界 364.6、ギャップ 8.3% | **最適 270.0 秒** (`trpb_swath3` の 300 秒の回も **最適 196.6 秒**) | 4 回 (1 回目は根の早めの再スタートで 70 本、2〜4 回目が木の中で 1101・37・107 本。4 回目は始めから約 114 秒、その求解の主スレッドの 6446 ノード目) | 最適 157〜191 秒 |
| csched008 | 時間切れ、171 / 174 | 時間切れ、171 / **176** (悪い) | 4 回 (固定 0 本) | 最適 191〜197 秒 |
| fiball | 時間切れ、138 / 142 | 時間切れ、138 / 142 (同じ) | 4 回 (固定 0 本、最初の 85 秒の間) | 最適 112〜129 秒 |
| neos-933966 | 時間切れ、318 / 321 (mitt600)・318 / 368 (`def600`) | 時間切れ、318 / **6381** (悪い) | なし | 最適 298〜375 秒 |

- **swath3 が解けるようになった** (2 回とも)。HiGHS と同じく、木の中で固定がたまってから再スタートし、問題が小さくなってから閉じる。
- kasai は下界が上がる (ギャップ 0.37〜0.44% → 0.20%) が、300 秒と 600 秒でほぼ同じ所 (986.2〜986.6k) で止まり、閉じない。
- csched008 は固定 0 本の再スタートを 4 回して暫定解が悪くなった (再スタートのたびに木を捨て、根からやり直す)。fiball も固定 0 本の
  再スタートを 4 回するが結果は同じ。`=f` (固定の数の閾値を見る) なら csched008・fiball・kasai の再スタートは起きない (kasai の効き目もなくなる見込み、未確認)。
- neos-933966 は主側の揺れが大きい (既定でも 321 と 368)。trp の回は根のヒューリスティクス (試作の影響を受けない段階) が 41 秒に 6381 を出した後、
  木の中で良くならず、ノードも 1048 (既定 `def600` は 2812) と少ない。1 回では揺れと区別できないが、`TREE1_POOL` で共有の待ち行列から取る
  ノードは最初の LP が重い (2.2 節) ので、ノードが遅くなった分の影響はありうる。

## 7. まとめと次

- 原因 (担当の下界の 3 問):
  1. **木の中の再スタートがない**。HiGHS は kasai・swath3・csched008 の 3 問とも木の途中で再スタートし、その後の下界の伸びが速い。swath3 は
     木の中で固定がたまってから再スタートして問題を小さくするのが決め手で、試作 (`TREE1_RESTART`) で 2 回とも解けた。ENOMOTO の再スタートは
     根 (と暫定解が良くなったときの早めの再スタート) だけで、木に入った後は固定がたまってもやり直さない。
  2. **4 スレッドの木で、全体の下界を決めるノードが共有の待ち行列に積もる** (2.3 節)。4 スレッドは 1 スレッドの 4〜6 倍のノードを解くのに下界は
     ほぼ同じ。`TREE1_POOL` で kasai の 300 秒の下界が 983855〜984381 → 985429。
  3. 1 スレッド・同じ打ち切り値でも、HiGHS の再スタート前の時点で ENOMOTO の下界の上がり方は約 1/3 (2.2 節)。強分岐の量・信頼の閾値を HiGHS に
     そろえても良くならない (`TREE1_SB`・`SB_BUDGET_HIGHS`) ので、分枝変数の選び方の強さではない。残りの差 (ノードの LP の強さ・木の中のカット・
     伝播と衝突) は分けて調べていない。
  - fiball・neos-933966 は主側 (根の下界がすでに最適値。HiGHS は木の中のサブ MIP で最適解を出す)。
- 試作の効き目 (trp = `TREE1_RESTART` + `TREE1_POOL` + `RESTART_PC`): swath3 が解ける (196.6・270.0 秒)、kasai のギャップ 0.37〜0.44% → 0.20%
  (閉じない)、csched008 は悪い (固定 0 本の再スタート 4 回で暫定解 174 → 176)、fiball は同じ、neos-933966 は 1 回では揺れと区別できない悪化。
  58 問は 6 章。
- 既定は変えない。
- 次:
  - 木の中の再スタートは固定 0 本でも起きる今の判定が csched008・fiball で損。HiGHS は再スタートの後の根の下界が大きく上がる (kasai: 970736 →
    984177) のに、ENOMOTO の再スタートの後の根は 970455 程度にしか上がらない (効いているカットしか持ち込まない、根のカットのループの違い)。
    固定 0 本のときは再スタートしない (`=f`) か、HiGHS のように再スタートの後の根を強くするかを決める。
  - セッション 4 が同じ形の `ENOMOTO_MIP_TREE4_RESTART` を入れている (rebase で `maybe_restart` の判定がぶつかったので、両方の強制を通すように
    直した)。木の重みの見積もり (二重に数える問題、4 章) を含めて 1 つにまとめる。
  - `TREE1_POOL` は共有の待ち行列から取るノードの最初の LP が重い (約 300 反復) ので、取り出しの速さ (セッション 3) と合わせて見る。
- テスト: `cargo test --release --lib` は 332 通過・1 失敗・18 ignore。失敗は `mip::tests::fix_tiny_width_columns_fixes_within_tolerance` で、
  この記録の変更ではなく、`ENOMOTO_MIP_MEM3_TINY_MARGIN` を既定にした変更 (ae1497cc 以降) とテストの期待値の食い違い
  (`ENOMOTO_MIP_MEM3_TINY_MARGIN=0` なら通る)。
- 計測のビルドは aaf30e0a + この記録の変更 (rebase の前)。rebase で入ったほかのセッションの変更は計測に入っていない。
