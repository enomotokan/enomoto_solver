# greenbea 再分解ブロックの単価内訳分析(自己改善ループ 反復#10, runtime 段) -- 単価増(5.3→9.4 ms/回)は Markowitz LU 1 段だけの増加で、原因は「コードが遅くなった」のではなく「再分解時の基底が密になった」こと。経路を変えない高速化余地は LU 内部の `col_max_abs` 遅延再計算(実測 -12〜-14%/再分解ブロック、全体 -2.8%)が最大で、非 LU 5 ステップは合計 3% なので該当なし

対象: NETLIB `greenbea`(2392 行 x 5405 列, 30,877 非零)。4 コア。
基点: `main` = 1d7a772。比較対象: 反復#7 の基点 418e62a(再分解単価 5.3 ms/回だった時点)。
前回分析: `analysis/greenbea_20260921_140700.md`(反復#9)。同分析 §1.2 の「再分解 2,262 ms / 241 回 = 9.4 ms/回、主ループの 22.7%」の**内訳**を取るのが本反復の目的。

全数値はこのセッションでこのコンテナ上で実測。worktree ごとに `CARGO_TARGET_DIR` を分け、`PYTHONPATH=<worktree>/python` で `_core` を切り替え、各実行で `_core.__file__` を stderr に出して取り違えがないことを確認した(§7)。計測用の一時パッチ(§7 の `patch_prof*.py`)は worktree 上だけに当て、リポジトリには残していない(作業後に worktree ごと削除)。推定で埋めた箇所はそう明記する。

## 0. 結論(要約)

1. **再分解ブロック 6 ステップのうち、時間の 97% は (1) `refactorize` = Markowitz LU 分解**(main: 2,262 ms / 2,332 ms)。残る 5 ステップ((2) `compute_rhs_affine` 0.7%、(3) `solve_into` x2 0.7%、(4) `snap_slopes` 0.0%、(5) `infeasible_rows.rebuild` 0.5%、(6) `fresh_d_into` 1.1%)は合計 70 ms(3.0%)で、**全部をゼロにしても全体時間の 0.7%** にしかならない。「`rebuild`/`fresh_d_into` が密に全走査している」のは事実(§2.2)だが、単価 48 us / 108 us で無視できる。**非 LU ステップの高速化は該当なし。**
2. **単価が上がったのは LU 分解 1 段だけ**(418e62a 5.67 ms → main 9.39 ms、+66%)。他の 5 ステップは同じかむしろ安い(§2.1: `compute_rhs_affine` 66→64 us、`rebuild` 47→49 us、`fresh_d_into` 88→108 us)。問題サイズはむしろ**縮小**している(m 2,056→1,985、n_total 6,701→6,446)ので、サイズ比例では説明できない。
3. **LU 単価が上がった機序は「基底行列の疎性低下」であり、分解コードの単位コストは変わっていない**(§3)。再分解 1 回あたりの基底非零数 nnz(B) が 7,195→10,280(+43%)、L+U の fill が 6,414→11,307(+76%)。基底中のスラック本数で層別すると、**同じ層では両ビルドの LU 単価が一致する**(スラック ≥1000 本: 4.13 vs 4.30 ms、500-999 本: 7.77 vs 8.04 ms、<500 本: 10.09 vs 11.36 ms)。違いは層の分布で、main は 241 回中 179 回(74%)が「スラック <500 本 = 構造列主体の密な基底」の時期に起きるのに対し、418e62a は 58 回中 5 回(9%)。418e62a の層別単価に main の層分布を掛けると 9.0 ms/回になり、実測 9.4 ms の 96% を説明する。つまり**反復数が 4.2 倍に伸びて「密な基底で走る後半」が長くなり、その後半でドリフト再分解が集中した**(前回分析 §1.3 の「93 回は再分解から 10 反復以内」)結果であり、fill-in の質(Markowitz の選択)や実装が劣化したのではない。
4. **経路(ピボット選択・目的関数値)を一切変えない高速化余地**(§5):
   - **(A) `MarkowitzState::refresh_column` の `col_max_abs` 再計算を遅延化**(`src/simplex/lu.rs:323-331` と `:350-399`)。現状は `eliminate` が触った列ごとに毎回 `col_rows[j]` 全体(BTreeSet 走査 + BTreeMap `get`)で列最大値を再計算するが、計測では **1,668,920 回の再計算のうち 1,255,273 回(75%)は一度も読まれずに次の再計算で上書きされ**、実際に安定性検査で読まれるのは 413,647 回(25%)、必要な演算量は 13.6M → 1.84M(13.5%)。「dirty フラグを立てて `find_best_pivot` の安定性検査で初めて読むときに再計算」に変えると読まれる値は完全に同じ(同じ集合・同じ値の max、順序非依存)。**scratch worktree で試作して実測**: 再分解ブロック 2,230-2,258 ms → 1,935-1,990 ms(**-12〜-14%、約 -280 ms**)、全体 wall 約 -2.8%。ピボット列・fill 系列(241 回すべての iter / l_nnz / u_off)・反復数・再分解回数・目的値がビット同一(§5.1)。リスク: 低(`lu.rs` 内 2 関数、`find_best_pivot` を `&mut self` にする)。
   - **(B) ピボット探索の空振り**(`find_best_pivot`、再分解ブロックの 33%): 同一バケット内で「勝者が決まった後にも走査した列」が全走査の 15.5%(6.46M / 41.6M 列)だが、勝者は「同点なら |v| が大きい方」で決まるため、後続列を厳密に安全に飛ばせる条件(行次数下限 r_min による `best_score < (r_min-1)(deg-1)`)は **0 回**しか成立しない。経路不変のままでは上限 1.2%(全体)で、実装可能な厳密ルールも見つからなかった → **該当なし**(HiGHS 型 `searchLimit=8` は経路を変える、§5.3)。
   - **(C) `refactorize` の `rows` 構築**(`extended_dual.rs:955-962`、79 ms = 0.8%)を `std.rows` 全走査(31.6k 非零)から基底列だけの `std.cols` 走査(10.3k 非零)に変える案: 上限 0.5%、行内の要素順が変わるので bordered 経路(`factorize_bordered`)を使う他問題ではビット同一の検証が要る。効果が小さく優先度低。
   - **(D) 非 LU 5 ステップ: 該当なし**(合計 3.0%、§2.2)。
5. 本反復の範囲外だが数値で裏付いた事実: 再分解**頻度**は HiGHS 並み(本ソルバ 1 回 / 115 反復、HiGHS 1 回 / 57 反復(44 回 / 2,524 反復、うち 37 回は synthetic clock))で、単価だけが問題。単価の根本は BTreeMap/BTreeSet ベースの Markowitz(fill 1 個あたり約 0.8 us: `lu_us ≈ 267 + 0.807 x (l_nnz+u_off)`、R²は高い、§3.2)にあり、これは `docs/lu_comparison_enomoto_vs_highs.md` §3.1 の既知事項。フラット配列化や HiGHS 型 `rebuild()`(前回ピボット順の再利用)は LU のピボット順や丸めが変わりうるので「経路不変」の枠外(§5.3)。

## 1. 計測方法

- 6 ステップ内訳: `extended_dual.rs` の 4 か所ある再同期ブロック(`grep -n "lu = refactorize(std, &basis_pos)?;"` → 2543 / 2690 / 3011 / 3419 行、いずれも同一の 7 行)の各行を `Instant` で個別計時し、`ENOMOTO_PROF_REFACTOR_BREAKDOWN=1` で 1 回ごとに `REFACTOR_BREAKDOWN iter=.. lu_us=.. rhs_us=.. s1_us=.. s2_us=.. snap_us=.. reb_us=.. d_us=.. nnzB=.. l_nnz=.. u_off=.. n_slack_basic=..` を出力、`PROF_PHASES_EXT` の report 末尾で合計 `REFPROF` を出力(一時パッチ `patch_prof.py`)。`refactorize` 内部も `rows` 構築 / `factorize_diagonal` 試行 / `factorize` / `FtLu::new` に分割。
- LU 内部: `lu.rs::factorize_flat_markowitz` を `MarkowitzState::new` / `find_best_pivot` / snapshot / `eliminate`(さらに entry ループ / `pi_cols` / `refresh_column` ループ)/ 組み立てに分割計時し、探索の走査量(列・行・BTreeMap lookup 数、到達バケット次数)、`eliminate` の作業量(affected 行数、entry 操作数、fill-in 数、touched 列数)、`refresh_column` の「無駄」(読まれる前に上書きされた回数)を計数(`patch_prof2.py` / `patch_prof3.py` / `patch_prof4.py`)。
- 計測は main / 418e62a とも 3 回ずつ(最初の 1 回は最小計装、2 回目以降は計装追加)。計装のオーバーヘッドで再分解ブロックは 2,332 → 2,480-2,660 ms に膨らむが、**ステップ比率と作業量カウンタは実行間で完全に同一**(決定的)。計装なし pristine ビルドの再分解時間は 2,230 / 2,235 / 2,258 ms(前回分析の 2,262 ms と一致)。

### 3.3 なぜ main は密な時期に再分解が集中するか(前回分析との接続)

- main は 27,654 反復のうち iter 4,000 以降(スラック <500 本の密な時期)が 23,600 反復あり、その期間のドリフト再分解が 179 回。418e62a は 6,602 反復で終わり、密な時期は 700 反復弱。**反復数 4.2 倍(前回分析の主因 = M 側スラッシング)が、再分解の「回数」だけでなく「1 回の重さ」も押し上げている**。再分解単価の問題は反復数の問題の従属変数であり、独立の劣化ではない。
- コードの差分(418e62a..1d7a772)で `lu.rs` が変わったのは BTRAN の U^T 段 hyper-sparse 化(反復#7)と `solve_transpose_unit_into` 追加、テスト追加のみ(`git diff 418e62a..HEAD -- src/simplex/lu.rs`)。Markowitz 部分は無変更で、層別単価の一致がそれを裏付ける。

## 5. 経路を変えない高速化余地

「経路を変えない」= LU の**ピボット順・fill・計算順序を一切変えない**(x_B, d, DSE 重みの丸めまでビット同一)ことを条件にした。この問題は前回分析 §4 の通り snap 閾値 1 桁で正答/偽 infeasible/誤答が飛ぶほど経路依存なので、LU のピボット順を変える最適化(§5.3)は本反復の候補から外す。

### 5.1 候補 A(推奨): `col_max_abs` の遅延再計算 — 実測で -12〜-14% / 再分解ブロック、ビット同一

**機序(該当行)**: `MarkowitzState::eliminate`(`lu.rs:412-479`)は各ステップの末尾で `touched_cols`(平均 3.5 列)の各列に `refresh_column`(`lu.rs:323-331`)を呼び、次数/バケットの更新に加えて **`col_max_abs[j]` を `col_rows[j]` 全走査(BTreeSet iter + 各行 BTreeMap `get`、平均 8.2 演算)で再計算**する。この最大値は `find_best_pivot` の安定性検査 `v.abs() < STABILITY * col_max_abs[j]`(`lu.rs:376`)でしか読まれない。計測(main、241 回合計):

| | 回数 / 演算数 |
|---|---|
| `refresh_column` 呼び出し | 1,668,920 回 / 13,618,121 演算 |
| うち max が実際に変わった | 288,718 回(17.3%) |
| うち**読まれる前に次の `refresh_column` で上書きされた(無駄)** | **1,255,273 回(75.2%)** |
| 安定性検査で実際に読まれた(必要) | 413,647 回(24.8%)/ 1,840,553 演算(**13.5%**) |
| 分解終了時に未読のまま残る | 0 回(= 最後まで使われない列の再計算も無駄に含まれる) |

**同一結果である理由**: `col_rows[j]` と `rows[i][j]` の値が変わる場所は `eliminate` 内だけで、変えた列は必ず同じ `eliminate` の末尾で `touched_cols` に入り `refresh_column` される。したがって「`refresh_column` 時点の max」と「次に `find_best_pivot` が読む時点の max」は同じ集合・同じ値に対する max であり、`f64::max` の fold は順序非依存(NaN なし)なので値はビット同一。dirty フラグ方式(`refresh_column` は `max_dirty[j]=true` だけ、`find_best_pivot` の安定性検査直前で dirty なら再計算)に変えても、探索が読む値・比較結果・選ばれる `(i,j)` は完全に同じ。次数/バケット更新(`update_col_degree`)は従来通り即時のまま。

**試作の実測**(scratch worktree、pristine 1d7a772 に `patch_lazy.py` を当てただけ、計装なし。各 3 回):

| 主ループ wall | 9,911.7 / 9,853.4 / 9,956.3 ms | 9,660.1 / 9,950.7 / 9,578.2 ms(-2.8% 平均、ばらつき ±1.5% と同程度) |

### 5.2 候補 C(効果小): `refactorize` の `rows` 構築を基底列だけの走査に

`extended_dual.rs:955-962` は `std.rows` の全非零(31.6k = nnz(B) 10.3k + 非基底 21.3k)を走査して `basis_pos` で篩う。`basis` の各列の `std.cols.row(j)` を走査すれば 10.3k で済む。79 ms(全体 0.8%)のうち推定 50 ms 削減(全体 0.5%)。ただし各行内の `(col, v)` の並び順が「元の列番号順」から「基底位置順」に変わる。`MarkowitzState::new` は BTreeMap に詰め直すので順序非依存だが、`factorize_bordered`(greenbea では使われない: `bordered_tried=0`)は `rows_in` を直接走査する箇所があり、他問題でビット同一かどうかは別途確認が要る。優先度低。

### 5.3 該当なし(経路不変の条件を満たさない、または効果が小さすぎる)

| 案 | 計測 / 理由 |
|---|---|
| `find_best_pivot` の走査打ち切り(HiGHS `searchLimit=8`、`docs/lu_comparison_enomoto_vs_highs.md` §2.5) | 探索は再分解ブロックの 33%(全体 7.5%)と大きいが、勝者決定後の走査は 15.5%(列)/16.6%(行)しかなく、さらに勝者は「同 score なら |v| 最大、同 |v| なら先着」なので後続列を厳密に飛ばせる条件(`best_score < (r_min-1)(deg-1)`)は **0 回**しか成立しなかった。上限 1.2%、厳密ルールなし。`searchLimit` はピボット順を変える → 経路不変でない。 |
| HiGHS 型 `rebuild()`(前回ピボット順の再利用、同 §2.2) | 探索 33% + `MarkowitzState::new` 8% を丸ごと飛ばせる可能性があるが、直前と異なる基底(5-10 反復で数列入れ替わる)に旧ピボット順を当てるので数値(丸め)が変わる。経路不変でない。 |
| BTreeMap/BTreeSet のフラット配列化(同 §3.1) | fill 1 個 0.8 us の根本原因だが、`col_rows` の走査順(行番号昇順)が変わると同 |v| の先着ルールで別ピボットになりうる。順序を保つ実装(ソート済み Vec)なら経路不変だが大規模改修。 |
| 非 LU 5 ステップ((2)-(6)) | 合計 3.0%(70 ms)。§2.2。 |
| `FtLu::new`(3.3%)/ L,U 組み立て(2.3%)/ `MarkowitzState::new`(7.8%) | 各々 O(nnz) の詰め替え。`new` の BTreeMap 構築は `entry().or_insert` の逐次挿入で、ソート済み一括構築にすれば多少速いが、上限 1.8%(全体)。 |
| 再分解の回数削減(ドリフト閾値) | 前回分析 §4 の通り経路が壊れる。対象外。 |

## 6. 想定との食い違い(そのまま報告)

- 依頼文の原因候補「問題サイズ自体の変化」は逆方向(m, n_total とも 3-4% 縮小)で、単価増を説明しない。
- 依頼文の「`rebuild` や `fresh_d_into` が疎構造を使わず密に全走査していないか」は事実だが、両者で 1.6%(37 ms)しかなく、反復#6/#7 型の「同じ結果をより安く」の対象としては該当なし。支配的なのは Markowitz LU 本体(97%)。
- 「基底行列の疎性低下(fill-in 増)」は当たりだが、正確には「fill 比(Markowitz の質)はほぼ同じで、入力 nnz(B) が増えた」。入力が増えたのは反復数増で密な基底の時期が長くなったからで、LU 単価は反復数問題の従属変数。
- 候補 A の全体効果は約 3% と小さい。再分解ブロック全体でも 22.7% が上限で、greenbea の 44 倍差を動かすのはやはり反復数(前回分析の候補 2: M 側列の双対フェーズ 1 化)。
