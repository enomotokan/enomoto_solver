# greenbea 実行時間分析(自己改善ループ 反復#4, runtime 段)

対象: NETLIB `greenbea`(2392 行 x 5405 列, 30,877 非零; `.netlib_cache/mps/greenbea.mps`)。
選定理由(`scripts/select_problem.py`): runtime 段、`ours 3.1034s vs highs 0.2555s (ratio 12.15x)` -- 正答している 93 問題中で最悪の比。
正答性は反復#2(PR #3)で解決済み: 本セッションでも両者 `optimal`、目的関数値 ours -72555248.12985753 / HiGHS -72555248.12984587(相対差 1.6e-13)。
対象コミット: `3c56c2d`(main)。HiGHS 1.15.1(`highspy`)、4 コア。全数値は本セッションでこの環境で実測したもの。推定値はその旨明記する。

作業開始時、ワーキングツリーには `src/simplex.rs` / `src/simplex/extended_dual.rs` に未コミットの `TMP_PROF` 計測パッチ(「temporary, to be reverted」と自己申告されたもの、486 行)が残っていた。内容が本分析に必要な計測(ドリフト検査の内訳、再分解の内訳、1 反復あたりの非零数、`ENOMOTO_TMP_*` 実験スイッチ)そのものだったので、scratchpad に退避(`preexisting_tmp_prof.patch`)した上でそのまま計測に使い、さらに `src/simplex/lu.rs` にピボット探索の形状カウンタを一時追加した。計測後に `git checkout` で 3 ファイルとも HEAD に戻し、HEAD のホイールを再インストールして基準時間を再確認した(直接呼び出し 3.02/3.04 s、ハーネス 3.10 s vs HiGHS 0.254 s = 12.19x: 計測用ビルドと同じ)。**コード変更はツリーに残っていない**。

## 結論(要約)

**分類: (c) 1 反復が重い。** 主ループ 6,601 反復で 431 us/反復(HiGHS 83 us/反復、5.2 倍)。そのうち **35.5%(1,010 ms / 2,845 ms)が「基底の健全性維持」コスト** -- 5 反復ごとの `x_B(M)` ドリフト検査 544 ms(19.1%、`extended_dual.rs:3138-3195`)と、それが起こす再分解 466 ms(16.4%、58 回 x 8.1 ms、`refactorize` `:902` → `sparse_lu::factorize` `lu.rs:876`)-- で、HiGHS はこの種の残差検査を持たない。残る 64.5%(核となる btran/price/chuzc/ftran/DSE 更新)も HiGHS 比 1.8 倍だが、突出した 1 項目はない。

- **presolve 不足ではない(実測で棄却)**: HiGHS は 2392→951 行(-60%)、本ソルバは 2392→2056 行(-14%)と縮約率は大差だが、**HiGHS が presolve した LP(951 x 2989)をそのまま本ソルバに渡しても 2.87-2.91 s(元問題 3.01 s から 5% しか縮まない)**。本ソルバの時間は問題サイズにほとんど依存していない。
- **反復数は同サイズ比較で 3.5 倍(8,889 vs 2,524)、元サイズ比較で 1.3 倍(6,601 vs HiGHS presolve off 5,109)**。副次要因として存在するが、退化(退化ピボット 0.2%)・DSE 誤差(99.6% が 1% 未満)・停滞(`stall_count=0`)のどれでもなく、extended dual の M 側解消の進み方(3,715 列 → 1,171 列 @ iter 6000)という設計レベルの話で、最小差分では触れない。
- ドリフト検査の中身: `residual_norm`(`:930`)を base/slope の 2 チャネル分、**全 A の非零 32,474 個を `basis_pos` でフィルタしながら 2 回走査**している(1,318 回 x 248 us = 327 ms)。基底列だけを列方向に 1 回走査すれば非零 7,195 個で済む。ツリーに残っていた実験スイッチ `ENOMOTO_TMP_FAST_RESID` がまさにそれで、**同一ピボット経路(1,318 回の判定が全て一致、目的関数値ビット一致)のまま 3.01 s → 2.72 s(-9.6%)**、他 8 問題でも 7-28% 短縮・全問題同じ最適値。
- 再分解の中身: `factorize` 7.2-7.9 ms/回のうち **ピボット探索(`find_best_pivot`, `lu.rs:349`)が 3.9 ms(50%)**、消去 2.4 ms(30%)。基底は fill がほぼ無い(L 2,054 + U 6,507 非零 vs A_B 7,195)のに、1 ステップあたり平均 33.5 列・95 個の BTreeMap 要素を調べている(バケット全走査後にしか早期終了しないため)。`lu.rs:113-125` の「ピボット探索はボトルネックではない(全体の 0.2% 未満)」という注記は greenbea には当てはまらない(全体の 6.7-7.6%)。

### 1.3 ドリフト検査の挙動(`ENOMOTO_DEBUG_XB_DRIFT_EXT=1`)

- 1,318 回の検査、57 回発火(全て base チャネル; slope の残差は全検査を通じて最大 4.6e-10 で、閾値 1e-8 に届いたことは一度もない)。
- エスカレーション梯子(`XB_DRIFT_TOL` `:594`, 10 回ごとに x10, 上限 1e-4): 閾値 1e-8 で 129 回検査 / 10 発火、1e-7 で 79 / 10、1e-6 で 157 / 10、1e-5 で 151 / 10、**上限 1e-4 で 802 回検査 / 17 発火**(iter 2,709 以降は上限に張り付き)。
- 発火間隔: 最小 5、中央値 60、平均 97、最大 970 反復。最後の 2 回(iter 5,921 / 5,926)は 5 反復しか離れておらず、残差 9.7e-4 → 再分解 → 1.0e-3 で即再発火。
- **残差は丸め誤差支配**: 行方向 2 回走査(現行)と列方向 1 回走査(実験)で同じ量を計算すると、相対差は最大 **0.84**(1e-6 桁の残差で)、1e-5 桁でも 0.37。x_B が 1e6-1e8、係数が最大 1e2 なので和の項は 1e10 に達し、1e-4 の絶対残差は 1e-14 相対、すなわち加算順序の丸めそのもの。上限 1e-4 での 17 回の発火はこの雑音を「ドリフト」として拾っている(反復#1 の分析が指摘した「絶対閾値と 1e6-1e8 の基底値のミスマッチ」の時間面での現れ)。ただし判定(発火する/しない)は greenbea では 1,318 回とも両方式で一致した。

3 分類への落とし込み(いずれも実測):

1. **presolve 不足 → 棄却**。縮約率の差は大きい(HiGHS が 1,441 行落とすのに対し 336 行)が、HiGHS 縮約後の LP を渡しても本ソルバは 5% しか速くならない(3.01 → 2.87 s)。行数が 2,056 → 993 に半減しても反復数は 6,601 → 8,889 に増え、1 反復は 431 → 322 us にしか下がらない。HiGHS 自身は presolve で 3.0 倍(0.765 → 0.256 s)速くなるが、本ソルバでは効かない。
2. **反復数過多 → 副次要因**。同サイズなら 3.5 倍(8,889 vs 2,524)。ただし元サイズでは HiGHS presolve off(5,109)の 1.3 倍で、DSE・BFRT・Harris は正常に機能している(§1.5)。差は extended dual の M 側解消(HiGHS の dual phase 1 に相当; HiGHS は DuPh1 1,244 反復で終える)の設計に由来すると考えられ(推定)、最小差分の対象ではない。
3. **1 反復が重い → 主因**。元サイズで 5.2 倍(431 vs 83 us)、HiGHS presolve off と行数を揃えても 2.9 倍(431 vs 150 us)、HiGHS の presolved LP 上でも 3.8 倍(322 vs 84 us)。全体比 11.8x ≈ 反復数 2.6x x 1 反復 5.2x x 0.87(finish・presolve の差)と整合する。

## 3. 機序(該当ソースを読んだ上での説明)

### 3.1 ドリフト検査(`src/simplex/extended_dual.rs:3138-3195`)-- 主ループの 19.1%

5 反復ごと(`XB_CHECK_INTERVAL = FT_CHECK_INTERVAL = 5`, `:545`; 古典経路は `FT_CHECK_INTERVAL * RESIDUAL_CHECK_MULTIPLIER = 100` 反復ごと、`simplex.rs:303,320`)に:

1. `compute_rhs_affine`(`:965`): 非基底列全体を走査して右辺 2 チャネルを作る。O(nnz(A_N))、63 ms。
2. `residual_norm`(`:930`)を base と slope で **2 回**呼ぶ(`:3154-3155`)。各呼び出しは `std.rows` 全 2,056 行・32,474 非零を走査し、非零ごとに `basis_pos[j]`(`Option<usize>`)を引いて基底列だけ拾う。すなわち 1 回の検査で 64,948 個の非零アクセス + 64,948 回のランダムな `basis_pos` 参照。**327 ms(検査 1 回 248 us)**。基底列は 2,056 本・非零 7,195 個しかないので、`basis`(位置 → 列番号)から `std.cols.row(j)` を列方向に 1 回走査すれば両チャネル同時に 7,195 個で済む(9 分の 1)。
3. 発火しなければ `fresh_d_into`(`:1135`, BTRAN 1 回 + 全列の O(nnz) 内積)で d のドリフト検査(`:3185`)。143 ms。

1 回の検査 413 us は 1 反復(431 us)とほぼ同じ重さで、5 反復に 1 回なので平均 20% の上乗せになる。HiGHS には対応する検査が無く、`updateVerify`(行/列 2 通りのピボット値比較; 本モジュールにも `pivot_grossly_inconsistent` として一部存在)と synthetic clock による定期 rebuild で代替している。

間隔を緩める(`ENOMOTO_TMP_XB_CHECK_INTERVAL=10/20`)と 2.45 s / 2.00 s と速くなるがピボット経路が変わり(5,991 / 5,732 反復)、`XB_CHECK_INTERVAL` の docs(`:524-544`)にある通り間隔 50 では cycle/degen3 が誤 infeasible になった記録がある。梯子と連動して間隔を広げる実験(`ENOMOTO_TMP_XB_INTERVAL_LADDER=3`)は 26,804 反復・18.2 s で反復上限に達し BIG_M フォールバックの**誤答**(-72465273.02、反復#1 分析の欠陥 (C))に落ちた。**間隔・閾値を触る変更は低リスクではない**。走査方法だけを変える変更(§4)は判定を変えない。

### 3.2 再分解(`src/simplex/lu.rs:876-994`)-- 主ループの 16.5%

`refactorize`(`extended_dual.rs:902`)は行ごとに基底列を集めて(`build_rows` 0.3 ms)`sparse_lu::factorize` を呼ぶ。`factorize` は境界列検出(1 列も無い)→ `factorize_flat_markowitz`(`lu.rs:902`)。この実装は活性部分行列を行ごとの `BTreeMap<usize,f64>`、列ミラーを `BTreeSet<usize>` で持ち(`MarkowitzState`, `:142-197`)、各ステップで `find_best_pivot`(`:349`)が列次数の小さいバケットから順に列を取り、その列の活性行ごとに `rows[i].get(&j)`(O(log d) の木探索)で値を引いて安定性閾値(`STABILITY=0.25`)と Markowitz スコアを評価する。早期終了は「スコア 0 を見つけた列の直後」か「バケットを最後まで走査してから `best_score <= deg^2`」のみ。greenbea の基底は列次数 3-4 が主体で列シングルトンが尽きやすく、行シングルトン(スコア 0)を探すためにバケットの列を順に舐めるので、1 ステップ平均 33.5 列・95 要素になる。2,056 ステップ x 95 = 約 19.5 万回の BTreeMap 探索 / 再分解。

`lu.rs:113-125` の注記(「`ganges`/`ship12s`/`stocfor2`/`fit1p` で探索時間は全体の 0.2% 未満、三角化前処理は不要」)は greenbea では成立していない: 探索 203-229 ms = 全体の 6.7-7.6%。fill が無い基底で 7.2-7.9 ms は、HiGHS が 951 行の基底を 43 回 rebuild して求解全体が 0.21 s である(1 回あたり多く見積もっても 1-2 ms)ことと比べて遅い。

### 3.3 核フェーズ(残り 64.5%)

`dse_update` 51 us(tau が 61% 密)、`btran` 44 us、`price` 42 us(走査 8,002 非零/反復、固定列判定 447 回/反復)、`chuzc1` 38 us(候補 521)、`ftran` 29 us。行数比で見ると 272 us / 2,056 行 = 0.13 us/行 に対し HiGHS presolve off は 150 us / 2,392 行 = 0.063 us/行(rebuild 込み)で約 2 倍。hyper-sparse でない(rho 25%、tau 61%)ので HiGHS の hyper-sparse 経路の恩恵はどちらも小さく、差は実装定数と見られる(推定; 個別には未追跡)。

## 5. 根本原因の分類

**(c) 1 反復が重い。** 内訳の筆頭 2 項目は、HiGHS が行っていない `x_B(M)` ドリフト検査(19.1%)と、その検査が起こす 8 ms/回の再分解(16.5%)で、合わせて主ループの 35.5%(solve 全体の 33.5%)。

- ドリフト検査は (i) 5 反復ごとという古典経路の 20 倍の頻度で、(ii) 1 回が 1 反復と同じ重さ(413 us)で、(iii) そのうち 60% が「全 A を 2 回走査して基底列を選り分ける」という走査方法の非効率(`residual_norm` `:930`)、26% が d の再計算(`fresh_d_into` `:1135`)。(i)(ii) を変えるのは過去の記録と本セッションの実験の両方で危険(§3.1)、(iii) は判定を変えずに直せる(§4)。
- 再分解は回数(HiGHS より少ない)ではなく単価(7.2-7.9 ms、fill ゼロの 2,056 行基底)の問題で、半分は `find_best_pivot` の走査(`lu.rs:349`)、残りは BTreeMap ベースの消去。
- presolve は実測で棄却(HiGHS の presolved LP でも 5% しか変わらない)。反復数は同サイズで 3.5 倍あるが設計由来(M 側解消)で、退化・悪条件・DSE・停滞のいずれでもない。
- 摂動 base の差(HiGHS 5e-5 vs 反復#1 記録の 1.58e-6)は未検証の候補(推定)。

## 6. 改善候補(優先順、効果見積もりつき)

1. **ドリフト検査の残差を基底列の列方向 1 回走査で計算する**(`src/simplex/extended_dual.rs`: `residual_norm` `:930` の置き換え、呼び出し側 `:3154-3155`)。具体的には `fn residual_norm_both(std, basis: &[usize], x_b_base, x_b_slope, rhs_base, rhs_slope, scratch_base: &mut [f64], scratch_slope: &mut [f64]) -> (f64, f64)` を追加し、`for (pos, &j) in basis.iter().enumerate() { for &(i, v) in std.cols.row(j) { sb[i] += v * x_b_base[pos]; ss[i] += v * x_b_slope[pos]; } }` の後に `‖sb - rhs_base‖`, `‖ss - rhs_slope‖` を取りつつスクラッチをゼロ戻しする。スクラッチ 2 本(長さ m)は `fd_cb`/`fd_y` と同じくループ前に 1 度確保する(`:1600` 付近)。`basis` は同関数内で既に `fresh_d_into` に渡している `Vec<usize>` そのもの。旧 `residual_norm` は他に呼び出しが無ければ削除。
   効果(実測): greenbea 3.01 → 2.72 s(-9.6%、比 11.8x → 10.7x)、他 7 問題で -5..-27%、正答性・最適値は不変。
   リスク: 加算順序が変わるので残差の値は丸めレベルで変わり(相対差最大 0.84)、他問題では発火判定が変わり得る(A/B で greenbeb/pilot がそれ; どちらも良化・同値)。93 問題スイープでの確認が必須。ビット一致を優先するなら「行方向のまま両チャネルを 1 パスで計算」(`std.rows` を 1 回だけ走査し `basis_pos` 参照も 1 回)という変種もあり、こちらは判定が完全に不変だが削減は約半分(推定 -140 ms; 未計測)。
2. **`find_best_pivot` に行シングルトンの O(1) 経路を足す**(`src/simplex/lu.rs:349-390`)。列バケット走査の前に `row_buckets[1]` を見て、活性な次数 1 の行 i があればその唯一の要素 (i, j) を、安定性条件 `|v| >= STABILITY * col_max_abs[j]` を満たす限り即座に返す(スコア 0 で現行の選択基準と同格; 行シングルトンのピボットは fill を一切起こさない)。HiGHS `buildSimple()` の行シングルトン剥がしに相当。
   効果(推定): 探索 203-229 ms(solve の 6.7-7.6%)が上限で、現実的には -4..-6%。
   リスク: ピボット順が変わり丸めが変わる → 経路が変わる問題が出る。安定性条件を外さないこと。93 問題スイープ必須。
3. (中リスク・本反復では非推奨)`fresh_d_into` による d ドリフト検査(143 ms, 4.7%)の頻度を `RESIDUAL_CHECK_MULTIPLIER` 相当に落とす。pilot4 の誤 infeasible 対策として入った検査なので、pilot4 を含むスイープなしには触れない。
4. (設計変更・別反復)ドリフト検査そのものを、丸め支配の絶対残差ではなく後退誤差相対(`‖A_B‖ ‖x_B‖` スケール)または HiGHS 型 `updateVerify` + synthetic clock に置き換える。`XB_DRIFT_TOL` docs(`:553-593`)にある 4 回の失敗記録の通り単一ノブでは決まらないので、本反復の最小差分には含めない。同じく `factorize` の BTreeMap ベース活性行列の置き換え(現状 fill ゼロの基底で 7-8 ms)は大きな改修。
5. (設計変更・別反復)反復数(同サイズで 3.5 倍): extended dual の M 側解消と HiGHS の dual phase 1 の比較、摂動 base の差の検証。
6. 診断: `PROF_PHASES_EXT` の報告にドリフト検査の時間(本分析で 19.1%、既存報告では「未計上」に隠れる)と `factorize` 内訳(探索/消去)を常設すると、この切り分けが一発でできる。`lu.rs:113-125` の「探索はボトルネックではない」注記は greenbea の数値で更新すべき。
