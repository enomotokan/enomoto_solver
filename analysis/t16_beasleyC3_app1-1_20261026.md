# beasleyC3・app1-1: 16 スレッドで HiGHS に解けて ENOMOTO に解けない件 (2026-10-26)

- 依頼: 手元 PC の 16 スレッドで、beasleyC3 と app1-1 を HiGHS は解き ENOMOTO は解けない。
- 環境: 専用コンテナ 4 CPU (`nproc` = 4)。ソルバーは同時に 1 つだけ動かした。コード: 2134cef (このブランチ)。HiGHS 1.15.1。
- 16 スレッドの再現: 診断用の `ENOMOTO_MIP_DIAG_HW_THREADS=16` で CPU の数の上限を外し、4 CPU に 16 本を詰め込む (下の名前 hw16)。
  CPU の数の上限を外さずに 16 を渡すと 4 本に頭打ちになる (`max_threads`、ログの `tree search with 4 threads`。名前 def)。
- 台本: `runs/bc3t16/run.py <名前> <回> <秒> [ENV=VAL ...]` (スレッド数 `TH`、既定 16、問題 `PROB`、既定 beasleyC3)、
  `runs/bc3t16/highs.py <回> <秒>`、要約 `runs/bc3t16/summ.py`。ログは `runs/bc3t16/logs/`。

## 0. 要約

- **このコンテナでは再現しない**: 16 本を詰め込んでも ENOMOTO は両方とも毎回解けた (下の表)。app1-1 は HiGHS より速い。
- **実機 16 コアの条件はここでは作れない**。詰め込みは「1 本あたりの速さが 1/4 の 16 本」であって、16 本が本当に同時に走る条件
  (共有の待ち行列・カットのプール・暫定解の錠の取り合い、メモリ帯域、SMT) は再現できていない。
- 実行中のスレッドを数えると、木の探索の間に同時に走っている (状態 R) のはちょうど 16 本 (全 39 本のうち残りは待機)。
  **ENOMOTO 自身が 16 コアを超えて CPU を取り合うことはない** (16 論理コア = 8 物理コア + SMT なら 1 本あたりは遅くなる)。
- 前回の app1-1 の調査 (`analysis/app1-1_20261020.md`) でも、手元 PC の 16 スレッドは −1 で時間切れ、詰め込みの 16 本は 19.6・28.5 秒で
  解けていた。**手元 PC の方が「1/4 の速さの 16 本」より悪い**ので、1 本あたりの遅さだけでは説明できず、本当の同時実行でだけ
  起きること (錠の取り合いなど) か、手元の版・設定の違いが疑わしい (推測、確かめていない)。

## 2. beasleyC3 の 16 本 (詰め込み) で遅くなる所 (確かめた事実)

- 根の経路は 5 回とも同じ (前景のカットの後 725.64 → 背景 751.23、根のヒューリスティクスの後 776 (1.2 秒の LP face))。4 本の def_2 も
  同じ経路 (751.18・776)。4 本の他の回は根でリスタートが入った別経路 (736.40、5.5 秒で 758)。経路の違いは前の調査
  (`analysis/beasleyC3_r3_20261020.md`) と同じ揺れで、スレッド数が直接決めているのではない。
- **同じ経路での違いは、776 から先の暫定解の改善**:
  - 4 本 (def_2): 主スレッドの木の RINS がノード 56 (9.8 秒) で 762 (サブ MIP 0.70 秒・197 ノード)。755 (14.9 秒)、754 (17.9 秒)。
  - 16 本 (hw16_1): 主スレッドの木の RINS のサブ MIP が **1.29 秒で時間切れ・15 ノード・807** (改善なし)。次の改善は 28.3 秒 (別スレッドの丸め 763)。
  - サブ MIP の時間の上限は壁時計 (`solve_submip_problem`: 残り時間 × `submip_time_frac`、上限 `submip_time_max`) なので、
    1 本あたりの CPU が減るとノードが進まないまま切れる。これは詰め込みの影響で、実機 16 コアでは起きないはず (推測)。
- ヒューリスティクス役 (16 本では 4 本) は起動の判定 (限界効用) を通らず、38 秒過ぎまで動かなかった (`ENOMOTO_MIP_HEUR_ROLE_VERBOSE=1`、
  hw16v_1)。4 本の回も役は動いておらず、改善は木のノードの丸め・RINS から。
- 16 本の回でだけ「a generated cut cuts off the incumbent (rejected)」が出た (hw16_1 108 回、hw16_2 10 回)。安全確認で捨てているので
  答えは変わらない。局所的にだけ正しいカットを大域の暫定解で確かめて捨てている可能性がある (確かめていない)。

## 3. 手元 PC で取ってほしいもの

原因を絞るには、手元 PC の 16 スレッドのログが要る。

1. 機種: 物理コア数・論理コア数 (SMT の有無)、OS、使ったコミット。
2. 既定のログ (60 秒):
   `ENOMOTO_MIP_LOG=1 python runs/bc3t16/run.py t16 1 60` (beasleyC3)、`PROB=app1-1 ENOMOTO_MIP_LOG=1 python runs/bc3t16/run.py t16 1 60`
   (`.miplib_cache/<問題>.mps.gz` が要る)。
3. 切り分け (同じ台本で `TH` と環境変数を変える):
   - `TH=4` と `TH=8`: スレッド数で悪くなるのか。
   - `TH=16 ... ENOMOTO_MIP_NO_HEUR_ROLE=1`: ヒューリスティクス役の有無。
   - `TH=16 ... ENOMOTO_MIP_HEUR_ROLE_VERBOSE=1`: 役の起動と成果。
- 見るもの: `tree search with N threads` の N、根の経路 (前景・背景のカットの後、根のヒューリスティクスの後の暫定解)、
  暫定解の推移、`sub-MIP:` の行のノード数と時間 (時間切れでノードが少なければ、サブ MIP が CPU を取れていない)。
