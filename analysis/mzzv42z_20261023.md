# mzzv42z: HiGHS との差 (依頼 F、2026-10-23)

環境: 4 CPU のクラウドのコンテナ。ソルバーは同時に 1 本。土台は inv/heur-ls-20261023 の 7f0d7c3。4 スレッド・60 秒。
HiGHS 1.15.1 (highspy、threads=4・mip_rel_gap=0)。
台本: `analysis/mzzv42z_20261023/base.sh <回数> <接尾辞> [ENV=VAL ...]` (既定と mixoc を交互に回す)・`run_highs.py`。
ログ: `analysis/heur_ls_20261023/logs/mzzv42z_{def,mixoc}{,_ref,_rr,_gr,_grtb}_<n>.log` (この調査のものは def 3〜5・mixoc 1〜3 と接尾辞つき全部。
def_1・def_2 は前からあったもの)、HiGHS は `analysis/mzzv42z_20261023/logs/h_1.log`。

## 結論

1. **足りないのは主に解 (主側)、とくに再スタートの後の 25〜35 秒が空回りしていること** (事実)。既定・mixoc の 6 回とも、60 秒の値は
   根のヒューリスティクスの後 (22〜31 秒) の暫定解と同じだった。6 回中 5 回は再スタートし、再スタートで暫定解が新しい問題の上で実行不能になって捨てられ (`the start solution is not
   feasible in the presolved problem; dropped`)、暫定解なしとして Feasibility Pump (10〜18 秒) とカット前の LP の RENS (実行不能) に
   時間を使い、木にはほとんど入らない (0 ノード)。再スタートしない 1 回 (def_5) も 36 ノードで良くならない。
2. 再スタートの前の値を決めるのは根の RENS (暫定解なし用) が崩れるかどうか (r4 と同じ): 2 段目の LP が実行不能で固定率 0.29〜0.37 に
   戻ると、サブ MIP が 0 ノードのまま 16 秒時間切れになり、locks → RINS で -18880〜-20294 にしかならない (6 回中 4 回が崩れた)。崩れなければ -20490〜-20500。
3. 下界は HiGHS より 50〜130 弱い (ENOMOTO -20722〜-20803、HiGHS -20674) が、HiGHS も 60 秒では閉じない。60 秒で効くのは解の側。
4. **手当て: `ENOMOTO_MIP_GR_RESTART=1`** (r4 の試作 (inv/mzzv42z-r4-20261021) をこの土台に移した。一般整数のある問題だけで
   再スタート前の暫定解を参照解として残して再スタート後の RINS の相手にし、背景のカットの後の LP で丸めと RINS をもう一度回す)。
   60 秒の値 (3 回ずつ): 既定 -20270 / -20490 / -18880 → **-20540 / -20480 / -20470**、mixoc -20500 / -20294 / -20060 →
   **-20450 / -20500 / -20500**。最悪の回が 2 組とも大きく良くなり (既定 -18880 → -20470、mixoc -20060 → -20450)、既定の 1 回は
   HiGHS と同じ最適値 -20540 に届いた (証明はなし)。60 秒で最適を証明するところまでは届かない。
5. 既定にする候補か: **候補** (親の 40 問 + 16 問の計測で決める)。働くのは一般整数が 1% 以上の問題だけ。qnet1・mik-250-20-75-4 を
   1 回ずつ見て、どちらも最適値は同じで時間も変わらない (qnet1 4.0 → 3.5 秒、mik-250 9.8 → 9.2 秒)。r4 の副作用の計測
   (一般整数のある 10 問を 2 回ずつ) でも誤った最適値は 0。

目的値の不一致 (HiGHS の最適値と違う「最適」) はこの調査では 0 回。

## 2. 下界と解のどちらが足りないか (事実)

- **下界**: HiGHS はカット後 -20769.6 → 再スタート後 -20674.4。ENOMOTO は根のカット後 -20867〜-20892、背景のカットの後 -20764〜-20802、
  再スタート後の根 -20722〜-20803。HiGHS より 50〜130 弱い。ただし HiGHS も 60 秒で閉じない (ギャップ 0.65%) ので、60 秒の結果を
  分けるのは下界ではない。
- **解**: HiGHS は根のカットの直後の RENS (前処理で列が 35% 少ない問題の上) 1 回で最適値 -20540 を出す (37.8 秒)。
  ENOMOTO は最良でも -20500 で、再スタートの後は 1 回も良くならない (上の表)。足りないのは解の側。
- 推測: HiGHS の RENS が 1 回で最適値に届くのは、前処理後の問題 (列が 4737 本少ない) の上の近傍だから。ENOMOTO の前処理は
  1024 列しか減らさない。この差は今回も調べていない (r4 と同じく未解明)。

## 3. 試した手当て (各 2〜3 回、60 秒の値)

| 設定 | 既定 | mixoc | 下界 (範囲) |
|---|---|---|---|
| なし | -20270 / -20490 / -18880 | -20500 / -20294 / -20060 | -20722〜-20803 |
| **`GR_RESTART=1`** | **-20540 / -20480 / -20470** | **-20450 / -20500 / -20500** | -20680〜-20758 |
| `GR_RESTART=1` + `TREE_ROOT_BASIS=1` | -20500 / -20450 | -20500 / -20380 | -20720〜-20805 |
| `RESTART_REF=1` + `BG_CUTS_REHEUR=rins` (土台にある切り替え) | -20500 / -20480 (※) | -20500 / -20460 | -20713〜-20803 |
| `RENS_RETRY=1` (この調査の試作) | -20000 / -20260 | -20370 / -20430 | -20731〜-20844 |

※ def_ref_2 は計測中に `cargo check` を走らせてしまった回 (CPU を取り合った)。

- `GR_RESTART` で何が起きるか (def_gr_1): RENS -19890 → RINS -20300 (24 秒) → 背景のカットの後の RINS (`[tree]`) -20340 → 再スタート →
  再スタート後の根の RINS が参照解 (再スタート前の暫定解) を相手に **-20540** (再スタートから 10.3 秒)。RENS が崩れた回
  (def_gr_2・mixoc_gr_1・mixoc_gr_2) も、背景のカットの後の RINS で -19970〜-20410 に戻り、再スタート後の RINS で -20450〜-20500。
  再スタートの後に暫定解のない Feasibility Pump に時間を使わない。
- `GR_RESTART` と `RESTART_REF + BG_CUTS_REHEUR=rins` は、mzzv42z では中身がほぼ同じ (GR は一般整数のある問題に限るだけと、
  2 回目以降の再スタートで暫定解がなければ参照解を次に渡す r4 の修正)。2 回目の再スタートは GR の 3 回で起きた。
- `TREE_ROOT_BASIS` (木の従の根の LP を主の基底から解く。r4 の「従が根の LP で時間切れなら下界 +inf」は土台の `root_fail_bound` に
  入っているので、移したのは基底の受け渡しだけ) は上乗せの効果が見えない。
- `RENS_RETRY` (`src/mip/heuristics.rs` の `dive_neighbourhood`。段の LP が実行不能で戻ったとき、LP を解き直し、列の順を混ぜ直し、
  段の幅を半分にしてやり直す): 固定率は 4 回とも 0.80 まで進むようになったが、サブ MIP が実行不能 (def_rr_1・def_rr_2) で解が
  出ない回があり、しかも再スタートの後の空回りは残るので、60 秒の値は良くならない (既定は悪くなった)。候補にしない。

## 4. 確かでない点

- 回数は 2〜3 回ずつ。主張は「2 組 (既定・mixoc) とも同じ向き」の、最悪の回が良くなった (既定 -18880 → -20470、mixoc -20060 → -20450)
  と、値の範囲が狭くなった (既定 1610 → 70、mixoc 440 → 50) こと。最良の回の差 (既定 -20490 → -20540、mixoc は -20500 で同じ) は言えない。
- 副作用は qnet1・mik-250-20-75-4 を 1 回ずつ見ただけ (r4 では一般整数のある 10 問を 2 回ずつ見て誤った最適値 0。ただし r4 は
  別の土台 (develop 34e55d0))。GR が働くのは `implbd_genint_for` が真の問題だけ。
- 60 秒で最適を証明するには、HiGHS 並みの下界 (前処理の差が大きいと推測) が要る。今回は手を付けていない。
