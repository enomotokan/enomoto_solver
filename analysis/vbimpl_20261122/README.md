# VB_IMPL (プロービングの含意を連続列の変数上下限に使う) を既定にしない理由の確かめと、木での使い方を絞る試作 (2026-11-22、利用者の依頼・案 B)

**閉じた (2026-11-22、利用者の判断)**: `ENOMOTO_MIP_VB_IMPL` と試作 `t` は既定オフのまま。

試作 `ENOMOTO_MIP_VB_IMPL` (src/mip/separation.rs の `separate`): プロービングの含意 `y = v ⇒ x_k <= b` / `x_k >= b` (y は 0-1 列、x_k は連続列) を、
cmir・経路の集約などの変数上下限 (VUB/VLB) に足す。unitcal_7 の根の下界の SCIP との差を埋めると記録されていた (slow2_20261117 §9、aggrsel_20261121)。

## 0. 結論

- **VB_IMPL も新しい試作 `t` も既定に勧めない。P の分担表は作らない。** 8 問 × 種 1〜3 (4 スレッド) で vb/def 1.045 [0.946, 1.143]、vbt/def 1.056 [0.894, 1.210]。
  unitcal_7 は 3 種の平均で vb 1.00・vbt 0.98 と、根の下界の伸びが時間に出ない。
- 遅くなる元は 2 つ (§3): 1 ノードの手間が増える (rocI-4-11 +37%・timtab1 +30%・kasai +11%) のと、ノードが増える (tr12-30 +30%・neos-1456979 +28%)。
  木の分離で含意を絞る `t` でも 1 ノードの手間はほぼ同じ (rocI 7.16 ms 対 vb 6.89 ms・def 5.02 ms) なので、重さは木の分離の手間ではなく、根で含意から作った
  カットが LP に残ることから来ていると見る (推測)。
- **誤答の件は VB_IMPL と無関係** (§1)。traininstance6 では VB_IMPL が足す変数上下限は 0 本 (含意はどれも 0-1 列どうし) で、VB_IMPL があってもなくても同じ道筋。
- 過去の「速い 5 問・遅い 8 問」の大半は VB_IMPL が何も足さない問題で、比は揺れ (§2)。

## 3. 試作 `ENOMOTO_MIP_VB_IMPL=t` と比べ (既定では使わない)

- 1 ノードの手間 (3 種の時間の和 / ノードの和): rocI-4-11 def 5.02 / vb 6.89 / vbt 7.16 ms、timtab1 0.91 / 1.18 / 1.05、kasai 1.73 / 1.92 / 2.37。
  ノードの数: tr12-30 50.3 万 / 65.1 万 / 58.8 万、neos-1456979 2.7 万 / 3.4 万 / 4.9 万。unitcal_7 は 1 ノード 59.8 / 48.8 / 49.7 ms (vb が軽い) でノード 1.27 / 1.19 倍。
- 読み: 木で含意を絞っても (`t`) 1 ノードの手間は vb と同じ程度に重く、ノードの増え方も変わらない。重さは木の分離ではなく、根で含意から作ったカットが

- 次に試すなら (推測): 根で含意の変数上下限から作ったカットを、根の終わりに LP から外す (プールに残す) 形、または `r` (外側の根だけ) の P の計測。
  ただし今回の unitcal_7 で根の下界の伸びが小さく (§2)、時間にも出ないので、優先は低い。
