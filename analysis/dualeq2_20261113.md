# DUALEQ2: binkar10_1 の害の仕組みと、DUALEQ の入れ直し (2026-11-13)

課題: DUALEQ (`ENOMOTO_MIP_DUALEQ`、双対の議論で不等式行を等式にする。src/mip/mod.rs の前処理の最後) は束 cand1113 にあったが、
binkar10_1 が 4 種そろって 1.45 倍になったので cand1114 で外した (analysis/cand1114_20261113/README.md)。記録 (cand1113 の loo.md) の見立ては
「1 列を消すだけで根の切除平面の打ち切り (mpsep gate) が 13 周目まで遅れ、ノードが増える」。この見立てを確かめ、カットのループの打ち切り側で直せるかを試す。

ビルド: ブランチ ccr-1beed81b-ex0uhq (このセッションのコミット)。機械は 4 コア、ソルバーは同時に 1 つ (4 スレッド)。
`c14` = cand1114 (analysis/cand1114_20261113/cfg.py)、`c14d` = c14 + `ENOMOTO_MIP_DUALEQ=1`。

## 結論

1. **害の大部分は、根のカットのループの停滞の判定が前処理の定数項 (offset) の置き方に左右されること** (DUALEQ の縮約そのものではない)。
   - 停滞の判定 (SCIP 式、目的値の相対変化 ≤ 1e-4) は offset を除いた内部の目的値で割る。binkar10_1 の c14 は内部の値が 1.005e6
     (offset −9.986e5、利用者の値 6.7e3) なので、1 周に 0.1% 伸びても相対変化 4e-6〜1.4e-5 で毎回停滞と数え、主のループは 6 周で止まる。
   - DUALEQ は R804 `C792 + C2147 ≥ 1` (C792 は連続 [0,1]、C2147 は 2 値。費用はどちらも約 1e6 の罰金) を等式にし、かけ直しが
     `C792 = 1 − C2147` を代入する。費用 1e6 が打ち消し合って約 1e6 が offset に移り、内部の値が 5.2e3 になる。すると判定が本来の尺度になり、
     主のループは 25 周の上限まで、**サブ MIP (RENS・根の被約費用・LP face など) の中のループも一部が 25 周**回る。根のヒューリスティクスの段が
     約 1〜2 秒延び (RENS のサブ MIP 0.29 → 1.62 秒、ノードは同じ上限)、木に入るのが遅れる。
   - 証拠: 試作 `ENOMOTO_MIP_STALL_SCALE=u` (offset 込みの目的値で割る、4. 節) を c14 に付けると、DUALEQ なしでも c14 自身が 8.9〜10.1 秒になる
     (c14 は 5.8〜7.7 秒、種 1〜4)。木に入る時刻 1.4〜1.8 → 3.5〜3.6 秒、木の時間はほぼ同じ。サブ MIP の中のループ (`ENOMOTO_MIP_DEBUG_CUTEXIT=s`、種 2):
     既定は 13 回のうち 12 回が 5〜7 周で停滞と数えて止まり、`u` は 15 回のうち 4 回が 24〜25 周回る。外側だけ (`uo`)・サブ MIP だけ (`us`) でも
     8.2〜9.1 秒で、両方が効いている。
   - 主のループだけを長くしても遅くならない: c14 を停滞で止めずに 25 周回しても (`ENOMOTO_T_MIP_CUT_STALL=100`、サブ MIP には効かない)
     6.2〜6.5 秒 (ノード 1.8〜1.9k)。c14d の主を 6 周で止めても (`ENOMOTO_T_MIP_CUT_ROUNDS=6`) 7.7〜8.3 秒 (3.7〜4.1k)。
     記録 (cand1113 の loo.md) の「mpsep gate が 13 周目まで遅れる」は、分離の多点 (MPSEP) の門のことで打ち切りではなく、どちらも mpsep は 0 周。
   - つまり binkar10_1 の c14 の速さは、offset が大きいために停滞を早く数えてしまう誤った判定に支えられている。
2. **残り (約 1.15〜1.4 倍) は等式にした構造の差**。尺度をそろえた (`u`) 回: c14u 8.9〜10.1 秒・2.6〜3.0k ノード、c14d + u 10.9〜13.7 秒・3.6〜5.2k。
   前処理の後の問題を等式にする前 (`_pre`) と後 (`_eq`) で MPS に書き出し (`ENOMOTO_MIP_DEBUG_DUMP_DUALEQ`、定数項は書き出されないので
   どちらも内部の値は 1.005e6。ただし `_eq` はかけ直しの代入でまた 1e6 が offset に移る) DUALEQ なしで解くと:

   | 設定 | `_pre` (秒・ノード) | `_eq` (秒・ノード) |
   |---|---|---|
   | c14 種 1〜4 (4 スレッド) | 7.0・6.9・6.3・6.2 秒 / 2.2〜2.5k | 10.5・10.5・10.3・11.2 秒 / 3.8〜4.6k |
   | def 種 1・2 | 6.1・7.0 秒 / 1.4k・1.6k | 8.0・8.3 秒 / 2.6k・2.4k |
   | c14 − RCSTRONG 種 1・2 | 6.4・6.5 秒 / 2.3k・2.5k | 13.4・9.9 秒 / 5.0k・3.9k |
   | c14 種 1〜3 (**1 スレッド**) | 22.0・18.2・17.4 秒 / 2359・1839・1799 | 23.3・24.1・20.2 秒 / 2036・2244・1819 |

   1 スレッドではノードの数はほぼ同じ (時間 +6〜32%)。4 スレッドでノードが 1.7 倍になるのは、根が長く (木に入る時刻 1.7〜1.8 → 2.8〜2.95 秒)、
   最適解を見つけるのが遅れる (種 1〜3 で 4.2〜6.6 秒 → 5.9〜6.9 秒、いずれも木の中の別スレッド) ことと、スレッド間の分担 (渡したノード 4〜29 → 69〜192)
   の差が重なったもの。代入で R273 `C791 + C792 − C1517 ≤ 1` が `C791 − C1517 − C2147 ≤ 0` (2 値の入った変数上界の形) になり、C2147 の費用が
   1e6 → −8.32 になる。LP の緩和は同じで、根の下界もほぼ同じ (6715.3〜6716.5 と 6716.1〜6717.2)。
3. **停滞の判定の尺度は DUALEQ と独立の不具合候補** (offset の大きさで打ち切りが変わる)。試作 `ENOMOTO_MIP_STALL_SCALE` (既定では使わない):
   `u` = offset 込みの目的値 (利用者の目的値) で割る、`m` = 内部の値と offset 込みの値の小さい方、`o`・`s` を足すと外側だけ・サブ MIP の中だけ。
   裏のカット (BG_CUTS_DETERM の窓) はもともと offset 込みの値で測っている。binkar10_1 では `u` は 1.4 倍の害 (上)。58 問の結果は 6 節。
4. **比較用の門 `ENOMOTO_T_MIP_DUALEQ_MINRED` = f** (既定 0 = 見ない。本命にはしない: 1 問の悪化を見て縮約を手前で止める門なので):
   DUALEQ のかけ直しで減った行・固定でない列の割合の大きい方が f 未満なら等式の問題を使わない。binkar10_1 は 0.0012、neos-960392 0.043・
   beavma 0.031・flugpl 0.133・neos859080 0.25。58 問を前処理だけ回すと、f = 0.01 で cand1114 と前処理が変わるのは beavma・flugpl・neos-960392 の 3 問だけ。
   種 1〜6 (c14 / c14 + DUALEQ + f=0.01、秒): binkar10_1 7.66/6.70・6.15/6.15・7.31/7.02・5.78/5.97・6.43/7.17・6.85/6.40、
   beavma 0.32〜0.55 / 0.32〜0.40、flugpl 0.12 / 0.11〜0.13、neos-960392 1.60〜1.94 / 1.47〜1.89。効きも害も見えない (DUALEQ の効きは示されていない)。

## 6. 58 問 × 種 1・2 (c14 と c14 + STALL_SCALE=u、`dualeq2_20261113/run.py`、`res_P.jsonl`)

60 秒・4 スレッド、58 問 × 種 1・2 = 116 対 (crash 0、目的値の食い違い 0)。`python summ.py` で集計。

- SGM (shift 1、どちらかが解けた 45 問、ブートストラップ 4000 回): c14u / c14 = **+0.5% [−3.4%, +4.9%]**。
- 解けた数: c14 88 / c14u 87。noswot は種 1 で c14 だけ時間切れ・種 2 で c14u だけ時間切れ (入れ替わり)、
  timtab1 種 2 が c14 46.4 秒 → c14u 時間切れ (種 1 は 1.00 倍)。
- 種をそろえて遅い (両種で比 > 1.25) のは **binkar10_1 だけ** (1.58・1.50 倍)。ほかの比の大きい問題 (neos5 2.25/1.14、
  nu25-pr12 2.31/0.94、10teams 1.46/0.84、mc11 1.64/0.74、noswot 0.48/1.83 など) は種で向きが変わり、ゆらぎの範囲。
  58 問のうち 26 問は両種とも ±10% 以内。
- DUALEQ の 4 問 (秒、種 1/種 2): binkar10_1 c14 6.40/7.04・c14u 10.08/10.59・c14ud 10.89/13.55・c14dg 6.60/5.93、
  beavma・flugpl・neos-960392 はどれも 0.1〜2.2 秒で差なし。
- `m` (内部の値と offset 込みの値の小さい方) は binkar10_1 では offset 込みの方が小さいので `u` と同じ動きになる (58 問は回していない)。

判定: 採用基準 (上限 ≲ +5%・解けた数が減らない・種をまたいで一貫して遅い問題がない) のうち、上限はぎりぎり満たすが、
解けた数が 1 減り、binkar10_1 が一貫して 1.5 倍遅い。**`STALL_SCALE=u` は採らない** (既定は変えない)。
尺度を「正す」と binkar10_1 は根とサブ MIP のループが長くなるだけで得がなく、ほかの問題ではほぼ中立。
offset に左右される判定は筋としては不具合だが、直すなら打ち切りの閾値 (1e-4) やサブ MIP の上限を一緒に見直す必要があり、
単独の直しとしての効きは 58 問では見えない。DUALEQ も、尺度をそろえても binkar10_1 で 1.1〜1.3 倍 (c14ud / c14u) の害が残り、
効く問題が見えないので、cand1114 に戻す理由はない (門 MINRED=0.01 なら害は消えるが効きもない)。

## 7. (a) の深掘り: DUALEQ の等式の構造でノードが約 2 倍になる仕組み (binkar10_1)

結論: **根のカットのループで選択に落ちた tableau 行の候補 (密、1 本 約 300 非零) がすべてカットプールに入り、プールが非零の上限
(20 万) まで埋まることが原因**。DUALEQ (と `STALL_SCALE=u`) で根のループが長くなると (主のループは 6 → 25 周)、こうした候補がたまる。
DUALEQ の等式で tableau 行の候補が 1 ラウンド 30 → 90〜105 本に増え、その分も効いている。これらの候補は根では 1 本も採られない。
試作 `ENOMOTO_MIP_POOL_TAB=x` (選択に落ちた tableau 行の候補をプールに入れない) で、binkar10_1 の DUALEQ の害は消える。

調べた順 (binkar10_1、cand1114、4 スレッドは種 1〜4、1 スレッドは種 1〜3。U = c14 + `STALL_SCALE=u`、UD = U + DUALEQ):

1. **最適解の見つけ方ではなく、木の探索そのもの**。最適値を打ち切り値として最初から与えても (`ENOMOTO_MIP_CUTOFF=6742.2001`)、
   4 スレッドの U は worker ノード 1.1〜1.2k、UD は 2.6〜3.5k で、差は縮まらない (与えないときは U 2.1〜2.3k・UD 2.2〜3.1k)。

## 8. 試作 `POOL_TAB=x` の 58 問 × 種 1・2 (`run.py ... 1,2 c14x,c14dx` と対照 `c14r`、`res_X.jsonl`)

c14x = c14 + `ENOMOTO_MIP_POOL_TAB=x`、c14dx = c14x + DUALEQ。60 秒・4 スレッド。集計は `python summ.py 基準 比べる設定`
(res_P と res_X を合わせて読む)。
