### 3.2 密化の構造的な理由 (HiGHS の最適基底、`neos_basis.log`)

- 最適基底: 基底構造列 36,723 本、基底スラック 442,396 本、非基底 (タイトな) 行 36,723 本。タイト行を辺、構造列を頂点とする
  グラフの連結成分は 18 個で、**最大成分が 36,690 頂点** (残りは 5 頂点以下)。最大成分の列に触れる行は 479,014 本 (全行の
  100.0%)。
- `x_i - x_j >= b` の行がタイトなら `x_i` と `x_j` は連動するので、成分内の 1 列 `q` の入基 (`B^-1 a_q`) は成分全体の基底構造列
  に非零を作り、それらの列に触れる行 (= ほぼ全行) の基底スラックにも非零が伝わる。したがって基底構造列が繋がってくるほど
  `alpha` は密になる (段階 B の 20K〜55K 反復で密度 0.09〜0.41)。`tau = B^-1 rho` も同様に密。これは基底の選び方ではなく
  問題固有 (最適基底自体がそうなっている) なので、**主問題で解く限り避けられない**。HiGHS も同じ。
- 段階 A (傾き問題) は疎 (`alpha` 非零 99、`tau` 70、`rho` 1.3) で 0.3〜0.4 ms/反復。段階 A は 17,252 反復で全 36,708 本の
  M フラグ列のうち 15,600 本ほどしか解消せず (`remaining_m_side` 36,708 → 21,064)、残りは段階 B で 1 反復 1 本ずつ減る
  (反復 84,000 で 10)。

### 3.3 各フェーズが O(m) になっている箇所 (file:line は HEAD `273d0d6`)

1. **FTRAN (385 s, 45%)**: 入る列と `tau` の融合 FTRAN `solve_sparse_into_pair_capture_tracked`
   (`lu.rs:4709` → `pair_r_u_permute_tracked` `lu.rs:5082`)。密度 0.15〜0.34 では `expected_dense_gate()` (`lu.rs:3045`、
   `EXPECTED_DENSE_FRACTION = 0.35` `params.rs:562`) を超えないので Gilbert–Peierls の L 段 + ヒープ式超疎 U 段
   (`u_solve_hyper_heap` `lu.rs:4078`) を試み、一覧が `U_HYPER_ABORT_FRACTION = 0.25·m` (`params.rs:578`) を超えると
   **残りを全走査で仕上げる** (`lu.rs:4123-4137`: ヒープと印付けの作業が丸ごと無駄) → 出力置換 `permute_out` (`lu.rs:5184`、
   `O(m)`、gdb で最多)。密度 0.35 超で密経路になっても `l_solve_into` (`lu.rs:2488`、`O(m + nnz(L))`) + `R` eta 全適用 +
   U 全走査 + 置換 ×2 本 (`alpha`, `tau`) で 7〜10 ms (nnz(LU) ≈ 0.8〜1.0M)。
2. **`x_B` 更新 (140 s, 16%)**: `alpha` の非零が `XB_LIST_DENSITY = 0.3·m` (`params.rs:436`、判定 `:4027`) 以下なら
   一覧 (6〜13 万行) を、超えれば `0..m` を走査し (`:4111-4160`)、行ごとに `refresh_row` (`:1464`: `x_b_slope`・
   `row_bounds.flat`・`row_dev` を読み、`InfeasibleRows::set` `simplex.rs:1756` で `pos`/`rows` をランダムアクセス更新)。
   gdb で `refresh_row` + `InfeasibleRows::set` が段階 B 前半の 24%。
3. **chuzr (128 s, 15%)**: 遅延ヒープモード (`:2531`, `:2640-2660`) は「変わった行を積む」設計だが、段階 B では毎反復
   6〜15 万行を積む (`:4356-4368`、各 push は `O(log)` + `Score2::new` + `dse.weight`) ので `chuzr_heap.len() > 2·pool + 1024`
   で 1〜2 反復ごとに全再構築 (`BinaryHeap::from` = `O(pool)`、プール 11〜13 万行)。全走査 (`chuzr_dense_scan`, `:2540`) は
   一覧が `None` (密度 > 0.3) のときしか使われない。
4. **DSE 更新 (78 s, 9%)**: `update_after_pivot_rows` (`simplex.rs:1716`) を一覧 (6〜13 万行) で、または
   `update_after_pivot` (`simplex.rs:1687`) を全行で。`x_B` 更新とは別パスなので `alpha`/`tau`/行配列を 2 度読む。
5. **BTRAN (53 s, 6%)**: `rho_p = B^-T e_r` も密 (`btran_l scatter` 経路 100%、`BTRAN_L_SCATTER_FRACTION = 0.10` は
   *入力* の非零で判定するので単位ベクトル入力では常にスキャッタ)。1.1〜1.7 ms/反復。
6. **再分解 + FT 更新 (47 s, 5.5%)**: 合成クロック (`SYNTH_CLOCK_FACTOR`, `params.rs:217-249`) が 340〜380 反復に 1 回発火
   (段階 B 中盤で 5,000 反復あたり 11〜15 回、1 回 170〜190 ms、`max_update_streak` 349〜749)。HiGHS はこの問題で
   約 1,900 反復に 1 回 (ログ 56 行 / 105K 反復)。FT 更新 0.6〜1.0 ms/反復は密 `a_tilde`/`e_tilde` の処理。
7. **段階 A の BFRT (5 s)**: 最初の 5,000 反復で 626 µs/反復 (0.75 フリップ/反復)。段階 A のフリップ列の傾きチャネルは
   `lu.solve_sparse_into` (`:3555-3560`) で、これは `U` 全走査 + `permute_out` `O(m)` の非超疎版 (`lu.rs:5232-5246`)。
   段階 B 用の `solve_sparse_into_hyper_tracked` (`:3596-3608`) は使われない。

## 5. 改善策 (優先順)

採用条件 (Netlib93 + Mittelmann 5 問 + neos で問題あたり 10% 超の退行なし、shifted geomean 2% 以上改善) に照らし、
各策に「Netlib を変えないゲート」を付ける。Netlib93 は最大でも m ≈ 1.7 万 (stocfor3)・n ≈ 1.6 万 (dfl001, fit2p) なので、
`m >= 10,000 && n_total >= 100,000` (pds-100・neos・stormG2 級) や `m >= 4·n` のゲートで Netlib の経路は変わらない。
以下の見積もりは今回の走行 (負荷あり、868 s) に対する削減。

### 策1: 行 ≫ 列の問題を双対化して解く (期待: 868 → 200〜400 s、HiGHS 並みなら ~50 s。難度: 高。Netlib 退行リスク: ゲートで 0)

- 根拠: §4。HiGHS は 8 倍、ours は現状の段階 A のままでも 2.2 倍。段階 B の密化 (§3.2) は主問題で解く限り不可避なので、
  1 反復コストの改善策 (策2〜7) を全部足しても HiGHS の 363 s 級が上限。
- 実装: `simplex.rs:1826` (`build_std_form_presolved` の後、`solve_std_form_decomposed` `:1850` の前) で、presolve 後の
  `StdForm` が `n_rows >= DUALIZE_ROW_COL_RATIO · n_orig` (HiGHS は `simplex_dualize_strategy` 自動判定で行数/列数を見る。
  4〜8 倍で十分) かつ `n_rows >= 50,000` なら双対 StdForm を作る: `min -b^T y` s.t. `A^T y (<=, =, >=) c` (列の境界の種類で
  行の向きを決める)、`y` の境界は行の種類で決める (`>=` 行 → `y >= 0`、`<=` 行 → `y <= 0`、等式 → 自由、範囲行は HiGHS と
  同じく列を 2 本に分ける)。箱型列 (`lb, ub` とも有限) は `x <= ub` を行として双対に足す (HiGHS の「5098 extra from boxed」)。
  最初は **全列が片側有限・行が等式/不等式のみ** (neos, stormG2 型) に限定し、それ以外は双対化しないゲートでよい。
- 解の復元: 主解 `x` は双対問題の**双対値** (行の双対 `y_B = B^-T c_B` の対応成分と非基底列の被約費用) なので、
  `SimplexResult` に双対値 (`y` と `d`) を載せる口が必要 (`slope_intercept_dual.rs` は `fresh_d_y`/`d` を内部に持っている)。
  `unscale_result` (`simplex.rs:1854`) の前に主解に戻し、既存の postsolve (`postsolve_log`) を通す。
- 補足 (ours の双対解きの段階 A): §4 のとおり双対 LP では `y >= 0` の 45 万本が全部 M フラグ列になり段階 A が 42 万反復
  かかる。HiGHS の Ph1 (双対実行不能の合計をコストにした補助問題) は数千反復で終わるので、双対化と同時に「M フラグ列が
  `n_total` の大半を占めるときの段階 A の打ち切り/別手法」を検討する価値がある (段階 A の `z^1 = 0` 到達判定を緩め、
  `remaining_m_side` の減り方 (1 反復 0.45 本) を見て早期に段階 B に移り、残った M 側列は `finish` の cleanup に任せる等。
  論文の正当性条件との整合が要るので難度は高い)。また双対の presolve では `parallelcols` が主の重複行 = 双対の平行列 5.2 万本の
  うち 3.2 万本を見逃している (ours 459,081 列 vs HiGHS 426,901 列) ので、`parallelcols.rs` の署名 (係数比の丸め、上限
  `PARALLELCOLS_STRIKES`) を確認する。
- ゲート: presolve 後の `n_rows >= 4·n_orig && n_rows >= 50,000` (Netlib・stormG2 (528K × 1.26M)・pds-100 (87K × 426K)・
  s250r10・square41・ex10 (63K × 16K = 3.9 倍: 境界。ex10 は `alpha` 80% 密なので双対化が有利な可能性もあるが、閾値は
  ex10 を A/B して決める) はいずれも非該当)。`ENOMOTO_DUALIZE=0/1` で強制できるようにする。

### 策2: 密度ゲート `EXPECTED_DENSE_FRACTION` を 0.35 → 0.10 に下げ、超疎 U 段の打ち切りを早める (期待: FTRAN 385 → 250 s 前後、全体 −10〜15%。難度: 低。リスク: 低)

- 根拠: §3.3 (1)。密度 0.15〜0.34 で超疎経路 (ヒープ + 印付け + 一覧 + 途中で全走査に切替) を通しており、gdb でも
  `pair_r_u_permute_tracked`/`permute_out` が最多。HiGHS は結果密度 0.10 (`kHyperFTRAN`) を超えたら密ループにする。
  `lu.rs:3045` の `expected_dense_gate()` (`ENOMOTO_EXPECTED_DENSITY_GATE`) を `m >= 10,000` のときだけ 0.10 にする
  (小さな問題では現状維持でビット一致を保つ; 密/超疎は値もビット一致と文書化されているので、実際は全問題で変えても
  値は変わらないはずだが、Netlib の時間退行を避けるためゲートする)。同時に `U_HYPER_ABORT_FRACTION` 0.25 → 0.10
  (`params.rs:578`): 一覧が m の 10% を超えたら早く全走査に落とす。
- 測定: `neos_long.log` の 20K〜60K 区間で FTRAN 7〜10 ms → 密経路のみの区間 (`density_gate_ftrans` ≈ 4,000/5,000 の
  30–35K) でも 8.2 ms なので、密経路自体 (`l_solve_into` + R + U + 置換 ×2) の定数も見直す (策3)。

### 策3: 密 FTRAN の定数削減 (期待: FTRAN −30%、全体 −10%。難度: 中。リスク: 低〜中)

- `alpha` と `tau` の融合密経路で、`R` eta 段は 2 本同時に dot (`lu.rs:5102-5110` は既にそう) だが `L` 段 `l_solve_into`
  (`lu.rs:2488`) は 1 本ずつ (2 本同時走査版 `lu.rs:2392-2400` は `solve_into_pair_capture` 用で、融合密経路 `pair_r_u_permute_tracked` の前段 (`solve_sparse_into_pair_capture_tracked` `lu.rs:4709`) が密入力でも使っているか確認する) → 密経路でも L 段を 2 本同時に。
- `permute_out` (`lu.rs:5184`) は分岐付き (`tiny_drop`、`single_piv` 除算) で `O(m)` を 2 本分。`tiny_drop() <= 0` のときの
  専用ループにして分岐を消し、`u_zero_skip` 側で `single_piv` の除算を `U` 段側に寄せる (S 策5 で ex10 では逆効果だった
  2 パス化ではなく、1 パス分岐なし)。
- 再分解間隔を広げる (策7) と `R` eta の本数 (349〜749 更新分) が減り FTRAN の R 段も減る。
- ゲート: `BIG` (m ≥ 300) の中でさらに `m >= 10,000`。

### 策4: 密モードの chuzr: 一覧が長いときはヒープに積まず全走査で選ぶ (期待: chuzr 128 → 30 s、全体 −11%。難度: 低。リスク: 低)

- 根拠: §3.3 (3)。`:4356-4368` の push ループは一覧 `k` が `pool / 8` (または `m / 64`) を超えたら実行せず
  `chuzr_scan_next = true` (`:2540`, `:4370-4372` の `xb_list_len.is_none()` 条件を `k > threshold` にも広げる) にして、
  次の反復は `infeasible_rows.rows` の線形走査 (`:2713-`、`O(pool)` = 11〜13 万行、1 回 ~0.5 ms) で選ぶ。ヒープの作り直し
  (`BinaryHeap::from`, `:2643-2647`) も同じ `O(pool)` だが、その前の push (`O(k log)`) と `Score2::new`/`dse.weight` の
  ランダムアクセスが無駄。選ぶ行は同じ (全走査と遅延ヒープは同じ順序規則) なのでビット一致。
- ゲート: 遅延ヒープ自体が `BIG && shortlist_auto` (`:2531`) なので Netlib 小問題は不変。

### 策5: `x_B` 更新・実行不能判定・DSE 更新を 1 パスに融合し、密モードでは行集合を再圧縮で作る (期待: `x_B` 140 + DSE 78 → 100 s、全体 −13%。難度: 中。リスク: 中 (ビット一致の維持))

- 根拠: §3.3 (2)(4)。段階 B では `x_b_slope` が全 0 で `theta_slope == 0` なので `:4141-4160` の分岐だけを通る。
  ここに DSE の `w[i] = max(w[i] - 2·ratio·tau[i] + ratio²·wp_old, floor)` (`simplex.rs:1716-1724`) を同じループへ入れる
  (`alpha`・`tau`・`x_b_base`・`w` を 1 度ずつ読む)。値は同じ演算順なのでビット一致 (DSE は行ごとに独立)。
- `refresh_row` (`:1464`) の `x_b_slope[i] == 0.0` 判定は段階 B 全体で常に真なので、段階 B 用に `x_b_slope` を読まない版
  (`flat` 境界のみ) を用意する (1 配列 3.4 MB/反復の読み出し削減)。
- `InfeasibleRows::set` のランダムアクセス (`simplex.rs:1756`) は、密モード (一覧 `k > m/16` 目安) では行ごとの set/unset を
  やめ、ループ後に `pos` を `rows` から再構築する (`InfeasibleRows::rebuild` `simplex.rs:1783`)。順序が変わると chuzr のタイブレークが
  変わりうるので、全走査 chuzr (策4) と組にして「行番号昇順」で決めるか、`rows` の順序を保つ再圧縮にする。
- ゲート: `m >= 10,000` (`FLIP_TRACK_MIN_M` と同じ)。

### 策6: 段階 A の BFRT フリップ列 FTRAN を超疎版にする (期待: 段階 A 10 → 6 s、全体 −0.5%。難度: 低。リスク: 低)

- 根拠: §3.3 (7)。`:3554-3560` の `lu.solve_sparse_into` を段階 B と同じ `solve_sparse_into_hyper_tracked`
  (`cas_track` 付き、`:3600-3608` と同形) に替える。値はビット一致 (文書化済み)。`BIG` のみ。
- neos では段階 A の半分 (4.6 s) だが、片側非有界列の多い問題 (双対化後の neos: BFRT 83 µs × 44 万反復 = 37 s) では効果が
  大きい。

### 策7: 再分解の合成クロックを密な問題で緩める (期待: 再分解 26 + FT 更新 21 + R 段の分 → −20 s、全体 −3%。難度: 低。リスク: 中 (数値))

- 根拠: §3.3 (6)。ours は 340〜380 反復に 1 回 (HiGHS ~1,900)。`SYNTH_CLOCK_DENSE_FRACTION = 0.3` (`params.rs:240`) の
  「密なら `sqrt(m)` 倍を掛けない」分岐が neos (密度 0.1〜0.4) で効いて係数が小さいまま。密度 0.3 未満の区間では
  `SYNTH_CLOCK_MID_*` が効くが、それでも 5,000 反復に 11〜15 回。`ENOMOTO_SYNTH_CLOCK_FACTOR` を 16 → 32〜64 にした A/B
  を先に取る (klein/pilot の数値トラブル既往があるので `m >= 10,000` に限る)。

### 策8: BTRAN `rho_p` の密化対策 (期待: BTRAN 53 → 30 s、全体 −3%。難度: 低。リスク: 低)

- 根拠: §3.3 (5)。`L^T` 段の scatter/gather 切替 (`BTRAN_L_SCATTER_FRACTION`, `lu.rs:3422` 付近) は入力非零で判定するので単位
  ベクトル入力では常に scatter。結果密度の履歴 (`FtranDensity` 相当を BTRAN にも持つ) で 0.1 を超えたら最初から
  密 (gather) 経路にし、超疎 `U^T` 段 (`u_transpose_solve_seeded`) の試行も省く。

### 策9: 段階 B での `Affine1` 2 チャネルの畳み込み (期待: `x_B`・chuzr・BFRT の配列帯域 −30%、全体 −5%。難度: 中。リスク: 低)

- 段階 B (`phase == Phase::B`) では `x_b_slope`、`row_dev.dev.slope`、`combined_alpha_slope` が全 0 で、`Score2`/`Affine1` の
  比較は base 成分だけで決まる。`row_dev` を `(dir: i8, dev_base: f64)` の密モード表現にして chuzr ヒープの要素
  (`ChuzrEntry`) と `refresh_row` の読み書き量を減らす。値は同じなのでビット一致。`m >= 10,000` に限定。

### 策10: presolve の双対側 `parallelcols` (双対化と併用時のみ。期待: 双対解きの列 459K → 427K (−7%)、反復数も減る見込み。難度: 低)

- §2 末尾。主問題側では効果なし (重複行は既に除去)。

### 策11 (反復数側、効果は限定的): 段階 A で解消しきれない M フラグ列 (21,064 本) の段階 B での解消は 1 反復 1 本

- 段階 B の 68K 反復のうち 21K は「M 側列の入基」で消費される。HiGHS も Ph2 で 8 万反復なので反復数の差は小さく、
  優先度は低い。双対化 (策1) の段階 A の問題の方が本質的。

### 5.1 効果の積算 (見積もり、負荷ありの 868 s 基準)

- 策1 (双対化) 単独: 403 s (現状の ours の双対解き)。段階 A の反復数を HiGHS 並み (数万) にできれば 100 s 以下。
- 策2+3+4+5+7+8 (主問題のまま): FTRAN 385 → ~230、chuzr 128 → 30、`x_B`+DSE 218 → 100、再分解系 47 → 30、BTRAN 53 → 30
  で合計 ~450〜500 s (HiGHS 363 s に迫るが超えない)。これらは pds-100 (alpha 密度 1%) や stormG2 には効かず、ex10
  (alpha 80% 密) には効く。
- 両方: 双対化後の問題は s250r10 型なので、s250r10 報告の策 (PRICE・chuzc1 の列添字アクセス) が効く。

### 5.2 Netlib・他問題を遅くしないためのゲートと確認

- 全策とも `m >= 10,000` (`FLIP_TRACK_MIN_M` 等と同じ) または `BIG` の内側に置き、Netlib93 は経路不変 (前回同様に
  `DEBUG_EXT` の反復数行と目的関数値のビット一致を確認)。
- 策1 のゲート `n_rows >= 4·n_orig && n_rows >= 50,000` は Mittelmann 5 問 (stormG2 0.42 倍、square41 0.07、pds-100 0.2、
  ex10 3.95、s250r10 0.03) を外す。ex10 は境界なので閾値を 4 か 6 かで A/B。
- 策2 の密度ゲート 0.35 → 0.10 は pds-100 (`tau` が 19% の反復で密) と ex10 (80% 密) の経路 (値は不変) を変えるので、
  両者で時間退行がないことを確認 (ex10 は FTRAN 32% なので改善方向のはず)。
- 策7 (再分解間隔) は数値経路が変わるので、Netlib の目的関数値・反復数の一致を必ず確認し、`m >= 10,000` 限定にする。
