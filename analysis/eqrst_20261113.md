# 再スタート後の EQUIV2 の誤答の確かめと解禁 (2026-11-13)

ブランチ `ccr-1beed81b-ex0uhq` (25cddf4c から)。台本・結果は `analysis/eqrst_20261113/`。
課題: 同値な列の組 (EQUIV2、`src/mip/mod.rs` の `probe`) を再スタートの後に使わない手当て (ecf2cfd、term_check_20261022.md §3) の
原因を特定し、正しさの問題が他の経路に隠れていないかを確かめる。

## まとめ

- **原因はすでに特定・修正済みだった (事実、analysis/equiv2_bug_20261022.md)**。原因は組ではなく、組の後の前処理の係数の強化
  (`tighten_coefficients`) にあった。幅 1e-9 の連続列 y を持つ、許容誤差の範囲で冗長な行 `x + y <= 1 - 1e-9` を `2e-9 x + y <= 1e-9`
  に縮め、行の尺度をかけた LP では x = 1 (最適解の値) を切っていた。手当ては 2 つあり、どちらも既定で動いている:
  1. 係数の強化の防御: 縮めた後の係数が `1e-6 (1 + |b|)` 以下の行は縮めない (`ENOMOTO_MIP_COEF_TIGHTEN_TINY` で以前どおり)
  2. 幅が許容誤差以下の列を 1 点に固定する (`fix_tiny_width_columns`、analysis/tinywidth_20261022.md。`ENOMOTO_MIP_NO_TINY_WIDTH_FIX` で外す)

  probe() の注記だけが「原因は未特定」のまま残っていた。履歴を squash したため、commit 18def7a は今のリポジトリにない。
- **既定の経路に同じ穴はあったか**: あった (係数の強化はすべての前処理で動く。equiv2_bug §4)。上の 2 つの手当てで既定の経路も直っている。
  今回の fuzz (§2) では、手当てを外しても厳密に実行可能な解を切る例は出なかった (今のコードでは、ほかの変更もあって出にくい)。
- **今のコードでの再現 (§1)**: uccase12 を再スタート後も EQUIV2 を使う設定で解いた。組を必ず使わせ (`MIN_FRAC=0`)、
  係数の強化を旧挙動にしても (`COEF_TIGHTEN_TINY`)、誤答は出なかった (計 12 回、下界 ≤ 11507.372、最適値 11507.405)。
- **変更**: 再スタート後の問題でも EQUIV2 を**既定で使う**ようにした。旧挙動は `ENOMOTO_MIP_PROBE_EQUIV2_NORESTART=1` で戻る。
  `ENOMOTO_MIP_PROBE_EQUIV2_RESTART` (以前の「使う」の指定) は今は既定と同じ。`cargo test --release --lib` は 415 件通る。
- **効き**: ほぼない。58 問 (10 秒) のうち、既定の閾値 (組が候補の 5% 以上) で再スタートの後に組を使ったのは beavma だけで、
  時間は既定と同じだった (0.5 秒前後 × 5 回)。uccase12 は再スタートの後に組を見つけるが (284〜692 組)、閾値に届かず使わない。
  uccase9・uct-subprob・fastxgemm-n2r6s0t2 は 60 秒の中で根で再スタートせず、同じ経路を通る (差は揺れ)。
  既定を変える理由は「正しさの手当てが要らなくなった制限を外す」ことで、速さの改善は見込まない。束に入れるかは親で決める。

## 2. 乱数の問題 (事実、`fuzz_eqrst.py`、`count.py`、`rejudge.py`、結果 `fz/`)

- 既存の fuzz (`mip_fuzz_vs_highs.py`・`fuzz_tiny.py`) の問題は小さく、再スタートしないので、この経路を通らない。そこで、
  再スタートと再スタート後の組を起こす生成を作った。unit commitment 風で、稼働・立ち上げ・出力・最小稼働の行に、費用付きの 0-1 列 z で
  緩めた論理の行を足し、半分の問題には幅 1e-9 の連続列とその行を入れる。ログ (`ENOMOTO_MIP_LOG=1`) で `restart check` の後の
  `equivalence pass ... used` を数え、HiGHS と最適値を突き合わせた (`ENOMOTO_MIP_REL_GAP=1e-9`)。
- 判定: 状態と値 (相対 1e-6) の一致。一致しないものは `rejudge.py` で、許容誤差 1e-10・前処理なしの HiGHS (厳密に実行可能な最良の値) と比べた。
  返した値がそれより悪ければ誤り、そうでなければ許容誤差の内の差 (行 `x + y <= 1 - 1e-9` で x = 1 を許すかの差) とした。

| 設定 (seed 0〜999) | 再スタートあり | 再スタート後に組を使った | 不一致 | 誤り |
|---|---|---|---|---|
| 既定 (修正前のビルド) | 111 | 0 | 0 | 0 |
| rf (再スタート後に組を必ず使う) | 121 | 80 | 0 | 0 |
| rtf (rf + `COEF_TIGHTEN_TINY`) | 117 | 72 | 0 | 0 |
| rf + `NO_TINY_WIDTH_FIX` | 118 | 79 | 5 | 0 (5 件とも許容誤差の内の差) |
| rtf + `NO_TINY_WIDTH_FIX` (手当てを 2 つとも外す) | 110 | 76 | 117 | 0 (117 件とも許容誤差の内の差) |
| 新しい既定 (このブランチ、閾値は既定の 5%) | 112 | 36 | 0 | 0 |

- 手当てを 2 つとも外すと、許容誤差の内の差が 117 件出る (ENOMOTO が厳密な側に寄せて悪い値を返す)。厳密に実行可能な解を切る誤りは 0 件。
  10 月の `fuzz_tiny.py` の seed 41 (以前の動作で -9.81、正しくは -10.9) も、今のコードでは手当てを 2 つとも外して 300 問中 0 件だった
  (`fz/tiny_off.txt`。値だけの判定の不一致は 85 件で、どれも許容誤差の内の差)。今のコードでは、この誤りの形はほかの変更でも出にくくなっている (推測。どの変更かは追っていない)。
- 再スタート後に組を使った問題で不一致が出たのは、手当てを外した設定の許容誤差の内の差だけだった。組の代入と再スタートの写像
  (固定・後処理の復元) に誤りの兆しはない。
