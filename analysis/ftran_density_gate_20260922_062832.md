# FTRAN 結果密度の移動平均による密/疎切替(`docs/lu_comparison_enomoto_vs_highs.md` §2.7)

対象: `FtLu::should_use_dense_solve` の判定基準。基点 `main` = a9a326a(反復#8 の
`ft_refactor_trigger` 採用後)。4 コア、rustc 1.94.1、highspy(Python 3.11)、
NETLIB93 全問題。

指摘された問題: `should_use_dense_solve(rhs_nnz)` は **入力 nnz だけ** で密/疎を判定し、
HiGHS の `expected_density`(過去の FTRAN 結果密度の移動平均)に相当するものを持たない。
規模が上がるほど FTRAN 結果が予測より疎/密になり、切替が後手に回る。

## 0. 結論

1. 指摘は実在した。入力側の判定(`DENSE_RHS_FRACTION = 0.4`)は **93 問題で
   一度も発火していない**(既存の `DENSE_RHS_BYPASSES` が全問題 0)一方、FTRAN の
   **結果**密度は重い問題ほど高い(dfl001 0.655、pilot87 0.803、fit2p 0.999、
   pilot 0.874)。「入力は疎、結果はほぼ密」という状態で、疎経路の DFS/epoch
   コストを払い続けていた(§1、§3)。
2. HiGHS 相当の移動平均ゲートを入れると、**59/93 問題**で発火し(全体壁時計の
   98.6% を占める問題群)、合計 **-1.25%**(51.99s → 51.34s)。目的関数値は
   93/93 一致(§4.3)。
3. 閾値は **0.35**。0.2 まで下げると BFRT combined チャネルまで密経路に回り、
   greenbeb の -22% が -1% に潰れるなど逆効果(§4.2)。
4. **10% 以上の退行は 1 問題もない**。best-of-2 で 10% 超に見えた nesm/fit2d/sc50a
   は高反復の取り直しで消えた。特に sc50a はゲート未発火(挙動完全同一)なのに
   12.5% 振れており、この環境の測定限界を示す対照になっている(§4.3)。
5. 確認された唯一の実退行は pilot87 +5.9%。原因は**反復数 +6.0%** であり、
   1 反復あたりのコストは悪化していない。ディスパッチ変更が `synth_tick` 経由で
   CLOCK 再分解のタイミングを動かすためで、同じ機序が dfl001 -1.9%、
   greenbeb -16%、pilot -5.7% と逆方向にも効いている(§4.4)。
6. 判定は CSV ハーネスではなく**同一プロセス内で設定を交互に切り替える直接計測**で
   行った。CSV 方式は同一コードの 2 回実行でも 4.3 倍の差を出すことがあり、
   10% 判定には使えない(§4.1)。

## 1. 現状の確認: 入力側の判定は実質的に一度も発火していない

`DENSE_RHS_FRACTION = 0.4` は **入力** rhs の非ゼロ率に対する閾値で、
`prof_phases::DENSE_RHS_BYPASSES` の既存コメントが記録しているとおり、実測で
全問題 0 回、つまり **主ループの FTRAN は常に Gilbert-Peierls 疎経路** を通っていた
(入基底列は元来疎で、BFRT の combined も 0.4·m を超えることは稀)。

一方 FTRAN の **結果** は疎とは限らない。反復#8 の分析
(`analysis/ft_refactor_trigger_20260922_040850.md` §2.4)が既に測っているとおり、
本ソルバの FTRAN 結果密度は HiGHS より高く(d2q06c 45% vs 13%、dfl001 49% vs 10%)、
eta 鎖の fill がそのまま出力密度に出る。入力の疎性は結果の疎性を保証しない。

## 2. 実装

- `sparse_lu::FtranDensity`: 呼び出し地点ごとに結果密度 `nnz/m` の移動平均を持つ。
  係数は HiGHS と同じ `kRunningAverageMultiplier = 0.05`
  (`DENSITY_AVERAGE_MULTIPLIER`)。
- `FtLu::should_use_dense_solve_tracked(rhs_nnz, &density)`:
  `should_use_dense_solve(rhs_nnz) || density.predicts_dense()`。
  **疎→密方向にしか動かさない**: 入力が 0.4·m を超える場合は GP の reach が
  それ以上になることが保証されるので、履歴で疎経路に引き戻す余地はない。
- 測定コスト 0: どの解法経路も最後に `out[col_perm[s]] = scratch[s]` の O(m)
  置換ループを通るので、そこで非ゼロを数える(分岐なしの `+= (v != 0.0) as usize`)。
  `solve_into` / `solve_into_capture` / `solve_sparse_into` /
  `solve_sparse_into_capture` が結果非ゼロ数を返す。
- **両分岐で記録する**ので、ゲートは固着しない。密経路に移った後に結果が疎に戻れば
  平均が下がり自動的に疎経路へ戻る(単体テスト
  `density_gate_flips_a_sparse_rhs_channel_dense_and_back` が固定)。
- 移動平均は `FtLu` ではなくソルバのループ側に置く。`FtLu` は再分解のたびに
  作り直されるため、基底が最も密になった瞬間に履歴を捨ててしまう
  (HiGHS も同じ理由で `HEkk` 側に持つ)。
- チャネルは 2 系統: 入基底列 FTRAN(`col_aq`)と BFRT combined(`bfrt`)。
  rhs の形が違い、密度も実測で 2 倍以上違う(§3)ので平均を混ぜない。
- 閾値 `EXPECTED_DENSE_FRACTION` は `ENOMOTO_EXPECTED_DENSITY_GATE` で上書き可能
  (`>= 1.0` でゲート無効 = 従来の入力のみ判定)。A/B はこの環境変数で、
  **同一バイナリ** に対して実施した(ビルド差によるノイズを排除)。

## 4. 計測2: 閾値の A/B

### 4.1 計測方法(CSV ハーネスではなく直接実行)

`python -m enomoto_solver.benchmark_highs` が書く CSV は、問題ごとに新しい
サブプロセスを立てて 1 回だけ解く。この環境ではそれだと**同一コードの 2 回実行**でも
adlittle 4.3 倍、finnis 2.9 倍、sc50b 2.4 倍といった差が出る(実測: baseline を
2 回取って比較)。10% 退行を判定する土俵として成立しないので、判定は
**同一プロセス内で A/B を交互に実行する直接計測**で行った
(`scratchpad/direct_ab.py`):

- 問題ごとにモデルを 1 回だけ読み、以後は解くたびに `PyModel` を作り直す。
- 1 回の solve ごとに `ENOMOTO_EXPECTED_DENSITY_GATE` を切り替える。Rust 側は
  solve のたびに環境変数を読むので、**同じバイナリ・同じプロセス・暖まった同じ
  キャッシュ**で設定だけが変わる。
- 設定を交互に回すので、マシン側のドリフトはどの設定にも等しくかかる。
- warmup 1 回を捨て、各設定の **min** で比較(median も併記して乖離を監視)。

この方式では min と median の差が 0.5〜2% に収まり、CSV 方式の数倍の振れは消えた。

### 4.3 全 93 問題(best-of-2、gate off vs 0.35)

合計 **51.99s → 51.34s(-1.25%)**、目的関数値は 93 問題すべて一致
(相対差 <1e-9)、status 変化なし。

主な改善: greenbeb -20.0%、wood1p -17.8%、pilot -11.6%、dfl001 -4.1%
(22.79 → 21.86s、絶対値では最大の -0.93s)、fit2p -2.3%。

best-of-2 の時点で 10% 以上の退行に見えたのは nesm(+29.2%)、fit2d(+14.1%)、
sc50a(+12.5%)の 3 問題。**いずれも 9 反復で取り直すと消えた**:

| 問題 | off(min) | 0.35(min) | 比(9反復) | 比(2反復) |
|---|---:|---:|---:|---:|
| nesm | 0.1353 | 0.1343 | 0.993 | 1.292 |
| fit2d | 0.2060 | 0.2057 | 0.999 | 1.141 |
| sc50a | 0.0008 | 0.0008 | 1.000 | 1.125 |

sc50a は**ゲートが一度も発火しない**問題(§3 の `density_gate_ftrans=0`)で、
両設定のバイナリ挙動は完全に同一である。それが best-of-2 で 12.5% 振れたことが、
この規模(0.8ms)での測定限界そのものを示している。nesm・fit2d も反復数・
再分解回数が両設定で完全一致(下表)なので、挙動差では説明がつかない。

### 4.4 確認された唯一の実退行: pilot87 +5.9%(反復数の増加)

| 問題 | gate | 反復 | 再分解 | うち clock | ゲート発火 |
|---|---|---:|---:|---:|---:|
| nesm | off / 0.35 | 1197 / 1197 | 5 / 5 | 4 / 4 | 0 / 73 |
| fit2d | off / 0.35 | 144 / 144 | 2 / 2 | 2 / 2 | 0 / 28 |
| sc50a | off / 0.35 | 29 / 29 | 0 / 0 | 0 / 0 | 0 / 0 |
| pilot87 | off / 0.35 | 6637 / **7033** | 59 / 62 | 7 / 5 | 0 / 8466 |
| dfl001 | off / 0.35 | 23856 / **23403** | 101 / 97 | 74 / 75 | 0 / 18030 |
| greenbeb | off / 0.35 | 5445 / **4597** | 27 / 19 | 16 / 12 | 0 / 2529 |
| pilot | off / 0.35 | 3343 / **3151** | 31 / 30 | 7 / 8 | 0 / 3186 |
| wood1p | off / 0.35 | 311 / 313 | 3 / 2 | 2 / 2 | 0 / 305 |

pilot87 は 4 反復で取り直しても min 11.71 → 12.41(+5.9%)、median 12.06 →
12.96(+7.5%)と再現する実退行。ただし**反復数が +6.0%(6637 → 7033)で、
壁時計の増分とほぼ一致する**ので、1 反復あたりのコストが悪化したのではない。

機序: 反復#8 で入った CLOCK 再分解トリガーは `FtLu::synth_tick` で発火し、その
tick は L 段に密経路なら `m`、疎経路なら `reach.len()` を加算する
(`lu.rs` の `ftran_through_l_and_r_into` / `solve_sparse_into`)。したがって
ディスパッチを変えると**再分解のタイミングが変わり、ピボット列そのものが変わる**。
これは片側に偏った効果ではなく、pilot87 は +6.0%、dfl001 は -1.9%、greenbeb は
-16%、pilot は -5.7% と両方向に出る。tick が密経路に `m` を課すのは実際の作業量
として正しい(密 L 段は本当に `m` を走る)ので、tick 側は変更していない。

**従って「1 回の FTRAN が速くなる」効果と「ピボット列が変わる」効果は本質的に
分離できない**。この点は正直に記録しておく。採否は end-to-end の壁時計で判断した。

## 5. 採否

**採用**(閾値 `EXPECTED_DENSE_FRACTION = 0.35`)。

- 全 93 問題で **10% 以上の退行なし**。確認された最大退行は pilot87 +5.9%
  (反復数 +6.0% に起因、1 反復あたりは不変)。best-of-2 で 10% を超えて見えた
  3 問題は高反復で消滅し、うち sc50a はゲート未発火の対照である。
- 合計 -0.98〜-1.25%(独立 2 回とも改善側、§4.3b)、目的関数値は 93/93 一致、
  status 変化なし。
- 測定オーバーヘッド(結果非ゼロ数の計数)は既存の O(m) 置換ループ内の
  分岐なし加算 1 個ぶんで、ゲート無効設定(`ENOMOTO_EXPECTED_DENSITY_GATE>=1`)
  でも常に払われている。上の A/B はその設定を基準にしているので、
  **-1.25% はオーバーヘッド込みの正味**である。

### 5.1 残る課題

- pilot87 の反復数増は CLOCK トリガーとの相互作用であり、この変更単体の問題では
  ないが、ディスパッチ変更が再分解タイミングを揺らすこと自体は将来の計測を
  読みにくくする。CLOCK の較正(`SYNTH_CLOCK_FACTOR`)を密/疎経路の混在前提で
  取り直す余地がある。
- BFRT チャネルは現状 0.35 では滅多に発火しない(密度 0.24〜0.49)。チャネル別に
  閾値を分ける案は試していない。
