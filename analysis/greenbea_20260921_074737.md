# greenbea 実行時間分析(自己改善ループ 反復#5, runtime 段) -- 「次の」ボトルネック

対象: NETLIB `greenbea`(2392 行 x 5405 列, 30,877 非零; presolve 後 2056 x 4645 x 32,474)。
起点コミット: `441a563`(ブランチ `claude/greenbea-20260921_072102`; 反復#4 の `residual_norm_affine` 修正込み)。
HiGHS 1.15.1(`highspy`)、4 コア、rayon 不使用(`RAYON_SIZE_THRESHOLD = 100_000 > m`)。
全数値は本セッションでこの環境で実測。推定値はその旨明記する。**ワーキングツリーへのコード変更は残っていない**(§7)。

## 0. 結論(要約)

- 現状: ハーネス `ours 3.39-3.49 s / HiGHS 0.298-0.300 s = 11.4-11.6x`、両者 `optimal`、目的関数値 ours -72555248.12985753 / HiGHS -72555248.12984587(相対差 1.6e-13)。主ループ 6,601 反復、480-491 us/反復(HiGHS presolve off: 166 us/反復 @ m=2392、presolve on: 99 us/反復 @ m=951)。
- **分類: (c) 1 反復が重い、が主因(HiGHS 比 2.9x @同規模)。反復数は副因(presolve off の HiGHS 比 1.3x、presolve on 比 2.6x)。presolve 不足は反復#4 で実測棄却済み。**
- 反復#4 の修正後、主ループの時間は「LU 系の実装定数」と「HiGHS が持たない検査」に広く分散しており、単独 30% 級の項目はもう無い。**次に大きい項目は再分解 623 ms(19.2%; 58 回 x 9.6 ms、うち `find_best_pivot` 295 ms + `eliminate` 141 ms、`lu.rs:349` / `:403`)** で、反復#4 の候補 #2 と同じ場所だが、本反復の実験で **「ピボット順を変える種類の高速化は greenbea を誤 infeasible にする」ことが判明した**(§4.3)。つまり再分解はピボット選択をビット単位で変えない方法(探索の定数削減)でしか触れない。
- 代わりに、**ピボット経路を一切変えずに確実に削れる項目を 2 つ、計測で確定した**(合計 -9%、目的関数値・反復数・再分解回数すべて不変):
  1. **d ドリフト検査 `fresh_d_into`(174 ms, 5.4%; `extended_dual.rs:3236-3256`)は測っている量が壊れている。** 残差から固定列(`lb == ub`、greenbea では等式スラック 1,549 本)を除くと相対残差は最大 7.8e-10(中央値 0)に落ちる。PRICE(`:2369`)が固定列を飛ばすため固定列の `d[j]` は設計上更新されず、それが残差の全てを占めている(全体では中央値 7.7%、最大 28%)。93 問題スイープで発火したのは 80bau3b の 1 回だけで、それも同じ理由の偽陽性(固定列を除くと 9e-18)。頻度を 20 分の 1(100 反復ごと)にすると greenbea -165 ms、12 問題で経路完全一致。
  2. **chuzc1 の全候補ソート(163-165 ms, 5.1%; `extended_dual.rs:2505-2511`)。** 候補 521 本/反復を毎回 stable sort しているが、BFRT の走査は平均 `k_star = 0.5`、Harris 窓 1.011 本しか消費しない。古典経路 `simplex.rs:4061-4072` が既に採用している min-heap の遅延プレフィックス方式を移植すると 35 ms(-128 ms)、経路はビット一致。
- 反復#4 の分析が「反復数の差は設計由来」とした点は据え置き。加えて本反復で、`d` ドリフト検査の欠陥と、LU ピボット順に対する経路の脆弱性(有効なピボット順の変更で偽 infeasible / 特異基底)を新たに記録した。

## 3. 機序(該当ソースを読んだ上での説明)

### 3.1 `d` ドリフト検査が固定列の「設計上の未更新」を測っている(`extended_dual.rs:3236-3256`)

PRICE(`:2362-2379`)は `std.lb[j] == std.ub[j]` の列を `a_p` に入れない → `touched_cols` に入らない → 双対更新(`:3119-3128`)も `d[j]` を触らない。一方 `fresh_d_into`(`:1176`)は全 `n_total` 列について `d[j] = c_j - a_j^T y` を計算する。よって固定列の `d[j]` は初期値のまま、検査のたびに fresh 値との差が残差に乗る。greenbea では固定列 1,549 本(等式スラック)がこれに当たり、相対残差 3-28% の全てを説明する(固定列除外後は ≤ 7.8e-10)。`D_DRIFT_TOL = 1.0` という異常に緩い閾値は、この汚染の上でしか成立しない値である(pilot4 の「百万単位のずれ」の記録 `:595-612` は真の drift だった可能性があるが、現行既定では pilot4 でも発火しない)。この検査は 5 反復ごとに BTRAN 1 回 + O(nnz(A)) を払い(138 us/回 = 1 反復の 28%)、93 問題で 1 回(80bau3b)しか発火せず、その 1 回も固定列由来。

### 3.2 chuzc1 の全候補ソート(`extended_dual.rs:2505-2511`)

`candidates.sort_by(ratio.total_cmp then j)` を毎反復、521 本に対して実行。その直後の BFRT 走査(`:2520-2533`)は `k_star`(平均 0.5)で止まり、Harris 第 2 パス(`:2598-2612`)は `k_star` から後ろ向きに窓 1.011 本しか見ず、フリップ適用(`:2649-2712`)も `candidates[..best_idx]` しか読まない。つまり必要なのは (ratio, j) 順の先頭 1-2 本。古典経路は同じ観察から `BinaryHeap<Reverse<ChuzcCand>>`(`simplex.rs:4061-4072`、O(k) 構築 + O(w log k) pop)に置き換え済みで、extended dual への移植漏れ。

### 3.3 再分解(`lu.rs:349-390`, `:403-470`, `:902-994`)

反復#4 §3.2 の通り。追加で判明した点: ピボット種別は行シングルトン 51% / 列シングルトン 26% / 核 23%。列シングルトンはバケット 1 の先頭で即決するので走査コストはほぼ全て行シングルトン探索(列バケット 2 以上を順に舐め、各列の全活性行を `BTreeMap::get`)と核ステップ(`best_score <= deg^2` までバケット全走査)。**しかし §4.3 の通り、行シングルトンを O(1) で先取りする「HiGHS 型の剥がし」はピボット順を変え、greenbea では偽 infeasible に落ちる**。安全に速くするには、現行の選択(列バケット順 → 列内の行順 → 同スコアなら |v| 最大)をビット単位で再現したまま、要素参照(`rows[i].get(&j)`)と `eliminate` の BTreeMap/BTreeSet 操作の定数を下げる必要がある。

### 3.4 U の eta ファイル表現が全 solve の U 段を O(m) 走査にしている(`lu.rs:1737-1800`)

`u_seq: Vec<UEta>` は eta ごとに別ヒープの `Vec<(usize,f64)>` を持ち、`u_transpose_solve_into` は毎回全 m 本の eta で内積、`u_solve_into` は全 m 本を逆順に走査(`xp == 0` スキップはあるが走査自体は O(m) + ポインタ追跡)。U の非対角非零は再分解直後 4,451 個だが FT 更新で平均 11,404 個/BTRAN まで膨らむ(`COMMIT_OFFDIAG_NNZ` 平均 67/更新、平均更新数 157)。結果、U 段だけで 528 ms(16.3%)。HiGHS は U を行方向・列方向の両方でパックし hyper-sparse な BTRAN/FTRAN を選択する。また `commit_update`(`:2166-2221`)は `(0..m)` の密走査 2 回 + `Vec::remove` の memmove + `slot_pos` 再番号付けを毎更新払う(98 ms, 3%)。

### 3.5 DSE の tau(`extended_dual.rs:2976`)

`lu.solve_into(&rho)` は常に密経路(rho 非零 38% < `DENSE_RHS_FRACTION = 0.4` だが疎経路は L 段だけの利得で、U 段が支配的)。tau は 61% 密。DSE を維持する限り本質的コスト(HiGHS も FTRAN-DSE を払う)。重み更新自体は 43 ms。

| 2 | 列シングルトンのみ O(1)(現行のバケット 1 先頭と同じ選択) | 経路ビット一致、6,601 反復、`find_best_pivot` 302 → 282 ms(-20 ms) |

| 1 | 列 → 行の順で O(1) | **偽 `Infeasible`**(6.8 s): iter 6,000-11,050 で `remaining_m_side=1241` に停滞、iter 11,050 に |alpha| ≈ 2e-9 のピボットで `VERIFY_FAIL`、直後の `refactorize` が特異(`returned None`)→ 古典経路へフォールバックして infeasible |

mode 1 の経路が基準から離れる最初の点は **iter 474 = 最初の Markowitz 再分解**(それ以前はスラック基底で `factorize_diagonal`)。つまり LU の(数学的に同等な)ピボット順の違いによる丸めだけで、greenbea の extended dual は「解ける経路」と「偽 infeasible / 特異基底に落ちる経路」に分かれる。反復#4 の `FAST_RESID` 実験(greenbeb/pilot で経路変化)や `XB_INTERVAL_LADDER=3` の誤答と同じ脆弱性の現れで、**再分解まわりの改善は「ピボット選択を変えない」ことが前提条件**になる。なお |alpha_q| ≈ 2e-9 の候補が chuzc1 の `TOL = 1e-9`(`:2389`)を通過して選ばれ得ることも、この停滞→特異化の経路を作っている一因(HiGHS のピボット許容は 1e-7 級)。

## 5. 根本原因の分類

- **速度: (c) 1 反復が重い。** 実装定数の問題で、内訳は再分解(19%)、DSE tau の密 FTRAN(11%)、PRICE(12%)、BTRAN(11%)、ドリフト検査(10%)、chuzc1(9%)、FTRAN(7%)と分散。うち HiGHS が払っていないのは「ドリフト検査 10%」「全候補ソート 5%」「BTreeMap ベースの再分解のうち fill ゼロの基底で 9.6 ms かかる分」。反復数(2.6x)は設計由来の副因。
- **正答性: 既定経路では正答だが、LU ピボット順に対して脆い(悪条件/退化由来の設計上の脆弱性)。** 有効なピボット順の変更 2 種類(§4.3)がどちらも偽 infeasible に落ちる。これは今回の計測範囲では greenbea 固有の観察(他問題では未検証)だが、再分解の最適化案の選別を決定づける。
- **検査の設計欠陥:** `d` ドリフト検査は固定列の未更新分を測っており、全 NETLIB で 1 回しか発火せずそれも偽陽性(§4.1)。

## 6. 改善候補(優先順、効果は greenbea 主ループ比)

1. **`d` ドリフト検査の修正 + 頻度削減**(`src/simplex/extended_dual.rs:3236-3256`)。
   - 残差ループ(`:3240-3244`)で `std.lb[j] == std.ub[j]` の列をスキップする(または `fresh_d_into` `:1181-1191` で固定列を飛ばし、`d[j]` を PRICE と同じ扱いにする)。これで検査が本来の意味(増分 `d` の丸め蓄積)を取り戻し、`D_DRIFT_TOL = 1.0` を意味のある値(例: 1e-6 相対; greenbea/80bau3b の実測上限 7.8e-10 から余裕あり)に締められる。
   - 頻度: x_B 検査(5 反復ごと)と同じ cadence にする必要はない。古典経路の `RESIDUAL_CHECK_MULTIPLIER = 20`(`simplex.rs:320`)に揃えて 20 回に 1 回(100 反復ごと)にするカウンタを `since_check` の隣(`:3160`)に足す。
   - 効果(実測): greenbea -165 ms(主ループ -5-6%、solve 全体 -4.8%)、他 12 問題 -4..-10%。経路は 13 問題全てビット一致。リスク: 低(93 問題で発火 1 回、それも偽陽性)。93 問題スイープでの確認は必要。
2. **chuzc1 の全候補ソートを min-heap の遅延プレフィックスに置換**(`src/simplex/extended_dual.rs:2505-2533`; `Cand` に `Ord`(`ratio.total_cmp` → `j`)を与え、`BinaryHeap<Reverse<Cand>>` を `candidates` と同様にループ前に 1 度確保して再利用、BFRT 走査(`:2520-2533`)を pop ループにし、pop 済みプレフィックスを `candidates` に戻せば Harris 第 2 パス(`:2598`)とフリップ適用(`:2649`)は無変更で動く。`bland_mode` の `sort_by_key(j)` 分岐は現状維持で可)。古典経路 `simplex.rs:4061-4114` が正確な雛形。`polish_with_true_bounds` の同じソート(`:3744`)にも適用可(293 反復なので効果は小)。
   効果(実測): -128 ms(主ループ -4%)、経路ビット一致(同じ全順序なので理論的にも同一)。リスク: 極小。
3. **再分解の定数削減(ピボット選択不変)**(`src/simplex/lu.rs:349-390`, `:403-470`, `:200-263`)。上限 295 + 141 + 43 = 479 ms(15%)、現実的には 150-250 ms(推定)。方針: (a) `MarkowitzState::rows` の `BTreeMap<usize,f64>` を、次数が平均 3.5 の行に見合うソート済み `Vec<(usize,f64)>`(二分探索・挿入 O(d))に替え、`col_rows` の `BTreeSet` も同様に; (b) `find_best_pivot` の走査順・早期終了・同点規則(`:369-370`)は一切変えない; (c) 変更後は greenbea で `refactor_count=58`、反復 6,601、目的関数値ビット一致を確認してから 93 問題スイープ。**行シングルトン先取り・HiGHS 型 `buildSimple` の剥がし・Dulmage-Mendelsohn 順序など「ピボット順を変える」案は §4.3 の通り greenbea を壊すので、本反復では不採用**(将来やるなら §4.3 の脆弱性そのもの -- 1e-9 級ピボットの受理 `:2389`、M 側停滞の検出 -- を先に直す必要がある)。
4. (中規模・別反復)**U の eta ファイルの連続メモリ化 / hyper-sparse 化**(`lu.rs:1640-1800`): U 段の solve 528 ms(16%)+ `commit_update` の密走査・確保 98 ms(3%)。HiGHS の `HFactor` は U を行・列両方向にパックし、BTRAN も DFS で hyper-sparse に解く(`docs/highs_dual_simplex.pdf`)。設計変更なので最小差分ではない。
5. (設計・別反復)反復数(2.6x)と §4.3 の脆弱性: extended dual の M 側解消の進み方、`TOL = 1e-9` 通過ピボットの扱い、摂動 base の差(HiGHS 5e-5 vs 本ソルバ 1.58e-6、反復#1 記録)。
6. 診断の常設化: `PROF_PHASES_EXT` に「drift check(x_B/d 別)」「factorize 内訳(state_new/find/eliminate)」「chuzc1 の sort」「U 段 solve」の行を足すと本分析の切り分けが 1 回で再現できる。`ENOMOTO_DEBUG_D_DRIFT_EXT` の出力には固定列除外後の残差を並記すべき。
