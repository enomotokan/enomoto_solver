## 0. 結論 (要約)

1. **LU 関連 (ftran+btran+refactor+ft_update) は 93 問合計 21.3 s の 55%** (11.7 s)。重い 6 問
   (dfl001, pilot87, fit2p, d2q06c, maros-r7, pilot = 17.8 s) では 58%、20〜500 ms の中規模 33 問では
   36〜45%、5 ms 未満の 18 問では 10%。**幾何平均に対しては中規模問題の FTRAN/BTRAN と再分解回数が主な
   レバー**で、5 ms 未満の問題では主ループ自体が solve の 19% しかなく LU 内の固定費は 1 割程度しかない。
2. **再分解トリガー (数値安定性パラメータ)**: `XB_DRIFT_TOL = 1e-8` (`extended_dual.rs:650`) は絶対値で、
   再分解直後の「新鮮な」残差 (問題ごとに 1e-16〜1e-6) と無関係。drift 起因の再分解 265 回のうち
   **90 回は直前の再分解から更新 10 回未満**、61 回は残差が「直前の再分解直後の残差の 3 倍未満」
   (再分解しても残差は下がらない)。pilot87 では冒頭 130 反復で 5 反復ごとに 10 回連続再分解 (~200 ms)。
   `ENOMOTO_XB_DRIFT_TOL=1e-7` の実験では 15 問中 11 問で反復数不変のまま再分解が 25〜70% 減
   (maros-r7 28→19, d2q06c 40→32, grow7 13→6, pilot4 10→3)、pilot87 は反復 +13% (経路変化)。
   → 案 A1/A2 (直前の新鮮残差に相対的な床、更新回数の下限)。
3. **微小値の非除去 (hyper-sparsity)**: FTRAN/BTRAN 結果の「非ゼロ」のうち |v|<1e-14 が dfl001 17.8%、
   greenbeb 42%、degen3 39%、80bau3b 55%、sctap3 75%、bnl1 44%。HiGHS は `kHighsTiny=1e-14` で
   FTRAN/BTRAN/eta 生成時に落とす。この crate は `!= 0.0` 判定のみなので、U 段の axpy・R eta の nnz・
   PRICE/xb_update の走査 (範囲外) が水増しされ、FT 更新の fill にもノイズが蓄積する。→ 案 A3。
4. **FTRAN の内訳**: 密な問題では R 段 (FT 更新の行 eta、gather 型で skip 不可) が R+U の 20〜42%
   (dfl001 7.0k/17.7k、maros-r7 18.0k/42.6k nnz-op/ベクトル)、U 段は eta ごとの `Vec` ヒープ + 48 B ヘッダ
   (`UEta`) の走査で dfl001 は 1 ベクトルあたり 2066 eta ヘッダ (99 KB) + 10.7k 要素 (172 KB)。
   疎な問題 (80bau3b, ship12l, stocfor2) では 1 ベクトルあたり 1.5k 演算に 9 µs (167 ops/µs、密な問題は
   ~500 ops/µs) と **O(m) の一括走査 (permute、`fill(0)`、全 eta 訪問、singles 訪問) が 7〜8 割**。
   → 案 C1 (平坦 U/R 格納)、C3 (τ FTRAN の L 段を GP 疎経路に: ビット同一)、C4 (BTRAN の O(m) 掃引削減)。
5. **再分解コスト**: dfl001 1089 ms (13.7%) のうちピボット探索 573〜590 ms (候補 120/step、探索上限到達
   28%)、eliminate 253 ms; pilot87 1221 ms (28%) のうち eliminate 605 ms、探索 334〜354 ms、
   `col_max_abs` 再走査 12M 要素。**fill 自体は良い** (pilot87 の同じ基底を SuperLU/COLAMD で分解すると
   L+U nnz 中央値 108.6k vs 本実装 54.9k; maros-r7 19.7k vs 15.3k) が、1 nnz あたりの速度は SuperLU の
   1/2〜1/3。ピボット順序再利用 (`factorize_reusing`) は 1 回 1.4〜2.3 ms で全分解の 1/10 なのに
   指数バックオフで **dfl001 86 回中 68 回、pilot87 61 回中 52 回スキップ**。→ 案 B1 (バックオフ緩和)、
   B2 (探索の行側走査 / 下限打ち切り)、B3 (末尾密ブロックの密 LU 切替)。
6. HiGHS との比較 (同 MPS、HiGHS 既定 presolve、threads=1): 再分解回数は同等かむしろ少ない
   (dfl001 86 vs 182、pilot87 61 vs 53、greenbea 17 vs 74)。差は再分解「回数」ではなく 1 反復あたりの
   FTRAN/BTRAN/再分解の単価と、drift 起因の無駄な再分解にある。

## 6. FTRAN / BTRAN の内訳と単価

refactor フェーズ (`extended_dual.rs:5021-5041`) は LU 分解 + `resync_x_b` (FTRAN) + `rebuild_rows` +
`fresh_d_into` (BTRAN + O(nnz(A)) PRICE) を含む。pilot の callgrind では `refactorize` (行構築 +
`factorize_reusing`) が 17.9%、うち `factorize` 14.65% (eliminate 8.0%、`find_best_pivot` 4.8%)、
`MarkowitzState::new` 1.3%、resync/fresh_d は 1% 未満。dfl001 の callgrind (命令数): `refactorize` 15.1%、
`factorize` 14.4% のうち **`find_best_pivot` 11.05%** (270,225 回、`row_get` 3.7M 回 0.6%)、`eliminate` 2.4%、
`MarkowitzState::new` 0.3%、`factorize_reusing_order` ≈0.5%、`fresh_d_into` 0.4%、`residual_norm_affine` 1.8%
(drift 検査 4,140 回)。dfl001 では探索が eliminate の 4.5 倍。

- **fill は良好**: 同じ基底行列を SuperLU で分解した L+U nnz (対角除く) の中央値: pilot87 108.6k (COLAMD)
  / 170.8k (MMD) vs 本実装 54.9k; maros-r7 19.7k / 30.5k vs 15.3k; **dfl001 398.1k / 891.3k vs 20.0k**
  (SuperLU 71.8 ms/回 vs 本実装 ~12 ms/回)。ピボット戦略 (`STABILITY=0.25`,
  Markowitz + 列バケット) は fill の点では問題ない。一方 SuperLU の分解時間中央値は pilot87 10.3 ms
  (本実装 ~18 ms、fill 2 倍で)、maros-r7 5.7 ms (本実装 ~4 ms)。**1 nnz あたりの eliminate 速度**が
  pilot87 で 3〜4 倍遅い (スーパーノード/BLAS の有無)。
- **ピボット探索** (`lu.rs:1086` `find_best_pivot`): dfl001 は 270k step で候補 32.5M (平均 120/step、
  `PIVOT_SEARCH_LIMIT=256` 到達 28%)、1 候補 18 ns なので単価は安く「候補数」が問題。バケットの列
  だけを走査し行側を見ないため、行次数が大きい dfl001 では score が `deg_col²` の早期打ち切り
  (`:1214`) を満たすまで次数 2..9 のバケットを全部舐める。HiGHS `buildKernel` は同じ count で列リストと
  **行リスト**を交互に探索し、`searchLimit=8` で打ち切る (8 は本 crate では経路を変え退行: `:275-299`)。
  pilot87 は候補 37/step だが `col_max_abs` の遅延再走査が 12M 要素 (`:1170-1188`)。
- **ピボット順序再利用** (`lu.rs:2017` `factorize_reusing`): 1 試行 1.4 ms (dfl001) / 2.3 ms (pilot87)
  = 完全分解の 1/10、採用率 55〜58%、採用時の nnz は完全分解と同程度 (再利用 fill 上限 1.25×)。
  しかし棄却後の指数バックオフ (`REUSE_MAX_BACKOFF=16`, `:2090`) で **dfl001 86 回中 68 回、pilot87 61 回中
  52 回、maros-r7 28 中 32 (複数回分)、pilot 34 中 26 回**が試行すらされない。`ENOMOTO_REUSE_FILL_LIMIT=2.0`
  の実験は採用率は上がる (dfl001 11/20→20/30) が再利用因子が密になり FTRAN が遅くなる問題
  (d2q06c ftran +24%、25fv47 +27%) があり、上限緩和ではなく**試行頻度**が正しいレバー。
- 再分解ごとの固定的な O(m)/O(nnz) 処理: `refactorize` の `vec![Vec::new(); m]` + push (`extended_dual.rs:1340`)、
  `factorize_diagonal` の試行 (`lu.rs:1883`、毎回)、`detect_border_columns` が `wants_bordered` (`:2083`) と
  `factorize` (`:2398`) で **2 回**、`is_dense_input` (`:2430`)、`MarkowitzState::new` の
  `col_buckets`/`row_buckets` `Vec<Vec>` ×2(m+1) (`:889-890`)、`FtLu::new` の eta ごと `Vec` ×2m +
  `HybridVec::pack` ×m (`:3692-3738`)、`u_entries: Vec<(usize,usize,f64)>` → `u_row: Vec<Vec>` の
  詰め替え (`:2531-2534`)。個々は小さく (pilot で合計 2% 程度)、L10 で一部試して不採用。C1 の平坦化と
  一緒にやると自然に消える。
- 原因分類: ピボット戦略は fill の点で良好 (**その他: カーネルの実装速度**)、探索は
  **ピボット戦略の違い** (行側探索なし)、再利用は **その他 (バックオフ方針)**。
