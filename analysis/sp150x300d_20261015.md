# sp150x300d が解けない原因の調査 (2026-10-15)

Mittelmann の MIP ベンチマークの sp150x300d (MIPLIB 2017) を HiGHS は一瞬で解くが、こちらは 10 分かけても終わらない。

## 結論

- **根の切除平面で下界が上がり切らず、木探索に持ち込まれているのが原因。** LP 緩和は HiGHS と同じ (34.14) だが、根のカットの
  後の下界は HiGHS 68.70 (最適値 69、目的値は整数なので根で証明) に対し、こちらは 56.64。木では 120 秒・8.7 万ノードで下界
  63.0 (gap 8.7%) までしか上がらない。
- カットを作る部分 (経路集約の集約行からの CMIR) は HiGHS と同等以上。差は **どのカットを LP に入れるか (カット選択) と
  根のループの進め方** にある。
- カット選択を緩めると (`ENOMOTO_T_CUTSEL_MIN_REL=0 ENOMOTO_T_CUTSEL_MAXPAR=0.9`) 根の下界は 65.3 になり **1.4 秒・159 ノード
  で解ける**。ただしこれを既定にすると MIPLIB 40 問の SGM が 32.83 → 38.00 (+16%) と悪化するので、そのままでは採れない。

## 問題の構造

450 行・600 列 (2 値 300)・非零 1200 の固定費用ネットワークフロー: 弧の流量 `x_j` (連続、上限 3049) と弧を開くかの
`y_j` (2 値、費用 1) で、`x_j <= 3049 y_j` (300 行) とノードのフロー保存の等式 (150 行) からなる。目的は開く弧の数の最小化。
前処理後は 329 行・476 列 (2 値 271)。両ソルバーとも VUB の係数を締めて (こちらは 85 個) LP 緩和は 34.136。

## 計測

| | 根の下界 | 結果 |
|---|---:|---|
| HiGHS 1.15.1 (threads=1) | 68.70 (16 ラウンド) | 0.1 秒、1 ノードで最適 69 |
| こちら (既定) | 56.64 (25 ラウンド、LP に 77 本) | 120 秒で時間切れ、下界 63.0、87k ノード |

計測パッチ付きの HiGHS (`scripts/highs_instrument.patch`) で分離器ごとに止めた結果 (根の下界、最適値は全て 69):

| HiGHS の設定 | 根の下界 | ノード | 時間 |
|---|---:|---:|---:|
| 既定 | 68.70 | 1 | 0.08 秒 |
| path mixing cut なし (`HIGHS_NO_MIX`) | 68.70 (経過も同一) | 1 | 0.07 秒 |
| tableau なし | 66.76 | 1 | 0.16 秒 |
| **path なし** | **55.65** | 130 | 0.47 秒 |
| mod-k なし | 68.68 | 1 | 0.07 秒 |
| implied bound なし / clique なし | 68.70 | 1 | 0.1 秒 |
| **path だけ** (tableau・mod-k なし) | **67.95** | 1 | 0.14 秒 |

**HiGHS では経路集約 (path aggregation) のカットだけで根がほぼ閉じる。** 当初は HiGHS 1.15 の path mixing cut (こちらの移植
`path_aggregation_highs` が除いている部分) を疑ったが、止めても経過は変わらなかった。

HiGHS の LP の行数の増分を見ると、1 ラウンドで LP に入るカットは 5〜35 本 (329 → 334 → 369 → 384 → 394 …) と少なく、
2 ラウンド目の 35 本で LP 値が 39.0 → 56.9 に上がる。こちらの既定はラウンドあたり候補 400〜600 本から 5〜30 本を採り、
1 ラウンドで 2〜4 しか上がらない。

### カット生成は同等

HiGHS の前処理なしの最初の分離ラウンドの経路集約の集約行 994 本 (`HIGHS_CUT_DUMP`) を、こちらの CMIR に通して比べた
(`cargo test --release --lib highs_cut_dump -- --ignored`): 両方でカットが出たもの 81 本 (平均効き目 HiGHS 0.3057、こちら
0.3048)、HiGHS だけ 2 本、こちらだけ 144 本。同じ集約行からはこちらも同等のカットを作れる。

### カット選択

既定の選択 (`select_cuts_hybrid`) には 3 つの絞りがある: 質が最良の 50% 未満は採らない (`ENOMOTO_T_CUTSEL_MIN_REL` 0.5)、
採ったカットとの平行度 |cos| が 0.3 を超えるものは捨てる (`ENOMOTO_T_CUTSEL_MAXPAR`)、1 ラウンド最大 50 本
(`ENOMOTO_T_MIP_ROOT_MAX_CUTS`)。最初のラウンドの候補 456 本のうち質の閾値を超えるのは 210 本で、平行度でさらに 31 本に
減る。この問題のカットは同じ `y_j` の係数が支配的なもの (例: `y_j >= 1 - (x_a + x_b)/11`) が多く、互いに平行と判定されやすい。

sp150x300d (時間上限 30〜60 秒、2 回):

| 設定 | 根の下界 | 結果 |
|---|---:|---|
| 既定 | 56.64 | 時間切れ (下界 62.6) |

MIPLIB 40 問 (1 問 90 秒、threads=1、4 問同時、`scripts/mip_bench/bench.py`。結果は
`sp150x300d_cutsel_base_20261015.json` / `sp150x300d_cutsel_c1_20261015.json`):

| | 解けた問題 | SGM |
|---|---:|---:|
| 既定 | 20 | 32.83 |
| `MIN_REL=0 MAXPAR=0.9` | 20 | 38.00 (+16%) |

悪化したのは mik-250 (15.8 → 時間切れ)、rout (28.6 → 78.8 秒)、neos-860300 (29.9 → 74.9 秒)、binkar10_1 (18.8 → 40.6 秒)、
nw04 (7.9 → 24.3 秒)。良くなったのは neos-911970 (時間切れ → 71.2 秒) だけ。誤答はなし。カットを多く入れると LP が重くなり、
木が大きくなる問題が多い (`MIN_REL` 0.5 を入れたときの評価と同じ傾向)。

## 残っている差と次の候補

- HiGHS は 1 ラウンド 5〜35 本で根を 68.7 まで閉じるが、こちらは選択を緩めて 100 本前後入れても 66.6 で止まる。HiGHS の
  ラウンドの中では、カットを LP に入れる前後に境界の伝播と根の被約費用固定 (`propagateRootRedcost`、暫定解 71 → 69 を使う)
  をしてから LP を解き直し、選択はラウンドをまたいだプール全体から行う (`HighsCutPool::separate`、効いていないカットは
  10 ラウンドで LP から外す)。どれが効いているかはまだ切り分けていない。
- 選択を緩める案は全体を悪くするので、問題の性質で切り替える必要がある。例えば
  (a) 既定の選択で根のループが止まった後に `MIN_REL=0 MAXPAR=0.9` で続ける第 2 段階 (今の `MIP_CUT_PHASE2` は HiGHS のスコアを
  使い、ラウンド上限 25 に先に当たるので sp150x300d では始まらない)、(b) 同じ整数変数の係数が支配的なカットどうしの平行度を
  連続変数の部分で測る、(c) 根の下界の伸びがラウンドごとに大きい (このラウンドで gap の数 % 以上) 間は採る本数を増やす。
  いずれも 40 問で SGM を確かめてから採る。

## 再現

```
curl -sSfL -o .miplib_cache/sp150x300d.mps.gz https://miplib.zib.de/WebData/instances/sp150x300d.mps.gz && gunzip .miplib_cache/sp150x300d.mps.gz
# HiGHS が読んだ LP から PyModel を作り、Model.solve(None, False, 60, None, None, 1, True) で解く (scripts/mip_bench/bench.py の worker と同じ)
ENOMOTO_MIP_LOG=1 ENOMOTO_T_CUTSEL_MIN_REL=0 ENOMOTO_T_CUTSEL_MAXPAR=0.9 python3 <上の手順のスクリプト>
```
