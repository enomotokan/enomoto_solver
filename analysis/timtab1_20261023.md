# timtab1 の後退 (mixoc) と HiGHS との差 (2026-10-23)

土台: `inv/heur-ls-20261023` の 7f0d7c3 (ソースの変更なし)。4 スレッド・60 秒、この機械 (4 CPU) で同じビルドを使った。
mixoc = `ENOMOTO_MIP_FJ_LMIP_MIX=1 ENOMOTO_MIP_SYM_ORIG_CUT=1`。ログは `analysis/heur_ls_20261023/logs/timtab1_*.log`。

## 結論

- timtab1 は、この機械では既定も mixoc も 60 秒で最適を証明できない (10 回ずつで 0 回)。HiGHS も 80 秒かかる。
- 最適値 764772 に届いた回数は、既定 7/10、mixoc 6/10。下界・ノード数も同じ程度。mixoc の後退は揺れの範囲で、mixoc に固有の原因は見つからなかった。
- `ENOMOTO_MIP_SYM_ORIG_CUT` の打ち切り値は timtab1 では一度も使われない ("kept as a cutoff value" は 0 回)。
- 最適値を最初から打ち切り値として与えても、証明に ENOMOTO は 95 秒、HiGHS は 94 秒かかる。証明の速さは HiGHS と同じ程度。
- 新しい手当ては入れていない。既存の切り替えで 3 つ試したが、どれも良くならなかった (下記)。timtab1 は mixoc を既定にすることを妨げる問題ではない、とみる。

## 依頼文の事実の確かめ (ba7f18b の JSON)

- 依頼文には「既定は 2 回とも 60 秒以内に最適 764772 を証明」とあるが、`inv/heur-ls-bench-20261023-s3` の JSON では、newdef6 は 2 回とも `time_limit`。
  - 目的値は 764772。下界は 721487・698221。
  - `table_bench_mix6.md` の「gap 0.000」は、主ギャップ (最適値との差) が 0 という意味で、証明したという意味ではない。
- mixoc6 は 776667・774858 (`time_limit`)、mix6 は 764772・768807 (`time_limit`)。
- 既定と mixoc の違いは「最適値に届いたか」だけで、2 回ずつでは揺れと区別できない。

- 届かない回の最終の値は、既定が 775212・774858・774858、mixoc が 780367・780367・774209・776667。
- 最初の暫定解:
  - 既定は 1.7〜3.9 秒に 0.93〜1.21e6。vector length diving、根の局所探索、RINS のどれか。
  - mixoc は 0.27〜0.29 秒に Local-MIP の 958055。10 回とも同じ。
- 木の開始は、既定 2.35〜3.87 秒、mixoc 2.66〜3.37 秒。
  - mixoc の根の RINS は、Local-MIP の解を中心にして見つからない (1.5 秒)。既定の RINS は 1.2e6 から 939183 を出した回がある。
- 根の下界は mixoc の方が少し高い (平均 619k と 611k)。
- 改善の出どころは、ほぼ全部が木の中の丸め ("tree rounding"・"tree randomized rounding"・"tree")。両設定とも同じ。
  - ヒューリスティクス役の ALNS は 60 秒で 11〜16 回呼ばれ、改善は 0〜1 回。
  - 限界効用の判定で、役から木の探索にすぐ戻る回が多い (`HEUR_ROLE_VERBOSE` の 30 秒の 1 回では、役にいたのは 0.88 秒)。
- 混ぜる形の FJ / Local-MIP のスレッド (`FJ_DEBUG`):
  - FJ は 40 回・0.40 秒で改善 0。Local-MIP は 7 区切り・1.33 秒で改善 3、最良 941k。
  - Local-MIP だけを 10 秒回しても 970k 止まり (`timtab1_tlm10_1.log`)。最適値の近くには届かない。
- `ENOMOTO_MIP_SYM_ORIG_CUT` の "kept as a cutoff value" は、mixoc の全ログで 0 回。
  - timtab1 では、対称性の行への並べ替え (オービトープ・lex-leader) が全部の解で成功している。

既定と mixoc の木の探索は、仕組みとしては同じ。
- mixoc の切り替えが木の中で効くのは、Local-MIP の名の解の lex 並べ替えと、ORIG_CUT だけ。ORIG_CUT は timtab1 では使われない。
- 違いは根の状態 (最初の暫定解・カット・時刻) だけ。そこから先の木は回ごとに大きく変わる (同じ設定でも、最適値に届く時刻は 12〜52 秒・届かないに散る)。

## 事実: HiGHS (1.15.1、4 スレッド、mip_rel_gap 0、この機械)

- 時間の上限なし (120 秒) で 80.0 秒に最適。ノード 9156 (`timtab1_highs_1.log`)。
  - 根: 569441 (1.0 秒、1 回目の再スタートの後)。
  - 19.5 秒に木から根へ再スタートし、根の下界は 630371 から 658398 に上がる。
  - 暫定解: sub-MIP で 816264・804458 (2.7・3.8 秒)。木 (T) で 768796 (45.6 秒)、764772 (58.9 秒)。
  - 下界は 59 秒で 703564。最適値が出た後の 21 秒で閉じる。
- ベンチマークの機械の 59.9 秒はぎりぎり。この機械では 60 秒に間に合わない。
- 打ち切り値 764772.5 を与えた場合 (`highs_cut.py`):
  - HiGHS は 93.8 秒・9649 ノード (`timtab1_highscut_1.log`)。
  - ENOMOTO の既定 (`ENOMOTO_MIP_CUTOFF=764772.5`) は 95.1 秒・29277 ノードで最適 (`timtab1_tdefcut_1.log`)。

推測:
- 60 秒の時点の下界は、ENOMOTO (690k〜744k) の方が HiGHS (約 704k) と同じか高い。
- ENOMOTO はノードの処理が速い (約 3 倍のノード数)。HiGHS は、木からの再スタートとノードあたりの下界の強さで、ノードを少なく済ませている。
- 最適解を早く知っていても、証明には両者とも 90 秒以上かかる。60 秒で証明できるかは、最適値をどれだけ早く見つけるかと、機械の速さで決まる。

## 推測と次の手

- mixoc で timtab1 が悪く見えたのは、木の中の丸めで最適値に当たるかの運による。2 組 (4 回) では揺れと区別できない。
- 10 回ずつでは、届いた回 7 と 6、時刻の中央値 28.7 と 30.8 秒で、差はほとんどない。
- 60 秒で証明するには、最適値を早く (10 秒前後で) 見つけることと、木の効率の両方が要る。
  - 改善のヒューリスティクス (ALNS のサブ MIP) は、timtab1 では近傍が大きすぎる (201 列のうち 201 列が自由の局所分枝・近接探索) か、時間が短すぎて当たらない。
  - 案 1: 木で解が良くなったときに、その解を中心にした小さい RINS / crossover を回す。
  - 案 2: HiGHS のような、木からの再スタート (19.5 秒に根の下界 630k から 658k)。
  - どちらも timtab1 だけでなく全体に効く変更なので、40 問 + 16 問での確認が要る。
- 目的値の不一致: なし。60 秒の回はすべて `time_limit`。最適と報告したのは打ち切り値付きの 1 回だけで、764772 (HiGHS と同じ)。
