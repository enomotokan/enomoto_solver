## 6. 当方で直すならどこか (優先順位つきの案、試作はしていない)

1. **集約行のカットの残し方とナップサックの被覆** (p200x1188c・mc11・beasleyC3 に効く見込み): 既存の `ENOMOTO_MIP_GEN_OLD=1` + `ENOMOTO_MIP_LIFTED_COVER=1` を
   今の版で P 58 問 × 種 1〜3 (60 秒) と M (600 秒) で広く測る。1 スレッド・種 1 の手元では 3 問で根の下界が SCIP 並みに上がりノードが 1/10〜1/100 になった。
   害の見込み: カットの候補と LP の行が増える (exp で 3.7 → 6.4 秒)。広く悪ければ、集約行ごとに「cmir に加えて被覆・flow cover が違反するなら 1 本足す」の
   中間の形 (SCIP の aggregation の形) を作る。
2. **根のループの上限 25 巡での止め方** (beasleyC3): 第 2 段階に入らずに 25 巡の上限で止まる経路で、直前の伸びが大きいなら延ばす。
   上限での延長 (`adapt_rounds`、直近 5 巡の伸び ≥ 全体の伸びの一定割合) は `ENOMOTO_MIP_CUT_ADAPT_ROUNDS` か HO6 の停滞の設定のときだけ働く作り
   (separation.rs 1889 行、事実)。beasleyC3 では直近 5 巡の伸び 7.6 が全体 482 の 1.6% で、既定の割合 5% には届かない (事実)。cutlen の不採用の記録が
   あるので、延ばすだけでなく 1 と組み合わせて測る。
3. **根の再スタートの起こり方** (mc11・beasleyC3): SCIP は「良い暫定解 (RENS) → 被約費用の固定 → 根で再スタート」で閉じる。当方は根の終わりの暫定解が悪く固定 0。
   1 で下界が上がると固定が起きるか (mc11 の genoldlc では再スタートが起きた) をまず見る。単独の手当て (RENS を強くするなど) は 1 の後に。
4. **衝突の制約の分離** (mc11 の logicor): SCIP は衝突から作った制約を根でカットとして分離している。当方にあるかを確かめてから (未確かめ)。
5. app1-1・neos-1171448・exp-1-500-5-5 は、今回の材料では案を出さない (主側の運・差が小さい)。

### 8.3 既定でも出るデバッグ解の衝突解析の出力 (rocI-4-11、親の依頼、2026-11-21)

既定 (`def_t4_s1`) と glc の直した版 (`glc_fl_t4_s1〜4`) で、デバッグ解つきに次の出力が出る (答えはどれも正しい −6020203)。
`conflict explanation … is wrong` が 48〜178 行、`analyze_multi conflict … cuts off` と `conflict (lits) cuts off` が 2〜12 行、`symmetric images`。

- **対称性ではない**: `MIP_DEBUG_SOL: 1 symmetric images` で、像はデバッグ解ただ 1 つ (rocI-4-11 には対称性の生成元がない)。
  そのため `ENOMOTO_MIP_NO_SYMMETRY` では回していない。
- デバッグ解自体は元の問題で厳密に実行可能 (`solviol.py`: 行の違反は最大 4.4e-16、整数性の違反 0)。
- **衝突はデバッグ解を厳密には切っていない** (`dbgconf.py`): `conflict (lits) cuts off` の全 26 行 (def 12・glc_fl 14) で、
  デバッグ解はリテラルの 1 つ (いつも連続列) を 9.46e-7〜9.97e-7 だけ満たさない。
  - 例: 衝突 `x119>=1 x203<=0 x2476>=0.9500009962` に対し、デバッグ解は x2476 = 0.95。
  - 診断の確かめはリテラルを 1e-6 の許容で見るので、許容の内側の外れを「切る」と出していた。
  - このリテラルは、デバッグ解を含まないノード (分枝の決定 x139 <= 0 をデバッグ解が破る、trace の `X`) での伝播の境界から来ている。
- `conflict explanation … is wrong` も同じ大きさ。不足 (必要量 − デバッグ解の活動量) は 1.1e-6〜4.0e-6 (相対で最大 3.2e-6)。
  大域的な境界の外れはなし。説明の必要量は FEASTOL の余裕を含み、デバッグ解は境界ちょうどにある。
  一方、「選んだ変更がデバッグ解で成り立つ」の確かめは 1e-6 の許容で甘い。そのための見かけの出力である。
- **判断**: 構造として正しい最適解を切る衝突は見つからない (誤答の元ではない)。
  - 残る影響は許容誤差 (1e-6) の大きさだけ。この種の衝突で連続列が最大 2e-6 程度締まっても、
    デバッグ解から 1e-6 以内の許容内の点は残る。
  - 診断を直すなら、リテラルを厳密 (例えば 1e-9) に確かめて、許容の内側の外れを別に数える
    (今は `dbgconf.py` で後から仕分ける)。ソルバーの動きを直す必要はないと考える。
- **診断の直し** (親の依頼、既定の求解の動きは変えない、デバッグ解つきのときだけ): 衝突 (`conflict (lits)`・`analyze_multi`) と説明 (`conflict explanation`) の確かめで、
  リテラル (説明では選んだ変更) をデバッグ解が外れる最大 (`domain::dbg_lits_gap`) を厳密に見る。外れが 1e-9 を越える (許容 1e-6 の内側だけで成り立つ) ものは
  `MIP_DBGTOL:` で 1 行だけ出し、本物 (`MIP_DEBUG_SOL:`) と分ける。rocI-4-11 既定 4 スレッド・種 1 (`def_tol`) で確かめた結果、衝突・説明の出力 30 行は
  全部 `MIP_DBGTOL:` になり、`MIP_DEBUG_SOL:` は解の確認と対称性の像だけ。cargo test 419 成功。
