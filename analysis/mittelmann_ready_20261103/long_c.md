# Mittelmann に出す前の確かめ: 長い時間の上限・問題の組 C (2026-11-03)

並列 6 セッションのうちの 4 (長い時間の上限、組 C)。今の既定 (canddet + p、土台 925975ae) と HiGHS (highspy 1.15.1) を、
4 スレッド・**600 秒**で 1 回ずつ、同じ機械 (クラウドの 4 コア・15 GB) で 1 ソルバーずつ順に解いた。

組 C (7 問): dano3_5、pg5_34、radiationm18-12-05、neos-4738912-atrato、sct2、neos-3627168-kasai、gen-ip054
(60 秒ではどちらも解けないがギャップの小さい問題)。

- ENOMOTO: `scripts/run_miplib_benchmark.py --worker-ours` (`ENOMOTO_MIP_THREADS=4` + `solve(..., 4)`)、`ENOMOTO_MIP_LOG=1`。
- HiGHS: `--worker-highs` (threads=4、mip_rel_gap=0、parallel は既定の choose)。
- 最大 RSS: この機械に `/usr/bin/time` が無いので、`run_long.py` が `os.wait4` の `ru_maxrss` (python の読み込みを含む) を取り、
  5 秒ごとに `/proc/<pid>/status` の VmRSS (子孫を含む合計) とログの大きさを記録した。
- **注意 (手順の誤り)**: 最初の 1 周は手元のチェックアウトが古いまま (fdcae947、p を既定にする前) でビルドして測ってしまった。
  気づいてから 925975ae でビルドし直し、ENOMOTO の 7 問を測り直した。下の表は 925975ae のもの。古い版の結果は
  `long_c/old_fdcae947/results_ours_600.json` に参考として残す (1 回ずつの揺れの大きさの参考になる)。HiGHS の結果は版に関係しない。

## 2. メモリとログは時間とともにどう増えるか

120 秒から終わり (600 秒か解けた時刻) までの RSS の増え方 (5 秒ごとの VmRSS から)。ログは `ENOMOTO_MIP_LOG=1` の標準エラー。

| 問題 | ENOMOTO RSS 120 秒 → 終わり (MB) | 増え方 (MB/秒) | 共有プールのノード (終わり) | ログ (KB/時) | HiGHS 増え方 (MB/秒) |
|---|---|---|---|---|---|
| dano3_5 | 404 → 427 | 0.08 | 0 | 255 | −0.04 |
| pg5_34 | 548 → 606 | 0.17 | 3500 (減っていく) | 596 | 0.17 |
| radiationm18-12-05 | 2809 → **9811** | **14.6** | **63742 (増え続ける)** | 437 | 0.52 |
| neos-4738912-atrato | 873 → 1018 | 0.63 | 4129 (減っていく) | 523 | 0.77 |
| sct2 | 979 → 1821 | **1.75** | 35424 (増え続ける) | 574 | 0.53 |
| neos-3627168-kasai | 839 → 1672 | **1.74** | 43602 (増え続ける) | 681 | 0 (75 秒で解けた) |
| gen-ip054 | 287 → 290 | 0.01 | 0 (最後に) | 1820 | 0.20 |

- **ログは問題にならない**: 多くて 1.8 MB/時 (進み具合の行が 2 秒ごと)。2 時間でも 4 MB 程度。利用者向けのログ (`ENOMOTO_MIP_LOG` なし) はさらに少ない。
- **メモリは「解けずに木が広がる問題」で直線的に増え続ける**。増えているのは共有プール (`pool_len`、スレッドの間で受け渡す開いたノード) で、
  各スレッドの手元の待ち行列は 1000 で頭打ちのまま、あふれた分がプールに積もる。1 ノードあたり sct2・kasai で約 28 KB、
  radiationm18 で約 110 KB (元の列 40623・行 7243 の問題。ノードが境界を密に持っている大きさ)。HiGHS は同じ問題で 0.5 MB/秒程度。
- 直線で延ばした見積もり (今の増え方が続くとして):
  - radiationm18-12-05: 600 秒で 9.8 GB、**15 GB の機械では約 15 分で足りなくなる**。2 時間なら約 100 GB。§4 の 1800 秒で確かめ、実際に 705 秒で OOM で落ちた。
  - sct2・kasai: 2 時間で 1.7 GB + 1.75 MB/秒 × 6600 秒 ≈ **13 GB**。16 GB の機械なら 2 時間もぎりぎり、8 GB なら約 1 時間で破綻しうる。
  - そのほか (解けた問題・プールが減っていく問題) は 1 GB 前後で頭打ち。
- Mittelmann 先生の機械のメモリと時間の上限はここからは確かめられなかった (組 A の記録と同じく plato.asu.edu は読めない) ので、
  「大きな問題で解けずに 1 時間以上回る」場合が一番危ない。

## 3. 下界が閉じない (負けの 3 問の共通点)

- sct2 の下界は **136 秒から 600 秒まで −231.027982 のまま一度も動かない** (古い版の 1 周でも同じ値 −231.02798217 で止まっていた)。
  主スレッドの待ち行列の lb もずっとこの値。下界がいちばん低いノード (たち) が処理されずに残っている疑いが強い。
- kasai も、主スレッドの待ち行列の lb は 988,500 前後 (暫定解 988,585.62 のすぐ下) なのに、報告される全体の下界は 985,319 で、
  共有プールに下界の低いノードが積もっている (600 秒で 43602 個)。
- 共有プールからノードを取るのは、`src/mip/solver.rs` の木の釣り合いで `pool_min < me − thr`
  (thr = `ENOMOTO_T_MIP_TREE_BALANCE_Q` 0.2 × (打ち切り値 − 全体の最小下界)) のときだけ。手元に 1000 個ずつノードを持つスレッドが
  暫定解の近くを掘り続け、プールの低い下界のノードは差が 2 割を超えないと取られない、という形がありうる (仮説。src は触っていない)。
  このとき (1) 下界が動かない、(2) プールが増え続けメモリが増える、の両方が説明できる。
- 長い時間の上限では 60 秒より効く問題なので、プールの最良下界のノードを一定の割合で必ず取る (HiGHS の最良優先との混ぜ方) か、
  ノードを境界の差分で持つかの手当てを、別の分担で確かめるとよい。

## 4. 1800 秒の確かめ (radiationm18-12-05)

メモリの増え方がいちばん大きい radiationm18-12-05 を、ENOMOTO だけ時間の上限 1800 秒で 1 回解いた。手元の機械 (15 GB) を守るため、
RSS が 13 GiB を超えたら止める安全弁 (`run_long.py --rss-cap-mib 13312`) を付けた。1 回目が横ばいの途中で安全弁に触れたので、
安全弁を 14.2 GiB に上げて 2 回目を回した。比べに HiGHS も 1800 秒で 1 回解いた。

| 回 | 終わり方 | 経過 (秒) | 最大 RSS (MB) | 暫定解 (最後) | 共有プールのノード | 結果 |
|---|---|---|---|---|---|---|
| ENOMOTO 1 回目 (`results_ours_1800_cap13g.json`) | 安全弁 (13 GiB) で止めた | 830 | 13477 | 17578 | 92738 (630 秒から横ばい) | 解なしで終わり (止めたため) |
| ENOMOTO 2 回目 (`results_ours_1800_oom.json`) | **コンテナのメモリの上限 (memcg) の OOM で SIGKILL** | 705 | 13635 (anon-rss 13.96 GB) | 17586 | 98484 (増え続ける) | 解なしで終わり (crash) |
| HiGHS (`results_highs_1800.json`) | **最適を示して終わり** | 1281.7 (`run()`) | 656 | 17566 (最適) | - | 65536 ノード |

RSS の推移 (MB、30 秒ごと):

- 1 回目: 120 秒 2955、300 秒 5177、450 秒 8443、600 秒 12253、630 秒 13082、その後 810 秒まで 13100〜13213 で横ばい
  (暫定解が 17930 → 17582 (680 秒ごろ) → 17578 (736 秒ごろ) と良くなった後、プールが 92000〜94000 で止まった)。
- 2 回目: 120 秒 2983、300 秒 4676、450 秒 7545、600 秒 11829、690 秒 13328 → 705 秒で OOM。暫定解は 200 秒から 17586 のままで、
  プールは 600 秒 92440 → 702 秒 98484 と増え続けた。
- 600 秒の計測 (暫定解 17588 を最初から持つ) でも 14.6 MB/秒で増えていたので、暫定解が良くなればプールの増加が止まる、とは限らない
  (1 回目の横ばいの理由は分からない)。

**この問題は 15 GB 級の機械では 12〜14 分で ENOMOTO がメモリを使い切って落ちる**。落ちると解 (17586 など、HiGHS より良い) も
下界も返らないので、Mittelmann の表では「解なし」になる。600 秒の計測でギャップ 0.14% と HiGHS (10%) に勝っていた問題が、
長い時間の上限では逆に負けになる。HiGHS は 1282 秒・656 MB で最適 17566 を示した (ENOMOTO の暫定解 17578〜17588 はまだ最適ではなかった)。

## 5. 判断

- **正しさ・時間の上限・ログ: 問題なし**。誤答・crash・警告なし (OOM を除く)、時間の上限は 0.4 秒以内で守る、ログは 2 時間でも数 MB。
- **メモリ: 長い時間の上限では破綻しうる (要対応)**。解けずに木が広がる問題では、共有プールに開いたノードが積もって RSS が直線的に増える。
  radiationm18-12-05 は 12〜15 MB/秒で、15 GB の機械では 12 分 (705 秒) で OOM により落ち、解も返さない。sct2・kasai も 1.7 MB/秒
  (2 時間で約 13 GB)。HiGHS は同じ問題で 0.5 MB/秒以下・最大 0.65 GB。Mittelmann 先生の機械のメモリ量次第だが、
  時間の上限が 1〜2 時間なら radiationm18 型の問題は落ちる見込みが高い。手当ての候補: (1) プールのノードを境界の差分で持つ
  (今は 1 ノード 28〜110 KB)、(2) メモリが一定を超えたらプールに積まず深さ優先に切り替える・最良下界のノードを優先して処理して捨てる
  (HiGHS のノードの上限の考え方)、(3) 最低限、メモリの上限の近くで探索を止めて暫定解と下界を返す。
- **長い時間での強さ: この組では HiGHS が上回る**。解けた数 4 対 6、600 秒では勝ち 3・互角 1・負け 3 だが、radiationm18 は 1800 秒では HiGHS が 1282 秒で解き ENOMOTO は OOM で落ちるので、実質は勝ち 2・互角 1・負け 4。負けのうち 3 問 (pg5_34・sct2・kasai) は
  最適値は見つけているのに下界が閉じない。sct2 は下界が 136 秒から一度も動かず、kasai はプールに下界の低いノードが残っている。
  共有プールのノードを取る条件 (§3) が、長い時間で下界を上げる妨げになっている疑いがある。
- 60 秒の 186 問の結果 (ENOMOTO が大きく上回る) は、主に「早く良い解を見つけて早く閉じる」問題の強さで、
  「長く回して下界を詰める」問題では弱いことがこの組から分かる。Mittelmann の表の時間の上限が長いなら、§2・§3 の 2 点を先に直すのがよい。

## 6. その他の気づき

- ログの進み具合の行の `nodes`・`open`・`lb` は**主スレッドだけ**の値 (`nodes` は主スレッドの数で、結果の `nodes` は全スレッドの合計。
  `open` は主スレッドの待ち行列で 1000 が上限。主の待ち行列が空のとき `lb inf` と出る)。全体の下界・プールの大きさは行の `pool_len` と
  結果の `bound` を見る必要がある。長い時間の計測でログを読むときに誤解しやすい。
- 再スタートの後は `MIP: finish done (…s)` などの時刻が再スタート後の求解の時計 (0 から) になる。dano3_5 は 144 秒で再スタートし、
  内側の `finish done (223.03s)` は全体の 367 秒。
- dano3_5 は返す前の解の研磨 (`polish_solution`、元の問題の前処理 + LP) に **16 秒**かかった (370.7 → 386.6 秒)。
  研磨は「時間を使い切っていれば LP を解かない」(`ENOMOTO_MIP_LATE_NO_RESOLVE`) が、上限の少し前に返ったときはこの 16 秒ぶん上限を
  超えうる (今回は超えていない)。
- 古い版の radiationm18 のログでは、再スタートの後に暫定解が「前処理後の問題で実行不能」として捨てられ (打ち切り値による固定のため)、
  ログの `ub` が最後まで inf と出ていた。打ち切り値 (`params.cutoff`) は引き継がれているので枝刈りには効いているが、ログは誤解しやすい。

## 再現手順

```
pip install -q highspy==1.15.1 maturin
git worktree add /tmp/wt925 925975ae && cd /tmp/wt925 && maturin build --release -o /tmp/whl \
  && pip install -q --force-reinstall --no-deps /tmp/whl/*.whl && cd -
# 問題の取得 (.miplib_cache/)
python3 -c "import sys; sys.path.insert(0,'scripts'); from pathlib import Path; import run_miplib_benchmark as r; \
  [r.fetch(n, Path('.miplib_cache')) for n in 'dano3_5 pg5_34 radiationm18-12-05 neos-4738912-atrato sct2 neos-3627168-kasai gen-ip054'.split()]"
D=analysis/mittelmann_ready_20261103/long_c
python3 $D/run_long.py --kind ours  --time-limit 600 --rss-cap-mib 13312   # ログは /tmp/long_c_logs/
python3 $D/run_long.py --kind highs --time-limit 600
python3 $D/run_long.py --kind ours  --time-limit 1800 --only radiationm18-12-05 --rss-cap-mib 13312   # 1 回目 (2 回目は 14540)
python3 $D/run_long.py --kind highs --time-limit 1800 --only radiationm18-12-05
python3 $D/summarize.py --tl 600   # summary_600.md と各問のログの要点 (*_excerpt.log)
```

ENOMOTO のログ全体 (1 問 25〜184 KB) は要点だけ `long_c/*_ours_600_excerpt.log` に残した (根の段階の行・終わりの統計・約 60 秒ごとの進み具合)。
