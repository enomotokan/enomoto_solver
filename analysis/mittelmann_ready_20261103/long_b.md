# Mittelmann に出す前の確かめ: 長い時間の上限・問題の組 B (2026-11-03)

並列 6 セッションのうちの 3 (担当: 長い時間の上限、問題の組 B)。60 秒ではどちらも時間切れで ENOMOTO のギャップが小さい 7 問
(neos-957323・uccase12・snp-02-004-104・dano3_3・gmu-35-40・gmu-35-50・tr12-30) を、今の既定 (canddet + p、コミット 925975ae) と
HiGHS (highspy 1.15.1) で 4 スレッド・**600 秒**で 1 回ずつ解き、勝ち負け・最大メモリ・ログの大きさ・時間の上限を確かめた。
ソルバーは同時に 1 つ (4 コア・メモリ 15 GB の機械、cgroup の上限 ≈ 13.6 GB)。

## 結論

- **メモリが一番の問題。uccase12 は ENOMOTO が OOM で落ちる** (起動から 325 秒、RSS 13.6 GB で cgroup の OOM killer に殺される。
  同じ問題を HiGHS は 410 秒・848 MB で最適まで解く)。同じ条件でもう 1 回・DSE を切った回・`MALLOC_ARENA_MAX=2` の回の 3 回とも
  同じように落ちた (下の「uccase12 の調べ」)。メモリが 16 GB 程度の機械では、Mittelmann の計測で uccase12 は「落ちた」になる。
- ENOMOTO の最大 RSS は HiGHS の **3〜21 倍** (gmu-35-40: 6.1 GB 対 0.37 GB、gmu-35-50: 7.9 GB 対 0.29 GB、tr12-30: 0.65 GB 対 0.12 GB)。
  開いたノードの数に比例して増える (gmu-35-40 で開いたノード 1 つあたり約 9 KB、始めから終わりまでほぼ一定。漏れではない)。
- 600 秒の勝ち負けは **HiGHS の勝ち 5・ENOMOTO の勝ち 1・互角 1**。60 秒では ENOMOTO のギャップが小さかった問題でも、長く回すと
  HiGHS が追い越す (tr12-30 は 317 秒対 512 秒、neos-957323 は 83 秒対 124 秒、gmu の 2 問は HiGHS の暫定解が良くギャップが小さい)。
  ENOMOTO が勝ったのは snp-02-004-104 (暫定解は同じ、下界が良くギャップ 1.25e-6 対 3.05e-5) だけ。
- 時間の上限は守る (求解 600.5〜600.8 秒、1800 秒の回は 1800.8 秒。超過は 1 秒未満。起動・読み込みを含めて 605 秒)。
- ログ (`ENOMOTO_MIP_LOG=1`) は小さい: 600 秒で 21〜182 KB、1800 秒で 411 KB (≤ 0.3 KB/秒)。2 時間でも 2 MB 程度で、破綻の心配はない。
- 両方が解けた 3 問 (neos-957323・dano3_3・tr12-30) の目的値は一致 (誤答なし)。`MIP: WARNING` は 0 件。ただし uccase12 の木の中の
  暫定解が HiGHS の最適値より 2.5e-3 小さい (下の「uccase12 の調べ」)。

## 1800 秒の確かめ: gmu-35-40 (メモリが時間とともに増え続けるか)

`log=True` で全スレッド (共有の待ち行列を含む) の済んだノード・開いたノードを 5 秒ごとに取った (`long_b/diag_gmu-35-40_1800.csv`)。

- 結果: 時間切れ (1800.8 秒)、目的値 -2406654.98・下界 -2406841.52 (ギャップ 7.75e-5)、ノード 265.9 万、最大 RSS 5.7 GB、ログ 411 KB。
  600 秒の HiGHS (ギャップ 1.96e-4) よりは良いが、600 秒の ENOMOTO (3.52e-4) からの縮みは遅い。
- **RSS は開いたノードの数に比例** (1 つあたり約 9 KB で一定)。開いたノードは 1000 秒ごろに約 65 万で頭打ちになり (暫定解の改善と
  下界の上がりで刈られる数と増える数が釣り合う。ソースに開いたノードの数の上限のしくみはない)、RSS も 5.6〜5.7 GB で止まった。
- 見積もり: 開いたノードが頭打ちになる問題なら何時間でも破綻しない。頭打ちにならない問題では、gmu の始めの増え方
  (開いたノード 約 2000 個/秒 × 9 KB ≈ 18 MB/秒) が続くと 1 時間で 60 GB を超える。gmu は小さい問題 (416 行・656 列) なので、
  1 ノードあたりの大きさは列・行が多い問題ほど大きい (下の uccase12 は 0.6 MB 以上)。

## uccase12 の調べ (OOM)

同じ問題を 600 秒で 3 回、少しずつ変えて回した (全スレッドの開いたノード数つき、`diag*_uccase12_600.csv`)。

| 回 | 落ちた時刻 (起動から) | 最後の済んだノード / 開いたノード | 落ちる直前の RSS |
|---|---:|---:|---:|
| 既定 (`long_ours`) | 325 秒 | (主スレッド 2261) | 12.8 GB (最大 13.6 GB) |
| 既定 + `log=True` (`diag_uccase12_600`) | 345 秒 | 8872 / 8859 (求解 268 秒) | 13.1 GB |
| `ENOMOTO_MIP_NO_DSE_ALL=1 ENOMOTO_MIP_POOL_DSE=0` (`diag_nodse_uccase12_600`) | 575 秒 | 24599 / 24592 (求解 480 秒) | 11.6 GB (最大 13.6 GB) |
| `MALLOC_ARENA_MAX=2` (`diag_arena2_uccase12_600`) | 約 330 秒 | 7952 / 7945 (求解 233 秒) | 13.4 GB |

- 済んだノードのほとんどが開いたまま残る (全体の下界は 11507.3679 から動かず、ギャップ約 3e-6 が閉じない)。HiGHS は 6949 ノードで閉じる。
- 気になる点: 木の中の暫定解 (進み行の ub) が 11507.40254 (既定の回、log=True の回) で、HiGHS が示した最適値 11507.40506 より
  **2.5e-3 (相対 2.2e-7) 小さい** (最小化)。前処理・再スタート後の問題での値で、元の問題で実行可能かは確かめていない
  (落ちたので最後の解は返っていない)。許容誤差の範囲の差とも読めるが、`analysis/uccase12_20261023.md` の「再スタート後の解を
  元の問題に戻すと実行不能」と同じ種類のことかもしれない。最後まで走れば「最適」と答える値が HiGHS より小さくなりうるので、
  メモリを直したら解の実行可能性と最終の値を確かめる。
- 既定では、開いたノードの増分 1 つあたり約 0.6 MB (求解 146→245 秒: 開いたノード +6046、RSS +3.5 GB)。分枝ごとに親の LP の基底
  (列 + 行、1 バイト)・DSE 重み (`dse_all()` の既定、`(u32, f32)` × 行 ≈ 68k 行で 550 KB)・基底で効くカットの番号を持ち、共有の
  待ち行列に出すノード (`SnapNode`) は基底と DSE 重み (`ENOMOTO_MIP_POOL_DSE` の既定) を Rc で共有せず写しで持つ。
  DSE を切ると増分は約 170 KB/ノードに下がり、落ちるまでの時間が 325 → 575 秒に延びた (DSE の保存が主な原因の 1 つ)。
- ただし、どの回も求解 100〜170 秒の間に、開いたノードが数千のうちに RSS が 1.5 → 8 GB に跳ねる (DSE を切っても同じ)。
  開いたノードの保存だけでは説明できない 5〜6 GB があり、木の RINS (105・131 秒に暫定解) などのサブ MIP の時期と重なる。
  `MALLOC_ARENA_MAX=2` で変わらないので、glibc のスレッドごとの領域に解放済みの領域が残るせいではない。何が持っているかは
  ヒーププロファイラで調べる必要がある (今回は src に触れないので見送り)。

## 気づいたこと・提案

1. uccase12 は Mittelmann で「落ちた」になりうる。少なくとも (a) 開いたノードに持つ DSE 重み・基底を間引く (HiGHS のように
   深いノードや待ち行列が大きいときは基底を持たない、DSE は f32 だけにして番号を持たないなど) と、(b) 求解 100〜170 秒の 5〜6 GB の
   跳ねの原因 (サブ MIP・スレッドごとの LP の写し?) を調べる必要がある。メモリの使い方に上限 (例えば開いたノードの合計の大きさが
   一定を超えたら基底・DSE を捨てる、深さ優先に寄せる) を置くのが安全。
2. 長い時間では HiGHS (実質 1 コア) に負ける問題が多い。木を閉じる速さ (tr12-30: ENOMOTO 18.8 万ノードで 512 秒、HiGHS 4.5 万ノードで
   317 秒) と、木の中の暫定解 (gmu) の差。60 秒の比べだけでは見えない。
3. ログ・時間の上限は問題ない。
4. uccase12 の木の中の暫定解が HiGHS の最適値より 2.5e-3 小さい (上の「気になる点」)。メモリを直した後に確かめる。

## 再現手順

```sh
pip install -q highspy==1.15.1 maturin
maturin build --release -o /tmp/whl && pip install -q --force-reinstall --no-deps /tmp/whl/*.whl
D=analysis/mittelmann_ready_20261103/long_b
P="neos-957323 uccase12 snp-02-004-104 dano3_3 gmu-35-40 gmu-35-50 tr12-30"
python $D/run_long.py ours 600 $P      # ENOMOTO (ENOMOTO_MIP_LOG=1)、long_ours.jsonl
python $D/run_long.py highs 600 $P     # HiGHS、long_highs.jsonl
python $D/run_long.py ourslog 1800 gmu-35-40            # 全スレッドの開いたノードつき (diag_worker.py、log=True)
python $D/run_long.py ourslog 600 uccase12
LONGB_TAG=_nodse ENOMOTO_MIP_NO_DSE_ALL=1 ENOMOTO_MIP_POOL_DSE=0 python $D/run_long.py ourslog 600 uccase12
LONGB_TAG=_arena2 MALLOC_ARENA_MAX=2 python $D/run_long.py ourslog 600 uccase12
python $D/summarize.py > $D/summary_table.md   # 表とログの要点 (logs/)
python $D/diag_series.py                       # 診断の回の推移 (diag*.csv)
```

- `run_long.py` は worker (`scripts/run_miplib_benchmark.py --worker-ours/--worker-highs`、ENOMOTO_MIP_THREADS=4) を子として起動し、
  5 秒ごとに /proc から RSS (子孫を含む和) とログの大きさを取り (`series`)、最大 RSS は `os.wait4` で得るその子の `ru_maxrss`
  (`/usr/bin/time -v` の Maximum resident set size と同じ値。この機械には /usr/bin/time がない)。
- ファイル: `long_b/long_{ours,highs,ourslog,ourslog_nodse,ourslog_arena2}.jsonl` (結果・推移)、`summary_table.md`、`diag*.csv`、
  `logs/*_summary.txt` (ENOMOTO のログの進み行の間引きと末尾 40 行)、`raw_logs.tar.gz` (全ログ、展開して 1.2 MB)。
