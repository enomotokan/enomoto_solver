# 開いたノードの数に比例して増えるメモリの持ち主と、減らす試作 ENOMOTO_MIP_MEMB (2026-11-04)

bench に使う環境変数: `ENOMOTO_MIP_MEMB=rcq` (試作の一番強い組み合わせ。`ENOMOTO_MIP_MEMB=1` は `rch`。既定では使わない)。
持ち物を見るだけなら `ENOMOTO_MIP_MEMB_DIAG=1` (`ENOMOTO_MIP_LOG=1` と一緒に。20 秒おきに標準エラー、動きは変えない)。

並列 3 セッションのうちの B (担当: 既定 (ae1497cc) でも開いたノードの数に比例して増え続けるメモリの持ち主を特定し、減らす試作を作る)。
A は「RSS を見て持ち物を捨てる上限」(`ENOMOTO_MIP_MEMCAP`)、C は supportcase18 の持ち主。4 スレッド、この機械は 4 コア・15 GB。
生データは `analysis/memcap_b_20261104/` (`runs.jsonl`・`cmp_summ.txt`・`bench58.jsonl`・`summ58.txt`・`logs.tar.gz`)。

## 要点

1. **持ち主は、開いたノード (ほとんどが共有の待ち行列の `SnapNode`) の DSE 重みと基底** (事実、一時の診断 `ENOMOTO_MIP_MEMB_DIAG` で数えた)。
   600 秒の既定の終わりで、CMS750_4 は共有の待ち行列に 31557 ノード・DSE 重み 1664 MB・基底 755 MB (1 つあたり 52.7 KB + 23.9 KB)、
   uccase12 は 4235 ノード・DSE 重み 1164 MB・基底 544 MB (1 つあたり 275 KB + 128 KB)。各スレッドの待ち行列は
   `ENOMOTO_T_MIP_TREE_LOCAL_CAP` (1000) で頭打ちになり、残りは全部共有の待ち行列に溜まる。
2. **RSS の伸びのほぼ全部をこれで説明できる**。CMS750_4 は求解 159 → 531 秒で RSS +1.92 GB に対し数えた持ち物 +1.77 GB、
   uccase12 は 191 → 450 秒で RSS +2.01 GB に対し +1.79 GB。数えていない分 (起動直後の分・LP・カットなど) はほぼ一定。
   増えたのは glibc の側 (4 KB 以上の確保) で、mimalloc の領域はほぼ一定 (既定)。
   `uccase12_mem2` で「目安に入らない約 100 KB/ノード」と書いた分は、既定の構成 (`MEM2=p`) では見えなかった (下の「考え」)。
3. 行の変更の記録 `row_log` は、カットを外すたびに LP の行数 (uccase12 で約 7 万) バイトの印 (`Vec<bool>`) を積み、切り詰めない
   (事実、コード)。ただし 600 秒では 8〜20 MB で小さい (外す回数が少ない)。試作 `r` で番号だけの形にした (ほぼ 0 MB)。
4. 試作 `ENOMOTO_MIP_MEMB=rcq` (基底を 2 ビットに詰める・DSE 重みを 8 ビットの対数にする・`row_log` の削除を番号で持つ) で、
   **最大 RSS が CMS750_4 3.37 → 1.24 GB (−63%)、uccase12 4.48 → 2.29 GB (−49%)**、240〜600 秒の伸びは 1 分あたり
   0.28 → 0.08 GB・0.46 → 0.11 GB。結果 (目的値・下界) は同じ、ノード数は CMS750_4 48589 → 48858、uccase12 8722 → 8091 (1 回、揺れの範囲か分けていない)。
5. 既存の `ENOMOTO_MIP_MEM2=pb`・`psb` は 600 秒ではあまり効かない (最大 RSS 2.9〜4.4 GB)。`b` の上限 (使えるメモリの 0.3 倍 ≈ 4.3 GB の
   0.9 倍) に持ち物の目安が届かず、捨てる処理が動かない。`s` (兄弟で写しを共有) は共有の待ち行列ではほとんど共有にならない
   (共有のノード 1 つあたりの基底が 23 KB のまま)。
6. 58 問 1 回 (4 スレッド・60 秒、`MEMB=rcq`): SGM 14.72 → 14.55 秒 (−1.2%)、解けた数 45 → 45、両方最適で目的値が違う問題・落ちた問題なし。
   60 秒では開いたノードが少なく、最大 RSS の和は 22.7 → 22.4 GB とほぼ同じ。**害は見えない** (1 回なので揺れの範囲)。

## 持ち物の数え方 (`ENOMOTO_MIP_MEMB_DIAG`)

- 各スレッドが 20 秒おき (`ENOMOTO_T_MIP_MEMB_DIAG_SECS`) に、自分の待ち行列のノードの持ち物 (境界の変更・基底・DSE 重み・効くカットの番号・
  強分岐の引き継ぎ・祖先の番号。`Rc` は共有の数で割る)、`row_log` の大きさ、潜りの兄弟の数と LU の写しの数を、主スレッドは加えて
  共有の待ち行列のノードの持ち物 (境界の変更・基底・DSE 重み・カットの基底) を `MEMB_DIAG:` の行で出す (`Solver::memb_diag_tick`)。
- 同時に `run_mem.py` が 5 秒ごとに `/proc/<pid>/smaps` を読み、mimalloc の 1 GB の領域・glibc の主ヒープとスレッドの 64 MB の領域・
  そのほかの無名の写像に分ける (`uccase12_mem1` の `watch_proc.py` と同じ分類)。`diag_summ.py <回>` が両方を時刻で並べる。
- heaptrack は、確保を全部 glibc に回した (`MIMALLOC_SIZE_LIMIT = 0`) デバッグ情報つきの wheel で uccase12 を 450 秒試したが、
  記録の手間で 46 ノードしか進まず、木の伸びは見られなかった (`ht_allglibc` の回)。持ち主は上の数え上げで足りたので、それ以上はしていない。

## 試作 `ENOMOTO_MIP_MEMB` (`src/mip/solver.rs`・`src/mip/queue.rs`・`src/mip/lp.rs`)

値 `1` で `rch`、または文字の組み合わせ。

| 文字 | 内容 |
|---|---|
| `r` | `row_log` の行の削除を、消した行の番号 (昇順の `u32`) だけで持つ (`RowEdit::DeleteIdx`)。当てはめ方は印の形と同じ (`RowEdit::retain_rows`) |
| `c` | 待ち行列 (`NodeQueue`) と共有の待ち行列 (`PoolNodes`) に置いている間、ノードの基底を 1 つ 2 ビットに詰める (`PackedStatus`、1/4)。取り出すときに戻す。続けて入れた兄弟が同じ基底 (`Rc`/`Arc`) なら詰めたものを共有する。待ち行列の中のノードの `basis` は `None` になる (待ち行列の中で基底を読む所はない) |
| `h` | ノードに保存する DSE 重み (`MEM2=p` の並び) を bf16 にする (`NodeDse::Half`、1/2、相対誤差 0.4% 以下) |
| `q` | `h` の代わりに 8 ビットの対数にする (`NodeDse::Byte`、1/4、2^((c−128)/8)、2^-16〜2^15.9 に丸め、相対誤差 4.4% 以下)。`1` には入らない |

- `ENOMOTO_MIP_MEMB_DIAG=1` (診断用): 上の「数え方」。
- 並行のセッション A の `ENOMOTO_MIP_MEMCAP` (`strip_frac`) と `MEM2` の `b` (`strip`) は、`c` の詰めた基底も捨てる。
- 既定の経路は変えていない (切り替えなしでは記録の形・待ち行列の中身は今までと同じ)。単体テスト 3 つ (`memb_pack_roundtrip`・
  `memb_queue_pack_basis`・`delete_idx_matches_mask`) を足した。`cargo test --release --lib` (rebase 後): 336 通過、0 失敗 (18 は無視の印)。

## 考え・次の手

- 開いたノードの数に比例する持ち物は、既定ではほぼ全部が基底と DSE 重み。持ち主がはっきりしたので、上限 (セッション A の MEMCAP) と
  組み合わせるなら、捨てる前に詰める (`MEMB=rcq`) 方が先に効く (同じメモリで 2.5〜4 倍のノードを持てる)。
- DSE 重みは、8 ビットに丸めても 600 秒の 2 問・58 問で結果に目立つ差は出ていない。重みはもともと近似 (戻した後の行の分は 1 か NaN) なので、
  さらに減らすなら共有の待ち行列のノードには DSE 重みを渡さない (`ENOMOTO_MIP_POOL_DSE=0`) 手もある (測っていない)。
- 基底は 2 ビットでも uccase12 で 1 ノード 27 KB。さらに減らすなら、親との差分 (分枝で変わるのはわずか) で持つ形がある (未実装)。
- `row_log` は切り詰めないので、カットの出し入れが多い長い求解では効いてくる見込み (`r` で 1 回あたり消した行の数 × 4 バイトになる)。
  待ち行列の最も古い `basis_epoch` より前を切り捨てる形も考えられる (未実装)。
- `uccase12_mem2` で「目安 1.46 GB に対し RSS 4.95 GB、約 100 KB/ノードが目安に入らない」としたのは、`MEM2=1` (全部入り) で `b` が捨てた後の
  回。今回の既定 (`MEM2=p`) では数えた持ち物と RSS の伸びがほぼ合う。差は、捨てた後もヒープの空きとして RSS に残る分 (glibc の 64 MB の
  領域は途中の空きを返さない) と見るのが自然だが、確かめていない。

## 再現手順

```sh
pip install -q highspy==1.15.1 maturin
maturin build --release -o /tmp/whl && pip install -q --force-reinstall --no-deps /tmp/whl/*.whl
D=analysis/memcap_b_20261104
bash $D/run_cmp.sh "def:" "memb:ENOMOTO_MIP_MEMB=1" "mem2pb:ENOMOTO_MIP_MEM2=pb" "mem2psb:ENOMOTO_MIP_MEM2=psb" \
  "membs:ENOMOTO_MIP_MEMB=1 ENOMOTO_MIP_MEM2=ps" "membq:ENOMOTO_MIP_MEMB=rcq" "membqs:ENOMOTO_MIP_MEMB=rcq ENOMOTO_MIP_MEM2=ps"
python $D/cmp_summ.py > $D/cmp_summ.txt; python $D/diag_summ.py def_CMS750_4_600 120
python $D/bench58.py 1 && python $D/summ58.py > $D/summ58.txt
```

- `run_mem.py` は `long_b/diag_worker.py` (log=True、4 スレッド) を子として起動し、5 秒ごとに RSS と smaps の分類を取る。`run_cmp.sh` は
  `ENOMOTO_MIP_MEMB_DIAG=1` を付ける (動きは変えない)。結果・推移 (`series`)・`MEMB_DIAG` の行 (`diag`) は `runs.jsonl`。
- `diagdef_*` の回は、heaptrack 用の wheel のビルドと同時に走ったので比べる表には入れていない (持ち物の数え方の確かめに使った)。
- 計測した wheel は f2750cff + この試作 (rebase 前)。push の時点で上流に `MEM3_TINY_MARGIN` の既定の変更 (86f8b130) などが入っている。
