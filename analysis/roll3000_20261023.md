### 1-4. ノードの LP の重さ (`ENOMOTO_PROF_TREE_PAR=1`・新しく足した `ENOMOTO_MIP_RESTORE_DIAG=1`)

最初の LP の反復数と時間 (`prof_1`、既定、スレッドごと。tid 3 はヒューリスティクス役から戻ったスレッド):

| | 潜りの子 | 自分の待ち行列から取ったノード | 共有の待ち行列から取ったノード |
|---|---|---|---|
| tid 0 | 292 回・121 反復・31 ms | 239 回・311 反復・95 ms | 0 回 |
| tid 1 | 318 回・87 反復・23 ms | 322 回・245 反復・58 ms | 5 回・**4022 反復・789 ms** |
| tid 2 | 160 回・78 反復・18 ms | 265 回・356 反復・105 ms | 2 回・**4139 反復・985 ms** |

- 自分の待ち行列から取ったノード:
  - 最初の LP は潜りの子の 3 倍ほど重く、各スレッドの時間の 3〜5 割を占める。
  - RESTORE_DIAG で、保存した後に LP に足されたカットの行の数ごとに分けた (`rdiag_1`):
    - 0 行: 中央値 42 反復
    - 11〜50 行: 108 反復
    - 51 行以上: 255〜297 反復
  - 兄弟へ戻るとき (行は増えていない) は中央値 193 反復。
  - ノードでの分離を止めてもこの重さは残った (1-3) ので、カットの行が増えることだけでは説明できない (推測)。
- 共有の待ち行列から取ったノード:
  - 1 回が根から解くのと同じくらい重い (根の LP は 2700 反復)。
  - 原因 (事実):
    - 渡す基底は、列と元の行の状態だけを持つ。
    - 受け取った側では、カットの行をすべて基底にする。
    - 渡した側で非基底 (効いていた) だったカットの数だけ、基底変数が余る。
    - それを `set_basis` の修復 (構造変数を後ろから外す) に任せるので、主にも双対にも実行可能でない基底から解くことになる。
  - `rdiag_2` の余りと反復の組: 余り 15〜36 の 14 回で 2002〜5653 反復。
  - 既存の `ENOMOTO_MIP_TREE_SHARE_CUT_BASIS=1` (同じカットがあればその状態にする) の場合 (`rdiagcb_2`):
    - 余りが 0 になった 3 回は 54〜198 反復。
    - 余りが残った 8 回は 647〜5643 反復のまま。
    - mc11 で「共有から取ったノードは 2173〜5242 反復のまま」(analysis/mc11_r3_20261020.md) だったのと同じ形。

## 2. 手当て: `ENOMOTO_MIP_TREE_POOL_BASIS=1` (試作、既定は切ってある)

- 変えたファイルと関数: `src/mip/solver.rs` の `Solver::open_from_pool`・`Solver::snap_of`、関数 `tree_pool_basis`。
- 中身:
  - 渡す側: 非基底だったカットの行の (ハッシュ, 状態) も付ける (`TREE_SHARE_CUT_BASIS` と同じ)。
  - 受け取る側: 当てはめても基底変数が余るなら、受け取った基底を使わない。今の LP の基底 (このスレッドの直前のノードの最適基底で、双対実行可能) から解く。
  - 余りが 0 なら、受け取った基底を使う (今までどおり)。
- 診断:
  - `ENOMOTO_MIP_RESTORE_DIAG=1`: 基底を戻した最初の LP ごとに `RESTDIAG:` の行を出す (スレッド・種類・保存後に足された行と消えた行・不一致・共有の余り・反復)。
  - `ENOMOTO_PROF_TREE_PAR=1` の `TREEPAR: ... cut basis:` の行に、受け取った基底を使わなかった回数を足した。
- 効き目 (`rdiagpb_1`、1 回):
  - 共有の待ち行列から取ったノードの最初の LP: tid 3 は 20 回・100 反復・33 ms、tid 1・2 は 1 回ずつ 202・175 反復。手当てなしでは約 4400 反復・0.65〜1 秒。
  - この回はノード 2805、60 秒の下界 12819。
- 残り:
  - 各スレッドが初めて共有の待ち行列から取るノード (木を分け合う始め) には基底が付かないことがあり、2000〜5000 反復かかる (`nots*` の pool 1 回)。今回は直していない。
- `cargo test --release --lib`: 313 件通過。

## 4. 既定にする候補か (推測を含む)

- roll3000 では効果が見えないので、roll3000 の手当てとしては候補にしない。
- 共有の待ち行列から取ったノードが根から解き直すのと同じくらい重い、という形は roll3000 に限らない (mc11 にも記録がある)。
  - 手当ては「余るときは今の基底を使う」だけで、余らないときは今までと同じ。
  - 40 問 + 16 問の 1 組で、木を分け合う問題 (mc11 など) を見る価値はある。
- roll3000 を 60 秒で証明するには、木の下界の伸びを 1.5 倍ほどにする必要がある。この機械では HiGHS も届いていない。
  - 手がかり: 自分の待ち行列から取ったノードの最初の LP が潜りの子の 3 倍重いこと (1-4)。HiGHS の強分岐の多さ (1-3)。

## 5. 確かでない点

- 自分の待ち行列から取ったノードの LP が重い理由:
  - 保存後に足されたカットの行が多いほど重いが、ノードでの分離を止めても重い。
  - 大域的な境界の締め付け (証明・衝突で 7599〜21208 本) で、親の基底から遠くなっている可能性がある。確かめていない。
- 60 秒の下界の揺れは 12551〜12819 と大きい。3 回ずつでは、100 程度の効果は区別できない。
- この機械の HiGHS が前の機械 (46.3 秒) より遅い理由。
