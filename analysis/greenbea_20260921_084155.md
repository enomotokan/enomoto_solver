# greenbea 実行時間分析(自己改善ループ 反復#6, runtime 段)

対象: NETLIB `greenbea`(2392 行 x 5405 列, 30,877 非零; `.netlib_cache/mps/greenbea.mps`)。
選定理由(`scripts/select_problem.py`): runtime 段、`ours 2.71s vs highs 0.26s (ratio ~10.6x)`、93 問題中で最悪の比(5 回目の選定)。
対象コミット: `05a2f2f`(main; PR #6 の `residual_norm_affine` 統合を含む。PR #7(d ドリフト検査の固定列除外・頻度削減、chuzc1 のヒープ化)は未マージで本チェックアウトには含まれない)。HiGHS 1.15.1(`highspy`)、4 コア、`perf` なし。
全数値は本セッションでこの環境で実測。推定は明記する。計測用の一時パッチ(`src/simplex/lu.rs` / `src/simplex/extended_dual.rs`、すべて `ENOMOTO_TMP_*` 環境変数ゲート)は `git checkout` で撤去し HEAD のホイールを再ビルド・再計測済み(`git status` は本ファイル以外クリーン)。

既存 3 本の分析(`greenbea_20260921_021218.md` = 偽 infeasible、`030127.md` = 同・許容誤差不整合と BIG_M フォールバックの誤答、`070407.md` = ドリフト検査の残差走査と再分解単価)と重複する指摘は繰り返さず、本反復で新たに計測した 2 点(eta ファイル肥大による solve コストの増大、ピボット探索の BTreeMap 参照)と、**それらの修正を阻む正答性の脆さ**を主題にする。

## 結論(要約)

1. **正答性の確認**: HEAD では両者 `optimal`、ours -72555248.12985753 / HiGHS -72555248.12984587(相対差 1.6e-13)。ハーネス `benchmark_highs --only greenbea`: ours 2.717 s / HiGHS 0.243 s = **11.17x**。直接呼び出し 2.73-2.86 s(6 回)。
2. **分類: (c) 1 反復が重い**(前回と同じ大分類)。主ループ 6,601 反復 x 387-397 us(HiGHS 83 us/反復、presolve off でも 136 us/反復)。突出した 1 項目はなく、内訳は 再分解 18%、eta ファイル肥大による solve 超過 14%(新規計測)、ドリフト検査 10%、新鮮な分解での btran/ftran/dse 20%、price/chuzc1/chuzr/xb/ft_update 他 35%。
3. **新規に特定したボトルネック 2 点**:
   - **eta ファイル肥大**(`src/simplex/lu.rs` の `FtLu`、`r_etas` ループ `:1811-1820, :1877-1883, :1951-1968`): FT 更新列が再分解まで最長 695 本、eta の非零は最大 132,836(L+U 自体は 8,561)まで伸び、btran+ftran+dse+bfrt の 1 反復コストは新鮮な分解直後の 80 us から 500 更新超では 386 us(4.8 倍)になる。新鮮時との差の総和は **377 ms = 主ループの 14%**。再分解のトリガーはドリフト(57 回)だけで、コスト起点のトリガー(HiGHS の synthetic clock、43 回 rebuild / 2,524 反復)が無い。同じ現象を greenbeb(12%)・d2q06c(17.5%)・pilot(8%)・25fv47(8.5%)でも確認(§2.3)。
   - **ピボット探索の BTreeMap 参照**(`lu.rs::find_best_pivot` `:349-390`): 1 回の求解で 11.0M 回の `rows[i].get(&j)`(O(log d) の木探索)を行い、探索 190 ms(factorize 400 ms の 48%)。スコア `(row_deg-1)*(col_deg-1)` は値を引かなくても分かるので、**スコアが現在の最良より厳密に悪い候補の値参照を省く**だけで参照は 1.35M 回(-88%)、factorize は 390 → 265 ms(-32%)、主ループは -4..-5%。**ピボット選択は完全に同一**(反復数・再分解数・目的関数値がビット一致)で、これが本反復の最小修正案(§5-1)。
4. **重要(正答性の脆さ、声高に報告)**: 上記以外の速くなり得る変更 — 行シングルトン優先、探索打ち切り、更新回数上限、eta 上限の引き下げ — はピボット経路を変える。**同種の 14 構成のうち 6 構成で greenbea は誤答**(偽 `infeasible` 3 件、`optimal` -72465273.02 の誤答 3 件)、2 構成は 15-38 s に爆発した。誤答はすべて同一機序: 拡張双対法の中で **`refactorize` が特異基底を返す**(または反復上限)→ `None` → `simplex.rs:2972-3000` の `BIG_M=1e7` フォールバック → 真の最適解に `x=3.3e8` があるため必ず誤る(反復#1 §5・反復#2 (C) で指摘済み、**HEAD でも未修正**)。HEAD が正答しているのは現在の丸め経路が偶然この穴を踏まないからで、正答性は「経路の運」に依存している。ピボット経路を変えるいかなる高速化も、§5-2 の安全網なしには適用できない。

lazy-get の正当性: `find_best_pivot` は候補を `score < best_score || (score == best_score && |v| > best_pivot_abs)` でしか採用しないので、`score > best_score` の候補は値 `v` を読む前に棄却して構わない。スコアは `row_degree`/`col_degree`(配列)だけで決まり、値参照(BTreeMap 探索)は安定性判定と同点比較にしか要らない。早期終了条件(`best_score == 0`、`best_score <= deg^2`)も候補の順序も不変なので、選ばれるピボットは完全に同じ。実測でも反復数・再分解数・目的関数値がビット一致。

## 4. 根本原因の分類

**(c) 1 反復が重い、その中で「再分解の単価 x 再分解間隔」の経済が壊れている**(分類上は「その他: 再分解コスト構造」)。

- 再分解 7.5 ms/回(fill ゼロの 2,056 行基底; 半分が BTreeMap 参照 11M 回のピボット探索)が高いため、更新列を最長 695 まで伸ばす運用になっており、その結果 eta ファイルが L+U の 10 倍まで肥大して FTRAN/BTRAN/DSE を 4.8 倍に遅くする。直接 18% + 間接 14% = 主ループの 32%。HiGHS は再分解が安価なので synthetic clock で 59 反復ごとに rebuild し、この超過を払っていない。
- presolve・退化・DSE 精度・停滞は HEAD の経路では原因ではない(§1.5)。
- ただし **正答性が経路依存**(§3.1): 拡張双対法が特異基底/反復上限に落ちた時のフォールバックが誤答を `optimal` として返す設計(反復#2 (C))が未修正のため、経路を変える高速化は 40% の確率で誤答に化ける。runtime 段の改善として安全に適用できるのは経路保存の変更(§3.2)だけ。

## 5. 改善候補(優先順)

### 5-1. [本反復の最小修正・経路保存] `find_best_pivot` の値参照をスコア判定の後ろに移す

- 場所: `src/simplex/lu.rs` `MarkowitzState::find_best_pivot`(HEAD `:349-390`)、内側ループ `:361-375`。
- 変更: `for &i in &self.col_rows[j]` の本体で、`let Some(&v) = self.rows[i].get(&j)` **より前に** `let score = (self.row_degree[i] - 1) * (self.col_degree[j] - 1);` を計算し、`if score > best_score { continue; }` を入れる。その後は現行どおり値を引き、安定性判定 → 採用判定(`score` は再計算しない)。10 行未満。
- 効果(実測): BTreeMap 参照 11.0M → 1.35M、`factorize` 390 → 265 ms(-32%)、refactor 465 → 340 ms、主ループ 2,556 → 2,422-2,469 ms(**-4..-5%**)、総時間 2.73 → 2.59-2.64 s(比 11.2x → ~10.7x)。ピボット選択・反復数・再分解数・目的関数値はビット一致。
- リスク: 数値経路ゼロ変更。他問題も同一経路のまま `factorize` が速くなるだけ(pilot のように再分解が主ループの 49% を占める問題ではより大きく効くはず; 未計測)。93 問題スイープでの状態・目的関数の不変確認は形式的に必要。
- 任意の追加(経路保存、+1%): `extended_dual.rs:2362-2379` の PRICE で `std.lb[j] == std.ub[j]` を非零ごとに引く代わりに、ループ前に `Vec<bool>` の固定列マスクを 1 度作って参照する(price 258 → 232 ms)。

### 5-2. [正答性の安全網 — 経路を変える変更の前提条件] `BIG_M` フォールバックの誤答を `optimal` として返さない

- 場所: `src/simplex.rs::solve_lp_dual` の `None` 分岐(`:2972-3000`; `solve_std_form_decomposed(&std, true)` の結果を `unscale_result` でそのまま返している `:3000`)。
- 変更(最小): フォールバックの結果が `Optimal` のとき、`BIG_M` 代入された境界(`build_std_form_presolved(.., clamp_unbounded: true)` が `:1055/:1058` で `±BIG_M/dj` を書いた列)のいずれかが最適解でその境界に張り付いている、または元単位で `|x_j| >= BIG_M*(1-1e-6)` なら、`Status::Optimal` ではなく非最適の状態(例: 既存の反復上限系ステータス、または新設)で返す。greenbea は `x_4180=3.3e8, x_4175=2.3e8 > 1e7` なので必ず検出される(dfl001 も同様: 反復#2)。
- 効果: 誤答が `select_problem.py` の正答性段に見えるようになる(現在は runtime 段の裏に隠れて「正答」扱い)。速度は変わらない。
- 根本対策(未検証・別反復向け): `extended_dual.rs` の再分解サイト(`:3264` `lu = refactorize(std, &basis_pos)?`、および `:2461/:2551/:2616/:2870`)で `None` が返ったら `None` を上に投げるのではなく、HiGHS の "possibly singular basis" 処理のように**直前のピボットを取り消して(`basis[r]` に退出変数を戻し `nb_status` を復元)一つ前の基底を再分解・再同期し、その (r, q) を次の chuzr/chuzc から除外して続行**する。あるいはピボット確定前に、更新済み LU(`lu.update_count() > 0`)上で `|alpha_full[r]| < 1e-7 * max(1, ‖alpha_full‖∞)` なら、候補を飛ばす(反復#1 実験 D: 双対実行可能性が壊れる)のではなく `:2610-2628` の Infeasible サイトと同じく「再分解して chuzr/chuzc をやり直す」。どちらも本セッションでは実装・検証していない。

### 5-3. [経路を変える高速化 — 5-2 の後にのみ] 再分解単価と eta 上限

- (a) `lu.rs::find_best_pivot`: 列バケット走査の前に `row_buckets[1]` の行シングルトンを O(1) で採る(§3.1 #1; 自明ステップの探索 84-88 ms → 8-10 ms)+ 非自明ステップの探索打ち切り(候補発見後 4-8 列で打ち切る Markowitz search limit; 非自明 105 ms → ~15 ms)。合わせて `factorize` 6.8 → 3.5-3.6 ms/回。
- (b) `extended_dual.rs:3184` の eta 上限を `super::FT_BUMP_LIMIT_FACTOR`(64, 古典経路と共有)からモジュール定数 16 に下げる(§3.1 #11: 363 us/反復, -6%)か、更新回数上限を `ft_max_updates(m)=3m` から 200-300 に(#2, #5)。本来は HiGHS 型 synthetic clock(累積 eta 非零 x solve 回数 が factorize コストを超えたら再分解)が正しい形で、(a) で再分解が安くなるほど最適列長は短くなる(§1.4 の概算)。
- 効果の上限: 直接 18% + 間接 14% = 32% のうち現実的には 10-15%(#5 の 349 us/反復が実測の最良)。リスク: §3.1 のとおり現状では 14 構成中 6 構成が誤答。5-2 なしには適用不可。

### 5-4. [設計変更・別反復] 反復数(HiGHS の 2.6x; 同サイズ 3.5x)、BTreeMap ベースの `eliminate`(2.1 ms/回)と `MarkowitzState::new`(0.6 ms/回)、密走査の `u_solve_into`/`l_solve_into`。ドリフト検査の `fresh_d_into`(143 ms)と chuzc1 ソートは PR #7 が対象なので本反復では扱わない。
