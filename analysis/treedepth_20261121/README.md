# 木の中の分離を深さ別に見る (2026-11-21)

問い: 根に近いノード (深さ 1〜5 程度) の木の中の分離 (`tree_sep`) は、深いノードより伸び・寿命・効き目が明らかに大きいか。大きいなら、分離の予算を深さに応じて配り直す (根に近いほど重く) 価値がある。

## 結論

- **浅いノードの分離が深いノードより明らかに効く、という傾向は見えない。設計案 (2^−深さ に比例した予算) は書かない。**
  - 1 ラウンドの伸び (打ち切り値までの差に対する割合) の中央値は、深さ 1-4 の方が 9 以上より小さいか同じ。4 スレッドで 10 問中 9 問、1 スレッドで 9 問中 6 問がそう。浅い方が大きいのは tr12-30 (4 スレッド 0.021 / 0.017、1 スレッド 0.015 / 0.0057) と、1 スレッドの neos-911970 (0.0066 / 0.00037) で、ほかは 1 スレッドの noswot の 2e-14 / 0 という誤差の差だけ。
  - 手間あたりの伸び (伸びの和/1e9 ticks) は、4 スレッドで tr12-30 以外のすべての問題で深い方が大きいか同じ。1 スレッドでは neos-911970 (10.7 / 2.7) だけが浅い方で大きい。
  - 浅いノードの分離で残った回数が多いのは、カット 1 本あたりの張った回数 (部分木が大きいから) だけ。misc07 (144 / 44)、tr12-30 (1086 / 657)、mik-250-20-75-4 (39 / 19) では浅い方が多い。一方 neos5 (8.6 / 42)、kasai (165 / 249)、uccase12、mzzv11 では逆。LP に入っていた回あたりの張った割合で見ると、そろった傾向はない。
  - いまの既定でも、浅いノードは数が少ないのでほぼ全部が分離されている (深さ 1-4 で分離する率はほぼ 1)。木の分離の手間のうち深さ 1-4 の分は 0〜10% (mzzv11 だけ 33%)。浅いところを重くしても、増やせる手間の量はそもそも小さい。
  - 寿命 (LP にあった回数) の中央値は、浅い方が長い問題と短い問題が半々 (misc07 655 / 259、tr12-30 1259 / 1888 など)。
- **問題をまたいで、木の分離の効き目 (伸びの和/手間) を一番よく説明するのは始めのギャップ。根で閉じた割合では説明できない。**
  - 順位相関は、始めのギャップで 0.60 (4 スレッド)、0.68 (1 スレッド)。根で閉じた割合では −0.32 と −0.26。
  - 「閉じた割合/手間 × ギャップ」は 4 スレッドで 0.41、1 スレッドで −0.20 で、ギャップだけの方が安定している。
  - 張った回/LP にあった回との相関は、どの量でも弱い (0.0〜0.55)。
  - 問題は 10 問ほどで、misc07 (ギャップ 0.5、伸び/手間 43) が順位を引っ張っている。傾向として読む程度にとどめる。
- 予算を配り直すなら、深さよりも問題 (またはその時点の部分木) の残りのギャップを測った量に比例させる方が、データとは合う。ただし、ここでは試作の設計までは進めない (下の「次に試すなら」に短く書く)。

## 計測

- 診断 `ENOMOTO_MIP_TREEDEPTH_DIAG=<ファイル>` (src/mip/treedepth.rs) は既定では動かない。診断ありとなしで結果が変わらないことを確かめた: misc07 (1 スレッド) は 12054 ノード・132026 反復で一致、noswot は 23695 ノードで一致。`cargo test --release --lib` は 419 passed。
- ビルド: 64249baf4 (診断を入れた木) と 56f044aa2 (根の値と木の始めの値を追加)。`pip install -e .` で入れた。
- 問題と制限時間:
  - M (600 秒): fiball、csched008、neos-3627168-kasai、neos-957323、mzzv11、tr12-30、uccase12
  - P (60 秒): neos-911970、misc07、neos5、mik-250-20-75-4、noswot
- 設定: 4 スレッドで種 1・2、1 スレッドで種 1。合わせて 36 本。neos-957323 は根で解けて木がない。
- 値は最小化形で、定数項込み。
  - 伸び = (解き直した LP の値 − 分離前の値) / (打ち切り値 − 分離前の値)。打ち切りになったら 1。
  - 寿命 = 木のカットが年齢で LP から外れるまでに LP にあった回数。最後まで残ったカットは寿命の中央値から除く。
  - 張った = 双対値が非零で、行が非基底。
- 根で閉じた割合 = (木の始めの下界 − 最初の根の LP の値) / (最良の解の値 − 最初の根の LP の値)。最初の根の LP の値は、カット・再スタートの前の値。
  - 診断の記録は木の探索の終わりに書かれるので、再スタートの前の求解は記録に残らない。そこで、最初の根の LP の値は rootlp.py が 1 スレッド・種 1 の stderr の `MIP: root LP` から拾った。
  - 手間は「木の始めまでの手間」(前処理・ヒューリスティック・再スタートを含む ticks)。
  - 主スレッドの最後の求解の根のカットのループだけを見ると、再スタートの後なので小さく出る (neos-911970 で 0.03 になった)。

## 次に試すなら (試作はしない)

- 深さで予算を変える前に、問題の残りのギャップに応じて木の分離の総量を変える方が見込みがある。
  - 例: 木の分離の ticks の上限の係数 (いまは経過の手間の 0.1 倍) を、閾値を置かずに、その時点の相対ギャップ (|ub−lb|/max(|ub|,1)) の単調な関数にする。
  - ギャップが 1e-5 程度の uccase12 や、根で下界が最適値に届いている fiball では、木の分離はほとんど何も生まない。
- 深さを組み合わせるなら、2^−深さ ではなく、ノードの LP の値と打ち切り値の差 (そのノードで残っているギャップ) を重みにする方がデータと合う。今回の伸びはその差で割った割合で、深さとの関係ははっきりしなかった。

## 台本と生データ

- run.py: 計測。途中から再開できる。`python run.py res.jsonl 4:1,4:2,1:1`
- res.jsonl: 各計測の結果。run.out は進み具合。
- logs/res_<問題>_t<スレッド>_s<種>.jsonl.gz: 診断の生の記録 (スレッドごと・求解ごとに 1 行)。.log は stderr のうち `MIP: node diag` / `adaptive` / `tree search` の行。
- rootlp.py → rootlp.jsonl: 最初の根の LP の値 (1 スレッド、種 1)
- summ.py: 深さ別の表と問題をまたいだ表。`python summ.py res.jsonl 4 > summ_t4.md`
- corr.py → corr.md: 問題をまたいだ順位相関
