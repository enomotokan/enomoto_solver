# EQUIV2 の再スタート後の誤った組の調査 (2026-10-22)

ブランチ `inv/equiv2-bug-20261022`。症状は analysis/term_check_20261022.md §3 (uccase12 を `ENOMOTO_MIP_PROBE_EQUIV2`
(+`_RESTART`) で解くと、再スタート後の前処理で `1356 pairs found, used` の回だけ根の LP が 12043.6 になり、誤った最適
11507.9037 を返す。HiGHS の最適値 11507.405)。

## まとめ

- **原因 (事実)**: 同値の組そのものは正しい。誤りは組の等式を足した問題の前処理の **係数の強化 (`tighten_coefficients`)**。
  伝播の誤差の分だけ緩めた **幅 1e-9 の連続列** y (`[0, 1e-9]`) と 0-1 列 x の行 `x + y <= 1 - 1e-9` は、最大活動量が右辺を
  2e-9 しか越えない (許容誤差の範囲で冗長な) 行だが、係数の強化がこれを `2e-9 x + y <= 1e-9` に縮め、x = 1 を厳密に切る
  (x = 1 なら y <= -1e-9)。元の行では x = 1 の違反は 1e-9 (許容誤差の内) だが、縮めた行は係数が 1e-9 の大きさなので、
  行の尺度をかけた LP では違反 0.5 に当たり、x <= 0.5 の行として効く (HiGHS の LP の双対値は 5.2e9)。こういう行が 90 本でき、
  最適解の x = 1 の列 (unit commitment の稼働の列) を切っていた。
- **修正 (18def7a、回帰テスト baad69b)**: 縮めた後の係数 `M - b` が `1e-6 (1 + |b|)` 以下の行 (許容誤差の範囲で冗長) は縮めない。既定の動作。
  `ENOMOTO_MIP_COEF_TIGHTEN_TINY` で以前どおり縮める。前処理のログに縮めなかった数を出す
  (`tightened N coefficients (skipped K in rows redundant within tolerance)`)。回帰テスト
  `tighten_coefficients_skips_rows_redundant_within_tolerance` と、小さな MIP の端から端までの回帰テスト
  `tiny_range_columns_keep_exactly_feasible_optimum` (以前の動作では -9.81、正しくは -10.9) を足した
  (`cargo test --release --lib` 310 件通る)。
- **既定の 1 巡目 (`ENOMOTO_MIP_PROBE_EQUIV`) に当たるか**: 同値の検出の論理には穴はない (2 巡目の組も正しかった)。
  穴は係数の強化にあり、係数の強化は既定のすべての前処理 (元の問題・再スタート後・サブ MIP) で動くので、**既定の経路も
  同じ穴を持っていた** (幅 1e-9 の列は既定のプロービングが作り、再スタートで大域的な境界として引き継がれる)。幅 1e-9 の
  連続列を入れた乱数の小さな MIP では、既定の設定 (EQUIV2 なし) で厳密に実行可能な最適解を切る例が出る (§5、seed 41)。
  MIPLIB の 55 問 (10 秒) では既定の設定でガードが働いた問題はなかった (前処理の結果は以前と同じ)。

## 1. 再現 (事実)

- `benchmarks/equiv2_bug_20261022/rep.py`: uccase12 を `ENOMOTO_MIP_PROBE_EQUIV2=1 ENOMOTO_MIP_PROBE_EQUIV2_RESTART=1`、
  4 スレッド・45 秒で解く。1 回目で再現した (`repro/res.jsonl`: 最適 11507.90369、根の LP 12043.596、再スタート後の
  前処理で `1356 pairs found, used` → 678 組)。
- 診断用の書き出しを足した (18def7a に含む):
  - `ENOMOTO_MIP_DEBUG_DUMP_RESTART=接頭辞`: 再スタートで渡す問題 (`接頭辞_r1.mps`)。打ち切り値 11507.903679 (暫定解 11507.903690)
    で、最適値 11507.405 より上 (最適解は打ち切り値の下に残るはず)。
  - `ENOMOTO_MIP_DEBUG_DUMP_PROBE=接頭辞`: プロービングの入力 (`接頭辞_N.mps`)、見つけた組 (`接頭辞_N.pairs`)、組の等式を足した
    問題 (`接頭辞_qN.mps`)。dump_mps は目的の定数を書かないので、値の比較では定数を足す。
- 書き出した再スタート後の問題 (`keep/uccase12_restart_r1.mps.gz`) を `ENOMOTO_MIP_PROBE_EQUIV2=1 ENOMOTO_MIP_NO_LP_PROBE=1`
  で直接解くと、同じ 1356 組・678 組が出て根の LP 12004.79 (+定数 38.80 = 12043.6) になる (決まった再現。`off2/e2e_old.log`)。

## 2. どこで切られるか (事実、HiGHS 1.15.1 で確かめた)

値は元の問題の目的値に直したもの。

| 問題 | LP | MIP | 最適解 x* (HiGHS) |
|---|---|---|---|
| プロービングの入力 (再スタート後、組の検出の前。`probe_2`) | 11507.356 | **11507.405** | — |
| 同 + 678 組の等式 | 11507.356 | 11507.405 | 組を 1 つも破らない |
| 組の等式を足した問題 q (プロービングで締めた境界を含む。`p_q0`) | 11507.356 | (x* が全部の行・境界を満たす) | 実行可能 |
| q の前処理の結果 (`p_1`) | **11528.53** | | 違反 1e-9〜4e-7 の行がある |
| 修正後の q の前処理の結果 (`off2/fix_0`) | 11507.356 | | |

- **どの組も最適解で成り立つ**: 678 組 (全部 `x_i = x_j`、1 つの稼働の列と 9 列おきの 4 列 = 5 時刻の稼働が等しい) は HiGHS の
  最適解 (`keep/uccase12_restart_probe_input_highs_sol.txt.gz`) で全部成り立ち、組を足しても MIP の最適値は 11507.405 のまま。
  EQUIV2 の 2 巡目の論理 (含意を足した定義域での同値の検出) は正しかった。
- q の前処理 (`presolve_mip`) が LP を 11528.5 に上げる。手順を止めて切り分けると (`off2/`、q を直接前処理):
  `ENOMOTO_MIP_NO_COEF_TIGHTEN` で整数列に小さな係数 (< 1e-6) を持つ行が 90 本 → 0 本、`ENOMOTO_MIP_NO_ROW_MERGE` では 90 本のまま。
- 係数の強化の入力と出力 (一時的な出力で確かめた): 入力 `x28 + y98 <= 1 - 1e-9` (x28 は 0-1、y98 は連続 `[0, 1e-9]`、
  目的の係数は負) → 出力 `2e-9 x28 + y98 <= 1e-9`。同じ形で `x28 + y80 + y89 + y98 <= 1 - 1e-9` → `4e-9 x28 + ... <= 3e-9` など。
  x* は x28 = 1、y = 0 で、元の行は 1e-9 だけ破り (許容誤差の内)、縮めた行は 1e-9 だけ破るが行の大きさが 2e-9 なので、
  尺度をかけると x28 <= 0.5 になる。HiGHS の LP (単体法・前処理なし・内点法とも 11528.53) の双対値はこの行で 5.2e9。
- 幅 1e-9 の連続列の出どころ: 元の問題の前処理のプロービングが締めた連続列の境界 (`131 bounds tightened`、プロービングは
  「連続列の境界は伝播の誤差の分だけ緩めて」問題に入れる) が 0 のところ 1e-9 になり、再スタートの問題に大域的な境界として
  入る (`restart_r1` に 131 本。元の問題の前処理後には 0 本)。再スタート後のプロービングでさらに締めて `[0, 2e-9]` のものも出る (q で 360 本)。
- 右辺 `1 - 1e-9` は、組の代入で 0-1 列がまとまったクリーク型の行 (`x + Σ y <= 1`) から、前処理が幅 1e-9 の列を上限 1e-9 で
  消した分 (推測。どの手順が上限で消したかは追っていない)。これ自体は許容誤差の内の変化。

## 3. 打ち切り値と最適値 (事実)

- 再スタートに渡した打ち切り値 11507.903679 > 最適値 11507.405。HiGHS で解いた再スタート後のプロービングの入力の MIP の最適値は
  11507.405 で、再スタートの問題 (打ち切り値で締めた境界・21 本のカットの行を含む) は最適解を含んでいた。打ち切り値・カット・
  前の求解からの持ち越しは原因ではない。

## 4. 既定の 1 巡目 (`ENOMOTO_MIP_PROBE_EQUIV`) と既定の経路

- コード: 1 巡目の組の検出は 2 巡目と同じ形 (x_j = 0 で x_k = 0、x_j = 1 で x_k = 1) で、伝播が正しい限り正しい。穴は
  組の後の前処理 (係数の強化) にあり、組の代入とは独立に、**どの前処理でも** 幅の極めて小さな連続列と 0-1 列の行が許容誤差の範囲で
  冗長になれば起きうる。組の代入はクリーク型の行の 0-1 列をまとめるので、この形の行を作りやすい。
- 既定の設定では、プロービングが境界を締めると (`Some(true)`) 組を代入しない (`probe_equiv_fix` が偽で
  `represolve_after_probe` が何もせず返る) ので、uccase12 の再スタート後 (678 組を見つけるが締め付けもある) では代入されない。
- 実験 (修正後のビルドで縮めなかった数を数えた):
  - uccase12 既定 × 3 (60 秒): `skipped` は 0 (ガードは働かず、以前と同じ動作)。最適 11507.480 / 11507.4109 / 11507.4098
    (既定の相対ギャップ 1e-4 の内)。
  - 55 問 × 既定・EQUIV2+RESTART (10 秒、`check55.jsonl`): ガードが働いた (`skipped` > 0) 問題は 0 (§5)。
  - 乱数の小さな MIP (`fuzz_tiny.py`、幅 1e-9 の連続列とクリーク型の行、既定の設定 = EQUIV2 なし): §5。

    持ち、HiGHS の解が 1e-9〜2e-9 だけ行を破る (許容誤差の内) ものが多く、どちらが正しいとは言えない食い違いを含む。

    この調査の誤り (厳密に実行可能な解を切る) とは別 (推測。手順は追っていない)。

## 6. 残り・推測

- 右辺 `1 - 1e-9` を作った手順 (幅 1e-9 の連続列を上限で消した手順) は特定していない。修正は係数の強化の側だけ。
- 根本の一因はプロービングが連続列の境界を 0 でなく 1e-9 として入れること (伝播の誤差の分の緩め)。幅が許容誤差より小さい列を
  1 点に固定する (HiGHS の前処理は幅が許容誤差以下の列を固定列として消す) 手当ても考えられるが、入れていない。
- ecf2cfd (再スタート後の問題では EQUIV2 を使わない) は残してある。原因は特定・修正したので戻してよいはずだが、戻すかは別に計測して決める。
