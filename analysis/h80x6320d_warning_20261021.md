# h80x6320d の MIP_WARNING=1 (計測 LDb・cutdse) の調査 (2026-10-21)

計測: 4 CPU・15 GB の Linux (クラウドのコンテナ)、`ENOMOTO_MIP_THREADS=4`・60 秒、`scripts/run_miplib_benchmark.py --worker-ours` を直接呼び
stderr を残した。ビルドは 7ce7077 (= develop d7a3136 + LP が終わらない調査の試作) と origin/develop e5b4982。

## 何が起きたか

計測 LDb (ブランチ inv/lpd-b-20261021、設定 cutdse = `ENOMOTO_MIP_CUT_DSE_EXACT=1`) で h80x6320d が optimal・49.28 秒・目的値 6382.09905
(正しい最適値) で終わったが、要約に MIP_WARNING=1 (stderr の "MIP: WARNING" が 1 行) が付いた。計測スクリプトは警告の件数しか残さない
(本文は正常終了のとき捨てる) ので、どの警告かは再現で確かめる必要があった。

7ce7077 の "MIP: WARNING" は 4 種類 (src/mip/solver.rs):

| # | 文 | 出る場所 |
|---|---|---|
| 1 | the shared best value … is better than the main thread's incumbent … at the end of the tree search | 木の探索の終わり (主) |
| 2 | nodes with lower bound … below the prune limit … remained …; not reporting optimality | 同上。状態を NotSolved にする |
| 3 | a solution from another thread was rejected | `take_inbox` (従の解を主が受け付けられなかった) |
| 4 | a tree thread ended with a better solution … than the main thread's | `join_workers` (従を待った後) |

(親の挙げた「根の被約費用を別の LP から取った」はこのビルドにはない。) #2 は状態を not_solved にするので、optimal で終わった今回の回ではない。

h80x6320d の 38 + 46 回では一度も出ていない)。

## 原因 (警告 #4 の誤報)

主と従 (木を分け合うスレッド) の解の受け渡しは次の順:

1. 従は解を見つけると `try_incumbent` で受信箱 (`Portfolio::inbox`) に解を入れ、その後で共有の最良値 (`Portfolio::best`) を公表する。
2. 主は待ち行列の頭 (`snap_sync` → `take_inbox`) で受信箱の解を受け取る。
3. 主の打ち切り値 (`prune_limit`) は自分の暫定解と共有の最良値の小さい方から作る。

主の待ち行列が空で共有の待ち行列も空のとき、主は `pool_acquire` の中で従が終わるのを待つが、**この待ちの間は受信箱を見ない**。
全ての従が待ちになって `done` になると主はループを抜け、`join_workers` で従を止めて待つ。7ce7077 の `join_workers` は、従の結果の目的値
(`r.objective`、従の暫定解) を **受信箱を受け取る前の** 主の暫定解と比べて #4 を出し、呼び出し側はその後で `take_inbox` を呼んでいた。

したがって、探索の終わり際 (主が待っている間) に従が解を見つけると、
- 従は解を受信箱に入れ最良値を公表する → 主・他の従はその値で木を全て刈り、`done` になる
- 主は `join_workers` で「従が主より良い解で終わった」と警告する (受信箱の解をまだ受け取っていないだけ)
- 直後の `take_inbox` でその解を暫定解にし、正しい最適値で optimal を報告する

という流れになり、「optimal・正しい目的値・警告 1 行」という観測に合う。ヒューリスティクス役の従 (4 スレッドのうち 1 本、`heur_role_run`)
は共有の待ち行列の `busy` に数えないので、木の従と主が刈り終えて `done` になったときに ALNS のサブ MIP の解が届く、という形でも起きる。
h80x6320d は根の RINS が最適解を見つけるかどうかが回ごとに変わる (見つけないと木の従が見つける) 問題で、計測の回はこの経路だったと見る。

警告 #3 (従の解を主が拒んだ) は同じ問題 (`snap_p` は主の `p` の写し) で同じ `is_feasible` を通した解なので起きにくいが、完全には除けない
(oneopt・連続変数の解き直しの後の解の実行可能性の判定が LP の許容誤差で揺れる可能性)。拒まれた場合は共有の最良値だけが下がり、木はその値で
刈られるので、終わりに #1 が出る。7ce7077 は #1 を警告だけ出して optimal と報告していた。

## 判定

計測の回の警告は、**解は正しく届いていて答えの正しさには関わらない誤報** (#4 の比べる順の問題) と判断する。ただし #1 の扱い (最良値を
公表した解が主に届かないまま optimal と報告する) は答えの正しさに関わりうる穴だったので、合わせて塞いだ。

## 修正 (このブランチ)

- `join_workers`: 従の結果の目的値と解を集めてから `take_inbox` で受信箱を受け取り、その後で比べる。受け取っても従の方が良ければ
  (受信箱で拒まれた・失われた)、従が返した解そのもの (`MipResult::x`、主の問題の空間) を `try_incumbent` で暫定解に試し、それでも悪ければ
  #4 を出す。`ENOMOTO_MIP_TREE_DIAG` で、従を待った後に受信箱から解を受け取ったことを出す。
- 木の探索の終わり: #1 (共有の最良値が主の暫定解より良い) のときは #2 と同じく NotSolved で終わる (下界は従・共有の待ち行列の下界と
  打ち切り値の小さい方)。`ENOMOTO_MIP_TREE_NO_END_CHECK` で以前どおり。

`cargo test --release --lib`: 308 件通過 (このコンテナでは pyo3 のリンクに `RUSTFLAGS="-C link-args=-lpython3.13"` と別の `CARGO_TARGET_DIR` が必要だった)。
修正版の挙動は上の表の最後の行 (警告 0、受信箱から受け取った診断行が 2 回)。パッチは origin/develop e5b4982 にもそのまま当たる (`git apply --check`)。develop の
`join_workers` も同じ順なので、取り込むなら develop にも入れる。

## 付記

- 再現の試行で、`ENOMOTO_MIP_NO_ROOT_RINS=1` にすると木の従が最適解を見つける回が多くなるが、主が待ち行列の頭で受け取れていて警告は出ない
  (競合の窓は主が `pool_acquire` で待っている瞬間だけで狭い)。
- 結果 JSON には正常終了のときの stderr が残らない。警告の本文を残すなら `run_miplib_benchmark.py` の `run_worker` で
  "MIP: WARNING" の行を結果 (`mip_warning_lines`) に入れるようにした。
