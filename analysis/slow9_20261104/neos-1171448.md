## ログで見たこと (事実)

- 根はどの回も同じ。根の LP は −309 (= 最適値) で 1.1〜1.5 秒、木の探索の始まりは 20〜21 秒、暫定解は 2.4〜3.4 秒に Local-MIP、
  10〜12 秒に RENS で −306〜−307.5。根の再スタートはない (newly fixed 0)。下界は根で最適値に届いているので、解き終わる時間は
  **−309 の解が見つかる時刻**で決まる。
- 遅い回: −309 は木の 480〜590 ノード目に他のスレッドの tree mutation で見つかる (def 71.7 秒・75.8 秒、nofstop 1 回目 62.4 秒)。
- 速い回 (nofstop 2 回目): 39.4 秒、202 ノード目に tree RINS で −309.0 が見つかる。
- MEMCAP はどの回も上限 12.2 GB に対して最大 RSS 0.5〜0.6 GB。段階の読み出しは 0/0/0 で、strips などの削減は何も起きていない。
- **解発見スレッドはどの回も起動していない** (ログに `find thread started` がない)。根で Local-MIP の良い解が入って `fj_poor` にならないため。
  `ENOMOTO_MIP_QIU_FIND_STOP_GAP` は `poll_find_thread` (`src/mip/solver.rs` の 14864 行目あたり) で解発見スレッドがあるときにだけ読まれ、
  ソースのほかの場所では使われていない。したがって、この問題では nofstop と def は同じ処理を通る。

## 結論

- **揺れ**。def の幅 (64〜79 秒) は preall4bs の幅 (40〜80 秒) に入っていて、5 つの既定のどれかが系統的に遅くしているという証拠はない。
  時間は「木のヒューリスティクス (tree RINS / mutation) が −309 をいつ見つけるか」で 40 秒前後か 70 秒前後に分かれる二山の分布になっている。
  前の測りの 27 秒 → 77 秒は、別の機械の 1 回ずつで、速い山と遅い山を 1 回ずつ引いた差と見るのが自然 (27 秒はこの機械の速い山よりさらに速い。機械の差と思われる)。
- nofstop は 5 回中 4 回が速い山、def は 7 回中 0 回で、数だけ見ると偏っている (この 12 回だけでのフィッシャーの正確確率は約 0.01)。
  しかしログでは nofstop が変える処理 (解発見スレッドの止め方) をこの問題は一度も通らない。**偶然の偏りと推測する** (スレッドの計時のずれで
  tree RINS が早く当たるかどうかが決まる)。mem3 (nomem3)・forceq (noforceq)・bs (nobs) は 2 回ずつとも遅い山で、これも def と区別できない。
- 推測: 速い山の確率は設定によらず 2〜4 割程度ありそうで (19 回 + ログ 4 回の計 23 回中 6 回)、def の 0/7 も偶然の範囲と思われる。
  確かめるなら def と nofstop を 10 回ずつ回すのがよい (今回はやっていない)。
