# neos-911970 の遅れ (前の既定 6 秒 → 新しい既定 15 秒) の切り分け (2026-11-04)

背景: `analysis/mitt600_20261103.md` の「新しい既定での測り直し」節で、neos-911970 が前の既定 5.6 秒 (ノード 2018、`res_s38.jsonl`) →
新しい既定 14.9 秒 (ノード 7252、`res2_s19.jsonl`) に遅くなった (どちらも 1 回、別の機械)。前の既定の後に既定にした 5 つ
(mem3・forceq・fstop・bs) のどれかの害か、揺れかを分ける。

## やり方

- ブランチ ccr-1beed81b-ex0uhq (69d4d10d を含む) をリリースでビルドし、`analysis/mitt600_20261103/run_cfg.py` で 4 スレッド・600 秒。
  機械は 4 コア 1 台、ソルバーは同時に 1 つだけ。
- 設定は `analysis/halve_submip_20261030/run.py` の CFGS の def (新しい既定) と preall4bs (前の既定、6 つの環境変数をすべて戻す)。
- def → preall4bs を交互に 3 ペア回し、時間の幅は重なったが 3 ペアとも def が遅かったので、念のため 4 ペア足して計 7 ペア。

## 結論

- **事実**: 同じ機械で交互に 7 回ずつ回すと、def と preall4bs の時間の幅は大きく重なり (9.1〜15.3 と 9.5〜13.0)、中央値は def の方が
  わずかに速い (11.6 と 12.2)。最初の 3 ペアは def が遅かったが、6・7 番目は def が 2〜4 秒速く、向きは揃っていない。
  時間はほぼノード数で決まり、ノード数は同じ設定でも 3 倍ほど揺れる (def 3283〜9878、preall4bs 3118〜8792)。
- **事実**: 測り直しで見た 6 秒 (ノード 2018) と 15 秒 (ノード 7252) は、どちらもここで見た揺れの幅の端にある
  (15.3 秒・9878 ノードの def の回もある)。
- **結論: 揺れ**。新しい既定の 5 つ (mem3・forceq・fstop・bs) のどれかの害とは言えないので、1 つずつ戻す切り分け (nomem3 など) は回していない。
- **推測**: 4 スレッドの木探索で、どのスレッドがいつ暫定解・下界を共有するかの順序がノード数を大きく変えているとみられる
  (最初の解は毎回同じなので、差はその後の探索で出ている)。6 秒の回はこの機械の 9 秒台にあたる速い側の当たりで、機械の違い
  (この機械は全体に遅め) も入っている。
