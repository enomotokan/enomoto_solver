# degen3 bottleneck analysis

Problem: NETLIB `degen3` (1503 rows x 1818 cols, 24,646 nnz; MPS at `.netlib_cache/mps/degen3.mps`).
Benchmark record (`scripts/benchmark_results.json`): ours 0.796 s vs HiGHS 0.186 s, both optimal at -987.294.
Re-measured this session (same harness, `--only degen3`): ours 0.750 s / HiGHS 0.179 s (4.19x); direct in-process reps: ours 0.759-0.805 s, HiGHS 0.174-0.178 s.

All numbers below were measured in this environment (HiGHS 1.15.1 via `highspy`, this crate at HEAD `0a09cc4`), not estimated. Throwaway instrumentation was added locally to `src/simplex/extended_dual.rs` / `src/simplex/lu.rs` to obtain the finer breakdowns, then reverted (`git checkout`) and the original wheel reinstalled; nothing was committed.

## Summary

`degen3` is **not** slow because of degeneracy, cycling, ill-conditioning, pivot selection or the starting basis: this crate takes **2163** dual-simplex iterations to HiGHS's **2098** (+3%), with zero degenerate pivots flagged, no Bland/stall/plateau fallback, zero numerically-triggered refactorizations, and DSE weights within 1% of exact on 100% of iterations. The entire 4.2x gap is **per-iteration cost** (353 us/iter vs HiGHS's ~76 us/iter all-in): the extended-dual main loop (`extended_dual::solve_lp_dual_extended`, which `degen3` takes because 1612 structural columns keep a genuine infinite bound) spends ~65-70% of its instructions in FTRAN/BTRAN solves through a Forrest-Tomlin eta file that is allowed to grow to ~90k nonzeros (vs. 8-17k for a fresh LU) before the fill-based refactor trigger fires, and then, at each of the 4 refactorizations, recomputes exact DSE weights with `DseState::from_basis` (1412 BTRANs each, 90 ms total = 12% of wall, and now redundant). A third, previously invisible slice (18% of wall, the "unaccounted" part of `PROF_PHASES_EXT`) is the every-5-iteration `x_B`/`d` drift check, which costs 313 us per check (more than a whole iteration) and never fires on this problem. Three env-only experiments (existing `ENOMOTO_DSE_REFRESH_ON_REFACTOR=0` + temporary overrides for the update-streak cap and the drift-check cadence) bring `degen3` from 0.76 s to **0.43 s** with a bit-identical 2163-iteration pivot path and objective; disabling the DSE refresh alone is a crate-wide -10.8% on the 77-problem NETLIB sweep with no status or objective changes.

Classification: **その他 (per-iteration work: linear-solve cost driven by refactorization/eta-file policy, plus refactor-time and periodic-check overheads)**.

* Rebuild/reinvert cadence: with `log_dev_level=2`, HiGHS reports a "Synthetic clock" rebuild roughly every 70-130 iterations (21 synthetic-clock rebuilds plus phase-boundary ones, ~25 total in 2098 iterations). HiGHS does **not** recompute DSE weights at rebuilds; it keeps the incrementally updated ones.
* Density columns (`C_Aq R_Ep R_Ap S_Ed`, printed as `int(-2*log10(density))`): phase 2 values `1 0-1 0 0` = alpha ~10-32% dense, rho / DSE > 32% dense. Same dense regime as ours (36-65%), so HiGHS is not winning via hyper-sparsity on this instance.
* Effective all-in cost: 0.16 s / 2098 = **~76 us/iter** including ~25 reinverts, vs. ours 353 us/iter (4.6x per iteration).

## Root cause classification

**その他 - per-iteration work, specifically the refactorization / eta-file policy and the overheads attached to it.** Evidence:

1. Iteration counts match (2163 vs 2098, +3%) - rules out 退化・サイクリング and ピボット選択の非効率 as the driver. Both solvers start from the all-slack basis with no crash, so 初期基底の質 is not a differentiator either.
2. No numerical trouble: 0 verify / try_update / drift / illcond refactorizations, DSE weights within 1% on every iteration, no Bland fallback - rules out 悪条件.
3. Per-iteration cost is 4.6x HiGHS's and decomposes into three concrete, measured pieces:
   * **Eta-file growth** (bump trigger at 64*m fill lets FT chains run to 860 updates / ~90k nnz): solve cost 65 -> 334 us/iter across a streak; the three solves average 127 us/iter = 36% of wall.
   * **`DseState::from_basis` at every refactor**: 90 ms = 12% of wall, 1412 BTRANs per event; makes each refactor cost ~36 ms and thereby makes *more frequent* refactorization (HiGHS's strategy) a net loss under the current code (cap 50 -> 1.58 s, cap 100 -> 1.02 s when the refresh is on).
   * **Every-5-iteration drift check**: 134 ms = 17% of wall, 313 us/check, never fires here.

## Suggested direction (no changes made)

Ordered by measured payoff / risk on `degen3`:

1. **Stop recomputing DSE weights at every refactor** - `dse_refresh_on_refactor` default at `src/simplex/extended_dual.rs:1763`, call sites `:2668` and `:3038`, implementation `DseState::from_basis` at `src/simplex.rs:2495`. It was introduced when the incremental weights drifted to >=100% error on `degen3`; the later `wp_old = ||rho_p||^2` fix in `DseState::update_after_pivot` (`src/simplex.rs:2541`) removed that drift (`dse_rel_err <1%` on 100% of iterations now), so the refresh has become pure cost: 90 ms / 12% on `degen3`, identical pivot path with it off, and -10.8% on the whole sweep with no status/objective change. Flip the default (or refresh only when the existing `dse_rel_err` diagnostic, which already computes `dot(rho,rho)` vs `weights.weight(r)`, observes real drift). This is also the prerequisite for (2): with the refresh on, every refactor costs ~36 ms, which is why shorter update streaks currently lose.

2. **Refactorize on a cost-balance rule rather than the 64*m fill cap** - trigger constants `FT_BUMP_LIMIT_FACTOR` (`src/simplex.rs:356`), `FT_MAX_UPDATES_FACTOR` / `ft_max_updates` (`src/simplex/extended_dual.rs:569-580`), checks at `:2941` and `:2949`. Solve cost is linear in eta fill (65 -> 334 us/iter); HiGHS reinverts every ~100 iterations via its "synthetic clock" (refactor when cumulative FTRAN/BTRAN work since the last INVERT exceeds a multiple of the INVERT cost). A fixed cap of ~200 updates already gives -24% (with (1)); a cost-balancing trigger (accumulate the measured or estimated solve work, compare with the last `refactorize` time) would adapt per problem instead of being a new magic constant. Note the LU itself (`lu::factorize` -> `factorize_flat_markowitz`, `src/simplex/lu.rs:876/902`; `MarkowitzState` with `BTreeMap`-per-row active submatrix, `src/simplex/lu.rs:142`) costs 2-16 ms per event on this basis and becomes the largest remaining phase (20%) once refactors are frequent - a cheaper factorization (e.g. peeling column/row singletons before the Markowitz phase; fresh L has only 0.9-5k nnz here, so most of the basis is already triangular) compounds with this item.

3. **Make the extended-dual drift check cheaper or rarer** - `XB_CHECK_INTERVAL` (`src/simplex/extended_dual.rs:439`), check body `:2955-3014` calling `compute_rhs_affine` (`:925`), `residual_norm` x2 (`:890`) and `fresh_d_into` (`:1095`). 313 us per check every 5 iterations = 17% of wall, never firing. The constant's own docs record that interval 50 once produced false `Infeasible` on `cycle`/`degen3`, so a bare cadence change needs the full-sweep check (see the sweep table above for what this session measured at interval 50); lower-risk alternatives are (a) keep the cadence but make the check O(m) instead of O(nnz)+BTRAN - e.g. check only the `x_B` residual and run `fresh_d_into` only when that residual is within an order of magnitude of the tolerance, or (b) tie the check to the refactor cadence from (2), where `x_B`/`d` are resynced anyway.

4. Secondary per-iteration costs worth a look once (1)-(3) land (each ~5-9% of the improved 420 ms): the DSE `tau` FTRAN uses the dense `solve_into` path with a 65%-dense result (`:2766`, inherent); `chuzc1` fully sorts ~255 candidates per iteration (`candidates.sort_by`, `:2324`, 4.7% of instructions) where BFRT only needs the prefix up to `k_star` (partial selection / heap, as the classical path's BFRT heap already does); `xb_update` scans all m rows and calls `infeasible_rows.set` per nonzero of `alpha_full` (`:2743`); `u_transpose_solve_into` (`src/simplex/lu.rs:1737`) has no zero-skip so BTRAN always costs nnz(U) - only matters while eta files are large.

Not recommended: anything aimed at degeneracy (perturbation, tie-breaking, Bland thresholds) or at pricing/initial basis - the iteration count is already at HiGHS's level.
