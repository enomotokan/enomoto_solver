# 根 (前処理〜木に入るまで) の並列化の調べ (2026-11-22、parspeed の (ii)、利用者の判断)

parspeed_20261122 で、4 スレッドの全体の 42〜51% が根で、根は 1.28 倍しか速くならなかった。根のどこに時間がかかり、
どこが既に並列で、どこが 1 本でしか動かないかを洗い出す。コードは変えていない (既存の `ENOMOTO_MIP_LOG` の行と /proc だけ)。

## 測り方 (run.py・plan.json → res.jsonl、集計 summ.py → summ.txt)

- 対象: parspeed の 32 問 + 30n20b8・supportcase26、種 1、1・4 スレッド、120 秒 (68 回)。ビルド 089fcd7af 以降の先頭 (5f4d16406、pip install -e .)。
- stderr の行を受け取った時刻 (起動からの壁の秒) で、印の行から段に分ける (求解 = 再スタートごとに繰り返し、足す):
  pre (〜`solving the root LP`: 外側・求解の前処理、プロービング、対称性など) / lp (根の LP) / cut (〜最後の `cut round`) /
  heur (〜`after root heuristics`) / post (〜再スタートか `TRSTAT: tree start`) / tree。pre からは起動〜求解の始め (Python の読み込み) を引く。
- 0.2 秒ごとに /proc を読み、段ごとのプロセス全体の CPU 秒 (終わったスレッドの分も含む) と、最も多く動いた 1 本の CPU 秒を出す。
  1 回目 (res_v1.jsonl・summ_v1.txt) はスレッドごとの CPU を足していたので、段の中で終わったスレッド (並列のサブ MIP など) の分が落ちていた
  (段の秒は正しい)。2 回目で直した。

## 並列にする案と見積り (アムダール、4T の根 256 秒・全体 668 秒に対して)

1. **分離の並列 (`ENOMOTO_MIP_SEP_PARALLEL`、既にある試作)**: cut は 4T の根の 38% (97 秒)。1 ラウンドの時間の大半は分離
   (h80x6320d で 1 ラウンド 0.35 秒のうち分離 0.30 秒)。候補は逐次と同じ順につなぐので決定的。仮に分離の半分が並列になって 2 倍速くなれば
   cut は 97 → 約 70 秒、根 −10%、全体 −4%。**作らずに測れるので最初に試す**。
2. **RINS (と残りの根のヒューリスティクス) を空いているスレッドで並走**: RENS と同じ並列のサブ MIP の形で RINS を出し、決まった所 (木に入る前など)
   で待って結果を受け取る。heur の 4T 86 秒のうち RINS 43 秒が隠れれば根 −17%、全体 −6%。決定性: サブ MIP は 1 スレッド・手間の上限で
   決定的にし、受け取る所を固定すれば 4 スレッドの再現も保てる (時間で打ち切る形 (TIMEDEP) は避ける)。1 スレッドの動きは変えない。
3. **プロービングの並列**: pre は 22% (56 秒)、その多くがプロービングと含意の同値の検出。2 値の列を塊に分けて並列に調べ、固定・含意を決まった順に
   合わせる。固定が次の列の調べに効く (逐次の依存) ので、塊ごとの結果を合わせ直す手間がかかる。得は大きくて pre の半分 (根 −11%)。作るのは重い。
4. **裏のカットの待ち (post 11 秒、根の 4%)**: 待つ所を木の最初の数ノードの後にずらす、などで隠せる。小さい。

まとめ: 4 スレッドの根では約 2 本が空いている。主のスレッドで逐次に動いているのは、カットのループ (分離の一部・LP の解き直し)・RINS・
プロービング。試作は 1 → 2 → 3 の順を提案 (1 は計測だけ、2 は RENS の並列の形を写せる、3 は作りが重い)。
