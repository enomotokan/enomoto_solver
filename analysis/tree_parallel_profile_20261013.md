# 並列分枝限定法 (木の探索の並列) の計測と損失の内訳 (2026-10-13)

問い: 並列分枝限定法を速くするには、ノードの配り方を工夫する必要があるか。

## 結論

1. **配り方による待ち (負荷の偏り) の損失は小さい**。木の探索の時間に占める待ちの割合は、時間のかかる問題でほぼ 0〜2%。
   ただし 20 問以上で、共有の待ち行列を通ったノードは**最初の 3 個 (従 1 本に 1 個) だけ**。最初に分けた部分木を各スレッドが
   最後まで掘る「静的な分割」になっている。待ちは出ないが、全体の下界は最も悪い部分木で決まり、ほかのスレッドは助けない。
   時間切れの問題では、ノード数が 2〜5 倍になっても下界の改善は小さい (timtab1 589750 → 600850。neos-911970 は 52.59 →
   51.52 と悪化)。**配り方を工夫する余地は「待ちを減らす」ではなく「下界の悪いノードに処理を集める (質の釣り合い)」にある**。
2. **最大の損失はスレッドあたりの処理速度**。ノードが軽い問題では、threads=4 のスレッドあたりのノード/秒が threads=1 の
   33〜49% (gen-ip054 0.39、pk1 0.33、mas74 0.49)。threads=1 の求解を 4 プロセス同時に動かしても速度は落ちない (gen-ip054
   30 秒で 4 本とも 13.0 万ノード、単独 13.0 万) ので、計算機の限界ではなく**ソフトウェア側の損失**。
   原因の一つは、ほかのスレッドから取り込んだ双対証明・衝突でノードごとの伝播が重くなること: gen-ip054 の証明のプールは
   threads=1 で 416 本、threads=4 で 1389 本。gdb のサンプリングで `proof_absorb` は 29% → 46%、LP は 34% → 8%。
   証明・衝突の共有を止めると (`ENOMOTO_MIP_TREE_NO_SHARED_PROOFS=1`、20 秒) スレッドあたりの速度は gen-ip054 44% → 71%、
   mas74 65% → 84%、pk1 35% → 43% (threads=1 比)。pk1 は共有を止めても LP の割合が 78% (threads=1) → 12〜34% のままで、
   残りの原因は未特定。LP が重い問題 (timtab1・assign1-5-8 など、LP が木の時間の 85% 以上) では速度は落ちていない。
3. **移ったノードは warm start がない分重い** (最初の LP の反復が自分の待ち行列のノードの 3〜10 倍) が、数が全体の 1〜3% と
   少なく、影響は binkar10_1・rout で木のスレッド時間の 6〜9% 程度 (見積もり)。
4. **根の処理 (立ち上がり)** が 60 秒のうち 15〜27 秒を占める問題がある (30n20b8 27 秒、blp-ar98 16 秒、h80x6320d 14 秒、
   graph20-20-1rand 14 秒)。その間は木の探索の並列は効かない。
5. **ばらつきが大きい**。rout の threads=4 は同じコードで 9.8・11.7・22.0・27.5 秒。時間は最適解が見つかる時刻でほぼ決まり
   (threads=1 は 22.3 秒で発見、threads=4 は 7.6 秒で発見した回がある)、見つかった後は 2 秒ほどで証明が終わる。
   下の表の問題ごとの速さの比は 1 回の計測なので、目安にとどめる。

優先度の提案: (1) 取り込む証明・衝突のノードごとの費用を減らす (取り込む量を抑える・短いものだけ取り込む・`proof_absorb` の
`HashSet` をやめる)。ノードが軽い問題でスレッドあたり 1.5 倍程度が見込める。(2) 質の釣り合い: 全体の下界から大きく離れた
部分木を掘っているスレッドの待ち行列からノードを出し、下界の小さいノードと入れ替える。(3) 移るノードに基底を付ける。
(4) 根の並列化。

## 計測の方法

- base `8e95f64` + 計測用のコード (`ENOMOTO_PROF_TREE_PAR=1` でスレッドごとの内訳を標準エラーに出す。`src/mip/solver.rs` の
  `TreeProf`)。
- MIPLIB 2017 の 40 問 (`scripts/run_miplib_benchmark.py` の `PROBLEMS`)、1 問 60 秒、1 問ずつ (同時には解かない)。
  threads=1 (`ENOMOTO_MIP_THREADS=1`) と threads=4 (`ENOMOTO_MIP_THREADS=4`、ベンチマークのスクリプトと同じ)。
  4 vCPU (Xeon、SMT なし)、15 GB。
- 結果と計測・集計のスクリプトは `benchmarks/tree_parallel_20261013/`
  (`drive.py THREADS 60 OUT.jsonl`、`analyze.py DIR`)。

## 次に調べること

- pk1 の残りの損失 (共有を止めても threads=1 の 43%): LP の割合が 78% → 12〜34% に落ちる原因。
- 速さの比のばらつき: rout・binkar10_1 などを複数回解いて、1 回の計測の比がどこまで信用できるかを確かめる。
- 質の釣り合いの効果: 時間切れの問題で全体の下界の推移を記録し、スレッドごとの下界の差を見る。

## 追記: 双対証明・衝突の共有の効き目 (自前と取り込み)

問い: 証明・衝突は取り込むほど緩和の質が良くなり、増えすぎると求解が遅くなるのか。

### 前提: 証明・衝突は LP には入らない

双対証明は LP とは別のプール (`dual_proofs`、上限 `ENOMOTO_T_MIP_PROOF_POOL` = 2000 本) に入り、各ノードの伝播
(`apply_dual_proofs`) で「最小活動量 > 右辺ならノードを刈る」「整数列の境界を締める」にだけ使う。衝突
(`LitConflictPool`) も伝播だけ。したがってトレードオフは「LP の強さと LP の速さ」ではなく、「伝播で刈れる・締められる量と、
ノードごとの伝播の費用」。費用は境界の変わった列を含む証明をたどる差分更新 (`proof_absorb`) が大半で、証明の本数に比例する。

### 計測

`ENOMOTO_PROF_TREE_PAR=1` の出力に、証明・衝突を自前 (own) と取り込み (imp) に分けて「調べた数・刈ったノード・締めた境界・
差分更新の回数 (費用の目安)・終わりに残っていた数」を加えた (`TreeProf::proof`・`LitConflictPool::stats`)。刈ったノードは
最初に矛盾を出した証明に数える (調べる順に偏りがありうる)。40 問、60 秒、threads=4 を、既定 (`s4.jsonl`) と
`ENOMOTO_MIP_TREE_NO_SHARED_PROOFS=1` (証明・衝突を取り込まない、`n4.jsonl`) で 1 回ずつ。既定の gen-ip002・gen-ip054 は
ビルドと重なったので解き直した値 (`s4_rerun.jsonl`。元は `s4_orig.jsonl`)。

- **取り込んだ証明も効いている**。刈ったノード・締めた境界は自前より多い。ただし費用あたりの効き目は自前の 6〜7 割。
- **プールの 3/4 が取り込みで埋まる**。上限 2000 本は自前と取り込みで共有なので、取り込みが自前の証明 (費用あたりで効く方) を
  押し出している (gen-ip054 の主: threads=1 では自前 537 本、threads=4 では自前 240 本 + 取り込み 1208 本)。
- 全体の速さは差が小さい: SGM 既定 22.37 秒、共有なし 22.66 秒 (+1.3%、計測のばらつき ±2% 程度の範囲)。解けた問題は
  どちらも 22 問。両方時間切れの 18 問では、共有なしのノード数が既定の 1.15 倍 (幾何平均)、ギャップは既定が小さい 6 問・
  共有なしが小さい 9 問。
- 問題ごとには両方向に大きく動く (1 回の計測。同じ設定でもノード数は ±15% 程度揺れる: gen-ip054 共有なし 38.1 万 / 45.9 万):
  既定が良い rout 9.2 / 13.4 秒、binkar10_1 17.8 / 24.8 秒、neos-860300 21.2 / 27.6 秒、timtab1 ギャップ 23.6 / 30.0%、
  bppc4-08 9.4 / 12.5%、neos-1456979 (共有なしは解なし)。共有なしが良い neos-911970 ギャップ 5.4 / 3.2%、mik-250-20-75-4
  9.2 / 7.0 秒、misc07 15.5 / 13.5 秒。

### 結論

「取り込むほど刈り込みは強くなるが、ノードごとの処理が重くなる」という形のトレードオフで、今は両者がほぼ釣り合っている
(止めても全体は速くならない)。改善するなら取り込みを止めるのではなく、費用あたりの効き目を上げる:

1. 自前と取り込みのプールの上限を分ける (自前の証明が押し出されないように。取り込みは例えば 500〜1000 本)。
2. 取り込む証明を選ぶ (短いもの、作ったスレッドで実際に刈った・締めたもの)。
3. `proof_absorb` の費用を下げる (呼び出しごとの `HashSet` をやめる。差分更新を整数列・効く側だけに絞る)。

## 追記: 双対証明の差分更新の改修 (69afe8f) の効果と、次の律速

### 改修

`proof_absorb` がたどる列の索引の項目の 85〜90% は、境界の変わった側が最小活動量に効かない (係数の符号が逆の) ものだった
(gen-ip054 threads=1 20 秒: たどった 3.7 億のうち足し引きは 4890 万。threads=4 で 23.6 億 / 3.5 億、mas74 threads=4 で
25.0 億 / 2.5 億)。索引を係数の符号で分け、境界の変わった側だけをたどるようにした。差分が変わった証明の印は `HashSet`
(SipHash) をやめて印の配列にした。足し引きの中身と順番は変わらない (差分の値を全計算と突き合わせて、6 問 threads=1/4 で
約 2.2 億回、食い違いなし)。`cargo test --release --lib` 301 件・`pytest tests` 43 件合格。

### 効果 (40 問、60 秒、1 回ずつ。`ab_{b,a}{1,4}.jsonl`、b = 改修前 de90caa、a = 改修後)

| | 改修前 | 改修後 |
|---|---:|---:|
| threads=4 SGM [s] | 22.61 | 21.68 (−4.1%) |
| threads=1 SGM [s] | 26.22 | 25.65 (−2.2%) |
| 解けた問題 (threads=4 / 1) | 23 / 19 | 23 / 19 |
| 両方時間切れの問題のノード数 (threads=4 / 1、幾何平均) | | 1.07 / 1.02 倍 |

目的値の不一致なし。大きく動いたのは markshare_4_0 (threads=1 26.6 → 11.3 秒、threads=4 6.6 → 2.9 秒) と mas76 (threads=4
52.7 → 27.7 秒) だが、どちらも探索の順が変わったことによるばらつきを含む。

### 次の律速: 証明による境界の締め付けの走査

gdb のサンプリング (行番号つきのビルド、gen-ip054 threads=4) で `proof_absorb` は 46% → 13% に下がり、代わりに
`apply_dual_proofs` の締め付けのループ (余裕 slack が根の状態の上限 `proof_base[k].2` = max |a_j| (u_j − l_j) より小さい証明の
係数を全部たどって締められる整数列を探す) が 60% を占める (うち 41% が整数で固定されていない列かを調べる 1 行)。

| 15 秒 | 締め付けを調べた証明 | うち締めた | たどった係数 | 根の幅で並べて打ち切ったら見る係数 |
|---|---:|---:|---:|---:|
| gen-ip054 threads=1 | 2416 万 | 103 万 (4%) | 5.1 億 | 4.7 億 |
| gen-ip054 threads=4 | 6396 万 | 174 万 (3%) | 14.3 億 | 13.0 億 |
| mas74 threads=1 | 34 万 | 5.5 万 | 1790 万 | 109 万 |
| mas74 threads=4 | 519 万 | 39 万 | 3.3 億 | 2943 万 |
| pk1 threads=1 | 369 | 157 | 9129 | 647 |
| pk1 threads=4 | 1469 万 | 12 万 | 6.6 億 | 547 万 |

- 締め付けを調べても 96〜99% は何も締まらない。根の状態の上限は、深いノード (多くの列が固定済み) では緩すぎる。
- 0-1 の問題 (mas74・pk1) では、係数を |a_j| × 根の幅の大きい順に並べておき、slack 以下になったら打ち切れば、たどる係数が
  1/10〜1/120 になる。一般整数の gen-ip054 では効かない。
- pk1 は threads=4 で締め付けの候補が 4 万倍に増える。threads=4 では良い暫定解 (11、threads=1 は 20) が早く見つかり、目的の
  証明の右辺 (打ち切り値 − 定数) が小さくなって、余裕の小さい証明が増えるため (加えて取り込んだ証明)。
- 小さい問題では証明のプールが問題より 2 桁大きい: 上限は 2000 行・非零 `10 nnz + 100000` で、gen-ip054 (非零約 650) では
  30 列の密な証明が最大 2000 本になる。

候補: (1) 係数を |a_j| × 根の幅の大きい順に持ち、打ち切る。(2) プールの上限を問題の大きさに合わせる (非零の下限 100000 を
小さく)、自前と取り込みで上限を分ける。(3) `proof_rhs` の `prune_limit()` (共有の最良値の読み込み) をループの外で 1 回だけ。

## 追記: 並列の効率の改善の候補の実装と評価 (2026-10-13〜14)

### 評価の方法

- 40 問、60 秒、threads=4 (`ENOMOTO_MIP_THREADS=4`)、1 問ずつ。候補は環境変数で切り替え、同じビルドの基準と比べる。
- 同じ設定でも 1 回の SGM は最大 4% ほど揺れる (基準 3 回: 22.22 / 22.95 / 22.90 秒) ので、候補は 2 回、基準は 2〜3 回の平均
  (問題ごとに時間の幾何平均を取ってから SGM)。
- SGM に加えて、全ての設定・回で時間切れの問題 (16 問) の時間切れのときの相対ギャップの幾何平均 (shift 1%) を見る
  (時間切れの問題の改善は SGM に出ないため)。
- 正しさ: 全ての計測で、最適と報告した問題の目的値が一致するか (下の racing の誤答を除き不一致なし)。
- 計測・集計のスクリプトは `benchmarks/tree_parallel_20261013/` (`drive.py`、`cmp.py`)。
