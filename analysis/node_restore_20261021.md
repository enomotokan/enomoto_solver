# 取り出したノードの最初の LP: 基底の復元と DSE 重み (2026-10-21)

ブランチ `inv/noderestore-20261021`。どの試作も既定では使わない (環境変数で有効にする)。計測はすべて 4 スレッド
(`ENOMOTO_MIP_THREADS=4`、`m.solve(..., 4)`) で、1 スレッドと書いたものは仕組みを見るための別の計測。ログは
`runs_nr/logs_20261021.tar.gz`、計測の小さな道具は `runs_nr/` (`ab.sh`・`ab1.sh`・`summ.sh`・`pairsum.sh`・`run1.py`)。

## 0. まとめ

- **事実**: 今の既定では DSE 重みはほぼ全ての LP で引き継がれている (`dse_all` → `WARM_DSE_ON`)。neos-911970 の木
  (行数 > 150 の LP、20 秒) で初期化の内訳は「引き継ぎ」9743 回、「単位重み (与えた基底から)」128 回、「単位重み
  (全スラック)」85 回。潜りの子も、今の基底のまま解く復元 (`fc2_keep`) も、直前の LP の最後の重みを使っている。
  単位重みから始まるのは、共有の待ち行列のノード (カットの行を基底にした基底を `set_basis` が修復したもの) と
  修復した復元だけ。このため B・C の効く場面は小さい (依頼の前提「それ以外は単位重み」は今のコードでは当たらない)。
- **事実**: 取り出したノードの最初の LP が重いのは、(1) 共有の待ち行列から来たノード (手元の待ち行列に釣り合いで入った
  ものを含む) の基底が壊れている (1 回 1300〜6500 反復)、(2) 保存してから数百〜千数百本のカットが加わり、それを満たす
  ための反復 (mapbig・keep で 200〜600 反復)。重みの差はどちらでも小さい。
- **A (`ENOMOTO_MIP_RESTORE_READD=3`) が既定にする候補**。共有の待ち行列のノードは 1300〜6500 → 150〜290 反復。
  mc11 (打ち切り値つき 90 秒) の下界 11557・11591 → 11642・11662、neos-2978193-inde (打ち切り値つき) は既定
  6 回のうち 4 回 74〜103 秒で解けたのに対し A3 は 4 回とも 75〜96 秒で解けた、10teams 37.6 秒・時間切れ → 15.1・21.3 秒。
  悪くなったのは qiu (28.9・28.9 → 38.5・33.7 秒) と neos-860300 (+1〜3 秒)。メモリが増える (neos5 168 → 331〜369 MB)。
- B (厳密な重み) は今の基底のまま解くノードで反復が 20〜45% 減るが、行の多い LP (mc11) では BTRAN m 回の分で 1 回の時間が
  増える。C (重みの写し) は今の基底のままの場面では既定がすでにそうしていて、修復した基底では効かない。どちらも採らない。
- D (試作、依頼の外: `ENOMOTO_MIP_RESTORE_NB=1`、保存した基底の列の上限・下限の側を置き場所の希望にする) は、同じノードで
  比べると neos-2978193-inde で 1 ノードの反復が 3〜5 割減るが、4 スレッドの解く時間は揺れの範囲で決められない。

## 1. 診断

### 1.1 計測の道具 (どれも既定では何もしない)

- `ENOMOTO_MIP_RESTORE_DIAG=1`: 終わるときにスレッドごとに `RESTDIAG` の 1 行。出どころ (dive = 潜りの子と兄弟、
  local = 手元の待ち行列、pool = 共有の待ち行列) × 復元の種類ごとに、最初の LP の回数・平均反復・平均ミリ秒・保存してから
  加わった行・外された効いていた行 (A のときだけ数える)・戻した行。`=2` なら取り出したノードごとに `RDLINE` の 1 行。
  種類 (`RD_*`): `exact` 行の変化なし、`map` 行は変わったが外された行は全て基底 (加わった行 50 以下)、`mapbig` (同 50 超)、
  `keep` 外された効いていた行があり今の基底のまま解く (`TREE_SEP` の既定)、`repair` 数を修復、`readd` A で戻した、
  `poolfix` カットの行を基底にした共有の待ち行列の基底で数が合わず `set_basis` の修復に任せた (釣り合いで手元の待ち行列に
  入ったものは `local/poolfix`)、`poolok` 数が合った。
- `ENOMOTO_MIP_RESTORE_PAIR=1`: 取り出したノードの最初の LP の前に、方式を入れ替えて 7 通り試し解きし (LP の状態と反復の
  合計は戻す)、同じノードで反復を比べる (`RESTPAIR`)。R_* = 置く基底 (保存した基底を写したもの) に、saved 保存した重み /
  exact 厳密な重み / unit 単位重み / nb 保存した重み + D。K_* = 今の基底 (直前のノードの最適基底) に、unit / warm 今の重み
  (既定の keep と同じ) / exact。試し解きの時間でノードの数が減るので 1 スレッドで使う。
- `ENOMOTO_DEBUG_DSEINIT=1`: 双対単体法の DSE 重みの初期化の経路を LP ごとに出す。

## 2. A: 効いていたカットの行を戻す (`ENOMOTO_MIP_RESTORE_READD`)

### 2.1 実装 (`src/mip/solver.rs`・`separation.rs`・`queue.rs`)

ビットの和: 1 = 手元の待ち行列 (兄弟を含む)、2 = 共有の待ち行列、3 = 両方。

- 行を外すとき (`delete_lp_rows`) に、外したカットの番号を `row_log` と同じ並びの `row_log_ids` に記録し、行の中身を
  `cut_rows` (カットの番号 → (係数, 下限, 上限)、`ENOMOTO_T_MIP_READD_CACHE` 本 (既定 30000) まで、古いものから捨てる) に残す。
- ビット 1: `restore_node_basis` で、保存した基底で非基底だったカットの行のうち保存した後に外されたもの (`row_fates` で
  `row_log` を再生して求める) を集め、今の LP に同じ行 (ハッシュが同じで今基底) があればその状態にし、なければ LP に加えて
  (`add_cut_rows`、普通どおり年齢 0 で外れうる) 保存した状態にする。保存した後に加わった行はスラックを基底のまま。
  基底変数の数が正確に合うので、保存した基底と (写した) 保存した重みをそのまま当てはめる。行のハッシュはカットの番号ごとに
  覚える (`cut_hash`)。中身が残っていなければ従来どおり (`readd_miss` に数える。計測した範囲では 0)。
- ビット 2: 共有の待ち行列に出すノード (`snap_of`) に、親の基底で非基底だったカットの行の中身と状態 (`ship`) と、列と元の行の
  DSE 重み (`ship_dse`) を付ける。受け取った側 (`open_from_pool`) はノードに持たせ、取り出して基底を置くときにビット 1 と同じ
  ように同じ行を探すか加える。受け取った側のカットの行は基底のまま。数が正確に合い、渡した側の基底をそのまま置ける
  (列と元の行の重みも、基底のスラックの行を足し引きしても変わらないので正確)。
- 注意 (推測): 加えるのは LP にあった (大域的に正しい) カットの行だけという前提。局所的にしか正しくない行が LP に入る経路が
  あれば、ビット 2 は誤り。今の木の中の分離はカットをプールにも入れて他のノードで使っているので、大域的と見ている。

## 3. B・C: DSE 重み

### 3.1 前提の確認

1.0 のとおり既定で重みは引き継がれている。単位重みから始まるのは `poolfix` と `repair` (と全スラックからの解き直し) だけ。

### 3.2 B (`ENOMOTO_MIP_RESTORE_EXACT_SEL=<種類のビットの和>`)

選んだ種類 (`1 << RD_*`、keep = 16、repair = 32、poolfix = 128、mapbig = 8、readd = 64) の最初の LP だけ
`DSE_EXACT_ONCE` で厳密な重みから始める。引き継ぎが既定なので、厳密な重みを頼んでも引き継ぎの重みが優先されていた
(`slope_intercept_dual.rs` の初期化の順)。頼まれたときは厳密な重みを優先するように変えた (既定は変わらない。既存の
`ENOMOTO_MIP_RESTORE_EXACT_DSE` も同じ旗を使うので、以前の計測とは意味が変わる)。

| 問題 | 既定 | B=144 (keep + poolfix) / B=128 |
|---|---|---|
| mc11 打ち切り値つき 90 秒 | 下界 11557・11591、keep 522〜564 反復・132〜150 ms | 11668・11614、keep 296〜421 反復・**182〜185 ms**、ノード 4200 → 2100〜2500 |
| neos-911970 60 秒 | 38.2・53.2 秒、keep 315〜331 反復・21〜23 ms | 31.0 秒、keep 254 反復・20 ms (1 回) |
| neos-2978193-inde (B=128) | | 89.5 秒 (1 回)、poolfix は 1326〜1401 反復で変わらず |

- 反復は減るが、行の多い LP では m 回の BTRAN の分で 1 回の時間が増える (mc11)。修復した基底 (poolfix) では厳密な重みでも
  反復は変わらない (基底そのものが悪い)。mc11 の下界が上がったのはノードが半分の回で、揺れか効果かは 2 回では言えない。
  既定にする候補ではない。

### 3.3 C (`ENOMOTO_MIP_RESTORE_COPY_DSE=<ビットの和>`)

keep (16): 今の基底のまま解くときに今の重みを引き継ぐ → 既定がすでにそうしている (何も変わらない)。repair (32)・poolfix
(128): 置く前の今の基底の重みを、置いた基底で今も基底の変数に写し、ほかは 1。neos-2978193-inde (C=128、1 回) は時間切れ、
poolfix 1397〜1616 反復で変わらない。Devex の参照枠は実装していない (重みの差より基底の悪さが効いているため)。採らない。

### 3.4 D (`ENOMOTO_MIP_RESTORE_NB=1`、依頼の外の試作)

基底を置いた後、非基底の構造列の置き場所の希望 (`nb_hint`) を保存した基底の状態 (下限・上限) から作る (`set_nb_hint`、
`TwoStageLp::nb_override`、次の求解の 1 回だけ)。既定は今の解 (直前のノードの LP 解) から希望を作るので、双対退化した列は
直前のノードの側に置かれる。同じノードの比較では neos-2978193-inde で効く (1.3) が、4 スレッドの解く時間は既定と揺れの範囲
(D 90.1・時間切れ、A3+D 66.4・99.5 (旧番号の `=2` + D))。mc11・neos-911970 は変わらない。

## 4. うまくいかなかったこと・分からないこと

- 外された効いていた行を戻して保存した基底を正確に置いても、保存してから加わった行が多い (neos-911970 で 300〜1500 本)
  ノードでは、今の基底のまま解くより重い。手元の待ち行列のノードの重さの主因は「加わったカット」で、基底の不一致や重みでは
  ない (mc11 は逆に A が良い)。加わった行の数で A と今の基底を選び分けるのは、境目が問題で違い (neos-911970 では 101〜500 本でも
  今の基底が良く、mc11 では A が良い) 試していない。
- `RESTORE_PAIR` の R_exact は重みの優先の修正の前に取ったので意味がない。R_unit・K_unit は `set_dse_vars(&[])` で単位重みにした。
- 4 スレッドの結果は揺れが大きい (neos-2978193-inde の既定は 73.6 秒〜時間切れ)。2〜6 回の比較で言えるのは mc11 の A3 と
  10teams・qiu くらい。

## 5. 次の手

  行に絞れれば軽くなる。
