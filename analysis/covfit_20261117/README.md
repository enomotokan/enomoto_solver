# 被覆カットの量をシグモイドで連続に決める案の下調べ (2026-11-17)

利用者の案: 持ち上げつきの被覆 (`ENOMOTO_MIP_ROW_LIFTED_COVER`) を、クリークのカットのシグモイド版 (analysis/rootgap_20261116/clq) と同じく
問題の量 s から f = 1 / (1 + exp(−a (s − b))) で連続に量を決める。その前に、得失と相関する量があるかを既存のデータで見た (新しい計測なし)。

データ: analysis/cutmix_20261111 の p58 (58 問 × 種 1・2、4 スレッド・60 秒、`stat` = SEPSTAT、`lcstat` = + ROW_LIFTED_COVER) と、
そのログの CUTMIX の型の割合・SEPLEARN の分離器ごとの最初の根の伸び。`fit.py` → `fit.txt`。両方 1 秒未満の 7 問を除いた 51 問。

得失の 3 つ:
- tr: 時間の比 log((t_lc + 10) / (t_stat + 10)) の種の平均 (負なら被覆で速い)
- db: 最初の根の下界の差 / max(1, |下界|) (正なら被覆で強い)
- rg: 最初の根の rows (元の行の分離。被覆はここに入る) の伸びの割合の差 (% 点) = 被覆が根で実際に効いた量

## 結果

| 量 | ρ (tr) | ρ (db) | ρ (rg) |
|---|---|---|---|
| ナップサック行の割合 knap | +0.32 | +0.04 | −0.43 |
| 締まったナップサック knaptight | +0.30 | +0.13 | −0.36 |
| 混合ナップサック mixknap | +0.18 | −0.15 | −0.08 |
| 整数の行 introw | +0.20 | +0.05 | −0.22 |
| 根の rows の伸びの割合 (stat) | +0.29 | +0.15 | −0.05 |

- 得失どうし: **tr × db = −0.08、tr × rg = −0.22**。被覆が根の下界を上げても (db > 1e-4 は 14 問)、時間とはほとんど結び付かない。
- 型の割合はどれも |ρ| ≦ 0.32 で、向きも「ナップサック行が多いほど被覆で遅い」(knap の ρ +0.32) と直感の逆。
- 得失の幅も小さい: tr は −0.16 (qnet1) 〜 +0.57 (roll3000)、大半は ±0.05 以内 (時間で ±5% 程度、種の揺れと同じ大きさ)。

## 結論 (見送り)

- 被覆が根で実際に効いた量 (rg) そのものが時間と ρ = −0.22 でしか結び付かないので、それを予め見積もる量 (根の LP で破れる被覆の数、
  分数の 0-1 列がナップサック行に入る割合、被覆 1 ラウンドの伸び) で s を作っても、相関はこれより弱くなる見込み。根だけの計測で量を
  足す価値は小さいと判断し、計測しなかった。
- クリークのカットのシグモイド版が成り立ったのは、クリークのカットに「根で大きく伸びて木が小さくなる問題」(10teams・mzzv11・mzzv42z) と
  「遅くなる問題」(noswot・irp) がはっきり分かれていたから。被覆カットの得失は 58 問の 60 秒ではほぼ揺れの大きさで、合わせる相手がない。
- 被覆のシグモイド版は見送る。やるなら、得失のはっきりした問題 (qnet1・p200x1188c・sp150x300d で速く、roll3000・noswot・neos-911970 で遅い)
  を増やすため、600 秒の重い問題で lcstat を測るところから。
