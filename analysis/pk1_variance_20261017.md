# pk1 の揺れの原因 (2026-10-17)

4 スレッド・60 秒で pk1 (最適値 11) の時間が 2 つの山 (20〜25 秒と 40〜50 秒) に分かれる原因を調べた。
原因は 2 つ重なっている。どちらも「スレッドの間の時間の違いの積み重なり」ではなく、仕組みで説明できる。

## 1. 最適解 11 を見つける時刻 (主側の運)

「最適解は 0.1 秒で見つかる」は誤り。0.1 秒で見つかるのは FJ の 42 と RENS の 23 で、11 は木の中のランダム丸め・
ノードの LP 解・LNS が 3.7〜50.9 秒に見つける。11 を見つけるまでは打ち切り値が 12〜14 で、下界が 10 以上のノード
(11 があれば刈れる) を処理し続ける。既定 7 回 (`ENOMOTO_PROF_TREE_PAR`):

| 11 を見つけた時刻 | 全体の時間 | スレッドあたりの下界 >= 11 のノード (無駄) |
|---|---|---|
| 3.7 秒 | 25.8 秒 | 0 |
| 8.3 秒 | 23.0 秒 | 約 250 |
| 8.9 秒 | 24.3 秒 | 約 1200 |
| 18.3 秒 | 33.3 秒 | 約 8000 |
| 18.8 秒 | 28.7 秒 | 約 5000 |
| 30.2 秒 | 49.7 秒 | 約 22000 |
| 50.9 秒 | 58.2 秒 | 20000〜31000 |

ランダム丸めの乱数の種はスレッド番号で決まっているが、どのノードの LP 解に当てるかはスレッドへのノードの配分 (時間に
依存) で変わるので、見つかる時刻は回ごとに違う。

## 2. ノード処理の速さ (証明側): 役の復帰で `idle` が下に回る → 待ち行列が空 → カットが保護されず LP が小さい

打ち切り値を最適値に固定して主側の運を除いても (`ENOMOTO_MIP_CUTOFF=10.5`、診断用に追加)、時間は 15.9・19.8・42.2・43.4 秒と
2 つの山に分かれる。ノード数は 13.5〜15.6 万でほぼ同じ (速さが 2 倍違う)。

速い回と遅い回の違い (スレッドごとの内訳):

| | 速い回 (19.8 秒) | 遅い回 (42.2 秒) |
|---|---|---|
| 主の待ち行列 (open) | 約 7 秒以降ずっと 0〜1 | 6000〜9000 で推移 |
| 共有の待ち行列の大きさ (取るときの平均) | 約 31000 | 約 4 |
| LP の行数 (元 45 行) | 48〜57 | 536〜546 |
| ノードの最初の LP (潜り) | 11.9 反復 0.24 ms | 11.6 反復 0.45 ms |
| ノードの最初の LP (自分の待ち行列から) | 12.7 反復 0.58 ms | 11.1 反復 1.08 ms |
| HEURROLE (役から木へ戻った) の行 | あり | なし |

仕組み:

1. ヒューリスティクス役のスレッドは役に就くとき `busy -= 1` して `pool_busy = false` にするが、待っているスレッドの数
   `pool.idle` は増やさない。役から木に戻って共有の待ち行列からノードを取るとき (`pool_acquire`) は `!pool_busy` なので
   `idle.fetch_sub(1)` し、`idle` は usize の下に回って約 1.8e19 になる。
2. 以後、毎ノードの `idle > len` が常に真になり、全スレッドが毎ノード自分の待ち行列の半分を共有の待ち行列に渡し続ける
   (`pool_donate(idle - len)`)。自分の待ち行列はほぼ空 (0〜1)、共有の待ち行列に 3〜9 万ノードがたまる。
3. 自分の待ち行列が空だと、待ち行列のノードの基底で効いているカットの保護 (`basis_protected_cuts`) がほぼ働かず、
   年齢の上限 (pk1 は 45 行なので 30) で外れ、LP は 50 行前後に収まる。保護が働く通常の形では待ち行列のノードが
   数千あってほぼ全てのカットが保護され、LP は 545 行まで膨らみ、同じ反復数の LP に 2 倍の時間がかかる。
4. 役に就くか (`ENOMOTO_MIP_HEUR_ROLE_TRIGGER` の既定、限界効用の判定) は時間に依存するので、回によって 1〜3 が起きたり
   起きなかったりし、2 つの山になる。`ENOMOTO_MIP_NO_HEUR_ROLE` では必ず遅い山、`ENOMOTO_MIP_PROOF_SWITCH` では役が
   戻るので速い山、`PROOF_KEEP_ROLE` では役が戻らないので遅い山、というこれまでの観測と合う。
   「役に就いたかどうかと山が一致しない」と見えたのは、役に就いても戻らなければ (役のまま終わる、または 11 が遅い回) 速くならないため。

副作用: 速い山でも共有の待ち行列が Vec で、取るたび (`pool_acquire`) と釣り合い (`pool_balance`、32 ノードおき) に
最小の下界を線形に走査するので、3〜9 万ノードでは 1 回 0.1〜0.3 ms かかり、スレッドあたり 3〜8 秒 (全体の 8〜19%) を
錠の中で使っていた (`lock` の内訳を `ENOMOTO_PROF_TREE_PAR` に追加して計測)。

## 3. 切り分けの実験 (打ち切り値 10.5 固定、各 3 回)

| 設定 | 時間 (秒) | 備考 |
|---|---|---|
| 既定 (4 回) | 15.9・19.8・42.2・43.4 | 2 つの山 |
| `ENOMOTO_MIP_ROLE_IDLE_FIX=1` (idle を合わせる) | 45.3・33.4・31.4 | 常に遅い山 (待ち行列が自分に残り、LP 545 行) |
| IDLE_FIX + `ENOMOTO_MIP_NO_PROTECT_QUEUE_CUTS=1` | 21.6・21.3・19.6 | 常に速い山。LP 50〜60 行、待ち行列から取るノードの LP は 13.5 反復 0.26 ms (保護ありは 11 反復 1.1 ms)。基底の不一致 2742 / 37000 回 |
| IDLE_FIX + `ENOMOTO_T_MIP_CUT_ROWS_CAP=2` | 42.4・41.0・45.8 | 効かない (上限の処理は保護されたカットを外さない) |

IDLE_FIX の回で、役から戻ったスレッド 3 だけは待ち行列が小さく LP も小さいままで、33 秒の間に 57506 ノード
(ほかの 3 本は 28000〜33000) を処理した: 同じ回・同じ時刻での対照になっている。

## 4. 除外したもの

- CPU の取り合い、根の状態 (根の LP 値 0、カット 42 本、再スタートなし、対称性なし、被約費用の固定 0 で毎回同じ)。
- 双対証明・衝突のプールの大きさ (どの回も live 344 本、取り込みの量はノード数に比例)。
- 擬似費用の初期化、強分岐 (sb の反復はどの回も約 3400〜3800)。
- 負荷の偏り (eval の待ち時間は眠って待った分は 0〜3 秒で、`lock` の内訳が大半)。

## 5. 40 問での比較 (4 スレッド、60 秒、各 1 回)

既定 (役の復帰で `idle` が下に回る状態のまま) と、`ENOMOTO_MIP_ROLE_IDLE_FIX=1 ENOMOTO_MIP_NO_PROTECT_QUEUE_CUTS=1`:

| | 既定 | IDLE_FIX + NO_PROTECT |
|---|---|---|
| SGM (shift 10) | 20.51 秒 | 20.83 秒 |
| 解けた数 | 25 | 25 |
| pk1 | 24.2 秒 (速い山に入った回) | 24.5 秒 |
| 良くなった | | noswot 56.1 → 33.2、h80x6320d 42.2 → 33.5、mas76 18.2 → 13.1、mas74・cvs16r128-89 の主値 |
| 悪くなった | | 10teams 8.2 → 30.1、eil33-2 29.9 → 50.5、binkar10_1 26.9 → 30.6、30n20b8 (553 → 解なし)、neos-1456979 199 → 213、supportcase26・timtab1 の限界 |

1 回ずつの比較で、差は問題ごとの揺れ (10teams・noswot・eil33-2 は揺れが大きいと分かっている) の範囲。全体の差はない。

## 6. 結論と扱い

- pk1 の 2 つの山は、(1) 最適解 11 を見つける時刻の運と、(2) 役の復帰で `pool.idle` が下に回り全スレッドの待ち行列が
  共有の待ち行列に移ってカットの保護が外れ LP が小さくなる、という 2 つの仕組みの重なり。(2) は不具合だが、
  pk1 ではその不具合の状態の方が 2 倍速い。
- `ENOMOTO_MIP_ROLE_IDLE_FIX` (idle を合わせる) は既定では入れない: 単独では pk1 が常に遅い山になり、
  カットの保護を外す組 (NO_PROTECT) と合わせた 40 問の比較は 1 回では差が出ず、揺れの大きい問題で両方向に動く。
  正しい直し方は「idle を合わせる」+「待ち行列が大きいときに LP の行数が膨らまない仕組み (保護を外す、
  または保護されたカットも含めて行数の上限で外す)」で、複数回の計測で確かめる必要がある。
- 既定の挙動に依存している計測結果 (これまでの 40 問の基準値) は、役の復帰の有無で挙動が変わる状態で取られたものなので、
  役を使う問題では揺れが大きいことに注意。
- 共有の待ち行列 (`PoolInner::nodes`、Vec) の最小の下界の線形走査は、ノードが多いときの明確な無駄
  (pk1 の速い山でスレッドあたり 3〜8 秒)。下界順の構造 (BTreeMap など) に替える価値がある。
- 追加した環境変数: `ENOMOTO_MIP_CUTOFF` (診断用、打ち切り値を元の目的の向きで与える)、`ENOMOTO_MIP_ROLE_IDLE_FIX`
  (役に就くとき idle を合わせる)。`ENOMOTO_PROF_TREE_PAR` のスレッドごとの行に idle の内訳 (lock / sleep)、共有の待ち行列の
  平均の大きさ (pool mean)、LNS の時間 (lns) を、開発用の経過の行に `pool_len`・`pool_idle` を加えた。
