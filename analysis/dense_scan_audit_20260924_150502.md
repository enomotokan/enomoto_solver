# 密ベクトル全走査・メモリ移動の監査 (FTRAN / BTRAN / FT更新 / LU分解) + 1e-14 ドロップ挿入点

- 対象: `src/simplex/lu.rs`、`src/simplex/extended_dual.rs`(必要箇所のみ `src/simplex.rs`)、コミット `fbcec94`
- 調査のみ。リポジトリのコードは編集していない(計測用に scratchpad へコピーしたものだけを計装した — §2.2)。
- 計測環境: 2 vCPU コンテナ、`maturin develop --release`(`CARGO_TARGET_DIR=/tmp/claude-0/target_fable`、venv `/tmp/claude-0/venv_fable`)。HiGHS は `highspy` 1.x(`solver=simplex, simplex_strategy=1(dual), threads=1, presolve=on`)。

## 0. 結論(要約)

1. **疎な問題では 1 反復あたりのコストの 30〜45% が「長さ m の全走査(≈1 ns/要素)」で、HiGHS との差(sctap3: 38.7 vs 16.0 us/iter)の大半を説明する**(§2.4 表 D)。密な問題(pilot87, dfl001, maros-r7)では同じ走査が 5〜10% 程度で、そこでの支配項はη列の実演算(スコープ内だが本監査のテーマ外)。
2. 全走査の内訳(sctap3, m=1344, 結果 nnz: rho 9 / alpha 110 / tau 147, us/iter):
   - BTRAN: `U^T` sweep が全 m スロットを舐める 1.86 + `L^T` 逆走査 1.50 + 出力 permute 2.54 + nnz カウント 0.36 = **6.3 us / BTRAN 7.1 us**(結果は 9 非ゼロ)。
   - FT更新: `push_scaled_dense` が `e_tilde`/`a_tilde` それぞれ 2 パス × m = **4.0 us / ft_update 4.8 us**(実際に詰める非ゼロは 7 個と 19 個)。
   - FTRAN: `tau`(rho の FTRAN)の U 全スキャン 1.5 + `permute_out` 2.1 + 各種 fill/copy 0.5。
   - リスト再構築: `compact_rows`(PRICE 用 rho、x_B 用 alpha)0.6 + 1.0。
3. **`fill(0.0)` / `copy_from_slice` 自体は安い**(memset/memcpy 0.05〜0.2 ns/要素 → m=2000 で 0.1〜0.4 us)。高いのは **分岐付き逐次走査・ランダム scatter(0.8〜1.3 ns/要素)** と **enumerate+分岐のパック**。優先順位はそこに合わせた(§5)。
4. メモリ移動: FT更新の `EtaFile::remove`(ヘッダ 3 配列の `Vec::remove` memmove、平均 3〜436 ヘッダ)+ `slot_pos` 再索引は 0.1〜6.8 us/iter。`std::mem::take(row_owners[p])` による確保捨て、dense-arm η の `to_vec()`(degen3 で `push_a` 7.8→3.8 us/iter に半減、§2.5)も確認。
5. 1e-14 ドロップ: 既に `ENOMOTO_TINY`(既定 0)の仕組みがあるが、現状は **密走査側(`permute_out` 等)で判定**しており、かつ **`u_hyper_ok` が `tiny_drop() <= 0.0` を要求するため有効化すると hyper-sparse U 経路が切れる**(lu.rs:4971)。挿入すべき点/してはいけない点を §6 に列挙した。

## 5. 改善候補(優先順)

前提: 出力の**加算順序を変えない**限りビット同一で反復経路は不変。以下、各候補に「ビット同一か / 経路が変わり得るか」を明記。工数は実装担当の目安。

### P1. FT 更新の η パックを非ゼロリスト駆動に(U1, U2, M4)— 期待 3〜6 us/iter(疎問題で 8〜12%)、**ビット同一**
- 追加 API: `EtaFile::push_scaled_list(&mut self, key, pivot, src: &[f64], idx: &[u32] /*昇順・重複なし*/, skip, scale, dense_fraction) -> usize`。`push_scaled_dense` と同じ判定(`tiny`, `!= 0.0`, `skip`)を idx 上だけで行い、nnz > dense_fraction·m のときだけ dense arm(その場合のみ `to_vec` 相当)。**idx を昇順にすれば生成される η の要素順は `push_scaled_dense` と同一 → `dot`/`axpy` の加算順も同一 → ビット同一**。
- シグネチャ変更: `FtLu::try_update_precomputed(&mut self, basis_slot, a_tilde: &[f64], a_tilde_idx: Option<&[u32]>, e_tilde: &[f64], e_tilde_idx: Option<&[u32]>, min_pivot)`(`None` で現行の密パック)。`commit_update` 5985 も同形。
- e_tilde リストの供給: `solve_transpose_unit_work` 5663 が `tracked` のとき `work.touch`(→swap 後 `e_touch`)を持つ。呼び出し側(ED 3839)へ `Option<&[u32]>` を返す(`UnitBtranWork` に `pub fn e_tilde_list(&self) -> Option<&[usize]>` を足すのが最小)。**touch は重複を含み得て順序は sweep 順**なので、`commit_update` 側で `sort_unstable + dedup`(k=4〜220、<0.5 us)。
- a_tilde リストの供給: 疎経路 `solve_sparse_into_*_capture`(5107/5197/5536)では `gp.reach`(昇順)+ R-η の `key` 列(5125 後、`r_etas.key` を追加して sort+dedup)。密経路(5061/5155/5032)は `None`。
- 併せて `a_tilde_out.copy_from_slice`(F5/M7)を同じリストで「前回リスト位置を 0 に戻す + 今回リスト位置を書く」に置換(a_tilde_buf は FTRAN しか書かない: ED 2757)。
- M4: `std::mem::take(&mut self.row_owners[p])` → `FtLu` に `rowp_scratch: Vec<(usize,f64)>` を持ち `mem::swap` で退避、ループ後 `clear()` して swap back。
- リスク: 低。リストが不完全だと η が欠落する(致命的)ので `debug_assert` で密パックとの一致を確認するテストを `ft_update_matches_full_refactor` 系(6642〜)に追加すること。

### P2. BTRAN の hyper-sparse 化(B1, B3, B5, E1)— 期待 疎問題で BTRAN 7→2 us(sctap3 で 14%)、fit2p で 25→10 us、**ビット同一(証明は `u_solve_hyper` 4873-4887 と同じ論法)**
- B1 `u_transpose_sweep_track` に DFS 版 `u_transpose_hyper(&self, z, seed, gp: &mut GpScratch) -> bool` を追加: `row_owners[p]` の `(q, _)` をエッジ(p→q)として seed から DFS、到達スロットを `slot_pos`(singles は先頭側)の昇順にソートして sweep と同じ順で適用。中止条件は `u_solve_hyper` と同じ(reach > 0.25m → false、dense-arm あり → false)。到達集合 = `touch`(重複なし)。ゲートは `rho` の結果密度履歴(`FtranDensity` を BTRAN 用に 1 本追加; HiGHS の `row_ep_density` 相当、閾値 0.15 から)。
- B3 `l_transpose_scatter_core` に DFS 版: `l_row.row(s)` の `k` をエッジ(s→k)として、入力支持(B1 の reach ∪ 適用 R-η の idx)から DFS、到達集合を **降順**にソートして同じ scatter を適用(順序が同じなら各 `w[k]` への加算順も同一)。
- B5 出力: `permute_btran_out_capture` 4069 に `list` 版を追加。rho の前回非ゼロリスト(呼び出し側で保持、`rho` を書くのは ED 3839 のみ)を 0 に戻し、今回リストを scatter。`cap.steps` はリストから直接。
- E1: `rho_rows` は「今回リストを昇順ソート」で置換(`compact_rows` 不要)。`last_rho_nnz` ゲート(3942)は不要になる。
- シグネチャ: `solve_transpose_unit_work(&self, i, out, e_tilde_out, work: &mut UnitBtranWork, cap, rho_list: &mut Vec<u32> /*in: 前回, out: 今回*/, density: &FtranDensity)`。
- リスク: 中。DFS 簿記のコストで m が小さい/結果が密な問題は損をする(sctap3 の FTRAN-U hyper が示すとおり)。ゲート必須。過去の全方向 hyper 化が 15-18% 遅かった経緯(3376-3400)は「毎回の visited 確保 + 事前 O(m) 密度走査」が原因と記録されており、`EpochMarks` + 履歴ゲートなら再発しない見込みだが、Netlib 全体で A/B すること。

### P3. FTRAN 出力を「permute しながらゼロ化 + 支持リスト出力」に(F3, F7, F9, E2)— 期待 1〜3 us/iter、**ビット同一**
- `permute_out` 5412 を `permute_out_zeroing(&self, scratch: &mut [f64], out, list_out: &mut Vec<u32>)` に: 読んだ位置を 0 に戻し(BTRAN の 4094 と同じ)、非ゼロの出力行 `col_perm[s]` を list_out に push(順序は s 順 = 非昇順)。これで F3 の `z.fill`、F9 の 5 箇所の `scratch.fill` が消え、`lu_scratch`/`sparse_scratch` の使い分け制約(5460-5471)も不要になる。
- E2: `xb_rows` は `list_out` を昇順ソート(alpha_nnz は 20〜2500; k log k)で `compact_rows` を置換。**昇順を崩すと `refresh_row` の順序 → chuzr のタイブレークが変わるので必ずソート**。
- `permute_list` 4950 の `out.fill(0.0)`(F8)は出力バッファの前回リストで疎クリア(alpha_full/tau は FTRAN しか書かない)。
- リスク: 低。`list_out` が m 超えの密結果でも動く(その場合ソートコストが m log m になるので、nnz > 0.3m なら従来どおり `compact_rows` へ)。

### P4. dense-arm η の見直し(F10, M5, §2.5)— 期待 degen3 で ft_update −30%、**ビット同一(設計上)**
- まず `ENOMOTO_T_DENSE_ETA_FRACTION=1.0` で Netlib 全体を A/B(既存の環境変数、実装不要)。改善なら既定 0.4 を引き上げる、または R-η だけ dense arm を禁止する(R-η は FTRAN ごとに O(m) `dot` を払う)。
- リスク: 低(結果同一)。

### P5. `EtaFile::remove` の memmove 回避(U4, M1)— 期待 0.3〜7 us/iter(pilot87, dfl001)、**ビット同一**
- 案: 削除ヘッダを **番兵スロット `m`** に付け替える(`key[k] = m`)。全 FTRAN/BTRAN 作業配列を長さ m+1 にし `x[m]` を常に 0 に保てば、既存の `x[p] == 0.0` スキップ(4857, 5293…)が追加分岐なしで死にヘッダを飛ばす(過去の tombstone 試行で「ヘッダごとの dead 判定が高くついた」3641-3646 への回答)。死にヘッダが 10% を超えたら 1 回で圧縮。`u_transpose_order` 4727 / `u_solve_hyper` 4916 / `n_headers`/`update_count` 6070 は死にヘッダを除外する必要あり(`update_count` は `r_etas` 側なので影響なし)。
- リスク: 中(作業配列長 m+1 の徹底; `permute_out` 5416 の `[..m]` スライスは既にあるので互換)。

### P6. BFRT 疎 rhs の受け渡しを `(idx, dense)` に(E4, M9)— 期待 <0.5 us/iter、ビット同一
- `l_solve_sparse_into(&self, idx: &[u32], vals: &[f64] /*dense*/, ...)` のオーバーロードを追加し、ED 4466/4498/4501 の `extend` を削除。

### P7. `DseState::from_basis`(simplex.rs 2938-2964)— 既定 off なので保留。有効化する場合は P2 の単位 BTRAN が結果リストを返せば O(m²)/再分解 → O(Σnnz)。

想定効果の合計(sctap3, 38.7 us/iter): P1 −4、P2 −5、P3 −2、E1/E2 −1.5 ≈ **−12 us(−31%)**。HiGHS 16 us までの残り(≈10 us)は chuzr/bfrt/ループ外の未計上分(17%)で本監査のスコープ外。密問題(pilot87 等)は合計 −3〜5%。

## 6. 1e-14 ドロップ(HiGHS `kHighsTiny` 相当)の挿入点

前提: `ENOMOTO_TINY`(`tiny_drop()` lu.rs:3992、既定 0)が既にあり、現在の適用点は `permute_btran_out*` 4000-4009/4070-4079/4095-4099、`permute_out` 5414-5439、`push_scaled_dense` 3786-3832(いずれも**密走査の中で判定**)。また **`u_hyper_ok` 4971 が `tiny_drop() <= 0.0` を要求**するため、有効化すると hyper U 経路と `permute_list` が全て無効になる(要修正: `permute_list` 4956-4962 に `|v| < tiny → 0` を足し、この条件を外す)。HiGHS の配置(記憶に基づく; `HVector::tight()` が末尾一括、`solveHyper` が index 登録時、`ftranL/ftranU/btranL/btranU` の各 pivotX 判定が `fabs(pivotX) > kHighsTiny`)と同じ方針で、**「値が確定して書き込む点」「非ゼロリストに登録する点」でのみ判定し、落とした位置は 0 を書き戻す**。すべて**経路変更あり**(ビット非同一)なので Netlib 93 問題の目的値一致で検証すること。

### 6.3 運用上の注意
- 絶対閾値 1e-14 はスケーリング後の値に対して使うこと(pilot 系は係数が 1e-6〜1e+6)。まず `ENOMOTO_TINY=1e-14` で既存の密走査側ドロップを有効にして Netlib 93 の目的値一致と反復数変化を見る(このとき `u_hyper_ok` の制約で hyper U が切れる点は計測に含めない/先に直す)。
- ドロップは登録点で 1 回だけ。同じ値に対して密走査側(`permute_out`)と登録点の両方で判定する二重コストは P3 で解消する。
