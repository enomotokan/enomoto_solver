# n2seq36q: MEMB の q を h (bf16) にすると速さが戻るか (2026-11-05)

`analysis/slow9_20261104/n2seq36q.md` で、n2seq36q は `ENOMOTO_MIP_MEMB` の `q` (待ち行列のノードの DSE 重みを 8 ビットの対数に丸める、
今の既定 `MEMB=rcq`) を含むと遅く (16 回中 14 回が 369〜600 秒)、含まないと 86〜110 秒だった。
ここでは `q` の代わりに `h` (重みを bf16、相対誤差 0.4% 以下に丸める) にした `MEMB=rch` で速さが戻るかを確かめた。

- コードは変えていない (cc75b06b のビルド)。`analysis/mitt600_20261103/run_cfg.py` で 4 スレッド・600 秒、4 コアの機械でソルバーは同時に 1 つ。
- 設定 (`analysis/halve_submip_20261030/run.py` の CFGS): membrch = `MEMB=rch`、membrc = `MEMB=rc`、def = 既定 (`MEMB=rcq`)。
- membrch → membrc → def の順で 3 周、計 9 回。生の結果は `cfg_{membrch,membrc,def}_n2seq36q.jsonl`。

## 結論

- **`rch` では速さは戻らない。** membrch は 3 回とも 425〜468 秒・ノード 1.3〜1.5 万で、def (`rcq`、429〜518 秒・1.3〜1.6 万) と同じ側に入る。
  `rc` は 3 回とも 105〜108 秒・ノード約 2200 で、前の記録 (86・110 秒) と合う。
- 事実: bf16 の丸め (相対誤差 0.4% 以下) でも、8 ビットの対数の丸めと同じく遅い側に寄った。重みを丸めない `rc` だけが速い。
- 推測: 前の記録の推測どおり、効いているのは丸めの粗さではなく「重みが丸めない値と少しでも違うこと」で、子ノードの LP の軸の選び方が変わって
  解の探し方の軌跡が別になり、52200 を早く拾えなくなる。この 1 問では `h` も `q` の代わりにならない。`q` / `h` が一般に悪いのかはこの 1 問からは分からない。
