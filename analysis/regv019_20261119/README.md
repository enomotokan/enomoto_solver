## physiciansched6-2 と VUBAGG

- VUBAGG はこの問題で 2283 列 (111827 列の 2.0%) をまとめるが、前処理の後は VUBAGG なしと同じ大きさ (行 12095・列 6159) になる。
  違いは根のカットの道で、def は 2 ラウンド目のカットの LP が 13598 反復 (約 7.6 秒) と重く、根で解き終わるのが 20.0 秒 (なしは RENS で 14.3 秒)。
- 4 スレッド 60 秒 (種 1〜3): def 28.1・35.6・30.9 / off_vub 25.4・21.9・21.0 / v019 21.2・29.1・13.2。off_vub / def は 0.90・0.61・0.68 で 3 種とも速い。
- VUBAGG が働く問題 (P 58 問・g1 の M 48 問・T、`vubcount.jsonl` と analysis/vsscip_slow_20261118/g1/scan.txt): まとめる割合は
  neos-787933 99% (200〜470 秒 → 0.4 秒)・neos-4722843-widden 6.9% (g1/def 0.77・1.02、中立)・physiciansched6-2 2.0% (遅い)・
  piperout-27 0.5%・neos8 0.07% (どちらも中立)。
- 試作 `ENOMOTO_T_MIP_VUBAGG_MIN_FRAC` = f (既定 0 = 従来どおり、src/mip/mod.rs): まとめる列が全部の列の f に満たなければまとめない。
  f = 0.05 で physiciansched6-2 は 19.8 秒 (1 スレッド)、neos-787933 は 0.4 秒のまま。
- **判断 (利用者、2026-11-19): physiciansched6-2 の差は、前処理の後が同じ大きさのまま根のカットの道が変わり重い LP に当たった「運」による差。
  1 問に合わせた対策になるので VUBAGG_MIN_FRAC は既定にせず、計測もしない (試作のコードは既定に影響しないので残す)。**

## neos5 (1 スレッドでも 2 倍、切れる機能ではない) の二分探索

`bistest.sh` (別の作業木でビルドし、neos5 を 1 スレッド・種 1・300 秒で解く。130 秒超なら悪い) で 713405e15 (0.1.9 の元) .. 351a4ede7 の
src を変えたコミットを `git bisect run` した (`bisect_neos5.txt`、秒・ノード数)。

- 713405e15: 84.4 秒・117312 ノード (PyPI の 0.1.9 は 88.7 秒・120141 ノード)。
- **最初の悪いコミット 8f4a55ebd** (「SYMDYN=f (orbital fixing + LexRed の併用) を既定から外す」、併用で最適解を切る誤答の直し):
  直前 79.9 秒・113386 ノード → 132.3 秒・216108 ノード。
- ただし f を戻すだけでは 0.1.9 に戻らない。誤答の本当の原因を直した 6e0cf3bce (LexRed の「等号を除く」締めの誤りの直し) の前後を
  `SYMDYN=f` で比べると 83.9 秒・113386 ノード → 112.2 秒・171930 ノード。今の版に `SYMDYN=f` を付けると 150.2 秒・180129 ノード
  (今の既定 163.7 秒・242871 ノード)。
- 見立て: neos5 の 0.1.9 の速さの大部分は、誤った (強すぎる) LexRed の締めによる余分な刈り込み。正しさと引き換えなので戻さない。
  残りの約 1.1 倍は f を既定から外した分 (f を既定に戻すかは、問題の特徴の場合分けではなく全体の判断。以前の得は P −0.4%・M +2.4% と小さい)。
