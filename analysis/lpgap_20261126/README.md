# 当方の LP (双対単体法) が HiGHS より遅い原因: アルゴリズムか実装か (2026-11-26)

親の依頼 (利用者「LP のアルゴリズム自体に問題があるわけではないと思うが、そのへんまで含めてはっきりさせてほしい」)。
先端 6e78c5d90 (7d839da81 を含む) でビルド、1 スレッド、冷えた始動 (基底なし)。HiGHS は highspy 1.15.1 の双対単体法
(`solver=simplex`・`simplex_strategy=1`・`threads=1`)。

## 0. 台本

- `mklp.py`: 比べる LP を `.lpgap_cache/` (gitignore) に MPS で書き出す。`dano3_3_fix` = dano3_3 の整数列 69 本を当方の 1 スレッドの最適解
  (576.34463303) の値で固定した LP、`*_rel` = 整数を外した LP 緩和。
- `one.py {ours|highs|highs_pre} LP名`: 当方 (`lp_solver="simplex"` = 傾き・切片双対二段解法、`threads=1`) か HiGHS (前処理なし / あり) で解く。
  当方の内訳は `ENOMOTO_PROF_PHASES_EXT=1` (主ループの段ごとの時間)。
- `highs_opt.py LP名 キー=値 ...`: HiGHS のオプションを変えて解く (摂動・価格付け・尺度の効き目)。

## 7. 結論 (アルゴリズムか実装か)

1. **1 反復の実装は、調べた LP の多くで HiGHS 並み**。前処理後の大きさが同じ dano3_3 で 349 対 348 µs・240 対 395 µs、neos-960392 で 197 対 631 µs、
   physiciansched6-2 の LP 緩和で 578 対 575 µs (前処理あり)。カットを足した LP の解き直しは 1.26 倍。
2. **例外は大きな疎の LP (uccase12、9 万行) の 1 反復 5 倍** (2368 対 466 µs)。実装の問題で、原因は 2 つ:
   (a) FTRAN・BTRAN の結果の 1e-14 未満の雑音を捨てない (α の非零の 3 分の 2 が雑音。HiGHS は `kHighsTiny` で捨てる)。既存の `ENOMOTO_TINY` は超疎の経路を切るので使えない。
   (b) 再分解の合成の時計が緩く FT 更新が千回以上続く (`SYNTH_CLOCK_FACTOR` 16 → 4 で 177 → 120 秒)。
   (a) は試作 `ENOMOTO_LU_TINY_HS` で直したが (1 反復 −21%)、FTRAN の中の走査 (`permute_out` の長さ m の密な置換・`U` 段の起点の判定) にはまだ雑音が残る。
3. **差の主は反復数で、退化の強い LP での道筋の差** (アルゴリズム側、ただし明白な誤りではない):
   - dano3_3_rel で当方 2.8 倍だが、摂動を外す (当方 0.46 倍)・HiGHS の前処理の並びで解く (1.4 倍)・微小値を捨てる (0.40 倍) で 0.4〜2 倍に動く。
     HiGHS 自身も摂動なしで固定 LP が 117 万反復でも終わらない (摂動あり 5.7 万)、Dantzig にすると 11.5 倍。
   - DSE 重みは正しい (選んだ行の 99.5〜99.8% が真値と 1% 以内)。BFRT の HiGHS 式のまとめ (`BFRT_GROUP=gz`) は反復 −28% だが 1 反復が重くなり時間は同じ。
   - 例外は supportcase42 の根の LP (既知、lpwarm_20261118): 自由列の入れ方で数値が破綻して解けない。これはアルゴリズム (比の判定) 側の不具合。
4. **出発点の数の読み直し**: dano3_3 の固定 LP の「58.7 秒 対 13.6 秒」は、1 スレッドでは当方 18.3 秒 (研磨では 17.7 秒) 対 HiGHS 前処理なし 19.9 秒・前処理あり 10.5 秒。
   残る差 (1.7 倍) は HiGHS の前処理の後の並びでの反復の差 (3.0 万対 5.0 万)。MIP の根の LP が 8384 反復なのは 1 スレッドでも内点法 → クロスオーバーで解くため。
   physiciansched6-2 の根のカットの LP の解き直しは HiGHS より速い (8.5 対 11.9 秒)。

**まとめ**: 「両方」だが重みは違う。LP のアルゴリズム (双対単体法・DSE・BFRT) に一般的な誤りは見つからず、多くの LP で HiGHS 並み。
差は (i) 退化の強い LP での道筋の差 (摂動・同点の扱い。HiGHS も同じ振れ幅を持つ) と、(ii) 大きな疎の LP での実装の手間 (微小値の雑音・再分解の頻度) に分かれる。
(ii) は直す余地がはっきりしている: 次は FTRAN の中の `U` 段の起点・`permute_out` でも雑音を捨てる形と、合成の時計を大きな疎の LP で強める形 (LUCLOCK の取り下げとの関係を見る)。

### 6.3 切り捨ての閾値は絶対か相対か (親の問い)

- HiGHS の `kHighsTiny` = 1e-14 は絶対値で、尺度を調整した LP (列の最大を 1 付近にそろえる) に対して使う。尺度がそろっていれば絶対値の判定はほぼ「ベクトルの大きさに対する相対」になる。
- 当方の LP の経路は、尺度の調整を行数 1 万以上・係数の幅 1e4 以上でしかかけない (`ENOMOTO_SIMPLEX_SCALE`、5 節)。尺度なしの LP で絶対 1e-14 を使うと、
  値の大きい列 (例: 係数 1e6 の列の FTRAN) では相対 1e-20 の雑音しか捨てられず、値の小さい列 (係数 1e-6) では意味のある値を捨てうる。
- 理屈に合うのは「そのベクトルの最大の絶対値 (または入力の列のノルム) × 1e-14」の相対の判定。FTRAN の結果では `|v| < 1e-14 · max_i |α_i|` は 1 回の走査の後でないと決まらないので、
  書き出す点 (置換の最終段・非零一覧) で 2 段 (最大を求めてから捨てる) にするか、入力の列 `a_q` の最大の絶対値で代える (FTRAN の前に分かる) のが実装しやすい。
  1e-14 は HiGHS の既存の値で、新しい閾値は足さない。uccase12 (尺度なしの経路、係数の幅は 5 節) で絶対と相対の違いを見るのは次の段。
