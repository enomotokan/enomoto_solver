# 当方の LP (双対単体法) が HiGHS より遅い原因: アルゴリズムか実装か (2026-11-26)

親の依頼 (利用者「LP のアルゴリズム自体に問題があるわけではないと思うが、そのへんまで含めてはっきりさせてほしい」)。
先端 6e78c5d90 (7d839da81 を含む) でビルド、1 スレッド、冷えた始動 (基底なし)。HiGHS は highspy 1.15.1 の双対単体法
(`solver=simplex`・`simplex_strategy=1`・`threads=1`)。

## 0. 台本

- `mklp.py`: 比べる LP を `.lpgap_cache/` (gitignore) に MPS で書き出す。`dano3_3_fix` = dano3_3 の整数列 69 本を当方の 1 スレッドの最適解
  (576.34463303) の値で固定した LP、`*_rel` = 整数を外した LP 緩和。
- `one.py {ours|highs|highs_pre} LP名`: 当方 (`lp_solver="simplex"` = 傾き・切片双対二段解法、`threads=1`) か HiGHS (前処理なし / あり) で解く。
  当方の内訳は `ENOMOTO_PROF_PHASES_EXT=1` (主ループの段ごとの時間)。
- `highs_opt.py LP名 キー=値 ...`: HiGHS のオプションを変えて解く (摂動・価格付け・尺度の効き目)。

|---|---|---|---|

| HiGHS 前処理なし | 57076 | 19.9 | 348 |

- 当方の LP の経路は HiGHS の前処理なしと同じ速さ (反復 0.92 倍、1 反復 1.00 倍)。HiGHS の前処理ありより 1.7 倍遅いのは反復の差 (30397 対 52305)。
  前処理の後の大きさは同じなので、差は前処理後の LP の形 (行・列の並び、尺度) から来る反復の違い。
- 58.7 秒は当方の 1 スレッドの冷えた LP では出ない。4 スレッドで他のスレッドと CPU を分け合った研磨の LP (nattai 6 節の 16〜17 秒の LP) を測った数と思われる。
- MIP の根の LP が 8384 反復で済むのは単体法が良いからではない: 1 スレッドでも根の最初の LP は内点法 → クロスオーバー → 単体法
  (`TwoStageLp::solve_seq_ipm`、gdb で確かめた) で解いていて、8384 はクロスオーバーの後の単体法の反復。5.6 秒のうち主ループは 1.85 秒で、残りは内点法。
- 研磨の LP (整数を固定した LP) は基底なしの単体法だけで解くので 17.7 秒かかる。MIP 全体 24.3 秒のうち 73% が研磨。

## 3. dano3_3_rel の反復の差の切り分け

当方の主ループの内訳 (164188 反復、39.4 秒): FTRAN 27.4%・x_B 更新 13.0%・価格付けの行 11.0%・再分解 11.0%・chuzc 8.5%・BTRAN 7.5%・BFRT 6.4%。

  作り直した後でも HiGHS の 1.7 倍あるので、ずれ以外の何か (BFRT の同点の扱い・傾き・切片の辞書式の行の比べ) も残る。
