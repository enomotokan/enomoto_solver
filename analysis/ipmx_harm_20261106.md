# 内点法 + クロスオーバーの試作一式 ipmx の害 2 つ (mc11 の悪化・期限の超過) の原因と直し (2026-11-06)

- 発端: bench27 (`analysis/halve_submip_20261030.md` の最後の節) で、(1) mc11 が既定 24.0・9.7・26.7 秒に対し ipmx は 3 回とも時間切れ、
  (2) dano3_3 (ipmx 74.0 秒)・chromaticindex512-7 (73.6 秒) が 60 秒の上限を約 14 秒越えて返った。
- 機械: 4 CPU、ソルバーは同時に 1 つ。4 スレッド・60 秒。土台はこのブランチの c3e7eb53 (+ この記録の直し)。
- 台本・生データは `ipmx_harm_20261106/`: `run.py 設定,... 問題,... 回数` (ログ `logs/<問題>_<設定><接尾辞>_<回>.log`、結果 `res.jsonl`。
  `ENOMOTO_MIP_LOG=1 ENOMOTO_DEBUG_RACE=1` を付け、`EXTRA_ENV`・`RUN_TAG` で環境変数と接尾辞を足す)、`summ.py 接尾辞` (表)、
  `bench58.py 設定,... 回` (58 問、`bench58.jsonl`)、`summ58.py` (58 問の集計)。設定の名前は `run.py` の `CFGS`
  (`H` = `T_XO_CLEANUP_HINT=3`、`R` = `XO_IPM_RETRY_PC=3`、`Z` = `XO_NO_BOUND_STOP_ZERO_COST=1`、`K` = `IPM_KKT_AUG_RATIO=4`、
  `ipmx_noX` = ipmx から X を外す、`M` = `XO_MIP_CLEANUP_HINT=1`、`ipmxm` = M + R + Z + K)。
  接尾辞なしと `_dbg`・`_sep`・`_ov3`・`_fix` は直しの前後の切り分け (直しの前のビルド)、`_v2` は直しの後のビルドでの比べ。

## 結論 (短く)

1. **mc11 を悪くしているのは `ENOMOTO_T_XO_CLEANUP_HINT=3` だけ** (事実、1 つずつ外す・足すの 30 回)。ほかの 3 つ (`RETRY_PC`・
   `NO_BOUND_STOP_ZERO_COST`・`KKT_AUG_RATIO`) は mc11 では何もしない (根の下界・時間とも既定と同じ)。
   - 仕組み (事実): mc11 の根の LP (大きさ 約 1.1 万) は二段解法と内点法 + クロスオーバーが 0.03〜0.06 秒でほぼ同着で、勝ち負けで根の頂点が
     変わる (`analysis/mc11_wait1_20261103.md`)。既定では、二段解法の勝ち → 根の下界 11683 の道 (約 10 秒)、内点法の勝ち → 11666 の道
     (15〜23 秒)。`CLEANUP_HINT=3` は仕上げの単体法に押し出しの頂点の非基底の向きを渡すので、**内点法が勝ったときの最適な頂点が別のものになり**、
     根のカットの 4 ラウンド目から値が分かれて **根の下界 11616 の道** (木 3000〜6000 ノード、32 秒〜時間切れ) に入る。11616 の道は、
     直しの前のビルドで `H` を含む 15 回のうち根の競争で内点法が勝った 14 回すべてで出た (残り 1 回は二段解法の勝ちで 11683、9.4 秒)。
     直しの後のビルドの ipmx 3 回も同じ (内点法の勝ち 2 回が 11616、二段解法の勝ち 1 回が 11683)。`H` を含まない 24 回 (直しの前 18 回・後 6 回) は 11666 か 11683 だけ。
   - 内点法 + クロスオーバーが MIP の中で使われるのは、LP の探りの最初の LP と根 (再スタートの後の根・整数を固定した LP の確かめを含む) の
     競争、根の LP の解き直し (`solve_rescue`) と、内点法による丸め (押し出しまで。仕上げはしない) だけ (コードとログで確かめた)。
     ノードの LP・サブ MIP (同時実行のスレッド数 1)・潜り・木のスレッドでは使われない。`CLEANUP_HINT` はクロスオーバーの仕上げにしか効かない。
     したがって mc11 の差は「LP が遅い」のではなく「根の頂点が変わって道が変わった」もの (根の LP 自体は 0.04〜0.06 秒で変わらない)。
2. **期限の超過は内点法 + クロスオーバーのせいではない** (事実、`ENOMOTO_DEBUG_CROSSOVER=1 ENOMOTO_DEBUG_IPM=1`)。ipmx で根の LP が早く
   終わる (chromaticindex512-7: 2.2 秒、既定は二段解法で 60 秒の間に終わらない) ので、既定では届かない後の段に届き、そこが期限を見ていなかった:
   - **chromaticindex512-7**: zerohalf の分離 (mod 2 の消去) が 1 回 約 21 秒かかり、期限を見ない。カットの選び方の比べ (予算 2.8 秒) で 2 回
     (比べの壁時計 44.8 秒)、根のカットの 0 ラウンド目で 1 回呼ばれ、後者が期限を 6 秒越えた (`_sep` の SEPPROF: zerohalf 64.5 秒 / 分離 66.6 秒)。
     既存の試作 `ENOMOTO_MIP_OVERRUN3` の `z` (zerohalf が期限を見る) で 60.03 秒に収まった。
   - **dano3_3**: MIP は 50〜52 秒で最適で終わるが、返す前の **解の研磨** (`polish_solution`: 整数を固定した元の LP を基底なしの単体法で解く) に
     期限がなく 16〜17 秒かかって 66〜69 秒で返っていた (既定では MIP が時間切れになり、時間を使い切ったときは研磨の LP を解かない既存の
     `ENOMOTO_MIP_LATE_NO_RESOLVE` の分岐に入るので出ない)。
3. 直し (既定の経路も変える。どちらも期限を過ぎた後だけ効く):
   - `ENOMOTO_MIP_ZH_DEADLINE` (新、既定 1、`=0` で以前の形): zerohalf の分離が求解の期限を見る (`OVERRUN3` の `z` と同じ働き)。さらに、期限が
     渡されているときは止めの合図 (`crate::cancel::halted`、木の探索の従のスレッド) も期限と同じに扱う。
   - `ENOMOTO_MIP_POLISH_DEADLINE` (新、既定 1、`=0` で以前の形): 研磨の LP に求解の期限 (始め + 時間の上限) を渡す。間に合わなければ研磨しない
     (整数の丸めと目的値の計算し直しだけ。返す値・状態は研磨なしのもの)。
   - 直しの後 (`_v2`): dano3_3 は ipmx・ipmxm で 4 回とも 60.01〜60.02 秒で最適 (目的値 576.34463303 は研磨ありと 1e-12 で同じ)、
     chromaticindex512-7 は 60.1 秒。
4. 害を除いた形 **ipmxm**: `CLEANUP_HINT=3` を MIP の根の LP だけに絞る版 `ENOMOTO_XO_MIP_CLEANUP_HINT=1` に替え、さらに **LP の大きさ
   (列 + 非零) が 5 万以上のときだけ** 向きを渡す (`ENOMOTO_T_XO_MIP_CLEANUP_HINT_MIN_SIZE`、既定 50000)。小さい LP では仕上げは向きなしでも
   数十ミリ秒で、向きを渡す得はなく頂点が変わるだけ。効くはずの問題は 9.6 万〜36 万。
   - mc11: ipmxm は 9.6・17.5・14.6 秒 (既定 15.1・17.1・22.8、ipmx 9.6・41.9・45.1)。11616 の道は出ない。
   - 効くはずの問題では ipmx と同じ得を保つ (5 節)。58 問は 6 節。

## 1. mc11 の切り分け (直しの前のビルド、3 回ずつ)

`python3 summ.py ""` の抜粋。`[..]` は LP の探り・根の競争の勝ち (s = 二段解法、i = 内点法 + クロスオーバー) を順に、rb は根の下界。

| 設定 | 時間 (秒) | 根の下界 | 根の競争の勝ち |
|---|---|---|---|
| def | 9.6・16.6・18.5 | 11683・11666・11666 | s・i・i |
| ipmx | 41.2・60.0TL・60.0TL | 11616 × 3 | i・i・i |
| H (`CLEANUP_HINT=3` だけ) | 9.4・44.4・60.0TL | 11683・11616・11616 | s・i・i |
| R・Z・K (1 つだけ) | 16.5〜19.4 (9 回) | 11666 × 9 | |
| ipmx_noH | 17.1・16.3・22.1 | 11666 × 3 | |
| ipmx_noR・noZ・noK | 31.8〜60.0TL (9 回) | 11616 × 9 | |
| ipmxm (直しの後) | 16.2・17.3・20.8 | 11666 × 3 | |

- 事実: 11616 の道は `H` を含む設定で根の競争に内点法が勝ったときだけ出る (14/14)。`H` なしの 18 回は 11666 (内点法の勝ち) か 11683 (二段解法の勝ち)。
- 事実: 根のカットのループは 3 ラウンド目まで同じ値で、4 ラウンド目に分かれる (既定 8650.4、ipmx 8614.0。`logs/mc11_def_0.log`・`mc11_ipmx_0.log`)。

  頂点の違いによる道の運で、`CLEANUP_HINT` が LP を悪くしているわけではない。ただし mc11 では 3 回中 2〜3 回の割で決まって出るので、
  「揺れ」ではなく系統的な害として扱った。

## 3. 直し

| 環境変数 | 既定 | 中身 | 場所 |
|---|---|---|---|
| `ENOMOTO_MIP_ZH_DEADLINE` (新) | 1 (`=0` で以前の形) | zerohalf の分離に求解の期限を渡し、mod 2 の消去・カットの組み立ての途中で見て、過ぎていればカットなしで戻る (`OVERRUN3` の `z` と同じ。逐次の分離・`SEP_PARALLEL` の分離の両方)。期限があるときは止めの合図 (`halted`) も見る | `src/mip/zerohalf.rs` (`zh_deadline_on`・`zh_past_deadline`)・`src/mip/separation.rs` |
| `ENOMOTO_MIP_POLISH_DEADLINE` (新) | 1 (`=0` で以前の形) | 返す解の研磨の LP (`polish_solution`) を `cancel::with_deadline(始め + 時間の上限)` の中で解く。最適で終わらなければ研磨しない | `src/mip/mod.rs` |

- 期限の 2 つの直しは、時間内に終わる回の道を変えない (zerohalf は期限を過ぎた後だけ、研磨は時間の上限までに終わらないときだけ違う)。
  `ENOMOTO_XO_MIP_CLEANUP_HINT` は既定では使わない試作のまま (閾値は試作を使うときだけ効く)。
- 研磨を期限で止めたとき、返す値は研磨なしの値 (整数の丸め + 誤差補償つきの和の目的値) で、状態は変えない (dano3_3 は最適のまま)。
