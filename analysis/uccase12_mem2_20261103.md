# uccase12 のメモリ不足: 開いたノードの持ち物を減らしメモリに上限を置く試作 ENOMOTO_MIP_MEM2 (2026-11-03)

bench に使う環境変数: `ENOMOTO_MIP_MEM2=1` (試作の全部。既定は今までどおり。上限を変えるなら `ENOMOTO_T_MIP_MEM2_FRAC` (既定 0.3) か
`ENOMOTO_T_MIP_MEM2_BUDGET_MB`)

並列 3 セッションのうちの 1 つ (担当: 開いたノード 1 つあたりの持ち物を減らし、メモリに上限を置く試作)。きっかけは
`analysis/mittelmann_ready_20261103/long_b.md` の「uccase12 の調べ (OOM)」。4 スレッド、この機械は 4 コア・15 GB。
生データは `analysis/uccase12_mem2_20261103/` (`runs.jsonl`・`bench58.jsonl`・`summ58.txt`・`logs/raw_logs.tar.gz`)。

## 要点

1. **求解 100〜170 秒の原因不明の 5〜6 GB は、潜りの兄弟に持たせる親の LP の LU の写し (`dive_stack` の `LuSnapshot`)** (事実)。
   既存の切り替え `ENOMOTO_MIP_NO_SIBLING_LU=1` で uccase12 を 300 秒解くと、跳ねが消える (求解 100〜170 秒で RSS 1.5 → 1.7 GB。
   既定は 1.5 → 8 GB)。潜りの深さの分だけ、68k 行の LU (と DSE 重み) を 1 つずつ持ち続けていた。開いたノードの数とは関係がない。
2. 試作 `ENOMOTO_MIP_MEM2=1` では uccase12 が **600 秒まで落ちずに走る** (最大 RSS 7.3 GB、既定は 325 秒・13.6 GB で OOM)。
   ただし **解けない** (時間切れ、目的値 11507.405062 = HiGHS の最適値、下界 11507.370457、ギャップ 3.0e-6、ノード 23281)。
   ギャップが閉じないのはメモリとは別の問題 (下の「uccase12 が閉じない」)。
3. 上限を下げる (`ENOMOTO_T_MIP_MEM2_FRAC=0.1`、上限 1.46 GB) と捨てる処理が働き、最大 RSS 4.95 GB (結果は同じく時間切れ、
   目的値 11507.405338、ノード 26084)。
4. gmu-35-40 1800 秒: 最大 RSS **2.7 GB** (long_b の既定は 5.7 GB)。開いたノード 1 つあたり約 5.6 KB (既定 9.2 KB)。上限には届かず、
   減ったのは DSE 重みを f32 の並びにした分と LU の写しの上限の分。ギャップは 1.46e-4 (long_b の既定は 7.75e-5。暫定解の揺れ、1 回)。
5. 58 問 1 回 (4 スレッド・60 秒): SGM 16.30 → 16.81 秒 (**+3.1%**)、解けた数 44 → 45、最大 RSS の和 25.2 → 21.9 GB。
   遅くなった側はいつも揺れる問題 (hypothyroid-k1・pk1・neos-911970)。1 回なので揺れの範囲と区別できない。

## 試作の中身 (`ENOMOTO_MIP_MEM2`、`src/mip/solver.rs`・`src/mip/queue.rs`)

値 `1` で全部、または文字の組み合わせ。

| 文字 | 内容 |
|---|---|
| `p` | ノードに保存する DSE 重みを、番号なしの f32 の並び (`NodeDse::Packed`) にする。番号は一緒に保存した基底の基底変数 (番号の昇順) から戻す。(u32, f32) の組の半分 (uccase12 で 1 ノード約 550 → 270 KB)。合わなければ組のまま |
| `s` | 共有の待ち行列に出すノード (`SnapNode`) の基底・DSE 重みを `Arc` にし、同じ親の兄弟を続けて出すときは写しを共有する |
| `b` | 開いたノード (各スレッドの待ち行列 + 共有の待ち行列) の持ち物 (基底・DSE 重み・効くカットの番号・境界の変更) の合計の目安を数え (`Solver::mem2_check`、待ち行列の長さの 1/8 (32 以上) ノードおき)、上限の 0.9 倍を超えたら深いノード (同じ深さなら下界の大きいもの) から DSE 重みを、足りなければ基底を捨てて 0.7 倍まで下げる (自分の待ち行列と共有の待ち行列を、合計に占める割合で)。合計が上限の 0.5 倍を超えたら新しいノードに DSE 重みを、0.9 倍を超えたら基底も保存しない。潜りの兄弟は捨てない |
| `d` | 合計が上限の 0.5 倍を超えたら深さ優先に寄せる (潜りのノード数の上限と、兄弟へ戻る下界の条件を外す) |
| `l` | 潜りの兄弟に持たせる LU を、新しい `ENOMOTO_T_MIP_MEM2_LU_KEEP` (既定 8) 個までにする (古いものは LU だけ捨て、基底は残す) |

- 上限 (`mem2_budget`): `ENOMOTO_T_MIP_MEM2_BUDGET_MB` があればその値、なければ (cgroup の上限 − 今の使用量 と MemAvailable の小さい方、
  最初に数えたときの値) × `ENOMOTO_T_MIP_MEM2_FRAC` (既定 0.3)。この機械では 4.36〜4.62 GB。
- `MIP: MEM2: tid 0 checks … over … peak … (budget …) stripped dse … basis …, nodes without dse … without basis …` を求解の終わりに出す
  (`ENOMOTO_MIP_LOG=1`)。
- 既定の経路は変えていない (`OpenNode::dse` の型を `Rc<NodeDse>` にし、`SnapNode` の基底・DSE を `Arc` にしたが、既定では中身は
  今までと同じ組・写しで、`Arc::try_unwrap` で写さずに取り出す)。`cargo test --release --lib`: 333 通過、0 失敗 (18 は無視の印)。

## uccase12 600 秒 (`run_mem.py`、全スレッドの済んだ・開いたノードつき)

| 回 | 結果 | 目的値 | 下界 | ノード | 最大 RSS | 開いたノード (最後の経過行) |
|---|---|---:|---:|---:|---:|---:|
| 既定 (long_b、参考) | 325 秒で OOM | - | - | (8872、log の回) | 13.6 GB | 8859 |
| `ENOMOTO_MIP_NO_SIBLING_LU=1` (300 秒) | 時間切れ | 11507.405062 | 11507.370448 | 5777 | 5.9 GB | 5655 (求解 228 秒) |
| `MEM2=1` | 時間切れ | 11507.405062 | 11507.370457 | 23281 | 7.3 GB | 21404 (求解 524 秒) |
| `MEM2=1`、`FRAC=0.1` | 時間切れ | 11507.405338 | 11507.370395 | 26084 | 4.95 GB | 21133 (求解 512 秒) |

| 回 | 5 s | 65 | 125 | 185 | 245 | 305 | 365 | 425 | 485 | 545 | 600 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 既定 (long_b) | | | | | 10043 (240 s) | 12759 (315 s、OOM) | | | | | |
| NO_SIBLING_LU | 609 | 776 | 1624 | 1834 | 3359 | (300 秒で終わり) | | | | | |
| MEM2=1 | 663 | 790 | 1990 | 2413 | 3270 | 4100 | 5162 | 5807 | 6327 | 6894 | 7113 |
| MEM2=1、FRAC=0.1 | 603 | 733 | 1953 | 2455 | 3149 | 3601 | 4252 | 4586 | 4639 | 4840 | 4952 |

- MEM2=1 の回は、持ち物の合計の目安が最大 2.9 GB (上限 4.36 GB の 0.67 倍) で、捨てる処理は動かず、新しいノードに DSE 重みを
  保存しなかったのが 2340 回 (0.5 倍を超えてから)。RSS は 600 秒の時点でまだ伸びている (開いたノード 1 つあたり約 0.25 MB)。
  合計の目安が上限の 0.9 倍 (3.9 GB) に届くと捨て始めるので、そこで頭打ちになるはず (FRAC=0.1 の回は 425 秒以降の伸びが 1 分あたり 0.1 GB 前後に鈍る)。
- FRAC=0.1 の回は、上限 1.46 GB を超えて基底を 223 MB 捨てた (主スレッドの分)。RSS は 425 秒以降 4.6〜4.95 GB (伸びは鈍るが止まってはいない)。
- **目安に入らない分が大きい**: FRAC=0.1 の回で目安 ≤ 1.46 GB に対し RSS 4.95 GB。起動直後の 0.6 GB と根の後の約 1.5 GB を
  引いても 2 GB 前後が開いたノードの数に連れて増える (2 万ノードで 1 つあたり約 100 KB)。目安に入れていないもの (待ち行列の索引、
  `SnapNode` の `cut_basis`、割り当ての余り、LU の写し 8 個 × 4 スレッド など) のどれかは確かめていない。上限を本当に守らせるには、
  /proc の RSS そのものを見る形にする方が確か (次の手)。
- 潜りの兄弟の LU は、既定 (`l` なし) では潜りの深さだけ持つ。`l` (8 個まで) でも、上の推移では求解 100〜170 秒の跳ねは出ていない。

### uccase12 が閉じない (メモリとは別)

- どの回も全体の下界は 11507.3704 前後から動かず、ギャップ約 3e-6 のまま。HiGHS は 6949 ノードで閉じる。
- 木の中の暫定解 11507.40254 は **元の問題で実行不能** (事実、`mem2_uccase12_600.log` の終わり): 後処理の修復で 11507.40441 になり、
  それも `the postsolved solution is infeasible in the original problem` で前処理なしの修復に回り、11507.405062 (HiGHS の最適値) で返る。
  long_b の「気になる点」(木の中の暫定解が HiGHS の最適値より 2.5e-3 小さい) は、再スタート後の問題での誤った解だった
  (`analysis/uccase12_20261023.md` の 4. と同じ種類)。打ち切り値が本当の最適値より小さいので、最適解を含む部分木を刈っているかも
  しれない (確かめていない)。下界が上がらない理由はこれとは別 (下界 11507.3704 は打ち切り値より十分小さい)。

## 考え・次の手

- **LU の写しの上限 (`l`) は単独でも入れる価値が高い** (uccase12 の 5〜6 GB の跳ねの原因で、60 秒の問題にはほぼ関係しない)。
  兄弟へ戻ったときの LU は分解を 1 回省くだけなので、深い所の写しを捨てても失うのは小さい。次は `l` だけ・`p` だけで 58 問を
  2〜3 回回して、遅くならないか確かめる (今回の +3.1% は全部入りの 1 回)。
- 上限の数え方は目安なので、本当に守らせるには /proc/self/statm の RSS を見て、RSS が (使えるメモリ × 割合) を超えたら捨てる形の方が
  確か。目安に入らない約 100 KB/ノードの正体はヒーププロファイラで確かめる。
- uccase12 を解くには、メモリより木の探索 (下界が 11507.3704 から上がらない、HiGHS の 3 倍のノードでも閉じない) と、再スタート後の
  誤った暫定解 (元の問題で実行不能) の方を直す必要がある。

## 再現手順

```sh
pip install -q highspy==1.15.1 maturin
maturin build --release -o /tmp/whl && pip install -q --force-reinstall --no-deps /tmp/whl/*.whl
D=analysis/uccase12_mem2_20261103
MEM_TAG=nosiblu ENOMOTO_MIP_NO_SIBLING_LU=1 python $D/run_mem.py 300 uccase12
MEM_TAG=mem2 ENOMOTO_MIP_MEM2=1 python $D/run_mem.py 600 uccase12
MEM_TAG=mem2_f10 ENOMOTO_MIP_MEM2=1 ENOMOTO_T_MIP_MEM2_FRAC=0.1 python $D/run_mem.py 600 uccase12
MEM_TAG=mem2 ENOMOTO_MIP_MEM2=1 python $D/run_mem.py 1800 gmu-35-40
python $D/bench58.py 1 && python $D/summ58.py > $D/summ58.txt
```

- `run_mem.py` は `long_b/diag_worker.py` (log=True) を子として起動し、5 秒ごとに RSS (子孫を含む和) を取る。RSS が `MEM_CAP_MB`
  (既定 12500) を超えたら止める (今回は一度も止めていない)。結果・RSS の推移 (`series`)・経過行の間引き (`prog`) は `runs.jsonl`。
- ログ (`ENOMOTO_MIP_LOG=1` の標準エラーと経過の標準出力) は `logs/raw_logs.tar.gz`。
