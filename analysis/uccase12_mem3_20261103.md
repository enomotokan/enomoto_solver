# uccase12: 木の中の暫定解が HiGHS の最適値より小さい件は誤答の芽か (2026-11-03)

uccase12 のメモリ不足の並列 3 セッションのうちの 1 つ (担当: `analysis/mittelmann_ready_20261103/long_b.md` の「気になる点」)。
long_b では木の中の暫定解 11507.40254 が HiGHS の最適値 11507.40506 より 2.5e-3 (相対 2.2e-7) 小さかった。
ブランチ ccr-1beed81b-ex0uhq (3076c6b7 から)。4 スレッド、1 回ずつ。ソルバーは同時に 1 つ。生データは `analysis/uccase12_mem3_20261103/`。

## 結論

- **木の暫定解が最適値より小さいのは、再スタートの後の前処理が行を許容誤差より大きく緩めた問題の解だから** (事実)。
  その解は元の問題で実行不能: 代入で消した連続列 74〜153 本が下限 0 を最大 **2.2e-5** 下回る (行の破れは 0 本)。
  最初の求解 (再スタートの前) の暫定解は元の問題で実行可能 (違反 1e-11 程度)。破れは再スタート 1 回目の後の解で 5.5〜6.3e-6、
  2 回目の後の解で 1.1〜2.2e-5 と、再スタートのたびに積み重なる。
- **緩めているのは `fix_tiny_width_columns` (src/mip/mod.rs) の丸めの余裕 `1e-9·(1+|b|)`** (事実)。前処理のプロービングで幅が
  許容誤差以下になった連続列を 1 点に固定するとき、その列を含む不等式の行を「ずれた分 w」に加えて余裕 1e-9·(1+|b|) だけ緩める。
  右辺 5000 前後の行 (容量の行) では余裕が 5.4〜5.9e-6 になり、ずれた分 (最大 1e-6、たいてい 1e-7 程度) よりずっと大きい。
  最初の前処理では対象の行の右辺が小さく余裕は 2e-9 だが、再スタートの後は木の伝播で締まった境界から幅の小さい列が増え、
  容量の行が緩む。小さい余裕にする試作では破れが消える (下の表)。
- **返す解そのものは今は正しい**: 最後の後処理で元の問題での実行可能性を確かめ、破れていれば整数列を固定した LP で直す
  (`ENOMOTO_MIP_POSTSOLVE_REPAIR`、今は既定で使う)。直した値はどの回も HiGHS の最適値より上 (560 秒の既定の回: 木の値 11507.40374 →
  直して 11507.40565 → もう 1 段直して 11507.40644)。
- **ただし誤答の芽ではある** (推測を含む): 木は実際の最適値より小さい値 (11507.40374) を打ち切りに使うので、本当の最適解を含む
  ノードを刈りうる。木が閉じれば「最適」と答え、値は直した後の値になる。この回なら 11507.40644 を「最適」と答え、本当の最適値
  11507.40506 との差は 1.4e-3 (相対 1.2e-7)。相対ギャップ 0 の約束は破るが、差は相対 1e-6 より小さい。修復の LP が解けなければ前処理なしの
  解き直しになり、時間が足りないと前の段の悪い解に戻る (analysis/uccase12_20261023.md の §4、REPAIR が既定になる前の 11507.90)。
- 試作 `ENOMOTO_MIP_MEM3_TINY_MARGIN=1` (余裕を `1e-9·(1+min(|b|,1)) + 4ε|b|` にする): uccase12 では暫定解が全部元の問題で実行可能
  (最大の違反 6.2e-7)、後処理の修復は一度も要らず、560 秒で 11507.40611 (HiGHS の最適値より上、木の値と返す値が同じ)。

## 1. 何を入れて測ったか

- 一時の診断 `ENOMOTO_MIP_MEM3_DEBUG_INC` (src/mip/mod.rs `mem3_debug_inc`、src/mip/solver.rs `try_incumbent`): 木の求解 (サブ MIP でない) が
  暫定解を受け取るたびに、入れ子の各段 (最初の求解・再スタートの後の求解) の後処理の手順と尺度で内側から順に戻し、各段の前処理前の
  問題での最大の違反・その場所・1e-6 を越える行・列の数・目的値を出す (`MEM3_INC` の行)。値がファイル名の接頭辞なら元の問題の解を書く。
  `fix_tiny_width_columns` は緩めた行の数・ずれた分の最大・余裕の最大を出す (`MEM3_TINY` の行)。どちらも環境変数がなければ何もしない。
- 回し方: `analysis/uccase12_mem3_20261103/run.sh 出力 時間の上限 [環境変数=値]` (`--worker-ours`、`ENOMOTO_MIP_LOG=1`・
  `ENOMOTO_MIP_DEBUG_POSTSOLVE=1`)。long_b (600 秒) と同じ前処理にするため、LP による固定の期限を 30 秒にそろえる
  (`ENOMOTO_T_MIP_LP_PROBE_TIME_FRAC=30/時間の上限`)。最初の回 (`def300_a`) だけはそろえておらず、根の LP に基底がなく 29.5 秒かかった。

  強分枝 1 回に約 5 秒かかっている。理由は調べていない。そのため OOM の前に止まり、メモリは問題にならなかった。

## 3. どの段で生じるか

- 各段の確かめ (`MEM3_INC` の段ごとの行) では、再スタート 2 回目の後の解は「再スタート 2 回目の前処理の前の問題」で既に 5.8e-6〜1.1e-5
  だけ行を破り (右辺 5340・5540 などの 60〜66 項の行。is_feasible の許容誤差は 1e-6 + 1e-9|b| ≈ 6.3e-6 なので 1.1e-5 のときだけ実行不能)、
  その 1 段外 (再スタート 1 回目の前処理の前の問題) では列の下限を 1.1e-5 破る。再スタート 1 回目の後の解は 1 段で 5.5〜6.3e-6。
  つまり **各再スタートの前処理が約 5.5e-6 ずつ緩め、2 回で 1.1e-5、緩んだ行が組み合わさると 2.2e-5** になる。
- 木の問題に緩んだ右辺が見える: 例 `[-inf, 5590.000005674333]` = 5590 + 1e-9·(1+5590) (= 5.591e-6) + ずれた分 8.3e-8。
  `[-inf, 5880.000006031]` も同じ形 (5.881e-6 + 1.5e-7)。
- `MEM3_TINY` (緩めの量、既定の 560 秒の回):

| 前処理 | 固定した列 | 緩めた行 | ずれた分の最大 | 余裕の最大 |
|---|---:|---:|---:|---:|
| 最初 | 131 | 289 | 5.0e-9 | 2.0e-9 |
| 再スタート 1 回目の後 | 174 (+16) | 465 (+46) | 1.0e-6 | **5.4e-6** |
| 再スタート 2 回目の後 | 55 | 214 | 3.0e-7 | **5.9e-6** |
| (サブ MIP の前処理、参考) | 10〜79 | 70〜460 | 8.8e-7 | 5.9e-6〜**1.4e-3** |

  MARGIN の回では余裕の最大はどこでも 2.0〜3.3e-9 (サブ MIP も)。
- 再スタートの関数 (`solver.rs` の再スタートで新しい問題を作る所) が呼ぶ `fix_tiny_width_columns` は、この回では 1 列も固定していない
  (`MIP: restart: fixed … columns` が出ない)。緩めているのは前処理の中のプロービング (`MIP: probing: fixed N columns of width within tolerance`)。

同じことを見ている。10-23 は「代入で消した連続列 74〜106 本が下限 0 を −5e-6〜−1.2e-5 下回る、行の破れ 0 本、各行の許容誤差 1e-6 が

## 4. 試作 `ENOMOTO_MIP_MEM3_TINY_MARGIN`

- `fix_tiny_width_columns` の丸めの余裕を `1e-9·(1+|b|)` から `1e-9·(1+min(|b|,1)) + 4ε|b|` (ε は f64 の機械イプシロン) にする。
  余裕の元の目的 (右辺 1 − 2e-9 の整数の行を緩めた後の正規化 `floor(b + 1e-9)` が 0 に落ちないこと、fuzz_tiny の seed 21) は |b| ≤ 1 では
  今までと同じ量なので保つ。|b| が大きい行の floor(b + 1e-9) は b の丸めの誤差 (4ε|b|) より余裕が大きければよい。
- 等式の行は緩めない代わりに、ずれの予算を 1e-9·(1+|b|) にしている (右辺 5590 なら 5.6e-6 まで行を破る固定を許す)。試作はここを
  変えていない。uccase12 では効いていない (MARGIN の回の違反 ≤ 6.2e-7)。
- 確かめ: `cargo test --release --lib` 333 件通過 (18 件は ignored)。`benchmarks/equiv2_bug_20261022/fuzz_tiny.py 400 0` は既定・MARGIN とも
  13/400 で食い違い、食い違う seed も同じ (下の「別件」)。uccase12 は上の表のとおり 290 秒・560 秒で 1 回ずつ。40 問 + 16 問の計測はしていない。

## 5. 気づいたこと・提案

1. MARGIN は既定の候補。効くのは右辺の大きい行を持ち、再スタートする問題だけのはずなので、40 問 + 16 問の 60 秒 2 回と、
   uccase12 などの長い時間で確かめる。
2. 後処理の修復 (`ENOMOTO_MIP_POSTSOLVE_REPAIR`) は下界を `z_修復後 − z_木` だけ上げる (`r.best_bound += z_orig - prob.objective(&xr)`)。
   この差は前処理の目的値の定数のずれではなく修復で目的値が上がった分なので、下界を上げる根拠はない (推測ではなく式の読み)。
   今回の回では下界 11507.370 と最適値の間が広く害はないが、木が閉じかけているときは下界が最適値を越えうる。下界のずれは
   後処理した (直す前の) 解で測る `p.objective(x) − prob.objective(xr)` を使う方が正しい。
3. is_feasible の許容誤差 1e-6 + 1e-9|b| は、右辺 5000 の行で 6e-6 の破れを通す。各段の後処理の確かめはこれで通り、最後に右辺 0 の
   列の下限で初めて見つかる。段の間の確かめを絶対 1e-6 にする案もあるが、前処理の他の手順の丸めとの兼ね合いは調べていない。
4. 別件 (未調査): `fuzz_tiny.py 400 0` が既定で 13/400 食い違う (seed 61・81・139・148・159・195・201・210・246・260 ほか)。
   `benchmarks/equiv2_bug_20261022/fuzz_summary.txt` では当時の既定が 300 問で 0 だった。ENOMOTO の解の違反は 2e-9 以下で、ENOMOTO の方が
   悪い値で「最適」と答える seed (61: −25.36 対 HiGHS −26.50、195: −14.02 対 −20.53) と良い値の seed (81: −37.53 対 −30.36) がある。
   許容誤差の境目の問題 (右辺 1 − 2e-9 の行、幅 1e-9 の列) だが、いつから食い違うようになったかは見ていない (`fz_check.py` で seed ごとの違反を出せる)。
