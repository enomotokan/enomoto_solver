# DRCRTU: DRCR の整数の組の TU の判定にネットワーク行列の一般の判定を入れる (2026-11-11〜12)

bench に使う環境変数: `ENOMOTO_MIP_FOLD` (既定 `riq`)。この記録で足した値の文字 `n` (試作、既定では使わない): 整数の組の TU の判定に、
ネットワーク行列 (とその転置) の一般の判定を 2 周目で足す。`ENOMOTO_T_FOLD_NET_WORK` (2 周目の仕事量の上限の倍率、既定 0.25。
上限 = 元の非零 × 倍率 + 200 万)、`ENOMOTO_T_FOLD_NET_MAX` (1 成分の非零の上限、既定 200 万)、診断 `ENOMOTO_T_FOLD_TUDUMP=<ディレクトリ>`
(TU に落ちた行列を書き出す)。計測の設定の名前 (`drcrtu_20261111/run.py`・`run_shard.py`): `def` (既定 = `riq`)、`net` (`rinq`)。

## 結論

- 今の判定 (剥がし + Heller-Tompkins の 2 色塗り) で TU に落ちて 1 列ずつに分けた組があるのは、MIPLIB 2017 benchmark 240 問のうち 28 問
  (外した理由は全部 TU。V_R の行が残る・±1 でない係数での外しは 0)。Mittelmann の HiGHS に負ける 47 問では 4 問 (cod105・widden・
  neos-933966・physiciansched6-2)。
- MATREC (van der Hulst、github の rolfvdhulst/matrec、MIT) の「列の追加」(Bixby-Wagner の SPQR 木) を `src/mip/network.rs` に移し、
  分解から組み立てたグラフで全部の列を確かめる証明書の検査を通ったときだけ TU と認める形で入れた。
- 列が縮むのは 3 問: **neos-4722843-widden は列 77723 → 63136 (今) が 77723 → 7300 に**、decomp2 7680 → 7650、physiciansched6-2
  69925 → 69787。ほかの 25 問は認める組が増えても畳まない (縮みが 95% の規則を越えない)。
- widden (600 秒・4 スレッド): 既定は種 1 で時間切れ (暫定解 25629、下界 12157)・種 2 で 476.9 秒、`net` は 45.3・42.7 秒で最適。decomp2・physiciansched6-2 (60 秒、種 1〜3) は
  揺れの範囲 (下の表)。
- 害: 畳めない問題の上乗せは最大 +1.2 秒 (square47 18.6 → 19.8 秒の数えの時間)、28 問の合計 55.7 → 51 秒台 (下の表)。2 周目方式なので
  1 周目は今と同じで、認める組は今の判定の上位集合。58 問で畳み方が変わるのは physiciansched6-2 だけ。
- 誤答: 0 (fuzz_net 2000 問 × 3 設定・fuzz_fold 2000・fuzz_tiny 400・mip_fuzz_vs_highs 300、安全網 0)。新しい判定の道を狙った fuzz_net で
  畳んだ問題 841 → 1344 (`ri` → `rin`)、戻した解は全部整数。cargo test 404 通過。
- 既定にするか: 58 問 × 種 1〜3 の対の計測 (6 分担、`shards.md`) の結果待ち。58 問で動きが変わるのは 1 問なので、基準 (SGM の区間・解けた数・
  揃った遅れ) は満たす見込み (推測)。

## 実装 (段階 2)

- `src/mip/network.rs`: MATREC の src/Network.c の列の追加 (`MATRECNetworkColumnAdditionCheck`・`Add` と、その下の SPQR 木の操作) を関数ごとに
  そのまま Rust に移した (約 1900 行)。C の `assert` だけで守っていた所 (剛の部分の道に始点・終点が無い) は偽にした。
- 証明書の検査 (`verify`): 列を全部足した後、分解の各部分 (直列 = 輪、並列 = 2 節点、剛 = 分解の節点) を組み立て、印の対で 2-和として
  両端を同一視したグラフを作る。行の弧が森になり、どの列も「両端を結ぶ木の道の弧 = 列の非零の行」で、符号が行・列の ±1 倍を除いて道の
  向きと一致する (2 色塗り) ときだけ真。2-和の貼り合わせの向きや直列の並びは閉路マトロイドを変えないので、MATREC の向きの情報に頼らない。
  Camion の定理 (TU な符号づけは行・列の ±1 倍を除いて一つ) で、ネットワーク行列ならこの検査は必ず通る。移植の誤りで添字が外れるなど
  panic したら `catch_unwind` で偽。数えた 28 問と fuzz で panic・検査の外れは 0。
- `tu::tu_cols_f64_net`: 2 色塗りの判定で分からなければ、剥がしの後の芯の連結成分ごとに「ネットワーク行列か、その転置か」を確かめる。
- `fold.rs` (`n`): 1 周目は今まで通り (2 色塗りの判定、組の大きい順)。1 周目で外れた組を同じ順に 2 周目で、触れる成分 + 組の行列を
  ネットワークの判定で確かめ直す。初めは 1 周目から一般の判定を使ったが、早く認めた組の成分が 2 色塗りで分からなくなり、後の組が
  まとめて外れた (s100 6289 → 1038 組、square41 920 → 664)。2 周目方式では認める組は今の上位集合。
- 仕事量の上限: 2 周目でネットワークの判定に渡す非零の合計 ≤ 元の非零 × 0.25 + 200 万 (決定的)。超えたら残りの組は試す行列も作らずに外す。
  上限なしでは畳めない問題で大きな成分を組ごとに確かめ直す手間が大きかった (chromaticindex1024-7 0.5 → 284 秒、s100 1.7 → 438 秒、
  `count_rin_nobudget.jsonl`)。20 倍・2 倍でも square47 で 41 秒・35 秒 (`count_rin_work20.jsonl`・`count_rin_2pass_w2.jsonl`)。当たる 3 問の仕事は
  widden 100 万・decomp2 400・physiciansched6-2 1500 で、上限に届かない。
- 単体テスト (`mip::network::tests`): 乱数の木と道で作ったネットワーク行列 3000 個 (行 60・列 120 まで) を MATREC も証明書も全部受理、
  符号を 1 つ変える・非零を足す/消すで摂動した 4000 個で「判定が真なら総当たり (全部の正方の部分行列の行列式) でも TU」と「MATREC の答えと
  証明書の検査が一致」、奇数の穴・区間行列・接続行列・R10 (TU だがネットワーク行列でも転置でもない → 偽)。
