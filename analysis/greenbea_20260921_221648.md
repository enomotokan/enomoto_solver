## 0. 結論(要約)

1. **申し送り(`loop_state.json` の `note_manual_reset` / `report/greenbea_20260921_213412.md`)の前提「polish_with_true_bounds は同型のフリップ非巻き戻しバグを持ち、それが誤答の原因」は、構造の半分は正しいが機序の説明としては誤り。** 構造: polish は確かに BFRT フリップを `nb_status` に確定(`extended_dual.rs:4026-4032`)してから `update_verify`(`:4059`)を行い、破棄時に巻き戻さない(§2)。しかし greenbea で実際に起きた破棄(polish iter 46)は **フリップ 0 本**(`n_flips=0`)で、巻き戻す対象が存在しない(§3.2)。プロトタイプ `UNFLIP` 単独の効果はゼロで、巻き戻しは今回の誤答に一切関与しない。
2. **実際の機序(§3、計装 `POLISH_PIVOT`/`POLISH_CANDS`/`POLISH_DISCARD`/`POLISH_TINY_COMMIT` で直接観測)**: polish iter 46 で chuzr が行 1811(偏差 4.86e5)を選ぶ。候補列 2338 は `d_j=-5.2e-7`(摂動コストで僅かに双対不能、`hat_c=max(σd,0)=0` で ratio 0)、`a_p[2338] = -1.8626e-9 = -2^-29`(PRICE の打ち消し残差; 同一 LU の FTRAN では `6.4e-16`、再分解直後は**正確に 0.0**)、幅 ∞。絶対許容 `TOL=1e-9`(`simplex.rs:139`)をわずかに超えるので候補になり、**幅 ∞ なので BFRT の歩行が k_star=0 で即停止**(`:3941-3944`)、Harris 窓(ratio 0 ± 1e-7)には他候補が無く(`n_ratio0=1`)、そのまま q=2338 が選ばれる。次候補 j=3180(ratio 2.5e-2、|alpha| 1.84、幅 ∞)は正常なピボットだが届かない。iter 46 は `update_count=46` なので verify が破棄(`:4059`)→再分解。**iter 47: 同じ行・同じ列が再選択され、`update_count()==0` で verify が飛び(`:4059` の `lu.update_count() > 0`)、`alpha_full[r]=0.0` のまま確定**(`theta = 4.86e5 / 1.86e-9 ≈ 2.6e14`)。x_B が発散(iter 48 の偏差 7.6e20、|alpha| 最大 4e18)、iter 49 で FT 更新拒否 → `refactorize` が `None`(`:4153`、特異基底)→ `solve_lp_dual_extended` が `None` → `simplex.rs:3038-3076` の BIG_M フォールバックが **`optimal` として -72465273.017(相対誤差 1.24e-3)を返す**。
3. **主ループとの構造差(§2.3)**: 主ループは同じ事象に対し (a) 破棄した `(q, r)` を行単位で禁止する `discard_row`/`discard_banned_cols`(`:2466-2468`, `:2991-3001`, `:3068-3071`)、(b) `update_count` に依らない `pivot_grossly_inconsistent`(`:2977-2980`)、(c) PR #13 で追加した破棄行の再 verify、を持つ。**polish には (a)(b)(c) のどれも無い**。これが「同じ関数に同じバグ」ではなく「同じ穴に対する防御が polish 側だけ未移植」という実態。
4. **プロトタイプ(§4)**: P2「禁止リストのみ」で greenbea は polish 593 反復・破棄 5 回(全て列 2338、5 行で別々に発生)・正答 **-72555248.12984587(HiGHS と全桁一致)**。P1「主ループ完全ミラー(巻き戻し + 粗不一致 + 再 verify + 禁止)」も P2 とビット同一。P3「粗不一致 + 再 verify、禁止なし」は **同じ (2338, 1811) を 65,153 回破棄し続けて 600 s 超で強制終了**(禁止リストが必要条件であることの実証)。P4「polish の chuzc に |alpha| ≥ `FT_MIN_PIVOT`(1e-7) の候補下限」は破棄 0・再分解 1 で正答(相対誤差 8e-14)。
5. **時間(§5、直列・無負荷・各 2 回)**: main 10.71 / 11.14 s、PR #13 + P1 10.75 / 10.94 s、PR #13 + P4 10.53 / 11.33 s、HiGHS 0.18-0.26 s(2,524 反復)。**主ループの反復数は PR #13 で 27,653 → 27,440(-0.8%)しか変わらず、合計時間はノイズ内で同じ**。反復#13 分析が「事故の直接・間接コスト ≈ 9 s(65%)」と見積もった分は、修正を当てても回収されない(§8 に食い違いとして記録)。**結合修正の価値は正答性・頑健性であり、runtime 段の改善基準(ours/highs 比の有意な改善)は満たさない。**
6. **93 問題全数(§5.2、計装ビルド)**: main 経路では polish で破棄・極小ピボット確定・再分解が起きる問題は **0 / 93**(polish が 1 反復でも回るのは dfl001 と greenbea の 2 問題のみ)。PR #13 + P1 では 93/93 で status・目的値が main と一致(相対差 ≤ 1e-6、実際は greenbea 以外ビット同一相当)。主ループ反復数が変わったのは greenbea と wood1p(251 → 332、main 自身の既知の非決定性、§5.2)のみ。**PR #13 の主ループ修正 + polish への禁止リスト移植(+ 対称性のための巻き戻し・粗不一致・再 verify)は、公式 93 問題ベンチマークに安全にかけられる**。
7. **原因分類: 正当性バグ(correctness bug)**。ただし「フリップ非巻き戻し」ではなく「数値的にゼロのピボットを候補化 → 破棄後の無検証再試行 → 特異基底 → BIG_M フォールバックが誤答を optimal として返す」という連鎖。退化・サイクリングでも初期基底でもない。極小ピボットの発生源(打ち消し残差)は悪条件性の兆候だが、HiGHS も同じ 1e-9 絶対許容で候補化する(§6)ので、区別要因は選択後の防御の有無。

HiGHS が同じ失敗を踏まない理由(確認できた範囲): (1) `chooseFinalLargeAlpha` の相対下限が 2^-29 級の残差ピボットを選択段階で弾く、(2) 万一特異基底になっても INVERT が階数落ちを修復して続行する。「フリップ確定が verify より前」「再分解直後の無検証」は HiGHS も同じであり、それ自体は差の原因ではない。

## 7. 原因分類と修正仕様

### 7.1 分類

**正当性バグ(correctness bug)**。証拠: (i) 確定されたピボットの真値が 0(FTRAN 0.0)であり、数学的に無効な基底交換(§3.2 iter 47)、(ii) 同じ入力で防御(禁止リスト)を足すだけで正答に戻り、経路の運不運ではない(P1/P2)、(iii) BIG_M フォールバックが `optimal` を返す設計(反復#6 以来の未着手リスク)が、内部バイアウトを誤答に変換した。悪条件性は残差ピボットの発生源として関与するが、HiGHS も同じ 1e-9 で候補化する以上、区別要因ではない。退化・サイクリング(P3 の無限破棄は防御の欠落による人工的ループ)、初期基底、ピボット選択効率、いずれも該当しない。

### 7.2 `polish_with_true_bounds` への修正仕様(主ループのミラー、優先順)

すべて `src/simplex/extended_dual.rs::polish_with_true_bounds` 内に閉じる。データ構造追加なし(`Option<usize>` と `Vec<usize>` の 2 変数)。

1. **[必須] 破棄候補の行単位禁止(主ループ `:2466-2468`, `:2991-3001`, `:3068-3071` の移植)**: 関数冒頭で `let mut discard_row: Option<usize> = None; let mut discard_banned_cols: Vec<usize> = Vec::new();`。chuzc(`:3885`)の先頭で `if discard_row == Some(r) && discard_banned_cols.contains(&j) { continue; }`。破棄分岐(`:4059` 内、`refactorize` の前)で主ループと同じ push/clear。ピボット確定後(`:4110` の後)で `if discard_row == Some(r) { discard_row = None; discard_banned_cols.clear(); }`。**greenbea はこれだけで正答**(P2)。
2. **[必須(1 とセット)] `pivot_grossly_inconsistent`(主ループ `:2977-2981` の移植)**: `let scale = alpha_q.abs().max(alpha_full[r].abs()).max(1e-300); (alpha_q - alpha_full[r]).abs() / scale > D_GROSS_MISMATCH_REL_TOL` を破棄条件に OR。iter 47 型(相対差 1.0)を `update_count` に依らず捕まえる。**1 なしで入れると無限破棄(P3)**。
3. **[推奨(1 とセット)] 破棄行の再 verify(PR #13 の `should_verify_pivot` の移植)**: `let should_verify = !update_verify_disabled && (lu.update_count() > 0 || discard_row == Some(r));`。同上、1 なしでは無限破棄。
4. **[対称性のため推奨、効果は latent] 破棄時のフリップ巻き戻し(PR #13 の移植)**: 破棄分岐で `for cand in &candidates[..best_idx] { nb_status[cand.j] = 反転 }` を `refactorize`/`compute_rhs_plain` より前に。x_B は直後の `compute_rhs_plain(std, nb_status)` が復元後の `nb_status` から再計算するので追加処理不要(主ループと同じ理由)。greenbea では破棄 5 回とも `n_flips=0`、93 問題で polish の破棄自体が 0 件なので、現時点で経路を変える問題は無い。`:4054-4058` のコメントは主ループ側と同様に書き換える。
5. **[任意] 候補下限 `|alpha_j| < FT_MIN_PIVOT` の除外(P4)**: 破棄自体を消すが、主ループの構造とは対応しない独自変更。入れるなら `candidates.is_empty()` → `Infeasible`(`:3920`)側に「除外した候補が存在した場合は Infeasible と結論しない」ガードが要る。93 問題で極小確定 0 件なので必要性は低い。
6. **極小 M ピボットガード(`BFRT_M_PIVOT_FLOOR`)は移植しない**: polish に M 側・`x_b_slope`・`cache.width` の slope が存在せず、ガードの発火条件(`w_r.slope != 0`)も snap 対象(`x_b_slope[r]`)も無い。greenbea の失敗候補は幅 ∞ の列で、失敗点は「破棄後の無検証再試行」であり、主ループのガードが対処した「雑音 slope を埋めるための極小 M 幅候補」とは別の事象。**構造的に非対称で、対称性を装って移植すると意味の無いコードになる**。

効果見積もり: 正答性のみ。greenbea の時間は main と同等(§5.1)。93 問題への影響は polish 側ゼロ、主ループ側は PR #13 と同一。

### 7.3 反復#13 の主ループ修正との結合可否

**可**。根拠: (a) fix + P1 で 93/93 の status・目的値が main と一致(§5.2)、(b) polish の変更は main 経路の全問題で no-op、(c) greenbea は誤答 → 正答。ただし採用理由を「runtime 改善」に置くことはできない(§5.1)。採用するなら「反復#13 で検証済みの主ループの双対実行可能性バグ修正を、polish 側の欠落防御を補って正答性を保ったまま取り込む」という正答性・頑健性の変更として扱うのが実態に即す。

### 7.4 スコープ外だが記録する残リスク

- `simplex.rs:3038-3076`: 内部バイアウト(`None`)→ BIG_M フォールバックが `optimal` を返す。本反復でも PR #13 単体・P3 がこの経路で誤答/長時間化。反復#6 以来未着手。
- `finish` の cleanup ピボット選択 `(0..n_rows).find(|&i| alpha_col[i].abs() > TOL)`(`:3531`)は「最初に 1e-9 を超えた行」で、最大ピボットではない。greenbea は cleanup 0 回なので無関係だが、同じ極小ピボットのリスク類。
- `hat_c = max(σd, 0)`(`:3899`)が僅かな双対不能列(列 2338、5.2e-7)を ratio 0 に丸めるため、その列に残差が乗るたび先頭候補になる。polish は最大 5 回の破棄で済んだが、`discard_row` は行単位なので別の行で毎回 1 回ずつ再分解を払う。

## 8. 想定との食い違い(そのまま報告)

- **依頼文・申し送りの「polish も同型のフリップ非巻き戻しバグで、同じ巻き戻し + 粗ピボットガードのセットで直る」は、機序として外れていた。** 構造(フリップ → verify → 破棄、巻き戻しなし)は確かに同型だが、greenbea の破棄はフリップ 0 本で起き、巻き戻しは何も変えない。直したのは主ループが以前から持っていた禁止リストの移植で、PR #13 が新規に追加した 4 点のどれでもない。極小 M ピボットガードは polish に対応構造が無い。
- **反復#13 分析の「事故コスト ≈ 9 s(65%)」は、修正で回収されなかった。** 主ループ反復数 27,653 → 27,440。反復#13 §4 が「UNFLIP 単独で 27,441 反復、M 側解消が遅くなる」と自ら記録した通りで、`parallelcols` 無効の 11,270 反復は別経路の値であって修正後の経路の値ではない。結合修正を runtime 改善として採用する根拠は本セッションの計測からは出ない。
- 反復#13 報告の「verify 不一致 → 続く refactorize が None」は 1 反復ずれ(§2.2)。None は 3 反復後の FT 拒否側。
- HiGHS が `update_count > 0` で verify を飛ばすこと、候補化の絶対許容が再分解直後 1e-9 であることは、本ソルバと同じだった(「HiGHS は毎反復 verify する」と想定していたが誤り)。差は選択後の相対下限と階数落ち修復。
- wood1p の主ループ反復数差(251 → 332)は PR #13 とは無関係の既存非決定性: **リポジトリの `.so` そのものを連続 2 回走らせて 251 と 332**(目的値 1.4429024115725584 / 1.4429024115734097)、base 計装ビルド 3 回は全て 332。同一バイナリで揺れるので PR #13 の影響ではない(§5.2)。
