# HOTSPOT: 1 スレッドの処理の効率の洗い出し (2026-11-22〜23、利用者の方針「計算機の性能を極限まで引き出す」の一部)

コードは変えていない (計測の台本と、ビルドの指定の比べだけ)。

## 0. 結論と、どこから手を入れるか (得の見積りは推測を含む)

1. **ビルドの対象 CPU を指定する (`-C target-cpu=x86-64-v3` 相当)。手間が最も小さく、確かめた得がある。**
   - 今は対象 CPU の指定がなく、x86-64 の基本 (SSE2) でビルドされる。`f64::floor` が命令 1 つ (roundsd) にならず、compiler-builtins の
     ソフトウェアの floor を呼ぶ。自身の時間で h80x6320d 5.4%・pk1 2.5%・mas76 1.8%。cachegrind では mas76 の条件分岐の予測失敗の 11.8% が floor。
   - v3 で同じ 1 スレッドの問題を解くと、**ノードは全問で同じ** (道筋は変わらない) で、時間は h80x6320d −7%・pk1 −5%・mas76 −4%・neos-911970 −3%・
     noswot −2%、60 秒の時間切れの supportcase26 はノード +8〜10% (§4)。
   - 配る wheel は基本の CPU 向けのままが要るので、計測・手元のビルドで指定するか、熱い関数 (cmir の丸めなど) だけ `#[target_feature]` と
     実行時の判定で切り替える形。
2. **双対証明の差分の更新 (mas76 42%・pk1 33%・noswot 8%・timtab1 7%)。** 証明の集まりが上限の 2000 本で、列が少なく (mas76 151 列) 証明が
   ほぼ全部の列にかかるので、境界が 1 本動くたびに約 2000 本の差分を足す。mas76: 12.2 万ノードで評価 4.5 億回 (1 ノード 3700)・差分の更新 14.3 億回
   (1 ノード 1.18 万)・枝刈り 6.0 万回 (評価の 0.013%)。pk1 も同じ形 (評価 6.1 億・更新 14.2 億・枝刈り 6.8 万)。
   - 案: 効かない証明を減らす (枝刈り・締めに使われない証明の年齢で外す)、本数でなく非零の総数で上限を持つ、密な証明を差分の更新から外して
     必要なときだけ全計算する。差分の手間は本数に比例なので、本数を半分にすれば mas76・pk1 で 15〜20% (枝刈りの力が落ちなければ。要計測)。
3. **伝播 (supportcase26 59%、mzzv42z 15%、pk1 12%)。** `Domain::propagate`・`update_activity`・`propose_lower` とカットプールの伝播。
   supportcase26 は木のノードの大半が伝播。活動量の差分の更新の並び (行ごとの Vec の散らばり) と、締まらない行を何度も見ていないかを次に見る。
4. **根のカットのループ (5 問の根だけ、§3)。** ループは根の 39〜74%、その中で分離が 60〜80% (行 1 本ずつ・集約の cmir の `generate_cuts` 24〜37%、
   経路の集約 7〜38%)。LP の解き直しは 5〜21% (p200x1188c だけ 41%)、カットの選び (平行度・点数) は 1〜4%、プールの管理 1〜3%、伝播 1% 未満。
   分離の中の熱い所は `cmir_terms` (δ の候補ごとの丸め、floor) で、1. の v3 がそのまま効く。分離を並列にしても縮みが小さかったのは、
   1 回の分離が多数の小さな `generate_cuts` (1 行・1 集約ごと) の積み重ねで、LP の解き直しと選びは逐次のままのため (推測)。
5. **LU・単体法 (LP の重い問題で 20〜55%)。** `FtLu::pair_r_u_permute(_tracked)`・`permute_out` (FTRAN の R・U 段と置換) が 3〜9%。
   すでに超疎・部分 tau などの手当てがあり、HiGHS との比べの専任の作業 (fable-bottleneck-analyst) の領分。ここでは数字だけ。
6. **メモリ確保 3〜6%。** `_mi_page_malloc_zero` (0 で埋めた確保、`vec![0; n]` に当たる) が 1〜2%。熱い経路 (分離の作業域・行の活動量の
   `row_activities_ref` の毎回の Vec) で作業域を使い回すと 1〜3% (推測)。

## 1. 道具とビルド

- perf: `apt-get install linux-tools-common linux-tools-generic` で入り、`/usr/lib/linux-tools-6.8.0-151/perf` を使った (カーネル 6.18 向けの
  パッケージはないが動く)。**この VM ではハードウェアのカウンタ (cycles・instructions・cache-misses・branch-misses) が `<not supported>`** で、
  perf stat の IPC などは取れない。perf record は cpu-clock の抽出で動く。
- キャッシュと分岐は valgrind 3 の cachegrind (`--cache-sim=yes --branch-sim=yes`) で模擬した (§5)。
- Rust の v0 の記号名は perf では戻らない (`rustfilt` は入れられなかった) ので、`dem.py` で記号の中の識別子から「型::関数」を取り出した (近似)。
- ビルド: 抽出のための wheel は `CARGO_PROFILE_RELEASE_DEBUG=line-tables-only RUSTFLAGS="-C force-frame-pointers=yes" maturin build --release`
  (行番号表とフレームポインタ。コードは変えない。フレームポインタの分だけ数 % 遅い)。ブランチ e22e59b8c。
- 台本: `prof.sh` (1 スレッド・種 1・60 秒の perf record と自身/子を含む上位、`out/<問題>.self.txt`・`children.txt`)、`cat.py` (段ごと、`cats.md`)、
  `rootprof.sh`・`rootloop.py`・`sepbreak.py` (根だけ・根のカットのループの内訳、`out/<問題>.root.txt`)、`cpu.py` (対象 CPU の比べ、`cpu.jsonl`)。
  perf.data は /tmp に置き、コミットしない。

## 5. キャッシュと分岐 (cachegrind、mas76、1 スレッド、ノード 3000 で止め、Python の起動を含む)
