# 根のカットのループの分離の時間の内訳と速くする試作 (2026-10-23)

- 機械: 4 CPU (専用コンテナ)。ソルバーは同時に 1 つだけ動かした (ビルドは計測の合間。prof2 の 30n20b8 以降の 1 本だけ、テストのビルドと重なった)。
- コミット: ブランチ `inv/sepspeed-20261023` (develop `c827553` から)。highspy 1.15.1。HiGHS 1.15.1 をソースからビルドし、
  前回の計装 (`analysis/cutloop_hl_20261022/highs_instrument_cutloop.patch`) に、分離のラウンドごとの段階の時間 `HSEPT` を足した
  (`sepspeed_20261023/highs_septime.patch` = HighsSeparation.cpp の差分全体)。
- 「1 スレッド・根だけ」は ENOMOTO `ENOMOTO_MIP_THREADS=1`・`NODE_LIMIT=1`・`ENOMOTO_MIP_NO_BG_CUTS=1`、HiGHS `threads=1`・`mip_max_nodes=1`
  (前処理はどちらも既定のまま)。数字は根の最初のカットのループ (再スタート前) のラウンドあたりの平均。
- ENOMOTO は 1 スレッドでも回ごとに経過が変わる (同じ設定で roll3000 の根 12351〜12391 など) ので、1 回ずつの比較の下界の差は誤差を含む。
- 台本・ログは `analysis/sepspeed_20261023/` (§6)。

## 1. 結論

事実:

1. **「分離が HiGHS の 5 倍」は問題によって中身が違う**。同じ段階 (HiGHS の最初の 5 ラウンド / 25 ラウンド) で比べると:
   - roll3000: ENOMOTO 97 ms (develop) に対し HiGHS 26〜33 ms。差の大半は経路集約 (ENOMOTO 63 ms: HiGHS の移植 38 + 従来のもの 24、
     HiGHS 5 ms)。経路集約のカットは選択でほとんど採られない (1 ラウンドに候補 71 本のうち 0.5 本)。
   - mzzv42z: ENOMOTO 450 ms (develop、1 スレッド) に対し HiGHS の最初の 5 ラウンドは **315 ms (tableau 117・clique 114・implied bound 74)**。
     HiGHS の平均 (分離 120 ms) が小さいのは、tableau の分離に通算の予算 (試す行の数の累計 ≤ 5000 + 50 × 呼び出し + LP 反復 / 10) があり、
     数ラウンドで使い切って後のラウンドが軽いため。ENOMOTO の根のループは時間の上限で 4〜5 ラウンドしか回らず、重いラウンドだけになる。
     mzzv42z の 1 ラウンドで重いのはむしろ LP (ENOMOTO 430〜990 ms、HiGHS の最初の 5 ラウンド 90〜210 ms)。
   - 30n20b8: ENOMOTO 262 ms (develop) に対し HiGHS の最初の 25 ラウンドは 80 ms (平均は mod-k が重く 196 ms)。ENOMOTO の差は tableau 行
     (生成 + finish_cut 172 ms、集約行の平均非零 1100、作ったカットの半分を finish_cut が捨てる)。
   - neos-911970: ENOMOTO 59 ms に対し HiGHS 6〜8 ms。ENOMOTO の半分以上は最適面の頂点 (面の LP 2 回 22 ms + 面の頂点での分離 19 ms)。
     ただし面の頂点のカットは選択で採られる側 (1 ラウンドに採る 11.3 本のうち 9.1 本)。
   - physiciansched6-2: ENOMOTO 3.3 秒 (うち **面の LP 2.28 秒、2 回とも時間の上限 1.14 秒に当たって使われない**) に対し HiGHS 0.11〜0.16 秒。
2. **分離の中では generate_cuts (置き換え + CMIR + flow cover) が大半**で、呼び出しの 9 割はカットを作らない (roll3000: 1 ラウンドに 5444 回、
   生のカット 491 本。置き換え 25 ms・CMIR 34 ms・flow cover 18 ms で分離 97 ms のうち 77 ms)。1 回あたりが重かった理由:
   - `substitute` (境界の置き換え) が整数の列の位置を **HashMap** で引いていた (roll3000 で 1 項 60 ns)。
   - `mir_efficacy` が δ ごとに係数の Vec を作っていた。CMIR は δ の候補 (整数の項の係数 ≤ 8 個) とその 1/2・1/4・1/8 の **最大 32 個**を、
     連続の項も含む全ての項で評価する。HiGHS は連続の項の寄与を先に 1 つにまとめて整数の項だけを回し、2・4・8 倍は最良の δ についてだけ試す。
   - flow cover の前処理 (`snf_relaxation`) が呼び出しごとに HashSet を 2 つ作っていた。
3. 結果の変わらない高速化 (既定に入れた、§3.1): 置き換えを密な配列に、`mir_efficacy` の Vec をなくす、`snf_relaxation` の HashSet を密な印に。
   1 スレッド・根だけの分離の時間 (develop → この変更): roll3000 97 → 60 ms、mzzv42z 447 → 322〜355 ms、30n20b8 262 → 180 ms、
   neos-911970 59 → 43 ms (置き換え: roll3000 25 → 6 ms、mzzv42z 136 → 31 ms)。
4. 試作 (既定では使わない、§4):
   - `ENOMOTO_MIP_FACE_ADAPT`: 面の LP の時間の上限を直前のカットの LP の 2 倍 (最初のラウンドは 0.25 秒) にし、解けなければそのループでは
     面の頂点の分離をやめる。physiciansched6-2 の 1 ラウンド 3.1 → 1.2 秒、10teams の根のループ 6.3 → 1.2 秒。
   - `ENOMOTO_MIP_SEP_FAST`: CMIR の効き目の評価を HiGHS と同じ形 (連続の項をまとめる) に。カットは同じ (乱数の行 5000 本で一致を確認、
     δ の同点で定数倍になることだけある)。roll3000 で CMIR 30 → 22 ms。
   - `ENOMOTO_MIP_CMIR_DELTAS_HIGHS`: δ の 1/2・1/4・1/8 を最良の δ にだけ試す。roll3000 の CMIR 22 → 12 ms だが、**mc11 の根の下界が
     11069 → 6302 に落ちる** (§5)。
   - `ENOMOTO_MIP_GEN_FRACSKIP` (整数の項がすべて整数値、または置き換えた行が箱の上で冗長なら CMIR を作らない) と `ENOMOTO_MIP_TAB_BUDGET`
     (HiGHS と同じ tableau の通算の予算) は、今回の問題ではほとんど働かなかった (飛ばせる呼び出しがない / 最初のループの 4〜5 ラウンドでは予算に届かない)。

5. 4 スレッド・60 秒 2 回ずつ (13 問、§5): 解けた回数は既定 14、Q (= SEP_FAST + FACE_ADAPT) 15、P (= Q + CMIR_DELTAS_HIGHS) 16 だが P は mc11 が
   2 回とも解けなくなる。FACE_ADAPT で 10teams が 時間切れ・11.5 秒 → 13.3・4.8 秒 (P は 4.9・4.8 秒)。
6. **既定にする候補**: §3.1 の結果の変わらない高速化 (この枝の既定にもう入っている。develop に取り込んでよい)。`ENOMOTO_MIP_FACE_ADAPT` は候補
   (10teams が速くなり、physiciansched6-2 で面の LP の無駄がなくなる。悪くなった問題は neos-911970 の 21〜24 → 28 秒だけで、根は同じ 47.26)。
   40 問で確かめてから。`ENOMOTO_MIP_CMIR_DELTAS_HIGHS` は不採用 (mc11)。SEP_FAST は効果が小さい (roll3000 の CMIR 30 → 22 ms 程度) ので急がない。

推測:

- roll3000 の経路集約は、HiGHS も同じ手順 (始点は効いている行全部、最大 6 段、各段で集約行と符号を反転したものを試す) なので、呼ぶ回数の差ではなく
  1 回の generate_cuts の重さの差 (上の 2) と、従来の経路集約 (`path_aggregation`) を重ねて回していること (24 ms) による。
- 30n20b8 の tableau 行は密 (平均 1100 非零) で、前回の試作 (`ENOMOTO_MIP_TAB_HIGHS_RULES`・`ENOMOTO_T_MIP_TAB_NNZ_BUDGET`) のとおり絞ると根の下界が
  下がる。ここを速くするには、生成の前に安く「切れない行」を見分ける必要があるが、今回の FRACSKIP の条件ではほぼ見分けられなかった。

## 2. 計り方

- `ENOMOTO_MIP_DEBUG_SEPPROF` (`src/mip/separation.rs` の `sepprof`): 根のカットのループ (裏のループ・サブ MIP を除く) の 1 ラウンドを
  面の準備・面の LP・今の頂点での separate()・面の頂点での separate()・プールへの追加・選択・行の追加・LP・外す、に分け、separate() の中を
  準備・元の行 1 本ずつ・zerohalf・clique・implied bound・経路集約 (HiGHS の移植 / 従来)・tableau (行の選択 / BTRAN + 集約 / 生成 + 仕上げ)・
  finish_cut に分ける。候補には分離器の印 (`Candidate::src`) を付け、分離器ごとの候補と採った本数を数える。`generate_cuts` の中
  (置き換え・CMIR・extended cover・flow cover) は `cuts::GEN_PROF` (呼んだスレッドの分だけ。4 スレッドでは並列の部分が入らない)。
  ループの終わりに `SEPPROF` 行で出す。
- HiGHS: `HSEPT impl clq prop tab path modk poolsel ncut` (分離のラウンドごとの秒)。`hsum.py` が平均を出す (根の後のラウンドも入る。
  同じ段階で比べるため最初の 5 / 25 ラウンドの平均も見た)。

### 3.1 結果の変わらない高速化 (この枝の既定)

- `cuts::substitute`: 整数の列 → 位置の HashMap を、スレッドごとの密な配列 (`SUBST_POS`、使った後に 0 に戻す) に。足す順は同じ。
- `cuts::mir_efficacy`: δ ごとに係数の Vec を作らず、同じ式をその場で計算 (足す順も同じ)。
- `cuts::snf_relaxation`: 行に現れる列・使った 0-1 変数の HashSet 2 つを、スレッドごとの密な印 (`SNF_MARK`) に。
- どれも出力は同じ (浮動小数の計算の順も同じ)。`cargo test --release --lib` 313 件通過。
