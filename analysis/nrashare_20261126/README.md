# 4 スレッドで nra の統計をスレッド間で共有する試作 `ENOMOTO_MIP_NRA_SHARE` (2026-11-26、親の依頼)

analysis/par4_20261126/README.md の候補 4。c2c の 4 スレッドの nra の害 (neos-631710 1.78 倍・neos-911970 1.66 倍) について、
各スレッドが自分の木だけで数える統計 (φ・f、ĝ) を全スレッドの合計で数える形にした。既定ではオフ。

## 0. まとめ

- **食い違いは大きい**。同じ時刻でもスレッドごとの f (外す割合) が 0.01〜0.99 に割れる (1 節)。
- **共有で f はそろう**。neos-911970 の同じ時刻のスレッド間の f の幅は、平均 0.29 → 0.12。
- **それでも害は共有では消えない**。neos-911970 の害を消すのは nra の `p` (φ の補正) で、共有を足しても良くならない。
  neos-631710 の遅れは nra の統計とは関係がない (2 節)。
- 1 スレッドの道筋は変わらない (プールがないので読まない)。cargo test は共有ありで 424 通過。
- **P の 4 スレッドでは中立** (6 節)。r0k23p の上で、共有ありの比 1.003 [0.990, 1.017]、全種 1.25 倍超の遅れなし、食い違い 0。
  解けた数の差 1 (neos5 種 1) は揺れ (同じ設定で回し直すと共有なしも時間切れになる)。
- neos-631710 の 4 スレッドの遅れの元は ENUM_ADAPT の時計の数え違い (7 節)。直しの試作 `ENUM_ADAPT` の `t`。

## 1. 診断: 4 スレッドの nra の統計のスレッドごとの食い違い

`diag.sh` (c2c、4 スレッド・種 1、`ENOMOTO_MIP_NRA_TRACE=500`・ログつき) → `diag_summ.py`。
各求解 (再スタートで区切る) の終わりの、スレッドごとの閉じた葉 [実行不能/下界] と、そこから計算した φ・f。最後の列は全スレッドの合計から計算した値。

| 問題 | 求解 | スレッドごと (φ / f) | 合計の φ / f |
|---|---|---|---|
| neos-631710 | 最後 | t0 0/0 (0.50 / 0.54)、t1 1/0 (0.67 / 0.95)、t2 4/0 (0.83 / 1.00)、t3 2/0 (0.75 / 0.99) | 7/0: 0.89 / 1.00 |
| neos-911970 | 最後 | t0 238/213 (0.53 / 0.65)、t1 227/210 (0.52 / 0.62)、t2 498/175 (0.74 / 0.99)、t3 410/173 (0.70 / 0.97) | 0.64 / 0.93 |
| rococoC10-001000 | 2 回目 | t1 (0.35 / 0.09)、t2 (0.31 / 0.04)、t3 (0.55 / 0.73) | 0.43 / 0.26 |
| rococoC10-001000 | 最後 | φ 0.19〜0.32 / f 0.01〜0.06 | 0.26 / 0.02 |

- `NRA_TRACE` の 4 行ずつの組で見た、同じ時刻のスレッド間の f の幅: neos-911970 は平均 0.29・最大 0.69、rococoC10-001000 は平均 0.42・最大 0.87。
- neos-631710 は、葉がほとんどないうちに f ≈ 1 に張りつく。ラプラスの補正 (1, 1) でも、実行不能の葉 1〜4 枚で φ > 0.49 になる。
  合計で数えても 7/0 で f 1.00 なので、共有では変わらない見込み。
- neos-911970 の最後の求解は、合計でも φ 0.64・f 0.93 (外す側)。共有しても外す側にいる見込み (par4 の見立てと同じ)。

## 2. 試作 `ENOMOTO_MIP_NRA_SHARE` (src/mip/solver.rs `nra_share_on`・`nra_leaf_counts`・`nra_gain_sums`・`pc_gain_add`)

- 木を分け合うプール (`WorkPool`) に、閉じた葉の数の加算器 `nra_sh_leaves` [実行不能, 下界] と、プールのラウンドの伸びの加算器 `nra_sh_gain` [和, 回] を置く。
- `nra_leaf` と `pc_gain` の更新で、自分の数に加えて加算器にも足す。プールがない間 (木を分け合う前) の分は取っておき、後の合計に足す。
- φ (`nra_share`) と、`p`・`g` の ĝ を、全スレッドの合計から計算する。
- プールがなければ (1 スレッド) 今のまま。再スタートの後はプールが新しく作られるので、合計も数え直し (今のスレッドごとの数と同じ)。
- 新しい閾値はない。
- 共有の効き (neos-911970、c2c + 共有、種 1、`logs_neos-911970_c2cs_s1.err`): `NRA_TRACE` の φ は同じ時刻で全スレッドが 0.474〜0.487 にそろい、
  f の幅は平均 0.12・最大 0.27 になった (共有なしは 0.29・0.69)。残る幅は、加算器を読む時刻の違いの分。

## 4. 確かめ

- 1 スレッド (`res1t.jsonl`、種 1、300 秒): 共有の有無で道筋は同じ。
  - neos-631710 は 4 形とも 1300 ノード。neos-911970 は c2cp・c2cps とも 7727 ノード。
  - c2c・c2cs の neos-911970 はどちらも 300 秒で時間切れ。そこまでに処理したノード数 (113685・113018) は速さで変わるので比べられない
    (1 スレッドではプールがなく、共有のコードは読まれない)。
- cargo test (`ENOMOTO_MIP_NRA_SHARE=1`): 424 通過・0 失敗。
- 試作をつけないときは、加算器に足すだけで読まないので、既定・c2c の道筋は変わらない (共有を読むのは `nra_share_on` のときだけ)。

## 6. P の 4 スレッド (58 問 × 種 1〜3、60 秒、1 本ずつ。`p4/`、`p4/summ.txt`)

c2c の nra を r0k23p にした形 (c2cp) と、それに共有を足した形 (c2cps) を、同じビルドで比べた (基準は c2cp、`p4/cfg.py` の `BASE`)。
348 回、crash 0。

| 比べ | 回 | ずらし幾何平均の比 | 95% 区間 | 解けた数 c2cp → c2cps | 全種 1.25 倍超の遅れ | 食い違い |
|---|---:|---:|---|---|---|---|
| c2cps 対 c2cp | 174 | 1.003 | [0.990, 1.017] | 138 → 137 | なし | 0 |

- 問題単位で 1.25 倍を超えたのは neos5 (1.27) だけ。種 1 で、c2cp 26.1 秒 (最適) に対し c2cps が 60 秒で時間切れだった。
- 同じビルドで neos5 の種 1 を 2 回ずつ回し直すと、c2cp は 54.8 秒・**時間切れ**、c2cps は 54.5・43.6 秒 (`p4/neos5_rep_{a,b}.jsonl`)。
  4 スレッドの揺れで、解けた数の差 1 は共有の害ではない。
- 結論: 共有は P で中立。区間の上端 1.017 は目安の 1.05 以下で、仕組みの遅れもない。利用者の方針 (中立なら入れる) に沿えば、入れてよい。

## 7. neos-631710 の 4 スレッドの遅れの原因: ENUM_ADAPT の時計 (親の追加の依頼)

c2c から部品を 1 つずつ抜いた形 (4 スレッド、種 1〜3、300 秒、`res3.jsonl`。幾何平均の秒):
既定 31.0、c2c 48.5、−nra 52.6、**−enum 34.3**、−heur 55.8、−fpls 59.5、−lmip 46.5、−bfrt 58.5、−tie 52.3、−cutu 54.3、−ppi 49.8、−sbpb 47.0。
ENUM_ADAPT を抜いたときだけ、既定並みに戻る。

**仕組み** (`logs_631710_enum_{c2c,noenum,c2ct}.err`、種 1):
- 4 スレッドでは、根の FJ のスレッドが自分で FJ_P3 の前処理 (`presolve_mip`) を回してから FJ・Local-MIP を回す。
- ENUM_ADAPT の時計 (`ENUM_T0`) はスレッドごとの変数で、主のスレッドの求解の始めにしか置かれない。
  FJ のスレッドでは経過が無限大になり、「時計がなければ c = 0 で常に続ける」の規則で、列挙とプロービングの繰り返し・かけ直しが止まらない。
- c2c では FJ_P3 の前処理に 10.1 秒かかって期限を過ぎ (`past the deadline`)、FJ・Local-MIP が 1 手も回らなかった。
- ENUM_ADAPT なしでは FJ_P3 は 2.3 秒で終わり、Local-MIP が 3.35 秒に最適値 203 を見つける。そこから根で 111 列が固定され、根から再スタートする。
  c2c は暫定解 343 のまま根を抜け、木の中のノード 80 (30 秒) まで再スタートしない。
- 1 スレッドでは FJ のスレッドが別にないので、この形では出ない。

**直しの試作 `ENOMOTO_MIP_ENUM_ADAPT` の `t`** (`=1st`、既定オフ): 前処理を回すスレッドに ENUM_ADAPT の時計がなければ、その前処理の始めを時計にし、
前処理の後で元に戻す。新しい閾値はない。最初は FJ_P3 にだけ入れた。

| neos-631710 (4 スレッド、同じビルド、`res631_fix.jsonl`) | 種 1 / 2 / 3 | 幾何平均 |
|---|---|---|
| 既定 | 28.8 / 27.3 / 21.7 | 25.6 |
| c2c | 47.1 / 47.1 / 48.3 | 47.5 |
| c2c + `t` | 32.1 / 39.1 / 36.4 | 35.8 |

- `t` をつけると、FJ_P3 は 3.48 秒で終わり、Local-MIP が 5.09 秒に 203 を見つけ、根で 94 列が固定される。
- 残る差 (約 1.4 倍) は、主のスレッドの前処理の列挙とプロービングの繰り返し (約 2.7 秒、1 スレッドでも出る ENUM_ADAPT の固定費) と、
  FJ のスレッドの列挙の残り (約 1.2 秒) と見る。
- 確かめ: `fuzz.sh enumt ENOMOTO_MIP_ENUM_ADAPT=1st ENOMOTO_MIP_NRA_SHARE=1` (`fuzz_enumt.out`) で、fuzz 7 本は誤答 0、cargo test は 424 通過。

## 8. `t` をどのスレッドの前処理にも広げた形 (親の依頼) と、その計測

**中身** (src/mip/mod.rs `EnumClockGuard`・`presolve_mip`): 時計を置く所を、FJ_P3 から前処理の入口 `presolve_mip` の見張りに移した。
- 時計のないどのスレッドの前処理 (FJ のスレッドの FJ_P3、PRECHAIN・TPRE、並列のサブ MIP など) でも、その前処理の始めを時計にし、抜けるときに元に戻す。
- 主のスレッドと入れ子の呼び出しは、時計があるので何もしない。既定オフ (`ENOMOTO_MIP_ENUM_ADAPT` に `t`)。

**1 スレッドの道筋** (`res_t1check.jsonl`、c2c 対 c2c+t、種 1、120 秒):
- 解けた問題は同じノード数: neos-631710 1300、neos-2987310-joes 0、neos-950242 0。
- 時間切れの net12・mushroom-best・neos-933966 は、処理したノード数が速さで変わるので比べられない。
- mushroom-best は、ログ (`logs_mush_t1_{1s,1st}.err`、60 秒) を比べた。木に入るまでの 221 行が、時刻を除いて全部同じだった。
- 1 スレッドでも別スレッドで前処理を回す所 (根の RENS の続きから解く形など) はあるが、主のスレッドには時計があるので、`t` は主には何もしない。

**VB の 4 スレッドの害の 6 問** (`res_vb6.jsonl`、4 スレッド、種 1〜3、300 秒、1 本ずつ。PAR4=fmr などの既定化を取り込む前のビルドで、3 形を同じビルドで回した。
2 時間の上限で 1 度止まり、同じコマンドで続きを回した)。幾何平均の秒 (時間切れは 300 で数える):

| 問題 | 既定 | c2c | c2c+t |
|---|---|---|---|
| neos-933966 | 106 / TL / 107 (**150**) | TL / 108 / 87 (**141**) | 265 / 102 / 96 (**138**) |
| tbfp-network | TL / TL / 201 (**263**) | TL / TL / TL (**300**) | TL / TL / TL (**300**) |
| gmu-35-40 | TL / 204 / TL (**264**) | TL / TL / TL (**300**) | TL / TL / TL (**300**) |
| **30n20b8** | 236 / 147 / 106 (**154**) | TL / 249 / 248 (**265**) | 210 / 111 / 143 (**149**) |
| mushroom-best | 149 / 170 / 173 (**163**) | TL / 247 / 255 (**266**) | 275 / 291 / 206 (**254**) |
| neos-3627168-kasai | 58 / 58 / 43 (**53**) | 120 / 64 / 100 (**91**) | 91 / 82 / 129 (**99**) |

18 回のずらし幾何平均: 既定 157.0、c2c 209.9、c2c+t 190.9。
- `t` で 30n20b8 の害が消える (265 → 149、既定 154)。
- tbfp-network・gmu-35-40・mushroom-best・kasai の害は残る。`t` の時計の件とは別の部品と見る (mushroom-best は 1 スレッドでも sbpb の害、comboharm 3 節)。

**P の 4 スレッド** (`p4t/`、58 問 × 種 1〜3、60 秒、348 回、crash 0。既定化 (PAR4=fmr・ROOTPAR_CUT・PARIDLE・UNIFY_FIX) を取り込んだ 558a012f2 のビルド。
c2c と c2c+t を同じビルドで比べた。基準は c2c):

| 比べ | 回 | ずらし幾何平均の比 | 95% 区間 | 解けた数 c2c → c2c+t | 全種 1.25 倍超の遅れ | 食い違い |
|---|---:|---:|---|---|---|---|
| c2c+t 対 c2c | 174 | 1.003 | [0.992, 1.013] | 137 → 138 | なし | 0 |

- **中立** (集計の目安は「候補」)。区間の上端 1.013 は目安の 1.05 以下で、解けた数は減らず、仕組みの遅れもない。
- `t` は時計の数え違いの直しで、効くのは主でないスレッドの前処理で ENUM_ADAPT が回るときだけ。P では中立、4 スレッドの neos-631710・30n20b8 の害を減らす。
  方針 (中立なら入れる) に沿えば、c2c に入れてよい。
