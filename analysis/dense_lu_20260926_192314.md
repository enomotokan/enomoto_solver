- **核の大きさと密度** (§2.3): nug08 は終盤で残り 1,600〜1,900 行の核がほぼ密 (k = 1000 で密度 0.8)、`L+U` の 88% がその因子、切替後は 92% 詰まる。

## 1. 現行 LU (src/simplex/lu.rs) の構造と、既存の稠密切替が何をしているか

### 1.1 因子の格納形式 (分解後は経路によらず同じ `LuFactors` → `FtLu`)

| 部分 | 型 / 場所 | 1 要素あたり | 備考 |
|---|---|---|---|
| `L` (列) | `LuFactors::l_col: CscMat` = `&[(usize, f64)]` (lu.rs:1405-1414, sparse.rs:871, 1106) | **16 B** | FT 更新で不変。FTRAN の `L` 段 (`l_solve_into*`, lu.rs:2398-2512) はこれを列順に走査 |
| `L` (行ミラー) | `LuFactors::l_row: CsrMat` (lu.rs:1419-1423) | 16 B | BTRAN `L^T` のスキャッタ形式 (lu.rs:2636) |
| `U` (列 eta) | `FtLu::u_seq: EtaFile` (`idx: Vec<u32>`, `val: Vec<f64>`、lu.rs:2767-2780) | **12 B** | 非対角 nnz が `DENSE_ETA_FRACTION (0.4)·m` を超える列は長さ `m` の密配列 (`ETA_DENSE`) |
| `U` (行ミラー) | `FtLu::row_owners: Vec<Vec<(usize, f64)>>` (lu.rs:3521) | 16 B | BTRAN `U^T` のスキャッタ (lu.rs:3816-3838) と FT 更新の行 `p` 消去 (lu.rs:6128) に使う。`U` は事実上 2 重に持つ |
| `U` シングルトン | `singles: Vec<SEta>` + `single_piv` | – | 非対角なしの列。`permute_out` (lu.rs:5184) で除算 |
| `R` eta | `r_etas: EtaFile` (行 eta) + 列方向索引 `r_head/r_next` | 12 B | 密になれば `ETA_DENSE` (長さ `m`) |

すべてが「添字 + 値」の疎形式。**密なブロックを密配列 (BLAS-2 の trsv) で解く経路は存在しない。**

### 1.2 分解の振り分け (`factorize` lu.rs:1936 → `factorize_routed` :1943)

1. `detect_border_columns` (:1533): 非零が `DENSE_COL_FRACTION (0.5)·m` を超える列を「境界列」とし、
   `border_wanted` (:1663、`0 < k ≤ 3000 かつ k ≤ 0.4 m`) なら `factorize_bordered` (:2167)。
   境界列を除いた疎 Markowitz (行シングルトン採用・行探索は無効化 :2189-2191) → `U_SD = L_SS^{-1} A_SD` を
   境界列ごとに密ベクトル前進代入 (:2283-2300) → `k×k` Schur 補行列を `factorize_dense_faer` → 結果を疎な `l_entries`/`u_entries` に戻す。
   **cont1 は `t` 列 (80,794 行に非零、m = 119,599 の 68%) が基底に入ると必ずこの経路になる**
   (§2.1: 68 回の分解のうち 46 回が faer 呼び出し = bordered `k = 1`)。この経路は `factorize_reusing` (:1624-1632) の
   ピボット順再利用の対象外 (`eligible = … && !border_wanted`) なので cont1 の再利用試行は 4 回 (全部 fill で棄却) しかない。
2. `is_dense_input` (:1437、nnz > 0.25 m²) なら全体を `factorize_dense_faer` (:1448)。
3. それ以外は `factorize_flat_markowitz_routed` (:1992)。`peel_column_singletons` の後、各ステップで
   `find_best_pivot` (:780、列バケット走査、探索上限 `PIVOT_SEARCH_LIMIT = 64`、`col_max_abs` の遅延再計算は
   `KernelMatrix::row_get` の二分探索 :289, :831-840) と行方向 `eliminate`。

### 1.3 既存の稠密切替 `ENOMOTO_LU_DENSE_SWITCH` (B3、既定 0 = off、lu.rs:2015-2059)

- `DENSE_SWITCH_CHECK_INTERVAL = 16` ステップごとに、**活性行を全走査して** (`(0..m).filter(!row_used).map(row_len).sum()`、O(m)) 活性非零数を数え、
  `active ≥ θ·k²` (k = 残り行数 ≥ `DENSE_SWITCH_MIN_ROWS = 64`) なら残りの `k×k` を `factorize_dense_faer` に渡す。
  この判定自体が `O(m²/16)` で、m = 120K の cont1 では 1 分解あたり 9 億回の読み出し (≈ 0.5〜1 s) になる
  (nug08 の m = 20K では 2,500 万で無害)。有効化するなら判定間隔を `max(16, m/256)` にするか活性非零数を差分更新する必要がある。
- 有効時は `peel_column_singletons` を使わない (:2022、判定順序を変えないため)。
- **切替後の密ブロックの因子は `dlu.u_row` / `dlu.l_col` を 1 要素ずつ `u_entries` / `l_entries` に戻して疎形式で保持する**
  (:2045-2054)。`FtLu::new` はそれを `u_seq` (u32+f64) と `row_owners` ((usize,f64)) の 2 重の疎形式に展開し、
  FTRAN/BTRAN は他の列と同じ疎ループ (`u_seq.axpy` = 添字経由のスキャッタ、`row_owners` のスキャッタ、`l_col` のスキャッタ) で処理する。
  つまり **B3 は Markowitz のピボット探索コストを消すだけで、求解は密ブロックも疎形式のまま** (LUSOL・CoinFactorization の dense 部分も同じ設計)。
  nug08 の終盤 (k ≈ 1,700) では密ブロックの因子は 92% 詰まっており (§2.2)、これを 12〜16 B/要素の添字付き形式で走査するのは
  8 B/要素の連続配列の 1.5〜2 倍のメモリ帯域を使い、複数右辺 (alpha, tau, BFRT) のブロック走査の共有もできない。
- FT 更新 (`commit_update_tracked` :6077): 旧 eta を `u_seq` から除き、行 `p` を `row_owners[p]` 経由で他の eta から消し (`remove_index`、密 eta なら O(1) の 0 書き)、
  スパイク `ã` を新しい列 eta として末尾に追加、`R` 行 eta を `ẽ` から作る。密ブロックの列が入れ替わるときの特別扱いは無い (すべて疎 eta なので不要)。

### 1.4 求解の経路 (密な右辺・密な結果のとき)

- FTRAN (`solve_into_pair_capture_tracked` :4659 → `pair_r_u_permute_tracked` :5082): `L` 段は alpha/tau の 2 本を 1 走査で (`l_solve_into_pair`)、
  `R` 段は全 eta と内積 (:5103)、`U` 段は超疎判定 (`try_u_hyper`) が密 eta の存在か到達数超過で失敗すると 2 本を 1 走査で `u_seq` 逆順に axpy (:5116-5131)、
  `permute_fused_out` で `col_perm` に戻しながらシングルトンの除算。`O(m)` のパスが入口 (`z[s] = rhs[row_perm[s]]`) と出口にある。
- BTRAN (`solve_transpose_unit_work_sparse` :5535): `U^T` は `row_owners` スキャッタ (0 スキップ付き)、`R^T` は eta 逆順 axpy、
  `L^T` は非零数が `BTRAN_L_SCATTER_FRACTION·m` 以下ならスキャッタ (`l_row`)、超えれば **ギャザー形式 `l_transpose_gather_core` (:2609) = `L` 全体を列順に読み `w[row_step]==0` を要素ごとに判定**。

≈ 1.7 ms、つまりこれもメモリ帯域律速で、これ以上は複数右辺の共有 (2 本で 2.4 ms、3 本でも ≈ 3 ms の見込み) でしか下がらない。

### 2.5 密ブロックを密配列のまま FT 更新する方式の数値検証 (`dense_ft_proto_check`, `ftproto_nug08.txt`)

nug08 の基底 #115 (θ = 0.3 で k = 1,696、s0 = 18,032) を分解し、密ブロック `L_DD`/`U_DD` を列優先の密配列、`D` 列の `S` 部分と
`S` 列は疎 eta、で保持。列の入れ替え 60 回 (半分は `D` ブロック内のスロット、半分は `S` のスロット。入る列は `B v` で非特異を保証)
を Forrest-Tomlin 更新 (§3.1 の規則) で行い、10 回ごとに更新後の基底を `factorize` + `FtLu` で分解し直した結果と比較:

```
after 10 updates (in_D=5):  ftran_rel_err=8.7e-15 btran_rel_err=0
after 60 updates (in_D=30): ftran_rel_err=2.6e-14 btran_rel_err=3.1e-18   r_etas=60 appended=60 rejected=0
DENSE_FT m=19728 k=1696 ftran_after_60_updates=1.89 ms (更新前 1.78 ms)
```

→ 密ブロックの列を「死なせて」スパイクを疎 eta として末尾に足す方式は、FTRAN/BTRAN とも再分解と 1e-14 で一致し、
60 更新後の FTRAN も 1.89 ms (現行 `FtLu` の更新前 2.5〜2.8 ms より速い)。試作の更新 1 回 2.9 ms は行 `p` の消去を全 eta の
`retain` で行う素朴な実装のためで、本実装では `row_owners` (行 → eta) で現行と同じ O(行 p の非零) になる。

## 3. 方式案 (一般的な方式との比較と、このリポジトリに合う 2〜3 案)

### 3.0 参考: 他実装の方式

| 実装 | 分解の密部分 | 求解 | FT 更新と密部分 |
|---|---|---|---|
| LUSOL (`lu1fac`, TPP/TRP/TCP) | `dens1 = 0.3` で列探索のみ、`dens2 = 0.6` で残りを **密 LU** (`lu1ful`) に切替。密因子は疎 `L`/`U` ファイルに戻す | 疎ファイルの走査 (密部分も疎形式) | `lu8rpc` は Bartels-Golub 型 (行の eta を `L` ファイルに追加)。密部分に特別扱いなし |

| HiGHS `HFactor::buildKernel` (`HFactor.cpp:867-1100`) | **密切替なし**。列に値を持つ CSC (`mc_value`) + 行索引ミラー (`mr_index`) + 次数リンクリスト。探索上限 `searchLimit = min(nwork, 8)` で列と行の両方を探す、`mc_min_pivot` を列ごとに保持 | `ftranU`/`btranU` は eta 列、密度履歴 `expected_density > kHyperFtranU` で超疎/全走査を選ぶ | Forrest-Tomlin (`updateFT`)、`update_limit = 100` |

このリポジトリでは FT 更新が `u_seq` (列 eta の作成順) + `row_owners` (行ミラー) + `R` 行 eta で実装されており (§1.1)、
密ブロックを密配列にする場合の論点は「`u_seq` の逆順走査と `row_owners` のスキャッタの途中に密 `L_DD`/`U_DD` の trsv を挟めるか」と
「密ブロック内のスロットが置換されたときの扱い」の 2 つ。

### 3.1 案 A (推奨、nug08 型向け): 稠密切替 + 密ブロックを密配列で保持 + FT 更新は「ブロック内の列を死なせる」

- 分解: 既存 B3 (`ENOMOTO_LU_DENSE_SWITCH`、θ = 0.3、lu.rs:2015-2059) を 91c1c3d の自動条件 (`m ≥ 10,000` かつ直前の nnz(L+U) ≥ 32 m) で
  有効化し、密ブロック `k×k` の因子を **疎に戻さず** `LuFactors` に `dense: Option<DenseBlock { s0, k, l_dd: Vec<f64>, u_dd: Vec<f64> }>`
  (列優先) として持たせる。`L` の列 `s ≥ s0` は空、`U` の行 `s ≥ s0` の列 `≥ s0` は `u_row` に入れない。
- `FtLu::new`: スロット `s ≥ s0` の eta は「`S` 部分 (`row_step < s0`) の疎 eta」+ 密ブロック内の列、として作る。
  `singles`/`single_piv` の扱いは変えない (`D` 列は非対角を持つので `u_seq` 側)。
- FTRAN の `U` 段 (`u_solve_into` :3962、`pair_r_u_permute_tracked` :5116): `u_seq` を逆順に走査する現行ループのうち、
  「作成順で密ブロックより後に追加された eta (更新スパイク)」→ 「密 `U_DD` の後退代入 (列 axpy、ゼロスキップ付き)」→
  「`D` 列の `S` 部分の疎 eta」→「`S` 列の疎 eta」の順にする。`u_seq` の並びが作成順なので、分解時の eta は位置 `< m`、
  追加 eta は位置 `≥ m` で区別できる (試作 `DenseFt::u_stage`)。alpha/tau/BFRT の複数右辺は密ブロックの走査を共有する (`ftran2`)。
- BTRAN の `U^T` 段 (`u_transpose_sweep` :3816): `S` 列 → `D` 列の `S` 部分 (`row_owners` スキャッタのまま) → 密 `U_DD^T` (内積形式) →
  追加 eta、の順。`L^T` 段は `L_DD^T` (内積) → 疎 `L^T`。
- FT 更新 (`commit_update_tracked` :6077): 置換スロット `p` が `D` 内なら `U_DD` の列 `p−s0` を 0 (対角 1) にし、行 `p−s0` も 0 にする
  (Tomlin の行 `p` 消去の密版 = O(k) の 0 書き)。`S` 部分の疎 eta は現行どおり `row_owners` で消す。スパイク `ã` は現行どおり
  全行の疎/密 eta として末尾に追加、`R` eta も現行どおり。`p` が `S` 内なら `U_DD` の行 `p` は無いので密側は無変更。
  → **密ブロックは分解後は「縮む」だけ** (列が死ぬと対角 1・要素 0 の no-op 列になる) で、更新で密ブロックが膨らむことはない。
  再分解のたびに作り直す。試作で 60 更新まで再分解と 1e-14 で一致 (§2.5)。
- ピボット順再利用 (`factorize_reusing_order` :1701): 密切替した分解の列順を再利用すると密ブロック部分の左視分解が k² 個の非零を
  疎に扱うので不可。密切替した分解は `eligible = false` にする (現状も `nug08` で採用率 35%、失敗は fill 超過)。
- 期待効果 (nug08、§2.4 の実測から): 再分解 6.6 s → 0.7 s (290 s → ~35 s)、FTRAN 2 本 5.3 → 2.4 ms、BTRAN 2.5 → 2.3 (単位) / 5.5 → 2.8 (密)。
  更新 eta の累積分 (スパイク 19K 非零/回) は残るので 1 反復 12.3 ms → **8〜9 ms** (完走 540 s → 380〜420 s。HiGHS 284 s には
  従属等式 1,458 行の除去 = 反復 −5〜10% が別途要る)。cont1 には効かない (核が疎、§2.3)。
- 難度: 高 (FtLu の `U` 段 5 経路 (`u_solve_into`, `u_solve_hyper` (密ブロックがあれば即 `false`)、`pair`/`triple` の融合走査、`u_solve_partial`) と
  `U^T` 段 3 経路、`commit_update`、`lazy_remove`/`n_dead` との整合)。切替が起きない問題は `dense = None` で経路・ビット不変。

### 3.2 案 B (推奨、全問題向け・A の前段): 疎因子の格納形式と O(m) パスの整理 (密切替なし)

- `L` の `CscMat<(usize, f64)>` (16 B) を添字 `u32` / 値 `f64` の別配列 (12 B、連続) に、`row_owners: Vec<Vec<(usize,f64)>>` (行ごとの
  ヒープ確保、16 B) を `u_seq` と同じプール形式に。§2.4 の `compact` は同じ演算順序で cont1 FTRAN (疎右辺) −25〜35%、BTRAN (密右辺) −40%、
  nug08 FTRAN −5〜10%、BTRAN −10%。**演算順序を変えなければビット一致** (試作で `diff = 0` を確認できる形)。
- BTRAN `L^T` のギャザー形式 (`l_transpose_gather_core` :2609、cont1 で 1.35 ms/反復) は、`w` の非零が 33% でもスキャッタ形式 (`l_row`) の方が
  安い (読む要素が `L` 全体でなく非零行の分だけ)。`BTRAN_L_SCATTER_FRACTION` を `m ≥ 10K` で上げる、または `touch` リストで駆動。
- `permute_out` (:5184、cont1 0.78 ms) の要素ごとの `if d != 0 && v != 0 { v /= d }` を、シングルトンをステップ順の連続区間にまとめる
  (`peel_column_singletons` の先頭区間はもともと連続) か、逆数の乗算にする (ビット非一致 → `m ≥ 10K` ゲート)。
- 期待効果: cont1 8.6 → 6〜6.5 ms/反復 (−25〜30%)、nug08 (A と併用) −5%、ex10/neos/square41 の密 FTRAN も −10〜20%。
- 難度: 中 (`CscMat::col` を使う箇所の置換は `L` 専用型を作れば lu.rs 内で閉じる)。Netlib: 順序不変ならビット一致、ゲート不要。

### 3.3 案 C (参考、不採用): Schur 補行列型の更新で密ブロックと FT の共存問題を回避する

- 分解 `B0` を固定し、更新は `r×r` の密 Schur 補行列 `S = E^T B0^{-1} A_new` で持つ。分解側は密ブロックを密配列のまま
  (更新で触らない) にできるので共存は自明で、実装も FT 更新より単純 (`V = B0^{-1} A_new` の列を 1 本追加するだけ)。
- ただし FTRAN は `B0^{-1} a` + `V y` (m × r の密 axpy) + `S^{-1}`、BTRAN も同様で、r = 100〜300 のとき `V` の走査が
  m × r = 20K × 300 = 6M 要素 (nug08) / 120K × 100 = 12M (cont1) と、現行の `R` eta (12.6 万非零) より桁違いに重い。
  密な `B^{-1}` の問題では `V` も密なので利点がない。**採らない**。

### 3.4 案 D (参考): 境界付き分解の拡張 (cont1 の `t` 列)

- cont1 の終盤基底は境界列 1 本 (`t`) で `factorize_bordered` を通る。flat Markowitz と時間・fill が同じ (§2.4) なので
  分解方式の問題ではなく、ピボット順再利用の対象外 (:1632) になることだけが損。再利用を許すか (境界列を最後に固定して
  左視分解)、cont1 は fill が増え続けて再利用が棄却される (4/4 失敗) ので効果は限定的。優先度低。
