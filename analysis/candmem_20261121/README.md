# 分離の候補のメモリと密なカット (2026-11-21、親の依頼、analysis/biglp_20261121 の直す案 2)

## 結論 (先に)

1. **結果の変わらない直しを既定に入れた** (src/mip/separation.rs の `separate` の tableau 行の並列の経路)。
   - 以前: 集約行 (基底逆行列の行 × LP の行) を全部作ってからスレッドに配っていた。rail01 では 1 回 2746 行 × 平均 2〜4 万非零を一度に持っていた。
     heaptrack の `separate` の `Vec<(usize, f64)>` の 2.2 GB がこれ。
   - いま: 主のスレッドが今までと同じ順で 1 行ずつ BTRAN・集約し、番号つきで作業のスレッドに流す (待ち行列はスレッドの数の 2 倍まで)。
     作業のスレッドはカットを作り、主は番号の順に受け取って予算を引き、候補に足す。
   - `ENOMOTO_MIP_TAB_NNZ_CBC` の予算に届いたら、後ろの行は作らない。以前も、その行のカットは作ってから捨てていた。
     ただし `ENOMOTO_MIP_FACE_TAB_SKIP`・`ENOMOTO_MIP_TAB_HIGHS_SIG` の測り・`ENOMOTO_MIP_DEBUG_SEP` のときは、以前と同じく全部作る。
   - `finish_cut` の係数の領域は、吸収の前の長さで取っていた。余りを返す (`shrink_to_fit`)。
   - `ENOMOTO_MIP_SEP_TAB_STREAM=0` で以前の持ち方に戻る (比べ用)。候補は同じで、メモリと時間だけが以前の形になる。
2. **候補は以前と同じ** (事実、2 節):
   - 同じ過程の中で、送った集約行から逐次に作り直した候補と、ビット単位で比べた。
   - 13 問 × 4 スレッド、根の分離の呼び出し 573 回 (予算のかかった 203 回を含む) で、すべて同じだった。
   - 違ったのは mzzv42z の 1 回だけで、30 秒の時間切れで作業のスレッドが残りの行を作らなかった回。以前の形でも同じく違う。
3. **rail01 (4 スレッド・600 秒) の最大 RSS は 6011 → 4052 MB (−33%)** (事実、3 節)。
   - 分離の 1 ラウンドの時間は同程度 (old 5.5〜8.9 秒、new 4.6〜10.4 秒)。
   - 根の道筋は 4 スレッドの競走で分かれるので、下界 (−81.47 / −80.13) の差は直しのせいではない。同じ old を 2 回回しても r0 の候補が違う問題がある (2 節)。
4. **候補を早く捨てる案は効かない** (事実):
   - rail01 の 1 ラウンドの候補 5468〜5547 本は、どのラウンドでも質の閾値 (最良の 0.5 倍) をほぼ全部が超える。
   - 落ちるのは、選んだカットとの平行度で落ちるもの (0 ラウンド目は 5519 本) か、本数の上限で見られないもの。どちらも選ぶまで分からない。
   - したがって、選択の結果を変えずに早く捨てられる候補はほとんどない。
5. **密なカットの既存の手** (どれも既定では使わない) は、rail01 で根の下界を上げない (3 節)。
   - `ENOMOTO_MIP_GAP4` に `l` を足す (カットの非零を 100 + 0.15 × 列 まで、HiGHS の postprocessCut と同じ) と、
     `ENOMOTO_MIP_ROOTCAP=d` (1 ラウンドのカットの非零の和の上限) は、メモリが 2.7 GB まで下がる。下界は −81.5・−82.1 で、new の −80.1 と同程度。
   - `ENOMOTO_T_CUTSEL_DENSITY_EXP=1` (点数を非零で割る) は、根のループの下界が −88.3 と大きく悪い。
   - nw04 (密な path_highs の候補、rootgap 7.2 節) は既定では 0 ノードで閉じるので、どの手も時間を縮めない (37〜45 秒、Local-MIP の競走の揺れが大きい)。
   - **新しい既定の候補は出なかった**。HiGHS が rail01 の根で −77.5 まで上げる差は、密なカットの扱い (本数・選び方) ではなく、ラウンドの数 (HiGHS は 600 秒で根のカットを回し続ける) にあると見る (推測)。
6. **残りのメモリ** (rail01 の 4 GB): 内点法の gemm の作業領域 2.2 GB (biglp の直す案 3、別の分担) と、主と裏のカットが同時に持つ候補 (1 回 約 1 GB)。

## 1. 直しの中身

- `separate` の `if par {` の経路 (根の分離、木を分け合う前、サブ MIP でない、既定の行の選び方)。
  - 行の選び方 (`basics` の並べ替え・上限)・集約・照合の記録 (`tab_memo`)・カットの生成 (`generate_cuts`・`finish_cut`・`keep_best`)・
    予算の引き方・つなぐ順は、以前のまま。
  - 変わったのは、集約行を作る時期 (流しながら) と、予算に届いた後の行を作らないことだけ。
- 作業のスレッドが読む `cut_int`・暫定解は写しにした (主は同時に LP の BTRAN と照合の記録を使うため)。
- BTRAN (`basis_inverse_row`) は LU の決定的な演算量の数え (`synth_tick`) を元に戻すので、後ろの行を作らなくても他の判断は変わらない。
  `crate::ticks` も分離の頭で 1 回足すだけ。
