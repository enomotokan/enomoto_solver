# RENS のやり直しを続きから継続する試作 (2026-11-01)

背景: 根の RENS のサブ MIP が `NodeLimit` で返ると、ノード上限を 4 倍にした `RENS (more nodes)` が同じ問題を最初から解き直す
(前処理・根の LP・カット・根のヒューリスティクス・入れ子の RENS・ノード 0 からの木を全部やり直す)。停滞・成果連動の打ち切りで止まった
ものも状態は `NodeLimit` なので、同じノード・同じ解で止まる空回りになる (analysis/cand_slow_n5-3_20261031.md・analysis/submip_where_20261101.md)。
`ENOMOTO_MIP_RENS_MORE_NODES_REAL` (別のセッション、analysis/rens_more_real_20261101/) は本当にノード上限まで進んだときだけやり直す。

ここでは止まり方で場合分けし、本当にノード上限で止まったものは **1 回目のサブ MIP の求解の状態を残して続きから** 解く試作
`ENOMOTO_MIP_RENS_RESUME` (既定では使わない) を入れて比べた。

- 機械: 4 CPU。4 スレッド・60 秒、ソルバーは同時に 1 つだけ。HiGHS (highspy) 1.15.1。
- ビルド: ブランチ `ccr-1beed81b-ex0uhq` の `908c585` (試作と下のログの行を入れたもの)。
- 台本・ログ: `analysis/rens_resume_20261101/`
  - `run.py 設定[,…] 問題[,…] 回数`: `def` (既定)・`real` (+ `ENOMOTO_MIP_RENS_MORE_NODES_REAL=1`)・`resume` (+ `ENOMOTO_MIP_RENS_RESUME=1`)。
    `ENOMOTO_MIP_LOG=1 ENOMOTO_MIP_SUBMIP_VERBOSE=1`。ログは `logs/<設定>/<問題>_r<回>.log`。
  - `analyze.py retries ログ…`: やり直し・継続を 1 本ずつ (直前の RENS、秒、根の秒と割合、解、親を良くしたか)。`retries.txt`・`retries_by_conf.txt`
  - `analyze.py summary logs def real resume`: 問題 × 設定ごとの 3 回の結果 (`summary.txt`)
  - `retries58_where.txt`: 58 問のログ (analysis/submip_where_20261101/logs) を別のセッションの `retries.py` で数えたもの

## 0. 足したログ (振る舞いは変えない)

`ENOMOTO_MIP_SUBMIP_VERBOSE` のときだけ `MIP: SMT tree tag=… restarts=… secs=… T=…` を出す (各求解が根を終えて木を始めた時刻、
`src/mip/solver.rs`)。やり直しのサブ MIP の「始め (SMT begin) から木の始めまで」を根の秒とし、その間に始めた子のサブ MIP の秒を入れ子の秒とする。

## 2. 試作 `ENOMOTO_MIP_RENS_RESUME` (既定では使わない)

`src/mip/solver.rs` の `rens_resume_on` の説明に詳しく書いた。

- **場合分け**: 停滞・成果連動の打ち切りで止まったもの (ノード数 < 上限) はやり直さない (`rens_more_nodes_real` は RESUME でも真になる。REAL と同じ)。
- **一時停止**: 根 (`nodes <= 1`) の RENS のサブ MIP を専用のスレッドで解く。サブ MIP の木がノード上限に達したら (`Solver::resume_pause`)、
  その時点の結果 (暫定解を後処理で元の空間に戻したもの、下界、ノード数) を呼び出し側に渡し、スレッドの中でそのまま合図を待つ。
  木・待ち行列・カットのプール・擬似コスト・LP・前処理の後の問題と後処理の手順は、そのスレッドのスタックに残る。呼び出し側はその結果を
  1 回目の結果として受け取る (受け入れ・ログ・`rens_node_limited` は今まで通り)。下界が打ち切り値に届いている (探索し残しがない) ときは一時停止しない。
  - 逐次のサブ MIP (`solve_submip_problem`): 主のスレッドで解く代わりにスレッドを立ててすぐ待つ (`spawn_resumable_submip`)。サブ MIP が読む
    スレッド局所の設定 (深さ・道筋・基底・pseudocost・成果連動の打ち切りの情報・`HS_DROP` など) は `SubmipTls` で写す。
  - 並列のサブ MIP (`spawn_submip`): 今のスレッドに一時停止の合図を足すだけ。`join_submips`・`poll_submips` は「終わった」か「一時停止の結果が届いた」
    を終わりとして受け取る (`take_submip`)。Solver を結果と一緒に返す形は、Solver が前処理の後の問題を借りていて (`&'a MipProblem`) スレッドを
    またいで持ち出せないので採らず、スレッドを止めて合図を送る形にした。逐次・並列で同じ仕組みになる。
  - 深さ 2 以上 (サブ MIP の中の RENS) も同じ (呼び出し側はサブ MIP のスレッド)。下の ran14x18-disj-8 は深さ 1 の並列のサブ MIP の中の深さ 2 の逐次の RENS。
- **継続** (`rens_resume`): やり直しの判定 (差 > 0.5%) が通れば、合図 `ResumeCmd` を送って終わりを待つ:
  - ノード上限: 1 回目の上限 × `ENOMOTO_T_MIP_RENS_MORE_NODES_MULT` (深さ 2 以上は `_SUB_MULT`)。通算なので 500 → 2000 なら続きの 1500 ノード
    (やり直しは 2000 ノード)。
  - 時間の上限: 今の残り時間から新しいサブ MIP と同じ決め方 (`submip_time_limit`、`solve_submip_problem` から切り出した) で決め直し、サブ MIP の
    期限を「今 + その秒」にする (1 回目の期限を引き継がない。analysis/cand_default_20261031.md 1.1 節と同じく、外側の残りを越えない)。
  - 打ち切り値: 外側の今の刈り込みの上限 (1 回目の後に見つかった解を含む) をサブ MIP の `params.cutoff` と成果連動の打ち切りの情報に渡す。
  - 継続の後は一時停止しない。
- **捨てる**: 一時停止のサブ MIP は `PausedSubmip` が持ち、落とすと止めの合図 (送り手を落とす) を出してスレッドの終わりを待つ (`Drop`)。
  サブ MIP はノード上限で止まったものとして普通に終わり、状態は消える。捨てる所: やり直しの判定の直後 (使っても使わなくても)、次の RENS を
  始めるとき (同時に持つのは 1 本)、求解が途中で返ったとき (Solver の破棄)。並列の待ち行列に残ったまま Solver が消えても、送り手が消えるので
  スレッドは自分で終わる。止めるのにかかった時間は 14 回 (次の RENS で 8・判定の後 6) で最大 5 ms。
- 診断用のログ (`ENOMOTO_MIP_SUBMIP_VERBOSE`): `sub-MIP paused at the node limit: nodes … open nodes … lower bound … incumbent …`、
  `sub-MIP resumed after …: nodes … open nodes … node limit … time limit … cutoff …`、`RENS (more nodes): resuming the paused … sub-MIP`、
  `paused sub-MIP … dropped (理由)`。`SMT end … paused=1` と、継続の分は新しい番号の `SMT begin kind=[RENS (more nodes)]` + `SMT resume id=… from_nodes=…`。

### 続きになっていることの確かめ

ran14x18-disj-8 (3 回とも同じ) の深さ 2 の 1 本:

```
MIP: sub-MIP paused at the node limit: nodes 500, open nodes 495, lower bound 3.4874604758e3, incumbent Some(4045.99999997352), cut pool 2, LP rows 274 (1.23s)
MIP: SMT end id=4 status=NodeLimit nodes=500 objective=Some(4045.99999997352) secs=1.227 T=5.517 paused=1
MIP:   RENS (more nodes): resuming the paused sequential sub-MIP at 500 nodes (objective Some(4045.99999997352), held 0.01s): node limit 500 -> 2000, time limit 3.80s, cutoff 4.0459999959e3
MIP: sub-MIP resumed after 0.01s: nodes 500, open nodes 495, node limit 2000, time limit 3.80s, cutoff 4.0459999959e3, incumbent Some(4045.99999997352)
MIP:   sub-MIP (resumed): status NodeLimit, nodes 2000 (1500 after the pause), objective Some(3926.9999999944557), 1.54s
```

一時停止の前後でノード数・開いたノードの数・暫定解が同じで、ノード数は 500 から続いて 2000 で終わる (根の前処理・LP・カットの行は出ない)。
supportcase26 (深さ 1 の並列) でも `nodes 500, open nodes 305` → 再開で同じ、2000 ノードで終わる。

## 4. まとめ

- 本当にノード上限まで進む RENS は少ない (58 問 1 回で 7 本、ran14x18-disj-8・supportcase26・blp-ar98)。空回りのやり直しを消す
  REAL の効きの方が大きく、継続はその上に、残ったやり直しの時間を深さ 1 で約 7 割、深さ 2 で約 5 割減らす。
- 継続は木を続けるだけなので、やり直しがもう一度回す根のヒューリスティクスの分の解の良さは失う (ran14x18-disj-8 の深さ 2)。外側の結果は REAL と同じ。
- 並列・逐次・深さ 2 以上で同じ仕組み (スレッドの一時停止) で動き、使わなかった状態は数 ms で捨てられる。

## 5. 58 問で確かめる形 (提案)

analysis/submip_where_20261101/run.py (`ENOMOTO_MIP_LOG=1 ENOMOTO_MIP_SUBMIP_VERBOSE=1`、4 スレッド・60 秒、1 問ずつ) で、58 問

REAL との差 (本当に上限まで進む数問だけが動くはず) を見る。
