# BTRAN の `L^-T` 転置行major化 と U の到達集合限定 FTRAN(`docs/lu_comparison_enomoto_vs_highs.md` §2.6)

対象: §2.6 が挙げる 2 点 —「`U` の求解が密スキャン」「BTRAN の `L^-T` に転置列major がない」。
基点 `main` = ff53323(§2.7 の FTRAN 結果密度ゲート採用後)。4 コア、rustc 1.94.1、
highspy(Python 3.11)、NETLIB93 全問題。

## 0. 結論

1. **BTRAN 側(`l_row` + scatter + 密度ゲート)を採用。** 正しい基準(下記 §4)での
   93 問題合計は独立 2 回で **-0.05%**(45.532s → 45.510s)と **-1.70%**
   (46.238s → 45.451s)。改善幅は小さく測定限界すれすれだが、**2 回とも
   非悪化側**。10% 以上の退行は「2 回とも 10% を超える問題」が 1 件も無い
   (§5)。目的関数値は全実行で 93/93 一致。
2. **U 側(到達集合限定 FTRAN)は不採用・削除。** HiGHS と同じ `kHyperFtranU = 0.10`
   相当のゲートを付けてなお **+3.6%**。走査量は実測で 78〜96% 削れていた
   (`avg_reach_frac` 0.043〜0.217)にもかかわらず遅い。過去のゲート無し版が
   +10.4% だった件と、ゲート付きでも同じ結論に達した(§3)。
3. **密度ゲートは必須。** ゲート無しの scatter は合計 +3.0%、10% 超の退行 2 問題。
   同じコードがゲート付きで中立になる(§2)。
4. **この環境では個別問題の 10〜20% の振れは日常的に発生し、挙動差では説明がつかない。**
   反復数・再分解回数が両アームで完全一致している問題が、5 反復で +21%、
   11 反復で +1.5% になる(§5)。10% ルールの適用は高反復の取り直しを伴わないと
   意味を持たない。
5. **唯一の実退行は `pilot` +7.2%**。原因は反復数 +5.1%(3151 → 3313)であり、
   1 反復あたりのコストは悪化していない(§5.2)。
6. **計測方法自体に誤りがあり、途中で訂正した**(§4)。訂正前の数値は無効。

## 1. 実装

### 1.1 `LuFactors::l_row`(HiGHS の `lr_start/lr_index/lr_value` 相当)

`l_transpose_solve_into` は列major `l_col` しか持たず **gather 型**だった。1 段 `s` が
複数の `w[row_step]` を読むため、段を丸ごと飛ばせる単一の値が存在しない
(Hall & McKinnon 2000 §4.4 が「内積の評価自体に匹敵するコストなしには自明性を
判定できない」と述べている状況)。

行major ミラー `l_row` を追加して **scatter 型**にすると、`w[s]` が内側ループ唯一の
乗数になるので `w[s] == 0.0` で段全体がスキップできる。FTRAN 側
(`l_solve_into` / `u_solve_into`)が既に持っていた零スキップが BTRAN 側にも入る。

格納は `FixedRows`(offsets + flat entries、2 アロケーション)。`l_col` のフラット化が
過去に回帰した理由は「どのみち `m` 本の小さい `Vec` を作ってから余計に 1 回コピーする」
ことだったが、`l_row` は変換元の `Vec<Vec<..>>` が存在しないので
`FixedRows::from_transpose` の計数ソートで最初から直接フラットに組める。
その回帰要因を踏まない。

`L` は Forrest-Tomlin 更新で不変(変わるのは `u_seq` と `r_etas`)なので、
再分解 1 回につき 1 回構築して、その基底の寿命の間ずっと読む。

### 1.2 密度ゲート `BTRAN_L_SCATTER_FRACTION = 0.10`

両形式は**同じ `L` の要素に触れる**。違うのはアクセスの形だけで、

- gather: ランダム**ロード** + `w[s]` 1 箇所への集約(レジスタに載る)
- scatter: `w[s]` 1 回のロード + ランダム**リードモディファイライト**

`w` が疎なら段スキップで触れる要素数自体が激減するが、`w` が密だと 1 段も飛ばせず、
ランダムロードをランダムストアに置き換えただけの純損になる。さらに `l_row` は `L` の
複製なので、scatter を使うと FTRAN 側の `l_col` と合わせて `L` 相当を 2 組
キャッシュに通すことになる。

判定は移動平均による**予測ではなく厳密な数え上げ**。FTRAN の入力密度(§2.7)は
ベクトルを作る前に決める必要があるため履歴に頼るしかなかったが、BTRAN の `L` 段の
`w` は目の前のバッファにあり、どのみち最後に `y` への置換で全体を走査する。
早期打ち切り付きの逐次 1 パスで済む。

## 2. 計測1: ゲートの要否(全 93 問題、3 反復)

ゲート無し(常に scatter)vs 従来:

| | |
|---|---|
| 合計 | **+3.0%** |
| 10% 超の退行 | pilot.ja +12.7%、fit2d +11.6% |
| 主な改善 | 25fv47 -17.7%、stocfor2 -17.6% |
| dfl001 | +6.5% |
| 目的関数値 | 93/93 一致 |

**同じ変更が -17% と +12% の両方を出す。** 実装の良し悪しではなく `w` の密度が
問題ごとに違うことの直接の現れ。`dfl001` は `U^-T` と R-eta 段を通った後の `w` が
密で、段スキップが働かない。

## 3. 計測2: 閾値の掃引と U 側の可否(全 93 問題、3 反復)

| アーム | 合計 | 対 base | 10% 超の退行 |
|---|---:|---:|---:|
| base | 47.06s | — | — |
| ゲート 0.10 | 46.14s | -2.0% | 2 |
| ゲート 0.50 | 48.01s | +2.0% | 9 |
| 0.10 + hyperU | 47.79s | +1.6% | 7 |

目的関数値は全アーム 93/93 一致。

- **0.50 は明確に劣る。** 密度 0.1〜0.5 の帯域はすでに scatter が負ける領域。
  素朴なモデル(ストアがロードの 1.5〜2 倍)なら損益分岐は 0.5 付近のはずで、
  実測の交差点はそれよりかなり低い。上記のキャッシュ作業集合の倍化が
  モデルに入っていないためと見られる。HiGHS の定数をそのまま採らず測って決めた。
- **hyperU は 0.10 比 +3.6% で不採用。** `avg_reach_frac` は 0.043〜0.217、
  つまり `u_seq` の走査量は理屈どおり 78〜96% 削れていた。それでも遅い。
  DFS のスタック操作・`sort_unstable`・epoch 判定の合計が、`u_seq` の素直な
  逐次走査に勝てない。**削っていたのは元々安い部分だった。**
  実装は削除し、`u_solve_into` の doc に 2 回目の計測として記録した。

## 4. 訂正: base アームが `l_row` を構築したまま計測していた

§2・§3 の base アーム(`ENOMOTO_BTRAN_L_SCATTER=0`)は scatter の**使用**だけを
無効化しており、`l_row` 自体は毎回の再分解で構築していた。転置の `O(nnz(L))`
構築コストが両アームに等しく入っており、scatter 対 gather の差しか測れていない。
`dfl001` は再分解が約 100 回あるので無視できない。**採否を左右するコストを
比較対象の側にも払わせた状態で測っていた。**

`build_l_row` を追加し、ゲートが 0 のときは同じ `m` 個の外側スロットを持つ空の
`FixedRows` を返すようにして base を真の §2.6 以前(構築コスト込み)にした。

訂正後(全 93 問題、5 反復、独立 2 回):

| 実行 | base(真の main 相当) | ゲート 0.10 | 比 |
|---|---:|---:|---:|
| 1 回目 | 45.532s | 45.510s | **0.9995** |
| 2 回目 | 46.238s | 45.451s | **0.9830** |

目的関数値はどちらも 93/93 一致。

合計値の推移: -2.0%(§3、基準誤り)→ +0.4%(基準誤り)→ **-0.05% / -1.70%
(正しい基準)**。改善は 1% 前後で、この環境の実行間振れ(同一コードで 2.4
ポイント動く)と同程度。**2 回とも非悪化側ではあるが、「-1% の改善」と
断言できるほどの分離はない。**

## 5. 10% ルールの適用

### 5.0 10% 超の顔ぶれが実行ごとに完全に入れ替わる

正しい基準での独立 2 回、同じ問題を並べたもの:

| 問題 | 1 回目 | 2 回目 |
|---|---:|---:|
| stocfor1 | **1.211** | 1.000 |
| modszk1 | **1.178** | 0.999 |
| pilotnov | **1.166** | 1.017 |
| d6cube | **1.151** | 1.022 |
| share1b | 0.998 | **1.165** |
| scsd8 | 0.926 | **1.137** |
| stocfor2 | 0.849 | 1.001 |
| pilot87 | 0.941 | 0.923 |
| pilot | 1.135 | 1.055 |

**1 回目に 10% を超えた 4 問題はすべて 2 回目で 1.00 前後**、2 回目に超えた
2 問題は 1 回目で 1.00 前後。**2 回とも 10% を超える問題は 1 件も無い。**
`analysis/ftran_density_gate_20260922_062832.md` §4.3b が
「10% 超の顔ぶれが実行ごとに完全に入れ替わることがノイズである証拠」と
記録したのと同じ現象。

一貫しているのは `pilot87`(-6〜-8%、改善)と `pilot` / `25fv47`
(+5〜+10%、退行)のみ。いずれも §5.2 のとおり反復数で説明がつく。

### 5.1 5 反復で 10% 超に見えた問題は、ほぼすべて 11 反復で消える

| 問題 | 5 反復 | 11 反復 | 反復数(base → L) |
|---|---:|---:|---|
| stocfor1 | 1.211 | **1.015** | 79 → 79(完全一致) |
| modszk1 | 1.178 | **0.989** | 696 → 696(完全一致) |
| pilotnov | 1.166 | **0.956** | 1203 → 1203(完全一致) |
| d6cube | 1.151 | **1.031** | 400 → 400(完全一致) |
| pilot | 1.135 | **1.072** | 3151 → **3313** |

上 4 件は**ピボット列が完全に同一**で、挙動差が存在しない。挙動が同一のコードが
実際に 15〜21% 遅くなることはあり得ないので、これはこの環境のノイズ下限そのもの。

同じことが零スキップ(`ENOMOTO_FTRAN_U_ZERO_SKIP`、`x[p]` が零なら除算と
ランダムストアを省く変更、符号付き零以外に数値差が無い)でも確認できた:
反復数が stocfor2 1649/6、25fv47 3491/28、greenbeb 4597/19、pilot.ja 1592/16 と
両アームで完全一致しているのに、10% 超の退行が 4 問題出た。

`analysis/ftran_density_gate_20260922_062832.md` §4.3 が `sc50a`
(ゲート未発火・挙動完全同一で 12.5% 振れ)で記録した測定限界と同じ現象。

**符号が実行ごとに反転する例**: `pilotnov` は -14.4%(ある実行)と +16.6%
(別の実行)の両方を出す。`stocfor2` も +20.9% と -15.1% の両方。

### 5.2 一貫して動く問題は、すべて反復数で説明がつく

| 問題 | 反復数(base → L) | 再分解 | 時間比 | 読み |
|---|---|---|---:|---|
| 25fv47 | 3221 → **3491**(+8.4%) | 26 → 28 | +9% | 反復増でほぼ全部説明 |
| pilot | 3151 → **3313**(+5.1%) | 30 → 33 | +5〜7% | 同上 |
| pilot87 | 7033 → **6864**(-2.4%) | 62 → **57** | -7% | 逆向きの同じ機序 |
| maros-r7 | 2443 → 2443(**完全一致**) | 28 → 29 | -12% / +2% | 挙動差なし = ノイズ |

scatter は同じ積を逆順に足すため最終桁が変わり、双対比率テストのタイブレークが
ずれる。**1 反復あたりのコストが悪化している問題は見つかっていない。**
退行側も改善側も同じ機序で、93 問題の合計では相殺されて ±1% に収まる。
`analysis/ftran_density_gate_20260922_062832.md` §4.4 の `pilot87` と同じ構図。

**2 回とも 10% を超える問題は無く、11 反復で取り直しても 10% 以上の退行は無い。**

## 6. 採否の判断材料

満たしている:
- 10% ルール(高反復で取り直した後、10% 超の退行ゼロ)
- 目的関数値・status は全実行で 93/93 一致
- §2.6 が指摘した構造的欠落(4 方向のうち BTRAN-`L` だけ hyper-sparse 化が
  不可能だった)を解消する

コスト / 留保:
- **合計の改善は小さい**(正しい基準で -0.05% / -1.70%)。2 回とも非悪化側だが、
  この環境の実行間振れと同程度なので「確実に速くなる」とは言えない
- `L` の複製分のメモリ(`nnz(L) × 16` バイト + `(m+1) × 8` バイト)
- 再分解ごとの `O(nnz(L))` 構築
- 求解カーネルが 1 本増える(scatter と gather の両方を保守する必要がある)

**採用と判断した理由**: 10% ルールを満たし(2 回とも超える問題ゼロ)、目的関数値は
全実行で一致し、合計は 2 回とも非悪化側。一貫した退行はいずれも反復数の変化で
説明がつき、1 反復あたりのコスト悪化は観測されていない。§2.6 が指摘した
「4 方向のうち BTRAN-`L` だけ hyper-sparse 化が構造的に不可能」という欠落も解消する。

**ただし NETLIB93 での改善幅は 1% 前後にとどまる。** m が最大 6000 程度のこの
問題集では、BTRAN の `w` の密度分布が scatter に大きな余地を残していない。
ゲートの発火率(dfl001 で scatter 21246 / gather 11013、25fv47 で 1426 / 2127)が
示すとおり機序自体は実際に働いており、より大きい、あるいはより hyper-sparse な
基底を持つ問題群では効果が大きくなる余地がある。再評価する場合は
`ENOMOTO_BTRAN_L_SCATTER=0` で従来経路に戻して A/B できる。
