# 疎行列表現の集約と、FTRAN/BTRAN/FT更新/LU分解まわりの疎化

対象: 疎表現(CSR/CSC/疎ベクトル)を1ファイルに集約し、そこから計算側を呼ぶ形に
する。その過程で未疎化だった箇所を疎化する。基点 `main` = c442d72(§2.7 FTRAN
結果密度ゲート採用後)。4 コア、rustc 1.94.1、highspy(Python 3.11)、
NETLIB93 **全93問**(`--max-vars` 制限なし)。

## 0. 計測方法

`python -m enomoto_solver.benchmark_highs --max-vars 1000000 --timeout 300` を
各ビルドで **3 回**。比較は

- **status**: 93 問すべてで一致するか。
- **目的関数値**: 3 回の平均どうしの相対差。**ただしこのソルバ自体が問題に
  よっては実行ごとに揺れる**(`SYNTH_CLOCK_FACTOR` の較正が実時間を読むため、
  どの反復で再分解するかが走行ごとに変わりうる)。そこで各問題の「自分自身の
  実行間ばらつき」も併記し、差がその内側かどうかで判断する。wood1p が代表例で、
  同一バイナリを3回走らせるだけで 1e-14 程度揺れる。
- **時間**: 問題ごとの3回の**最小値**の合計。あわせて各群の「走行全体の合計」
  3つを並べ、その散らばり(spread)も出す。**差が spread より小さければ識別
  できていない**、という読み方をする。重い10問が合計の9割を占めるので、
  「重い10問」と「残る83問」に分けた小計も出す。

この箱での spread は概ね ±1〜2.5%。1回の全93問走行は約1分46秒。

> 計測中にコンパイルを走らせてしまった回が1度あり、その回は汚染として破棄して
> 取り直した。以下の数値はすべて、ベンチ実行中に他の負荷をかけていない回のもの。

## 1. 集約: `src/sparse.rs`

クレート内に散っていた疎表現を1ファイルに集めた。

| 型 | 中身 | 置き換えたもの |
|---|---|---|
| `CsrMat` / `CscMat` | `offsets` + フラットな `(index, value)`。相互変換は counting sort 1回 | `simplex` の `FixedRows` |
| `SparseVec` | 疎ベクトル。scatter/gather、dense との内積、prune/canonicalize、`from_dense_tol` による疎化 | 各所の素の `Vec<(usize,f64)>` 操作 |
| `SparseAccum` | エポック印つき疎アキュムレータ (SPA) | presolve 4箇所の `BTreeMap` 行結合 |
| `HybridVec` | fill 次第で疎リスト/密配列を切替えるベクトル | `lu.rs` の `OffDiag` |
| `EpochMarks` | 「このパスで触ったか」集合 | 手書きコピー3つ |
| `CscBuilder` | 列を昇順に吐く生産者向けの直接構築 | (新規) |

faer の `Csr` は presolve の公開インターフェースと `interior_point::kkt` が
使うので残し、`csr_row_iter` / `csr_rows` / `csr_rows_pruned` / `csr_row_vec` /
`csr_col_counts` / `csr_to_csc` を橋渡しに置いた。presolve と kkt に写経されて
いた `col_indices_of_row(i).zip(values_of_row(i))` 約40箇所がここに集約された。

`EpochMarks` への集約は、同じ技法の手書きコピー3つ(`SparseAccum` の占有マップ、
`GpScratch` の Gilbert-Peierls visited 集合、`FtLu::ut_needed`)のうち**ラップ
アラウンドを処理していたのが1つだけ**で、残り2つは 2^32 パス後に古い印が現在の
印として読まれる潜在バグだった、という副産物もあった(`GpScratch` のそれは
FTRAN の reach 集合が黙って欠けることを意味する)。

## 2. 疎化した箇所と計測

各段は「演算を一切変えない(出力ビット一致)まま仕事量だけ減らす」変更として
設計した。したがって計測は速くなったかどうかだけの判定になる。

### 2.1 f6ef405 + cb42e04 — 集約と、presolve/simplex 側の疎化

- presolve の行の線形結合 4 箇所(`freevar`/`aggregator` の重複した `axpy_row`、
  `sparsify` の対象行マージ、`doubleton::rewrite_row`)を `BTreeMap` から SPA へ。
  O(nnz log nnz) + ノードごとのアロケーションが O(nnz) の平坦な配列書き込みに。
  `take_sorted` が列昇順で吐くので、出力の並びも浮動小数の結果も従来と同一。
- `parallelcols`/`dualpropagate` の列ビュー構築を `vec![Vec::new(); n]` + push
  から `CscMat::from_entry_stream` へ(列ごと1ヒープ確保 → 全体で2確保)。
- 基底へのアクセス 4 箇所(`basis_rows_sparse`、`basis_residual_norm`、
  `extended_dual::refactorize`、`residual_norm`)が A の**全行**を走査して非基底
  成分を読んでは捨てていた (O(nnz(A)))。`std.cols` 経由で基底列だけを辿る
  O(nnz(A_B)) に。列を昇順に辿るので各行の成分順序 = LUのピボット順のタイ
  ブレークと残差の加算順序は従来と完全一致する(この不変条件は
  `simplex::freeze_std_matrices` の `debug_assert` に明文化した)。

**結果**: status 93/93 一致。目的関数値 最大相対差 6.2e-16(wood1p、同問題の
自己ばらつき 8.9e-15 の内側)。時間 **-0.31%**(spread +1.04% / +1.77%)。
重い10問 -0.32%、残る83問 -0.25%。→ **識別できない差**。集約が目的の段なので
「回帰していないこと」が確認できれば十分。

### 2.2 bb6e94a — `HybridVec` と `EpochMarks`

eta の消費側は「dense との内積」と「dense への axpy」の2つしかないのに、表現
ごとの `match` が FTRAN/BTRAN と capture 版にまたがって **8箇所**に写経されて
いた。`dot_dense` / `axpy_into_dense` に集約。

**結果**: status 一致、目的関数値ビット一致(= 演算は変えていない)。時間
**+0.31%**(spread +1.77% / +2.44%)。重い10問 +0.35%、残る83問 -0.12%。
→ **識別できない差**。重複除去とバグ修正が目的なので採用。

### 2.3 a7f464f — 単位ベクトル右辺の BTRAN

このクレートの BTRAN の右辺はほぼ全てが単位ベクトル `e_i` (ピボット行 `rho_p`、
DSE重み更新の `rho`、`DseState::from_basis` の m 本の参照解、拡張法の
`trial_row_ratio` と polish 側)。残る密な右辺は `y = B^-T c_B` と
`w = B^-T alpha` の2つだけ。それを長さ m の密ベクトルで渡していたため、非ゼロ
1個を表現するのに O(m) のパスを2本払っていた:

1. `solve_transpose_into` 冒頭の置換 gather `scratch[s] = rhs[col_perm[s]]`
   (ステップごとのランダムアクセス読み) → `fill(0.0)` + 1ストア
2. `u_transpose_solve_into` 冒頭の「z の非ゼロを needed 集合に播く」O(m) 走査
   → そのステップ (`col_perm_inv[i]`) を直接 mark

合成 tick は両経路で同一に課金する。ここを食い違わせると「どの反復で再分解
するか」が変わり、解の軌跡そのものが変わってしまうため(テストで tick の一致も
検証している)。

**結果**: status 一致、目的関数値ビット一致。時間 **-0.77%**(spread +2.44% /
+1.27%)。重い10問 -0.74%、**残る83問 -1.10%**。→ spread よりは小さいが、
軽い83問の小計のほうが問題数が多くノイズが平均化されるぶん信頼できる。
仕事量が厳密に減る変更なので採用。

### 2.4 189f2fd — `l_col` のフラット直接構築 と `fill_count` の O(1) 化

**`LuFactors::l_col` を `CscMat` に。** このフラット化は以前一度試して回帰し
差し戻されているが、その時のポストモーテムが原因と対処を名指しで残していた:
あれは完成した `Vec<Vec<(usize,f64)>>` を後からフラットにコピーする実装だった
ので、消すはずだった「列ごとの小さな Vec」は結局全部作った上に O(nnz) のコピー
が足され、圧縮形のコスト(列アクセスごとに offsets を2回読む)だけ払って利点は
何も買っていなかった。「offsets を1パス、entries を2パス目で直接構築する版なら
まだ見込みがある。今回はその版を作らなかっただけ」と書かれていた。

`CscBuilder` がその版にあたる。このファイルの4つの分解はいずれも L の列を昇順に
吐く(left-looking な消去は step s で列 s を完成させる)ので、**計数パスすら
不要**で、フラットバッファに追記しながら列境界を記録するだけでよい。L 全体で
m+1 個だったアロケーションが2個になり、`l_solve_into` の `for s in 0..m` 走査が
連続領域を舐めるようになる。

**`FtLu::fill_count` を O(1) に。** 再分解トリガー(3)が毎反復これを読むが、実装は
`u_seq` の全要素(長さ m)を舐め直していた。自身のコメントは "`O(1)`-ish" と
書いていたが実際は O(m) で、`u_solve_into` / `u_transpose_solve_into` が本当に
必要としている走査に加えて eta ファイルをもう1周する分だった。更新が触る数箇所で
加減するように変え、`fill_count` には元の総和と一致することの `debug_assert` を
残した(debug ビルドの全テストがこれを検証する)。

**結果(2つ合算)**: status 一致、目的関数値ビット一致。時間 **-1.84%**
(spread +1.27% / +2.08%)。重い10問 **-1.87%**、残る83問 **-1.42%**。
両方の小計で一貫して効いており、これまでで最大の改善。最大の勝ちは最重量問題
`pilot87` の -4.2%(11.62s → 11.13s、絶対値で -0.49s)、次いで wood1p -18.9%、
fit2d -7.0%、grow15 -5.2%。

**内訳** (`fill_count` だけを元の O(m) 総和に戻したビルドを挟んで3回ずつ):

| | 全体 | 重い10問 | 残る83問 |
|---|---|---|---|
| A. `l_col` フラット直接構築のみ | **-1.58%** | **-1.77%** | +0.44% |
| B. さらに `fill_count` を O(1) に | **-0.25%** | -0.10% | **-1.86%** |
| 合算 (A+B) | **-1.84%** | -1.87% | -1.42% |

**2つはきれいに相補的だった。** `l_col` は m が大きく再分解が多い重い問題で
効く (L が大きく、連続領域化とアロケーション削減が効く)。軽い問題では
`l_col[s]` が短く、圧縮形の「列アクセスごとに offsets を2回読む」コストが
相対的に重いため ±0 付近 — これは初回のフラット化が回帰した理由そのもので、
**後付けコピーをやめても消えない固有のコスト**が小問題側には残っている、と
読める。逆に `fill_count` は毎反復の固定費が支配的な軽い問題でこそ効き
(-1.86%)、重い問題はほとんど反応しない (-0.10%)。

したがって「`l_col` のフラット化は勝ちか」への答えは **「重い問題では勝ち、
軽い問題では中立。合算すると勝ち」** であって、無条件の勝ちではない。
`docs/lu_comparison_enomoto_vs_highs.md` §4-5 の「直接構築する版なら勝つ余地」
という予想は、重い問題側については当たっていた。

## 2.5 通し (c442d72 -> 4b586c8) の確定値

段ごとの A/B とは別に、基点と最終形を**各5回**ずつ測り直した。

- **status**: 93/93 一致。
- **目的関数値**: 最大相対差 **7.7e-16** (wood1p、同問題の自己ばらつき 2.1e-14
  の内側)。他92問は全走行でビット一致。
- **時間** (問題ごと最小値の合計):

  | | baseline | HEAD | |
  |---|---|---|---|
  | 全93問 | 49.9135s | 48.9649s | **-1.90%** |
  | 重い10問 | 45.6087s | 44.7485s | -1.89% |
  | 残る83問 | 4.3048s | 4.2165s | -2.05% |

  走行全体の合計は baseline `50.917 / 51.345 / 51.028 / 50.670 / 50.744`
  (spread +1.33%)、HEAD `50.361 / 50.539 / 50.169 / 49.787 / 50.133`
  (spread +1.51%)。**差 -1.90% は spread +1.3〜1.5% と同程度**なので、走行合計
  だけを見るなら「やや速い」以上は言えない。重い10問と軽い83問の小計が独立に
  同方向へほぼ同じ幅で動いていること、および段ごとの A/B で -0.77% と -1.84%
  が別々に観測されていることが、合算の裏付けになっている。

- **HiGHS 比** (5回平均): **2.788x -> 2.731x**。HiGHS 側は全ビルドで同一
  バイナリで 18.27s / 18.38s (この差がこの箱のノイズ下限の目安)。

なお段ごとの A/B は3回ずつで、そこでの通し値は -2.59% だった。5回にすると
両側とも最小値が下がり、baseline 側の下がり幅のほうが大きかったため -1.90% に
落ち着いた。**回数を増やしたこちらを確定値とする。**

置き換えられない。ここは HiGHS のフラット配列 + リンクリスト方式との差が残る。
