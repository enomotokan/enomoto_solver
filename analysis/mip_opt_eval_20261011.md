# MIP の精度と高速化の評価 (2026-10-11)

改善策の一覧は `analysis/mip_survey_20261011.md`。ここには計測の方法と各候補の採否を記録する。

## 計測の方法

- MIPLIB 2017 の 40 問 (`scripts/run_miplib_benchmark.py` の `PROBLEMS`)、1 問 90 秒、`threads=1`。4 問を同時に解く
  (4 vCPU の VM)。時間は `Model.solve` だけ (MPS の読み込み・モデル構築を除く)。
- 指標は shift 10 秒の幾何平均 (SGM、解けなかった問題は 90 秒)。**1% 以上良くなり、誤答がなければ採用**。
- 正しさ: 解けた問題の目的値を参照値と比べる。参照値は MIPLIB の解 (`.sol`) の整数変数を固定し、連続変数を HiGHS の LP
  (許容誤差 1e-10) で解き直して誤差補償つきの和で計算した値 (MIPLIB の `.solu` は 10 桁程度に丸めてあり、許容誤差の
  範囲の違反を含む解から計算したものもあるため。例: binkar10_1 の `.solu` は 6742.1998835、実行可能な解の値は 6742.200024)。
  相対差 1e-9 を超えたら誤答とする。
- ばらつき: 同じコードでも SGM が計測ごとに約 2% 揺れる (misc07 は 52〜69 秒)。さらに、ほかの処理 (コンパイルなど) が
  同時に動くと、`nice 19` でも 15〜35% 遅くなった。そこで計測中は他の処理を止め、ベースは 2 回の計測の問題ごとの
  log(t+10) の平均、1% 以上良く見えた候補はもう 1 回計測して平均で判定した。neos-860300 は同じコードでもノード数が
  280〜2041 と変わり、1 問で SGM が ±1% 動く。
- 探索の経路を変えない候補 (ノード数が同じ) は、純粋に速さの差になる。

## 段階 1: 最適値の相対誤差

| 変更 | 内容 |
|---|---|
| `mip_rel_gap` の既定 1e-4 → 0 (`abs_gap` 1e-6 → 0) | 枝刈りの許容は相対 1e-9 (目的値が整数刻みなら刻み 1 つ分)。サブ MIP は従来どおり 1e-4 |
| 返す解の研磨 (`mip::polish_solution`) | 整数変数をちょうどの整数に丸め、連続変数があれば整数を固定した元の問題の LP を解き直して取り替える。目的値は誤差補償つき (Neumaier) の和で計算し直す |
| 研磨の採否 | 違反が増えず目的値が悪くならないとき、または違反が真に減って目的値の悪化が相対 1e-6 以下のとき (許容誤差の範囲の違反で最適値より良く見えていた解を正す: binkar10_1・qiu で 3e-8・1.5e-9 の誤差が出ていた) |

| | 解けた問題 | 参照値との相対誤差の最大 | SGM |
|---|---:|---:|---:|
| 変更前 (gap 1e-4) | 20 | 3.1e-12 (binkar10_1)、khb05250 2.2e-14 | 35.66 |

## 計測中に見つけて直した不具合

- 研磨の採否が「目的値が悪くならない」を必須にしていたため、許容誤差の範囲の違反で最適値より良く見える解
  (binkar10_1 で 3.3e-8、qiu で 1.5e-9 の相対誤差) を正せなかった。違反が真に減るなら採るように直した。
- lifted cover のカバーの並べ方が許容誤差つきの比較 (推移的でない) で、Rust の sort が panic した
  (`ENOMOTO_MIP_ROW_LIFTED_COVER` の qnet1 など)。厳密な比較にした (既定の経路では使われない)。
