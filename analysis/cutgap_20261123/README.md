## 2. net12: HiGHS の enumeration 前処理

- HiGHS の前処理後の問題を当方に解かせると根の LP 128.31・カットの後 129.99 (HiGHS 130.33 と同じ)。差は前処理。
- `presolve_rule_off` で規則を 1 つずつ切ると、根の LP を 68 → 128 にするのは **kPresolveRuleEnumeration (ビット 16)** だけ (ほかは 128 のまま。
  Probing を切ると 128.29)。HPresolve::enumerateSolutions: 8 列以下の純 0-1 の行 (最大 400 行、重なり 50% 超を除く、空振り 6 回続けばやめる) の割り当てを
  伝播つきで全部書き出し、全部の解で共通の境界・クリーク・2 列の一致 (x = y)・相補 (x = 1 − y) を入れる。net12 では、詰め込みの行の 2 列を相補で置き換えた行
  (例 R0633: a + b + c + d ≤ 1 → a + c ≤ y) が LP を締める。
- 当方にも同じ前処理の試作 `ENOMOTO_MIP_ENUM_PRESOLVE` (既定オフ、`enumerate_rows`) がある。そのままでは 30 行で空振りの上限 (6 回) に当たり、
  見つける組は probing と同じ 35 組で根の LP は 68.40 のまま。**行の数・空振りの上限を外す** (`ENOMOTO_T_MIP_ENUM_ROWS=100000 ENOMOTO_T_MIP_ENUM_FAILS=100000`) と
  953 行・0.05 秒で 154 組・6 固定、**根の LP 128.29・カットの後 129.72** (HiGHS 並み)。
- HiGHS が同じ上限で止まらないのは、行の並べ方 (列のクリークの含意の数の積で並べる) と、クリークを足しただけでも「空振りでない」と数えるためと見る
  (当方は固定・締め付け・組だけを数える)。

## 3. istanbul-no-cutoff: SCIP の前処理 (probing と linear の繰り返し) と cmir

- 整数列は 30 本だけ (連続 5252 本)。SCIP の根は 66.83 → 132.29 (53 ラウンド)。
- SCIP の分離器を切る (allsep・aggregation・cmir・flowcover・impliedbounds・mixing・gomory): cmir を切ると 88.3、aggregation 全体で 78.1、ほかは 115〜140。
  効くのは **cmir** (6730 本)。
- SCIP の前処理を切る (presolving/maxrounds=0) と根の LP 51.11・カットの後 79.21 (当方 71.0 に近い)。前処理器を 1 つずつ切ると (カットは切って根の LP だけ)、
  効くのは **probing** (切ると 68.07 → 52.63)。linear を切ると 63.24。SCIP は probing (14294 本の境界の変更) と linear の前処理 (係数の締め 47989・左右辺 21087) を
  13 周交互に回し、締めた連続列の境界で係数を締め、その係数でまた probing が締める。
- SCIP の前処理後の問題を当方に解かせると根の LP 66.83・**カットの後 100.10**。前処理で 71 → 100、同じ問題でのカットの差で 100 → 132。
- 当方は probing で 904 本の境界を締めるが、固定が 0 本なので「プロービングの後の前処理のかけ直し」を飛ばす (`ENOMOTO_T_MIP_PRR_MIN_FIXED` 1)。
  `ENOMOTO_T_MIP_PRR_MIN_FIXED=0 ENOMOTO_T_MIP_PRR_MIN_ROW_FRAC=0 ENOMOTO_T_MIP_PROBE_REPRESOLVE_MAX=20` で 11 周 (係数の締め 3772・5268・5137・… と減っていく) 回すと
  根の LP 60.94・カットの後 84.22 (71.0 から)。SCIP の 66.83 には届かない (締めた境界の数が SCIP の半分ほど)。
- 同じ問題 (SCIP の前処理後) でのカットの差 (当方 100.1 対 SCIP 132〜137): SCIP に前処理・伝播を切って前処理後の問題を解かせても 136.6 (含意・変数の上下限の
  制約は使えない形)。そこから aggregation を切ると 77.6、cmir を切ると 83.1、flowcover を切っても 135.5。**行の集約の段数** `separating/aggregation/maxaggrsroot`
  を 0 にすると 85.7、1 で 114.9、既定の 6 で 136.6。SCIP の集約 cMIR (連続列を消すために行を 6 本まで足す) が効く。当方の path_highs (HiGHS の path と同じ形)
  は 90 ラウンドで候補 29.8 万本・選ばれた 2716 本・得 5.5、HiGHS 自身も元の問題で 74.4 なので、HiGHS 型の集約では届かない。

## 途中のまとめ

- 「カット」型の 13 問のうち、ここで見た 8 問で根の下界の差がはっきりあるのは 3 問で、3 問とも差の始まりは前処理 (net12: 列挙、istanbul: probing と
  係数の締めの繰り返し、ns1830653: 含意を使う probing)。分離器そのものの差は istanbul の cmir (同じ問題で 100 対 132) と ns1830653 の rows_cmir に残る。
- 計測の注意: survey.sh の計測と、上の切り分けの 1 本ずつの計測は一部重なって回した (どれも 1 スレッド、根の下界は時間にほとんどよらない。当方の根のカットの
  時間の上限 60 秒に当たる net12 の 12 ラウンド目だけは時間による)。

## 8. 適応形 `ENOMOTO_MIP_ENUM_ADAPT` (既定オフ、2026-11-24、利用者の方針「問題によって効き方が違う試作は、却下せずシグモイドで効き方を変える」)

7 節の `ENUM_PRESOLVE=all`・`ENUM_WHERE=loop`・`PRR_TIGHT=1` は net12・istanbul-no-cutoff・ns1830653 の根の下界を大きく上げるが、protoscreen の途中集計で
noswot が 4 スレッドで 2.6 倍、mzzv42z が 1.25 倍遅かった。2 択でなく、周の成果と時間から強さを連続に変える形にした。ビルドはこの節のコミット (pip install -e .)。

### 8.1 害の出どころ

- **mzzv42z: `ENUM_WHERE=loop` の止め方の不具合**。loop は「新しい衝突の組」が出る間は回り続けるが、回の間のプロービング (CLQPRB=d) が含意の表を作り直して
  列挙の組が落ちるので、同じ 728 組を毎回「新しい」と数え、前処理の時間の止め (求解の上限) まで 17 回・60 秒回っていた (`logs/adapt_mzzv42z_t1_enumold.log.gz`、
  1・4 スレッドとも 0 ノードで時間切れ)。**直した** (`ENUM_EDGES_SEEN`: ループの中では回をまたいで見た組を覚えて数える)。直した後も、2 周目からは固定・
  締め付けが少ない (2 周目 315 本・3 周目から衝突の組だけ) のに 1 周 3〜5 秒かかり、かけ直し (PRR_TIGHT) の後の周も含めて前処理が 10 → 34 秒になる
  (`logs/adapt_mzzv42z_t1_enumfix.log.gz`)。害は **繰り返し (列挙とプロービング) とかけ直しが時間を食うこと** で、道筋の違いではない。
- **noswot: 列挙は何も見つけない** (1 行・6 解・固定も組も 0)。それでもプロービングの含意が 2 本増え (clique の辺 58 → 60)、木の道筋が変わる。種 1 では 1 スレッドで
  19.4 → 11.5 秒 (速い)、4 スレッドで 3.4 → 3.4〜5.5 秒。protoscreen の 2.6 倍 (種 3) は道筋の揺れと見る (列挙が何も見つけない問題で、時間は前処理でなく木)。

### 8.2 形

`src/mip/mod.rs` の `enum_adapt_on`・`enum_adapt_continue`。`ENOMOTO_MIP_ENUM_ADAPT=1` は上の 3 つを全部つけ、loop の 2 周目から・かけ直しの前ごとに、直前の周
(loop の 1 回、かけ直しの前はその loop 全体) について

- g = 得 / 列の数 (得 = 固定 + 締め付け + 新しい同値な組。衝突の組は数えない: mzzv42z ではかけ直しで列の番号が変わると同じ組を数え直す)、
- c = その周の秒 / 周の始めの残り時間 (前処理の期限 = 求解の時間の上限まで)、
- s = log10(g / c) (残り時間の割合あたりの得)、f = sigmoid(a (s − b))

を出し、**次の周が直前の周と同じだけ時間を使うとして、その割合 c が f 以下なら続ける** (f は残り時間のうち次の周に使ってよい割合)。続けるときは次の列挙で
並べた行の先頭の f の割合だけを列挙する。得が 0 なら止める (以前の規則と同じ)。PRR_TIGHT の 0.0008 の打ち切りはこの判定に置き換える。時間の上限が無ければ c = 0 で
常に続ける (7 節の形と同じ)。ログは `MIP: ENUM_ADAPT: ...`。

## 9. 適応形の直し (2026-11-24、protoscreen の集計 (analysis/protoscreen_20261124/README.md 9 節) を受けて)

protoscreen の P で enum (7 節の試作) が全種で遅れたのは neos8・nu25-pr12・air03・neos-960392 (どれも既定なら根で解ける 6 秒以下の問題) で、遅れの中身は

(neos8 2431 本。既定でも見つかる) を得に数えていた、(2) 時間の割合 c を残り時間 (約 60 秒) で割るので小さく出て、根で解ける問題の固定費が測れなかった。

### 9.1 直した形 (`src/mip/mod.rs` の `enum_adapt_continue`・`enum_probe_loop`・`enum_presolve_step`・`represolve_after_probe`)

- **得**: 次の周の材料になる成果だけを数える。固定・締め付け (列挙とプロービング。定義域が変わると次のプロービングが新しく見つけうる) と列挙の同値な組。
  プロービングの同値な組は 1 周目は数えず、2 周目からは数える。衝突の組は数えない (8 節と同じ)。
- **時間の割合**: c = その周の秒 / 周の始めの求解の経過時間 (`ENUM_T0`、最初の求解の始め)。根で解ける問題では前処理の固定費がそのまま c に出る
  (neos8 の 1 周目 3.9 秒 / 0.7 秒 = 5.5)。
- **列挙そのもの**: この求解の 2 回目からの列挙は、前の列挙の (得, 秒, 経過時間) で同じ判定をして、止めなら回さない (`ENUM_STEP_LAST`。再スタートの後にも引き継ぐ)。
  得が 0 の列挙の後は回さない (neos8・air03・istanbul・mzzv42z の列挙は最初の 1 回だけになる)。最初の 1 回は回す (下の 9.4)。
- **かけ直し**: 止めの判定なら、PRR_TIGHT でなく既定のかけ直しの規則 (固定の本数・行の 10% の減り) に戻す (8 節の形は止めたらかけ直さなかった)。
- `ENOMOTO_MIP_ENUM_ADAPT=log`: 判定を出すだけで止めない (係数を決めるためのデータ集め)。
