## 0. 要約

**両問題とも 600 s を使い切る主因は同じで、「実行不能行数プラトー検出」(`slope_intercept_dual.rs:2263, 3982-4005`)

- HiGHS は 10,227 反復で 8.8 ms/反復、再分解 51 回 (合成クロック 36、特異疑い 12) = 200 反復に 1 回。

## 3. 原因 1: 実行不能行数プラトー検出の誤発火 → Bland 規則 (両問題共通、最大の原因)

`src/simplex/slope_intercept_dual.rs:2263`
```rust
let infeasible_plateau_limit = (INFEASIBLE_PLATEAU_STALL_MULT * stall_limit).min(MAX_ITERS_FLOOR / INFEASIBLE_PLATEAU_BUDGET_DIVISOR);
```
と `:3982-4005` (「これまでの最小の実行不能行数 `best_infeasible_len` を `infeasible_plateau_limit` 反復更新できなければ
`bland_mode = true`」)。`stall_limit = 5m` (`params.rs:279-282`) だが `MAX_ITERS_FLOOR / 4 = 5,000` で頭打ちなので
(`params.rs:14, 297, 301`)、**m ≥ 250 の全問題で上限は 5,000 反復固定**。

- ex10: 全スラック開始の実行不能行は 204 本 (右辺の大半が 0 で開始点がほぼ主実行可能)。双対単体法では主実行不能
  行数は単調ではなく、反復 2,000 で 10,008、4,000 で 20,952 と増えて (HiGHS でも 197 → 28,822 と増える)、
  「最小値 204」は反復 5,000 まで一度も更新されない → `bland_mode` (base 走行の `iter=6000 ... stall_count=999 bland_mode=true`)。
- square41: 反復 5,054 で発火 (計装ログ `bland_mode entered by plateau at iter=5054 limit=5000 best_infeasible=195 cur=636`)。
  HiGHS のログでも主実行不能行数は 700〜1,600 で振動し続け、最後の数百反復で一気に 0 になる。
- `bland_mode` に入ると chuzr は最小行番号 (`:2632`)、chuzc も全候補ソート (`:3132-3183`) で DSE を捨てるため、
  以後のピボットはほぼ全部が退化 (ex10 base: `stall_count` が反復数と同じ速さで増える) で、**一度入ると段階移行まで
  抜けない**。ex10 は 1,500 s / 38.8 万反復 (3.9 ms/反復) でも未収束、square41 も 600 s で未収束。
- 外すと: ex10 145 s (HiGHS の 0.91 倍の反復数)、square41 760 s。**したがって両問題の「タイムアウト」は 1 反復コストではなく
  この誤発火が主因**。
- 検出器はもともと `pilot4` (実行不能行数が 31 で 16,000 反復静止) と `greenbea` (248/249 で振動) 用
  (`docs/improvement_history.md` L1104-1122, L1924-1975)。「最小値の更新」は双対単体法の進捗の尺度として不適切
  (主実行不能行数は最適解に近づくまで増えてよい)。進捗の正しい尺度は摂動済み費用での双対目的関数 (`Σ theta·d_q` =
  `contribution_base` の累積) で、ex10 でも square41 でも各反復の `contribution` は非零 (`stall_count` は 0〜数十) だった。
  目的関数の累積 (`obj_acc`) は square41 で反復 2,000 に 6.30、4,000 に 7.31、6,000 に 7.76 (HiGHS: 2,184 で 6.11、
  4,116 で 7.31、6,158 で 8.06) と HiGHS と同じ速さで進んでいる最中に Bland に落とされている。

## 4. 原因 2: square41 の 1 反復コスト (23 ms vs HiGHS 8.8 ms) と反復数

### 4.1 再分解が 20 反復に 1 回 (8.7 ms/反復 = 37%)

- トリガはほぼ全部 `bump` (1,582/1,584 回): `slope_intercept_dual.rs:4178`
  `lu.fill_count() > FT_BUMP_LIMIT_FACTOR * m` (`params.rs:53`、64 × 1,754 = 112K 要素)。
  入る列の `alpha` は 1,630/1,754 非零 (93%)、`rho` も 560〜1,460 非零なので、FT 更新 1 回で U eta + R eta に
  2〜3K 要素が積まれ、20 回で上限に達する (`max_update_streak=196` は合成クロック分)。HiGHS は 200 反復に 1 回。
- 再分解 1 回 179 ms (LU 非零 165K → 216K に成長)。うち Markowitz のピボット探索の走査 (`pivot_search scan`) 64 ms
  (探索上限 64 のヒット 49%、候補 46 列/段)、`col_max_abs` の再走査 411K 要素/回。
  **ピボット順の再利用 (`factorize_reusing`、`lu.rs:1624`) は 0 回試行**: 基底に `m` の 50% を超える非零を持つ列
  (`DENSE_COL_FRACTION`、`params.rs:423`) があるため境界付き分解 (`border_wanted`、`lu.rs:1680`、`params.rs:461-465`)
  に回され、`eligible = ... && !border_wanted(...)` (`lu.rs:1632`) で再利用が禁止される。
- A/B (すべてプラトー無効、反復あたりの数値は同じ反復数時点で比較):

| 設定 | 反復 4,000 時点 ms/反復 (再分解 / PRICE) | 反復 10,000 時点 | 完走 |
|---|---|---|---|
| 既定 | 16.8 (6.7 / 6.1) | 21.9 (8.6 / 8.3) | 759.5 s、32,693 反復 |
| `ENOMOTO_T_FT_BUMP_LIMIT_FACTOR=100000` (bump 無効、再分解は合成クロック 330 反復に 1 回) | 11.4 | **13.9 (0.53 / 8.1)**; FTRAN 0.62→0.84、BTRAN 0.37→0.47、未計時 16%→24% | **254.4 s、17,247 反復** (14.5 ms/反復) |
| `ENOMOTO_PIVOT_SEARCH_LIMIT=8` (HiGHS と同じ) | 14.2 (4.9 / 5.6)、LU 非零 165K → 216K | – | (170 s 枠) |
| `ENOMOTO_T_BORDER_MAX_FRACTION=0` (境界付き禁止 → 再利用可) | 再利用 26 試行 5 採用 (19%、fill 超過で棄却 21)、再分解 7.1 ms/反復で**改善なし** | – | (170 s 枠) |
| `ENOMOTO_LU_DENSE_SWITCH=0.3` | 発火 0 回、変化なし | – | (170 s 枠) |
| `ENOMOTO_PRICE_COLUMN=1` (列方向 PRICE) | 20.5 (7.3 / **9.4**) → 行方向より遅い | 25.7 | 700 s で未収束 (26,000 反復、目的関数 7.82 で凍結) |
| bump 無効 + 列方向 PRICE | 16.0 (0.55 / 10.1) | – | **130.0 s、7,838 反復** |

  bump 上限を単に外すと eta 連鎖が長くなって FTRAN/BTRAN/FT 更新 (密 eta の走査) が増えるので、「fill を LU 非零に対する
  比率で判定」または「合成クロックに fill を織り込む」のが筋。再利用は fill 上限 `REBUILD_FILL_LIMIT=1.25` (`params.rs:481`)
  で 8 割棄却されるので、この問題では再利用より探索そのものの高速化 (早期打ち切り、`col_max_abs` の遅延) が効く。

### 4.2 行方向 PRICE の密化 (9.2 ms/反復 = 40%)

- `rho` の非零は 560 (反復 2,000) → 1,460 (反復 32,000、m の 83%)。行方向 PRICE (`slope_intercept_dual.rs:2870-2915`)
  は非零行ごとに行 (平均 2,470 要素) を散布するので要素数 1.6M → 3.8M/反復、**2.4 ns/要素**で 3.8 → 9.2 ms。
  各要素で `touched[j]` の分岐と `touched_cols.push`、`a_p` (24K 要素 = 190 KB) へのランダム散布。
  3.8M 要素 × 12 B = 46 MB/反復の読み出しで L3 に乗らない。
- 列方向 PRICE (S9 `ENOMOTO_PRICE_COLUMN=1`、`rho` 密度 > 0.1 で列ごとの内積、`:2846-2864`) は 8.4〜10 ms と
  行方向より**遅い** (非基底 22K 列 × 182 要素 = 4M 要素の gather を毎回行うため)。HiGHS も密度 0.75 未満は行方向
  (`kDensityForColPrice`) なので、行方向のまま定数を詰めるのが正しい: `rho` 密度が高いときは `touched` を使わず密な
  `a_p` に加算し、最後に非基底列を全部候補にする (HiGHS の `priceByRowSparseResult` → 結果が密になったら index 管理を
  やめて配列に落とす方式)。
- なお列方向 PRICE は加算順が変わって経路が変わり、この問題では反復数が 7,838 (bump 無効時) に減った (§4.3)。

### 4.3 反復数 (既定経路 32,693 = HiGHS の 3.2 倍、経路に非常に敏感)

- 実行不能行数の推移 (既定、プラトー無効): 1,717 → 855 (2K) → 750 (4K) → 758 (6K) → 433 (8K) → 336 (10K) → 328 (12K) →
  316 (14K) → 362 (16K) → 381 (18K) → 326 (20K) → 326 (22K) → 385 (24K) → 352 (26K) → 373 (28K) → 293 (30K) → 378 (32K) → 0 (32,693)。
  **反復 10,000 から 30,000 まで 300〜380 本で停滞**し、最後に一気に収束する。HiGHS は反復 8,000 で 690、10,227 で 0。
- 同じ問題で設定を変えると 17,247 反復 (bump 無効)、**7,838 反復 (bump 無効 + 列方向 PRICE、HiGHS より少ない)**、
  列方向 PRICE のみでは 700 s / 26,000 反復でも未収束になる。目的関数値はどれも一致。
- **tail の正体は双対目的関数のプラトー** (計装の `obj_acc` = `Σ theta·d_q`): bump 無効の走行では反復 6,000 で 7.745、
  8,000 で 7.7979、以後 **16,000 まで 7.7979 のまま** (8,000 反復で 5e-5 未満しか増えない = 1 反復あたり < 6e-9、
  費用摂動 1e-6 より 2 桁小さい)、その後 17,247 で 8.840 に到達。列方向 PRICE のみの走行では反復 8,000 から 26,000 まで
  7.8219 で凍結。HiGHS は同じ 7.8 付近を反復 5,400 で通過して止まらない (5,412: 7.813 → 5,627: 7.878 → 6,158: 8.062)。
  つまり**巨大な双対退化面 (摂動後も `d_q` が 1e-8 級の列が多数) を抜けるのに ours は 1〜2 万反復、HiGHS は数百反復**。
  1 反復の寄与は `STALL_PROGRESS_EPS=1e-9` (`params.rs:36`) を超えるので `stall_count` には現れず (最大 28)、
  一方で健全な区間 (§3) はプラトー検出に引っかかる — 現在の 2 つの停滞検出はどちらも進捗の尺度を誤っている。
- 退化ピボットは 0.03%、`stall_count` は最大でも 28、DSE 重みの相対誤差は 100% が 1% 未満、Harris 窓 1.008、
  BFRT フリップは全体で 0.043 回/反復 (最初の 2,000 反復は 0.5)。退化・DSE 精度・BFRT の不足ではない。
- 経路への感度が極端なのは、係数が全部 1・逸脱が整数格子・`rho` の成分が `±1/k` の形で、**PRICE の `a_p[j]`
  や比率が無限精度では同点になる候補が多数あり、丸めの最終ビットで順位が決まる**ため (列方向 PRICE = 内積の加算順が
  変わるだけで 17K → 7.8K)。HiGHS はここに費用摂動 (列 5e-7) に加えて**行 (双対) 側の摂動 1e-12** を入れ、
  最後に `Perturbation cleanup` で外す。ours の `perturb_costs` (`src/simplex.rs:756-800`) は列側だけで、全列 `c=1`・
  箱型 100% なので `pc = 1 + (1+r)·2·5e-7` を全列に加える (`r` は列番号ハッシュ)。
- 切り分けには「反復 10,000 以降の theta・dj_q・同点候補数・選択行の逸脱の分布」の追加計測が要る (未実施)。
  候補: (a) 双対側 (`x_B` の境界) 摂動の追加、(b) chuzc の同点タイブレーク (現在 `(ratio, j)` の `j` 昇順) を
  `|alpha|` 最大優先に (Harris 第 2 パスの中でさらに `|alpha|` 最大を選んでいるかの確認)、(c) chuzr の `Score2`
  同点 (`LEX_REL_TOL=1e-9`) を `|dev|` 大きい方優先に。

### 4.4 未計時 16% (3.7 ms/反復)

- 再分解直後の `fresh_d_into` (`:1548, 3070`: BTRAN + `O(nnz(A))` = 4.3M 要素) と `compute_rhs`/`resync` (同じく
  `O(nnz(A))`) が 20 反復に 1 回 → 約 0.5 ms/反復。残りは `touched` の消去 (21K 列/反復)、DSE 更新 (`tau` 1,740 非零)、
  `update_verify`、ドリフト検査 (`XB_CHECK_CADENCE=20`) など。策 2 で再分解間隔が伸びれば前者は自然に消える。

## 5. 原因 3: ex10 の 1 反復コスト (6.09 ms vs HiGHS 3.41 ms)

- 入る列の `alpha = B^-1 a_q` が 50K/63K 非零 (80%)、`tau` 53K、`rho` 2.3K: 基底の逆行列が密な問題で、HiGHS も

## 6. 改善策 (優先順)

採用条件は「Netlib93 + Mittelmann 5 問で 10% 超の退行なし、shifted geomean 2% 以上改善」。Netlib は `m ≤ 約 6K`、
1 反復 40〜650 µs なので、規模でゲートできる策はそうし、経路を変える策は A/B を要する。

### 6.1 効果の積算 (見積もり)

- square41: 策 1 で 600s+ → 760 s (最適)。策 2 だけで 254 s (実測、17,247 反復)。策 3 で PRICE 9.2 → ~6 ms、
  策 9/12 で −1 ms → 1 反復 ~10 ms。反復数が HiGHS 並み (策 4、8〜10K) になれば **~100 s** (HiGHS 95 s)。
- ex10: 策 1 で 600s+ → 145 s (最適、HiGHS 90 s)。策 11 で 137 s (実測)。策 5・6・7・8 で −2 ms/反復 →
  1 反復 6.1 → ~4 ms、23.7K 反復で **~95 s**。

### 6.2 実装時の注意

- 策 1 は Netlib の `pilot4`/`greenbea` (プラトー検出の導入理由) と `degen2`/`dfl001` (誤発火の前歴) を必ず個別に確認する。
  `ENOMOTO_T_PLATEAU_LIMIT` のような上書き変数を入れておくと A/B が楽 (本調査の計装と同じ)。
- 策 2/9/10/11 は再分解の時期を変えるので、対象問題以外では発火しないゲート (fill 比率、eta 密度、`m`) を選ぶこと。
  合成クロックの過去の較正 (`docs/improvement_history.md` L2649-2690: `pilot87` が係数 12 で崖) に注意。
- 策 3 は `touched_cols` の順序 (候補の並び) を変えないこと。chuzc1 の候補は `touched_cols` 順に作られ、ヒープ/ソートの
  タイブレークは `(ratio, j)`。
- square41 は経路にきわめて敏感 (同じ問題で 7.8K〜32.7K 反復、プラトーに入るかどうかで決まる) なので、square41 単独の
  改善は経路の偶然でありうる。
  採否は 5 問 + Netlib の総合で判断し、square41 だけの反復数減を根拠にしない。
- 採否判定は `scripts/ab_bench.py` の 93 問 + `scripts/run_mittelmann_benchmark.py --timeout 600`。
  square41 は MPS 700 MB でモデル構築 16 s・メモリ ~3 GB。
