並列 6 セッションのうちの G4。背景は `analysis/mitt600_20261103.md` (186 問・4 スレッド・600 秒で ENOMOTO 68 問、HiGHS 86 問)。

| `ENOMOTO_MIP_HO4_ACFIX` | `interior_rounding` (`src/mip/heur_ipm.rs`) | 費用 0 の根の LP (カット込み) の解析的中心で、大域の境界から TOL 以内の整数列をその境界に大域に固定 (HiGHS の `finishAnalyticCenterComputation` と同じ考え) | `ENOMOTO_T_MIP_HO4_ACFIX_TOL` 1e-6 |
| `ENOMOTO_MIP_HO4_NODECAP` | 木のノードの LP の時間の上限 | 上限を MULT x 主の根の LP の秒 (プロセスで最大) より短くしない | `ENOMOTO_T_MIP_HO4_NODECAP_MULT` 1 |
| `ENOMOTO_MIP_HO4_DIAG` (診断) | ノードの LP・裏のカットの基底 | ノードの LP ごとに反復・秒・状態・上限・全論理変数基底からの解き直しを `HO4DIAG:` で出す | - |

注意 (推測): `ACFIX` は内点法の精度に頼る。境界から 1e-6 以内でも実行可能領域全体でその値とは限らない (HiGHS も同じ許容誤差で固定している)。
600 秒の回と 58 問では誤った「最適」は見ていない (7 節) が、数値的に際どい問題で解を切る恐れは残る。

## 5. 既存の試作の効き目

- `TREE3_DIVECAP`: satellites の再スタートの後の Pump (231 秒) を止めるのに要る (c0 → c0d)。
- `TREE3_CLIQUECAP`・`_JOINCAP` (puriri): tree_close3 と同じく locks のサブ MIP の 81460 で木に入る。それ以上は進まない。
- `ENOMOTO_MIP_TAB_HIGHS_RULES`: カットは疎になるが、puriri のカットの LP の遅さは変わらず、neos-873061 の下界は下がる (110.4 → 105.6)。
- 前処理の組 `pre` (mzzv11): 前処理で 475 行減り根の LP は上がるが、それだけでは 0 ラウンド目で止まって悪くなる。`HO4_CUT0` と一緒で初めて効く。

## 6. 判断と残り

- **既定にはしない**。担当の 4 問で 600 秒で解けた問題はない。
- 既定にする候補として次に確かめたいもの: `HO4_BGNB` (返された基底の置き場所を渡すだけで、satellites で 385 秒 → 0.035 秒。害の筋道が少ない)、
  `HO4_CUT0` (4 問に共通の 0 ラウンド目の打ち切りを避ける。ただし 1 回の LP が長くなる問題はある)、`HO4_NODECAP` (根の LP が 0.5 秒を超える問題だけで働く)。
  `HO4_ACFIX` は効き目が大きい (satellites) が、固定の確かさの検査 (後処理で元の問題の実行可能性を見る回を増やす) が要る。
- 次に調べること:
  1. puriri のカットを足した LP の再分解の重さ (要点 5)。カットの LP を `ENOMOTO_MIP_DEBUG_DUMP_CUT_LP` で書き出し、`cut_lp_debug` で再分解の回数と
     1 回の時間を数える (analysis/lp_hang_20261021.md の手順)。fable-bottleneck-analyst の担当範囲 (LU・FT 更新)。
  2. 再スタートの後の根のカット (satellites -29 対 -25)、neos-873061 のカットの形 (本数が少なく密)。
  3. 木のノードの LP の反復 (satellites の根の子で 13.7 万反復、HiGHS 約 2500)。
  4. mzzv11 の前処理 (HiGHS の probing と clique の統合、presolve_gap_20261022.md の残り)。
